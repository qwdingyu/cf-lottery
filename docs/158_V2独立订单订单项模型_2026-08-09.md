# V2 独立订单/订单项模型

> 日期：2026-08-09
> 目标：一次性落地独立订单/订单项模型，避免后续出现“实施一半、语义继续沿用 V1”的异常。
> 本文为最终决策版，优先级高于 `docs/141`、`docs/155`、`docs/157` 中任何旧的批发/阶梯价表述。

## 0. 结论

V2 的正确形态不是“继续在 `payment_orders` 上加字段”，而是把支付领域拆成三个层级：

1. **参与记录（entry）**：谁参与了活动，只负责参与资格与活动名额，不负责支付订单语义。
2. **订单（payment_order）**：一次购买事实的主实体，独立于 entry 存在。
3. **订单项（payment_order_item）**：一笔订单里每一件商品/卡密的明细行，负责履约、换码、退款、补发。

这意味着：

- 订单不再依赖 `payment_orders.prize_code_id`
- 查单、找回、回调、补发都围绕 `order_id + order_items` 闭环
- `entry_id` 可以保留为来源关联键，但不能再承担“订单唯一性”的业务责任
- 任何保留旧字段兼容读写的做法，都不属于 V2

## 1. 为什么 V1 必须被替换

V1 的问题不在“数量字段不够”，而在**领域边界放错了**：

### 1.1 `entry_id` 承载了过多语义

V1 把这些概念绑在一起：

- 参与资格
- 名额预约
- 支付订单
- 查单入口
- 重试入口
- 回调履约入口

这会导致任何一个边界变化，都可能把别的状态机一起拖坏。

### 1.2 订单级 `prize_code_id` 无法表达真实履约

只在订单头保存一个 `prize_code_id`，会带来三个问题：

- 订单数量大于 1 时，无法表达每一件的独立卡密
- 补发/换码只能覆盖“整单”或“第一张码”，明细账不完整
- 查单/找回需要用 fallback 逻辑拼接，容易静默选错

### 1.3 “半兼容”会制造灾难

如果 V2 只是新增字段，但运行时仍读取旧字段，就会出现：

- 新单按新模型写，旧路径还按旧模型查
- 某些接口看到的是订单头，某些接口看到的是订单项
- 回调成功但前端查不到卡密，或者后台误判已发卡

所以 V2 必须是**一次性切换**，不能做运行时双语义并存。

## 2. 最优方案

### 2.1 领域模型

#### 参与层

`lottery_entries` 只保留参与事实：

- `tenant_id`
- `draw_id`
- `identity_type`
- `identity_value`
- `payment_status`

它只回答“谁参与了、占了多少名额”。订单件数不要放回参与层。

#### 订单层

`payment_orders` 是支付主实体：

- `id`
- `tenant_id`
- `draw_id`
- `entry_id`
- `buyer_identity_type`
- `buyer_identity_value`
- `buyer_display_name`
- `quantity`
- `unit_price_cents`
- `pricing_snapshot_json`
- `amount_cents`
- `currency`
- `status`
- `provider`
- `current_attempt_id`
- `access_token_hash`
- `access_token_expires_at`
- `paid_at`

注意：

- `entry_id` 仅作来源关联，不再是唯一约束的核心
- `buyer_identity_*` 是订单审计快照，不再回查 entry 取身份
- `prize_code_id` 不应继续存在于订单头
- `prize_codes.payment_order_id` / `winner_id` 只能作为发卡审计与追踪冗余，不能作为业务真相；业务读路径必须只认 `payment_order_items.prize_code_id`
- 管理端、找回页、查单页展示购买者时，必须读取订单头快照，不得回读 `lottery_entries` 当前值

#### 订单项层

`payment_order_items` 是明细真相：

- `id`
- `payment_order_id`
- `tenant_id`
- `draw_id`
- `line_no`
- `item_type`
- `title`
- `quantity`
- `unit_price_cents`
- `amount_cents`
- `currency`
- `pricing_snapshot_json`
- `status`
- `prize_code_id`

注意：

- 在 V2 中，每个 `payment_order_item` 代表 1 个可履约单位，`quantity` 固定为 `1`
- 批量件数只体现在 `payment_orders.quantity`
- 如果未来需要套餐或赠品，不要把单项数量改大，应新增 item 或 item_type

这层负责：

- 每一件商品的卡密归属
- 每一件商品的退款/换码
- 每一件商品的审计和查单展示

### 2.2 状态机分层

必须继续坚持“三套状态域分离”：

- `entry.payment_status`：名额与参与生命周期
- `payment_orders.status`：整单支付与履约结果
- `payment_order_items.status`：单件履约结果
- `payment_order_attempts.status`：单次网关尝试结果

禁止在事务外、或用定时任务去“事后推导”某一层状态来修正另一层状态。

> 说明：跨层状态在业务上确实存在“结果一致”的关系（例如“该订单所有明细都已 fulfilled → 整单应视为已履约”）。
> 但正确的做法是**在同一事务内、由同一段业务代码显式地同时落库相关状态**，而不是事后用另一层状态去反推、纠正。
> 强调“禁止推导”的意图，是防止出现“某层状态漏更新后，靠另一层状态在查询时临时拼凑、掩盖脏数据”的写法，
> 而不是禁止在事务内做一致性的联动更新。

## 3. 业务规则

### 3.1 价格

采用 **cliff unit pricing**：

- 命中某阶梯后，本单所有件数都按该阶梯单价计算
- 前端只提交 `quantity`
- 服务端是价格唯一权威

订单必须保存：

- `quantity`
- `unit_price_cents`
- `amount_cents`
- `pricing_snapshot_json`

这样即使运营后来改价，历史订单也不会漂移。

### 3.2 发卡

V2 的履约原则是：

- `quantity = N` 时，必须尝试领取 `N` 个卡密
- 成功：`payment_orders.status = paid`
- 失败：`payment_orders.status = paid_fulfillment_failed`
- 不允许静默部分发放后当作完成

订单项必须按 `line_no` 顺序绑定卡密，不能只靠“第一张码”或 fallback。

### 3.3 查单与找回

公开查单与 OTP 找回都必须走订单项：

- 查单从 `payment_order_items` 反查 `prize_codes`
- 找回按 `buyer_identity_type + buyer_identity_value` 或短期访问令牌定位订单
- 不再依赖 `payment_orders.prize_code_id`
- 后台列表展示购买者信息时，也必须使用 `payment_orders.buyer_identity_*` 快照，而不是 `lottery_entries` 当前身份

### 3.4 回调与重试

支付网关回调的主键仍然是 `payment_order_attempts.id`。

流程必须保持：

1. 校验回调签名
2. 用 attempt 定位订单
3. 校验金额、币种、租户
4. 事务内领取卡密
5. 事务内更新订单项
6. 事务内更新订单头

重试逻辑必须复用同一条订单，不得通过 entry 重新猜测订单归属。
同一 entry 在任意时刻只允许存在一笔在途订单。如果 entry 已在 join 阶段预占 1 件名额，则首次创建订单仅需额外预约 `quantity - 1`；一旦该 entry 已存在前序订单，后续创建必须按完整 `quantity` 预约，并且只能在前一笔订单进入可重试终态（`cancelled` / `expired`）后再次发起；`paid_fulfillment_failed` 与 `paid_late_needs_refund` 只能走运营补发/退款，不得让用户直接再下单，不得把 entry 当成无限多单入口。

## 4. 迁移原则

### 4.1 必须一次性收口

V2 迁移必须做到：

- 运行时不再读取旧字段
- 旧字段只作为迁移输入，不作为业务依赖
- 迁移完成后所有查询都以订单项为准

### 4.2 不能出现的迁移问题

以下做法都不可接受：

- 用固定 `1..20` 序列 backfill 订单项
- 只回填第一张卡密，其他件数静默丢失
- 保留旧字段让新旧逻辑并存
- 迁移成功但查询仍然回落到旧字段

### 4.3 推荐迁移方式

1. 重建 `payment_orders`
2. 新增 `payment_order_items`
3. 以旧订单的 `quantity` 精确生成同数订单项，序列生成必须覆盖任意 `quantity`
4. 把已发卡密精确映射到对应订单项；item title 以活动/商品快照为准，不得回填为买家名称
5. 删除运行时对旧 `prize_code_id` 的依赖

回填明细时必须支持任意 `quantity`，不能写死上限。固定 `1..20` 序列属于错误实现，必须改成递归 CTE 或等价的动态序列生成。
如果旧数据只保留了订单头级别 `prize_code_id`，而无法还原每一件的真实卡密，则迁移必须显式失败或进入人工核验，不得伪造“精确映射”。
换句话说，迁移脚本要 fail closed，而不是“尽量猜一个看起来合理的 item 状态”。

## 5. 关键不变量

### 5.1 必须保持

- 支付回调幂等
- provider 交易号唯一
- amount/currency 由服务端权威计算
- 一笔订单的所有明细要么一起成功，要么进入待补发/失败态
- 订单项与卡密是一对一绑定

### 5.2 必须废弃

- `payment_orders.prize_code_id` 作为运行时真相
- 用 `entry_id` 作为查单唯一键
- 在路由层拼装订单项真相
- 用 `.limit(1)` 处理可能多行的订单集合
- 任何把 `prize_codes.payment_order_id` 当作业务真相的读路径

## 6. 当前实施状态的风险点

当前工作区里的代码还只是部分 V2，不能视为完成品。已暴露的风险包括：

- 还有旧字段引用没清掉
- 管理端订单列表仍可能从 `lottery_entries` 读当前身份，应该切到 `payment_orders.buyer_identity_*`
- 测试还在按旧模型断言
- 历史订单如果只有订单头级别卡密而无法还原明细，需要人工核验或阻断迁移，不能伪造 item 绑定

这意味着现在最重要的不是再加功能，而是先把语义收口。

## 7. 推荐实施顺序

1. 先把 schema 定稿，只保留订单头 + 订单项
2. 再改支付服务，所有发卡都走订单项
3. 再改公开路由，查单/找回不再读旧字段
4. 再改后台列表和补发
5. 再补测试
6. 最后才允许迁移上线

不要跳步。

## 8. 测试矩阵

必须覆盖：

- 同一订单 quantity = 1 / 2 / 10 的回调发卡
- 码池不足时整单失败而不是部分成功
- 订单项恢复与补发
- 订单查单和 OTP 找回
- 旧订单数据回填后的读写一致性
- 并发下的重复回调、重复重试、迟到回调

## 9. 结论

V2 的最优方案是：

> **支付订单做独立主实体，订单项做唯一履约明细，entry 只保留参与事实。**

只要还有任何代码路径在把 `entry_id` 或 `prize_code_id` 当成真相来源，V2 就没有完成。

## 10. 已落地检查点（2026-08-09）

- `payment_orders` 仅保留订单头语义，`payment_order_items` 承担履约真相。
- 创建订单时按 `quantity` 一次性生成对应数量的订单项。
- 支付回调只按订单项领取和绑定卡密，不再读 `payment_orders.prize_code_id`。
- 管理端补发只处理 pending 订单项，不能按订单总数重复补码。
- `prize_codes.payment_order_id` 仅作为审计冗余，不得作为业务真相。
- 同一 `reserved` entry 的并发创建会被门禁拦截，避免重复在途订单。
- 已通过 `npx tsc --noEmit`、`npx vitest run`、`cd frontend && npx vue-tsc -b --pretty false` 验证。
