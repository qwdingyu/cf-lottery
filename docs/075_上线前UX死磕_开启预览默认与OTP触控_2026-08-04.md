# 075 上线前 UX 死磕：开启预览默认与 OTP 触控

> 日期：2026-08-04  
> 原则：死磕用户路径；低成本；有证据；不拆巨页、不改 API  
> 承接：docs/074、docs/055a P1

---

## 一、问题（代码证据）

| 路径断点 | 证据 | 用户感受 |
|----------|------|----------|
| 开启成功后再弹「是否打开用户页？」 | `handleOpen` 用 `askConfirm(adminOpenedWithPreview)` | 复制链接后多一次二元心智；默认应「确认≈预览」 |
| ConfirmDialog 选项能力未接线 | `useConfirmDialog` 有 `askConfirmWithOptions`，但 AdminLotteryView 只绑 `message` | 已有 checkbox API 闲置 |
| 草稿开启失败仅 toast | 列表 draft 行无门禁失败痕迹 | 运营反复点「开启」才看到缺什么 |
| 参与 OTP 输入 34px | `.modal-form input { height: 34px }` 盖过 `.code-input min-height: 44` 意图 | 手机难点、易缩放 |

---

## 二、本轮改动

### 1. 开启 / 创建后预览：默认勾选

- 接好 `ConfirmDialog` 的 `options` / `optionValues` / `update:option`
- `askOpenPublicPreview`：`askConfirmWithOptions` + `openPublic` 默认 `defaultChecked: true`
- 纯函数 `shouldOpenPublicPreview`（可测）
- 文案同步：确认后可预览，可取消勾选

### 2. 草稿门禁失败行内提示

- 点「开启」且 `!canPublish` 时：`draftPublishBlockers[id] = 首条 error 截断`
- 名称列展示「开启前需处理：…」（警告色，不抢 failureReason）
- 通过门禁后 `clearDraftPublishBlocker`
- **不**列表预拉 publish-check（避免 N+1）

### 3. 参与弹窗移动端

- 表单 input：`min-height: 44`、`font-size: 16`（防 iOS 缩放）
- `.code-input`：`min-height: 48`、更大字号
- 窄屏：overlay 底对齐 ≈ bottom-sheet；safe-area；主按钮全宽 48px

### 4. 可测

- `admin-list-ux.ts`：`shouldOpenPublicPreview`、`draftPublishBlockerSnippet`

---

## 三、刻意不做

- 不批量预检所有 draft（成本高）
- 不改 publish / join API
- 不重写 AdminLotteryView / LotteryView
- 不做 Product Tour

## 四、验收

```bash
npx tsc --noEmit
npx vitest run
npm run type-check:frontend
npm run frontend:build
```

人工路径：

1. 草稿缺奖项点开启 → 行内出现「开启前需处理」+ toast/进编辑  
2. 开启成功 → 弹窗默认勾选「打开用户页」→ 确认新标签预览  
3. 手机宽：参与邮箱/OTP 输入 ≥44px，键盘不挡底栏 safe-area
