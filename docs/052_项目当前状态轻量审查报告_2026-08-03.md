## 二、总体判断

代码结构整体是清晰的：`admin / public / platform / auth` 分层明确，Drizzle ORM 用得比较一致，核心流程也有测试覆盖。当前没有发现必须立刻阻断发布的 **CRITICAL** 问题。

## 三、发现

### 1. 高风险：`my-result` / `cancel` 没有速率限制，6 位验证码可被持续试探

| 位置 | 问题 |
|------|------|
| `src/routes/public-lottery.ts:610-731` | `POST /draws/:slug/my-result` 和 `POST /draws/:slug/cancel` 只有验证码校验，没有任何 `checkRateLimit` / `checkDbRateLimit` |
| `frontend/src/views/LotteryView.vue:566-588` | 前端真实调用的是 `/public/draws/:slug/my-result`，不是 `/result` |

影响：
- 这两个接口把 6 位验证码当成唯一门槛，但没有尝试次数控制
- 验证码空间只有 100 万，且代码未在失败时递减有效性，暴力尝试具备现实可行性
- 影响面不只是结果查询，`cancel` 还会影响接龙/预约的参与状态

建议：
- 给 `my-result` 和 `cancel` 补同级别的 IP / 邮箱限流
- 更进一步可在连续失败达到阈值后作废当前验证码，减少试探窗口

### 2. 中风险：公开参与链路仍主要依赖内存 Map 限流

| 位置 | 问题 |
|------|------|
| `src/routes/public-lottery.ts:22-34` | 公开路由的限流实现是模块级 `Map` |
| `src/routes/public-lottery.ts:296-314`、`355-363`、`490-498`、`751-759`、`806-810` | `events / access-code / verify-join / join / result` 都在用这套内存限流 |

影响：
- 在 Workers 多 isolate 场景下，这类限流只能算软约束
- 分布式请求会分散到不同实例，实际拦截效果会比代码里的阈值弱

建议：
- 把公开高频接口的限流也迁到持久层
- 如果要保留内存层，只能把它当作前置缓冲，不能当最终防线

### 3. 低到中风险：Logto 登录回调绕过了统一的 token 写入路径

| 位置 | 问题 |
|------|------|
| `frontend/src/App.vue:35-52` | Logto 回调成功后直接 `localStorage.setItem('admin_token', data.token)` |
| `frontend/src/composables/useAdminAuth.ts:99-105` | 统一的 `setToken()` 会写入过期时间并清理 `impersonated_token` |

影响：
- 这条路径没有走 `useAdminAuth().setToken()`，所以 8 小时 TTL 和模拟登录清理逻辑都被跳过
- 如果浏览器里残留过 `impersonated_token`，新的 Logto 会话可能被旧模拟态覆盖

建议：
- 统一改成走 `setToken()`
- 或至少把 `setToken()` 里的过期和清理逻辑在 Logto 分支补齐

---

## 四、简短结论

这个项目的主干是稳的，整体也符合“轻量、小而美、能落地”的方向。
当前最该优先修的是公开链路的验证码试探面，其次是把公开接口的限流从内存计数升级为可跨实例生效的实现。Logto 登录路径则更像一致性修补，但最好尽快收口。
