# cf-lottery 在日卡营销中的能力边界：发卡 / 核销 / 退群处罚的完整生命周期分析

> 文档编号：114
> 创建时间：2026-08-04
> 目的：回答"抽奖发卡→中转站核销→退群处罚"这条完整链路中，cf-lottery 到底能管到哪一步，产品迭代方向是什么
> 前置文档：111、112（生态）、113（评估）
> 结论一句话：**cf-lottery 管的是"凭证发放到核销之间"的窗口期，管不了核销之后。退群处罚必须区分五个时间点，做五个不同处理。产品只需加一种新状态 + 一个回传事件，就能覆盖所有可处理的阶段。**

---

## 一、问题还原：用户的困惑在哪里

**用户问的核心**：

> 抽奖/刮刮乐发完卡密之后，用户去中转站兑换了额度，这时候退群了，cf-lottery 怎么处罚？我们能解决哪一段的问题？

这触及了之前 111 方案中一个被忽略的边界：**cf-lottery 的活动生命周期（有限、一次性）和中转站日卡营销的运营周期（持续、递延）之间存在时间窗口不匹配。**

---

## 二、两条路径必须分清楚

cf-lottery 实际提供了**两条完全不同的业务路径**，混淆在一起会导致错误设计：

### 路径 A：prizeCodes 抽奖发卡（封闭活动）

```
中转站手工导入卡密 → 进 prizeCodes 表（available）
  → 活动开奖（performDraw）→ prizeCode issued → 用户看到 code
  → 用户拿 code 去中转站兑换额度
  → 活动进入 drawn 状态（"结束"）
```

- 生命周期：**有明确终点的活动**（draft → open → drawing → drawn）
- 时间窗口：开奖是一次性事件
- 发卡时机：**仅在开奖时**（performDraw）
- 发完就"结束"了，没有"后续运营"

### 路径 B：111 日卡归因 + Webhook 通知（持续营销）

```
用户分享链接 ?ref=xxx → 归因成功（shareRecords joinedCount++）
  → cf-lottery webhook 通知中转站 reward.earned { account, amount, eventId }
  → 中转站自己生成兑换码 → 发给用户
  → 退群检测 → cf-lottery 计算波及名单 → webhook 通知中转站 penalty.requested
```

- 生命周期：**无终点的持续运营**（只要社群存在，就可以一直拉新发卡）
- 时间窗口：随时可以触发（归因是实时事件，退群也是）
- 发卡方式：**不发 prizeCodes**，只发 Webhook 通知
- 中转站侧的兑换码由中转站自己管理（生成、面额、有效期、核销）

### 两条路径的关键区别

| 维度 | 路径 A（prizeCodes 抽奖） | 路径 B（111 Webhook 通知） |
|:-----|:------------------------|:--------------------------|
| 发卡动作 | cf-lottery 发卡（available→issued） | cf-lottery 只发 Webhook 通知 |
| 卡密存储 | prizeCodes 表（cf-lottery） | 中转站账务系统 |
| 有效期管理 | prizeCodes.expiresAt（新增字段） | 中转站自己管 |
| 时间窗口 | 有终点（drawn 后"结束"） | 无终点（持续运营） |
| 退群处罚 | revoked prizeCode + webhook | webhook 通知中转站作废 |

---

## 三、退群处罚的五个时间点（这是关键矩阵）

不管走路径 A 还是路径 B，退群可能发生在五个不同的时间点。每个时间点 cf-lottery 能做的不同：

| # | 退群时间点 | 用户的卡密状态 | cf-lottery 能做什么 | 中转站需要做什么 | 实效 |
|:-:|:----------|:-------------|:--------------------|:---------------|:-----|
| ① | 归因成功，但还没开奖 | 没拿到任何卡密 | webhook 通知中转站作废兑换码（路径 B）；阻止 prizeCode 分配（路径 A，如果未开奖） | 作废未发放的兑换码 | ✅ 完全有效 |
| ② | 开奖后、拿到卡密、**还没去中转站兑换** | prizeCode status=issued；中转站兑换码未核销 | **revoked prizeCode（路径 A）**；webhook 通知中转站作废（路径 B） | 作废对应兑换码 | ✅ 完全有效 |
| ③ | 开奖后、拿到卡密、**已经去中转站兑换了额度** | prizeCode status=issued；中转站兑换码已核销（中转站知道，cf-lottery **不知道**） | revoked prizeCode 是无效操作（因为对应的兑换码已经被核销了） | 扣用户余额（核销的是额度，余额还在中转站账上） | ⚠️ 仅中转站能做 |
| ④ | 没中奖（路径 A） | 无 prizeCode | 不需要做任何事 | 不需要 | N/A |
| ⑤ | 路径 B 的归因成功 + 中转站发了兑换码 | 无 prizeCode（cf-lottery 没发卡） | webhook 通知中转站作废兑换码 | 作废兑换码（如果还没核销）；扣余额（如果已核销） | ✅ 未核销有效；已核销仅中转站 |

**核心结论**：
- cf-lottery 管**时间点 ① 和 ②**（凭证发放到核销之间的窗口）
- 中转站管**时间点 ③**（核销之后，余额在主）
- 关键缺失：cf-lottery **不知道**用户什么时候在中转站核销了兑换码 → 不能区分时间点 ② 和 ③

## 四、缺失的闭环：中转站回传核销状态

当前设计中，中转站可以回传 `ext:reward.issued`（发了卡）和 `ext:penalty.executed`（执行了处罚），但**没有回传 `ext:reward.redeemed`（用户核销了兑换码）**。

**这个回传是区分时间点 ② 和 ③ 的关键**：

```
路径 A 的完整闭环：
  中转站导入卡密 → prizeCodes available
  → 开奖 → issued
  → 用户去中转站兑换 → 中转站回传 ext:reward.redeemed { prizeCodeId, redeemedAt }
  → cf-lottery 标记 prizeCode status = redeemed
  → 此时退群 → 检查 status：如果 redeemed → 不管（中转站自己扣余额）；如果 issued → revoked + webhook
```

**这个能力只需两个轻量改**：
1. prizeCodes 状态新增 `redeemed`（与 revoked / expired 同级）
2. 外部事件 API 已支持 `POST /events`（已在当前 PR 中实现），只需中转站多调一次回传

**为什么不是必需项而是增强项**：
- 没有这个回传，cf-lottery 默认把 issued 的卡当做"可能还没核销"，退群时统一 revoked
- 如果用户已经核销了，revoked 是冗余操作（不会让兑换码失效），但也不会有副作用（兑换码已在中转站核销过）
- **真正的风险**：中转站已经扣了余额 + cf-lottery 又发了 revoked webhook → 中转站可能误判为需要再扣一次。**防御：Webhook payload 带 originalStatus 字段，中转站检查状态后再决定是否执行**

## 五、cf-lottery 精确的能力边界（最终答案）

| 能力 | cf-lottery 能做 | 中转站做 | 边界原因 |
|:-----|:---------------|:--------|:---------|
| 归因（谁拉了谁） | ✅ | ❌ | 活动引擎本级能力 |
| 发卡（prizeCodes available→issued） | ✅ | ❌ | 活动引擎本贴能力（抽奖/刮刮乐） |
| 通知中转站发卡（111 路径 B） | ✅ webhook | 生成兑换码 | 兑换码在中转站 |
| 退群波及名单计算 | ✅ | ❌ | 依赖归因链路，中转站可能没有 |
| 撤回未核销卡密（prizeCode revoked） | ✅ | webhook 通知中转站作废 | 双面同步 |
| 撤回已核销额度 | ❌ | ✅ | 已核销 = 账务变更，cf-lottery 无权限 |
| 监控退群 | ❌ | QQ 机器人 | 聊天平台集成 |
| 兑换码有效期 | ❌（路径 B） | ✅ | 中转站账务体系的一部分 |
| 跟踪核销状态 | ✅（需回传） | 回传 | 回传是关键闭环 |

**一句话**：cf-lottery 管"发到没发、发了能不能收回来"；中转站管"收了之后余额怎么样"。中间需要一条回传消息（`ext:reward.redeemed`）来让 cf-lottery 知道"发了的卡已经被用了"。

## 六、产品迭代建议（按优先级）

### 6.1 当前 PR（本次已完成）

| 能力 | 说明 |
|:-----|:-----|
| prizeCodes.expiresAt | 限时卡密过期时间 |
| 券/码统一 revoked 状态 | 退群/违规撤奖/人工作废 |
| 波及名单反查 | activityEvents refCode → 被邀请者列表 |
| POST /events API | 退群上报 / 回传入口 |
| Webhook reward.earned / penalty.requested | 奖励/处罚通知 |

### 6.2 必须补的（P0，下一个 PR）

| 能力 | 说明 |
|:-----|:-----|
| **prizeCode 状态机扩展**：issued → redeemed | 中转站回传核销状态后标记，区分"发了没换"和"发了已换" |
| **POST /events 新增事件类型**：`reward.redeemed` | 中转站核销后回传：`{ prizeCodeId, redeemedAt }` |

### 6.3 可以推后的（P1）

| 能力 | 说明 |
|:-----|:-----|
| prizeCodes 过期自动标记（cron） | 扫描 expiresAt 过期未核销卡密 → expired |
| 退群时根据 redeemed 状态做不同处理 | 当前默认全 revoked（冗余但无害），未来区分处理 |

### 6.4 不需要做的

| 事项 | 原因 |
|:-----|:-----|
| cf-lottery 管理兑换码核销账务 | 在中转站 |
| cf-lottery 主动查询中转站核销状态 | 同步调用不可靠，回传才是正确模式 |

## 七、结论

1. **cf-lottery 能管的**：卡密从 available → issued → revoked 的**全部状态**，和从 issued → redeemed 的**状态标记**（需中转站回传）。退群在核销前发生 → revoked 有效。退群在核销后发生 → 中转站自己处理。

2. **当前系统缺的**：prizeCode 没有 `redeemed` 状态（不知道卡被用没有），中转站没有 `reward.redeemed` 回传事件。**只需加这两个轻量能力，整个闭环就完整了。**

3. **不要混淆路径 A 和路径 B**：路径 A（prizeCodes 抽奖）是封闭的、一次性的事件；路径 B（111 Webhook 通知）是持续的运营引擎。退群处罚对两条路径都有效，但机制不同——路径 A 通过 prizeCode 状态机撤回，路径 B 通过 Webhook 指令撤回。

4. **产品方向**：当前 PR 的 4 个 P0 扩展（事件 API / Webhook / expiresAt+revoked / 波及名单）+ 本文档提出的 redeemed 状态 + reward.redeemed 回传 = **日卡营销全链路闭环完成**。之后可以按 113 的路线，把这些能力产品化为可售卖的玩法包。
