# 205 容量与边界处理机制——行业最佳实践对比评估

> 日期：2026-08-12
> 评估对象：docs/204 梳理的 10 类超额/不足场景的防护机制
> 方法：对比行业通用实践（秒杀架构、库存扣减、分布式锁模式），评估当前设计是否最优，指出潜在问题

---

## 0. 评估框架

| 维度 | 评估标准 |
|:-----|:---------|
| 正确性 | 是否保证不超发、不超卖、不重复发放 |
| 一致性 | 是否保证数据最终一致（事务内 / 最终一致） |
| 性能 | 是否在高并发下保持可接受的吞吐 |
| 可运营性 | 异常后是否可恢复（人工/自动） |
| 简洁性 | 是否过度设计，是否易于理解和维护 |

---

## 1. 即时抽奖（Instant Spin）—— `awardedCount < winnerCount` CAS

### 1.1 当前设计

```
先取码 → 再 CAS 占用奖档名额（awardedCount + 1 WHERE awardedCount < winnerCount）
→ CAS 失败时释放已取码
```

### 1.2 行业最佳实践对比

| 维度 | 当前设计 | 行业最佳实践 | 评价 |
|:-----|:---------|:------------|:-----|
| 名额控制 | `awardedCount < winnerCount` CAS | 同样使用 CAS 乐观锁（或 Redis 原子计数器） | ✅ 一致 |
| 取码 vs 占名额次序 | **先取码，后 CAS** | 先锁名额，后取码（或同时） | ✅ **当前次序更优**——先取码确保有货，再 CAS 占名额；如果先 CAS 后取码但码不足，会导致"名额已占但无货"的幻象 award |
| 并发安全 | SQLite 事务串行化 | MySQL/PostgreSQL 需行锁或分布式锁 | ✅ SQLite 单写者下 CAS 足够安全 |
| 性能 | 每次 spin 1-2 条 SQL | Redis 原子计数器 + 异步落库 | ⚠️ 当前方案在 SQLite 下性能足够（~1000 req/s），但扩展性受限于 SQLite 单写者 |

### 1.3 优化建议

**无**。先取码后 CAS 的次序是行业最佳实践，SQLite 下 CAS 是标准做法。

## 2. 卡密领取（Prize Code）—— 循环领取 + 原子回滚

### 2.1 当前设计

```typescript
for (let i = 0; i < quantity; i++) {
  // 逐条子查询 LIMIT 1 领取
  UPDATE prizeCodes SET status='issued', ... 
  WHERE id = (SELECT id FROM prizeCodes WHERE status='available' LIMIT 1)
  RETURNING id;
  // 不足时回滚已领卡密
}
```

### 2.2 行业最佳实践对比

| 维度 | 当前设计 | 行业最佳实践 | 评价 |
|:-----|:---------|:------------|:-----|
| 领取方式 | **循环逐条领取**（N 条 SQL） | 批量领取（一条 SQL 领取 N 个） | ⚠️ **当前方式有性能分发**——quantity=100 时 100 条 SQL。但 SQLite 不支持 UPDATE ... RETURNING ... LIMIT N，所以是 SQLite 限制导致的折中 |
| 库存锁定时机 | **支付回调时领取**（不预占） | 下单时**预占库存**（reserved），支付时扣减 | ⚠️ **当前方式可能导致"用户已付款但卡密不足"**（FULFILLMENT_FAILED）。虽然是源头扼杀预检，但不锁定库存，并发下仍可能不足 |
| 部分领取处理 | **全量回滚**（不部分发放） | 同——部分发放导致运营混乱 | ✅ 不半单发放是标准做法 |
| 领取失败兜底 | `FULFILLMENT_FAILED` → 可补发 | 同——标记失败后可人工/自动补发 | ✅ 可补发是最低要求的兜底 |

### 2.3 优化建议（P2）

**建议：下单时预占卡密库存（reserve），而非回调时才领取。**

```typescript
// 下单时（createPaymentOrder 事务内）：
const reserved = await UPDATE prizeCodes SET status='reserved', orderId=?
  WHERE id = (SELECT id FROM prizeCodes WHERE status='available' LIMIT quantity)
  RETURNING id;
// 不足时回滚并拒绝下单

// 回调时（handlePaymentCallback 事务内）：
UPDATE prizeCodes SET status='issued', ... WHERE orderId=? AND status='reserved'
```

**优点**：彻底消除"付款后卡密不足"的 FULFILLMENT_FAILED 场景。
**代价**：需要新增 `reserved` 状态 + 超时释放 reserved 卡密的定时任务。改动较大，P2 优先级。

## 3. 秒杀名额预约（Flash Sale）—— `activeParticipantCount + δ ≤ capacity` CAS

### 3.1 当前设计

```sql
UPDATE lottery_draws SET activeParticipantCount = activeParticipantCount + reserveQuantity
WHERE drawId = ? AND activeParticipantCount + reserveQuantity <= capacity
```

### 3.2 行业最佳实践对比

| 维度 | 当前设计 | 行业最佳实践 | 评价 |
|:-----|:---------|:------------|:-----|
| 名额控制 | 行级 CAS（单字段计数器） | 同——MySQL 行锁 / Redis 原子计数 | ✅ CAS 是标准做法 |
| 容量计算 | `resolveEffectiveStockLimit(flashSale, maxParticipants)` | 同——明确名额来源 | ✅ 设计清晰 |
| 批量预约 | `reserveQuantity = quantity 或 quantity-1`（base 1 已在 join 时计入） | 同——首次 base 1 预占，追加全额预约 | ✅ 设计合理 |

### 3.3 优化建议

**无**。名额 CAS 是行业标准做法，SQLite 下单写者无需额外锁。

## 4. 参与活动（Join Draw）—— `activeParticipantCount < maxParticipants` CAS

### 4.1 当前设计

```sql
INSERT INTO lottery_entries SELECT ... WHERE (
  SELECT activeParticipantCount FROM lottery_draws WHERE drawId = ?
) < maxParticipants
```

### 4.2 行业最佳实践对比

评价：**标准做法。** 先检查再插入保证了原子性，与 MySQL 下的 `SELECT ... FOR UPDATE` + INSERT 等价（SQLite 单写者无需 FOR UPDATE）。

### 4.3 优化建议

**无。**

## 5. 限购（Per-User Limit）—— 累计检查

### 5.1 当前设计

```typescript
const alreadyBought = SUM(PAID + FULFILLMENT_FAILED orders.quantity);
if (alreadyBought + quantity > maxPerUser) reject;
```

### 5.2 行业最佳实践对比

| 维度 | 当前设计 | 行业最佳实践 | 评价 |
|:-----|:---------|:------------|:-----|
| 统计口径 | `PAID + FULFILLMENT_FAILED` | 含 `PENDING`（下单即占限购额度） | ⚠️ **当前口径不含 PENDING**——用户可创建 PENDING 订单后不支付，不占用额度。但 `existingOrder` 去重防止了同时有多个 PENDING，所以风险可控 |
| 统计范围 | 同一 entry 在同一 draw 下 | 同一身份（identityValue）在所有 entry 下 | ⚠️ **当前按 entry 统计**——同一用户用不同邮箱参与多个 entry，每个 entry 都有独立的限购额度。但直付秒杀中 entry 是 joinDraw 创建的，每个 entry 对应一个用户身份，所以实际等价于按身份统计 |
| 并发安全 | 事务内统计 | 同——事务内统计避免并发超限 | ✅ SQLite 串行化事务安全 |

### 5.3 优化建议

**无。** 当前设计在 SQLite 单写者下是安全的，且与业务语义一致（每个 entry 限购 N 件）。

## 6. 活动过期释放（Expired Release）—— expireOverdueOrders

### 6.1 当前设计

```typescript
// 定时任务/下单前触发，清理超时 PENDING 订单
// 事务内释放订单 + 释放名额 + 释放 entry
```

### 6.2 行业最佳实践对比

| 维度 | 当前设计 | 行业最佳实践 | 评价 |
|:-----|:---------|:------------|:-----|
| 触发时机 | **下单前触发** + 定时任务 | 定时任务 + 查询时被动检查 | ✅ 下单前触发减少"过期但未清理"的窗口 |
| 超时时间 | 系统配置 `payment_order_timeout_minutes`，默认 30 | 同——可配置超时时间 | ✅ |
| 候补递补 | **不触发递补** | 释放时自动递补候补用户 | ⚠️ **存在优化空间**——当前释放名额后，候补用户不会自动激活 |

### 6.3 优化建议（P2）

**建议：名额释放时触发候补递补。** 在 `expireOverdueOrders` 中，释放名额后检查是否有候补用户，如果有则自动递补。

```typescript
// expireOverdueOrders 事务内，释放名额后：
const waitlist = SELECT ... FROM lottery_entries WHERE status = 'waitlisted' ORDER BY joinedAt LIMIT 1;
if (waitlist) {
  UPDATE lottery_entries SET status = 'reserved' WHERE id = waitlist.id;
  UPDATE lottery_draws SET activeParticipantCount = activeParticipantCount + 1 WHERE drawId = ?;
}
```

## 7. 多奖品保护（Multiple Prize）—— fail-closed

### 7.1 当前设计

```typescript
if (rows.length > 1) {
  // fail-closed 返回 null，不发放任何卡密
  console.error("[payment] 活动配置了多个卡密奖品");
  return null;
}
```

### 7.2 行业最佳实践对比

| 维度 | 当前设计 | 行业最佳实践 | 评价 |
|:-----|:---------|:------------|:-----|
| 多奖品处理 | `fail-closed` 返回 null，不发放 | 选择第一个奖品，或按权重分配 | ⚠️ **当前方式过于严格**——运营配置错误时，所有用户都拿不到卡密 |
| 发布预检 | 发布时阻断多奖品配置 | 同——发布预检应阻断多奖品 | ✅ 发布预检是第一道防线 |

### 7.3 优化建议

**运行时建议改为按权重/顺序选择第一个奖品，而非 fail-closed。** 发布预检已阻断多奖品配置，运行时的 fail-closed 是过度防御。改为 `rows[0]` 即可（按 `sortOrder` 排序取第一个）。

## 8. 整体架构评估

### 8.1 与行业标准的对比总表

| 维度 | cf-lottery 当前 | 行业标准（如秒杀系统） | 差距 |
|:-----|:---------------|:---------------------|:-----|
| 库存扣减 | 下单占名额，回调时领取卡密 | 下单时锁定库存（reserved），支付时扣减 | ⚠️ 当前方式有 FULFILLMENT_FAILED 窗口 |
| 容量控制 | CAS 乐观锁 | CAS 乐观锁 / Redis 原子计数器 | ✅ 一致 |
| 超时释放 | 事务内释放订单+名额+entry | 同 | ✅ 一致 |
| 候补递补 | 手动触发 | 自动递补 | ⚠️ 有优化空间 |
| 多奖品保护 | fail-closed | 按权重/顺序分配 | ⚠️ 可适当放宽 |
| 限购统计 | 按 entry 统计 | 按身份（identity）统计 | ✅ 当前场景下等价 |
| 幂等保护 | idempotencyKey UNIQUE | 同 | ✅ 一致 |
| 数据库 | SQLite 单写者 | MySQL/PostgreSQL/Redis | ⚠️ 扩展性受限于 SQLite，但当前规模足够 |

### 8.2 结论

**整体设计处于行业中等偏上水平。** 核心的 CAS 乐观锁、原子回滚、事务内释放等机制都是行业标准做法。主要差距在两个方面：

1. **卡密领取时机**（P2 优化）：下单时预占库存可消除 FULFILLMENT_FAILED 窗口
2. **候补递补自动化**（P2 优化）：释放名额时自动递补候补

这两个优化都是有价值的，但不是 P0 级别的缺陷（当前机制已通过 FULFILLMENT_FAILED 和手动补发兜底）。

### 8.3 未发现的新问题

**本次评估未发现新的致命漏洞或设计缺陷。** 当前设计在 SQLite 单写者约束下是合理的，所有超额/不足场景均有至少两层防护（CAS + 事务回滚），且资金安全相关路径有额外源头扼杀预检。
