## 一、系统全景

cf-lottery 是一个**多租户、可白标、可嵌入的活动引擎平台**。系统由 46 张本地数据库表 + 3 张 cf-core 导入表构成，覆盖活动生命周期管理、支付订单、卡密发放、裂变传播、奖励发放、兑换核销、平台消息投递、处罚管控等 13 个业务域。

**核心设计理念**：
1. 三个独立维度配置（participation_mode × experience_type × result_mode），互不可推导
2. 三层防超发架构（幂等标记 → 出口 CAS → 总量约束）
3. 多租户纵深防御（所有查询带 tenantId）
4. 确定性/不确定失败分类（防资金黑洞）

## 三、活动生命周期

```
创建活动(draft)
 ├── 发布预检 → publishDraw(draft→open) [CAS: WHERE status='draft']
 ├── open（进行中）
 │   ├── 暂停 → paused → 恢复 → open
 │   ├── 开奖中 → drawing → drawn
 │   │   [scheduled: Cron processDueDraws 自动触发]
 │   │   [manual: 管理员手动触发]
 │   └── 取消 → cancelled
 └── cancelled（终止运营）
```

**创建校验链**：标题非空 → startAt < endAt → scheduled 必须设 drawAt → lottery 必须 winnerCount ≥ 1 → instant 必须 maxSpinsPerEntry ≥ 1 → 密码模式 SHA-256 哈希 → 租户配额检查 → publicSlug = UUID 前 8 位（冲突重试 3 次）

**发布预检**：7 大检查域（basic/participation/prizes/promotion/payment/webhook/activity_config），共 80+ 校验项。

## 四、支付与订单系统

### 4.1 三态隔离

| 状态域 | 所在表 | 语义 |
|--------|--------|------|
| `lottery_entries.payment_status` | entries | 名额与参与生命周期（NONE/reserved/pending/paid/expired） |
| `payment_orders.status` | orders | 逻辑订单支付与履约 |
| `payment_order_attempts.status` | attempts | 单次网关交易结果 |

**设计原则**：不允许用 payment_orders.status 的字符串直接判断 lottery_entries.payment_status。两套状态域语义独立。

### 4.2 完整状态机

```
payment_orders.status:

 pending ── 支付成功+发卡成功 ──→ paid
 │         支付成功+发卡失败 ──→ paid_fulfillment_failed
 │         超时未支付 ──→ expired
 │         网关确定性失败 ──→ cancelled
 │         迟到回调 ──→ paid_late_needs_refund
 expired ─── 用户重试 ──→ pending（新 attempt）
 cancelled ─── 用户重试 ──→ pending（新 attempt）
 paid_fulfillment_failed ─── 运营补发成功 ──→ paid
 paid / paid_fulfillment_failed / paid_late_needs_refund ──→ refunded
```

### 4.3 支付渠道抽象

通过 `@usethink/cf-pay` 包实现渠道抽象（easypay/stripe/alipay），核心能力：
- `PAYMENT_PROVIDER_CATALOG` 静态渠道目录
- `loadTenantConfig()` 从 `tenant_configs.providers` 读取租户级配置（敏感字段加密存储）
- 支持 `requireDirectFulfillment` 过滤（直付路由只取支持自动发卡的渠道）
- 支持 `allowDisabled` 模式（恢复在途订单/退款时停用渠道仍可验签）

### 4.4 预占-确认两阶段卡密

```
下单阶段 reservePrizeCodes():
  available → reserved（CAS 原子更新）
  不足时回滚已预占卡密

回调阶段 confirmPrizeCodes():
  reserved → issued
  不足时回滚已确认卡密

兜底路径 acquirePrizeCodes():
  confirmPrizeCodes 不足时触发
  直接从 available → issued
```

### 4.5 超时释放机制

懒清理模式（Lazy Cleanup），在创建订单前、查询订单摘要前、定时 cron 被动触发：
- 从 systemConfig 读取 `payment_order_timeout_minutes`（默认 30 分钟）
- 入口释放三级策略：有 PAID/FF 订单 → 保持 paid；有 PENDING → 保持；无其他有效订单 → expired + 释放名额
- 释放预占卡密（reserved → available）

### 4.6 退款流程

前置校验：有 redeemed 卡密时拒绝（"钱退人、卡被用"双重损失）。
事务内：order→refunded、attempt→refunded、items→refunded、卡密→revoked（保留审计）、入口三级释放策略。
测试覆盖：7 个用例（viewer 403、正常全链路、跨租户隔离、幂等拒绝、redeemed 拒绝）。

## 五、邀请、裂变与排行榜

### 5.1 数据流全景

```
分享者生成 shareCode (POST /share)
 │
 ▼
被邀请人带 refCode 参与 (joinDraw)
 │
 ├─ 1. recordAttributedJoin() ─── shareRecords.joinedCount + 1
 │
 └─ 2. maybeTriggerReward() （归因成功后，与 joinDraw 同事务）
     │
     ├─ [路径1] grantViralSpinsToSharer() ─── instant 每邀请 +N spins
     ├─ [路径4] processReferralRewardsEngine() ─── engine 里程碑奖励
     └─ [路径5] triggerRewardEarned() ─── 配额校验 + Webhook入队
```

### 5.2 归因链路（recordAttributedJoin）

1. 通过 refCode 查 shareRecords
2. **自邀请防御三层**：entryId 比对 → identityType/identityValue 跨类型证明 → 签到活动剥离日期后缀
3. `shareRecords.joinedCount + 1`（SQL 条件更新）
4. 写 activityEvents: attributed_join

### 5.3 三重防超发架构

```
第一重（幂等层）: rewardMilestonesGranted JSON 数组
  → 整标记 = 已足额发完，跳过
  → 部分标记 rewardId:N = 续发差额

第二重（出口 CAS）: grantBonusSpin 的 spinsTotalGranted 乐观锁
                  grantBonusCoupon 的 couponCodes.status='available' 原子更新

第三重（总量约束）: maxSpinsPerEntry 硬顶（bonus_spin）
                  couponCodes 码池可用性（bonus_coupon）
```

### 5.4 引擎里程碑（referral-rewards-engine）

**配置校验**：单一真相原则 — `validateReferralRewardDef()` 是唯一实现，normalizeReferralRewardDefs 和 collectReferralRewardDefIssues 共用。

**金额安全解析**：与引擎 decimal.js 严格对齐，排除带空格（" 5 "）、布尔、百分号（"5%"）、空串、科学计数法（"1e3"）。

**conditions 字段白名单**：`totalJoinedCount, activityKind, eventValue, eventType`。算子白名单：`GTE/GT/LTE/LT/EQ/NE`。

### 5.5 排行榜

- **全量排名再截 Top20**：myRank 在全量上计算，未进榜也是真实名次
- **同票 tie-break**：邀请数降序，同票按 entryId 字典序稳定排序
- **P0 修复**：按 sharerEntryId 聚合 joinedCount 后每名次只发一次（旧实现按行发放导致超发）

### 5.6 shareRecords.joinedCount 设计限制

joinedCount 是聚合计数器，不存每个被邀请者的 entryId 明细。退群处罚需要反查 `activityEvents WHERE refCode IN (...) AND eventType='attributed_join'`。

## 六、秒杀与批量场景

### 6.1 两种秒杀模式

| 模式 | paymentRequired | 支付处理 | 适用场景 |
|------|----------------|---------|---------|
| 展示/导流壳 | false | 外部系统 | 导流到 cf-shop 等外部商城 |
| 直付发卡 | true | cf-lottery 内部 EasyPay/ZPay | 站内秒杀发卡 |

### 6.2 阶梯定价（批发优惠）

```typescript
pricingTiers: Array<{
  minQuantity: number;   // 起购数量（首档必须为 1）
  unitPriceCents: number; // 阶梯单价（分）
  label: string;          // 阶梯名称
}>
```

按 minQuantity 升序匹配，取不超过购买数量的最高阶梯。服务端计算权威金额，前端不提交金额。

### 6.3 flash-sale-rush 模板

- activityKind = claim（非 lottery）
- experienceType = flash_sale
- resultMode = instant
- 默认 priceCents=990、maxPerUser=5、stockLimit=100
- 配置要求：必须配置 priceCents + EasyPay/ZPay 支付设置 + 单一卡密码池

### 6.4 批量删除（batch-delete）

| 模式 | open/drawing 处理 | 订单处理 |
|------|-------------------|----------|
| force=false（默认） | 计入 failed | 不清理 |
| force=true | 放行 open/drawing | 所有订单均为 expired 时清理；有资金痕迹则 fail-closed |

**级联删除顺序**：先子表后主表（payment_order_items → payment_order_attempts → payment_orders → ... → lottery_draws），有外键依赖关系。

**支付数据保护**：只要存在任一非 expired 订单，即抛出 `DrawDeletionBlockedError`。

## 八、处罚机制

退群处罚是一个**纯查询模块**（不修改任何数据），计算波及名单：

```
步骤 1：定位退群者（lotteryEntries 按 identityValue 查找）
步骤 2：找邀请人（attributed_join 事件 → refCode → shareRecords.sharerEntryId）
步骤 3：找被邀请者（shareRecords → shareCode → activityEvents WHERE refCode IN (...))
```

**为什么用 activityEvents 而不是 shareRecords 查被邀请者**：shareRecords.joinedCount 是聚合计数器，不存明细。activityEvents 的 attributed_join 事件每条记录一个 entryId 和一个 refCode。被邀请者查询有 `.limit(500)` 安全上限。

## 九、CAS 乐观锁全面覆盖

| 位置 | CAS 条件 | 保护目标 |
|------|----------|----------|
| grantBonusSpin | spinsTotalGranted == 旧值 | 防止裂变/里程碑重复加次 |
| grantBonusCoupon | couponCodes.status='available' | 防止同一张券发两人 |
| grantLeaderboardRewards | leaderboardRewardedAt='' | 防止排行榜重复发放 |
| markRewardIdsGranted | rewardMilestonesGranted==旧值 | 防止幂等标记覆盖 |
| performInstantSpin 扣次 | spinsLeft >= 1 | 防止次数超扣 |
| performInstantSpin 奖档 | awardedCount < cap | 防止名额超发 |
| performInstantSpin 取码 | prizeCodes subquery UPDATE | 防止同一码双发 |
| flash-sale 活动级 | activeParticipantCount < max | 防止秒杀超卖 |
| flash-sale entry 占位 | paymentStatus=EXPIRED 二次校验 | 防止并发抢占同一 entry |

## 十一、数据流走向总览

### 11.1 抽奖类（lottery + manual/scheduled）

```
创建(draft) → 发布预检 → 发布(open)
 → 用户参与(join) → entries + activity_events(participation_completed)
 → [viral 裂变] → share_records + 邀请者加权/加次
 → [定时/手动开奖] → performDraw → winners + prize_codes(issued)
 → email_deliveries → 中奖通知/安慰券
 → webhook_deliveries(draw.completed/prize.issued)
```

### 11.2 即时开奖类（lottery + instant）

```
创建(draft, maxSpinsPerEntry≥1) → 发布 → 用户参与(join) → entries(spinsLeft=initial)
 → 每次 spin → performInstantSpin 事务
 → lottery_spins(幂等) → winners(if won) + prize_codes(issued)
 → [pity 保底] consecutiveNoWinSpins >= threshold → 强制中奖
 → [dailyFreeSpin] 每日首次进入自动 +count
 → [裂变加次] → grantViralSpinsToSharer → +N spins
```

### 11.3 直付秒杀（claim + flash_sale + paymentRequired）

```
创建 → flashSale.stockLimit/priceCents
 → 发布预检(支付+卡密+库存) → 发布(open)
 → 用户参与 → entries + payment_status=reserved → CAS activeParticipantCount++
 → 创建支付单 → orders(pending) + items + attempts
 → 支付成功回调 → orders(paid) → 发卡
 → prize_codes(issued) + items(fulfilled)
 → 超时未付 → cron expireOverdueOrders → orders(expired)
 → 名额软释放
```

### 11.4 裂变传播完整链路

```
用户A 分享 → share_records(shareCode, sharerEntryId)
 → 用户B 通过 refCode 参与 → share_records.joinedCount++
 → activity_events(attributed_join)
 → [viral 裂变] → 用户A 获得额外 spins/权重
 → [referralRewardDefs 里程碑] 达标 → grantBonusSpin / grantBonusCoupon
 → [排行榜] 排名计算 → leaderboardRewards 发放
 → [导流追踪] click_traffic 已由前端写入（LotteryView.vue:3715），external_conversions 待后续接入
```

> **勘误（docs/260/261 审查）**：`click_traffic` 事件类型在 `types.ts:107` 定义，**前端 `LotteryView.vue:3715` 在 `trackCtaClick` 函数中已写入**（与 `cta_click` 并行记录，用于区分导流商品卡点击与普通 CTA）。后端 `integration.ts:92` 已展示 `trafficClicks` 计数。但缺少"曝光"环节事件（`cta_impression` 的 traffic 变体），漏斗的"曝光→点击"链路不完整。

## 十二、关键架构优势

1. **三层防超发架构**：幂等标记 → 出口 CAS → 总量约束
2. **事务边界清晰**：joinDraw 内参与+归因+奖励原子执行
3. **事件溯源**：activityEvents 统一 20 种事件类型
4. **多租户隔离**：所有查询带 tenantId
5. **三态隔离**：entry/order/attempt 状态独立
6. **预占-确认两阶段卡密**：下单 reserved → 回调 issued → 超时释放
7. **CAS 乐观锁全面覆盖**：9+ 个 CAS 点
8. **fail-closed 批量删除**：有支付订单的活动拒绝删除
9. **确定性/不确定失败分类**：防止资金黑洞
10. **单一真相原则**：引擎校验、预检校验共用同一函数

## 十三、已知设计限制

1. **shareRecords.joinedCount 是聚合计数器**：无法存储每个被邀请者的 entryId 明细，退群处罚需反查 activityEvents
2. **签到奖励只更新 spinsLeft 不更新 spinsTotalGranted**：spinsUsed = granted - left 低估实际消耗次数（设计决策）
3. **my-rewards 只查 identityType='user_id'**：open（email 身份）参与者的奖励不在 my-rewards 中
4. **配额 0 值语义**：配置值 0 被提升为 1（关闭限制需用 -1 或删除配置）
5. **withDbTransaction 重试风险**：回调内有外部状态依赖时需在事务外处理
6. **pity/dailyFreeSpins/referralRewards 公开端脱敏**：防止用户精确计算保底/里程碑门槛
7. **裂变面板三处条件不一致**：ViralLeaderboard 和 LotteryView 的 `shouldShowViralPanel` 只判断 `viral.enabled || referralRewardDefs.length > 0`；GameResultModal 额外加了 `inviteShareAllowed && entryId` 安全门。活动已取消/开奖后 ViralLeaderboard 仍可能渲染，GameResultModal 则不展示（P1-3，见 docs/260）
8. **referralRewardDefs 前端类型为 unknown[]**：3 处消费方（types.ts:82、ViralLeaderboard.vue:247、GameResultModal.vue:162）均无明确接口，IDE 无辅助（P1-5，见 docs/260）
