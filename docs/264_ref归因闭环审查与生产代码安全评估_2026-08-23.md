## 三、后端并发安全审查

### 3.1 秒杀容量控制（joinDraw）

**机制**：CAS 原子递增 `activeParticipantCount + 1 WHERE activeParticipantCount < effectiveMax`

**安全性**：✅ SQLite 写锁序列化并发事务，CAS 更新只有一条能成功（rowsAffected=1），其余被 WHERE 条件拒绝。不存在 TOCTOU 竞态。

**回滚保护**：INSERT 失败时 `activeParticipantCount - 1` 回滚计数器。

### 3.2 普通活动容量控制

**机制**：条件 INSERT `WHERE (SELECT COUNT(*) FROM lottery_entries ...) < effectiveMax`

**安全性**：✅ SQLite 写锁保证串行化。但 COUNT 语义是 entry 行数，不是名额数（quantity>1 时可能偏低）。对于非秒杀活动（无 quantity 字段），语义一致，无风险。

### 3.3 并发 Spin 扣次

**机制**：`spinsLeft - 1 WHERE entryId = ? AND spinsLeft > 0`

**安全性**：✅ CAS 原子扣减，不存在超扣。幂等键防止重复 spin。

### 3.4 优惠券核销

**机制**：`UPDATE couponCodes SET status = 'redeemed' WHERE status = 'issued' AND code = ? AND recipientEmail = ?`

**安全性**：✅ CAS 防并发重复核销。限流 10 次/分钟/IP 防枚举。

### 3.5 归因 joinedCount 递增

**机制**：`SET joined_count = joined_count + 1`（SQL 层面原子递增）

**安全性**：✅ SQLite 写锁序列化。同一 refCode 多次归因会多次 +1（如签到跨日），但奖励引擎的 CAS 幂等标记（rewardMilestonesGranted）防止重复发放。

### 3.6 奖励引擎幂等性

**机制**：CAS 乐观锁 `UPDATE shareRecords SET rewardMilestonesGranted = ? WHERE id = ? AND rewardMilestonesGranted = 旧值`

**安全性**：✅ CAS 失败时 grant 层的独立 CAS（spinsTotalGranted / couponCodes.status）兜底防止重复发放。
