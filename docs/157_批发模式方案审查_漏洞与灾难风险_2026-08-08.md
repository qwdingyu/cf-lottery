# 157 批发模式方案审查——漏洞、错误与灾难风险

> 日期：2026-08-08
> 针对 docs/155《批发模式与阶梯定价最优方案》的深度审查，对照代码库验证

## 0. 结论

`docs/155` 的**业务方向正确**（批发模式 + 阶梯定价是合理需求），但**技术方案存在 3 个灾难性漏洞**，若按原文实施会**破坏生产秒杀的去重防线并可能造成超卖**。必须修正后才能实施。

**严重等级**：
- 🔴 灾难（必须修复）：3 项
- 🟠 设计缺陷（建议修复）：3 项
- 🟡 次要（规范问题）：2 项

---

## 1. 🔴 灾难 1：全局 UNIQUE 索引改造会破坏所有活动类型的参与去重

### 现状（代码验证）

`schema.ts:334` 的 UNIQUE 索引是**全局共享**的，所有 `activity_kind` 都依赖它：

```ts
uniqueIndex("idx_entries_unique").on(t.tenantId, t.drawId, t.identityType, t.identityValue)
```

它保证"同一身份同一活动只能有一条参与记录"。直付秒杀（docs/131）的"1 人/场"正是靠它**在 DB 层兜底**。

### 文档错误

`docs/155 §3.1.1` 提出把 UNIQUE 改成含 `purchase_seq` 的 5 列索引，并声称：

> "秒杀仍然 `purchase_seq=0`，UNIQUE 约束天然生效"

**这是错误的**。`purchase_seq` 由代码写入，不是 DB 强制。只要代码存在任何 bug（或恶意请求传 `purchase_seq=1`），DB 就不再拒绝同一身份在同一活动的重复参与——**秒杀的"1 人/场"防线被静默移除**。

### 影响

- 秒杀可能超卖（同一用户重复抢购）
- 变更全局索引 = 影响所有现有活动，不只批发
- 属于**不可逆的生产降级**，违反 docs/131 的"UNIQUE 是参与去重最后防线"原则

### 正确做法

**不要改动全局 `idx_entries_unique`**。批发模式与秒杀/抽奖应**使用独立的参与存储**（见 §5 修正方案），或采用**部分唯一索引**（只在非批发活动上保持 4 列去重）。

## 2. 🔴 灾难 2：`purchase_seq` 与 `quantity` 两套模型自相矛盾

### 文档内部冲突

`docs/155` 同时提出了两个**互斥**的数据模型：

| 位置 | 模型 | 说明 |
|------|------|------|
| §3.1.1 | `purchase_seq` | 一身份**多行**，每行 1 件 |
| §3.3 | `quantity` | 一身份**一行**，每行 N 件 |

- §3.1.1 顶部加 `quantity` 列，但紧接着的"为什么"段落又讲 `purchase_seq`
- §3.1.2 索引表用 `purchase_seq`，§3.4 支付流程又用 `quantity`
- §1.1 业务表写"1 entry = N orders"，§3.4.1 下单又是"1 entry = 1 order（带 quantity）"

### 影响

照此实施会语义混乱：到底同一用户购买 3 件是 3 行 entry 还是 1 行 entry？退款、库存、发卡、进度展示全部会歧义。

### 正确做法

**二选一，必须明确**。推荐"**1 entry : 1 order : quantity=N**"（一行 entry 记录 N 件，一笔订单），因为：
- 数据库行数少
- 与现有 `payment_orders.entry_id` 唯一约束兼容（1 entry = 1 order）
- 退款/发卡按 quantity 处理即可

## 3. 🔴 灾难 3：去掉 `payment_orders.entry_id` UNIQUE 破坏重试与回调

### 现状（代码验证）

`payment-service.ts` 有**两处**依赖 `entry_id` 唯一：

1. **`retryPaymentOrder`（line 694）**：
   ```ts
   .where(eq(paymentOrders.entryId, input.entryId))
   ```
   用 `entryId` 精确查找要重试的订单。去掉 UNIQUE 后这个查询可能返回**多行**，`.limit(1)` 会**静默选中错误订单**重试——用户可能给错误的订单续支付。

2. **并发防重（line 168-172）**：`NOT EXISTS (SELECT 1 FROM payment_orders WHERE entry_id = ...)` 的双订单防护依赖 entry_id 唯一。

### 文档错误

`docs/155 §3.1.1` 主张去掉 `entry_id` UNIQUE 以支持"1 entry = N orders"。但 §3.4.1 又写的是"1 entry = 1 order（带 quantity）"——**如果采用 quantity 模型，根本不需要去掉 entry_id UNIQUE**。这个改动是"为了一个不采用的模型去破坏现有安全机制"。

### 正确做法

在"1 entry : 1 order : quantity=N"模型下，**`payment_orders.entry_id` 保持 UNIQUE 不变**，只加 `quantity` 与 `unit_price_cents` 列。这样 `retryPaymentOrder` 和并发防重逻辑全部无需改动。

## 4. 🟠 设计缺陷 1：阶梯定价模型未明确（cliff vs 分档）

### 问题

`docs/155 §3.2` 的 `calculateTieredPrice` 是 **cliff pricing**（达到档位门槛后，**全部 N 件**按该档单价计费）：

```ts
// 买 3 件 → 全部按 8900 计（3 件都打折）
```

但市面上还有 **incremental pricing**（分段计价：前 2 件按 9900，第 3 件起按 8900）。两种模型对买家公平性和营收影响差异巨大。

### 建议

在文档中**明确标注**选 cliff（实现简单、客户感知强），并说明门槛语义。前后端共享同一个 `calculateTieredPrice`，避免展示与实收不一致。

## 5. 🟠 设计缺陷 2：`activeParticipantCount` 语义冲突

### 问题

`activeParticipantCount`（`schema.ts:223`）当前是**直付秒杀的名额占用计数器**（CAS `+1`）。文档主张批发复用同一字段做 `+quantity`。

但：
- 秒杀的 CAS 是"名额"语义（`+1`）
- 批发的是"件数"语义（`+quantity`）
- 两者在同一 `lottery_draws` 行上，若同一活动既开秒杀又开批发（docs/155 §4.2 设想），会**互相污染计数器**

### 建议（2026-08-08 二次审查修正）

- ❌ ~~V1 明确**批发活动不使用 `activeParticipantCount`**，而用独立的 `lottery_entries.quantity` 的 `SUM()`~~ → 废弃此方案，见 §9.4
- ✅ **复用 `activeParticipantCount`**：CAS 语义从"名额"升级为"件数"，5 处 `+1` → `+quantity`
- ✅ 发布预检应**阻断**同一活动同时启用秒杀 + 批发（V1 不做叠加）——此条依然有效，防止计数器语义污染

## 6. 🟠 设计缺陷 3：展示 claimed 计数需按 `SUM(quantity)` 而非 `COUNT(*)`

### 问题

现有 `buildFlashSaleRuntime` 用 `COUNT(*)` 计算已参与人数。批发模式下"已售件数"应为 `SUM(quantity)`。文档未提及展示层差异。

### 建议（2026-08-08 二次审查修正）

- **公开详情**：批发活动的 `claimed` 已通过 `public-lottery.ts:185-187` 的 `paymentRequired === true` 分支直接读 `activeParticipantCount`，因 `activeParticipantCount` 已是"件数"语义，无需额外 `SUM(quantity)` 查询
- **`buildFlashSaleRuntime`**：是秒杀专用函数，批发不调用。批发应有独立的 `buildBulkRuntime`，但 `claimed` 参数值来源相同（`activeParticipantCount`）
- 展示层**零改动**：`activeParticipantCount` 已同时满足秒杀和批发的展示需求

## 7. 🟡 次要 1：发卡"全部或全部"与代码矛盾

`docs/155 §3.4.2` 的代码草图 `if (!code) break;` 是**部分发放**，与其正文"要么全部发完，要么进入 fulfillment_failed"矛盾。应改为：
```ts
for (let i = 0; i < quantity; i++) {
  const code = await acquirePrizeCode(tx, ...);
  if (!code) { /* 全部回滚 or 标记 partial 待补发 */ throw/return; }
}
```
且 `handlePaymentCallback`（line 844）当前只调用 `acquirePrizeCode` **一次**，需改为循环 `quantity` 次，并保证事务内原子。

## 9. 修正后的推荐方案（替代 docs/155 的原始方案）

### 9.1 数据模型（明确二选一）

```
推荐：1 entry : 1 order : quantity = N
lottery_entries.quantity      ← 新增（默认 1，兼容秒杀）
lottery_entries UNIQUE        ← 保持 4 列不变（不动生产去重）
payment_orders.entry_id       ← 保持 UNIQUE 不变（不动重试/防重）
payment_orders.quantity       ← 新增
payment_orders.unit_price_cents ← 新增
```

### 9.2 批发参与走独立逻辑

添加 `draw.activityKind === "wholesale"` 分支，**不碰秒杀热路径**。同一用户购买多件 = 一条 entry（quantity=N）+ 一笔订单（amountCents = unitPriceCents × N）。

### 9.3 限购语义

批发活动是否允许"同一用户重复购买多笔订单"？若允许，则必须**新增独立存储**（如 `bulk_orders` 表）或**部分唯一索引**，不能碰全局 UNIQUE。V1 建议：**一个身份一个活动只允许一笔批发订单**（quantity=N），即保持 UNIQUE 4 列不变，天然满足"一次购买 N 件"，无需放宽任何约束。

> 这恰好是**最安全**的 V1：不动任何现有约束，批发 = 秒杀的"多件"变体（1 entry : 1 order : quantity≥1）。

### 9.4 库存与展示（2026-08-08 二次审查修正）

**不要用 `SUM(quantity)` 做库存校验。** 复用 `activeParticipantCount` CAS 机制，语义从"已占名额数"升级为"已占件数"：

- **参与 CAS**：`activeParticipantCount = activeParticipantCount + quantity WHERE activeParticipantCount + quantity <= effectiveMax`
- **回滚**：INSERT 失败时 `activeParticipantCount = MAX(0, activeParticipantCount - quantity)`
- **释放**：`decrementActiveFlashSaleCount(tx, tenantId, drawId, quantity)`（该函数已支持 `amount` 参数，无需改动）
- **展示**：`public-lottery.ts:185-187` 对 `paymentRequired=true` 直接读 `activeParticipantCount`，批发自动显示"已售 N 件"

**为什么这比 SUM(quantity) 更可靠：**

| 维度 | SUM(quantity) ❌ | activeParticipantCount CAS ✅ |
|------|-----------------|-------------------------------|
| 并发机制 | 条件 INSERT + 子查询聚合，`SELECT SUM(...)` 再 `INSERT` 存在读取时读到过期数据 | 单行条件 UPDATE，原子 CAS，已生产验证 |
| 扩展性 | `SUM(quantity)` 扫描 entries 表，O(n) 随参与数增长 | 单行 UPDATE，O(1) |
| 改动面 | 新增独立库存路径 + 数据迁移 + 新索引 | 仅改 `+1` → `+quantity`，5 处调用点 |
| 展示层 | 需对批发单独做 `SUM(quantity)` 查询 | 已有 `activeParticipantCount` 读路径，零改动 |
| 回滚一致 | 需新事务回滚机制 | 已有 `MAX(0, ... - amount)` 回滚（line 366） |

**需要改动的 5 处代码（全部是 `+1` → `+quantity`）：**

1. `participation.ts:240` 重开路径：`activeParticipantCount + 1` → `activeParticipantCount + quantity`
2. `participation.ts:322` 新参与路径：`activeParticipantCount + 1` → `activeParticipantCount + quantity`
3. `participation.ts:366` 回滚：`activeParticipantCount - 1` → `activeParticipantCount - quantity`
4. `payment-service.ts:209` 到期释放，需 `.returning({ drawId, quantity })` 替代 `+1`
5. `payment-service.ts:224` 僵尸释放，需 `.select({ id, drawId, quantity })` 替代 `+1`

## 10. 结论

**docs/155 的建议方案不能直接实施**。必须：
1. ❌ 放弃修改全局 `idx_entries_unique`
2. ❌ 放弃修改 `payment_orders.entry_id` UNIQUE
3. ✅ 明确采用"1 entry : 1 order : quantity=N"模型
4. ✅ 批发作为 `claim` 的"多件"变体，V1 一个身份仅一笔订单

## 11. 二次审查补充（2026-08-08，第二次深度审查后追加）

### 11.1 代码中 `entry_id` UNIQUE 的承重路径（完整清单）

以下是 `payment_orders.entry_id UNIQUE` 约束在代码库中**所有**的承重点，验证了"去掉约束会产生连锁破坏"的断言：

| 代码位置 | 用途 | 对 UNIQUE 依赖度 |
|----------|------|-----------------|
| `payment-service.ts:694` `retryPaymentOrder` | 按 `entryId` 查订单，`.limit(1)` | 🔴 去掉 UNIQUE 后可能查到错误订单 |
| `payment-service.ts:168-172` `expireOverdueOrders` | `NOT EXISTS (SELECT 1 FROM payment_orders WHERE entry_id = ...)` 判断"预留无订单" | 🟡 不依赖唯一，但语义依赖"1 entry = 1 order" |
| `payment.ts:152-160` 公开下单路由 | 查已有订单，`.limit(1)`，注释"一参与一订单" | 🔴 去掉 UNIQUE 后 `.limit(1)` 静默选错 |
| `payment-service.ts:83` `issuePaymentOrderAccessToken` | `WHERE entry_id = ...` 签发令牌 | 🟠 仍可工作，但查询语义不确定 |
| `payment-service.ts:578-587` `createPaymentOrder` | CAS `UPDATE entry WHERE payment_status=reserved` + INSERT order | 🟡 依赖 NOT EXISTS 防重，非 UNIQUE 本身 |
| `migrations/0037_reconcile_paid_fulfillment_entry_status.sql` | 修复脚本，`WHERE entry_id = ...` | 🟡 一次性脚本 |
| `publish-check-service.ts:137-147` 发布预检 | 阻断 `maxPerUser !== 1`，注释"一参与一订单" | ✅ 代码层，不依赖约束 |

**结论**：`entry_id` 是支付系统的核心关联键。去掉其 UNIQUE 约束会在至少 3 处生产路径造成静默错误，验证了 docs/157 §3 的"灾难"定级。

### 11.2 V1 产品约束必须显式文档化

"1 identity : 1 entry : 1 order : quantity=N"模型有一个**产品层面的硬约束**：

> **V1 限制**：同一用户在同一个批发活动中只能购买**一次**（一笔订单，quantity≥1）。不能先买 3 件再到同一活动追加 5 件。

这是因为 `lottery_entries` 的 UNIQUE(4 列) 约束不允许同一身份的第二条 entry。如果产品需要"一个人多次购买"，V2 必须新增独立存储（如 `bulk_orders` 表）或部分唯一索引，**不能碰全局 UNIQUE**。

### 11.3 新增校验：订单数量必须与参与数量一致

`payment.ts` 的公开下单路由必须增加校验：

```ts
// 新增：订单 quantity 必须等于 entry.quantity
if (body.quantity !== entry.quantity) {
  return fail(c, "订单数量与参与数量不一致", 409);
}
```

防止前端传不同的 quantity 来绕过价格计算（价格由服务端根据 entry.quantity 计算，但 order.quantity 也应与 entry 一致，确保退款/发卡语义清晰）。

### 11.4 二次审查修正：废弃 `SUM(quantity)`，复用 `activeParticipantCount` CAS

**2026-08-08 二次审查修正**：docs/157 原始 §9.4 推荐使用 `SUM(quantity)` 做批发库存校验，但该方案存在以下问题：

1. ❌ **并发窗口**：`SELECT SUM(quantity)` + `INSERT` 是读-写模式，在 Turso/libSQL 的 HTTP 事务下缺乏行级锁保护，存在读到过期数据后写入的风险
2. ❌ **扩展性**：`SUM(quantity)` 扫描 `lottery_entries` 的匹配行，O(n) 随参与数增长，与 docs/141 警告的 COUNT 扩展问题同类
3. ❌ **改动面大**：需要引入独立库存校验路径 + 数据迁移回填已有活动的 `activeParticipantCount` + 新索引验证

**修正方案**：复用 `activeParticipantCount` CAS 机制，语义从"已占名额数"升级为"已占件数"。

修正后的库存模型：

```
参与 CAS:  UPDATE lottery_draws
           SET activeParticipantCount = activeParticipantCount + quantity
           WHERE activeParticipantCount + quantity <= effectiveMax
           AND id = drawId AND tenantId = tenantId AND status = 'open'

释放 CAS:  UPDATE lottery_draws
           SET activeParticipantCount = MAX(0, activeParticipantCount - quantity)
           WHERE id = drawId AND tenantId = tenantId
```

**`decrementActiveFlashSaleCount`（payment-service.ts:114-128）已接受 `amount` 参数**，无需改动签名。仅需改动 5 处调用点（见 §9.4 表格）。

**发布预检**：`publish-check-service.ts` 中对于批发活动，校验 `effectiveMax > 0` 且 `quantity` 字段被正确配置。不涉及 `activeParticipantCount` 的预检改动。

**现有活动数据回填**：若已有批发活动上线（当前无），需一次迁移将 `activeParticipantCount` 设为 `SUM(quantity)`。V1 新功能上线时无此问题。

### 11.5 二次审查最终结论

docs/157 原始审查结论**全部验证正确**，两个关键修正点被进一步确认：

1. ✅ **不动 `idx_entries_unique`**：它的覆盖范围>40 个表，所有 activity_kind 共享，任何修改都会波及抽奖、签到、接龙、秒杀的去重语义。
2. ✅ **不动 `payment_orders.entry_id` UNIQUE**：它在 3 个生产路径上承重，去掉后无安全替换方案。

增量发现：
- 新增 `order.quantity === entry.quantity` 一致性校验（V1 必须加）
- ❌ **废弃** `SUM(quantity)` 库存方案，改为复用 `activeParticipantCount` CAS（5 处 `+1` → `+quantity`，更小的并发窗口和改动面）
- V1 的"一次购买"产品限制必须显式文档化，避免后期产品/运营误解

**背景**：`flash-sale-config.ts:247` 的 `calculateFlashSalePrice` 原写法为
`Number(matched.unitPriceCents || basePrice)`。JS 的 `||` 把 `0` 视为 falsy，
因此当某阶梯 `unitPriceCents: 0`（免费档）时，会静默回退到 `basePrice`，
导致免费档无法生效、用户被多收费。

**影响**：⚠️ 低严重度。发布预检已用 `price_invalid`（`unitPriceCents <= 0`）阻断 0 分档，
正常运营配置不会触发；但若存在历史数据 / 直接改库 / 未来放开免费档，运行时会被错误多收。

**修复**（commit `b6014dd`）：
- `||` 改为 `??`（nullish coalescing），仅当 `unitPriceCents` 为 `null/undefined` 时才回退 basePrice
- 新增测试：构造含 0 分阶梯的 config，验证按 0 计算而非回退 basePrice
