## 一、最终定位

`cf-lottery` 的长期定位不应是“抽奖工具”，而应是：

> **多租户、可白标、可嵌入、可集成的轻量活动引擎 SaaS。**

抽奖是第一个模板，接龙是第二个自然模板。后续的预约、领券、资料领取、问卷、投票、签到、候补、审核申请、内测码发放等，应该复用同一套活动引擎，而不是为每个玩法新建一套系统。

核心产品公式：

```text
活动模板
  + 资格校验
  + 参与记录
  + 结果/权益分配
  + 导流承接
  + 事件归因
  + 通知/集成
  + 审计/运营
= 可持续扩展的活动 SaaS
```

因此，顶层设计必须围绕 8 个稳定域冻结：

| 稳定域 | 作用 | 当前状态 |
|---|---|---|
| `tenant` | 租户、套餐、品牌、成员、配额 | 基础已建，平台运营后台待补 |
| `activity` | 活动主模型、状态机、模板 | 基础已建，命名仍偏 lottery |
| `qualification` | 谁能参加、如何验证 | open/roster/password/invite_code 基础已建 |
| `entry` | 用户参与事实 | 基础已建，通用表单 payload 待补 |
| `outcome` | 中奖、名额、候补、审核、领取、计票 | 抽奖和接龙基础已建 |
| `promotion` | CTA、外链、优惠、下一活动、分享 | 基础已建，多 CTA 和规则化待补 |
| `event` | 浏览、开始、完成、点击、分享、外部转化 | 基础已建，租户侧活动数据面板已补；平台级看板待补 |
| `audit/integration` | 审计、Webhook、API Key、导入导出 | 基础已建，运营化待补 |

## 二、行业痛点与产品机会

中小团队、社群运营、教育培训、门店、本地服务、B2B 增长团队的共同痛点不是“缺一个炫酷抽奖动画”，而是：

1. **活动创建慢。** 每次报名、抽奖、投票、领券都重新拼表单、二维码、名单、导出。
2. **资格和名额难控。** 名单、邀请码、密码、限量、候补、审核容易靠人工维护。
3. **导流没有闭环。** 能发链接，但不知道谁看了、谁参与了、谁点击了、谁最终在外部系统转化。
4. **结果发放易出错。** 卡密重复发、候补顺序乱、核销无审计、邮件失败无补偿。
5. **多租户运营缺后台。** SaaS 平台方需要看租户、套餐、用量、异常、失败任务，而不是直接查库。
6. **扩展新玩法容易重做。** 如果抽奖、接龙、预约、投票各自一套表和流程，MVP 稳定后必然推翻。

最佳实践校准：

- 事件体系要先定义 tracking plan，即明确要收集哪些事件、属性、代码位置和业务原因。参考 Segment/Twilio Tracking Plan 文档。
- 异步投递和队列默认要按“至少一次”理解，业务侧必须用幂等键去重。参考 Cloudflare Queues delivery guarantees。
- 高并发名额、排队、候补转正这类强顺序场景，应考虑按活动维度做状态协调。参考 Cloudflare Durable Objects 的 stateful coordination 定位。
- SaaS 计费不要把 plan 判断散落在业务代码里，长期应使用 entitlement/feature/quota 层。参考 Stripe Billing Entitlements。

参考链接：

- https://segment.com/docs/protocols/tracking-plan/best-practices/
- https://developers.cloudflare.com/queues/reference/delivery-guarantees/
- https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/
- https://docs.stripe.com/billing/entitlements

## 三、抽奖和接龙是否同类

结论：**抽奖和接龙是同一类活动引擎问题，但不是同一种结果模式。**

共同点：

| 共同能力 | 抽奖 | 接龙 |
|---|---|---|
| 活动生命周期 | 需要 | 需要 |
| 公开链接/二维码 | 需要 | 需要 |
| 资格校验 | 需要 | 需要 |
| 重复参与控制 | 需要 | 需要 |
| 容量/名额 | 奖项名额 | 报名名额 |
| 参与记录 | entry | entry |
| 结果记录 | winner/outcome | assignment/outcome |
| 导流承接 | 中奖/未中奖页 CTA | 成功/候补页 CTA |
| 通知导出 | 需要 | 需要 |
| 审计 | 开奖审计 | 顺序/候补审计 |

差异：

| 维度 | 抽奖 | 接龙 |
|---|---|---|
| 结果本质 | 随机或加权随机选出 winner | 按顺序或优先级占位 |
| 公平性重点 | 随机种子、算法版本、防重复中奖 | 顺序一致性、容量扣减、候补转正 |
| 用户反馈 | 等待开奖或即时揭晓 | 立即知道成功/候补/序号 |
| 高并发风险 | 开奖防双发、码池防重 | 抢名额、队列顺序、候补晋升 |

推荐建模：

| 玩法 | `activity_kind` | `result_mode` | `allocation_policy` | `experience_type` |
|---|---|---|---|---|
| 定期开奖 | `lottery` | `scheduled` | `random` | `wheel/card` |
| 即时抽奖 | `lottery` | `instant` | `random/weighted_random` | `scratch/reveal/grid` |
| 报名接龙 | `signup_chain` | `ordered_assignment` | `capacity/fifo` | `list/queue` |
| 满额候补 | `signup_chain` 或 `waitlist` | `ordered_assignment` | `waitlist` | `queue` |

## 四、更多低成本高价值玩法矩阵

### 4.1 P0/P1：最适合当前架构的玩法

这些玩法与当前 `activity -> entry -> outcome -> event -> promotion` 骨架共享度最高，优先做。

| 玩法 | 业务价值 | 推荐实现方式 | 成本 | 变现点 |
|---|---|---|---:|---|
| 普通抽奖 | 福利、传播、活动氛围 | 已有抽奖模板继续稳定 | 低 | 活动数、参与上限、品牌 |
| 即时抽奖 | 强可玩性，适合导流 | 后端即时 outcome，前端 reveal/scratch/grid | 中 | 高级模板、去品牌 |
| 报名接龙 | 社群、课程、活动报名高频 | `signup_chain + ordered_assignment` | 低 | 导出、模板、成员协作 |
| 候补排队 | 满额后继续收集需求 | outcome 状态区分 confirmed/waitlisted | 中 | 候补通知、导出 |
| 资料领取 | B2B 获客、课程资料、白皮书 | form submission + instant claim | 低 | 表单字段、导出、Webhook |
| 问卷调研 | 留资、用户研究、满意度 | form schema + no_result/summary | 低 | 导出、品牌、数据留存 |
| 领券活动 | 直接承接购买/到店 | coupon code pool + claim outcome | 中 | 码池、核销、外部回传 |
| 限量预约 | 门店、沙龙、咨询、课程 | 单时段 capacity_assignment | 中 | 预约模板、提醒 |
| 投票评选 | 社群传播、内容评选 | vote_tally + ballot experience | 中 | 反刷、榜单、公示 |
| 签到打卡 | 复访、训练营、活动现场 | checkin + unique period | 中 | 连续签到、导出 |
| 审核申请 | 内测、试用、白名单 | review_task + approval outcome | 中 | 审核席位、Webhook |
| 内测码发放 | SaaS/游戏/课程试用 | approval/claim + code pool | 中 | 码池、通知、审计 |

### 4.2 P2：可作为组合模板的玩法

| 玩法 | 本质 | 组合方式 | 注意事项 |
|---|---|---|---|
| 盲盒开箱 | 即时结果皮肤 | `lottery/claim + reveal` | 前端只展示后端结果 |
| 九宫格抽奖 | 抽奖皮肤 | `lottery + grid` | 不改变结果算法 |
| 翻牌抽签 | 分配皮肤 | `assignment + card` | 先分配再翻牌 |
| 分享加次数 | 邀请策略 | `referral policy + lottery` | 只按有效参与归因，不按点击 |
| 邀请解锁资料 | 有效邀请触发权益 | `promotion + claim` | 设置上限和反作弊 |
| RSVP 确认 | 预约简化版 | `reservation + form` | 先单场次 |
| 线下核销券 | 领券后到店 | `claim + redemption` | 必须有核销审计 |
| 现场签到码 | 线下活动签到 | `checkin + code/password` | 防代签、防重复 |
| 提名推荐 | 表单 + 评选 | `survey + vote` | 隐私和撤回 |
| 作品征集 | 表单/上传 + 审核/投票 | `approval + vote` | 上传走 R2，不进 D1 |
| 答题抽奖 | 资格前置 | `quiz + lottery` | 题目版本化 |
| 测验评分 | 表单计算结果 | `quiz + outcome` | 不扩成 LMS |
| 课程选座 | 容量分配 | `reservation/assignment` | 多资源以后再做 slots |
| 众测招募 | 申请 + 审核 + 发码 | `approval + claim` | 审核和通知要闭环 |
| 加群申请 | 表单 + 审核/外链 | `approval + promotion` | 入群成功需外部回传 |

### 4.3 P3：可做但不要进入内核

| 方向 | 能力价值 | 为什么不进内核 |
|---|---|---|
| 积分任务中心 | 复访和留存 | 容易变成营销自动化大系统 |
| 邀请裂变排行榜 | 拉新 | 反作弊、奖励结算复杂 |
| 直播抽奖 | 场景明确 | 直播互动链路是另一产品域 |
| 内容社区评选 | 可传播 | 内容审核、举报、评论成本高 |
| 联盟分销 | 可变现 | 佣金、结算、合规过重 |
| 自建商城 | 可交易 | 商品、订单、库存、支付会吞掉活动引擎 |

明确不建议近期做：

- 自建支付、购物车、订单、退款。
- 自建广告交易市场。
- 自建复杂 CRM。
- 自建内容社区。
- 自建分销佣金结算。

正确策略是：**活动引擎只做连接、承接、归因、回传，不吞并外部业务系统。**

## 五、引流、导流、归因、变现闭环

### 5.1 四层数据口径

| 层级 | 数据来源 | 可以证明 | 不能证明 |
|---|---|---|---|
| 渠道参数 | UTM/source/ref | 流量来源 | 真实成交或核销 |
| 平台事件 | `activity_events` | 浏览、开始、完成、CTA 点击、分享 | 外部订单结果 |
| 有效邀请 | `share_records.joined_count` + `attributed_join` | 分享带来成功参与 | 外部付费 |
| 外部转化 | `external_conversions` | 外部系统明确回传的注册、购买、核销 | 未回传的外部事实 |

当前代码已经有 `activity_events`、公开事件上报、有效邀请归因、Webhook delivery、`external_conversions` 基础表和集成路由。正确口径是：

```text
外部转化回传基础已建；
租户侧基础漏斗可视化已补；来源校验、API Key scope、回传导入工具和平台级运营告警仍待补。
```

### 5.2 用户侧体验闭环

```text
看到活动链接/二维码
  -> 打开活动页
  -> 完成参与/报名/领取/投票/提交
  -> 获得结果或状态
  -> 根据结果看到自然 CTA
  -> 点击外链/复制券码/下载资料/加入下一活动
  -> 平台记录事件
  -> 外部系统可回传真实转化
```

设计原则：

- 先让用户完成来活动页的核心任务，再导流。
- 导流 CTA 必须与结果相关，不做无关强推。
- 未中奖、候补、审核中也要有承接。
- 不做自动强跳转，避免破坏信任和归因质量。

### 5.3 租户侧运营闭环

```text
选择模板
  -> 配置资格、容量、奖品/权益、导流 CTA
  -> 发布链接/二维码
  -> 观察浏览、参与、完成、CTA、分享、外部回传
  -> 导出、通知、复盘
  -> 复制模板进入下一轮活动
```

租户真正愿意付费的能力：

- 模板和复制，降低创建成本。
- 资格、容量、候补、审核，降低人工成本。
- 事件看板和外部回传，提高复盘可信度。
- 品牌配置和嵌入能力，提升专业感。
- 团队协作、审计、导出、Webhook，满足组织使用。

### 5.4 平台侧变现路径

短期卖 SaaS 权益，不卖流量：

| 套餐 | 建议权益 |
|---|---|
| Free | 少量活动、低参与上限、平台品牌、抽奖/接龙基础模板 |
| Pro | 更多活动、更多参与人数、品牌配置、导出、基础事件看板 |
| Team | 多成员、RBAC、审计、Webhook、模板库、批量导入 |
| Enterprise | 白标、自定义域名、API 高配额、专属集成、数据保留策略 |

当前 `PLAN_LIMITS` 和兑换码额度可作为 MVP 运营手段。长期要收敛为：

```text
plan -> entitlement -> quota -> usage -> audit
```

兑换码适合当前阶段用于人工售卖、渠道赠送、试用延期、线下成交开通。它不是最终计费系统，但能让平台先具备简单运营变现能力。

## 六、简单但完整的 SaaS 后端

### 6.1 租户后台

租户后台要从“抽奖管理”升级为“活动运营台”：

| 一级模块 | 必备能力 |
|---|---|
| 工作台 | 活动状态、待处理事项、参与趋势、套餐用量 |
| 活动 | 创建、编辑、发布、暂停、复制、归档、模板化 |
| 参与者 | 列表、筛选、导出、名单、邀请码、黑名单 |
| 结果 | 中奖、名额、候补、审核、核销、人工修正 |
| 奖品/权益 | 奖品、码池、券码、资料领取、发放记录 |
| 导流 | CTA、商品链接、优惠券、下一活动、渠道参数 |
| 数据 | 浏览、开始、完成、CTA、分享、有效邀请、外部转化 |
| 通知 | 邮件、Webhook、失败重试、模板 |
| 团队 | 成员、角色、邀请、移除 |
| 品牌 | Logo、颜色、公开页文案、自定义域名预留 |
| 审计 | 规则变更、结果修正、导出、成员变更 |

### 6.2 平台运营后台

平台后台必须简单，但不能缺：

| 一级模块 | 必备能力 |
|---|---|
| 租户管理 | 租户列表、状态、套餐、创建时间、最近活跃 |
| 套餐/额度 | plan、兑换码、手动加量、到期时间、超限记录 |
| 用量 | 活动数、参与数、事件数、Webhook 数、导出数 |
| 活动监管 | 异常活动、投诉、下架、封禁 |
| 模板运营 | 官方模板、行业模板、启停、排序 |
| 投递监控 | 邮件失败、Webhook 失败、重试队列 |
| 风控 | IP/身份异常、重复参与、分享刷量 |
| 系统配置 | 邮件、限流、注册开关、Webhook 策略 |
| 支持诊断 | 只读查看租户状态、活动状态、失败原因 |
| 平台审计 | 平台管理员跨租户操作必须记录 |

平台后台设计原则：

- 平台管理员默认只读诊断。
- 任何跨租户修改必须写 `audit_logs`。
- 套餐变更和兑换码开通必须有记录。
- 系统配置和租户配置必须分层。

## 七、架构演进原则

### 7.1 五个维度绝不能混淆

| 维度 | 职责 | 示例 |
|---|---|---|
| `activity_kind` | 活动业务语义 | lottery/signup_chain/reservation/vote/survey |
| `participation_mode` | 资格入口 | open/roster/password/invite_code |
| `experience_type` | 前端交互皮肤 | wheel/scratch/slot/form/ballot/queue |
| `result_mode` | 结果何时产生 | instant/scheduled/ordered_assignment/vote_tally |
| `allocation_policy` | 名额或权益如何分配 | random/fifo/capacity/waitlist/approval |

不要让转盘决定抽奖规则，不要让接龙列表决定资格，不要让 UTM 决定成交。

### 7.2 新玩法准入标准

新增玩法前必须回答：

1. 是否能复用 `activity` 主表？
2. 是否能复用 `entry` 参与记录？
3. 结果能否表达为 `outcome`？
4. 是否需要新的资格校验，还是只是已有资格组合？
5. 是否只是新的 `experience_type`？
6. 是否需要通用表单 schema？
7. 是否会引入支付、库存、内容社区等重域？

只要答案显示“会复制整套主流程”，就应暂停，先补内核抽象。

### 7.3 Cloudflare 分层建议

| 场景 | 推荐 |
|---|---|
| CRUD、配置、审计、轻量统计 | D1 |
| Webhook/邮件异步投递 | D1 delivery 表 + Cron；规模上来后接 Queues |
| 高并发抢名额、候补转正、排队 | 每活动 Durable Object |
| 图片、海报、资料文件 | R2 |
| 高维事件分析 | 先 D1 事实表，后续 Analytics Engine 或外部仓库 |

当前不建议马上引入 Durable Objects 或 Queues 重构。正确路线是：先用 D1 把事实、幂等、状态、审计做稳；当单活动高并发或异步投递量成为真实瓶颈，再迁移协调层。

---

## 八、分步实施路线

### 阶段 0：MVP 稳定和口径纠偏

目标：不推翻现有代码，修正会阻碍扩展的点。

已完成或基础已建：

- 活动主表已有 `activity_kind/participation_mode/experience_type/result_mode/allocation_policy/policy_version/promotion_config`。
- 抽奖基础闭环存在。
- 接龙基础 outcome 存在。
- 事件表、公开端基础埋点、有效邀请归因存在。
- Webhook delivery、签名、重试状态、Cron 调度存在。
- 外部转化回传基础表和集成路由存在。
- 兑换码和租户额外额度字段存在，可支持早期人工运营变现。

仍需补：

1. 平台级活动事件运营看板。
2. 外部转化回传的来源校验、API Key scope 和调用日志。
3. Webhook 失败告警。
4. 后台菜单和文案逐步从“抽奖管理”上移到“活动管理”。

### 阶段 1：活动引擎内核成型

目标：新增资料领取、问卷、预约时不复制主流程。

实施：

1. 抽出统一 qualification 管线。
2. 抽出统一 outcome service。
3. 新增 `activity_form_schema` 和 `activity_submissions`。
4. 新增 `activity_templates`。
5. `promotion_config` 升级为多 CTA、按结果条件展示。

验收：

- 新增“资料领取”不建新参与表。
- 新增“问卷”只扩表单 schema 和导出，不复制活动 CRUD。
- 新增“预约”先复用容量 outcome，后续才引入 slots。

### 阶段 2：高价值玩法库

优先顺序：

1. 接龙稳定化：候补转正、通知、导出。
2. 资料领取/问卷：通用表单、导出、Webhook。
3. 领券：唯一码池、领取记录、核销入口。
4. 预约：单时段容量，多时段后置。
5. 投票：去重计票、公示脱敏。
6. 签到：按天/场次重复控制。
7. 审核申请：审核任务、通过/拒绝通知、发码。

### 阶段 3：SaaS 运营化

实施：

1. 平台运营后台。
2. `feature_entitlements` 和 `tenant_usage_snapshots`。
3. 兑换码后台完善：创建、禁用、兑换记录、租户额度追踪。
4. 成员邀请和 RBAC。
5. API Key scope、调用日志、Webhook 可视化。
6. 白标配置和自定义域名预留。
7. 官方模板和行业模板运营。

### 阶段 4：生态集成

只连接，不吞并：

- 支付系统：接入订阅状态和 entitlement，不把支付写进活动内核。
- 电商系统：只接 CTA、券码、外部转化回传，不做订单库存。
- CRM/企微/飞书：只做联系人同步、通知、Webhook。
- 数据仓库：同步事件和转化事实。

---

## 九、当前最优下一步

从全局收益看，下一步不应继续堆动画，而应按这个顺序做：

1. **资料领取/问卷 vertical slice**：最低成本验证通用表单 schema，复用活动/entry/event/promotion。
2. **接龙稳定化**：候补转正、通知、导出，把第二玩法做扎实。
3. **平台运营后台最小版**：租户、套餐、兑换码、用量、失败投递、系统配置。
4. **外部转化治理**：来源校验、API Key scope、调用日志和回传导入。
5. **领券/核销**：承接导流变现，但不做电商。
6. **预约/投票/签到**：按共享骨架逐步扩展。

一句话原则：

> **MVP 可以小，但抽象不能错。先把 activity/entry/outcome/event/promotion/audit 这条主干做稳，再不断加低成本玩法模板。**
