# P1 运营闭环完善详细方案

> 文档编号：031
> 日期：2026-08-01
> 定位：对齐 014 全局 TODO 中最需要补齐的 5 个方向，形成可实施、可测试、符合 Cloudflare Workers Free + Turso/libSQL Free 前提的详细方案。
> 结论：当前不应继续堆玩法；应先补“轻量配置、发布预检、媒体治理、漏斗复盘、平台运营审计”五个闭环。

---

## 一、前置约束

### 1.1 官方资源口径

以 2026-08-01 核对的官方页面为准：

| 资源 | 当前设计采用的约束 | 对本项目的设计要求 |
|------|------------------|--------------------|
| Cloudflare Workers Free | 100,000 requests/day、10 ms CPU/request、128 MB memory、50 subrequests/request | 公开热路径必须少请求、少计算、少大 JSON；后台低频检查可以做 COUNT，但不能放到每次公开访问里。 |
| Cloudflare R2 Free | 免费层有存储和 Class A/B 操作额度；具体数字以后续官方 pricing 为准 | 奖品图只做少量运营图片，单图 2MiB；不做用户侧上传、图库、裁剪、批量大文件。 |
| Turso/libSQL Free | 关注 rows read、rows written、storage；COUNT 主要风险是 rows read 和延迟，不是 Worker CPU | 高频事件不能逐条滥写；问卷/投票提交只写必要记录；后台统计分页读取。 |

参考：

- Cloudflare Workers Limits: https://developers.cloudflare.com/workers/platform/limits/
- Cloudflare R2 Pricing: https://developers.cloudflare.com/r2/pricing/
- Turso Pricing: https://turso.tech/pricing
- Turso Usage and Billing: https://docs.turso.tech/help/usage-and-billing.md

### 1.2 本项目产品约束

客户付费购买的是：

```text
快速创建
少出错
能复盘
能承接
能接系统
能托管运营
```

因此 P1 不能再按“玩法数量”验收，而要按运营闭环验收。

### 1.3 不做清单

P1 明确不做：

1. 不做重型表单平台。
2. 不做租户自定义 RBAC。
3. 不做用户侧图片/文件上传。
4. 不做复杂 BI、自定义报表和任意 SQL 查询。
5. 不做高频事件持久化限流表。
6. 不做媒体库 UI、在线裁剪、批量上传、图片处理流水线。
7. 不做投票复杂反作弊，只做基础去重、限流、固定选项和异常提示。

## 二、总体架构

### 2.1 最优数据分层

当前已有稳定骨架：

```text
lottery_draws          活动主表
lottery_entries        参与记录和身份去重
activity_outcomes      接龙/预约/审核等结果
activity_events        漏斗事件
external_conversions   外部转化回传
prizes/prize_codes     奖品和码池
webhook_deliveries     Webhook 投递记录
platform_members       平台成员
tenant_usage_snapshots 租户用量快照
```

P1 推荐只新增 3 个轻量结构：

| 结构 | 类型 | 用途 | 为什么需要 |
|------|------|------|------------|
| `lottery_draws.activity_config` | JSON 文本字段 | 保存问卷字段、投票选项等玩法配置 | 避免为每个玩法增加配置表；版本化即可长期演进。 |
| `activity_submissions` | 新表 | 保存问卷答案、投票选择、资料领取表单结果 | `lottery_entries` 没有 payload；不能把问卷答案塞进身份字段，也不能污染 outcome。 |
| `media_assets` | 新表 | 记录 R2 managed key、大小、租户、状态 | 没有资产表就无法做租户额度、清理、审计和异常定位。 |

不建议把问卷/投票结果塞进 `activity_outcomes.metadata_json`：

- `activity_outcomes` 是“结果分配”层，适合接龙、候补、审核、预约。
- 问卷/投票的本质是“提交事实”，不是结果分配。
- 混用会让导出、统计、Webhook payload 和后续核销逻辑都变乱。

### 2.2 `activity_config` 版本化结构

新增字段：

```sql
ALTER TABLE lottery_draws
  ADD COLUMN activity_config TEXT NOT NULL DEFAULT '{}';
```

统一结构：

```json
{
  "version": 1,
  "kind": "survey",
  "survey": {
    "submitText": "提交",
    "successMessage": "提交成功",
    "fields": []
  },
  "vote": {
    "submitText": "投票",
    "successMessage": "投票成功",
    "showResults": "after_submit",
    "maxChoices": 1,
    "options": []
  }
}
```

P1 只允许受控字段：

| 字段 | P1 支持 | 限制 |
|------|---------|------|
| `text` | 是 | 最大 200 字符 |
| `email` | 是 | 使用简单邮箱格式校验 |
| `phone` | 是 | 最大 30 字符，只做格式宽松校验 |
| `textarea` | 是 | 最大 1000 字符 |
| `select` | 是 | 选项 2-30 个 |
| `radio` | 是 | 选项 2-30 个 |
| `checkbox` | 是 | 选项 1-30 个，P1 保存数组但不做复杂逻辑 |
| `number/date/hidden/divider/heading` | 暂不做 | cf-form 有经验可借鉴，但 P1 不引入，避免 UI 和校验复杂化。 |

字段限制：

```text
每个问卷最多 20 个字段
每个字段 key 1-40 字符，只允许 [a-zA-Z0-9_]
label 最多 80 字符
placeholder 最多 120 字符
单次提交 payload JSON 最多 10KB
投票选项最多 30 个
P1 投票默认单选，maxChoices 固定为 1；多选放 P2
```

## 三、方向 1：问卷/投票轻量配置界面

### 3.1 当前问题

当前代码已有：

- `activity_kind = survey/vote`
- `experience_type = form/ballot`
- `result_mode = no_result/vote_tally`
- 模板入口
- 投票 `/draws/:id/tally` 基础接口

但仍有重大缺口：

1. 问卷没有字段配置。
2. 投票没有固定选项配置。
3. 当前投票统计依赖 `lottery_entries.identity_value` 分组，这会把“用户身份”误当“投票选项”，不能作为正式模型。
4. 运营者无法在后台快速理解和配置问卷/投票。

### 3.2 推荐方案

新增轻量配置面板，嵌入现有 `AdminLotteryView` 的活动编辑表单，不单独做大型页面。

当 `activityKind === "survey"`：

```text
活动基础信息
参与规则
问卷字段
承接动作
发布前预检
```

当 `activityKind === "vote"`：

```text
活动基础信息
参与规则
投票选项
结果展示设置
承接动作
发布前预检
```

UI 设计原则：

1. 默认模板自动带 2-3 个字段或选项，不让客户面对空白表单。
2. 字段/选项用简单列表编辑，不做拖拽、不做嵌套逻辑、不做条件显示。
3. 每行字段包含：类型、标题、必填、选项、删除。
4. 投票选项包含：标题、说明、图片 URL（可选，复用媒体上传）、排序。
5. 发布按钮旁边显示预检状态。

### 3.3 数据表

新增 `activity_submissions`：

```sql
CREATE TABLE activity_submissions (
  id TEXT PRIMARY KEY,
  tenant_id TEXT NOT NULL,
  draw_id TEXT NOT NULL,
  entry_id TEXT NOT NULL,
  submission_kind TEXT NOT NULL,
  primary_value TEXT NOT NULL DEFAULT '',
  payload_json TEXT NOT NULL DEFAULT '{}',
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE UNIQUE INDEX idx_activity_submissions_entry_kind
  ON activity_submissions(tenant_id, draw_id, entry_id, submission_kind);

CREATE INDEX idx_activity_submissions_tally
  ON activity_submissions(tenant_id, draw_id, submission_kind, primary_value);

CREATE INDEX idx_activity_submissions_draw_time
  ON activity_submissions(tenant_id, draw_id, created_at);
```

字段含义：

| 字段 | 用途 |
|------|------|
| `entry_id` | 绑定现有参与记录，继续复用资格、去重、容量、邀请码、名单、密码逻辑。 |
| `submission_kind` | `survey` 或 `vote`。 |
| `primary_value` | 投票单选的 `optionId`；问卷为空。用于高效 group by，不扫描 JSON。 |
| `payload_json` | 问卷答案或投票提交详情，限制 10KB。 |

为什么不按每个问卷字段建列：

- 租户字段不同，列会爆炸。
- P1 目标是轻量 SaaS，不是数据库报表平台。
- 后台导出可以分页解析 JSON。
- 常用统计只对固定字段做轻量聚合，不做任意维度分析。

### 3.4 API

管理端：

```text
GET   /api/admin/draws/:id/activity-config
PATCH /api/admin/draws/:id/activity-config
GET   /api/admin/draws/:id/submissions?limit=50&offset=0
GET   /api/admin/draws/:id/tally
```

公开端：

```text
GET  /api/public/draws/:slug
POST /api/public/draws/:slug/join
POST /api/public/draws/:slug/verify-and-join
```

公开活动详情返回脱敏配置：

```json
{
  "activityConfig": {
    "version": 1,
    "kind": "vote",
    "vote": {
      "submitText": "投票",
      "showResults": "after_submit",
      "options": [
        { "id": "opt_a", "label": "方案 A", "description": "", "imageUrl": "" }
      ]
    }
  }
}
```

公开提交策略：

1. 不新增独立 `/submit` 热路径，优先扩展现有 `join` / `verify-and-join`，让“参与记录 + 提交记录”在一个事务里完成。
2. 校验资格通过后写 `lottery_entries`。
3. 根据 `activity_kind` 写 `activity_submissions`。
4. 写 `activity_events.participation_completed`。
5. 返回承接动作。

事务顺序：

```text
读取活动 -> 校验配置 -> 校验资格 -> insert entry -> insert submission -> record event -> return
```

不要先写 entry 后让前端再调提交接口，否则会产生“已参与但无问卷答案/无投票选择”的半成功数据。

### 3.5 校验

问卷提交：

- 必填字段必须有值。
- 字符长度按字段类型限制。
- `select/radio/checkbox` 只能提交配置中存在的 option value。
- 未配置字段忽略，不写入 payload。
- payload 超 10KB 直接拒绝。

投票提交：

- `optionId` 必须存在于配置选项。
- P1 只允许单选。
- 同一 `entry_id` 只能有一条 vote submission。
- 同一身份重复参与继续依赖 `lottery_entries` 唯一约束。

### 3.6 测试

必须补：

1. 创建 survey 活动时默认 `experience=form/result=no_result/winnerCount=0`。
2. survey 无字段时发布预检失败。
3. survey 必填字段缺失时提交失败。
4. survey 提交成功时同时写 entry + submission。
5. vote 少于 2 个选项时发布预检失败。
6. vote 选项不存在时提交失败。
7. vote 提交成功后 tally 按 `primary_value` 聚合。
8. 重复投票返回已参与/重复提交。
9. payload 超限拒绝。
10. 非当前租户不能读取 submissions。

## 四、方向 2：奖品图片媒体测试与 R2 存储治理

### 4.1 当前状态

已经具备：

- `prizes.image_url`
- `prizes.value_text`
- 后台奖品图片上传
- R2 binding `LOTTERY_MEDIA`
- 受控 key：`images/{uuid}.{jpg|png|webp|avif}`
- 公开读取：`/api/media/images/:filename`
- 单图 2MiB 限制
- 默认图由前端内联 SVG 提供，不写 DB
- 长缓存 header

### 4.2 风险判断

当前公开图片走 `/api/media/...`，因为 `wrangler.jsonc` 让 `/api/*` 进入 Worker，所以图片请求仍会计入 Worker 请求。

P1 可以接受的原因：

- 奖品图是少量运营图片。
- 默认图是内联 SVG，不产生额外请求。
- R2 读取有边缘缓存，能减少 R2 Class B 操作。

但必须设置边界：

```text
Free 阶段：只适合少量奖品图/活动图。
如果活动页图片访问量明显增加，应切换到 R2 自定义域名或其他静态直出方案，避免图片浏览消耗 Worker requests/day。
```

### 4.3 新增 `media_assets` 表

```sql
CREATE TABLE media_assets (
  id TEXT PRIMARY KEY,
  tenant_id TEXT NOT NULL,
  key TEXT NOT NULL UNIQUE,
  url TEXT NOT NULL,
  content_type TEXT NOT NULL,
  size_bytes INTEGER NOT NULL,
  status TEXT NOT NULL DEFAULT 'active',
  created_by TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE INDEX idx_media_assets_tenant_status
  ON media_assets(tenant_id, status, created_at);
```

作用：

1. 上传时记录 key/size/tenant。
2. 后台低频校验租户图片数量和容量。
3. 未来可做清理、禁用、迁移、自定义域名替换。
4. 平台可定位异常租户，不需要扫 R2 bucket。

P1 不做媒体库 UI，只做数据记录和治理基础。

### 4.4 配额建议

先写死代码常量，后续可接入套餐配置：

| 套餐 | 图片数量 | 图片总量 | 单图 |
|------|----------|----------|------|
| Free | 20 张 | 40MiB | 2MiB |
| Pro | 200 张 | 400MiB | 2MiB |
| Team | 1000 张 | 2GiB | 2MiB |

说明：

- 上传是后台低频动作，上传时做一次 `COUNT/SUM(size_bytes)` 可以接受。
- 公开读取不查 `media_assets`，只按 managed key 和 R2 读取，避免每张图片多一次 DB read。
- 删除功能 P1 可不做；如做删除，只标记 `status=deleted` 并异步/手工清理 R2。

### 4.5 测试

参考 cf-shop 的媒体测试，适配本项目返回结构和 RBAC：

1. owner/admin 可上传合法 PNG/JPEG/WebP/AVIF。
2. viewer 上传返回 403。
3. 未绑定 `LOTTERY_MEDIA` 返回 503。
4. MIME 声明和文件签名不一致返回 400，且不写 R2。
5. 超过 2MiB 返回 400 或 413。
6. 空文件返回 400。
7. SVG/GIF 拒绝。
8. 公开读取只允许 managed key。
9. 路径穿越不读 R2。
10. 返回 `Cache-Control`、`Content-Type`、`Content-Disposition`、`X-Content-Type-Options: nosniff`。
11. 上传成功写 `media_assets` 和租户审计。

## 五、方向 3：发布前预检升级

### 5.1 当前状态

已有 `GET /api/admin/draws/:id/publish-check`，可以做基础校验。

问题是覆盖范围还不够：

- 问卷无字段也可能发布。
- 投票无选项也可能发布。
- CTA/Webhook 风险没有统一提示。
- 奖项绑定和码池不足需要更清晰。
- 前端发布按钮附近需要展示预检结果，而不是让运营靠记忆。

### 5.2 预检规则

通用规则：

| 类型 | 规则 |
|------|------|
| 基础 | title/startAt/endAt 必填；endAt > startAt；scheduled 必须有 drawAt。 |
| 容量 | `maxParticipants` 建议有值；Free 默认不建议超过 1000。 |
| 准入 | roster 必须有名单；invite_code 必须有可用邀请码；password 必须设置密码。 |
| 承接 | `promotion_config.enabled=true` 时必须有合法 URL 和标题；没有任何 CTA 时给 warning。 |
| Webhook | 已配置 webhook 但无有效 URL/事件为空给 warning/error。 |
| 公开链接 | 必须有 `public_slug`。 |

抽奖规则：

| 规则 | 级别 |
|------|------|
| 至少一个奖项 | error |
| 奖项必须绑定奖品 | error |
| 实物/卡密类奖品的可用码少于中奖名额 | warning 或 error，按 prizeType 决定 |
| `winnerCount` 与奖项合计不一致 | warning |
| `experience_type` 是转盘/老虎机时，提示最终结果以后端为准 | info |

问卷规则：

| 规则 | 级别 |
|------|------|
| 字段数为 0 | error |
| 字段 key 重复 | error |
| 必填字段 label 为空 | error |
| select/radio/checkbox 选项少于 2 个 | error |
| 字段过多或 payload 可能过大 | warning |

投票规则：

| 规则 | 级别 |
|------|------|
| 选项少于 2 个 | error |
| option id 重复 | error |
| option label 为空 | error |
| 选项超过 30 个 | error |
| 未配置结果展示口径 | warning |

接龙规则：

| 规则 | 级别 |
|------|------|
| 没有设置容量 | warning |
| 候补开启但成功/候补承接文案缺失 | warning |

### 5.3 API 返回结构

```json
{
  "canPublish": false,
  "errors": [
    { "code": "vote.options.min", "message": "投票至少需要 2 个选项", "section": "activity_config" }
  ],
  "warnings": [
    { "code": "promotion.empty", "message": "未配置提交后的承接动作", "section": "promotion" }
  ],
  "infos": [
    { "code": "media.default_image", "message": "未上传奖品图时将使用默认图", "section": "prizes" }
  ]
}
```

前端展示：

- 发布按钮旁显示 `可发布 / 需修复 / 有提醒`。
- 错误阻止发布。
- warning 不阻止，但必须可见。
- 点击预检项滚动到对应表单区域。

### 5.4 成本控制

发布预检是后台低频操作，可以做必要 COUNT：

- 名单数量 COUNT。
- 邀请码可用数量 COUNT。
- 奖品码池 COUNT。
- Webhook 配置读取。

不能做：

- 扫描全租户活动。
- 扫描所有历史事件。
- 生成大 CSV。

## 六、方向 4：租户侧活动漏斗看板

### 6.1 当前状态

已有：

- `activity_events`
- 公开端基础自动埋点
- `getActivityEventSummary()`
- 管理端统计基础
- 外部转化回传表

问题：

- 运营者需要看漏斗，不是看原始事件。
- 需要能判断哪里掉了：有浏览没人开始、有开始没人完成、有完成没人点 CTA、有 CTA 没外部转化。

### 6.2 P1 看板设计

单活动详情中新增“复盘”区域：

```text
浏览 page_view
开始 participation_started
完成 participation_completed
CTA 点击 cta_click
分享 share_click
有效邀请 attributed_join
外部转化 external_conversion_reported
```

展示指标：

| 指标 | 计算 |
|------|------|
| 开始率 | started / page_view |
| 完成率 | completed / started |
| CTA 点击率 | cta_click / completed |
| 分享率 | share_click / completed |
| 外部转化率 | external_conversion / completed |

前端文案必须用运营语言：

```text
浏览
开始参与
完成参与
点击承接
分享
外部转化
```

不要使用 `event_type` 原始英文暴露给客户。

### 6.3 后端策略

P1 继续使用现有汇总接口即可：

```text
GET /api/admin/draws/:id/analytics
GET /api/admin/draws/:id/events/summary
GET /api/admin/draws/:id/conversions
```

低频后台读取可以按单活动聚合。不要在公开端每次页面加载时查询统计。

后续 P2 再增加日粒度快照：

```text
activity_event_daily_snapshots
tenant_id, draw_id, date, page_view, started, completed, cta_click, share_click, external_conversion
```

触发条件：

- 单活动事件超过 50,000。
- 管理端统计响应超过 1 秒。
- Turso rows read 明显被事件汇总拖高。

### 6.4 事件写入治理

公开事件仍是最大风险之一。P1 策略：

1. 事件类型白名单保留。
2. 字段长度限制保留。
3. `page_view` 可采样或按 session/window 去重。
4. `cta_click/share_click/participation_completed` 保持强记录。
5. 不把公开事件全部写入持久化限流表。
6. 用 `ipHash + slug + eventType + minute bucket` 做内存限流；需要持久化时只对高价值事件做低基数聚合。

## 七、方向 5：平台 owner 初始化与独立平台审计

### 7.1 首个 platform_owner 初始化

不推荐做公开 bootstrap endpoint。

原因：

- 公共端点容易出现遗留风险。
- 初始化是一次性运维动作，不应长期暴露在 Worker 路由。
- Cloudflare Free 下也没必要为一次性动作增加运行时判断。

推荐方案：

```text
scripts/bootstrap-platform-owner.mjs
```

输入：

```bash
node scripts/bootstrap-platform-owner.mjs --email owner@example.com --role platform_owner
```

行为：

1. 读取本地 `.env` 或部署环境中的 Turso 连接配置。
2. 查找 `users.email`。
3. 如用户不存在，提示先通过平台注册/创建租户账号。
4. 插入或更新 `platform_members(user_id, role, status='active')`。
5. 打印可审计结果。

安全规则：

- 只允许 `platform_owner/platform_operator/platform_support`。
- 默认只创建 `platform_owner`。
- 不支持通过普通租户后台升级平台角色。
- 不创建 `tenant_id=NULL` 或 `__platform__` 特殊租户。

### 7.2 独立平台审计表

新增：

```sql
CREATE TABLE platform_audit_logs (
  id TEXT PRIMARY KEY,
  actor_user_id TEXT NOT NULL,
  actor_role TEXT NOT NULL DEFAULT '',
  action TEXT NOT NULL,
  target_type TEXT NOT NULL,
  target_id TEXT NOT NULL DEFAULT '',
  tenant_id TEXT NOT NULL DEFAULT '',
  metadata_json TEXT NOT NULL DEFAULT '{}',
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE INDEX idx_platform_audit_created
  ON platform_audit_logs(created_at);

CREATE INDEX idx_platform_audit_tenant
  ON platform_audit_logs(tenant_id, created_at);

CREATE INDEX idx_platform_audit_action
  ON platform_audit_logs(action, created_at);

CREATE INDEX idx_platform_audit_actor
  ON platform_audit_logs(actor_user_id, created_at);

CREATE INDEX idx_platform_audit_target
  ON platform_audit_logs(target_type, target_id, created_at);
```

必须记录的平台写操作：

| 操作 | action |
|------|--------|
| 修改系统配置 | `platform.system_config.update` |
| 重置系统配置 | `platform.system_config.reset` |
| 生成额度码 | `platform.redemption_codes.batch_create` |
| 修改租户套餐/状态 | `platform.tenant.update` |
| 新增/停用平台成员 | `platform.member.update` |
| 手动重跑 Webhook | `platform.webhook.retry` |

不要用租户 `audit_logs` 承载平台审计，因为这会污染租户隔离和统计。

### 7.3 平台审计 UI

P1 只做最小列表：

```text
时间
操作者
角色
操作
目标
关联租户
摘要
```

查询限制：

- 默认 50 条，最大 200。
- 按时间倒序。
- 支持 action/actor/tenantId 简单筛选。
- 不做全文搜索。

## 十、容量预算

### 10.1 单次公开参与预算

目标：

```text
DB read：1-3 次
DB write：2-4 次
Worker CPU：只做 JSON 校验、字符串校验、少量 hash
payload：<= 10KB
```

普通抽奖：

```text
读活动 1
写 entry 1
写 event 1
必要时写 outcome/winner/code
```

问卷：

```text
读活动 1
写 entry 1
写 submission 1
写 event 1
```

投票：

```text
读活动 1
写 entry 1
写 submission(primary_value=optionId) 1
写 event 1
```

### 10.2 后台统计预算

后台可以做单活动聚合，但要分页：

```text
submissions 列表默认 50，最大 200
导出最大 10,000 行，超过后提示分批或未来异步导出
event summary 单活动聚合，超过阈值后切日快照
```

### 10.3 媒体预算

```text
单图 2MiB
Free 租户建议 20 张 / 40MiB
默认图内联，不产生请求
/api/media 图片请求仍计入 Worker requests/day
大流量图片触发迁移到 R2 自定义域名或静态直出
```

## 十一、最终验收口径

这 5 项完成后，系统才算进入“受控 Beta 可运营”状态：

1. 运营者能从模板创建抽奖、问卷、投票，并在 3 分钟内完成必要配置。
2. 发布前预检能阻止明显错误：无奖项、码池不足、问卷无字段、投票无选项、CTA/Webhook 配置异常。
3. 奖品图片上传安全、可追踪、可限额，公开页默认图稳定。
4. 活动结束后，租户能看到浏览、开始、完成、CTA、分享、外部转化漏斗。
5. 平台方能初始化 owner、查看平台审计、追踪租户用量和异常。

不满足以上任一项，不应宣传为“完整 SaaS 平台”，只能称为“内部测试版活动引擎”。
