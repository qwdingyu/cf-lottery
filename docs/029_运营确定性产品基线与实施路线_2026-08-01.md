# 运营确定性产品基线与实施路线

> 文档编号：029
> 日期：2026-08-01
> 定位：把 cf-lottery 从“玩法集合”校准为“轻量 SaaS 运营确定性平台”的后续开发基准。

---

## 一、核心结论

用户真正购买的不是抽奖、接龙、问卷这些玩法本身，而是：

```text
快速创建
少出错
能复盘
能承接
能接系统
能托管运营
```

因此后续所有玩法都必须服从同一套活动引擎骨架：

```text
activity       创建与配置
participant    资格、去重、容量
outcome        结果、候补、发放
event          浏览/开始/完成/点击/分享
promotion      CTA、资料、优惠、下一活动
integration    Webhook、API Key、外部转化回传
operation      平台租户、套餐、用量、失败任务、异常
```

新增玩法只有在复用这些骨架时才允许进入；不允许为单个玩法另起一条独立主链路。

## 二、系统配置路由口径

### 2.1 为什么不能使用 `/api/admin/system-config`

`/api/admin/*` 的冻结语义是租户后台。系统配置是平台级能力，不能放回 admin 命名空间。

错误做法：

```ts
await adminRequest<any>('/api/admin/system-config')
```

风险：

- 把 L3 平台配置重新暴露给 L2 租户后台。
- 违背 024/026 已冻结的 `/api/admin/*` 与 `/api/platform/*` 分层。
- 未来维护者会误以为租户管理员可管理全局配置。

### 2.2 为什么保存后读取 `/api/system-config/system-config`

`/api/system-config/system-config` 不是管理入口，而是公开读取入口：

- 无鉴权。
- 只返回 `PUBLIC_SYSTEM_CONFIG_KEYS` 白名单。
- 用于前台公开页面读取可公开配置。
- 在平台配置页保存 `scope = public` 的配置后，请求该接口只是做“公开端是否可读”的同步验证。

因此前端应保留两个常量：

```ts
const PLATFORM_SYSTEM_CONFIG_API = '/api/platform/system-config'
const PUBLIC_SYSTEM_CONFIG_API = '/api/system-config/system-config'
```

两者不是不一致，而是语义不同：

| 常量 | 路由 | 权限 | 返回内容 | 用途 |
|------|------|------|----------|------|
| `PLATFORM_SYSTEM_CONFIG_API` | `/api/platform/system-config` | `platform_owner` | 完整配置和 definitions | 平台管理读写 |
| `PUBLIC_SYSTEM_CONFIG_API` | `/api/system-config/system-config` | 无鉴权 | 公开白名单配置 | 前台公开配置验证 |

## 三、六类运营确定性能力矩阵

| 用户诉求 | 必须能力 | 当前状态 | 下一步 |
|----------|----------|----------|--------|
| 快速创建 | 模板、复制、二维码、默认规则 | 复制/二维码基础已有，默认规则已后端化 | 建活动模板表或模板 JSON；把复制提升为“从模板创建” |
| 少出错 | 资格校验、去重、容量、候补、码池、防重复发放 | 去重、容量、候补、码池、CAS 发放基础已建 | 补发布前校验清单和玩法级规则预检 |
| 能复盘 | 浏览、开始、完成、CTA、分享、外部转化 | `activity_events`、`share_records`、`external_conversions` 基础已建 | 补租户侧漏斗看板、来源治理、异常事件采样 |
| 能承接 | 未中奖/候补/提交成功后的 CTA、资料、优惠、下一活动 | `promotion_config`、优惠券码池基础已建 | 统一 Outcome 后动作：CTA/资料/优惠/下一活动 |
| 能接系统 | Webhook、API Key、导出、外部转化回传 | API Key、Webhook delivery、外部转化回传、导出基础已建 | 补 Webhook 失败告警、租户侧可视化、API Key scope |
| 能托管运营 | 平台方看租户、套餐、用量、失败任务、异常 | `/api/platform/*` 基础路由和用量快照已建 | 补平台审计、异常规则、首个 platform_owner 初始化 |

## 四、后续实施顺序

### 阶段 A：发布前必须闭合

1. 保持 `/api/admin/*` 只做租户后台，禁止恢复 `/api/admin/system-config`。
2. 保持 `/api/platform/*` 只做平台后台，平台写操作后续必须补审计。
3. 所有新增 schema 必须有 migration，并通过迁移验证。
4. 公开热路径只做必要查询和写入，事件与限流不能失控写表。
5. 平台运营用量接口优先读快照，缺失时只做低频兜底。

### 阶段 B：Beta 可运营

1. 活动模板：把“复制活动”产品化成模板库。
2. 发布前校验：资格、容量、时间、码池、Webhook 配置、CTA 配置。
3. 统一承接配置：提交成功、候补、未中奖、中奖后分别配置 CTA。
4. 租户漏斗看板：浏览、开始、完成、CTA、分享、外部转化。
5. 平台异常看板：失败 Webhook、异常事件写入、用量突增、接近套餐上限。

### 阶段 C：小规模商业化

1. 资料领取/问卷 vertical slice：复用 entry/event/promotion，不做重型表单平台。
2. 接龙稳定化：候补转正、通知、导出、后台调整状态。
3. API Key scope：外部转化、Webhook、只读导出分别授权。
4. 平台审计表：所有平台写操作留痕。
5. 用量快照保留策略：日快照保留 90 天，月汇总长期保留。

## 五、验收口径

一个新功能只有同时回答以下问题，才算符合“运营确定性”：

1. 运营者能否在 3 分钟内创建并发布？
2. 参与者是否不会因资格、容量、重复提交而得到错误结果？
3. 活动结束后是否能复盘从浏览到转化的关键链路？
4. 每种结果状态是否有承接动作？
5. 外部系统失败时是否能重试、查看、定位？
6. 平台方是否能看到租户用量和异常，不需要直接查数据库？

如果只新增了一个玩法入口，但没有这些闭环，就是错的。
