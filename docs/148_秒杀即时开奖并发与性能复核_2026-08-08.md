# 秒杀即时开奖并发与性能复核

日期：2026-08-08

## 一、审查范围与结论

本次复核覆盖本地 SQLite / libSQL 驱动的事务语义、秒杀参与、即时开奖、支付超时释放、定时开奖和未中奖发券链路。

结论必须区分两件事：

1. **当前单 Node + 本地 SQLite 的正确性**：写事务通过 `BEGIN IMMEDIATE` 串行化，现有秒杀名额 CAS 和即时开奖的奖档 COUNT 不会出现两个已开始的写事务同时基于同一旧快照提交。
2. **可迁移的领域正确性**：奖档上限目前由 `COUNT(lottery_winners)` 推导，没有保存为可条件更新的事实。迁移到 PostgreSQL/MySQL、多进程多写者或修改事务实现前，必须改为奖档计数器 CAS；不能把 SQLite 当前的串行副作用当作业务约束。

因此，“instant spin 奖档没有 CAS”是**迁移前 P0 架构风险**，但不是已经证实的当前 SQLite 超发事故。

## 二、busy_timeout = 5000 的判定

### 2.1 不是 WAL 的重复配置，但不适合放在请求中间件

`PRAGMA journal_mode = WAL` 与 `PRAGMA busy_timeout` 解决的问题不同：

- WAL 允许读与写并发，仍只有一个写事务。
- busy_timeout 是**连接级**的 SQLite 锁等待时间。

当前中间件每个请求创建一个 `@libsql/client`，若在 `src/index.ts` 设置 busy_timeout，就会给每个请求连接设置原生同步锁等待。`@libsql/client@0.14.0` 的 file driver 中，事务开始和 SQL 执行直接同步调用原生 SQLite；Drizzle 的 `transaction()` 默认发起 write transaction，最终为 `BEGIN IMMEDIATE`。

实测命令：

```bash
npm run benchmark:sqlite -- --cas-requests=10 --count-iterations=10 --busy-timeout-ms=0
npm run benchmark:sqlite -- --cas-requests=10 --count-iterations=10 --busy-timeout-ms=5000
```

同一开发机本轮结果：

| busy_timeout | 成功 | 总耗时 | p50 | 应用层总重试 |
|---:|---:|---:|---:|---:|
| 0ms | 10 | 399.506ms | 355.868ms | 18 |
| 5000ms | 10 | 47,103.409ms | 47,085.531ms | 18 |

5000ms 没有降低重试次数，只在每次锁竞争前增加最多 5 秒的原生阻塞。当前保留 `withDbTransaction()` 的 5 次、50ms 起步、有界异步指数退避是正确选择；该等待通过 `setTimeout` 让出 Node 事件循环。

`src/db/apply-migrations.ts` 中的 5000ms 可以保留：迁移在服务开始接收请求前运行，目标是避免两个启动者同时执行 DDL 时立即失败，和请求热路径不是同一个场景。

### 2.2 已落实的代码修正

已从 `src/index.ts` 撤回请求连接的 `PRAGMA busy_timeout = 5000`，并把原有“WAL 防 database locked”的误导性注释改为准确说明：WAL 不取消 SQLite 单写者约束。

## 三、逐项核对

| 结论项 | 判定 | 证据与准确表述 |
|---|---|---|
| 即时开奖逐奖档 COUNT、没有奖档 CAS | 属实 | `spin-execution.ts` 对每个候选奖档执行 `COUNT(lottery_winners)`，再调用 `weightedPickTier()`；`lottery_prize_tiers` 尚无 `awarded_count`。 |
| 当前 SQLite 会因此立即超发 | 不属实 | 事务在首次业务 SQL 前已用 `BEGIN IMMEDIATE` 获取写锁；`spins_left` 条件 UPDATE、奖档 COUNT、写 winner 在同一短写事务内串行执行。 |
| 迁移 PG/MySQL 时会有超发风险 | 属实 | MVCC 下两个事务可读取相同 `COUNT=0` 后都写 winner。不能只依赖“先读再写”。但并不意味着所有查询都要加 `FOR UPDATE`；应优先使用条件 UPDATE CAS，只在确有读改写需求时锁定具体行。 |
| 普通参与每次都有全活动 COUNT | 基本属实，但原表述不精确 | `participation.ts` 的条件 INSERT 在**非直付秒杀**路径使用活动维度 COUNT；候补活动绕过容量条件，直付秒杀已经改用活动计数器 CAS。该 COUNT 命中覆盖索引，但复杂度仍随该活动 entries 增长。 |
| 每次 spin 对每奖档一次 COUNT | 属实 | 当前没有 `(tenant_id, draw_id, tier_id)` winners 索引，查询至少要扫描活动 winners 的索引范围。 |
| 定时开奖全量加载 entries | 属实 | `draw-execution.ts` 读取整个候选池后再做等权或加权无放回抽样。此为 P2 内存/延迟问题，不能在未验证公平算法前草率改成随机 SQL。 |
| 未中奖发券全量加载且逐条更新 | 属实 | `grantLoserRewards()` 读取全部 entries、全部 winners、可用券后逐条 CAS 更新。此为 P2 批处理性能问题。 |
| SQLite 单写者是高峰瓶颈 | 属实 | WAL 不改变写事务串行化。支付回调、秒杀参与、发卡与活动事件会竞争同一写者。是否需要队列或 PostgreSQL，必须由目标 VPS 的混合压测决定。 |
| activity_events 缺少归档策略 | 属实 | schema 只有查询索引，没有保留周期、归档任务或容量水位。属于运营性 P2，先补监控和归档方案，不以理论行数直接断言上线不可用。 |
| 现有测试完全没有并发场景 | 不属实 | `spin-execution.test.ts` 已覆盖同 entry 的双并发扣次、两个用户争抢一张卡密；`security-audit-verification.test.ts` 覆盖 20 并发限流。 |

## 四、奖档 CAS 的一步到位方案

不要只为当前 COUNT 增加一个临时 winners 索引。应把奖档可发放数量建模为长期领域事实。

1. 在 `lottery_prize_tiers` 增加 `awarded_count INTEGER NOT NULL DEFAULT 0`。
2. 迁移时按 `lottery_winners` 的 `(tenant_id, draw_id, tier_id)` 聚合回填；回填后必须校验 `0 <= awarded_count <= winner_count`。
3. 即时开奖抽到某档后，在同一事务先执行：

```sql
UPDATE lottery_prize_tiers
SET awarded_count = awarded_count + 1
WHERE id = ?
  AND tenant_id = ?
  AND draw_id = ?
  AND awarded_count < winner_count;
```

只有 `rowsAffected = 1` 才能进入该档的卡密领取和 winner 写入。CAS 失败时从候选集合移除此档并重新抽取，直至命中可用档或成为未中。

4. 卡密奖品必须把“奖档占位、卡密 CAS、spin/winner 落库”放在同一数据库事务。码池不足时，在提交未中结果前把该档 `awarded_count` 回退；事务未提交前其他事务不可观察到临时占位。
5. 定时开奖同样维护 `awarded_count`，否则同一张 tier 表会出现“计数列只对 instant 可信”的双重语义。活动模式虽互斥，数据不变量不应分叉。
6. 增加后台校验/修复工具：定期按 winners 聚合，与 `awarded_count` 比较；发现不一致先报警，人工确认后才执行修复，禁止静默覆盖。

这项改造完成前，不应把 PostgreSQL/MySQL 多写者迁移列为可执行事项。

## 五、测试真实缺口

已有并发用例不能替代以下四类：

1. 两个不同 entry 并发抽 `winner_count=1` 的同一奖档，断言只有一个 winner，且未来 `awarded_count=1`。
2. 两个并发 `createPaymentOrder()` 请求同一个 `reserved` entry，断言只产生一个 order/attempt，另一个得到“预约已失效”。
3. 两个并发 `handlePaymentCallback()` 针对同一 attempt，断言只发一张卡密、订单最终为 paid 或 paid_fulfillment_failed，重复回调幂等。
4. `expireOverdueOrders()` 与支付回调并发，断言结果只可能是“先支付并履约”或“先过期后进入 paid_late_needs_refund”，绝不出现卡密已发而名额已释放。
5. 两个不同身份同时参与最后一个直付秒杀名额，使用真实多个 libSQL client，断言成功数、`active_participant_count` 和 `reserved/pending/paid` entries 数一致。

需特别澄清：最后一个秒杀名额由 `joinDraw()` 的活动级 CAS 占用，不是由 `createPaymentOrder()` 抢占；两类测试必须分开，避免把错误层级的测试误当作覆盖。

## 六、优先级与发布判断

| 优先级 | 工作项 | 当前结论 |
|---|---|---|
| P0 | 奖档 `awarded_count` CAS、迁移回填、双写路径维护、并发回归 | PostgreSQL/MySQL 或多写者迁移前必须完成；当前 SQLite 发布前应完成以消除架构债。 |
| P0 | 支付回调与过期释放的竞争测试 | 必须补齐，支付、发卡和名额释放属于资金/库存核心链路。 |
| P1 | 目标 VPS 的公开参与 + 下单 + 回调 + 发卡 + 事件混合压测 | 未完成前不能给出秒杀 TPS、名额上限或在线人数承诺。 |
| P1 | 普通活动容量计数器设计 | 先定义候补、取消、签到、开奖的独立计数语义；不能直接复用直付秒杀的 `active_participant_count`。 |
| P2 | 定时开奖流式/抽样改造、未中奖发券批处理、事件归档 | 以真实活动规模和 p95/p99 为触发条件，不做无证据优化。 |

本次审查不批准“已可按任意数据库横向扩展”的结论；批准继续使用当前单 Node + SQLite 架构进行测试，但必须按以上 P0/P1 顺序收口。
