# 剩余性能优化点跟踪

> 基于 153 上线审查分析 + 二次验证后整理的 3 个真实优化点。
> 当前数据量下均不影响运行安全，按数据量增长触发后逐步实施。

## 背景

在 153 上线审查中，对后端竞争条件、查询效率、扩展性进行了全面分析。经过 commit `0a2d294` 的修复后，以下 3 个问题被识别为"数据量增长后的性能问题"，在当前用户规模下不阻断上线，但需要跟踪记录。

---

## 1. `performDraw` 全量加载候选池到内存

### 级别

P1 — 中等风险，数据量增长后触发

### 位置

`src/services/lottery/draw-execution.ts:142-145`

```typescript
// 当前代码：全量加载所有参与者到内存
const entries = await db
  .select()  // SELECT * FROM lottery_entries WHERE draw_id = ?
  .from(lotteryEntries)
  .where(eq(lotteryEntries.drawId, drawId));
```

### 问题描述

`performDraw` 函数将活动的所有参与者记录一次性加载到 Node.js 内存中进行随机抽取。当参与人数达到 10 万级时：

1. **基础内存占用**：每条 entry 约 200-400 字节，10 万条 ≈ 20-40 MB（尚可接受）
2. **裂变加权场景**：`weightedPool` 展开权重（一个 entry 权重可达 1+100），展开后数组可能达到数百万元素，每个元素包含完整 entry 对象 + 权重数字，内存占用呈倍数增长
3. **`weightedSampleUnique` 内部实现**：使用"按权无放回"算法，需要额外的 Set 和 Map 数据结构跟踪已抽取项

### 触发条件

- 单活动参与人数 > 50,000（裂变加权时触发更早）
- 同时开奖多个大活动

### 建议方案

改为数据库级分批抽取，避免全量加载到内存：

```typescript
// 方案：SELECT COUNT(*) 获取总数，然后按需随机抽取
// 等权抽取：使用 ORDER BY random() LIMIT 1 OFFSET ?
// 裂变加权：在数据库层面计算权重后分批拉取

// 示例：等权场景
const [countRow] = await db
  .select({ count: count() })
  .from(lotteryEntries)
  .where(eq(lotteryEntries.drawId, drawId));

const totalEntries = Number(countRow?.count || 0);
// 逐个随机抽取（每次随机选一个偏移量）
for (let i = 0; i < totalWinners; i++) {
  const offset = randomInt(totalEntries - i);  // CSPRNG
  const [entry] = await db
    .select()
    .from(lotteryEntries)
    .where(eq(lotteryEntries.drawId, drawId))
    .limit(1)
    .offset(offset);
  // ... 处理中奖逻辑
  // 移除已中奖者（通过排除 ID 或标记）
}
```

### 预计成本

约 2 小时（含测试验证）

## 2. Admin 活动列表 OFFSET 分页

### 级别

P2 — 低风险，数据量较大后触发

### 位置

`src/routes/admin-lottery.ts:371-372`

```typescript
// 当前代码：使用 OFFSET 分页
.limit(limit)   // 默认 50，最大 200
.offset(offset); // 最大允许 100,000
```

分页函数定义在 `src/routes/admin-lottery-helpers.ts:170-175`：

```typescript
export function parseAdminPagination(c, fallbackLimit = 50, maxLimit = 200) {
  return {
    limit: clampInteger(c.req.query("limit"), fallbackLimit, 1, maxLimit),
    offset: clampInteger(c.req.query("offset"), 0, 0, 100_000),
  };
}
```

### 问题描述

SQLite 的 `OFFSET` 分页在偏移量增大时性能退化——它仍然需要扫描和跳过所有被跳过的行。虽然 `idx_draws_tenant_status` 索引覆盖了 `(tenantId, status, createdAt)` 排序，但 `OFFSET 50000` 仍然需要扫描 50000 行索引条目。

### 触发条件

- 单租户活动数量 > 10,000
- 运营者翻到第 200 页以后（每页 50 条）

### 建议方案

已实施（2026-08-08）。方案概述：

**后端**（`src/routes/admin-lottery.ts`）：
- 新增 `cursor` 参数（base64 编码的 `createdAt,id` 复合游标）
- `ORDER BY createdAt DESC, id DESC`（增加 id 作为去重键，确保排序确定性）
- 游标模式：`WHERE (createdAt < cursorCreatedAt) OR (createdAt = cursorCreatedAt AND id < cursorId)`
- 始终多取 1 条（`LIMIT limit + 1`）判断 `hasMore` 并生成 `nextCursor`
- 保留 `offset` 参数兼容旧版页码跳转（`@jump` 事件）
- `cursor` 与 `offset` 同时提供时 `cursor` 优先

**前端**（`AdminLotteryView.vue`）：
- 新增 `cursorMap: Map<number, string>` 记录每页对应的游标
- 顺序翻页（prev/next）时使用 `cursorMap` 中缓存的游标
- 跳页（`@jump`）时若目标页游标未知则回退到 `offset` 分页
- 筛选变化时 `resetCursorMap()` 清空游标缓存回到第一页

**工具函数**（`src/routes/admin-lottery-helpers.ts`）：
- `encodeDrawCursor(createdAt, id)` — 编码游标
- `decodeDrawCursor(cursor)` — 解码游标

**测试**（`src/routes/p0-flow.test.ts`）：
- 验证 3 页分页无重复/遗漏
- 验证 `hasMore` / `nextCursor` / `total` 正确性

### 预计成本

约 1 小时（含前端游标传递改造）

## 3. Dashboard 实时 COUNT 聚合

### 级别

P3 — 低风险，运营者规模扩大后触发

### 位置

`src/routes/admin-lottery.ts:101-127`

```typescript
// 当前代码：每次 Dashboard 加载执行 5 个独立 COUNT(*)
const [openRow] = await db.select({ count: sql<number>`COUNT(*)` }).from(lotteryDraws)
  .where(and(eq(lotteryDraws.tenantId, tenantId), eq(lotteryDraws.status, "open")));
const [draftRow] = await db.select({ count: sql<number>`COUNT(*)` }).from(lotteryDraws)
  .where(and(eq(lotteryDraws.tenantId, tenantId), eq(lotteryDraws.status, "draft")));
const [drawnRow] = await db.select({ count: sql<number>`COUNT(*)` }).from(lotteryDraws)
  .where(and(eq(lotteryDraws.tenantId, tenantId), eq(lotteryDraws.status, "drawn")));
const [dueRow] = await db.select({ count: sql<number>`COUNT(*)` }).from(lotteryDraws)
  .where(and(eq(lotteryDraws.status, "open"), sql`${lotteryDraws.drawAt} <= ${now}`));
const [failedNotifyRow] = await db.select({ count: sql<number>`COUNT(*)` }).from(lotteryWinners)
  .where(and(eq(lotteryWinners.tenantId, tenantId), eq(lotteryWinners.notificationStatus, "failed")));
```

### 问题描述

每次运营者加载 Dashboard，后端执行 5 次独立的 `COUNT(*)` 查询。虽然索引覆盖了大部分查询：

- `openCount` / `draftCount` / `drawnCount`：`idx_draws_tenant_status` 覆盖
- `dueCount`：`idx_draws_due` 覆盖
- `failedNotifyCount`：`idx_winners_notification_status` 覆盖（新增）

但高频刷新（如每 30 秒自动刷新）时，多次索引范围扫描仍会增加数据库压力。

### 触发条件

- 同时有 50+ 运营者频繁刷新 Dashboard
- 或 Dashboard 配置了自动刷新（如每 30 秒轮询）

### 建议方案

利用已有的 `usage_snapshots` 表，将 COUNT 聚合值写入快照，Dashboard 直接读快照：

```typescript
// 方案 A：Cron 写入快照（约 5 分钟间隔）
// 在 src/services/admin/usage-snapshots.ts 中增加聚合逻辑
// Dashboard 读快照而非实时 COUNT

// 方案 B：懒缓存（简单的内存缓存，TTL 30 秒）
// Dashboard 端点首次加载走实时 COUNT，缓存结果 30 秒
// 30 秒内同一租户的后续请求直接返回缓存
```

### 预计成本

约 3 小时（含快照写入逻辑 + Dashboard 读取改造）
