# 发布前预检结构化门禁实施记录

> 文档编号：035  
> 日期：2026-08-01  
> 定位：记录 P1.18 的实现基线和后续扩展边界。  
> 前置约束：Cloudflare Workers Free + Turso/libSQL Free，发布预检必须低频、轻量、可解释，不允许演变成重型规则引擎。

---

## 一、本轮决策

本轮优先做“发布门禁”，而不是继续新增玩法。

原因：

1. SaaS 客户真正购买的是快速创建、少出错、能承接、能复盘。
2. 抽奖、接龙、问卷、投票只是入口；如果发布时缺奖项、码池、资格、CTA 或 Webhook，活动会直接损害客户信任。
3. 问卷/投票当前没有字段配置器和提交结构闭环，继续允许正式发布会造成“看起来有玩法、实际不可运营”的灾难。

---

## 二、实现基线

新增统一服务：

```text
src/services/publish-check-service.ts
```

返回结构：

```json
{
  "canPublish": false,
  "errors": [
    { "code": "prizes.tiers.required", "message": "抽奖活动必须至少配置一个奖项", "section": "prizes" }
  ],
  "warnings": [],
  "infos": []
}
```

已接入两个入口：

```text
GET /api/admin/draws/:id/publish-check
POST /api/admin/draws/:id/publish
```

真实发布服务 `publishDraw()` 也复用同一套校验，避免未来出现“前端预检拦住，但脚本/API 仍能发布”的规则漂移。

---

## 三、当前校验范围

阻断项：

- 活动标题为空。
- 公开 slug 缺失。
- 活动时间缺失、格式错误、开始不早于结束、结束时间已过。
- 定时开奖未设置开奖时间，或开奖时间不晚于参与结束时间。
- 密码模式未设置访问密码。
- 名单模式未导入名单。
- 邀请码模式没有可用邀请码。
- 抽奖活动没有奖项。
- 奖项未关联可用奖品。
- 卡密奖品可用码数量小于中奖名额。
- 导流配置 JSON 非法或导流 URL 非 http/https 外部地址。
- 启用的 Webhook URL 或事件列表无效。
- 问卷字段配置器未完成前禁止正式发布。
- 投票选项配置器未完成前禁止正式发布。

非阻断提示：

- 未配置参与完成后的 CTA/导流承接。
- 未配置 Webhook，外部系统不会自动接收事件。
- 奖品未上传图片时使用默认图。
- 奖品未填写价值展示文案。
- 活动中奖人数和奖项名额合计不一致。

---

## 四、Free 计划资源判断

发布预检是后台低频操作，可以接受少量必要 COUNT，但必须满足：

- 查询只围绕当前 `tenant_id + draw_id`。
- 码池查询只查当前奖品的 `available` 数量。
- Webhook 只查当前租户启用配置，并限制读取数量。
- 不在公开热路径新增全局统计。
- 不把 page_view、点击等高频事件接入数据库限流。

因此本轮没有引入缓存、队列、规则 DSL 或预聚合表。等活动规模和真实 rows read 数据出现后，再按观测结果决定是否预聚合。

---

## 五、测试覆盖

本轮补充/调整：

- 抽奖无奖项不能发布。
- 卡密码池不足不能发布。
- 名单/邀请码模式必须具备资格数据。
- 有效抽奖可以发布，但返回 CTA/Webhook/默认图提示。
- 问卷未完成字段配置闭环前不能正式发布。
- 投票未完成选项配置闭环前不能正式发布。
- 服务层测试的 `setupDraw()` 不再鼓励空奖池发布，而是先配置独立手动发放奖品。

验证命令：

```bash
npm run type-check:all
npm run test
npm run frontend:build
node scripts/verify-migrations.mjs
git diff --check
```

## 六、后续边界

下一步不能继续把问卷/投票塞进描述或 `identity_value`。

正确方向：

1. 新增轻量 `activity_config`：版本化 JSON，保存问卷字段、投票选项、资料领取配置。
2. 新增 `activity_submissions`：保存结构化提交，和参与记录同事务写入。
3. 发布预检从“问卷/投票未完成阻断”升级为真实校验：
   - 问卷至少 1 个字段。
   - 投票至少 2 个固定选项。
   - 字段/选项数量、文本长度、图片数量受 Free 计划限制。
4. 前端发布按钮附近补持久化预检面板，而不是只依赖 toast。

---

## 七、注意事项

- 不要为每种玩法单独写一套发布判断。
- 不要把发布预检变成用户参与热路径逻辑。
- 不要在问卷/投票闭环前恢复正式发布能力。
- 不要把 CTA/Webhook 缺失设为硬阻断，它们是承接能力，不是所有活动的必要条件。
