## 二、后端竞争/锁/超发/漏发审查

### 2.1 奖励发放竞争 ✅ 安全

| 机制 | 实现位置 | 防护方式 |
|------|---------|---------|
| bonus_spin 发放 | reward-exits.ts:grantBonusSpin | CAS：`WHERE spinsTotalGranted = 旧值`，rowsAffected=0 跳过 |
| bonus_coupon 发放 | reward-exits.ts:grantBonusCoupon | CAS：`WHERE status = 'available'`，原子 UPDATE |
| 里程碑幂等标记 | referral-rewards-engine.ts:markRewardIdsGranted | CAS：`WHERE rewardMilestonesGranted = 旧值`，best effort |
| 秒杀库存 | participation.ts:joinDraw | CAS：`UPDATE lotteryDraws SET activeParticipantCount + 1 WHERE < max` + entry 状态 CAS + 回滚补偿 |

**三重防超发架构**（docs/254 §3.1）：
- 第一重：幂等层（rewardMilestonesGranted 列表判断）
- 第二重：出口 CAS（spinsTotalGranted / couponCodes.status）
- 第三重：总量约束（maxSpinsPerEntry 硬顶 / 码池可用性）

### 2.2 秒杀并发安全 ✅ 已处理

`joinDraw` 中直付秒杀的并发处理（participation.ts:~300-380）：
1. CAS 递增 `activeParticipantCount`（活动级名额锁）
2. 检查 entry 状态（EXPIRED → RESERVED 占位）
3. 若 entry 已被并发方抢占（rowsAffected=0），**回滚** `activeParticipantCount` 避免虚拟占用泄漏

⚠️ **潜在风险（🟡 中）**：步骤 2→3 之间有极短窗口期，另一个并发请求可能同时通过 CAS 并抢占 entry。当前实现通过 rowsAffected 检查 + 回滚补偿处理了这种情况，但回滚使用 `MAX(0, count - 1)` 而非精确 CAS，在极端并发下可能出现计数轻微偏移。建议后续考虑使用 SQLite 的 `RETURNING` + 事务内重试。

### 2.3 reissue 补发安全性 🟡 需关注

`POST /draws/:id/rewards/reissue`（admin-lottery.ts:1447-1479）：
- 无事务包裹：逐条重试 `triggerRewardEarned`，每条独立
- `triggerRewardEarned` 内部有配额检查（perUserPerDay / globalPerDay），不会超发
- 但 `all=true` 批量重试时，若某条重试成功后同一分享者再次触发归因，配额可能被消耗两次（不同路径：reissue 走 triggerRewardEarned，正常归因走 processReferralRewardsEngine）

**建议（🟢 低）**：当前 `triggerRewardEarned` 的配额检查已足够防止重复发放，但审计日志中应区分 reissue 与正常归因来源。

### 2.4 查询效率 🟡 需关注

| 位置 | 问题 | 影响 |
|------|------|------|
| referral-rewards-engine.ts:aggregateSharerData | 按 sharerEntryId 查全部 shareRecords（无 LIMIT） | 分享者名下记录极多时可能慢 |
| referral-rewards-engine.ts:main loop | 每个 rewardId 独立 grant（bonus_spin 逐条 CAS，bonus_coupon 循环发券） | 奖励条目多时 O(n) DB 操作 |
| admin-lottery.ts:getRewardFailures | 按 drawId 查 activityEvents（无 LIMIT） | 失败记录极多时可能慢 |

**建议**：
- aggregateSharerData 加 LIMIT（如 1000），超限时 warning
- getRewardFailures 已有 `orderBy(desc(createdAt))` 但无 LIMIT，建议加 `.limit(200)`

## 六、关键风险总结

### 🔴 高风险：无

### 🟡 中风险（3 项）

1. **秒杀并发补偿窗口期**（participation.ts:~340）：CAS 递增 → entry 状态检查之间有极短窗口，并发请求可能同时通过 CAS。当前 rowsAffected + 回滚补偿可处理，但极端并发下 activeParticipantCount 可能轻微偏移。建议：后续版本考虑 SQLite RETURNING + 事务内重试。

2. **reissue 批量重试无事务包裹**（admin-lottery.ts:1447）：逐条 triggerRewardEarned 独立执行，部分成功部分失败时结果不一致。当前设计可接受（配额保护防超发），但审计日志应区分 reissue 来源。

3. **aggregateSharerData 无 LIMIT**（referral-rewards-engine.ts:~300）：分享者名下 shareRecords 极多时查询可能慢。建议加 LIMIT 1000 + warning。

### 🟢 低风险（4 项）

4. **getRewardFailures 无 LIMIT**（admin-lottery.ts:~1370）
5. **中奖名单无分页**（AdminLotteryView.vue）
6. **里程碑进度实时预览缺失**（管理端无法预览配置效果）
7. **cta_impression watch 去重缺少单测**
