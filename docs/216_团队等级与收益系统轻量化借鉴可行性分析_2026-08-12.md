# 216 团队等级与收益系统轻量化借鉴可行性分析（2026-08-12）

> 分析对象：`rbb_java/investment-platform/docs/02_团队等级与团队收益逻辑梳理.md`
> 目标平台：cf-lottery（多租户可白标活动引擎）
> 决策原则：不做大而全的系统，做小而美的瑞士军刀；不过度设计，不过度开发

---

## 一、10 秒钟看懂结论

| 问题 | 答案 |
|:-----|:-----|
| 能直接搬过来吗？ | **不能**。投资盘团队系统是**金融收益分配**模型，cf-lottery 是**活动参与与结果分配**引擎，领域不同 |
| 有值得借鉴的概念吗？ | **有**。多级裂变归因、等级化权益解锁、链式比例分配这三个算法思想可以轻量化改造 |
| 推荐怎么做？ | **不建用户树，不做每日批处理**。在现有**活动级裂变分享**能力上，叠加「可配置的推荐奖励阶梯」（P0 短期）和「活动级等级权益」（P1 中期），见 §六 |
| 什么情况下才需要做完整版？ | 当 cf-lottery 从「活动引擎」演进为**带交易市场的平台**（如 affiliate 联盟营销、分销市场）时，再考虑完整版 |

## 二、投资盘团队系统的本质（摘录对照）

摘录原文档核心机制，作为对照基准：

### 2.1 两套独立逻辑

| 逻辑 | 核心 | 执行频率 |
|:-----|:-----|:---------|
| 团队等级评估 | 用户达标 → 升级（V0~V12），循环到收敛 | 每日 00:01 定时任务 |
| 团队收益分配 | 方舱释放 X 元 → 沿上级链按级差比例分配 | 每日 00:50 定时任务 |

### 2.2 依赖的基础设施

| 基础设施 | 说明 | cf-lottery 是否有？ |
|:---------|:-----|:--------------------|
| 用户关系树（parent_id） | 每个用户一个推荐人，形成森林 | ❌ 无 |
| 每日投资释放（release_amount） | 产生可分配金额的源头 | ❌ 无 |
| 等级配置表（team_level_rules JSON） | 13 级配置，每级有 rate/directCount/selfInvestment/teamPerformance | ❌ 无 |
| 定时任务调度 | 00:01 升 V，00:50 算收益，00:58 算补贴 | ✅ 有 maintenance 任务，但无此精细窗口 |

### 2.3 核心算法

**等级评估**：对每个用户，三项条件（直推数、自投金额、团队业绩）→ 取最高满足的等级。因下级升了上级才能升，需多轮循环直到收敛。

## 三、cf-lottery 当前架构对标

### 3.1 已有的相关能力

| 能力 | 位置 | 说明 |
|:-----|:-----|:-----|
| 分享裂变（shareRecords） | schema.ts:728 | 活动级分享记录，追踪 click + join，但**无层级关系** |
| 归因（refCode） | activityEvents.refCode | 事件级来源追踪，但**无永久性用户绑定** |
| 活动事件（activityEvents） | schema.ts:743 | 统一事件表，支持归因分析 |
| 系统配置（systemConfig） | schema.ts:582 | JSON 可扩展，可承载等级规则 |
| 维护任务（maintenance） | 定时清理/快照 | 周期执行基础存在 |
| 用户身份（users） | schema.ts:29 | 无 parent_id，无树结构 |

### 3.2 关键缺失

| 缺失项 | 影响 |
|:-------|:-----|
| 用户间永久推荐关系（parent_id） | 无法建立用户树，无法做「团队业绩」递归求和 |
| 每日可分配金额（release_amount） | 没有「钱」的源头，收益分配缺乏标的 |
| 用户等级字段 | 无 level/rate，无法做级差分配 |
| 租户级用户树 | 用户是全局的，不属于某个租户（tenant_members 是租户成员关系，不是推荐关系） |

### 3.3 架构层面的根本差异

```
投资盘团队系统模型：
  用户树（parent_id） → 等级 → 每日产生收益 → 沿树上分配

cf-lottery 模型：
  活动 → 参与 → 结果分配（每人独立，不依赖用户关系）
```

**这是两个不同的业务域**：投资盘是「人→钱」的金融分配，活动引擎是「人→活动→结果」的参与分发。强行把用户树和等级系统塞进 cf-lottery 会：

1. 引入跨租户用户关系（用户是全局的，不属于租户，用户树在哪一级？）
2. 引入每日批处理任务（当前维护任务只有清理和快照，没有收益计算）
3. 引入「分配金额」概念（当前没有货币流通模型，支付是秒杀卡密直付，不走收益释放）
4. 破坏「小而美」的定位（加了用户树就不是活动引擎了，变成社交电商平台）

## 四、轻量化借鉴方案

### 4.1 方案一：活动级推荐奖励阶梯（P0，短期）

**思路**：不建全局用户树，不改数据库 schema，在现有活动裂变能力上叠加「邀请奖励阶梯」。

**借鉴点**：等级评估的「条件达标」思想（直推数 → 奖励等级），但**不做递归树、不做每日批处理、不做级差分配**。

**实现**：

```
┌─ 活动配置（promotion_config JSON）新增字段：
│   "referralRewards": [
│     { "requireCount": 1,  "rewardType": "bonus_spin", "rewardValue": 1 },
│     { "requireCount": 3,  "rewardType": "bonus_spin", "rewardValue": 1 },
│     { "requireCount": 5,  "rewardType": "bonus_entry", "rewardValue": 1 }
│   ]
│
└─ 运行时：用户每次完成分享 → 累计 shareRecords.joinedCount
           → 按阶梯检查是否满足新等级 → 发放奖励
           → 奖励通过 activityOutcomes 记录（复用现有结果系统）
```

**优势**：
- 零 schema 变更（promotion_config 已是 JSON 字段）
- 零新表（shareRecords 已有 joinedCount）
- 零定时任务（实时触发，不依赖批处理）
- 完全活动级隔离（不跨活动，不跨租户）
- 可嵌入现有 spin/join 流程

**劣势**：
- 单活动级，无法跨活动累计（用户参加 A 活动邀请的人，不能算 B 活动的推荐数）
- 无树形结构，只有「邀请者→被邀请者」单层关系

### 4.2 方案二：活动级等级权益（P1，中期）

**思路**：借鉴「等级→权益」的映射思想，但等级由**用户在单个活动内的行为**决定，而非全局用户属性。

**借鉴点**：等级配置的「多条件组合 + 最高满足」判定逻辑。

**实现**：

```
┌─ 活动配置新增字段：
│   "participantLevels": [
│     {
│       "level": 1,  "label": "青铜",
│       "conditions": { "spinCount": 5, "inviteCount": 1 },
│       "benefits": { "extraSpin": 1, "prizeWeightMultiplier": 1.0 }
│     },
│     {
│       "level": 2,  "label": "白银",
│       "conditions": { "spinCount": 20, "inviteCount": 3 },
│       "benefits": { "extraSpin": 3, "prizeWeightMultiplier": 1.5 }
│     }
│   ]
│
└─ 运行时：用户每次完成动作（spin/join/invite）
           → 实时计算最高满足等级
           → 生效对应权益（加分、加抽奖次数等）
```

**优势**：
- 活动级隔离，多租户天然支持
- 实时计算，不依赖定时任务
- 权益可通过现有 outcome 系统实现（加分权重在抽奖算法层）
- 条件可组合（行为 + 邀请 + 支付等）

**劣势**：
- 需要新增 `lottery_entries` 上的累计字段（spinCount, inviteCount 等）或从 activityEvents 聚合计算
- 权重计算需要修改抽奖算法（当前是均匀随机，需要支持权重）

### 4.3 方案三：多级裂变归因与链式奖励（P2，长期）

**思路**：借鉴「链式比例分配」算法，但只用于**奖品/积分分配**，不用于金融收益。

**借鉴点**：收益分配中「沿上级链按比例分配」的算法结构。

**实现**：

```
┌─ 新增表 activity_referral_trees（活动级推荐树）
│   tenantId, drawId, entryId, parentEntryId, depth
│
└─ 新增表 activity_referral_rewards（链式奖励记录）
│   tenantId, drawId, sourceEntryId, rewardEntryId, level, rewardAmount
│
└─ 当用户中奖时：沿推荐树向上找 N 级，按比例分配「额外奖励积分」
│   （级差比例从活动配置读取，可用类似 team_level_rules 的 JSON）
│
└─ 奖励积分可兑换额外抽奖次数、兑换码等
```

**优势**：
- 多级裂变，激励用户邀请更多人
- 链式分配算法成熟（投资盘已验证）
- 分配标的不是钱，而是平台积分/额外权益，风险可控

**劣势**：
- 需要新增 2 张表
- 需要在活动中奖流程中插入奖励分配逻辑
- 需要引入「积分」概念（当前没有）
- 复杂度较高，需要仔细设计防止循环引用和性能问题

## 五、方案对比与选型建议

### 5.1 综合对比

| 维度 | 方案一：推荐奖励阶梯 | 方案二：等级权益 | 方案三：链式奖励 |
|:-----|:-------------------|:----------------|:----------------|
| 工作量 | ★☆☆ 1-2 天 | ★★☆ 3-5 天 | ★★★ 8-12 天 |
| schema 变更 | 无 | 少量（entries 加字段） | 中等（2 张新表） |
| 定时任务 | 无 | 无 | 无 |
| 树结构 | 无（单层） | 无（单层） | 有（多级） |
| 裂变激励 | 中等 | 中等 | 强 |
| 多租户隔离 | 天然 | 天然 | 天然 |
| 对现有代码影响 | 小（仅 spin/join 流程加点） | 中（抽奖算法层需改） | 大（新增服务 + 流程） |
| 用户理解成本 | 低 | 中 | 高 |
| 与核心定位对齐 | ✅ 强（活动级） | ✅ 强（活动级） | ⚠️ 偏重（平台级倾向） |

### 5.2 推荐路径

```
        当前
          │
          ▼
  方案一（P0）── 推荐奖励阶梯
          │ 1-2 天，0 schema 变更
          ▼
  方案二（P1）── 活动级等级权益
          │ 3-5 天，少量 schema 变更
          ▼
  方案三（P2）── 多级链式奖励
          │ 8-12 天，需引入积分体系
          ▼
  完整版（仅当产品定位扩展为交易市场时才考虑）
```

**短期（P0）**：方案一。利用现有 promotion_config + shareRecords，1-2 天上线推荐奖励阶梯。这是**最小可行借鉴**，ROI 最高。

**中期（P1）**：方案二。如果方案一验证了「等级化激励」有效，再扩展为活动级多维度等级权益。此时才真正借鉴了投资盘「等级配置 + 条件判定」的思想。

**长期（P2）**：方案三。如果产品从「活动引擎」扩展到「带交易属性的平台」（如分销市场、联盟营销），再引入多级链式奖励。在此之前，**不做用户树，不做跨活动累计，不做每日批处理**。

## 六、具体实施建议（不写代码，给出设计原则）

### 6.1 方案一实施要点

> ✅ **已实施 P0**（2026-08-12，详见 `docs/217_推荐奖励阶梯P0实现_2026-08-12.md`）
> 实施中根据架构深度审读对原设计做了两处修正：
> - **幂等存储改用 `shareRecords.reward_milestones_granted` 列**，而非 `activityOutcomes`——该表 UNIQUE(tenant, draw, outcomeType, entryId) 会限制同一 entry 只能有一条同类型 outcome，无法支撑同用户多个里程碑；shareRecords 上的单调集合恰好是"joinedCount 只增不减"的最佳伴侣。
> - **奖励类型 P0 仅实现 `bonus_spin`**；`bonus_entry`（延迟模式额外参与名额）、`prize_upgrade`（奖品升级）无对应机制，属方案二/三范畴，defer 到 P1。

1. **配置位置**：`lottery_draws.promotion_config` JSON 新增 `referralRewards` 数组
2. **触发时机**：shareRecords.joinedCount 更新时（现有入口：`participation.ts` 中的 `recordAttributedJoin` → `maybeTriggerReward` → `processReferralMilestoneRewards`）
3. **奖励发放**：bonus_spin 直接叠加 `lottery_entries.spinsLeft`/`spinsTotalGranted`（不占 viral.maxExtra 预算，仅受 maxSpinsPerEntry 总顶）；发放记入 `spins_log`（reason=viral，refId=`milestone:{requireCount}`）供审计
4. **奖励类型**：P0 仅 bonus_spin（额外抽奖次数）；bonus_entry、prize_upgrade 待 P1
5. **幂等性**：`shareRecords.reward_milestones_granted`（JSON 数组）+ CAS UPDATE 防并发重放，每个 `shareRecordId + requireCount` 只发放一次
6. **限流**：不新增独立限流；阶梯处理是附加行为，异常/未配置静默跳过，不影响参与主流程

### 6.2 方案二实施要点

1. **配置位置**：`lottery_draws.activity_config` JSON 新增 `participantLevels` 数组
2. **条件来源**：从 `activityEvents` 聚合（eventType = participation_completed, attributed_join 等）
3. **权益实现**：spin 次数在 `lottery_entries.spinsLeft` 字段上叠加；权重在抽奖算法层按 `prizeWeightMultiplier` 调整
4. **实时计算**：参与者每次完成动作后，服务层计算当前最高等级，必要时更新 entry 上的等级快照
5. **审计**：等级变更记录到 `activity_event`（eventType: "participant_level_up"）

### 6.3 方案三实施要点

1. **推荐树**：`activity_referral_trees` 表存 entryId → parentEntryId（活动级，不跨活动）
2. **链式分配**：算法直接复用投资盘「级差比例分配」实现（`parentRate - lastEffectiveRate`），但分配标的改为积分/额外权益
3. **积分体系**：引入 `participant_points` 表（非必须，可先用 `activityOutcomes` 记录每笔奖励，按需聚合）
4. **防环检测**：插入推荐关系时，向上遍历 depth≤10，发现循环引用则拒绝写入
5. **性能**：单次中奖的链式分配在事务内完成，最多向上遍历 10 级，控制在 10ms 以内

### 6.4 共识：不做的几件事

| 不做 | 原因 |
|:-----|:-----|
| ❌ 不做全局用户树（parent_id） | 用户是跨租户的，引入用户树会破坏多租户隔离 |
| ❌ 不做每日批处理等级评估 | 活动是短周期的（数天~数周），每日批处理延迟大、运维成本高 |
| ❌ 不做金融收益分配 | cf-lottery 不是投资平台，引入「钱」的分配会带来金融合规风险 |
| ❌ 不做跨活动累计 | 活动级隔离是核心设计原则，跨活动累计引入全局状态，增加复杂度 |
| ❌ 不做递归团队业绩计算 | 活动级的用户树深度有限（≤10），不需要递归缓存和环检测这种重型工程 |

## 七、评审记录

### 7.1 第一轮评审（2026-08-12）

**问题**：投资盘的团队系统本质是「金融收益分配」，cf-lottery 的定位是「活动引擎」，强行借鉴会不会导致定位漂移？

**结论**：会。所以方案一和方案二都严格限定在「活动级」，不引入全局用户树。方案三也只在活动级建立推荐树。三个方案都保持「活动结束后数据可归档」的短期特性，不产生永久性全局依赖。

### 7.2 第二轮评审（2026-08-12）

**问题**：方案三的「积分」概念，是不是又引入了新的大系统？

**结论**：方案三的积分是**轻量级活动积分**，不是平台级通用积分。只在 single-activity 范围内有效，活动结束即作废。不需要积分兑换商城、积分有效期管理这些重型功能。如果后续需要跨活动积分，再单独评估。

### 7.3 第三轮评审（2026-08-12）

**问题**：方案一「推荐奖励阶梯」与现有「分享裂变」能力的边界在哪里？

**结论**：现有分享裂变只做**归因统计**（谁分享了、谁点击了、谁加入了），不做**奖励发放**。方案一是在归因统计的基础上，叠加上「按阶梯发放奖励」的能力。两者是上下游关系，不重叠。

## 九、P0 实施记录（2026-08-12）

### 实施范围

按 §6.1 方案一实施推荐奖励阶梯，仅覆盖 instant 模式 + bonus_spin 类型。

### 架构审读发现

实施前对现有代码做了深度审读，发现：

1. **现有 `grantViralSpinsToSharer` 已实现 per-invite 线性加次**（`promotion_config.viral.extraSpinsPerInvite`），与阶梯是互补关系。
2. **`spinsViralEarned` 有严格不变式**（≤ maxExtraSpins），里程碑若计入该字段会破坏不变式。
3. **`activityOutcomes` 表有 UNIQUE(tenant, draw, outcomeType, entryId) 约束**，无法支撑同 entry 的多个里程碑记录。

### 设计修正

| 原设计（§6.1） | 修正后（P0 实施） | 原因 |
|:---------------|:-----------------|:-----|
| 幂等存 activityOutcomes | 存 `shareRecords.reward_milestones_granted` | UNIQUE 约束限制同 entry 多里程碑 |
| 奖励类型：bonus_spin + bonus_entry + prize_upgrade | 仅 bonus_spin | 后两者无对应机制，待 P1 |
| 受 double-cap 约束 | 仅受 maxSpins 约束，不占 viral budget | requireCount 有限，无刷次风险 |
