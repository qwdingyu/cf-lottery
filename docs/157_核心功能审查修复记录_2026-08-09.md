# 核心功能审查修复记录

日期：2026-08-09

## 背景

本次审查聚焦核心业务功能，不包含部署脚本和文档一致性问题。范围包括公开参与、邀请码资格、直付秒杀名额、支付回调发卡、管理端补发卡密、中奖邮件、外部核销、管理端统计导出和库存预警的多租户隔离。

## 发现的问题

### 1. 邀请码在参与失败时被消耗

`joinDraw()` 原逻辑在事务内先执行 `lottery_invite_codes.used_count + 1`，再进行容量条件写入。若活动已满或秒杀名额 CAS 失败，函数会正常返回“名额已满/已抢光”，事务随之提交，导致用户没有成功参与但邀请码次数已被消耗。

这违背“资格只随成功参与消耗”的业务不变量，也和代码注释中的设计意图不一致。

### 2. 支付邮件和库存预警查询缺少租户过滤

支付成功后的中奖邮件异步补充查询、Dashboard 库存预警的奖品和卡密关联查询，依赖全局 UUID 正常不碰撞。但多租户系统的核心约束是查询路径必须显式带 `tenant_id`，不能只依赖 ID 唯一性。

### 3. 管理端补发卡密会批量锁定同奖品所有可用码

`POST /api/admin/draws/:id/winners/:winnerId/retry-code` 原逻辑直接执行：

```sql
UPDATE prize_codes
SET status = 'issued'
WHERE prize_id = ? AND tenant_id = ? AND status = 'available'
```

这会把同一奖品下所有可用卡密一次性标记为已发放。接口随后只把其中一张码挂到中奖记录，其余卡密会被错误消耗，造成库存损坏。

### 4. 外部核销事件缺少状态 CAS

`reward.redeemed` 事件先读取卡密状态，再按 id 更新为 `redeemed`。若并发撤销或重复事件发生在读写之间，可能覆盖中间状态。核心库存状态流转应在更新条件中包含租户和当前状态。

### 5. 管理端统计和导出计数缺少显式租户条件

`/draws/:id/stats` 和 `/draws/:id/export` 的参与人数 COUNT 只按 `draw_id` 过滤。`draw_id` 是主键，正常数据不会跨租户碰撞；但多租户纵深防御要求统计口径必须显式包含 `tenant_id`，避免脏数据或未来导入工具绕过约束时污染运营统计和导出限制判断。

## 修复方案

1. `joinDraw()` 改为先校验邀请码可用并取得 `inviteCodeId`，参与记录成功插入后再执行 `used_count + 1` 的 CAS 扣减。
2. 若并发下邀请码在插入后被其他请求耗尽，抛出领域错误回滚整笔事务，并返回“邀请码无效或已用完”。
3. 支付邮件异步查询 `lottery_entries`、`lottery_draws`、`prize_codes`、`prizes` 时补齐 `tenant_id`/`draw_id` 条件。
4. Dashboard 库存预警关联 `prizes`、`prize_codes` 时补齐 `tenant_id` 条件。
5. 管理端补发卡密改为事务内 `UPDATE ... WHERE id = (SELECT ... LIMIT 1) RETURNING id`，只锁定一张可用码，再更新中奖记录。
6. 外部 `reward.redeemed` 改为 `tenant_id + id + status='issued'` 条件更新，避免覆盖并发状态变化。
7. 安慰券发放、即时开奖奖品计数等库存相关写入补齐租户条件。
8. 管理端 stats/export 参与人数计数补齐 `tenant_id`；中奖通知状态更新补齐 `tenant_id + draw_id`。

## 回归测试

新增测试：

- `invite_code：活动满额时拒绝参与但不消耗邀请码次数`
- `单个 winner 补发只锁定一张卡密，不会批量消耗同奖品码池`
- `活动 stats 只统计当前租户参与记录，忽略异常跨租户同 drawId 脏数据`

## 建议

后续凡是“先消耗资格/库存，再写主记录”的流程，都应优先采用“主记录成功后 CAS 消耗，失败则抛错回滚”的事务结构。不要用正常返回来表达需要回滚的业务失败。
