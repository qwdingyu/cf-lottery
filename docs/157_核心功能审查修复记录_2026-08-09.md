# 核心功能审查修复记录

日期：2026-08-09

## 背景

本次审查聚焦核心业务功能，不包含部署脚本和文档一致性问题。范围包括公开参与、邀请码资格、直付秒杀名额、支付回调发卡、中奖邮件和库存预警的多租户隔离。

## 发现的问题

### 1. 邀请码在参与失败时被消耗

`joinDraw()` 原逻辑在事务内先执行 `lottery_invite_codes.used_count + 1`，再进行容量条件写入。若活动已满或秒杀名额 CAS 失败，函数会正常返回“名额已满/已抢光”，事务随之提交，导致用户没有成功参与但邀请码次数已被消耗。

这违背“资格只随成功参与消耗”的业务不变量，也和代码注释中的设计意图不一致。

### 2. 支付邮件和库存预警查询缺少租户过滤

支付成功后的中奖邮件异步补充查询、Dashboard 库存预警的奖品和卡密关联查询，依赖全局 UUID 正常不碰撞。但多租户系统的核心约束是查询路径必须显式带 `tenant_id`，不能只依赖 ID 唯一性。

## 修复方案

1. `joinDraw()` 改为先校验邀请码可用并取得 `inviteCodeId`，参与记录成功插入后再执行 `used_count + 1` 的 CAS 扣减。
2. 若并发下邀请码在插入后被其他请求耗尽，抛出领域错误回滚整笔事务，并返回“邀请码无效或已用完”。
3. 支付邮件异步查询 `lottery_entries`、`lottery_draws`、`prize_codes`、`prizes` 时补齐 `tenant_id`/`draw_id` 条件。
4. Dashboard 库存预警关联 `prizes`、`prize_codes` 时补齐 `tenant_id` 条件。

## 建议

后续凡是“先消耗资格/库存，再写主记录”的流程，都应优先采用“主记录成功后 CAS 消耗，失败则抛错回滚”的事务结构。不要用正常返回来表达需要回滚的业务失败。
