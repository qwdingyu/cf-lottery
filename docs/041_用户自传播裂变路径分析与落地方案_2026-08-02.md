| 能力 | 代码位置 | 确认状态 |

### 🔴 发现的断点（必须在代码中修复）

| 断点 | 位置 | 严重性 | 描述 |
|:-----|:-----|:------:|:-----|
| **entryId 不返回前端** | `public-lottery.ts:403-407` | 🔴 阻断 | `verify-join` 和 `join` 两个端点都返回 `{ joined, activityKind, outcome? }`，**不包含 `entryId`**。但 `/share` API 要求 `{ entryId }`。前端无法生成带归因的分享链接。 |
| **GameResultModal 零上下文** | `GameResultModal.vue` | 🔴 阻断 | 组件只接收 `show: boolean` prop，不接收 `entryId`、`drawSlug` 或 `email`。"📤 分享活动"按钮只是 `copy(window.location.href)`，无归因。 |
| **裂变配置缺失** | `promotionConfig` JSON | 🟡 缺失 | 当前 `promotionConfig` 结构只有 `{ version, kind:'destination', destination, tracking }`，没有 viral 相关配置。 |
| **排行榜 API 缺失** | 无对应端点 | 🟡 缺失 | 无公开查询排行榜的 API。 |

### 🔴 方案修正：extra entry 不能写入 lottery_entries

**原方案错误：** 在 `recordAttributedJoin()` 中为分享者插入额外 `lottery_entries` 记录。

**为什么错误：**
1. 额外 entry 会被 `maxParticipants` 容量检查计入，导致活动名额被"虚拟参与者"挤占
2. 额外 entry 的 `identity_type` 需要特殊处理，会污染 `lottery_entries` 表的语义（"谁参与了活动"≠"谁有几次抽奖机会"）
3. 数据库膨胀：1000 人 × 10 次邀请 = 10000 条额外记录

**正确做法：开奖时加权展开候选数组**
- `lottery_entries` 只存真实参与者（语义不变）
- 开奖时查询每个参与者的 `invitedCount`（来自 `shareRecords.joinedCount`）
- 在 `randomSelect()` 调用前，将候选数组按权重展开：`1 + invitedCount` 次
- 展开后的数组中同一 `entryId` 可能出现多次，但 UNIQUE 约束保证不会重复中奖

## 一、现状诊断：传播链路已搭好骨架，但缺"发动机"

### 1.1 当前传播路径

```
运营者在后台创建活动 → 复制链接/二维码 → 手动分发到各社区
                                                    ↓
                                          用户点击链接 → 参与活动
                                                    ↓
                                          （传播到此为止，无裂变）
```

### 1.2 裂变断点（代码核验）

```
裂变 = 动机 × 能力 × 触发
```

| 要素 | 代码现状 | 根因 |
|:-----|:---------|:-----|
| **动机** | ❌ 零 | 用户分享后得不到任何回报，shareRecords 只记录事实不发奖励 |
| **能力** | ❌ 断裂 | `verify-join` 不返回 `entryId` → `GameResultModal` 没有上下文 → 无法调用 `/share` API → 分享链接无归因码 |
| **触发** | ❌ 太弱 | `GameResultModal` 里一个不起眼的 ghost button"📤 分享活动"，用户大概率直接关掉 |

## 二、方案设计（代码审查修正版）

### 2.1 数据模型（零迁移）

裂变配置存放在 `lottery_draws.promotion_config` JSON 字段中（版本化）：

```json
{
  "version": 1,
  "kind": "destination",
  "destination": { "url": "...", "title": "...", "imageUrl": "...", "priceText": "..." },
  "tracking": { "enabled": true },
  "viral": {
    "enabled": true,
    "extraEntriesPerInvite": 1,
    "maxExtraEntries": 10,
    "leaderboardEnabled": true
  }
}
```

现有 `promotionConfig` 结构完全兼容，只新增可选 `viral` 子对象。零数据库迁移。

1. 查询该 entryId 对应的 shareRecords

#### Fix-4: 开奖加权（核心）

**位置：** `src/services/lottery-service.ts` 中的 `performDraw()`

**当前逻辑（第 1790 行附近）：**
```typescript
const entries = await db.select().from(lotteryEntries).where(...)
const selected = await randomSelect(entries, totalWinners)
```

**修改后逻辑：**
```typescript
const entries = await db.select().from(lotteryEntries).where(...)

// 查询裂变配置
const viralConfig = parseViralConfig(draw.promotionConfig)

// 构建加权候选数组
let candidates: typeof entries = []
if (viralConfig?.enabled) {
  // 查询所有参与者的邀请数
  const shareRows = await db
    .select({ sharerEntryId: shareRecords.sharerEntryId, joinedCount: shareRecords.joinedCount })
    .from(shareRecords)
    .where(and(eq(shareRecords.tenantId, tenantId), eq(shareRecords.drawId, drawId)))

  const inviteMap = new Map<string, number>()
  for (const row of shareRows) {
    inviteMap.set(row.sharerEntryId, row.joinedCount)
  }

  for (const entry of entries) {
    const invites = inviteMap.get(entry.id) || 0
    const extraTickets = Math.min(invites, viralConfig.maxExtraEntries ?? 10)
    // 每个参与者至少出现 1 次，最高 1 + extraTickets 次
    for (let i = 0; i < 1 + extraTickets; i++) {
      candidates.push(entry)
    }
  }
} else {
  candidates = entries
}

const selected = await randomSelect(candidates, totalWinners)
// 注意：selected 中同一 entryId 可能出现多次，winner 写入时 UNIQUE 约束自动去重
```

**为什么这样安全：**
1. `lottery_entries` 语义不变（只存真实参与者）
2. `maxParticipants` 容量检查不受影响
3. `lotteryWinners` 的 `UNIQUE(tenantId, drawId, entryId)` 自动去重
4. 加权展开只在内存中，不影响数据库

- 无裂变配置的活动（回归）

- 有人邀请，验证候选人数组长度正确
- 同一人被多次选中（UNIQUE 去重验证）

## 四、防刷与公平性

| 防护层 | 机制 | 覆盖场景 |
|:-------|:-----|:---------|
| 邮箱验证码 | `emailAccessCodes` 表 + 6 位验证码 | 机器批量注册 |
| UNIQUE 约束 | `lottery_entries(tenantId, drawId, identityType, identityValue)` | 同一邮箱重复参与 |
| IP 限流 | `checkRateLimit` 每分钟 10 次 | 同 IP 高频请求 |
| 黑名单 | `lotteryBlacklist` 表 | 封禁可疑用户 |
| 自邀防护 | 分享者自己再参与会被 UNIQUE 拒绝 | 刷自己邀请数 |
| 名额不变 | 加权展开不消耗 maxParticipants | 虚拟参与者不占名额 |

## 五、不做清单

| 不做 | 原因 |
|:-----|:-----|
| **写入额外 lottery_entries** | 污染参与表语义 + 挤占活动名额 + 数据库膨胀 |
| **修改 randomSelect 算法** | 保持核心算法不变，降低回归风险 |
| **助力/组队/红包/分销** | 超出活动引擎边界 |
| **强制分享才能参与** | 损害体验 + 违反平台政策 |

## 六、总结

### 关键变更（与原文档 041 的差异）

| 原方案 | 修正后 | 原因 |
|:-------|:-------|:-----|
| recordAttributedJoin 写入额外 entry | 开奖时加权展开候选数组 | 不污染 lottery_entries + 不影响容量 |
| 先改 GameResultModal 再改 API | 先改 API 返回 entryId，再改前端 | 依赖关系反了，前端需要数据才能工作 |
| promotionConfig 用嵌套结构 | 保持现有 version 1 结构，新增可选 viral 子对象 | 不破坏现有结构 |

### 最小可行路径

```
Fix-1 (entryId 暴露) → Fix-2 (前端分享引导) → 分享链路即可跑通
                              ↓
                       Fix-3 (排行榜 API) → 社交证明驱动
                              ↓
                       Fix-4 (开奖加权) → 利益驱动闭环
```

**P0 只需 Fix-1 + Fix-2，分享就不再是"复制裸链接"，而是"生成带归因的专属链接"。**
