# cf-lottery 用户自传播裂变路径分析与落地方案

> 文档编号：041
> 创建时间：2026-08-02
> 定位：从"运营手动分发"到"用户自传播"的路径分析，基于现有代码能力给出可落地的方案
> 角色：行业专家 + 产品经理 + 资深用户 + 技术架构师

## 一、现状诊断：传播链路已搭好骨架，但缺"发动机"

### 1.1 当前传播路径

```
运营者在后台创建活动 → 复制链接/二维码 → 手动分发到各社区
                                                    ↓
                                          用户点击链接 → 参与活动
                                                    ↓
                                          （传播到此为止，无裂变）
```

**核心问题：** 传播动力完全依赖运营者的人力，活动跑不出"运营者朋友圈半径"。用户参与后没有动机去传播，即使传播也没有得到任何回报。

### 1.2 已具备的传播基础设施（代码核验）

经过对全量代码的审计，以下能力已经存在：

| 能力 | 代码证据 | 状态 |
|:-----|:---------|:----:|
| **分享码生成** | `POST /draws/:slug/share` → `shareRecords` 表写入 | ✅ 已实现 |
| **分享链接点击追踪** | `GET /draws/:slug/ref/:shareCode` → `clickedCount++` + `share_click` 事件 | ✅ 已实现 |
| **裂变归因** | `joinDraw()` 中 `recordAttributedJoin()` → `joinedCount++` + `attributed_join` 事件 | ✅ 已实现 |
| **refCode 透传** | 前端 `LotteryView.vue:910` 从 URL 读取 `?ref=` 参数，参与时带入 | ✅ 已实现 |
| **活动事件漏斗** | `activityEvents` 表记录 `share_click` / `attributed_join` | ✅ 已实现 |
| **管理端分享统计** | `GET /admin/draws/:id/shares` 返回 shares + totalClicks + totalJoins | ✅ 已实现 |
| **前端分享按钮** | `GameResultModal.vue` 参与成功后显示"📤 分享活动" | ✅ 已实现 |
| **管理端漏斗面板** | `AdminLotteryView.vue` 展示 `share_click` 事件数 | ✅ 已实现 |

**结论：归因链路 100% 完整。** 运营者已经可以在后台看到"谁分享了、带来多少点击、带来多少参与"。

### 1.3 裂变断点：用户为什么不传播？

裂变的三个要素缺一不可：

```
裂变 = 动机（我为什么要分享）× 能力（我能不能轻松分享）× 触发（什么时机提醒我分享）
```

| 要素 | 现状 | 问题 |
|:-----|:-----|:-----|
| **动机** | ❌ 无 | 用户分享后得不到任何回报（额外参与次数、中奖概率提升、排行榜荣誉） |
| **能力** | ⚠️ 半成品 | GameResultModal 的"分享活动"按钮只复制当前 URL，**没有调用后端 API 生成带归因码的分享链接**。这意味着即使用户分享了，也追踪不到是谁分享的。 |
| **触发** | ❌ 弱 | 参与成功后弹窗里有一个不起眼的 ghost button，用户大概率直接点"知道了"关掉。开奖结果页、未中奖页都没有分享入口。 |

**核心断点：动机为零。** 这是裂变不起来的根本原因。

## 二、裂变模式选型：什么适合 cf-lottery？

### 2.1 行业常见裂变模式对比

| 模式 | 原理 | 适合 cf-lottery？ | 理由 |
|:-----|:-----|:-----------------:|:-----|
| **助力/组队** | N 人助力才能参与/解锁奖励 | ❌ | 需要复杂的组队状态机 + 反作弊，与"轻量活动引擎"定位冲突 |
| **红包裂变** | 分享后双方得红包 | ❌ | 需要支付/余额系统，偏离活动引擎边界 |
| **分销返佣** | 邀请成交得佣金 | ❌ | 需要订单/结算/税务系统，明确不做（见文档 038） |
| **任务裂变** | 完成分享任务得奖励 | ❌ | 需要任务系统和防刷机制，过重 |
| **额外参与次数** | 分享后获得额外抽奖码 | ✅ | **简单、闭环、符合抽奖场景** |
| **排行榜裂变** | 邀请最多的人上榜获额外奖励 | ✅ | **轻量、激励竞争、适合社区传播** |
| **邀请码裂变** | 分享专属邀请码，双方获益 | ⚠️ | 已有 `lotteryInviteCodes` 但那是运营者控制发行，非用户生成 |

### 2.2 推荐方案：两层裂变引擎

```
第一层（基础）：分享得额外参与次数
  "邀请好友参与，每成功邀请 1 人，你额外获得 1 次抽奖机会"
  → 简单直接，用户秒懂

第二层（进阶）：邀请排行榜 + 额外奖励
  "邀请排行榜 Top 3 获得额外奖品"
  → 制造竞争，提升分享动力
```

**为什么选这两个？**
1. **实现成本极低**：基础设施全在（shareRecords、activityEvents、refCode 归因），只需加 2 个字段 + 2 个 API + 1 个前端组件。
2. **符合活动引擎定位**：不涉及钱、不涉及复杂状态机，纯"参与次数"维度。
3. **用户心智成熟**：拼多多砍一刀、美团外卖红包已经把"分享得额外机会"教育透了。
4. **防刷可控**：参与需要邮箱验证码，天然阻止机器刷量。

## 三、落地方案设计

### 3.1 数据模型扩展（最小改动）

`lottery_draws` 表新增字段：

```sql
-- 裂变配置（JSON 字段，存放在已有的 promotion_config 中或独立字段）
-- 方案 A：复用 promotion_config（推荐，零迁移成本）
promotion_config 扩展为：
{
  "productLink": { ... },        // 已有：商品导流
  "postParticipation": { ... },  // 已有：参与后承接
  "viralConfig": {               // 新增：裂变配置
    "enabled": true,
    "extraEntriesPerInvite": 1,  // 每成功邀请 1 人，额外获得 N 次参与机会
    "maxExtraEntries": 10,       // 最多额外获得 M 次
    "leaderboardEnabled": true,  // 是否展示邀请排行榜
    "leaderboardPrizeTierId": "" // 排行榜奖励关联的奖品层级 ID（可选）
  }
}
```

**为什么不新建表？**
- `promotion_config` 本身就是版本化 JSON，设计初衷就是承载这类扩展
- 零数据库迁移，零 ORM schema 变更
- 符合项目"不重复造轮子"原则

### 3.2 API 设计

#### 3.2.1 生成分享链接（改造现有接口）

**现状问题：** `POST /draws/:slug/share` 需要 `entryId` 参数，但前端 `GameResultModal.vue` 没有传。

**改造：**
```
POST /api/public/draws/:slug/share
Body: { entryId: string }
Response: { shareCode, shareUrl, stats: { clickedCount, joinedCount } }
```

前端改造：参与成功后展示分享卡片，包含专属链接和实时统计。

#### 3.2.2 查询我的裂变数据（新增）

```
GET /api/public/draws/:slug/my-viral-stats?entryId=xxx
Response: {
  invitedCount: 5,           // 已邀请人数
  extraEntriesEarned: 5,     // 已获得的额外参与次数
  maxExtraEntries: 10,       // 最多可获得次数
  leaderboardRank: 3,        // 排行榜排名（如果开启）
  shareCode: "abc123",       // 我的分享码
  shareUrl: "/slug?ref=abc123"
}
```

#### 3.2.3 邀请排行榜（新增）

```
GET /api/public/draws/:slug/viral-leaderboard
Response: {
  entries: [
    { rank: 1, displayName: "张***", invitedCount: 15 },
    { rank: 2, displayName: "李***", invitedCount: 12 },
    ...
  ],
  myRank: { rank: 3, invitedCount: 5 }  // 如果提供了 entryId
}
```

**隐私保护：** 只展示脱敏后的 displayName，不暴露邮箱。

#### 3.2.4 开奖时计入额外参与次数（核心逻辑）

在 `joinDraw()` 的 `recordAttributedJoin()` 调用处，当分享者获得一次有效邀请时，为分享者在 `lotteryEntries` 表中**额外插入一条参与记录**作为额外机会。

或者在开奖时（`drawWinners()`），先查询每个参与者的邀请数，按 `1 + extraEntries` 加权抽取。

**推荐方案：写入额外 entry（简单可靠）**
- 在 `recordAttributedJoin()` 中，当邀请有效时，自动为分享者写入一条额外 entry
- `identity_type = "viral_bonus"`，与原 entry 关联
- 开奖时自然多一条记录，中奖概率翻倍

**为什么不用加权抽取？**
- 加权抽取需要修改开奖算法，引入复杂度
- 额外 entry 方案直观、可审计、可追溯
- 参与者在后台能直接看到"我有 N 次参与机会"

## 四、防刷与公平性

### 4.1 为什么不容易被刷？

1. **邮箱验证码门槛**：每个新参与者必须通过邮箱验证码验证，机器无法批量注册
2. **UNIQUE 约束**：`lotteryEntries` 表有 `UNIQUE(tenant_id, draw_id, identity_type, identity_value)`，同一邮箱不能重复参与
3. **黑名单**：`lotteryBlacklist` 表可以封禁可疑邮箱
4. **IP 限流**：`checkRateLimit` 限制同一 IP 每分钟 10 次参与
5. **extraEntry 不突破活动总名额**：额外 entry 写入时受 `maxParticipants` 约束

### 4.2 额外保护措施（可选）

- 分享者自己不能通过自己的分享链接再参与（已在 UNIQUE 约束中自然阻止）
- 同一 IP 下的邀请不计入（可选，通过 `lotteryEntries.ipHash` 比对）

## 五、运营视角：裂变如何真正跑起来？

### 5.1 运营者的角色变化

```
Before: 运营者 = 唯一的分发渠道
After:  运营者 = 裂变引擎的启动者（点火），用户 = 传播的燃料
```

运营者只需要：
1. 创建活动时勾选"开启裂变传播"
2. 设置合理的额外参与次数（建议 1-3 次/人，最多 10-20 次）
3. 在第一批种子用户中发布活动链接
4. 后台查看裂变数据，优化活动策略

### 5.2 裂变效果的运营杠杆

| 杠杆 | 效果 | 建议 |
|:-----|:-----|:-----|
| **奖品吸引力** | 直接影响参与意愿和分享意愿 | 奖品越好，用户越愿意分享 |
| **额外参与次数** | 每邀请 1 人得 1 次 → 邀请动力适中 | 不宜超过 3，否则显得"廉价" |
| **最多额外次数** | 10 次 → 有上限感，用户会努力达标 | 10-20 是心理舒适区 |
| **排行榜** | 前 3 名额外奖励 → 制造稀缺感和竞争 | 排行榜奖励要有吸引力 |
| **分享文案** | "免费抽 iPhone！快来！" vs "抽奖活动" | 好的文案提升点击率 3-5 倍 |

### 5.3 指标衡量

| 指标 | 定义 | 目标 |
|:-----|:-----|:----:|
| **裂变系数 (K-factor)** | 每个参与者带来的新参与者数 | > 0.3 就是有效裂变 |
| **分享率** | 参与后生成分享链接的比例 | > 15% |
| **邀请转化率** | 分享链接点击 → 实际参与的比例 | > 20% |
| **裂变参与占比** | 通过裂变参与的人数 / 总参与人数 | > 30% 说明裂变在驱动增长 |

## 六、风险评估

| 风险 | 概率 | 影响 | 缓解措施 |
|:-----|:----:|:----:|:---------|
| 用户用临时邮箱刷额外次数 | 中 | 参与质量下降 | 已有邮箱验证码 + IP 限流 |
| 竞争导致不公平感 | 低 | 用户投诉 | 排行榜脱敏 + 明确的规则说明 |
| 额外 entry 导致 DB 膨胀 | 低 | 存储成本 | 参与结束后清理或标记 |
| 裂变过度像"骚扰" | 中 | 品牌受损 | 不强制分享、不弹窗骚扰、用户可选择不参与裂变 |

## 七、对比：有裂变 vs 无裂变

| 维度 | 当前（无裂变） | 方案后（有裂变） |
|:-----|:-------------|:---------------|
| **传播动力** | 纯靠运营手动分发 | 用户有动力传播 |
| **传播半径** | 运营者朋友圈 | 参与者的社交网络 |
| **增长模式** | 线性（运营发一条，来一批） | 指数（用户带用户） |
| **获客成本** | 运营人力 + 渠道费用 | 奖品成本（边际为零） |
| **活动生命周期** | 发布即高峰，之后衰减 | 持续传播，长尾效应 |
| **运营者价值感知** | "我发链接才有人来" | "活动自己在跑，我在看数据" |

## 八、不做清单（明确边界）

| 不做 | 原因 |
|:-----|:-----|
| **助力/组队玩法** | 需要复杂的组队状态机 + 反作弊体系，超出轻量活动引擎边界 |
| **红包裂变** | 需要支付/余额/结算，明确不做（文档 038） |
| **强制分享才能参与** | 损害用户体验，违反微信/抖音等平台政策 |
| **自动读取通讯录/关系链** | 隐私合规红线 |
| **复杂的分销佣金** | 需要结算/税务系统，偏离活动引擎定位 |
| **朋友圈/群发自动检测** | 需要客户端能力，Web 端无法实现 |

## 九、总结

### 9.1 一句话结论

> **cf-lottery 已具备裂变传播的全部技术骨架（分享码、归因、漏斗），只差"给用户一个分享的理由"。补齐"分享得额外参与次数"这一个闭环，就能让活动从"运营者推着走"变成"用户带着跑"。**

### 9.2 核心改动清单

1. **修复分享链接生成**（改 `GameResultModal.vue`，调用 `/share` API 拿到带归因码的链接）
2. **参与成功后展示分享引导弹窗**（替代当前"知道了"弹窗，展示裂变进度和专属链接）
3. **`recordAttributedJoin()` 中写入额外 entry**（分享者获得额外参与机会）
4. **裂变数据查询 API**（my-viral-stats + viral-leaderboard）
5. **管理端裂变配置 UI**（在活动创建页增加裂变开关和参数）

### 9.3 为什么这个方案是"正确的"？

- **不越界**：仍然是活动引擎，不做社交网络、不做分销系统
- **不重复**：基础设施全在，改动量极小
- **不脆弱**：有邮箱验证码 + UNIQUE 约束做防刷，不依赖复杂风控
- **可度量**：后台已有完整的漏斗数据，裂变效果一目了然
- **可渐进**：P0 先让分享链路跑通，P1 再加排行榜，P2 再完善管理端，每一阶段都有独立价值
