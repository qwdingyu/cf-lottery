## 二、确认问题

### 1. 公开结果查询和取消参与缺少限流

| 位置 | 结论 |
|------|------|
| `src/routes/public-lottery.ts:610-745` | `POST /draws/:slug/my-result` 与 `POST /draws/:slug/cancel` 只有验证码校验，没有任何 `checkRateLimit` / `checkDbRateLimit` |
| `frontend/src/views/LotteryView.vue:566-599` | 前端真实调用的是 `/public/draws/:slug/my-result`，不是 `/result` |

影响：
- 6 位验证码只有 100 万空间，没有失败次数控制
- `cancel` 会直接影响接龙/预约状态，攻击面比“查结果”更大
- 这不是“限流不够强”，而是“完全没有限流”

建议：
- 给 `my-result` 和 `cancel` 增加 IP + 业务键双层限流
- 连续失败达到阈值时作废当前验证码

### 2. IP 限流在公开链路仍依赖内存计数，Node 入口又直接信任 `X-Forwarded-For`

| 位置 | 结论 |
|------|------|
| `src/routes/public-lottery.ts:22-34` | 公开路由限流使用模块级 `Map`，只在单个 isolate 内有效 |
| `src/routes/public-lottery.ts:296-314`、`355-363`、`490-498`、`751-759`、`806-810` | `events / access-code / verify-join / join / result` 都依赖这套内存限流 |
| `src/lib/platform.ts:20-27` | `getClientIp()` 直接接受 `X-Forwarded-For` |
| `src/server.ts:1-39` | Node 入口没有反代可信边界校验，直接暴露 HTTP 服务 |

影响：
- Cloudflare 多 isolate 下限流会被拆散
- Node / 自托管模式下，客户端可以伪造 `X-Forwarded-For` 绕过 IP 限流

建议：
- 公开写接口的最终限流必须落到持久层
- Node 部署时只在可信反代后读取 `X-Forwarded-For`

### 3. 登录态写入点没有统一走 `useAdminAuth.setToken()`

| 位置 | 结论 |
|------|------|
| `frontend/src/App.vue:35-52` | Logto 回调成功后直接写 `localStorage.setItem('admin_token', data.token)` |
| `frontend/src/views/AdminRegisterView.vue:80-97` | 注册成功后也直接写 `localStorage.setItem('admin_token', data.token)` |
| `frontend/src/composables/useAdminAuth.ts:99-105` | 统一的 `setToken()` 会写入过期时间并清理 `impersonated_token` |

影响：
- 这两条路径绕过了过期控制
- 旧的 `impersonated_token` 可能残留，导致新会话被模拟态覆盖
- 同一项目里出现两套写 token 的方式，后续很容易继续分叉

建议：
- 两个页面都改成调用 `setToken()`
- 若需要保留旧字符串兼容，放在 `setToken()` 内统一处理

### 4. `maxParticipants` 的空值语义在创建和编辑接口里不一致

| 位置 | 结论 |
|------|------|
| `src/routes/admin-lottery.ts:589-590` | 创建活动时，`body.maxParticipants` 为 `0` 会被 `Number(0)` 传入服务层 |
| `src/services/lottery/draws.ts:95-163` | 服务层把 `0` 当成 falsy，最终回退到默认容量，而不是“无限制” |
| `src/routes/admin-lottery.ts:660` | 编辑活动时，`0` 会被写成 `null` |

影响：
- API 语义前后不一致
- 外部调用方如果把 `0` 当作“无限”，会得到不同结果

建议：
- 统一约定“null 表示不限，0 直接拒绝”
- 或统一把 `0` 规范成 `null`，不要在创建和编辑两个分支做不同处理
