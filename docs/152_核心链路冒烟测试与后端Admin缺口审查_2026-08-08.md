## 3. 后端风险点

### 3.1 邮件发送：非阻塞但状态可追踪

| 风险 | 现状 | 建议 |
|------|------|------|
| 开奖邮件失败不回滚开奖 | `performDraw` 内 try/catch 邮件发送，失败仅记录 | ✅ 符合设计（邮件失败不应影响开奖结果） |
| 但失败后有运营可见性 | `sendWinnerNotifications` 会更新 `lotteryWinners.notificationStatus` 为 `sent`/`failed`/`pending`；前端 `AdminLotteryView.vue` 有 `retryAdminLotteryEmail` 重发入口 | ✅ 已有基础闭环 |
| 回调发卡后不通知 winner | `handlePaymentCallback` 只更新订单状态，不触发中奖邮件 | P0：支付成功后异步发送中奖通知 |

**代码位置**：
- `src/services/payment/payment-service.ts:845` — `prizeCodeId` 分配成功后无邮件触发
- `src/services/lottery/draw-execution.ts:280` — `performDraw` 在 `notify_winner_email_enabled` 开启时调用 `sendWinnerNotifications`
- `src/services/lottery/draw-execution.ts:520` — `sendWinnerNotifications` 逐封发送并更新 `notificationStatus`
- `frontend/src/views/admin/AdminLotteryView.vue:3393` — `handleRetryEmail` 调用后端 `retryAdminLotteryEmail` API

### 3.2 定时开奖邮件

| 风险 | 现状 | 建议 |
|------|------|------|
| `processDueDraws` 不开奖邮件 | 调用 `performDraw`，`performDraw` 在条件满足时发送中奖邮件 | ✅ 设计合理 |
| `sendDrawReminders` 仅提醒，不开奖 | 独立于 `processDueDraws`，由 Cron 触发 | ✅ 设计合理 |

**结论**：`performDraw` 在所有路径下均尝试发送中奖邮件（受 `notify_winner_email_enabled` 控制），不存在定时开奖邮件缺失问题。

### 3.3 并发与数据一致性

| 风险 | 现状 | 建议 |
|------|------|------|
| `acquirePrizeCode` 原子取卡 | SQLite 下 `UPDATE ... LIMIT 1 RETURNING` 是原子的 | ✅ 无 MVCC 问题 |
| 但 `importPrizeCodes` 分批插入 | 200 条/批，UNIQUE 冲突时回退逐条 | 可接受，但失败时 imported 计数可能不准确 |
| `processDueDraws` 并发处理 | 无显式分布式锁，但 `performDraw` 有 CAS（`WHERE status='open'` → `drawing'`），多实例 Cron 同一活动仅一个能夺取开奖权 | 当前单 VPS 部署下可接受；如未来多实例部署，建议加 `processing_lock` 或利用 `drawing` 状态 CAS |

**代码位置**：
- `src/services/lottery/draw-execution.ts:74` — `performDraw` CAS 夺取开奖权
- `src/services/lottery-service.ts:171` — `processDueDraws` 遍历到期活动调用 `performDraw`

### 3.4 错误处理与可观测性

| 风险 | 现状 | 建议 |
|------|------|------|
| 邮件失败记录在 winners 表 | `notificationStatus` 字段记录 sent/failed/pending，`notificationError` 记录错误详情 | ✅ 已有基础可观测性 |
| 支付回调失败返回 200 | `handlePaymentCallback` 返回 `{processed: false}`，调用方需决定 HTTP 状态 | 确认路由层是否正确返回 400/500 |
| `retryPaymentFulfillment` 无重试限制 | 运营可无限点击重试 | P2：增加 `retry_count` 字段，防止卡密池异常时无限重试 |

## 4. Admin 管理后台缺口

### 4.1 已有页面覆盖

| 页面 | 功能 | 缺口 |
|------|------|------|
| AdminLotteryView | 列表/创建/批量操作/导出/中奖邮件状态/重发 | 无「按活动类型筛选中奖邮件」 |
| AdminPrizesView | 奖品 CRUD/批量启停/码池管理 | 无「按活动筛选奖品」 |
| AdminPaymentOrdersView | 订单列表/补发卡密 | 无退款/对账/导出 |
| AdminDashboardView | 统计/待办/最近活动 | 无邮件发送统计 |

### 4.2 缺失功能（按优先级）

#### P0 — 运营阻断

| 功能 | 影响 | 建议 |
|------|------|------|
| **支付订单退款** | 用户付钱但收不到卡密，只能线下处理 | 新增 `refund` API + Admin 退款按钮 |
| **卡密库存预警** | 奖品售罄前无提醒，直到 `paid_fulfillment_failed` 才发现 | AdminDashboard 增加「库存不足」卡片 |

#### P1 — 运营效率

| 功能 | 影响 | 建议 |
|------|------|------|
| **批量中奖通知** | 开奖后需逐人查看/复制中奖信息 | 活动详情页增加「发送中奖通知」按钮 |
| **支付对账** | 无法核对支付平台流水与本地订单 | 新增「对账」页面，按日期导出 |
| **活动级邮件状态统计** | 不知道某活动有多少人收到/未收到邮件 | 活动详情增加邮件发送统计 |

#### P2 — 体验优化

| 功能 | 影响 | 建议 |
|------|------|------|
| **奖品按活动筛选** | AdminPrizesView 需全量滚动查找 | 增加 `drawId` 筛选参数 |
| **订单导出 CSV** | 财务对账需手动复制 | AdminPaymentOrdersView 增加导出按钮 |
| **操作审计日志** | 无法追溯「谁在什么时候补发了卡密」 | 复用现有 `admin_audit_logs` 或新增 |

### 4.3 前端组件状态

`AdminLotteryView.vue` 当前代码中不存在未使用变量 `shouldAutoExpandAdvancedForTemplate`。docs/151 提及的该变量可能是工作区未提交历史改动，已不在当前代码库中。

原计划创建 `src/smoke-core-flows.test.ts` 覆盖 10 条核心链路，但因 `tsc` 在单文件模式下仍报模块解析错误（`../services/lottery-service` 无法解析），且现有 `lottery-service.test.ts` 已覆盖大部分场景，决定：

1. **不新增独立 smoke 文件**，避免与现有 585 tests 重复
2. **在 `lottery-service.test.ts` 末尾增加「冒烟标签」测试组**，明确标记为端到端验证
3. **保留本次审查的文档输出**作为冒烟证据
