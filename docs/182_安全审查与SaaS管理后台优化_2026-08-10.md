## 一、QQ 群 → Web 找回 → 跨平台绑定 全链路闭环审查

### 1.1 主流程追踪（P0：卡密 Web 找回）

```
用户 → QQ 群 → /抽奖 中奖 → 私聊发送卡密 → 私聊失败 → 群回复追加 accessUrl
→ 用户点击 Web 链接 → 查看卡密
```

| 步骤 | 状态 | 说明 |
|------|------|------|
| 用户发送命令 | ✅ | inbound.ts 识别 + provisionPlatformUser 自动建用户 |
| 中奖后私聊 | ✅ | commands.ts 返回 privateMessages，路由层发送 |
| 私聊失败降级 | ✅ | QQ/Telegram 路由都有 catch，追加 accessUrl 到群回复 |
| Web 页验证令牌 | ✅ | SHA-256 哈希 + 5 分钟 + 一次性 CAS 消费 |
| Web 页查询卡密 | ⚠️ | **见下方 P0-1：跨租户数据泄露** |

### 1.2 跨平台绑定流程追踪（P1：QQ ↔ Telegram 身份合并）

```
用户 A → QQ 群 → /绑定 → 得到 6 位码 → 群内显示 → 群内成员 B 看到
→ B 在 Telegram 发 /绑定 <码> → B 的 Telegram 合并到 A 的 userId
```

| 步骤 | 状态 | 说明 |
|------|------|------|
| 生成绑定码 | ✅ | 28 字符集 × 6 位 = 4.8 亿组合，10 分钟，一次性 |
| 消费绑定码 | ✅ | CAS + 跨平台检查 + 同用户检查 |
| 合并 identity | ✅ | 重写 authIdentities.userId + 最佳努力清理孤儿 users |
| 码在群内公开 | 🔴 | **见下方 P0-2：绑定码公开 → 账号接管风险** |

## 二、高危漏洞（P0）

### P0-1：Web 卡密页跨租户隔离违规（命令已限租户，Web 兜底未限）

**严重级别：🟠 P0（隔离违规，非跨用户泄露）**
**结论置信度：✅ 确认**

**代码证据（逐行核对）：**
- `src/routes/public-access.ts` 第 48-101 行：`/api/public/access/card-codes?token=xxx`
  - 第 48-54 行：`identities where userId`（无租户过滤）
  - 第 69-74 行：`entries where (identityType, identityValue)`（无租户过滤）
  - 第 83-101 行：`winners where entryId in [...]`（**无 drawId、无 tenantId 过滤**）
- 对比：`src/services/platform/commands.ts` 第 832-837 行 `executeCardCodeCommand`：
  - `eq(lotteryWinners.tenantId, input.tenantId)` + `eq(lotteryWinners.drawId, input.drawId)` — **命令本身已正确限租户/限 draw**
- `src/services/platform/commands.ts` 第 849 + 893 行 `buildCardCodeAccessUrl`：
  - `generateAccessToken(db, input.user.userId, "card_code")` — **令牌只绑定 userId，未绑定 tenantId/drawId**

**攻击场景推演（✅ 确认成立）：**
1. 同一 QQ 号加入两个不同租户的 QQ 群，且在两租户都中过卡密
2. 用户在租户 A 群发 `/我的卡密` → 命令正确只返回租户 A 卡密（限 `input.drawId`）
3. 但生成的 `accessUrl` 令牌只绑定 `userId` → 打开 Web 页时 `public-access.ts` 忽略 draw 上下文，**同时返回租户 A 和租户 B 的卡密**
4. 违反验收标准：**"卡密不跨租户"**

**反向验证（"这不是漏洞"的辩护是否成立）：**
- 辩护："泄露的是用户自己的卡密，不是别人的，所以不算泄露"
- 反驳：SaaS 多租户验收标准明确要求"卡密不跨租户"。租户 A 的访问上下文不应暴露租户 B 的数据（即使属于同一用户）。租户 B 可能有更严格的隐私约束或已吊销该用户访问权。**该辩护不成立，隔离违规成立。**

**根因分析：**
- `provisionPlatformUser`（`src/services/platform/user-provision.ts` 第 80-88 行）：`authIdentities` 用 `UNIQUE(provider, providerUserId)` 唯一约束（schema.ts 第 57 行）→ 同一 QQ 号在任何租户都映射到**同一个 `users.id`**
- `buildCardCodeAccessUrl` 令牌只带 `userId`，丢失 `drawId` 上下文 → Web 页无法限租户
- 命令与 Web 兜底**作用域不一致**：命令限 `drawId`，Web 兜底不限

**修复方向（最小改动）：**
1. 令牌生成时记录 `drawId`（`access_tokens` 表新增 `draw_id` 列，migration 0051）
2. `public-access.ts` 第 97-100 行查询 winners 时增加 `eq(lotteryWinners.drawId, token.drawId)` 过滤
3. 这样 Web 页与命令作用域一致，完全隔离

### P0-2：绑定码群内公开 → 跨用户账号接管（绑定后可查看受害者卡密）

**严重级别：🔴 高危（跨用户数据泄露）**
**结论置信度：✅ 确认**

**代码证据（逐行核对）：**
- `src/services/platform/commands.ts` 第 954-964 行 `executeBindCommand`（无参模式）：
  - 第 964 行：`reply: \`🔗 你的绑定码：${bindingCode}\\n\\n请在另一个平台...\`` — **绑定码明文直出到群回复**
- `src/services/platform/binding.ts` 第 99-199 行 `consumeBindingCode`：
  - 第 126-128 行：只检查 `sourceProvider !== targetProvider`（不同平台）
  - 第 131 行：只检查 `sourceUserId !== targetUserId`（不同用户）— **不验证"消费者是否就是码的拥有者"**
  - 第 180-187 行：**直接将目标用户的 auth_identities.userId 重写为发起方的 userId**

**攻击场景推演（✅ 确认成立）：**
1. 受害者 A 在 QQ 群发 `/绑定` → Bot 在群内回复 `🔗 你的绑定码：X2W9K7`
2. 攻击者 B（同为该 QQ 群成员）在群内看到码
3. 攻击者 B 在 Telegram 群（任意已配置 Bot 的群）发送 `/绑定 X2W9K7`
4. 攻击者 B 的 Telegram `authIdentities.userId` 被重写为受害者 A 的 `userId`（binding.ts 第 180-187 行）
5. 攻击者 B 打开 `accessUrl`（Web 页）→ `public-access.ts` 查询 `identities where userId = A_userId` → 返回 (tg, B_tg_id) 和 (qq, A_qq_id) → 查询 entries 和 winners 返回**两者并集** → **B 看到 A 的卡密**

**反向验证（"这不是漏洞"的辩护是否成立）：**
- 辩护①："选举 /我的卡密 命令查询 entry 时用 identityValue，不是 userId，所以 B 看不到 A 的卡密"
  - 反驳：`/我的卡密` 命令本身确实限 `identityValue`，但 Web 访问 URL（`public-access.ts`）不限制，它通过 `identities where userId` 查出所有身份，再查所有 entries → 最终合并 wins。**B 通过 Web URL 可以看到 A 的卡密。** 辩护不成立。
- 辩护②："B 需要先有 Telegram 身份才能发 /绑定"
  - 反驳：`/绑定` 命令由 `inbound.ts` 路由 → `provisionPlatformUser` 在 `executeBindCommand` 之前自动创建 authIdentities 记录。B 第一次发 `/绑定` 时即被自动创建 Telegram 身份。**B 不需要任何前置交互。** 辩护不成立。
- 辩护③："B 只对同一租户的群有效"
  - 反驳：绑定码与卡片皆无 `tenantId` 关联。B 可在**任何租户**的 Telegram 群使用该码。辩护不成立。

**根因分析：**
- 绑定码设计为"持有即证明"，但码在群聊（公开场合）下发，群内任何人都能看到
- 绑定码与卡片皆无 `tenantId` 隔离，攻击者可在任意 Telegram 群使用
- 消费绑定码时不验证"消费者是否就是码的合法拥有者"

**即刻缓解措施（不改变方案）：**
1. 绑定码像卡密一样：**优先走私聊下发**，群内只回显`🔗 绑定码已通过私聊发送，请查看私聊消息。`
2. 私聊失败时，**不在群内显示绑定码明文**，改为提示`⚠️ 私聊发送失败，请检查隐私设置后重新发送 /绑定`
3. 绑定码回复中增加隐私提示（即使私聊也有）

**长期方案（方案 B/C 见 docs/181）：**
- 方案 B：OAuth 授权（点击链接完成身份验证，不在群内显示任何码）
- 方案 C：交叉验证（两个平台都发送 /绑定 并携带对方码）

## 三、中等风险项（P1-P2）

### P1-1：私聊投递失败无审计

**严重级别：🟡 中**

**代码证据：**
- `src/routes/platform-qq.ts` 第 114-123 行：私聊 catch 后只改 `result.reply`，不写 `platformDeliveries`
- `src/routes/platform-telegram.ts` 第 111-118 行：同上

**影响：**
- 运营者后台无法看到"某用户的私聊投递失败"事件
- 无法排查是用户关闭了私聊权限，还是适配器配置问题
- 群助手健康监控缺失

**修复方向：**
- 私聊发送失败时，写入 `platformDeliveries` 记录，`status = "failed"`, `lastError = "私聊发送失败"`
- 后台增加投递失败告警/统计

### P1-2：绑定码明文存储（已登记）

**严重级别：🟡 中**

**代码证据：**
- `src/db/schema.ts` 第 104 行：`code: text("code").notNull()` — 明文存储
- 注释注明"无需哈希：短时效 + 一次性 + 高熵"

**风险：**
- 数据库泄露后，历史绑定码可见
- 但因绑定码短时效（10 分钟）+ 一次性，泄露历史码无实质危害
- 已登记为已知风险，维持现状

---

### P2-1：命令层无速率限制

**严重级别：🟡 低（当前）- 随时间推移可能上升**

**代码证据：**
- `src/services/platform/commands.ts` — `executeBindCommand`、`executeCardCodeCommand` 均无 `checkDbRateLimit` 调用
- 系统已有 `src/lib/rate-limit.ts`，但未接入平台命令路径

**风险：**
- 用户可高频刷 `/我的卡密` 生成大量令牌（5 分钟有效，但令牌行数无限增长）
- 用户可高频刷 `/绑定` 生成大量绑定码（10 分钟有效，行数无限增长）
- 恶意用户可高频试探 `/绑定 XXXXXX` 暴力破解绑定码（28^6=4.8 亿组合，但 10 分钟窗口内无限制请求降低安全性）

**修复方向：**
- `/绑定` 生成：每人每 60 秒 1 次
- `/绑定 <code>` 消费：全局每 10 秒 1 次（防暴力破解）
- `/我的卡密` 生成：每人每 30 秒 1 次
- `/card-codes` 公共端点：按 IP 每 10 秒 1 次

### P2-2：过期令牌/绑定码永不清理

**严重级别：🟡 低**

**代码证据：**
- `cleanExpiredTokens` 定义在 `access-token.ts` 第 105 行，但**从未被任何代码调用**
- `platform_bindings` 完全无清理函数

**影响：**
- `access_tokens` 和 `platform_bindings` 表无限增长

**修复方向：**

- 新增 `cleanExpiredBindings` 函数（清理 >24h 的绑定码）
- 与 `cleanExpiredRateLimits` 等现有清理任务串在一起执行

### P2-4：绑定码使用 `Math.random()` 非密码学安全随机数

**严重级别：🟡 低**
**结论置信度：✅ 确认**

**代码证据：**
- `src/services/platform/binding.ts` 第 40-47 行：
  ```typescript
  function generateCode(): string {
    let code = "";
    for (let i = 0; i < BINDING_CODE_LENGTH; i++) {
      const idx = Math.floor(Math.random() * BINDING_CODE_CHARS.length);
      code += BINDING_CODE_CHARS[idx];
    }
    return code;
  }
  ```
  — **使用 `Math.random()`，非 CSPRNG**

**与代码库既定规范不一致：**
- `src/services/lottery/utils.ts` 第 17-19 行（显式注释）：
  > `Math.random()` 是伪随机数生成器，可预测且不安全。`crypto.getRandomValues()` 是密码学安全的随机数生成器，适合抽奖等公平性场景。
- `src/routes/platform-redemption-codes.ts` 第 32-33 行：兑换码生成使用 `crypto.getRandomValues()`
- `src/services/lottery/spin-quota.ts` 第 155-156 行：spin-quota 使用 `crypto.getRandomValues()`
- 代码库已有明确模式：**安全敏感随机数用 `crypto.getRandomValues()`，不用 `Math.random()`**

**实际风险：**
- `Math.random()` 在 V8 中使用 xorshift128+（非密码学安全 PRNG），攻击者如果观察到足够多的连续绑定码输出，有可能重建 PRNG 状态并预测未来绑定码
- 但在本场景中风险极低：绑定码短时效（10 分钟）+ 一次性 + 每组 6 位（28^6 ≈ 4.8 亿组合），且攻击者需要逆推 xorshift128+ 状态
- 主要问题是**代码质量不一致**，应修复以保持代码库安全编码规范的一致性

**修复方向：**
- 将 `binding.ts` 第 40-47 行的 `generateCode` 改为使用 `crypto.getRandomValues()`：
  ```typescript
  function generateCode(): string {
    const chars = BINDING_CODE_CHARS;
    const bytes = new Uint8Array(BINDING_CODE_LENGTH);
    crypto.getRandomValues(bytes);
    let code = "";
    for (let i = 0; i < BINDING_CODE_LENGTH; i++) {
      code += chars[bytes[i] % chars.length];
    }
    return code;
  }
  ```
