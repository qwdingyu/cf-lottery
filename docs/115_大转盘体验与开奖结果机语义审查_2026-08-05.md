# 115 大转盘体验与开奖结果机语义审查

> 日期：2026-08-05  
> 范围：公开页游戏壳（wheel/slot/scratch 等）× `joinDraw` × `performDraw` × `my-result`  
> 原则：**只写源码可证事实**；不臆造「已实现即时开奖停扇」；不把运营文案当实现。  
> 状态：语义结论已对齐；模板营销文案已纠偏；**未实现** lottery×instant 结果机（产品可选路线，非本轮施工）

---

## 一、一句话结论

| 问题 | 证据结论 |
|:-----|:---------|
| 用户转大转盘「得到什么资格」？ | **参与资格（`lottery_entries` 一行）**，不是当场中奖资格 |
| 转盘停在哪一扇 = 中了该奖？ | **否**。停止角随机，无服务端奖项索引；动画是参与成功氛围 |
| 中奖何时产生？ | **`performDraw`（手动或 scheduled 到点）** 写入 `lottery_winners` + 可选锁 `prize_codes` |
| 用户能看到哪一阶段信息？ | 见第三节阶段表 |
| 后端开奖流程是否「搞错了」？ | **延迟开奖路径正确**；错在 **营销/模板文案暗示「转即中」**，以及产品文档里 **instant 抽奖尚未接线** 却常被写成目标态 |
| 是否最佳实践？ | **「体验壳 ≠ 结果机」是正确架构**（行业与 docs/055a 一致）；若产品要「转盘即开奖」，必须 **另建 instant 结果路径**，不能假装现有 wheel 已是 |

## 二、三轴分离（领域铁律，源码已落实）

| 轴 | 字段 | 大转盘模板实际值 | 决定什么 |
|:---|:-----|:-----------------|:---------|
| 业务类型 | `activity_kind` | `lottery` | 中奖落 `lottery_winners`，不是接龙 outcome |
| 体验壳 | `experience_type` | `wheel` | 前端渲染 `WheelGame`，只 `emit('play')` |
| 结果机 | `result_mode` | **`manual`（模板默认）** 或 `scheduled` | **何时**产生中奖；**不**由转盘决定 |

证据：

- 模板注释写死：`joinDraw` 对 lottery **不产生即时结果**；故 `resultMode: "manual"`（`src/lib/activity-templates.ts`）
- `joinDraw`：非 `signup_chain` 成功返回 `{ joined, entryId, … }`，**无** `outcome`、**不写** `lottery_winners`（`participation.ts`）
- `WheelGame`：点击只 `emit('play')`；`celebrateKey` 后 `runCelebrateSpin` **随机停角**，注释写明「不对准中奖扇区」（`WheelGame.vue`）
- 游戏契约：`types.ts` —「动画不得在无服务端结果时宣称为个人中奖」
- 中奖唯一写入：`performDraw`（`draw-execution.ts`）CAS `open→drawing→drawn`，抽样 + 事务写 winners / 锁码
- 查结果：`POST .../my-result` 对 lottery 查 `lottery_winners`（+ 码/履约字段）；`drawStatus` 区分 open/drawn（`public-lottery.ts`）

**禁止互相推导**：不能从 `experience_type=wheel` 推出「已开奖」；不能从 `result_mode=instant`（若运营误配）推出 join 会出结果——**当前 join 根本不读 resultMode 做开奖**。

## 三、用户信息阶段（可观测）

以默认 **lottery + wheel + manual** 为例：

| 阶段 | 用户可见 | 后端事实 | 关键 UI |
|:-----|:---------|:---------|:--------|
| 0 未参与 | 奖池陈列（扇区奖品名）、规则、倒计时、裂变榜（若开） | 无 entry | `WheelGame` 空闲文案「立即参与」 |
| 1 点击转盘 | 按钮「提交中」+ 可选 idle 慢转 | 尚无 entry；在走身份/OTP/join | `loading` |
| 2 join 成功 | 庆祝旋转（随机）+ 弹窗「参与成功」+ manual 说明「主办方开奖后查询」 | **`lottery_entries` 已写**；`entryId` 返回 | `celebrateKey++`、`GameResultModal` |
| 3 已参与待开奖 | 状态「已参与」；可邀请（未终态）；可查 my-result → `joined=true, won=false` | status 仍 `open` | 公开卡 + 查结果 |
| 4 运营/系统开奖 | 邮件（若配置）；公开状态 drawn | `performDraw` → winners / 码 | 管理端开奖 / scheduled 任务 |
| 5 用户查结果 | 中奖：奖品名/档/卡密；未中：诚实未中 + 可选安慰券 | `my-result` 读 winners | 结果区 |

**用户在阶段 2 得到的「资格」精确含义：**

1. **本场参与席位**（entry）——开奖候选池一员  
2. **身份可恢复的 entryId**（本机 hints / 查结果）——裂变分享、榜「是我」依赖它  
3. **不是** 奖项档位、**不是** 卡密、**不是** 转盘停扇对应的奖品  

若开启裂变：阶段 2 起可生成 `?ref=` 分享；邀请计入 `share_records`；开奖时权重 `1 + min(invited×per, max)`——**仍只影响中奖概率，不在 join 时发奖**。

## 四、与其它 result_mode / activity_kind 对照（防混淆）

| 组合 | join 时有无结果 | 说明 |
|:-----|:----------------|:-----|
| lottery + manual/scheduled | **无** 个人中奖 | 本审查主路径 |
| lottery + **instant（若配置）** | **仍无**（源码） | 模板故意不用 instant；join **不**根据 resultMode 开奖；运营若手改 instant 只会 **文案误导**（`GameResultModal` 走 instant 提示）而无结果 |
| signup_chain + ordered_assignment | **有** assignment outcome | 第 N 位 / 候补 |
| claim + instant | 产品目标「领取」；体验 reveal | 非转盘抽奖；勿与 lottery 混谈 |
| survey/vote + no_result / vote_tally | 参与即提交 | 无 lottery winners 语义 |

`defaultResultModeForActivity("lottery")` → `manual` 或 `scheduled`（看 drawTrigger），**不是** instant（`draws.ts`）。

## 五、开奖流程是否最佳实践？

### 5.1 当前延迟开奖（manual / scheduled）——** indstry 合理且实现正确**

适合：名额有限、要公平抽样、要防刷后统一开奖、要裂变加权、要邮件/码履约。

优点（源码已有）：

- CAS 防双开；drawing 治愈；幂等再开  
- 裂变与榜同一 `aggregateViralInviteCounts`  
- 中奖与锁码同事务；邮件失败不回滚开奖（项目验收铁律）  
- 公开查结果与管理端 winners 同源表  

### 5.2 用户/运营的「错觉」从哪来？

| 来源 | 问题 | 本轮处理 |
|:-----|:-----|:---------|
| 模板 description「转动转盘**随机获得**奖品」 | 像即时中奖 | **已改**诚实文案 |
| 刮刮卡 description「**即时揭晓**是否中奖」 | 与 resultMode=manual 矛盾 | **已改** |
| 历史 docs/021 矩阵写「即时抽奖 lottery+instant」 | 目标态，非实现 | 本文标明 **未接线** |
| 转盘视觉像赌场即开 | 行业常见；靠文案+结果弹窗纠偏 | 055a 已做语义；保持 |

### 5.3 若要做「真·转盘即开奖」——正确做法（路线，**本轮不实现**）

必须同时满足，否则是灾难：

1. `result_mode=instant` **且** `joinDraw`（或独立 spin API）在服务端 **原子** 决定中奖/未中 + 写 winners/码  
2. 响应返回可映射的 `prizeTierIndex` / `won`  
3. 前端 **仅在有索引时** 停扇对齐（docs/055a P1+）  
4. 库存/名额/防刷在 join 热路径；与「全员参与完再抽」产品互斥——**二选一或分模板**  
5. 裂变加权与 instant 的冲突要产品拍板（每人 join 时抽 vs 全局池）  

**禁止**：只改 `resultMode` 字段或只改转盘停扇，不改 join。

### 5.4 结论：没有「搞错整条开奖链路」

- **搞对的**：entry → 池 → performDraw → winners → my-result  
- **没做的**：instant lottery  
- **易误导的**：模板/部分产品文档把体验说成即开  

这是 **产品叙事与实现差一截**，不是 performDraw 算法写反。

### 5.5 续审发现：定时开奖接线断点（2026-08-05，源码可证）

| 层 | 事实 | 后果 |
|:---|:-----|:-----|
| 管理端表单 | `drawTime` **必填**；hint「系统自动开奖时间」 | 运营以为到点会自动开 |
| 创建 payload（修复前） | 只传 `drawAt`，**不传** `drawTrigger` | — |
| `createDraw` / 路由（修复前） | `drawTrigger` 缺省 **`manual`** | 有 `drawAt` 仍是 manual |
| Cron / dashboard 到期 | 只扫 `drawTrigger === 'scheduled'` | **到点不会自动 performDraw** |
| 手动开奖 | `POST .../draw` → `performDraw` 仍可用 | 运营可点「立即开奖」补救 |

**结论**：延迟开奖**算法**没错；**产品表单与 trigger 字段脱节**导致「看起来是定时、实际是纯手动」。

**本轮修复（证据闭环）**：

1. 前端 `resolveDrawTrigger` / `resolveLotteryScheduleFields`：lottery + drawAt → 提交 `drawTrigger=scheduled` + `resultMode=scheduled`  
2. 后端 `createDraw` + `POST /draws`：lottery 有 drawAt 且未显式 trigger → 推断 scheduled；显式 `manual` 仍尊重  
3. 发布预检：`basic.draw_at.orphan` 警告（有 drawAt 仍 manual）  
4. Cron / dashboard due：加 `activityKind=lottery` 纵深  

**未改（有意）**：不实现 lottery×instant；不重写 performDraw 抽样。

## 七、验收

1. 创建「大转盘」模板 → 有开奖时间时 `drawTrigger/resultMode=scheduled`；转盘 → 参与成功，**无**卡密  
2. 管理端开奖后 / 定时到期后 → my-result 见 won/奖品  
3. 转盘停扇 **不必** = 中奖奖品  
4. 已参与条「查询结果」为主色按钮；裂变文案谈「票/权重」不谈「再参与」  
5. 库内历史数据：若仍 `drawAt` + `manual`，发布预检见 orphan 警告；需重存或改 trigger 才进 Cron
