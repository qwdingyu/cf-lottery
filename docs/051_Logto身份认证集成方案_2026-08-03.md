# 051 Logto 身份认证集成方案

> 日期：2026-08-03
> 方案依据：cf-shop 050 号文档的 Logto 评估 + cf-lottery 认证体系现状分析
> 方案选择：Logto Cloud Free + 自签 JWT 交换（最低成本、最小改动）

---

## 一、方案概述

### 1.1 背景

cf-lottery 当前认证体系：
- 管理员/运营者：用户名+密码 → HMAC-SHA256 → JWT(24h)
- 参与者(open 模式)：邮箱验证码(6 位数字，无盐 SHA-256) → JWT
- 参与者(registered 模式)：用户名+密码 → JWT
- RBAC：tenantRole(owner/admin/viewer) + platformRole(platform_owner/operator/support)
- 限流：内存 + DB 级原子条件 INSERT

### 1.2 方案选择

**Logto Cloud Free + 自签 JWT 交换**：

```
前端(Logto SDK) → 登录 → Logto 签发 ID Token → 
前端用 ID Token 交换自签 JWT → 
后端验证自签 JWT(现有中间件零改动)
```

### 1.3 为什么不是其他方案

| 方案 | 月成本 | 拒绝原因 |
|------|--------|---------|
| Logto Pro + RBAC | $56 | 当前免费层部署，$56/月超预算 |
| Logto 自部署 OSS | $5-20 + 运维 | 需要 PostgreSQL + Docker，运维成本高 |
| SuperTokens/Zitadel | 自部署 | 学习成本高，Workers 适配同需自实现 |
| 保持现状 | $0 | 无法满足"必须使用 Logto"的业务需求 |

### 1.4 Free 方案可行性

Logto Free 方案的限制与规避：

| 限制 | 影响 | 规避方案 |
|------|------|---------|
| 无 API Resource | 无法保护自定义 API | 自签 JWT 交换，API 验证自签 JWT |
| 无 RBAC | 无法管理角色 | 沿用现有 tenantRole + platformRole |
| 3 个应用 | 应用数量限制 | 用户端 SPA + 管理后台 SPA，够用 |
| 50,000 MAU | 月活用户上限 | 当前阶段远低于此 |
| 无组织管理 | 多租户管理 | 沿用现有 tenantId 逻辑 |

## 二、架构设计

### 2.1 认证流程

```
┌──────────┐         Logto 登录         ┌──────────┐
│ 前端 SPA  │ ────────────────────────→  │  Logto   │
│          │   (邮箱/社交/密码)          │  Cloud   │
│          │ ←────────────────────────  │  (Free)  │
│          │   ID Token + Access Token  └──────────┘
│          │                                │
│          │   POST /api/auth/logto-exchange │ 验证 ID Token
│          │   (携带 ID Token)              │ (jose + JWKS)
│          │        │                       │
│          │        ▼                       │
│          │   ┌──────────────┐             │
│          │   │ 后端 API     │             │
│          │   │ (CF Worker)  │◀────────────┘
│          │   │              │
│          │   │ 验证成功后签发自签 JWT     │
│          │   │ (含 sub/email/tenantId/role)│
│          │   │              │
│          │◀──│ 返回自签 JWT  │
│          │   └──────────────┘
│          │
│          │   后续 API 请求携带自签 JWT
│          │   (现有中间件 requireAuth 验证)
│          ▼
│    现有 RBAC + 租户隔离（全部不变）
```

### 2.2 关键设计决策

**自签 JWT 格式**（与现有格式兼容）：
```json
{
  "sub": "logto|user_id",      // Logto 用户 ID
  "email": "user@example.com",
  "tenantId": "tenant_xxx",    // 现有租户 ID
  "tenantRole": "owner",       // 现有角色
  "platformRole": null,        // 现有平台角色
  "impersonated": false,       // 现有模拟登录
  "exp": 1712345678            // 24h 有效期
}
```

**为什么不是直接用 Logto Access Token 验证 API**：
- Logto Free 方案无 API Resource，无法验证 audience
- 自签 JWT 可以携带现有 tenantId/role 等字段，不需要改动现有中间件
- 自签 JWT 使用现有 JWT_SECRET 签名，与现有流程一致

## 四、实施步骤

### 第 1 步：注册 Logto 租户并获取配置

1. 访问 https://cloud.logto.io 注册免费账号
2. 创建租户（选择 Free 方案）
3. 创建应用：SPA 应用（用户端）+ SPA 应用（管理后台）
4. 配置邮箱连接器（Resend 或 SendGrid）
5. 获取 `LOGTO_ENDPOINT`（如 `https://xxx.logto.app`）和 `LOGTO_APP_ID`

### 第 2 步：后端新增 logto-auth.ts（负责 JWKS 验证 + 自签 JWT 签发）

```typescript
// src/lib/logto-auth.ts
// 功能：
// 1. 从 Logto JWKS 端点获取公钥并缓存（减少额外请求）
// 2. 验证 Logto ID Token（使用 jose 库）
// 3. 签发自签 JWT（含现有 tenantId/role 等字段）
// 4. 供 POST /api/auth/logto-exchange 端点使用
```

### 第 3 步：后端新增 token 交换端点

```typescript
// POST /api/auth/logto-exchange
// 请求：{ idToken: string }
// 流程：验证 Logto ID Token → 查询/创建用户 → 签发自签 JWT → 返回
// 响应：{ token: string, email: string, ... }
```

### 第 4 步：前端集成 Logto SDK

```typescript
// frontend/src/main.ts
import Logto from '@logto/vue'
app.use(Logto, {
  endpoint: LOGTO_ENDPOINT,
  appId: LOGTO_APP_ID,
})
```

### 第 5 步：替换登录页

AdminLoginView.vue 中加"使用 Logto 登录"按钮，点击后跳转 Logto 登录页。

### 第 6 步：替换参与登录流程

LotteryView.vue 中 open 模式的登录弹窗改为 Logto 登录。

## 六、部署注意事项

1. **环境变量**：生产环境通过 `wrangler secret put` 设置 Logto 相关变量
2. **CORS**：Logto 登录页跳转需要允许 Logto 域名的 CORS
3. **回调 URL**：Logto 应用配置中需设置正确的回调 URL（如 `https://lucky.eforge.xyz/callback`）
4. **用户数据迁移**：现有用户数据（邮箱映射）需要迁移到 Logto（或保持双轨运行）
