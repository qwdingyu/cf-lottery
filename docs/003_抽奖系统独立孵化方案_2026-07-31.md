# 抽奖系统独立孵化方案_2026-07-31

> 文档编号：084
> 创建时间：2026-07-31
> 修订时间：2026-07-31
> 状态：专家顾问修订版
> 目标：从 `cf-shop` 抽取抽奖能力，孵化一个面向商户/组织的多租户 SaaS 抽奖产品

---

## 一、结论先行

可以借用 `cf-shop` 现有抽奖体系孵化独立项目，但不能直接复制当前实现。

`cf-shop` 的抽奖模块是单商户、单后台、依附商品/卡密/订单/邮件体系的功能模块；新的产品目标是多租户 SaaS，每个客户登录后自主管理自己的活动、奖品、参与名单、开奖和通知。因此最优方案是：

1. **复用验证过的业务经验**
   - 开奖状态机：`open -> drawing -> drawn` 的 CAS 思路。
   - 中奖邮件：独立 `lottery_winner` 模板，不复用订单发货邮件。
   - 卡密发放：中奖后锁定并发放一条未使用卡密。
   - 定时开奖兜底：Cron 只处理到期活动，任务必须有界。
   - 公开页展示控制：参与人数、中奖人数、中奖名单可按活动配置隐藏。

2. **重建 SaaS 必需的底座**
   - 租户表、用户表、成员表、角色权限。
   - 所有业务表必须有 `tenant_id`。
   - 管理端必须按 `tenant_id` 过滤，禁止任何跨租户查询。
   - 名单、邀请码、卡密必须拆成独立表，不能放 JSON 字段。
   - 活动公开链接使用不可枚举 slug，避免暴露活动 ID。

3. **不要照搬 cf-shop 的交易模型**
   - 不需要 `orders`、支付、余额、返佣、商品 storefront。
   - 奖品不是商品，奖品库存不是电商库存。
   - 抽奖发奖只产生 `winner` 和 `prize_code` 状态，不产生支付订单。

一句话：**这不是把 cf-shop 的 lottery 文件夹拷出去，而是把抽奖领域经验抽象成一个独立、多租户、低耦合的 SaaS 产品。**

## 二、产品定位

### 2.1 产品定义

产品定位为：**轻量、多场景、可自助开通的抽奖 SaaS**。

目标用户不是消费者，而是需要组织抽奖活动的运营者：

- 企业 HR
- 社群运营
- 课程老师
- 电商店主
- 自媒体博主
- 活动策划方
- 展会/线下门店
- 开发者工具或数字内容商家

核心闭环：

```text
客户注册租户 -> 创建奖品 -> 配置参与规则 -> 发布活动链接/二维码
-> 用户参与 -> 自动/手动开奖 -> 发奖/通知 -> 导出结果/复盘
```

### 2.2 产品边界

MVP 不做大而全营销平台，只做抽奖 SaaS 的高频闭环：

- 做：活动创建、参与、名单限制、抽奖、发奖、通知、导出、审计。
- 不做：支付、商城、复杂 CRM、营销自动化、分销返佣。
- 可预留：付费套餐、品牌自定义、Webhook、API 接入。

### 2.3 平台角色

原文“没有超级管理员”不适合 SaaS。正确设计是：

| 角色 | 是否需要 | 权限边界 |
|---|---:|---|
| 平台 Owner | 需要 | 管理平台配置、套餐、风控、租户封禁，不代运营活动 |
| 平台 Support | 可选 | 只读排障，默认不得查看卡密明文 |
| 租户 Owner | 需要 | 管理自己的租户、成员、活动、奖品 |
| 租户 Admin | 需要 | 管理活动和奖品 |
| 租户 Operator | 建议 | 只能创建/编辑活动、查看统计 |
| 租户 Viewer | 可选 | 只读查看活动数据 |
| 参与者 | 需要 | 通过公开活动页参与，不进入管理后台 |

关键边界：**平台管理员用于 SaaS 运维，不是代替客户管理抽奖活动。客户必须能自助完成闭环。**

## 三、使用场景和抽奖模式

### 3.1 典型场景

| 场景 | 组织者 | 参与者 | 关键诉求 | 推荐模式 |
|---|---|---|---|---|
| 公司年会 | 企业 HR | 员工 | 名单内参与、防作弊、导出名单 | 限定名单 |
| 课程福利 | 老师/机构 | 学员 | 学员邮箱验证、奖品码发放 | 限定名单 + 卡密奖品 |
| 社群活动 | 社群运营 | 群成员 | 密码/口令进入、快速传播 | 密码进入 |
| 粉丝抽奖 | 博主 | 粉丝 | 公开参与、分享传播 | 公开抽奖 |
| 展会抽奖 | 展台运营 | 到场人员 | 手机扫码、现场开奖 | 公开 + 手动开奖 |
| VIP 福利 | 商家 | 会员 | 只有会员可参与 | 名单/邀请码 |
| 内测资格 | 产品团队 | 申请者 | 选中后发放激活码 | 申请审核 + 卡密奖品 |
| 门店促销 | 店主 | 到店顾客 | 二维码参与、中奖后核销 | 公开 + 核销码 |

### 3.2 参与模式

不要只做“随意人员/限定人员”两个粗粒度模式。SaaS 应该支持以下几类，并通过配置组合覆盖实际需求。

| 模式 | 标识 | 说明 | MVP 优先级 |
|---|---|---|---|
| 公开参与 | `open` | 任何访问活动链接的人可参与 | P0 |
| 限定名单 | `roster` | 预先导入邮箱/手机号名单，名单内才可参与 | P0 |
| 访问密码 | `password` | 输入活动密码后可参与 | P0 |
| 邀请码 | `invite_code` | 输入邀请码参与，可限制每码次数 | P1 |
| 一人一码 | `unique_code` | 每个参与者有唯一参与码 | P1 |
| 申请审核 | `approval` | 用户先报名，运营审核后进入候选池 | P2 |
| API 校验 | `external_check` | 调外部 API 判断资格 | P2 |

### 3.3 身份字段

MVP 建议以邮箱为主键，手机号作为可选扩展：

- `email`：默认参与者身份，便于通知和去重。
- `phone`：可选，适合线下/中国大陆活动。
- `name`：可选展示字段。
- `external_id`：企业员工号、学号、会员 ID 等。

参与者唯一性建议：

```text
UNIQUE(tenant_id, draw_id, identity_type, identity_value)
```

不要只用 email 写死所有场景，否则线下活动和企业内部活动会不灵活。

### 3.4 开奖模式

| 模式 | 标识 | 说明 | 风险 |
|---|---|---|---|
| 手动开奖 | `manual` | 租户后台点击开奖 | 最稳，MVP 必做 |
| 定时开奖 | `scheduled` | 到时间自动开奖 | 需要 Cron 兜底 |
| 即时开奖 | `instant` | 用户参与后立即知道结果 | 易被刷，P2 |
| 分批开奖 | `batch` | 每天/每小时抽一批 | 复杂，P2 |
| 加权开奖 | `weighted` | 根据权重提高概率 | 需透明规则，P2 |

MVP 推荐只做 `manual + scheduled`。

### 3.5 奖品模式

| 奖品类型 | 标识 | 发放方式 | MVP |
|---|---|---|---|
| 纯名单奖 | `manual_fulfillment` | 只生成中奖名单，租户线下联系 | P0 |
| 卡密/券码 | `code` | 从导入码池发一条给中奖者 | P0 |
| 文件/链接 | `digital_link` | 中奖后展示固定链接或说明 | P1 |
| 实物奖品 | `physical` | 收集地址，租户发货 | P1 |
| 多奖项 | `tiered` | 一等奖/二等奖/三等奖 | P1 |

MVP 不要做“多商品、支付、订单”，但要支持一个活动多个奖项的扩展方向。

## 四、SaaS 多租户架构

### 4.1 租户模型

核心概念：

```text
tenant = 客户组织
user = 登录账号
tenant_member = 用户在某个租户里的角色
```

一个用户未来可以加入多个租户，但 MVP 可以先让注册用户自动创建一个默认租户。

### 4.2 隔离原则

所有业务表必须包含：

```text
tenant_id TEXT NOT NULL
```

所有管理端查询必须满足：

```text
WHERE tenant_id = currentTenantId
```

所有公开活动页查询也必须通过 `public_slug` 先解析活动，再用活动自身的 `tenant_id` 查询关联奖品、名单、中奖记录。

禁止：

- 后端仅靠前端传 `tenantId`。
- 管理端 API 漏掉 `tenant_id` 条件。
- 用递增 ID 或可枚举 ID 做公开链接。
- 卡密明文跨租户共表无租户字段。

### 4.3 认证方案

用户要求用户名和密码的管理端，因此推荐：

- 用户名或邮箱登录。
- 密码用 Argon2id 或 bcrypt hash，不存明文。
- 登录成功签发短期访问 JWT。
- 刷新 token 存服务端 session 表，支持撤销。
- 管理端敏感操作二次确认，不建议一开始做 MFA，但要预留。

MVP 可用：

```text
username + password + session JWT
```

后续可扩展：

- 邮箱验证
- MFA
- SSO/OIDC
- 邀请成员加入租户

## 五、推荐数据模型

下面是建议模型，不建议继续使用 `roster_json`、`invite_codes_json` 这类 JSON 大字段。名单和邀请码是高频校验数据，必须建表和索引。

### 5.1 租户与用户

```sql
CREATE TABLE tenants (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  plan TEXT NOT NULL DEFAULT 'free',
  status TEXT NOT NULL DEFAULT 'active', -- active | suspended | deleted
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE users (
  id TEXT PRIMARY KEY,
  username TEXT NOT NULL UNIQUE,
  email TEXT NOT NULL DEFAULT '',
  password_hash TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'active',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE tenant_members (
  tenant_id TEXT NOT NULL,
  user_id TEXT NOT NULL,
  role TEXT NOT NULL DEFAULT 'owner', -- owner | admin | operator | viewer
  created_at TEXT NOT NULL,
  PRIMARY KEY (tenant_id, user_id)
);
```

### 5.2 奖品与码池

```sql
CREATE TABLE prizes (
  id TEXT PRIMARY KEY,
  tenant_id TEXT NOT NULL,
  name TEXT NOT NULL,
  description TEXT NOT NULL DEFAULT '',
  image_url TEXT NOT NULL DEFAULT '',
  prize_type TEXT NOT NULL DEFAULT 'code',
  fulfillment_note TEXT NOT NULL DEFAULT '',
  active INTEGER NOT NULL DEFAULT 1,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE prize_codes (
  id TEXT PRIMARY KEY,
  tenant_id TEXT NOT NULL,
  prize_id TEXT NOT NULL,
  code TEXT NOT NULL,
  secret TEXT NOT NULL DEFAULT '',
  note TEXT NOT NULL DEFAULT '',
  status TEXT NOT NULL DEFAULT 'available', -- available | locked | issued | revoked
  locked_by_winner_id TEXT DEFAULT '',
  issued_at TEXT,
  created_at TEXT NOT NULL
);

CREATE INDEX idx_prize_codes_prize_status
  ON prize_codes(tenant_id, prize_id, status, created_at);
```

卡密加密建议：

- MVP 可用服务端密钥加密 `secret`。
- 管理端默认脱敏展示。
- 中奖邮件才解密发送。
- 平台 Support 默认不可查看明文。

### 5.3 活动

```sql
CREATE TABLE lottery_draws (
  id TEXT PRIMARY KEY,
  tenant_id TEXT NOT NULL,
  public_slug TEXT NOT NULL UNIQUE,
  title TEXT NOT NULL,
  description TEXT NOT NULL DEFAULT '',
  status TEXT NOT NULL DEFAULT 'draft',
  participation_mode TEXT NOT NULL DEFAULT 'open',
  draw_trigger TEXT NOT NULL DEFAULT 'manual',
  start_at TEXT NOT NULL,
  end_at TEXT NOT NULL,
  draw_at TEXT,
  max_participants INTEGER,
  expected_participants INTEGER NOT NULL DEFAULT 0,
  winner_count INTEGER NOT NULL DEFAULT 1,
  show_participant_count INTEGER NOT NULL DEFAULT 1,
  show_winner_count INTEGER NOT NULL DEFAULT 1,
  show_winner_list INTEGER NOT NULL DEFAULT 0,
  require_email_verify INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  drawn_at TEXT,
  failure_reason TEXT NOT NULL DEFAULT ''
);

CREATE INDEX idx_lottery_draws_tenant_status
  ON lottery_draws(tenant_id, status, created_at DESC);

CREATE INDEX idx_lottery_draws_due
  ON lottery_draws(status, draw_at);
```

### 5.4 多奖项

即使 MVP 前端先做单奖品，也建议数据模型支持多奖项：

```sql
CREATE TABLE lottery_prize_tiers (
  id TEXT PRIMARY KEY,
  tenant_id TEXT NOT NULL,
  draw_id TEXT NOT NULL,
  prize_id TEXT NOT NULL,
  tier_name TEXT NOT NULL DEFAULT '中奖',
  winner_count INTEGER NOT NULL DEFAULT 1,
  sort_order INTEGER NOT NULL DEFAULT 100
);
```

好处：

- 年会一二三等奖可自然表达。
- 不需要后续大改开奖结果表。

### 5.5 参与资格

限定名单：

```sql
CREATE TABLE lottery_roster_members (
  id TEXT PRIMARY KEY,
  tenant_id TEXT NOT NULL,
  draw_id TEXT NOT NULL,
  identity_type TEXT NOT NULL DEFAULT 'email',
  identity_value TEXT NOT NULL,
  display_name TEXT NOT NULL DEFAULT '',
  metadata_json TEXT NOT NULL DEFAULT '{}',
  created_at TEXT NOT NULL,
  UNIQUE(tenant_id, draw_id, identity_type, identity_value)
);
```

邀请码：

```sql
CREATE TABLE lottery_invite_codes (
  id TEXT PRIMARY KEY,
  tenant_id TEXT NOT NULL,
  draw_id TEXT NOT NULL,
  code TEXT NOT NULL,
  max_uses INTEGER NOT NULL DEFAULT 1,
  used_count INTEGER NOT NULL DEFAULT 0,
  active INTEGER NOT NULL DEFAULT 1,
  created_at TEXT NOT NULL,
  UNIQUE(tenant_id, draw_id, code)
);
```

### 5.6 候选池与中奖记录

```sql
CREATE TABLE lottery_entries (
  id TEXT PRIMARY KEY,
  tenant_id TEXT NOT NULL,
  draw_id TEXT NOT NULL,
  identity_type TEXT NOT NULL DEFAULT 'email',
  identity_value TEXT NOT NULL,
  display_name TEXT NOT NULL DEFAULT '',
  invite_code_id TEXT DEFAULT '',
  joined_at TEXT NOT NULL,
  ip_hash TEXT NOT NULL DEFAULT '',
  user_agent_hash TEXT NOT NULL DEFAULT '',
  UNIQUE(tenant_id, draw_id, identity_type, identity_value)
);

CREATE INDEX idx_lottery_entries_identity
  ON lottery_entries(tenant_id, identity_type, identity_value);

CREATE TABLE lottery_winners (
  id TEXT PRIMARY KEY,
  tenant_id TEXT NOT NULL,
  draw_id TEXT NOT NULL,
  tier_id TEXT NOT NULL,
  entry_id TEXT NOT NULL,
  identity_type TEXT NOT NULL,
  identity_value TEXT NOT NULL,
  prize_code_id TEXT DEFAULT '',
  drawn_at TEXT NOT NULL,
  notification_status TEXT NOT NULL DEFAULT 'pending',
  notification_error TEXT NOT NULL DEFAULT '',
  UNIQUE(tenant_id, draw_id, entry_id),
  FOREIGN KEY (draw_id) REFERENCES lottery_draws(id),
  FOREIGN KEY (tier_id) REFERENCES lottery_prize_tiers(id),
  FOREIGN KEY (entry_id) REFERENCES lottery_entries(id),
  FOREIGN KEY (prize_code_id) REFERENCES prize_codes(id)
);
```

实施时还应在应用层继续校验这些关联记录的 `tenant_id` 一致。SQLite 外键只能保证记录存在，不能替代多租户隔离判断；跨租户写入必须在 service 层通过 `tenant_id` 过滤和事务约束兜住。

### 5.7 审计与导出

```sql
CREATE TABLE audit_logs (
  id TEXT PRIMARY KEY,
  tenant_id TEXT NOT NULL,
  actor_user_id TEXT NOT NULL,
  action TEXT NOT NULL,
  target_type TEXT NOT NULL,
  target_id TEXT NOT NULL,
  metadata_json TEXT NOT NULL DEFAULT '{}',
  created_at TEXT NOT NULL
);
```

所有高风险操作必须写审计：

- 发布活动
- 暂停/取消活动
- 开奖
- 重发中奖通知
- 导入/删除名单
- 导入/导出卡密
- 查看卡密明文

## 六、核心流程设计

### 6.1 创建活动

```text
选择活动模式 -> 配置身份规则 -> 选择奖品/奖项 -> 配置时间和开奖方式
-> 配置公开展示 -> 保存草稿 -> 发布 -> 分享链接/二维码
```

发布前校验：

- 活动标题存在。
- 起止时间合法。
- `scheduled` 必须有 `draw_at`。
- `winner_count` 大于 0。
- 卡密奖品可用码数量 >= 预计中奖数。
- `roster` 模式名单数量 > 0。
- `password` 模式必须设置密码 hash。
- `invite_code` 模式必须有可用邀请码。

### 6.2 参与活动

参与流程必须先校验资格，再插入候选池：

```text
读取活动 -> 检查活动状态/时间 -> 校验参与模式 -> 去重插入候选池 -> 返回参与成功
```

并发注意：

- `UNIQUE(tenant_id, draw_id, identity_type, identity_value)` 防止重复参与。
- 最大参与人数不能先 `count` 再 `insert`，应使用原子条件写入或计数器事务。
- 邀请码使用次数必须 CAS 更新：

```text
UPDATE invite_codes
SET used_count = used_count + 1
WHERE id = ? AND used_count < max_uses AND active = 1
```

### 6.3 开奖

状态机：

```text
draft -> open -> drawing -> drawn
             -> paused
             -> cancelled
```

开奖流程：

```text
CAS: open -> drawing
-> 读取候选池
-> 按奖项随机抽取
-> 对卡密奖品逐个锁码
-> 写入 winners
-> drawing -> drawn
-> 异步发送通知
```

关键原则：

- 开奖必须单事务完成核心结果。
- 邮件发送不能在事务内。
- 开奖失败必须记录 `failure_reason`，允许租户重试或平台排障。
- 随机算法必须可解释，至少记录 `draw_seed_hash` 或开奖摘要，便于争议处理。

### 6.4 公平性与争议处理

抽奖 SaaS 面向多个客户，后续一定会遇到“是否暗箱操作”的质疑。MVP 不需要做复杂公证链，但必须留下可解释证据。

建议在 `lottery_draws` 或独立 `lottery_draw_runs` 中记录：

| 字段 | 说明 |
|---|---|
| `draw_seed_hash` | 开奖前生成随机种子的 hash，先记录 hash，开奖后可展示原始 seed 或保留给审计 |
| `candidate_count` | 开奖时实际候选人数 |
| `winner_count_snapshot` | 开奖时实际中奖人数 |
| `algorithm_version` | 抽样算法版本，例如 `uniform_v1` |
| `drawn_by_user_id` | 手动开奖操作者，定时开奖可为空并标记为 system |
| `drawn_at` | 开奖完成时间 |

算法建议：

- P0 只做等概率不放回抽样。
- 候选池先按稳定字段排序，例如 `entry_id`，避免数据库返回顺序影响结果。
- 使用服务端安全随机源生成 seed，不使用前端传入随机数。
- 对外导出开奖报告：活动配置、候选人数、中奖名单、开奖时间、算法版本、操作者。

不建议 MVP 做：

- 区块链上链。
- 第三方公证接口。
- 用户自定义随机算法。
- 加权概率和即时抽奖。

原因是这些会显著增加解释成本、实现成本和争议面，不符合第一版“小而美”的目标。

### 6.5 发奖

卡密奖品：

```text
中奖记录 -> 锁定 prize_codes.available -> issued -> 通知中奖者
```

实物/线下奖品：

```text
中奖记录 -> 收集联系信息/地址 -> 租户人工处理 -> 标记 fulfilled
```

MVP 可以只做卡密和人工履约，但表结构要能扩展。

## 七、API 设计

### 7.1 租户后台 API

所有后台 API 均需登录，并从 session 中解析 `tenant_id`。

| API | 说明 |
|---|---|
| `POST /api/auth/register` | 注册用户并创建默认租户 |
| `POST /api/auth/login` | 登录 |
| `POST /api/auth/logout` | 注销当前 session |
| `GET /api/me` | 当前用户和租户 |
| `GET /api/admin/prizes` | 奖品列表 |
| `POST /api/admin/prizes` | 创建奖品 |
| `PATCH /api/admin/prizes/:id` | 编辑奖品 |
| `POST /api/admin/prizes/:id/codes/import` | 导入卡密 |
| `GET /api/admin/draws` | 活动列表 |
| `POST /api/admin/draws` | 创建活动 |
| `PATCH /api/admin/draws/:id` | 编辑活动 |
| `POST /api/admin/draws/:id/publish` | 发布活动 |
| `POST /api/admin/draws/:id/pause` | 暂停活动 |
| `POST /api/admin/draws/:id/draw` | 手动开奖 |
| `GET /api/admin/draws/:id/entries` | 候选池 |
| `GET /api/admin/draws/:id/winners` | 中奖名单 |
| `GET /api/admin/draws/:id/export` | 导出 CSV |

### 7.2 公开参与 API

| API | 说明 |
|---|---|
| `GET /api/public/draws/:slug` | 公开活动详情 |
| `POST /api/public/draws/:slug/join` | 参与抽奖 |
| `GET /api/public/draws/:slug/result` | 查看结果 |
| `POST /api/public/draws/:slug/access-code` | 邮箱验证码，可选 |
| `POST /api/public/draws/:slug/verify` | 验证邮箱/手机号，可选 |

### 7.3 平台 API

平台 API 必须和租户后台分开路由，例如：

```text
/api/platform/*
```

仅用于：

- 查看租户状态
- 封禁违规租户
- 查看系统错误
- 套餐和额度管理

平台 API 不应直接替客户编辑活动内容。

## 八、前端信息架构

### 8.1 租户后台

```text
/login
/register
/app
  /app/dashboard
  /app/draws
  /app/draws/new
  /app/draws/:id
  /app/prizes
  /app/prizes/:id
  /app/participants
  /app/settings
```

后台首页应该聚焦运营动作：

- 进行中的活动
- 到期待开奖
- 中奖通知失败
- 卡密库存不足
- 最近 7 天参与趋势

### 8.2 活动创建体验

建议使用分步表单：

1. 基础信息：标题、描述、封面。
2. 参与规则：公开/名单/密码/邀请码。
3. 奖品奖项：选择奖品、中奖人数。
4. 时间与开奖：开始、结束、手动/定时。
5. 展示与通知：参与人数、中奖名单、邮件模板。
6. 发布检查：展示所有风险提示。

发布前必须给明确提醒：

- 卡密不足。
- 名单为空。
- 邀请码没有可用次数。
- 已关闭中奖名单公开。
- 邮件服务未配置。

### 8.3 公开活动页

公开页应优先服务参与者：

- 活动名和奖品第一屏可见。
- 参与按钮清楚。
- 模式要求明确：需要密码、邀请码或名单内身份。
- 已参与后显示状态，不重复提交。
- 开奖后能清楚看到“是否中奖”。

不要把后台规则解释堆在公开页，公开页只保留参与者需要知道的信息。

## 九、从 cf-shop 抽取的最佳路径

### 9.1 可复用

| cf-shop 资产 | 是否复用 | 说明 |
|---|---:|---|
| `lottery-service` 开奖 CAS 思路 | 是 | 重写为 tenant-aware |
| `lottery_winner` 邮件模板 | 是 | 改为 SaaS 奖品模板 |
| CSV 导出工具 | 是 | 注意 PII 脱敏 |
| Admin 表格交互经验 | 是 | 但页面要重做信息架构 |
| Cron 到期开奖思路 | 是 | 增加租户额度和任务上限 |
| 卡密锁定经验 | 是 | 改为 `prize_codes` |

### 9.2 不应复用

| cf-shop 资产 | 原因 |
|---|---|
| 商品/订单/支付模型 | SaaS 抽奖不应依赖电商交易事实 |
| `ADMIN_TOKEN` 单后台 | 多租户必须用户名密码 + session |
| 单租户抽奖表 | 缺 `tenant_id`，不能直接迁移 |
| 商品作为奖品 | 概念不清，运营会混乱 |
| 用户端邮箱长期会话 | 可以借鉴体验，不要直接复用密钥命名空间 |

### 9.3 推荐抽取步骤

1. 新建项目，不在 cf-shop 内继续长分支。
2. 复制基础工程能力：Hono、Drizzle、测试框架、i18n、邮件模板结构。
3. 先建 SaaS 底座：tenant/user/session/member。
4. 再迁移抽奖领域：draw/prize/entry/winner。
5. 最后迁移 UI 经验：列表、详情、确认弹窗、导出。

## 十、性能与并发设计

### 10.1 查询原则

- 活动列表按 `tenant_id + status + created_at` 索引。
- 公开活动按 `public_slug` 查询。
- 候选池按 `tenant_id + draw_id` 分页，不一次性全量返回。
- 中奖名单按 `tenant_id + draw_id` 查询。
- 名单校验和邀请码校验必须索引命中。
- 不用 JSON 字段做名单、邀请码、卡密查询。

### 10.2 并发原则

必须避免：

- 先 count 再 insert 判断人数上限。
- 开奖多实例重复执行。
- 邀请码使用次数并发超发。
- 卡密重复发放。
- 邮件发送阻塞核心开奖事务。

建议：

- `draw` 状态 CAS。
- `entries` 唯一约束。
- `invite_codes` 条件更新。
- `prize_codes` 条件更新或事务内锁定。
- Cron 每次最多处理固定数量活动，例如 20 个。

### 10.3 大批量导入

名单和卡密导入必须分批：

- 前端限制文件大小。
- 服务端逐批解析，单批 500-1000 行。
- 去重后批量写入。
- 导入结果返回：成功、重复、格式错误。
- 不在一次 Worker 请求中处理超大 CSV。

## 十一、安全、隐私与合规

### 11.1 密码与 session

- 密码 hash 使用 Argon2id 或 bcrypt。
- session 支持撤销。
- 登录、注册、发送验证码要限流。
- 管理端所有写操作需要 CSRF 或同源 token 策略。

### 11.2 PII

参与者邮箱/手机号属于个人信息：

- 导出需要权限。
- 平台 Support 默认不可导出租户参与者数据。
- 公开中奖名单默认不展示完整邮箱。
- 邮件退订和隐私说明后续需要补齐。

### 11.3 反作弊

MVP 可以做轻量防刷：

- IP 限流。
- 邮箱/手机号验证码可选。
- Turnstile 可选。
- 同身份唯一参与。
- 邀请码次数限制。

不要一开始做复杂风控引擎。

## 十二、技术栈建议

| 层 | 推荐 | 说明 |
|---|---|---|
| 前端 | Vue 3 + Vite | 沿用项目经验 |
| 后端 | Cloudflare Workers + Hono | 轻量、部署简单 |
| ORM | Drizzle | 保持类型和迁移清晰 |
| 数据库 | D1 或 Turso/libSQL | MVP 均可；重点是 schema 和索引 |
| 邮件 | Resend / Cloudflare Email Service | 通过 provider 抽象层发送事务邮件 |
| 定时任务 | Cloudflare Cron | 到期开奖和失败邮件重试 |
| 密码 hash | Argon2id 或 bcrypt | 不自研 |
| 文件导入 | PapaParse/自有 CSV parser | 批量校验 |

多租户数据库选择：

- MVP：单库 + `tenant_id` 隔离，成本低、迁移简单。
- 中后期：大客户可拆库，先不要过度设计。

### 12.1 SaaS 套餐和额度

第一版可以不接支付，但必须先把套餐边界设计清楚，否则多租户上线后很容易被少数大活动拖垮。

Cloudflare + SQLite/D1 的 Free 计划适合验证产品和承载小活动，不适合无上限 SaaS 生产商业化。按 2026-07-31 官方文档核对，关键边界是：

| 资源 | Free 边界 | 对抽奖 SaaS 的影响 |
|---|---:|---|
| Workers 动态请求 | 100,000 次/天 | 公开页静态资源可走 Pages，参与、查询结果、后台 API 才进 Worker |
| Workers CPU | 10ms/次 | 请求内不能做大 CSV 解析、复杂统计、批量邮件、全量抽样排序 |
| D1 rows read | 5,000,000 行/天 | 所有公开页、候选池、中奖名单都必须索引命中并分页 |
| D1 rows written | 100,000 行/天 | 免费版不能承诺大促级参与写入；索引也会增加写入行数 |
| D1 总存储 | 5GB/account | 适合早期多租户试点；卡密、导入日志、审计日志要有保留策略 |
| D1 单库大小 | 10GB/database | Free 仍受账户总存储 5GB 限制；Paid 后大客户可按租户拆库 |
| D1 单次 Worker 读查询数 | Free 50 次/invocation | 后台详情页必须合并查询，避免一次打开页面打爆子查询数 |
| SQLite 写入特性 | 写入天然更适合短事务 | 不适合把大客户、大活动、所有租户无限堆在一个热点库里 |

因此免费计划下的真实 MVP 边界应更保守：

- Free 租户默认单活动最多 300-500 人。
- 单次名单或卡密导入最多 500 行，超过则提示升级或分批导入。
- Cron 每次最多处理 10-20 个到期活动，每个活动开奖候选池设硬上限。
- 后台统计默认展示近 7 天摘要，不做实时全局大盘。
- 邮件发送必须异步、限速、可重试，不能在开奖请求里同步批量发送。
- 活动页静态内容尽量缓存，动态接口只返回必要字段。
- 超过 MVP 边界的客户，最低应切到 Workers Paid，而不是继续压榨 Free 计划。

建议先做“配置存在、收费不开启”的额度模型：

| 额度项 | Free | Pro | 用途 |
|---|---:|---:|---|
| 活跃活动数 | 3 | 30 | 防止租户无限创建公开活动 |
| 单活动参与人数 | 500 | 5000 | 控制候选池规模；更大活动单独评估 |
| 单次名单导入 | 500 | 5000 | 控制 Worker 请求耗时和 D1 写入行数 |
| 月邮件通知数 | 500 | 30000 | 控制邮件成本和发送失败重试压力 |
| 卡密总库存 | 1000 | 50000 | 控制存储和导出风险 |
| 成员数 | 2 | 20 | 支持小团队协作 |

实现原则：

- 套餐只限制资源上限，不影响已经完成的开奖记录。
- 超限时阻止新增或发布，不在进行中活动里突然中断参与。
- 后台首页必须展示接近额度的提醒，例如“邮件额度剩余不足”。
- 平台 Owner 可以手动调整租户额度，所有调整写入审计。

MVP 可以先用表字段或配置常量表达额度，不必立即接 Stripe、Creem、余额或发票系统。

### 12.2 免费计划下的架构取舍

为了符合 Cloudflare + SQLite/D1 Free 计划，第一版建议采用：

```text
Cloudflare Pages 静态前端
-> Workers/Hono API
-> 单 D1 数据库 + tenant_id 隔离
-> Cron 有界扫描
-> 邮件 provider 异步重试
```

暂不建议：

- 每个租户一个 D1 数据库：Free 只有 10 个数据库，不适合早期多租户获客；Paid 后可为大客户拆库。
- Workers for Platforms：适合客户自定义代码，不适合第一版抽奖 SaaS，成本和复杂度都偏高。
- 大批量实时排行榜：会显著增加读写和缓存失效复杂度。
- 抽奖参与强依赖登录账号：会降低转化，公开页应允许低摩擦参与。

必须做的工程护栏：

- 所有列表接口带 `limit`，默认 20-50。
- 所有公开查询必须有 `public_slug` 或 `tenant_id + draw_id` 索引。
- 参与接口只做资格校验和一次写入，不返回大对象。
- 开奖接口不做邮件发送，只写中奖记录和通知任务。
- 统计接口优先读聚合快照，必要时后台异步刷新。
- 删除或归档历史日志、失败邮件、过期卡密导入批次，避免长期膨胀。

## 十三、市场、引流与变现设计

### 13.1 是否有应用场景

有应用场景，但不能定位成“通用抽奖系统”。通用抽奖工具市场已经拥挤，真正有价值的是围绕“引流、留资、发放权益、活动复盘”的轻量工具。

最适合切入的客户：

| 客户 | 高频痛点 | 成交理由 |
|---|---|---|
| 社群运营 | 群活动难留资、难发奖、难复盘 | 抽奖链接天然促进参与和邮箱/手机号收集 |
| 课程/知识付费 | 学员福利、资料码、内测资格发放繁琐 | 卡密发放和名单抽奖刚需明确 |
| 小商家/门店 | 线下扫码活动需要低成本工具 | 二维码参与 + 中奖核销可直接带动到店 |
| 自媒体/博主 | 粉丝福利抽奖需要公平和导出 | 公平报告、中奖名单、邮件通知降低信任成本 |
| B2B 工具/开发者产品 | 内测资格、优惠码、活动码发放 | 与现有卡密/券码体系匹配度高 |

不建议优先做的客户：

- 大型电商秒杀和百万级活动：并发、风控、合规成本高。
- 博彩、现金抽奖、付费抽奖：法律和支付风险高。
- 强监管行业抽奖：需要法务和公证能力，不适合 MVP。

### 13.2 最优产品定位

建议定位为：

**“面向社群、课程、门店和独立商家的轻量引流抽奖工具：3 分钟生成活动页，收集潜客，自动公平开奖，自动发放券码/卡密。”**

这个定位比“抽奖 SaaS”更容易变现，因为客户购买的不是抽奖算法，而是：

- 获客线索。
- 参与转化。
- 奖品自动发放。
- 公平可信的活动结果。
- 运营复盘数据。

### 13.3 变现路径

第一阶段不要先做复杂订阅系统，先用“免费试用 + 人工开通 Pro”的低成本方式验证付费意愿。

| 阶段 | 收费方式 | 适合原因 |
|---|---|---|
| MVP | 免费版 + 人工 Pro 开通 | 不接支付，最快验证真实客户 |
| 早期 | 月付 Pro | 按额度和品牌能力收费，容易理解 |
| 成熟 | 活动包/邮件包/白标包 | 与成本和客户价值直接绑定 |

建议套餐：

| 套餐 | 目标客户 | 核心权益 |
|---|---|---|
| Free | 试用、个人、小活动 | 3 个活动、500 人/活动、平台品牌 |
| Pro | 社群/课程/门店 | 30 个活动、5000 人/活动、自定义品牌、导出、邮件模板 |
| Business | 高价值客户 | 更高额度、独立域名、专属发件域、人工支持、可选独立库 |

真正能收费的功能：

- 去平台品牌。
- 自定义活动页品牌、Logo、颜色、域名。
- 导出完整线索。
- 邮件模板和发件域。
- 更高参与人数和导入额度。
- Webhook/表单系统集成。
- 公平开奖报告。

不建议收费的功能：

- 基础开奖能力。
- 基础公开参与。
- 基础中奖名单。

这些应该作为免费获客入口。

### 13.4 引流闭环

每个免费活动页都应该成为产品自身的增长入口，但不能影响租户体验。

建议：

- Free 活动页底部保留轻量品牌入口：“由 X 提供抽奖工具”。
- 中奖结果页引导运营者创建自己的活动。
- 导出 CSV 时附带活动复盘摘要，增强工具价值感。
- 后台首页展示“复制活动链接 / 下载二维码 / 查看线索 / 重发通知”四个核心动作。
- 公开页参与流程只收一个必要身份字段，降低移动端阻力。

不要做：

- 弹窗强推注册。
- 参与者必须登录平台账号。
- 在客户活动页大面积展示平台广告。
- 把抽奖页做成复杂营销落地页编辑器。

### 13.5 最小可卖版本

最小可卖版本不是功能最多，而是闭环最短：

```text
租户注册 -> 创建奖品 -> 创建活动 -> 分享二维码
-> 参与者提交邮箱/手机号 -> 系统开奖 -> 自动通知/发码
-> 租户导出线索和中奖报告
```

只要这个闭环稳定，就可以开始获客；邀请码、审核、Webhook、自定义域名都可以后置。

### 13.6 风险判断

| 风险 | 判断 | 处理 |
|---|---|---|
| 市场同质化 | 高 | 不卖“抽奖”，卖“引流留资 + 自动发奖 + 公平报告” |
| 免费计划超限 | 中 | Free 套餐强限制，Pro 迁移 Workers Paid |
| 合规风险 | 中 | 不做现金、博彩、付费抽奖，补充使用条款 |
| 邮件送达 | 中 | 支持重试和第三方 provider，重要客户配置专属发件域 |
| 大活动并发 | 中高 | 单活动人数上限、Cron 有界、候选池分页，大客户单独评估 |
| 运营误操作 | 中 | 发布检查、危险操作确认、审计日志 |

最终建议：

1. 可以做，但必须以引流变现工具切入，不要做泛抽奖平台。
2. Cloudflare + D1 Free 只适合 MVP 和小规模获客，商业化客户应准备 Workers Paid。
3. 第一版必须把额度、索引、分页、异步通知和审计做好，否则免费计划很容易被单个活动打爆。
4. 变现优先卖品牌、额度、导出、邮件、自定义域名和公平报告，不要卖复杂抽奖玩法。

## 十四、实施路线图

### Phase 0：评审和原型

- 固定术语：租户、活动、奖品、参与者、中奖记录。
- 确认 MVP 模式：公开、名单、密码。
- 确认不做支付和商城。
- 做 1 个后台流程原型和 1 个公开页原型。

### Phase 0.5：抽取验收清单

从 `cf-shop` 抽取时，必须逐项确认，不能按文件夹粗暴复制：

| 检查项 | 验收标准 |
|---|---|
| 领域拆分 | 抽奖核心代码不再 import 商品、订单、支付、余额、storefront 服务 |
| 租户隔离 | 所有后台列表、详情、写操作都有 `tenant_id` 过滤 |
| 公开访问 | 公开页只通过 `public_slug` 进入，不暴露后台 ID |
| 发奖链路 | 卡密奖品使用 `prize_codes`，不依赖 cf-shop 的 cards/products |
| 通知链路 | 中奖通知可失败重试，失败不回滚开奖结果 |
| 审计闭环 | 发布、开奖、导入、导出、查看明文均有 audit log |
| 测试闭环 | 至少覆盖跨租户隔离、重复参与、人数上限、并发开奖、卡密不重复发放 |

只要上述任一项不满足，就不能宣称“抽取完成”。

### Phase 1：SaaS 底座

- users / tenants / tenant_members / sessions。
- 注册、登录、退出。
- 租户上下文中间件。
- 审计日志。

验收：

- 用户 A 看不到用户 B 的活动。
- 所有后台 API 无 `tenant_id` 漏过滤。

### Phase 2：奖品和码池

- 奖品 CRUD。
- 卡密导入、列表、脱敏展示。
- 可用码数量统计。

验收：

- 卡密不会跨租户。
- 卡密不会重复发放。

### Phase 3：活动和参与

- 活动 CRUD。
- 公开/名单/密码三种模式。
- 公开活动页。
- 候选池去重。

验收：

- 名单外不能参与。
- 重复参与不会新增候选。
- 活动过期不能参与。

### Phase 4：开奖和通知

- 手动开奖。
- 定时开奖。
- 中奖邮件。
- 重发失败邮件。
- 导出中奖名单。

验收：

- 并发点击开奖不会重复中奖。
- 卡密不会重复发放。
- 邮件失败不回滚开奖结果。

### Phase 5：SaaS 完整化

- 邀请码模式。
- 成员管理。
- 套餐额度。
- 品牌自定义。
- Webhook。

## 十五、MVP 不做清单

为避免过度设计，第一版明确不做：

- 支付参与。
- 商城售卖。
- 余额、优惠券、返佣。
- 复杂 CRM。
- 外部 API 资格校验。
- 即时抽奖。
- 加权概率。
- 多语言模板市场。
- 多租户分库。

这些可以放入路线图，但不能阻塞 MVP。

## 十六、对原方案的关键修正

原方案方向正确，但需要修正以下点：

1. **“没有超级管理员”表述不准确**
   - SaaS 需要平台运维角色，但它不应代运营租户活动。

2. **名单和邀请码不能用 JSON 存储**
   - JSON 适合配置，不适合高频校验和大批量导入。

3. **缺少租户成员和角色模型**
   - 多租户 SaaS 不能只有 `users`。

4. **奖品模型不能等同 cf-shop 商品**
   - 奖品是活动履约资源，不是交易商品。

5. **缺少审计和隐私边界**
   - 抽奖涉及邮箱、手机号、中奖名单、卡密明文，必须有权限和审计。

6. **缺少性能边界**
   - 公开页和活动列表不能做全量扫描。
   - 导入不能一次性吃完整 CSV。
   - Cron 必须有界。

7. **模式设计需要分层**
   - “随意人员/限定人员”太粗。
   - 应拆成参与资格、开奖触发、奖品履约、展示策略四层配置。

## 十七、最终建议

建议采用“小而美 SaaS”的路线：

1. 第一版做多租户底座 + 公开/名单/密码抽奖 + 卡密/人工奖品。
2. 不做支付、不做商城、不做复杂营销平台。
3. 数据模型从一开始支持多租户、多奖项、名单表、邀请码表。
4. 复用 cf-shop 的开奖和发奖经验，但重写与租户、权限、奖品相关的部分。
5. 所有活动都必须由租户自助创建、发布、开奖、导出，平台只负责系统运维和风控。

最稳的产品表达是：

**“给每个组织一个自己的抽奖后台，几分钟创建活动，分享链接即可参与，系统自动公平开奖并发奖。”**
