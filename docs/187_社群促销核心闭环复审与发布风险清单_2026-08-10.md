# 社群促销核心闭环复审与发布风险清单

> 日期：2026-08-10
> 范围：QQ 群、Telegram 群、签到、抽奖、发卡、导流、成交/秒杀、平台投递、VPS maintenance、admin 运营配置
> 复审原则：只记录代码中已验证的事实；不确定项标为风险或待办，不当成已完成能力。

## 1. 本轮新增修复

1. **Telegram webhook 鉴权升级**：`platform-telegram.ts` 优先读取官方 `X-Telegram-Bot-Api-Secret-Token` 头，`?secret=` 只保留旧 webhook 兼容。原因是 URL secret 会进入代理/访问日志；Telegram Bot API 官方 `setWebhook.secret_token` 会以该 header 回调。
2. **平台投递 processing 恢复修复**：`delivery.ts` 统一使用 ISO 时间计算 `staleProcessingCutoff`。修复前用 SQLite `datetime('now', '-10 minutes')` 与 ISO `updatedAt` 字符串比较，超时 `processing` 记录实际不会被重新领取，导致维护进程崩溃后消息永久卡住。
3. **平台投递私聊闭环测试补强**：新增测试证明 QQ 私聊队列最终调用 `/send_private_msg`，并传递 `user_id` 与 `group_id`，避免“入队成功但发错目标”。
4. **admin Telegram 测试发送闭环**：后台测试消息从 QQ-only `baseUrl` 门禁改为平台感知门禁：QQ 校验 `baseUrl`，Telegram 校验 `botToken`。修复前 Telegram 群能创建但无法在后台完成“配置 -> 测试发送 -> 上线”。
5. **裂变奖励审计一致性**：`grantViralSpinsToSharer` 检查乐观更新 `rowsAffected`。并发下奖励余额未写入时不再写 `spins_log`，避免“流水显示加次、余额未加”的审计错账。

## 3. 仍未完成或不应声称完成的内容

1. **Telegram botToken 加密存储仍未完成**：当前仍在 `adapterConfigJson` 中存 botToken。发布前至少确认生产库/接口是否会向前端明文回显；后续应迁移到租户级凭据加密存储，并列表/详情脱敏。
2. **QQ 私聊仍走 webhook 热路径同步发送**：Telegram 已异步入队，QQ 仍同步调用 NapCat。若 NapCat 不可达，QQ webhook 仍可能被拖慢；建议后续把 QQ 私聊也改为 `enqueuePrivatePlatformMessage`。
3. **邮件通知仍没有持久化队列**：中奖邮件 fire-and-forget，不回滚开奖结果是正确的，但进程崩溃会丢通知。平台投递已有队列，邮件可复用类似 delivery 表。
4. **活动级运营参数不足**：缺活动级参与频率/IP 策略、开奖前 N 分钟锁定参与、转盘概率可视化、统一导出入口、全局公告/站内信、配置版本回滚。
5. **大表效率隐患未全部修复**：平台投递、webhook、rate_limit、spins 等清理/扫描路径仍需要按 `(status,next_retry_at,created_at)`、`(tenant,draw,identity)` 等补索引方案评估。

## 5. 后续优化建议（不阻塞本轮发布）

1. 把 QQ 私聊统一改为平台投递队列，做到 QQ/Telegram 出站行为一致。
2. 给 `platform_deliveries` / `webhook_deliveries` 增加面向 maintenance 的状态+重试时间索引。
3. 将 botToken、NapCat token 等凭据迁移到加密存储，管理端只显示脱敏值。
4. 给 admin 系统配置增加“前端可见性审查”：后端生效但前端不可配置、前端 stub 但后端无实现的项必须列为发布阻断或显式隐藏。
5. 为 OTP verify/consume 并发窗口做事务化设计，避免同一个邮箱验证码在极端并发下被重复用于不同幂等键。
