# 社群促销核心闭环复审与发布风险清单

> 日期：2026-08-10
> 范围：QQ 群、Telegram 群、签到、抽奖、发卡、导流、成交/秒杀、平台投递、VPS maintenance、admin 运营配置
> 复审原则：只记录代码中已验证的事实；不确定项标为风险或待办，不当成已完成能力。

## 1. 本轮新增修复

1. **Telegram webhook 鉴权升级**：`platform-telegram.ts` 优先读取官方 `X-Telegram-Bot-Api-Secret-Token` 头，`?secret=` 只保留旧 webhook 兼容。原因是 URL secret 会进入代理/访问日志；Telegram Bot API 官方 `setWebhook.secret_token` 会以该 header 回调。
2. **平台投递 processing 恢复修复**：`delivery.ts` 统一使用 ISO 时间计算 `staleProcessingCutoff`。修复前用 SQLite `datetime('now', '-10 minutes')` 与 ISO `updatedAt` 字符串比较，超时 `processing` 记录实际不会被重新领取，导致维护进程崩溃后消息永久卡住。
3. **平台投递私聊闭环测试补强**：新增测试证明 QQ 私聊队列最终调用 `/send_private_msg`，并传递 `user_id` 与 `group_id`，避免“入队成功但发错目标”。
4. **admin Telegram 测试发送闭环**：后台测试消息从 QQ-only `baseUrl` 门禁改为平台感知门禁：QQ 校验 `baseUrl`，Telegram 校验 `botToken`。修复前 Telegram 群能创建但无法在后台完成“配置 -> 测试发送 -> 上线”。
5. **裂变奖励审计一致性**：`grantViralSpinsToSharer` 检查乐观更新 `rowsAffected`。并发下奖励余额未写入时不再写 `spins_log`，避免“流水显示加次、余额未加”的审计错账。

## 1.1 本轮继续实施（2026-08-10 追加）

1. **平台凭据加密/脱敏闭环**：新增 `services/platform/adapter-config.ts`，Telegram `botToken` 与 QQ/NapCat `token` 新保存时写入 cf-core v2 密文；管理端列表/详情仅返回 `••••••••` 占位符；运行时投递和后台测试发送按需解密。
2. **QQ 私聊异步化**：`platform-qq.ts` 不再在 webhook 热路径同步调用 NapCat `/send_private_msg`，改为写入 `platform_deliveries`，由 maintenance 异步发送和重试，与 Telegram 出站语义一致。
3. **维护热点索引**：新增 `migrations/0054_operational_hot_path_indexes.sql`，覆盖 `platform_deliveries`、`webhook_deliveries`、`rate_limit_log`、`lottery_spins`、`lottery_entries` 的维护/公开查询热点索引。
4. **spin OTP 并发窗口收敛**：instant spin 先校验幂等键，再 CAS 核销 OTP，只有成功领取验证码的请求能进入抽奖事务，避免同一验证码并发双抽。
5. **QQ/Telegram 凭据运行时测试**：补充测试证明密文 QQ token 会转为 Authorization 头，密文 Telegram botToken 会用于 Bot API URL，后台不回显真实凭据。
6. **社群套餐配额运营闭环**：Free/Pro/Team 群绑定数与每群成员数接入 `system_config` 和后台“套餐额度”分区，运营可动态调整，后端创建绑定和命令运行时读取同一套动态 limits。
7. **群绑定创建并发超发修复**：后台创建群绑定时，把重复 target 检查、套餐群数 COUNT、`platform_targets` INSERT 放进同一个写事务，并补并发 API 回归测试，避免两个不同群同时创建穿透套餐上限。

## 1.2 发布前一步到位调整（2026-08-10 追加）

1. **平台凭据取消明文兼容**：项目仍在测试阶段，不保留历史明文 `botToken/token` 运行分支。运行时发现敏感字段不是 cf-core v2 密文会直接失败，并提示重新保存配置。
2. **统一邮件投递队列**：新增 `email_deliveries` 表，中奖通知、支付成交发卡、开奖提醒、未中奖安慰券邮件均先入队，再由 maintenance/管理端重发路径处理。验证码邮件保持同步，因为它是用户当前请求的即时凭证。
3. **邮件队列幂等与重试**：`tenantId + sourceType + sourceId` 唯一，避免 cron 窗口重叠或重发按钮重复发同一业务邮件；pending/processing 超时由发送器重新领取。

## 1.3 运营可见性继续补齐（2026-08-10 追加）

1. **邮件投递后台可见**：新增平台运营接口 `/api/platform/email-deliveries`，支持按租户、状态、模板筛选，返回收件人、来源、尝试次数、错误和投递时间。
2. **邮件投递手动重试闭环**：新增 `/api/platform/email-deliveries/:id/retry`，owner/operator 可把 failed/pending/processing 记录恢复为 pending 并立即交给统一邮件发送器；sent 记录禁止重复重试。
3. **平台权限边界**：support 角色读取邮件投递时必须指定 tenantId，不传返回空列表；重试会真实调用邮件网关，只有 owner/operator 可执行并写平台审计。
4. **前端运营页**：新增 `/platform/email-deliveries` 页面和菜单，支持筛选、批量选择、单条/批量重试、错误查看。
5. **系统配置前端可见性补齐**：`system-config-definitions.json` 中所有 group 均已被 `SYSTEM_CONFIG_SECTIONS` 承接，新增活动设置、秒杀/支付、邮件通知分区，避免后端配置生效但运营页面不可配置。

## 1.4 活动级运营参数继续补齐（2026-08-10 追加）

1. **开奖前锁定参与**：新增 `activityConfig.operational.lockJoinBeforeDrawMinutes` 运行时门禁；`joinDraw` 服务层统一拦截，QQ/Telegram/公开页所有新增参与入口都不能绕过。
2. **活动级参与频率/IP 策略**：新增 `activityConfig.operational.joinIpLimitPerMinute`、`joinIdentityLimitPerMinute`、`accessCodeIdentityLimitPerMinute`，公开发码、verify-join、快捷 join 在全局限流外再执行活动级覆盖。
3. **发布前校验**：`publish-check` 会阻断超范围或非整数的活动级运营参数；运行时仍 fail-soft 回落默认，避免坏配置导致线上入口崩溃。
4. **默认安全策略**：未配置活动级参数时继续使用平台全局 `rate_limit_join_per_minute` / `rate_limit_access_code`。

## 2. 核心闭环判定

| 链路 | 当前状态 | 证据 |
|---|---|---|
| QQ 群签到 -> 参与记录 -> 奖励次数 | 基本闭环 | `platform-qq.test.ts`、`commands.test.ts`、`lottery-service.test.ts` 覆盖签到、连续签到、奖励配置；私聊出站已异步入队 |
| Telegram 群签到/抽奖/我的奖品 | 基本闭环 | `platform-telegram.test.ts` 覆盖 header/query 鉴权、签到、分享、抽奖、回放、我的奖品 |
| 即时抽奖 -> 扣次 -> 原子锁码 -> 中奖记录 | 闭环 | `spin-execution.ts` CAS 扣次、卡密原子锁；全量测试覆盖 409 次数耗尽与幂等回放 |
| 延迟开奖 -> 中奖记录 -> 邮件/webhook/平台通知 | 闭环加强 | `draw-execution.ts` status CAS + winners/drawn 同事务；邮件、webhook、平台消息均异步入队 |
| 我的卡密 -> 一次性 Web 链接 -> drawId 范围读取 | 闭环 | `public-access.test.ts` 覆盖旧空 drawId 令牌拒绝、跨平台身份 OR、跨租户隔离 |
| 导流/裂变 -> 分享记录 -> 邀请奖励 | 基本闭环 | reward 24h 限流清理已锁测试；并发审计错账已修 |
| 秒杀/成交 -> 订单/占位/付款发码 | 闭环加强 | EXPIRED 重抢计数虚高已修；支付成功发卡邮件先写 `email_deliveries`，维护任务可补发 |
| VPS maintenance -> 到期开奖/webhook/平台投递/邮件投递/清理 | 闭环加强 | 已加入 systemd service/timer；processing 超时恢复测试已补；平台密文凭据由 maintenance 解密发送；邮件队列由 maintenance 补发 |
| admin 平台目标配置 -> 测试发送 -> 审计 | QQ/Telegram 均闭环 | `admin-lottery-platform.test.ts` 覆盖 QQ 与 Telegram 测试发送、缺配置不发外部请求、投递审计、凭据脱敏 |
| platform 邮件投递运营 -> 筛选 -> 重试 -> 审计 | 闭环 | `platform-rbac.test.ts` 覆盖 owner/operator 重试、support 最小权限、审计写入；前端 `/platform/email-deliveries` 已接入 |
| platform 系统配置 -> 后端定义 -> 前端分区 | 闭环 | 机器核对 `system-config-definitions.json` 所有 group 均存在于 `SYSTEM_CONFIG_SECTIONS`；前端类型检查通过 |
| 活动级运营门禁 -> 发布校验 -> 公开参与/社群参与 | 部分闭环 | `p0-flow.test.ts` 覆盖开奖前锁定参与、活动级身份限流；`publish-check-service.test.ts` 覆盖非法参数发布阻断；锁定逻辑在 `joinDraw` 服务层统一生效 |
