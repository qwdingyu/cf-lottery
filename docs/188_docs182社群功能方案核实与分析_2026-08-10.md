## 2. 发现的 3 处文档表述偏差（非代码 bug）

1. **§2.1 "POST/PUT 拦增量" 不准确**：实际只有 POST 创建调用 `canTenantCreatePlatformTarget`，**PUT 分支未调用**。这是正确的设计（PUT 更新已有 target 不增加群数）。**✅ 本轮已修正代码注释为“POST 创建校验”。**

2. **`community_members.identity_value` 语义与 schema 注释不符**：schema 注释原写"平台用户 ID（QQ号），兜底"，但实现 `enforceGroupMemberCap` 写入的是 `identityValue: input.userId`（是 users.id UUID，非 QQ 号）。字段实际是"userId 冗余存储"，非"平台号兜底"。**✅ 本轮已修正 schema 注释，避免后续误用。**

3. **docs/182 §2.2 称 enforceGroupMemberCap "防并发超限"**：实现依赖 `withDbTransaction`（BEGIN IMMEDIATE）的单写者串行化 + `uq_community_members_target_user` 唯一索引，**并发下确实安全**，但代码本身是"SELECT COUNT + INSERT"两步，未用单条原子 INSERT...SELECT。当前因 BEGIN IMMEDIATE 串行化而无竞态，但脆弱（若未来换成 deferred/远程 hrana 惰性 BEGIN 则有窗口，同 F2 风险模式）。建议用单条条件 INSERT 收敛。

## 4. 值得复评的设计问题（按影响排序）

### P1（中）社群配额不走动态 system_config，与活动配额不一致
- `getTenantCommunityPolicy`（`community-policy.ts:47-62`）用 `getTenantPlanName` + `getTenantPlanLimits`（`plan.ts:44`，**纯静态**），而活动配额 `getTenantUsage`（`plan.ts:88-120`）会读 `loadDynamicPlanLimits`（system_config 动态覆盖）。
- 后果：平台运营者在 `/platform/config` 调整套餐额度时，只会影响活动配额，**群数/群人数上限始终用硬编码 PLAN_LIMITS**，两套配额来源不一致，L3 无法动态调整社群容量。
- 建议：`getTenantCommunityPolicy` 改为调用 `getTenantUsage` 拿动态 limits，或在 PLAN_LIMITS_CONFIG_KEYS 增加社群配额 key（注意 plan config 的 `max_platform_targets/max_group_members` 尚未暴露给 /platform/config）。

### P2（中）`enforceGroupMemberCap` 对只读命令也计数，存在"过度计数"风险
- 调用点：`commands.ts:180` 在**所有启用命令**分发前统一执行，包括 `/排行榜`、`/我的卡密`、`/我的奖品` 等**只读查询**命令。
- docs/180 §3.3 语义是"服务过的成员"（参与活动），但实现是"发过任一启用命令的用户"都会被写入 `community_members`。
- 后果：一个只在群里查排行榜/看奖品、从不参与的用户也占名额，`maxGroupMembers` 被查询者消耗，而非真实的活跃参与成员。群人数上限的实际约束力被削弱/偏移。
- 建议：只在"产生参与/服务副作用"的命令（checkin 签到、spin 抽奖、share 分享、bind 绑定）触发 capCheck，只读命令（leaderboard、my_prize、card_code）跳过；或调整 docs 语义为"使用过群服务的用户"。

### P3（中）`enforceGroupMemberCap` 写入成员在命令 handler 执行**之前**，失败命令也被计入
- capCheck 写入 member 时，handler 还未执行。若 handler 随后因活动未开启/抽奖失败等原因返回失败，用户已计入 member。
- 影响：失败尝试也消耗名额（与 P2 同类，都是"计数与真实服务脱节"）。
- 建议：member 写入推迟到 handler 成功后，或接受"尝试即算服务"并更新 docs 语义。

### P4（低）`canTenantCreatePlatformTarget` 的群数 COUNT 无并发保护
- **✅ 本轮已修复**：`admin-lottery-platform.ts` 创建群绑定时，把重复 target 检查、套餐群数 COUNT、`platform_targets` INSERT 放进同一个 `withDbTransaction` 写事务。
- 补充回归测试：`admin-lottery-platform.test.ts` 并发创建两个不同群，验证 free 套餐最终只落库 1 个。

## 5. 确认安全 / 设计合理的点

- **群人数上限的运行时强制是硬配额**：BEGIN IMMEDIATE 串行化 + 唯一索引，并发超限被阻（`community-policy.ts:124-170`），测试 `community-policy.test.ts:206` 第 201 人边界验证 ✅。
- **存量成员放行（grandfathering）**：`community-policy.ts:145-147` 先查存量，命中即 return，不伤老用户 ✅。
- **userId 为空降级不阻断**：`community-policy.ts:128-129` + `inbound.ts:60-71`，provision 失败仍可用，符合"僵尸不卡死"原则 ✅。
- **PATCH 防灾难红线正确**：`platform.ts:410-431` 遍历该租户所有群，拒绝设上限低于当前成员数 ✅。
- **覆写"部分覆盖"**：`getTenantCommunityPolicy` 覆写时未覆盖字段用套餐默认，符合 docs/180 §2.3 ✅。
- **DELETE 恢复默认**：`platform.ts:486-521` 删除覆写 + 审计 ✅。
- **`maxGroupMembers` 设计堵免费容量漏洞**：按群绑定累计去重、跨活动生效，正确解决 `maxParticipantsPerActivity` 可被切换活动绕过的漏洞（docs/180 §2 论证充分）✅。

## 6. 最优方案建议

**照单全收的采纳**（无需改动，属正确实现）：表结构、迁移、套餐基线、PATCH/DELETE、存量放行、防灾难红线。

**建议跟进**（按 ROI 排序）：
1. **P1（社群配额接入动态配置）**：让 `getTenantCommunityPolicy` 复用 `getTenantUsage` 的动态 limits，统一配额来源。ROI 高——L3 运营是社群变现核心，无法动态调额度会卡运营。**✅ 已实施（见下）**
2. **P3（member 写入时机）**：把 `community_members` 写入从"命令前"推迟到"handler 成功后"，避免失败尝试占用名额。改动小、语义更准。**未实施（待确认）**
3. **P2（只读命令不计入）**：调节 capCheck 触发范围，只对产生服务副作用的命令计数。需产品确认"成员"语义。**未实施（待确认）**
4. **P4（群数 COUNT 加事务）**：`canTenantCreatePlatformTarget` 与实际 INSERT 在创建路由内同事务执行，堵并发穿透。**✅ 已实施**
5. **文档修正**：docs/182 §2.1 改"POST 创建校验"；修正 `identity_value` 注释语义。**✅ 已实施**

## 7. 踩坑记录

- **对称写死 vs 动态配置不一致**：同类配额（活动 vs 社群）若一个读 system_config、一个读硬编码，会产生"改了配置不生效"的隐性断点，运营排障困难。规则：同类配额统一配置来源。
- **运行时门禁的计数时机**：门禁在副作用前计数（先计后做）会比"实际服务"偏宽，导致资源被占用但不产生价值。设计门禁时应明确计数到哪个语义粒度（真实服务 vs 请求尝试）。
