# P0-1 邀请奖励出口多样化 — 落地实施方案

> 文档版本：1.0.0
> 最后更新：2026-08-20
> 基于：cf-lottery（多租户活动引擎）× @usethink/incentive-engine v3.4.10（激励计算引擎）
> 核心原则：**最小侵入，不破坏现有状态机**

---

## 一、现状全景（必须先理解透彻再动手）

### 1.1 cf-lottery 邀请奖励调用链路（当前完整路径）

```
joinDraw()
  └── recordAttributedJoin()          ← 归因（自邀请拦截 + joinedCount +1）
      └── maybeTriggerReward()        ← 归因成功后触发奖励
          ├── [1] grantViralSpinsToSharer()     ← instant 单次邀请 +spins
          ├── [2] processReferralMilestoneRewards()  ← 里程碑 bonus_spin
          └── [3] triggerRewardEarned()          ← reward_earned 事件 + webhook
```

**所有奖励都只支持 `bonus_spin`（额外抽奖次数），且只对 `resultMode=instant` 生效。**

### 1.2 三个奖励路径的职责与数据流

| 路径 | 触发条件 | 配置来源 | 幂等机制 | 奖励出口 |
|------|---------|---------|---------|---------|
| [1] grantViralSpinsToSharer | 每次归因成功 + instant | `promotionConfig.viral.extraSpinsPerInvite` | `spinsTotalGranted` CAS 乐观锁（行级） | `lotteryEntries.spinsLeft +1` |
| [2] processReferralMilestoneRewards | 每次归因成功 + instant + 有 shareRecordId | `promotionConfig.referralRewards` | `shareRecords.rewardMilestonesGranted` JSON 数组（CAS 行级） | `lotteryEntries.spinsLeft +n` |
| [3] triggerRewardEarned | 每次归因成功 | `activityConfig.reward` | `checkDbRateLimit` 原子 INSERT | `activityEvents` 事件 + webhook 通知中转站 |

### 1.3 cf-lottery 已有的奖励出口基础设施

| 奖励出口 | 基础设施 | 当前使用场景 | 可复用性 |
|---------|---------|-------------|---------|
| **bonus_spin** | `lotteryEntries.spinsLeft/spinsTotalGranted/spinsViralEarned` | 裂变加次、里程碑、排行榜 | ✅ 现有路径 |
| **bonus_coupon** | `couponCodes` 表（status: available/issued/redeemed/expired/revoked） | `grantLoserRewards` 未中奖发券 | ✅ 现成可用 |
| **bonus_entry** | `lotteryViralExtraEntries`（无此表）/ `viral-weight.computeViralDrawWeight` | 裂变加权（纯计算，不写 entry） | ❌ 需新建 |

### 1.4 incentive-engine 的能力边界（只使用核心计算）

```
distributeByDefs({ event, rewardDefs, ... })
  └── 纯函数，输入/输出都是普通对象
  └── 不依赖 joi/sequelize（cf-lottery 只需安装 decimal.js）
  └── FIXED 类型：固定金额奖励，与 eventValue 无关
  └── CUSTOM 类型：固定金额 + 动态取数（amountFrom）
  └── conditions：COMPARE/AND/OR/NOT 条件树
  └── 输出：records [{ nodeId, rewardId, rewardType, amount, snapshot }]
```

## 二、设计方案（核心决策）

### 2.1 核心策略：保持现有路径不动，新增扩展层

```
⚠️ 铁律：现有路径 [1][2][3] 一行代码不改。
```

**现状配置**（不动）：
```json
{
  "referralRewards": [
    { "requireCount": 1, "rewardType": "bonus_spin", "rewardValue": 2 },
    { "requireCount": 3, "rewardType": "bonus_spin", "rewardValue": 5 }
  ]
}
```

**新增配置**（平行存在）：
```json
{
  "referralRewardDefs": [
    {
      "rewardId": "milestone_1",
      "type": "FIXED",
      "target": "SOURCE",
      "fixedAmount": "2",
      "conditions": [
        { "field": "totalJoinedCount", "operator": "GTE", "value": "1" }
      ],
      "metadata": {
        "rewardExit": "bonus_spin",
        "exitLabel": "邀请1人获2次抽奖"
      }
    },
    {
      "rewardId": "milestone_3",
      "type": "FIXED",
      "target": "SOURCE",
      "fixedAmount": "5",
      "conditions": [
        { "field": "totalJoinedCount", "operator": "GTE", "value": "3" }
      ],
      "metadata": {
        "rewardExit": "bonus_spin",
        "exitLabel": "邀请3人获5次抽奖"
      }
    }
  ]
}
```

> ⚠️ **conditions 字段名不带 `attrs.` 前缀**（已实测验证）：incentive-engine 的 `condition-evaluator._resolveField` 通用分支是 `data.attrs?.[field] ?? data[field] ?? 0`，它把 `field` 当作**顶层键**去 `event.attrs` 里找。所以条件应写 `field: "totalJoinedCount"`（引擎自动去 `event.attrs.totalJoinedCount` 找），**不能写 `field: "attrs.totalJoinedCount"`**（那样会去 `event.attrs["attrs.totalJoinedCount"]` 找，永远找不到返回 0，条件不满足）。

> ⚠️ **metadata 不透传到 engine 输出**（已实测验证）：incentive-engine 的 `distributeByDefs` 输出 `record.snapshot` 只包含计算字段（rewardId/rewardType/target/rate/fixedAmount/sourceNodeId），**不透传 rewardDef 的 `metadata`**。因此 cf-lottery 实现中通过 `rewardId → rewardDef` 映射，从**原始 rewardDef** 读取 `metadata.rewardExit`，而非从 `record.snapshot` 读取。

### 2.2 新增路径（engine-powered）

```
maybeTriggerReward()
  ├── [1] grantViralSpinsToSharer()           ← 完全不动
  ├── [2] processReferralMilestoneRewards()   ← 完全不动
  ├── [3] triggerRewardEarned()               ← 完全不动
  └── [4] NEW: processReferralRewardsEngine() ← 新增路径
        └── 仅读取 promotionConfig.referralRewardDefs
        └── 调用 distributeByDefs 计算奖励
        └── 映射到 rewardExit（bonus_spin / bonus_coupon）
        └── 幂等标记（写入 shareRecords.rewardMilestonesGranted）
```

### 2.3 为什么两个路径可以共存不会冲突

| 对比维度 | 现有路径 [2] | 新增路径 [4] |
|---------|------------|-------------|
| 读取配置 | `promotionConfig.referralRewards` | `promotionConfig.referralRewardDefs` |
| 配置格式 | `{ requireCount, rewardType, rewardValue }` | incentive-engine `rewardDefs` 格式 |
| 计算方式 | 纯 JS 手写 `evaluateReferralMilestones` | `engine.Distribute.distributeByDefs` |
| 幂等标记 | 共用 `shareRecords.rewardMilestonesGranted` | 共用 `shareRecords.rewardMilestonesGranted` |
| 奖励出口 | 仅 `bonus_spin` | `bonus_spin` / `bonus_coupon` |

**幂等标记共用同一字段**：`rewardMilestonesGranted` 存储的是已发放的 `requireCount` 数组。
- 现有路径写 `{ "rewardMilestonesGranted": "[1,3]" }`（requireCount 列表）
- 新路径写 `{ "rewardMilestonesGranted": "[\"milestone_1\",\"milestone_3\"]" }`（rewardId 列表）
- 格式不同，互不冲突

⚠️ **但这样做有风险**：两个路径可能会同时判断同一个 `rewardId` 是否已发放。为了避免混淆，**设计上要求"同一活动，两个路径不能同时启用"**。即：
- 如果 `promotionConfig.referralRewards` 有值 → 走现有路径 [2]，新路径 [4] 跳过
- 如果 `promotionConfig.referralRewardDefs` 有值 → 走新路径 [4]，现有路径 [2] 跳过
- 两个都配置 → 发布预检拒绝，报"不能同时配置两种奖励格式"

### 2.4 支持的奖励出口（P0-1）

| 奖励出口 | `metadata.rewardExit` 值 | 实现方式 | 适用 activityKind |
|---------|------------------------|---------|-----------------|
| 额外抽奖次数 | `bonus_spin` | `lotteryEntries.spinsLeft +N`（复用现有 grant 逻辑） | lottery（instant） |
| 优惠券码 | `bonus_coupon` | `couponCodes` 表 CAS 发券（复用 grantLoserRewards 模式） | flash_sale / claim |
| 额外加权票 | `bonus_entry` | 需要新建 `lotteryEntries.extraViralEntries` 字段（P1 暂缓） | signup_chain / delayed lottery |

## 三、具体实现

### 3.1 安装依赖（仅一个必要依赖）

```bash
npm install @usethink/incentive-engine
```

`@usethink/incentive-engine` 的生产依赖仅 `decimal.js`。`joi`/`sequelize` 是可选 peerDependencies，**cf-lottery 不需要安装它们**——`distributeByDefs` 纯计算不依赖 joi/sequelize。

### 3.2 新增文件：`src/services/lottery/referral-rewards-engine.ts`

这是整个 P0-1 的核心实现。职责：

1. **读取配置**：从 `promotionConfig.referralRewardDefs` 解析 incentive-engine 格式的 rewardDefs
2. **构建事件**：聚合分享者数据（totalJoinedCount、activityKind 等），构建 `EngineEvent`
3. **调用引擎**：`distributeByDefs({ event, rewardDefs })` 纯计算
4. **幂等过滤**：检查 `rewardMilestonesGranted` 已发放的 rewardId，只处理未发放的
5. **执行奖励**：按 `rewardExit` 类型分发到具体奖励出口
6. **标记幂等**：写入 `rewardMilestonesGranted`

```typescript
// 核心函数签名
export async function processReferralRewardsEngine(
  tx: DbType,
  draw: {
    id: string;
    tenantId: string;
    activityKind: string | null;
    maxSpinsPerEntry?: number | null;
    promotionConfig?: string | null;
  },
  shareRecordId: string,
): Promise<void>
```

### 3.3 修改文件：`src/services/lottery/participation.ts`

在 `maybeTriggerReward` 函数末尾、现有路径之后新增：

```typescript
// 新增路径 [4]：engine-powered 奖励（仅读取 referralRewardDefs，不读 referralRewards）
if (attribution.shareRecordId) {
  try {
    await processReferralRewardsEngine(tx, draw, attribution.shareRecordId);
  } catch (err) {

    console.error(`[lottery] processReferralRewardsEngine failed for ${draw.id}:`, err);

}
```

**仅新增 10 行代码**，不修改现有路径的任一行。

## 四、数据流图（完整路径）

```
joinDraw() 事务内
  │
  ├── recordAttributedJoin()
  │   ├── shareRecords.joinedCount +1
  │   └── activityEvents: attributed_join
  │
  └── maybeTriggerReward()
      │
      ├── [1] grantViralSpinsToSharer()
      │   └── lotteryEntries.spinsLeft +1（CAS + spins_log）
      │
      ├── [2] processReferralMilestoneRewards()
      │   └── 读取 referralRewards → evaluateReferralMilestones → spinsLeft +N
      │
      ├── [3] triggerRewardEarned()
      │   └── activityEvents: reward_earned → webhook → 中转站
      │
      └── [4] processReferralRewardsEngine()  ← 新增
          │
          ├── 读取 referralRewardDefs
          ├── 聚合分享者数据（totalJoinedCount）
          ├── 调用 distributeByDefs({ event, rewardDefs })
          │     └── 纯计算，不落库
          ├── 幂等过滤（已发放的 rewardId 跳过）
          │
          └── 循环执行奖励出口
              ├── bonus_spin → grantBonusSpin()
              │   └── lotteryEntries.spinsLeft +N（CAS + spins_log）
              └── bonus_coupon → grantBonusCoupon()
                  └── couponCodes: available→issued（CAS + 幂等）
```

## 五、安全性分析（关键路径的并发安全）

### 5.1 奖励计算（纯函数，无副作用）
`distributeByDefs` 是纯函数，没有 IO 操作，不需要并发保护。

### 5.2 幂等性（单个事务内）

| 场景 | 保护机制 | 是否安全 |
|------|---------|---------|
| 同一事务内重复调用 | `rewardMilestonesGranted` 列表判断 | ✅ 安全 |
| 并发两条记录同时归因 | 各自独立事务，CAS 更新 | ✅ 安全 |
| 并发写同一分享者 | CAS `spinsTotalGranted` 乐观锁 | ✅ 安全（现有机制） |
| 一个分享者多条分享码 | 按分享者聚合，写入全部记录 | ✅ 安全（现有机制，P1 修复） |

### 5.3 优惠券 CAS 发放
`grantBonusCoupon` 复用 `grantLoserRewards` 的 CAS 模式：
```sql
UPDATE coupon_codes SET status='issued', ...
WHERE id = ? AND tenant_id = ? AND status = 'available'
```
`rowsAffected=0` 时表示码已被其他请求占用，跳过本次发放。

### 5.4 不变量保证
- `spinsLeft + spinsUsed = spinsTotalGranted ≤ maxSpinsPerEntry`（CAS 保护）
- 同一 `couponCode` 只发放给一个用户（`status='available'` CAS 保护）
- 同一 `rewardId` 只发放一次（`rewardMilestonesGranted` 列表保护）

## 六、意外情况处理

### 6.1 奖励失败（容错）
与现有路径一致：`try/catch` 包裹，奖励失败不影响参与主流程。日志记录错误信息。

### 6.2 配置冲突
发布预检拦截 `referralRewards` + `referralRewardDefs` 同时配置。运行时如果两个都配置了，新路径 [4] 处理 `referralRewardDefs`，旧路径 [2] 处理 `referralRewards`——但**此时幂等标记 `rewardMilestonesGranted` 的格式不同**，旧路径写 `requireCount` 数组，新路径写 `rewardId` 数组，双方互读对方的标记会误解。所以发布预检必须拦截，运行时也做防御性检查。

### 6.3 优惠券码池耗尽
`grantBonusCoupon` 发券时，如果 `couponCodes` 中可用码不足，`rowsAffected=0` 时跳过，记录日志。不报错。

### 6.4 优惠券 label 不存在
`grantBonusCoupon` 按 `couponLabel` 过滤可用码。如果指定 label 无可用码，发券失败，记录日志。

### 6.5 兼容性
- 存量活动（有 `referralRewards` 无 `referralRewardDefs`）：行为不变，走现有路径 [2]
- 新活动（有 `referralRewardDefs` 无 `referralRewards`）：走新路径 [4]
- 两个都无：两个路径都跳过，行为不变
- 两个都有：发布预检拒绝，不会到运行时

## 九、关键设计决策记录

### 决策 1：为什么不是替换而是共存？
**避免灾难**：替换现有路径意味着所有存量活动在升级后走新路径，如果新路径有 bug，所有活动的邀请奖励都受影响。共存意味着：
- 存量活动（`referralRewards`）行为不变
- 新活动（`referralRewardDefs`）走新路径
- 新路径一旦出问题，退路是"改回用旧配置"，而非"回滚整个 deploy"

### 决策 2：为什么只用 `distributeByDefs` 不用 `GenericSettlementService`？
`GenericSettlementService` 依赖 `sequelize`（incentive-engine 的 optional peer dependency），而 cf-lottery 使用 drizzle。引入 `GenericSettlementService` 需要额外安装 `sequelize`（即使不使用它的 ORM 功能，只是为了错误类），增加依赖负担。`distributeByDefs` 是纯函数，无需任何外部依赖，完美适配 drizzle 的事务模式。

### 决策 3：为什么 P0-1 不做 `bonus_entry`？
`bonus_entry`（额外加权票）需要：
- 新增 `lotteryEntries` 字段 `extraViralEntries`（schema 迁移）
- 修改 `viral-weight.computeViralDrawWeight` 读取该字段
- `signup_chain` 的 `ordered_assignment` 结果模式需要额外支持
风险较高，适合 P1 单独评估。

### 决策 4：为什么 P0-1 不做前端 UI 变更？
前端 UI 变更涉及 `growth-config.ts` 的解析/回填/提交逻辑，风险较高。P0-1 阶段通过 API 直接写入 `promotionConfig.referralRewardDefs`（API 鉴权已保护，仅 L2 管理员可操作），前端 UI 延后到 P1。这符合"先验证后扩展"的原则。

## 十二、灾难风险分级

### 12.1 明确排除的灾难（本方案不会造成）

| 灾难 | 排除理由 |
|------|---------|
| **存量活动奖励失效** | 现有路径 [1][2][3] 一行不改，存量活动（referralRewards）行为完全不变 |
| **参与主流程回滚** | 新增路径 [4] 用 try/catch 包裹，奖励失败不影响 joinDraw 提交（与现有容错一致） |
| **重复发放奖励** | 幂等标记 `rewardMilestonesGranted` + CAS 乐观锁双重保护 |
| **跨租户数据泄漏** | 所有查询带 tenantId 过滤（沿用现有模式） |
| **schema 迁移风险** | 本方案**零 schema 迁移**（不新增字段/表） |
| **依赖冲突** | incentive-engine 生产依赖仅 decimal.js，与 cf-lottery 现有依赖无冲突 |

### 12.2 需重点防护的事故风险（及触发条件）

| 风险 | 触发条件 | 防护措施 | 严重度 |
|------|---------|---------|--------|
| **配置冲突导致幂等错乱** | 同一活动同时配置 `referralRewards` + `referralRewardDefs` | 发布预检拦截 + 运行时防御性检查 | 🔴 高 |
| **优惠券超发** | 并发下同一 coupon 被两个请求同时领取 | `status='available'` CAS 原子更新（rowsAffected=0 跳过） | 🔴 高 |
| **spins 超发** | 并发下同一分享者被两条归因同时加次 | `spinsTotalGranted` CAS 乐观锁（现有机制） | 🟡 中 |
| **incentive-engine 版本升级破坏** | 升级引擎版本引入行为变化 | 锁定版本（^3.4.10），升级前跑全量测试 | 🟡 中 |
| **奖励出口未实现导致静默不发** | 配置了 `rewardExit` 但适配器未实现 | 发布预检校验 rewardExit 白名单 | 🟡 中 |

### 12.3 回滚方案

由于本方案是**共存式**（新增路径 + 保留现有路径），回滚极其简单：
1. **代码回滚**：`git revert` 本次 commit，恢复 `participation.ts` 和 `publish-check-service.ts` 的改动
2. **数据回滚**：无需回滚——新路径只写 `shareRecords.rewardMilestonesGranted`（现有字段）和 `lotteryEntries.spinsLeft`（现有字段），不新增任何持久化结构
3. **配置回滚**：删除活动的 `promotionConfig.referralRewardDefs` 配置即可，存量活动不受影响

**回滚成本：极低**。这是"共存式"设计最大的优势。

## 十三、是否值得做（结论）

### 13.1 价值

1. **直接补上架构缺口**：邀请奖励从"只支持 bonus_spin、只对 lottery 生效"扩展为"支持 bonus_spin/bonus_coupon、对 flash_sale/claim 等生效"，符合 AGENTS.md"所有环节形成闭环"铁律
2. **引入配置驱动的奖励计算底座**：为后续 P1（bonus_entry、CUSTOM 动态金额、LEVEL 多级）和 P2（封顶/预算、活动期加成）铺路
3. **复用 incentive-engine 成熟能力**：196 个测试全绿、纯计算零副作用、decimal.js 高精度，避免重复造轮子

### 13.2 成本

- 约 3.4 人日（含测试）
- 新增一个生产依赖（@usethink/incentive-engine，仅 decimal.js 传递依赖）
- 新增约 450 行代码（含测试）

### 13.3 时机建议

**值得做，且建议现在做**。理由：
1. 风险极低（共存式、零 schema 迁移、回滚成本极低）
2. 直接补记忆里的架构缺口（"邀请不能只局限在免费抽奖"）
3. 为后续秒杀/批发返佣（P0-3）铺路——P0-3 需要同样的 engine 计算底座

**但建议分两步走**：
- **第一步（本次）**：只做 `bonus_spin` 出口的 engine 化（复用现有 spins 逻辑），验证 engine 接入链路
- **第二步（验证后）**：再加 `bonus_coupon` 出口（复用 grantLoserRewards 发券模式）

这样即使 engine 接入有意外，影响面也最小（只影响新增的 bonus_spin 路径，且可回滚）。
