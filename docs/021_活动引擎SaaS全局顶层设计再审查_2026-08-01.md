## 一、最终判断

`cf-lottery` 不应继续定义为“抽奖 SaaS”，也不应定义为“导流小游戏集合”。最优定位是：

> **多租户、可白标、可嵌入、可集成的轻量活动引擎 SaaS。**

抽奖只是第一个玩法。接龙、预约、投票、问卷、签到、候补、审核、领券、资料领取、内测申请、抽签分组、线下核销等，本质都是同一个活动引擎问题：

```text
租户配置活动规则
  -> 用户通过公开链接/二维码进入
  -> 平台校验资格和时间窗口
  -> 用户提交参与记录
  -> 平台生成或记录结果
  -> 平台展示结果、导流 CTA、通知和导出
  -> 平台沉淀事件、审计、归因和复盘
```

因此，平台内核应围绕以下 7 个词设计：

```text
Activity / Entry / Qualification / Outcome / Promotion / Event / Audit
```

当前仓库已经具备正确的骨架，不能推倒重做；但必须防止继续在服务层、接口层、后台文案里把所有事情都命名成 lottery/winner/draw。MVP 可以保留旧表名作为兼容层，未来平台能力必须逐步上移到 `activity` 语义。

## 二、对 009 和 010 的复审结论

### 2.1 009 的价值和边界

009 的“商品链接 + UTM + 简单优惠券”是正确的 MVP 选择，因为它避免把活动系统拖进电商域：

- 不做商品 SKU。
- 不做订单。
- 不做库存。
- 不做购物车。
- 不做佣金结算。
- 不做广告交易市场。

这符合当前产品阶段。活动引擎要做的是“把用户带到正确的下一步”，不是替代商家的交易系统。

但 009 不能作为长期导流闭环的完整方案。原因是：

- UTM 只能识别来源、媒介、活动，不能证明成交或核销。Google Analytics 官方文档也把 UTM 定义为在目标 URL 上添加 campaign 参数，用于识别 referral links/ad campaigns 带来的流量，而不是证明外部业务结果。
- 商品链接字段只能表达一个静态 CTA，无法承载多目标导流、结果分层导流、外部转化回传、模板复用和行业化配置。
- “未来用 Worker 日志统计点击”不足以支撑 SaaS 后台。平台需要结构化 `activity_events`，否则租户无法在后台稳定复盘漏斗。

结论：

```text
009 的 productLink 应保留为旧字段兼容；
长期导流应以 promotion_config + activity_events + external_conversions 为主线。
```

### 2.2 010 的价值和边界

010 的“可插拔游戏引擎”方向正确，但必须限制在体验层：

- 转盘、老虎机、刮刮卡、翻牌、九宫格、盲盒开箱，都是 `experience_type`。
- 它们不应该决定谁能参加，也不应该决定谁中奖。
- 前端动画只能制造悬念和反馈，结果必须由后端的规则、资格、容量、随机/顺序/审核/计票逻辑决定。

010 当前最大的战略价值不是“做更多动画”，而是让前端支持：

```text
同一个 activity_kind 可以换不同 experience_type；
同一个 experience_type 可以服务不同 activity_kind。
```

例如：

| 活动 | 可用体验 | 后端结果 |
|---|---|---|
| 即时抽奖 | 转盘/刮刮卡/盲盒/九宫格 | 后端即时分配 |
| 领券 | 刮刮卡/揭晓卡/普通提交 | 后端发放权益 |
| 接龙 | 列表/排队/翻牌 | 后端顺序占位 |
| 预约 | 日历/时间段/普通表单 | 后端容量确认 |
| 投票 | 票选卡片/排行榜 | 后端去重计票 |

结论：

```text
010 应继续推进，但所有游戏组件都必须接受后端结果，不允许前端伪造奖品或结果。
```

### 3.1 已经做对的部分

| 领域 | 当前证据 | 判断 |
|---|---|---|
| 多租户 | `tenants`、`tenant_members`、`users`，管理端请求普遍带 `tenantId` | 基础正确 |
| 活动抽象 | `lottery_draws` 已含 `activity_kind`、`participation_mode`、`experience_type`、`result_mode`、`allocation_policy`、`policy_version`、`promotion_config` | 方向正确 |
| 结果抽象 | `activity_outcomes` 已能承载接龙/预约/候补/审核等非抽奖结果 | 基础正确 |
| 事件追踪 | `activity_events` 已存在，服务层有 `recordActivityEvent()` / `getActivityEventSummary()` | 已建立事实表基础 |
| Webhook | `webhook_configs.signing_secret`、`webhook_deliveries`、签名、重试状态、投递记录、Worker Cron 到期重试调度已存在 | 接近 SaaS 集成基础 |
| 套餐配额 | `PLAN_LIMITS` 覆盖活动数、参与人数、成员数、Webhook 数 | MVP 可用 |
| 接龙 | `signup_chain` 已按顺序生成 outcome，支持容量和 waitlist policy | 已是第一个非抽奖闭环 |
| 公开端埋点 | `LotteryView.vue` 已上报 `page_view`、`participation_started`、`participation_completed`、`cta_click` | 导流漏斗基础已建 |

### 3.2 不能误判为已完成的部分

| 能力 | 当前状态 | 正确口径 |
|---|---|---|
| 活动引擎 | 有字段和接龙闭环 | 还不是完整多玩法引擎 |
| 导流归因 | 有 UTM、事件、分享点击、服务端有效邀请归因 | 还不能证明外部成交或核销 |
| Webhook | 有 delivery、手动处理接口和 Cron 到期重试 | 还缺 Queue/告警化运营和租户侧可视化 |
| SaaS 后台 | 有租户和配额基础 | 还缺平台运营后台 |
| 玩法库 | 有抽奖和接龙基础 | 预约/问卷/投票/签到仍需要 vertical slice |
| 商业化 | 有 plan 字段和硬编码限制 | 还缺套餐权益、用量快照、订阅状态同步 |

### 3.3 未来最容易导致推翻重做的风险

1. **业务语义继续被抽奖命名绑住。**  
   表名可以先不改，但新服务、新 API、新后台信息架构应逐步使用 activity/outcome/promotion/event 语言。

2. **每个玩法复制一套路由和表。**  
   预约、投票、问卷、签到不能各自新增完整独立参与表。应该复用 `activity -> entry -> outcome -> event`。

3. **把导流等同于成交。**  
   没有外部订单/核销/注册回传，就只能说点击、来源、完成参与，不能说成交。

4. **把游戏体验等同于玩法。**  
   转盘、刮刮卡、老虎机是皮肤，不是业务模型。

5. **把支付、电商、库存、广告交易塞进核心。**  
   这些是外部集成域，不应进入 activity core。

## 四、顶层架构：一套内核，多种玩法

### 4.1 稳定内核

建议长期冻结为 12 个模块：

| 模块 | 职责 | 当前基础 | 下一步 |
|---|---|---:|---|
| `tenant` | 租户、状态、品牌、套餐、配额 | 有 | 补平台运营视图和套餐变更审计 |
| `user/team` | 用户、成员、角色、邀请 | 有 | 补成员邀请、RBAC 权限矩阵 |
| `activity` | 活动主模型、状态机、模板 | 有 | 建立 service facade，弱化 lottery 命名 |
| `rule/policy` | 活动规则、容量、字段、版本 | 部分 | 引入 `rule_schema` / `policy_json` 版本校验 |
| `qualification` | 资格校验 | 部分 | 抽出统一资格管线 |
| `entry` | 参与记录、提交数据 | 有 | 增加通用表单 submission |
| `outcome` | 中奖、名额、候补、审核、计票、领取 | 部分 | 抽奖长期也映射到统一 outcome 视角 |
| `reward/benefit` | 奖品、券码、资料、权益发放 | 部分 | 建立 `reward_grants`，不做商品库存 |
| `promotion` | CTA、外链、优惠、下一活动、渠道 | 部分 | 以 `promotion_config` 为主，productLink 仅兼容 |
| `event/analytics` | 曝光、参与、点击、分享、转化回传 | 部分 | 补漏斗看板、有效邀请、外部回传 |
| `notification/integration` | 邮件、Webhook、API、失败重试 | 部分 | 增加后台任务、告警、签名轮换 |
| `audit/risk` | 操作日志、风控、规则变更、结果修正 | 部分 | 覆盖平台管理员和人工干预 |

### 4.2 五个必须解耦的维度

这些维度必须稳定，不应互相推导：

| 维度 | 含义 | 示例 |
|---|---|---|
| `activity_kind` | 业务类型 | `lottery`、`signup_chain`、`reservation`、`vote`、`survey`、`claim` |
| `participation_mode` | 资格入口 | `open`、`roster`、`password`、`invite_code`、`approval`、`external_check` |
| `experience_type` | 前端体验 | `wheel`、`scratch`、`slot`、`card`、`form`、`calendar`、`ballot`、`queue` |
| `result_mode` | 结果产生方式 | `instant`、`scheduled`、`ordered_assignment`、`capacity_assignment`、`vote_tally`、`review_decision`、`no_result` |
| `allocation_policy` | 分配策略 | `capacity`、`waitlist`、`fifo`、`priority`、`random`、`weighted_random`、`approval` |

关键原则：

```text
activity_kind 决定业务语义；
participation_mode 决定资格校验；
experience_type 决定页面交互；
result_mode 决定结果生成方式；
allocation_policy 决定名额/权益分配策略。
```

### 4.3 推荐活动状态机

长期统一为：

```text
draft -> published -> open -> closed -> processing -> completed -> archived
```

旁路状态：

```text
paused
cancelled
failed
```

当前 `drawing/drawn` 可以兼容映射：

| 当前状态 | 平台语义 |
|---|---|
| `draft` | `draft` |
| `open` | `open` |
| `drawing` | `processing` |
| `drawn` | `completed` |
| `paused` | `paused` |
| `cancelled` | `cancelled` |

不要为投票、接龙、预约、问卷各自发明状态机。

## 五、抽奖、接龙是否同类

结论：**接龙和抽奖是同一类活动引擎问题，但不是同一种结果模式。**

共同点：

- 都需要活动创建、发布、暂停、归档。
- 都需要公开链接/二维码。
- 都需要资格校验和重复参与控制。
- 都需要容量或名额。
- 都需要参与记录。
- 都需要结果或确认。
- 都需要导流、通知、导出、审计。
- 都需要租户隔离和套餐配额。

差异：

| 维度 | 抽奖 | 接龙 |
|---|---|---|
| 结果本质 | 随机抽取 winner | 顺序占位 assignment |
| 关键公平性 | 随机算法、种子、开奖审计 | 顺序一致性、容量扣减、候补转正 |
| 用户反馈 | 等待开奖或即时揭晓 | 立即知道第几位/是否候补 |
| 导流机会 | 中奖/未中奖结果页 | 报名成功/候补页/群接龙页 |

建模建议：

```text
抽奖:
activity_kind = lottery
result_mode = manual | scheduled | instant
allocation_policy = random | weighted_random

接龙:
activity_kind = signup_chain
result_mode = ordered_assignment
allocation_policy = capacity | waitlist | fifo
```

## 六、更多类似抽奖/接龙的低成本高价值玩法

### 6.1 第一梯队：必须纳入核心玩法库

这些玩法与现有架构共享度最高，适合做成 SaaS 模板。

| 玩法 | 推荐 `activity_kind` | 推荐 `result_mode` | 推荐体验 | 业务价值 | 成本 |
|---|---|---|---|---|---:|
| 普通抽奖 | `lottery` | `manual/scheduled` | `wheel/card` | 活跃、传播、福利发放 | 低 |
| 即时抽奖 | `lottery` | `instant` | `scratch/reveal/grid` | 可玩性强，导流承接自然 | 中 |
| 报名接龙 | `signup_chain` | `ordered_assignment` | `list/queue` | 社群、课程、活动高频 | 低 |
| 限量预约 | `reservation` | `capacity_assignment` | `calendar/form` | 门店、沙龙、课程、咨询 | 中 |
| 候补排队 | `waitlist` | `ordered_assignment` | `queue` | 满额后不浪费需求 | 中 |
| 领券 | `claim` | `instant` | `reveal/scratch` | 直接导向购买或到店 | 中 |
| 资料领取 | `claim/survey` | `instant/no_result` | `form/reveal` | B2B 获客、教育资料分发 | 低 |
| 问卷调研 | `survey` | `no_result` | `form` | 留资、用户研究、满意度 | 低 |
| 投票评选 | `vote` | `vote_tally` | `ballot` | 社群传播、活动参与 | 中 |
| 签到打卡 | `checkin` | `no_result/instant` | `checkin` | 复访、课程训练营、社群运营 | 中 |
| 审核申请 | `approval` | `review_decision` | `form` | 内测、试用、白名单 | 中 |
| 抽签分组 | `assignment` | `ordered_assignment/random` | `card/list` | 分班、分组、座位、任务分配 | 中 |

### 6.2 第二梯队：适合作为模板或组合玩法

| 玩法 | 本质 | 推荐组合 | 风险控制 |
|---|---|---|---|
| 盲盒开箱 | 即时结果揭晓皮肤 | `lottery/claim + reveal` | 后端先决定结果 |
| 刮刮乐 | 即时揭晓皮肤 | `lottery/claim + scratch` | 禁止前端伪造结果 |
| 幸运九宫格 | 游戏皮肤 | `lottery + grid` | 动画只展示结果 |
| 翻牌抽签 | 游戏皮肤 | `assignment + card` | 分配后再翻牌 |
| 答题抽奖 | 答题资格 + 抽奖 | `quiz + lottery` | 题库和判分要版本化 |
| 测验评分 | 表单 + 分数结果 | `quiz` | 不要扩展成复杂 LMS |
| 作品征集 | 表单/上传 + 审核/投票 | `contest + approval/vote` | 内容审核和隐私 |
| 提名推荐 | 表单 + 评选 | `survey/vote` | 防刷、隐私、撤回 |
| RSVP 活动确认 | 报名确认 | `reservation` | 多场次再引入 slot |
| 现场签到码 | 验证码签到 | `checkin` | 防代签、限设备 |
| 邀请解锁 | 有效邀请触发权益 | `promotion + claim` | 不能只按点击发奖 |
| 分享加次数 | 邀请增加资格 | `referral policy + lottery` | 要有效参与归因和上限 |
| 试用申请 | 留资 + 审核 + 名额 | `approval/reservation` | 审核任务和通知 |
| 内测码发放 | 审核 + 唯一码池 | `approval + claim` | 码池防超发 |
| 线下核销券 | 领券 + 核销 | `claim` | 核销审计 |
| 加群/入会申请 | 表单 + 审核/外链 | `approval + promotion` | 外部结果需回传 |
| 课程选座/排号 | 容量分配 | `reservation/assignment` | 多资源时再引入 slots |
| 众测招募 | 表单 + 审核 + 码池 | `approval/claim` | 隐私和资格校验 |
| 每日任务打卡 | 重复 checkin | `checkin + reward` | 避免变成重营销自动化 |
| 结果公示榜 | outcome 可见性 | `vote/lottery/assignment` | 脱敏、公示开关、撤回 |

### 6.3 第三梯队：可以做，但不要进入内核

| 玩法 | 可以做的原因 | 不进内核的原因 |
|---|---|---|
| 排行榜冲榜 | 提升传播 | 反作弊和社区治理重 |
| 邀请裂变竞赛 | 可拉新 | 奖励结算、作弊识别复杂 |
| 积分任务中心 | 可提升复访 | 会滑向营销自动化平台 |
| 直播抽奖 | 活动结果可复用 | 直播互动链路是另一产品域 |
| 内容社区评选 | 投票可复用 | 内容审核、评论、举报复杂 |
| 联盟分销活动 | 可导流变现 | 佣金、结算、合规是重域 |

### 6.4 暂不建议做

这些会破坏轻量活动引擎边界：

- 自建电商商品库。
- 自建订单、库存、购物车。
- 自建支付和退款。
- 自建广告交易市场。
- 自建分销佣金结算。
- 自建开放内容社区。
- 自建复杂会员 CRM。

正确方式是通过外链、Webhook、API、导入导出、外部转化回传连接这些系统。

## 七、导流与变现闭环

### 7.1 引流、导流、归因分层

| 层级 | 数据来源 | 能证明 | 不能证明 |
|---|---|---|---|
| 渠道参数 | UTM/source/ref | 用户从哪里来 | 成交、核销、真实拉新 |
| 平台事件 | `activity_events` | 浏览、开始参与、完成、点击、分享 | 外部订单结果 |
| 有效邀请 | ref + 新参与者成功入库 | 某分享带来有效参与 | 外部付费 |
| 外部回传 | Webhook/API/CSV import | 注册、下单、核销、付费等外部结果 | 如果外部不回传则无法证明 |

推荐事件命名：

```text
page_view
participation_started
participation_completed
outcome_assigned
cta_impression
cta_click
share_created
share_click
attributed_join
external_conversion_reported
coupon_issued
coupon_redeemed
review_approved
review_rejected
waitlist_promoted
```

### 7.2 用户侧闭环

```text
看到分享/二维码/渠道链接
  -> 打开活动页
  -> 完成参与/领取/预约/投票/提交
  -> 获得结果或状态
  -> 看到自然 CTA
  -> 点击外链/复制券码/下载资料/加入下一活动
  -> 平台记录事件
```

用户体验原则：

- 先完成用户来活动页的核心任务，再导流。
- 未中奖、候补、审核中也要有承接，不能让用户空手离开。
- 不做强制跳转，避免破坏信任。
- 导流文案必须和结果相关，例如“候补成功 -> 加群等待通知”，“未中奖 -> 领取优惠券”，“资料领取成功 -> 预约咨询”。

### 7.3 租户侧闭环

```text
选择模板
  -> 配置规则、资格、导流目标
  -> 发布链接/二维码
  -> 查看参与、完成、CTA、分享、转化回传
  -> 导出/通知/复盘
  -> 复制模板继续运营
```

租户愿意付费的不是动画，而是：

- 更快创建活动。
- 更安全控制资格、容量和权益。
- 更专业的品牌页。
- 更清楚的漏斗数据。
- 更稳定的通知和 Webhook。
- 更方便的导出和团队协作。
- 更少人工整理接龙、报名、投票、领券数据。

### 7.4 平台侧变现

短中期优先卖 SaaS 能力，而不是卖流量：

| 套餐 | 推荐限制/权益 |
|---|---|
| Free | 少量活动、低参与上限、平台品牌、水印、基础抽奖/接龙 |
| Pro | 更多活动和参与人数、导出、品牌配置、基础事件看板、更多模板 |
| Team | 多成员、角色权限、审计、模板库、Webhook、批量导入 |
| Enterprise | 白标、自定义域名、API、Webhook 高配额、专属支持、集成服务 |

长期可以支持用量计费，但不要早期把系统复杂化。Stripe 订阅文档强调订阅生命周期、状态、发票、失败支付、Webhook 与 entitlement 的联动；这意味着即使未来接支付，也要把“付费状态/权益开通”和活动引擎分层处理。

## 八、简单但完整的 SaaS 后端

### 8.1 租户运营后台

租户后台不是活动 CRUD，而是“运营工作台”。最小完整后端应包含：

| 域 | 必备接口/能力 |
|---|---|
| 工作台 | 活动状态、参与趋势、待处理项、套餐用量 |
| 活动 | 创建、编辑、发布、暂停、复制、归档、模板化 |
| 参与 | 参与列表、筛选、导出、名单、邀请码、黑名单 |
| 结果 | 中奖、接龙名额、候补、审核、核销、人工修正 |
| 导流 | CTA、商品链接、优惠券、下一活动、渠道参数 |
| 事件 | 浏览、参与、完成、点击、分享、有效邀请、外部转化 |
| 通知 | 邮件、Webhook、失败重试、模板 |
| 团队 | 成员、角色、邀请、移除 |
| 品牌 | Logo、颜色、公开页标题、自定义域名预留 |
| 套餐 | 当前计划、用量、限制、升级提示 |
| 审计 | 活动规则变更、结果修正、成员变更、导出记录 |

### 8.2 平台运营后台

平台方需要单独的运营后台，不能只靠数据库手改：

| 域 | 必备能力 |
|---|---|
| 租户管理 | 租户列表、状态、套餐、创建时间、最近活跃 |
| 用量管理 | 活动数、参与数、事件数、Webhook 数、导出数 |
| 套餐权益 | plan -> entitlement -> quota -> feature flag |
| 活动监管 | 异常活动、投诉、封禁、下架 |
| 投递监控 | 邮件失败、Webhook 失败、重试队列 |
| 模板运营 | 官方模板、行业模板、启停、排序 |
| 风控 | IP/身份异常、分享刷量、重复参与 |
| 系统配置 | 邮件、限流、Webhook、注册开关 |
| 支持诊断 | 只读查看租户状态、活动状态、失败原因 |
| 平台审计 | 平台管理员任何跨租户操作必须记录 |

原则：

- 平台管理员可以诊断，但不能无审计修改租户业务数据。
- 套餐变更、配额调整、结果修正必须写 audit。
- 系统配置和租户配置分层，避免一个租户配置影响全局。

### 8.3 推荐新增/强化数据模型

| 模型 | 作用 | 优先级 | 当前关系 |
|---|---|---:|---|
| `activity_templates` | 官方/租户模板，支持复制复用 | P1 | 当前缺 |
| `activity_form_schema` | 报名、问卷、申请、资料领取字段配置 | P1 | 当前缺 |
| `activity_submissions` | 通用表单提交 payload | P1 | 当前缺 |
| `tenant_usage_snapshots` | 日/月用量快照 | P1 | 当前缺 |
| `feature_entitlements` | 套餐功能和额度，不让硬编码扩散 | P1 | 当前缺 |
| `external_conversions` | 外部转化回传 | P1/P2 | 当前缺 |
| `reward_grants` | 奖品、券码、资料、权益发放统一记录 | P2 | 当前部分由 winners/coupon/prize_codes 承担 |
| `review_tasks` | 审核活动任务和决策 | P2 | 当前缺 |
| `activity_slots` | 预约多时段、多资源容量 | P2 | 当前缺 |
| `risk_signals` | 风控信号和处理结果 | P2 | 当前缺 |

### 8.4 Cloudflare 架构建议

当前使用 Worker + D1 是合理 MVP。后续按压力和一致性逐步加能力：

| 场景 | 推荐能力 | 理由 |
|---|---|---|
| 普通 CRUD、查询、配置 | D1 | 关系数据、租户隔离、审计查询 |
| Webhook/邮件异步投递 | Queues 或 Cron + D1 delivery 表 | Cloudflare Queues 默认至少一次投递，需用幂等键去重 |
| 定时开奖、定时重试、用量快照 | Cron Triggers | Cloudflare Cron 可用 `scheduled()` handler 执行周期任务，注意 UTC |
| 高并发接龙/抢名额/候补转正 | Durable Objects | 每活动一个协调单元可承载强一致顺序、容量、幂等 |
| 图片、海报、资料下载 | R2 | 文件和大对象不要塞 D1 |
| 高维事件分析 | Analytics Engine 或外部仓库 | `activity_events` 可做事实源，分析层后置 |

Cloudflare Durable Objects 官方定位就是用于需要多客户端协调的状态型场景，并且对象存储与计算同处一处，支持强一致访问。对本项目来说，它不是现在必须迁移的 P0，但应作为未来“每活动协调单元”的目标。

## 九、分阶段实施路线

### 阶段 0：MVP 稳定，不推翻现有代码

目标：保留当前抽奖能力，同时把会阻塞扩展的点收口。

已完成或基本完成：

- 非抽奖活动不再强制 `winnerCount >= 1`。
- `activity_kind`、`experience_type`、`result_mode`、`allocation_policy` 已进入活动主表。
- `signup_chain` 已有基础 outcome。
- `activity_events` 已有事实表和公开端基础埋点。
- `webhook_deliveries` 已有投递记录、签名和重试状态。

仍建议立刻补齐：

1. Webhook 失败告警：到达重试阈值后写事件并在运营后台展示。
2. 归因反作弊和归因窗口：当前 `ref` 只有在新参与者成功入库后才产生 `attributed_join`，下一步补同设备/同身份限制和奖励上限。
3. 活动事件看板：先展示浏览、开始、完成、CTA 点击、分享点击、有效邀请，不显示成交。
4. 后台文案改口径：把“抽奖管理”逐步上移为“活动管理”，保留抽奖作为模板。

### 阶段 1：活动引擎内核成型

目标：新增玩法时不复制主流程。

实施项：

1. 抽出 `qualification` 管线：open、roster、password、invite_code、unique_code、approval、external_check。
2. 抽出 `outcome` 服务：assignment、waitlist、claim、vote、review、checkin。
3. 建立 `activity_form_schema`：支持资料领取、问卷、申请、预约字段。
4. 建立 `activity_templates`：抽奖、接龙、资料领取、预约、投票、签到作为模板。
5. 建立 `promotion_config` V2：多 CTA、展示位置、结果条件、渠道参数、下一活动。

验收标准：

- 新增“资料领取”不需要新表。
- 新增“预约”不需要重写公开端参与流程。
- 新增“投票”只新增 vote outcome/summary，不复制租户、资格、事件、导出。

### 阶段 2：高价值玩法库

优先顺序：

1. 接龙稳定化：候补转正、导出、通知、可见性。
2. 资料领取/问卷：通用表单 schema + 导出 + CTA。
3. 领券：唯一码池、领取记录、核销入口。
4. 预约：先单时段容量，再多时段 slots。
5. 投票：去重、匿名/实名、公示脱敏。
6. 签到：按天/场次重复控制，连续签到奖励。
7. 审核申请：review task、通过/拒绝通知、发码。

### 阶段 3：SaaS 运营化

实施项：

1. 平台运营后台：租户、套餐、用量、异常、投递失败。
2. 套餐权益表：从 `PLAN_LIMITS` 逐步收敛到 entitlement service。
3. 用量快照：活动数、参与数、事件数、Webhook 数、导出数。
4. 成员邀请和 RBAC。
5. API Key scope 和调用日志。
6. 白标和自定义域名预留。
7. 模板市场：官方模板、行业模板、租户私有模板。

### 阶段 4：外部生态集成

只连接，不吞并：

- 支付订阅系统。
- CRM。
- 邮件营销。
- 电商优惠券。
- 外部会员校验。
- 外部订单/核销回传。
- 企业 SSO。

## 十一、最优实施顺序

### 11.1 近期 4 个工程切片

1. **Webhook 告警闭环**  
   在现有 Worker `scheduled()` 到期重试基础上，失败达到阈值后写告警事件，并在租户后台/平台后台展示。

2. **归因反作弊和窗口**  
   在现有服务端 `attributed_join` 基础上，补同设备/同身份限制、归因有效期、单分享奖励上限和异常分享事件。

3. **活动事件看板**  
   管理端展示 funnel：浏览、开始、完成、CTA、分享点击、有效邀请、外部回传。命名上不能写“成交”。

4. **资料领取 vertical slice**  
   引入最小通用表单 schema/submission，复用 `activity_events`、`promotion_config`、`activity_outcomes`，证明平台不是只能抽奖/接龙。

### 11.2 中期 4 个产品切片

1. 模板库：官方模板 + 租户复制。
2. 租户运营工作台：用量、待处理、失败通知。
3. 平台运营后台：租户列表、套餐、异常、投递失败。
4. 套餐权益服务：将硬编码 `PLAN_LIMITS` 封装成 entitlement facade。

## 十二、不可妥协的设计原则

1. **结果由后端产生或确认。**  
   前端游戏组件只展示过程和结果，不决定结果。

2. **导流归因必须诚实。**  
   点击就是点击，参与就是参与，外部转化必须由外部回传或导入证明。

3. **activity_kind、participation_mode、experience_type、result_mode 分离。**  
   不允许为了快速上线把某种玩法写死在某个组件或路由里。

4. **SaaS 后台优先于花哨玩法。**  
   没有租户、套餐、用量、审计、失败处理，多玩法越多越难运营。

5. **电商、支付、广告、社区不进核心。**  
   通过集成连接，不在活动引擎里内建。

6. **MVP 表名可以兼容，服务语义必须升级。**  
   `lottery_draws` 可以暂时存在；新增服务、文档和后台导航应逐步使用 `activity`。

7. **先 vertical slice，再横向铺玩法。**  
   每个新玩法必须走完管理端、公开端、服务层、事件、通知、导出、审计的最小闭环。

## 十四、结论

最优方案不是“在抽奖上继续堆玩法”，而是：

```text
以活动引擎为内核，
以抽奖和接龙作为前两个 vertical slice，
以资料领取、领券、预约、投票、签到、审核作为低成本高价值扩展，
以 promotion/event/webhook/audit/tenant_usage 构成 SaaS 运营闭环，
以外部集成连接电商、支付、CRM 和核销系统。
```

这样做的好处是：

- MVP 不需要推翻，现有 `lottery_*` 表可作为兼容层继续运行。
- 接龙、预约、问卷、投票、签到不会各自长出一套系统。
- 导流数据诚实，不把点击误报为成交。
- SaaS 后台可运营、可收费、可支持团队客户。
- 未来需要强一致抢名额时，可以把关键写路径迁移到每活动 Durable Object，而不是重写全部业务。

下一步最推荐的工程顺序：

```text
Webhook 失败告警
  -> 归因反作弊
  -> 活动事件看板
  -> 资料领取 vertical slice
  -> 模板库
  -> 平台运营后台
```
