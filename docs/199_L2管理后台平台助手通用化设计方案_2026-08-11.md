# 199 L2 管理后台「平台助手」通用化设计方案

> 日期：2026-08-11
> 背景：当前 L2 管理后台只有 `AdminQqAssistantView.vue`（626 行，QQ 专用），但后端 `platform_targets` 表已是通用设计（`platform` 字段区分 qq/telegram），且未来可能接入 Telegram 和微信小程序。需要评估是否将 QQ 专用页面改造为通用「平台助手」。
> 原则：不重复造轮子，对齐后端抽象层，避免未来接入新平台时再写一遍 600 行重复代码。

---

## 0. 现状分析

### 0.1 后端已经是通用架构

`platform_targets` 表（`src/db/schema.ts:998`）的字段设计：

| 字段 | 通用性 | 说明 |
|------|:---:|------|
| `platform` | ✅ 通用 | `"qq"` / `"telegram"` / 未来扩展 |
| `targetId` | ✅ 通用 | QQ 群号 / Telegram chat_id |
| `targetName` | ✅ 通用 | 显示名称 |
| `activeDrawId` | ✅ 通用 | 绑定活动，所有平台共享 |
| `adapterProvider` | ⚠️ 默认 `"napcat"` | 各平台可不同，Telegram 用 `"telegram_bot"` |
| `adapterConfigJson` | ✅ 通用 JSON | 各平台存自己的连接配置 |
| `inboundSecretHash` | ✅ 通用 | 入站消息验证 |
| `builtinCommandsJson` | ✅ 通用 | 命令配置，平台无关 |
| `assistantEnabled` | ✅ 通用 | 开关 |

**结论**：后端从第一天就是通用设计，但前端只做了 QQ 的实现。

### 0.2 前端当前硬编码的 QQ 特定内容

`AdminQqAssistantView.vue` 中以下内容与 QQ 强绑定：

| 行号 | 内容 | 绑定程度 |
|:---:|------|:---:|
| 322 | `callbackUrl = .../api/platform/qq/message` | 硬编码，需按平台动态生成 |
| 588 | 同上（测试消息） | 硬编码 |
| 597 | 公证人 QQ 号提取逻辑 | QQ 特有，Telegram 无此概念 |
| 表单 | NapCat 地址输入框 | QQ 特有（`adapterProvider="napcat"`） |
| 表单 | 入站密钥配置 | 通用，但 QQ 专有提示文字 |
| i18n | `adminQqAssistant.*` 键 | 全部以 QQ 命名 |

## 1. 设计方案

### 1.1 总体思路

把 `AdminQqAssistantView.vue` 改造为通用的 `AdminPlatformTargetView.vue`，核心思想：

```
┌──────────────────────────────────────────────┐
│  平台助手（Platform Assistant）                │
│                                              │
│  ┌──────────────────────────────────────────┐│
│  │  [QQ] [Telegram] [全部]  ← 平台筛选标签  ││
│  ├──────────────────────────────────────────┤│
│  │  列表：显示所有平台目标                    ││
│  │  ┌──────┬──────┬──────┬──────┬──────┐   ││
│  │  │ 名称  │ 平台 │ 目标ID│ 绑定活动│ 状态 │   ││
│  │  ├──────┼──────┼──────┼──────┼──────┤   ││
│  │  │ 群A  │ QQ   │ 123  │ 活动X │ 启用 │   ││
│  │  │ 群B  │ TG   │ -456 │ 活动Y │ 启用 │   ││
│  │  └──────┴──────┴──────┴──────┴──────┘   ││
│  ├──────────────────────────────────────────┤│
│  │  [新建]  → 弹窗：选择平台 → 填写配置     ││
│  │     ┌── 通用配置（所有平台都有） ──┐     ││
│  │     │ 目标名称、目标ID、绑定活动    │     ││
│  │     │ 命令开关、启用状态            │     ││
│  │     ├── 平台特定配置（动态切换） ──┤     ││
│  │     │  QQ:  NapCat地址、入站密钥    │     ││
│  │     │  TG:  Bot Token、Webhook URL  │     ││
│  │     └──────────────────────────────┘     ││
│  └──────────────────────────────────────────┘│
└──────────────────────────────────────────────┘
```

### 1.5 回调 URL 的自动生成逻辑

```typescript
function getCallbackUrl(platform: string): string {
  const origin = window.location.origin;
  const paths: Record<string, string> = {
    qq: `${origin}/api/platform/qq/message`,
    telegram: `${origin}/api/platform/telegram/message`,
    miniapp: `${origin}/api/platform/miniapp/message`,
  };
  return paths[platform] || '';
}
```

## 2. 改造策略（分步实施，不阻塞上线）

### 2.1 第一步：重命名 + 通用化改造（P1，建议上线后做）

| 步骤 | 内容 | 风险 |
|------|------|:---:|
| 1 | 复制 `AdminQqAssistantView.vue` → `AdminPlatformTargetView.vue` | 低 |

| 3 | 提取平台特定配置为子组件（`QqConfigForm.vue`、`TelegramConfigForm.vue`） | 中 |
| 4 | 添加平台筛选标签（QQ / Telegram / 全部） | 低 |
| 5 | 更新路由和 i18n 键名 | 低 |

## 3. 选项对比

### 选项 A：通用化改造（推荐）

| 维度 | 评价 |
|------|------|
| 工作量 | 1-2 人日（改造现有 626 行，不是重写） |
| 风险 | 中（需重构当前 QQ 功能，改后需回归测试） |
| 收益 | 接入新平台时零前端成本（只需写 80 行的配置表单） |
| 架构对齐 | 与后端 `platform_targets` 通用表对齐 |
| 代码复用 | 避免未来重复写 600 行 |

### 选项 B：保持现状，需要时再手工加

| 维度 | 评价 |
|------|------|
| 工作量 | 0（现成的） |
| 风险 | 低 |
| 收益 | 低（每次接入新平台都重写一遍 600 行页面） |
| 架构对齐 | 不对齐 |

### 选项 C：保持 QQ 专用，加一个 Telegram 专用页面

| 维度 | 评价 |
|------|------|
| 工作量 | 中（复制+修改，约 400 行重复代码） |
| 风险 | 中（两套代码，修改时需同步更新） |
| 收益 | 极低，代码重复，维护成本线性增长 |

**推荐选项 A**：通用化改造。后端已是通用设计，前端不通用会导致"后端写一次，前端写 N 次"的反模式。

## 4. 上线前的建议（不做改造，只做最小调整）

考虑到当前 NapCatQQ 不可用，且上线前不宜做大规模重构，建议：

| 操作 | 原因 |
|------|------|
| 当前 `community_feature_enabled` 保持 `true` | Telegram 平台可能仍可用，不关闭整个社群功能 |
| 不做改造，上线后 P1 再做通用化 | 避免上线前引入风险 |
| 如果确实没有 Telegram 需求，也可以下线 | 菜单入口可见但配置不可用，影响不大 |
