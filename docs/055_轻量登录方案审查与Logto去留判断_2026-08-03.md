# 055 轻量登录方案审查与 Logto 去留判断

> 日期：2026-08-03
> 目标：在不引入复杂 SSO / RBAC 的前提下，评估“Better Auth + Google 登录 + Turnstile”是否适合 cf-lottery 的参与端。
> 结论先行：**Better Auth 可用，但它只能解决登录与会话，不会自动解决公平性；Logto 不应立即删除，但最终应收敛为单一认证方案。**

---

## 一、问题边界

本次只讨论参与端体验，不讨论企业级身份平台。

要解决的是：
- 用户不想再被邮箱验证码打断。
- 不能退回到纯游客模式，否则容易批量刷单。
- 仍要保留“同一身份只参与一次”的公平约束。
- 不引入复杂 RBAC / SSO / 多组织管理。

因此，方案核心不是“换一个更大的身份平台”，而是：
- 用更轻的登录方式替代邮箱验证码前置；
- 用 Turnstile、限流、唯一性约束、领奖二次校验兜住公平性。

---

## 二、对 Logto 去留的判断

### 2.1 现在不能立刻删

当前仓库里 Logto 已经深入到多处：
- `frontend/src/main.ts`
- `frontend/src/App.vue`
- `frontend/src/views/AdminLoginView.vue`
- `frontend/src/views/LotteryView.vue`
- `src/lib/logto-auth.ts`
- `src/routes/auth.ts` 的 `/logto-exchange`
- 多个测试与文档

如果现在直接删，会同时打断：
- 管理端登录回调
- 参与页的 Logto 自动登录路径
- 自签 JWT 交换链路
- 相关测试基线

### 2.2 最终应删，但要等替代方案落地

如果最终采用 Better Auth 作为唯一登录基座，那么 Logto 这套适配应当删除，避免双认证源并存。

建议的删除条件：
1. Better Auth 登录链路已在参与端跑通。
2. 管理端或参与端不再依赖 `/api/auth/logto-exchange`。
3. `@logto/vue`、`src/lib/logto-auth.ts`、Logto 环境变量、Logto 回调逻辑都已替换。
4. 经过一轮真实活动验证后，没有回退需求。

结论：
- **短期：保留 Logto 作为回退，不要先删。**
- **长期：若 Better Auth 方案稳定，Logto 应彻底移除。**

---

## 三、Better Auth 是否适合

### 3.1 官方定位

Better Auth 官方把自己描述为 TypeScript 的认证/授权框架，不是必须依赖的托管登录服务。它支持自托管，也提供可选的 managed infrastructure。

官方信息：
- 开源框架，MIT 许可，代码可自托管。
- 另有 Infrastructure 页面，属于可选付费服务。

### 3.2 费用判断

结论分两层：

1. **框架本身**
   - 开源
   - MIT license
   - 自己部署，不需要按用户收费

2. **官方托管基础设施**
   - 有单独的 pricing 页面
   - 当前公开价格为 Starter Free、Pro $20/month、Enterprise Custom
   - 这部分是可选，不是框架本体必须开销

因此：
- 如果我们自托管 Better Auth，**软件层面不必付费**。
- 如果要买官方 managed infrastructure，**那就是额外付费**。

---

## 四、Better Auth 支持哪些常规登录方式

官方文档明确支持：

- Email and password
- Social provider：Google、GitHub、Apple 等
- OAuth / OpenID Connect 通用接入
- 插件扩展：username、magic link、passkey、email-otp、phone-number、anonymous、one tap 等

对本项目真正有价值的只有：
- Google 登录
- Google One Tap
- Passkey（可选）
- 账号链接能力（用于后续增强）

不建议作为主流程的：
- 邮箱验证码
- Magic Link
- Phone OTP
- Anonymous

原因很直接：
- 这些方式要么摩擦仍高，要么依旧绕不开验证码，要么不能作为公平抽奖身份。

## 五、Google 接入难度

### 5.1 难度判断

结论：**中等难度，不是高难度，但也绝不是“装个包就完”**。

主要工作不在代码，而在 Google Cloud 配置。

### 5.2 需要做的事

Google 官方要求你至少完成：
- 创建 Google Cloud 项目
- 配置 OAuth consent screen
- 创建 Web application OAuth client
- 配置 Authorized JavaScript origins
- 配置 Authorized redirect URIs
- 准备 support email、隐私政策、品牌信息

如果用 Google One Tap，还要额外注意：
- `baseURL` 配置正确，否则容易 `redirect_uri_mismatch`
- 站点 origin 必须配置准确
- 生产环境可能涉及品牌验证或审核

### 5.3 实际坑点

常见坑主要有：
- 回调地址和线上域名不一致
- `baseURL` 配错导致 redirect mismatch
- 测试模式下用户访问受限
- OAuth consent screen 没配完整
- 账号链接策略没想清楚，容易出现“同一邮箱多个身份”的合并问题
- 前端跨域 cookie / credentials 配置漏掉

这类坑不是代码难，而是配置多、链路长、容易漏项。

## 六、对抽奖场景是否满足

### 6.1 满足的部分

Better Auth 可以很好地覆盖：
- 用户端快速登录
- 同一用户身份识别
- 会话保持
- 登录后直接参与活动
- 结果查询免验证码

### 6.2 不满足的部分

Better Auth **不能单独保证公平性**：
- 一个用户可以创建多个 Google 账号
- 一个设备可以切多个账号
- 光有登录，并不能阻止批量刷单

所以必须配套：
- Turnstile
- IP / 身份限流
- 同身份唯一参与
- 高价值领奖二次校验

### 6.3 最合适的身份策略

不要做纯游客参与，也不要做邮箱验证码强前置。

推荐：
- 普通参与：Google / One Tap + Turnstile
- 领奖阶段：必要时补邮箱或手机号
- 高价值奖品：再加人工或二次验证

---

## 七、实施建议

### 7.1 推荐路线

1. 先保留 Logto，不要立刻删。
2. 新增 Better Auth 参与端链路，先做 Google / One Tap。
3. 把参与身份切到 `user_id` 或受控 guest session。
4. 保留 Turnstile 和 DB 限流。
5. 实际活动验证稳定后，再移除 Logto 旧链路。

### 7.2 不建议的路线

- 继续加 Logto 功能
- 做完整 SSO / RBAC
- 用纯游客模式替代验证码
- 把邮箱验证码继续作为所有用户的唯一入口

---

## 八、结论

### 结论一
Better Auth 适合当前项目，但只适合作为轻量登录基座，不适合作为重型身份平台。

### 结论二
它是开源自托管框架，不是必须付费的官方托管服务；官方 managed infrastructure 才收费。

### 结论三
Google 登录接入难度中等，主要难点是 Google Cloud 配置和生产验证，不是库本身。

### 结论四
Logto **不应立即删除**，但如果 Better Auth 方案上线并稳定，最终应彻底移除，避免双轨维护。
