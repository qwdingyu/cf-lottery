## 〇、瑞士军刀约束（本文一切建议的边界）

本项目定位是**多租户、可白标、可嵌入的活动引擎**，抽奖是第一种玩法，不是唯一玩法。前端改造必须服从 007 与 AGENTS 的「小而美」铁律：

| 原则 | 含义 | 对前端的硬约束 |
|------|------|----------------|
| **闭环优先** | 只做能走通「创建 → 分享 → 参与 → 结果 → 复盘」的体验 | 禁止为了「好看」加半截功能 |
| **少而精** | 瑞士军刀是多工具折叠，不是工具箱堆满 | 不新增玩法皮肤；先修主路径 |
| **渐进披露** | 新手看到 3 步；专家才看到高级项 | 导流/裂变/CTA 不得与核心字段同级压迫 |
| **诚实反馈** | 动画不决定结果；文案不夸大 | 禁止假中奖展示；禁止假 Demo 按钮 |
| **可增量** | 每次改动能独立上线、可回滚 | 不重写整站设计系统；不引入重型 UI 框架 |
| **不重复造轮子** | 沿用现有 Token、Admin 共享样式、GameRegistry | 扩展协议，不另起炉灶 |

**本文明确不做（反模式）：**

- 不做完整 Design System 大重构、不引入 Ant Design / Element 全家桶  
- 不做活动广场、不做 C 端社区、不做营销自动化 UI  
- 不把「参与资格」重新耦合进「游戏类型」（012b 已否决，代码已解耦，禁止回退）  
- 不承诺未验证的「覆盖 90% / 3 分钟」——可把 TTV 当目标，用路径步数验收，不当广告口号写死

## 一、执行摘要

### 1.1 一句话结论

> **工程与领域建模偏强；面向「第一次用的运营者」和「点开链接就想参与」的用户，前端仍偏内部工具。**  
> 最优解不是加功能，而是：**收敛信息架构、诚实结果反馈、把复杂度藏进模板与高级折叠**——用轻量改动兑现「小而美」。

### 1.2 分项评分（10 分制，对照行业同类 SaaS / 活动工具）

| 维度 | 分 | 说明 |
|------|:--:|------|
| 产品定位与信息架构 | **7.5** | 011 Option C（SaaS 首页 + 深链活动页）正确，实现基本对齐 |
| 设计 Token / Admin 中台 | **7.0** | `base.css` / `admin.css` 有规约、有密度、有 a11y 局部实践 |
| L2 创建 → 发布体验 | **4.5** | 能力全、路径长；与「3 分钟」承诺落差大（046b） |
| L1 参与页体验 | **5.0** | 游戏有壳；信任感、状态机、移动沉浸不足 |
| 落地页增长与信任 | **4.0** | 文案强，证据弱；次 CTA 行为不诚实 |
| 无障碍 / 移动端 | **5.5** | Admin 好于公开页；游戏层参差 |

### 1.3 核心矛盾（必须先承认）

后端与领域已按活动引擎生长：`participation_mode` / `experience_type` / `result_mode` 解耦、发布门禁、裂变与 CTA 配置齐全。  

前端仍大量用 **「大表单 + 大列表 + 多 Modal + 动画壳」** 承载，没有把复杂度藏进正确的交互范式。  

**结果：** 能力越多，第一次使用的认知负担越重——这是瑞士军刀最忌讳的「刃口朝外」。

### 1.4 只做三件事（最高 ROI，且轻量）

若资源只够三件事，**按此顺序**，与「最优轻量方案」一致：

1. **公开单活动页**：深链即沉浸；状态机文案；单一主 CTA（拆/收敛 `LotteryView` 职责，不重写玩法）。  
2. **创建路径**：模板可发布草稿 + 高级配置默认折叠 + 列表操作收敛（不重做整页后台）。  
3. **游戏语义诚实化（分层）**：**先改文案/状态**（提交中 vs 抽奖中），禁止未确认奖品展示；**仅在 `result_mode=instant` 且有服务端结果时**再做停扇对齐。禁止把「定时/手动开奖」的 join 动画误改成「对准中奖扇区」。

## 三、三类用户路径审查

### 3.1 访客 / 潜在客户（`LandingView`）

**定位（011 已决，正确）：** 首页面向**运营者**，不是参与者广场。Option C = SaaS 工具首页。

#### 亮点（保持）

- 信息骨架合格：Hero → 三步 → 模板 → 能力 → 场景 → CTA  
- 文案产品感较好（「选模板 → 设规则 → 看效果」）  
- 响应式有基础断点  

#### 问题（按瑞士军刀优先级）

| 级别 | 问题 | 证据 | 为什么违反小而美 |
|------|------|------|------------------|
| **P0** | 次 CTA「看看别人怎么玩的」与主 CTA 同指 `/admin/register` | `LandingView.vue` Hero 双按钮；i18n `landing.viewDemo` | **不诚实** = 信任事故；瑞士军刀靠可信，不靠漏斗话术 |
| **P1** | 无真实可点 Demo / 截图 / 录屏 | 模板区为 CSS 装饰小图 | 无法验证价值 → 注册转化靠猜 |
| **P2** | 能力图标用数字 1–6；缺 Free 边界与案例 | 模板与 capability 区 | 观感像未完成落地页，非必须重设计 |

#### 轻量最优改法（禁止大改营销站）

1. **P0（半日级）**：次按钮改为打开**固定 Demo 活动** ` /lottery/<demo-slug> `（只读或沙箱租户一条活动），或改为锚点「#how-it-works」。**禁止**再链到注册。  
2. **P1（1 日级）**：用一张真实活动页截图或 15s 录屏替换 Hero 空区；不必做完整品牌站。  
3. **P2**：能力区改用现有 Emoji 或单色 SVG 即可，不引入图标库也可接受；一行 Free 额度说明与真实套餐一致。  

**明确不做：** 独立营销站、多页官网、价格计算器、客户 Logo 墙（无真实客户前不硬编）。

### 3.2 L2 运营者（注册 → Onboarding → Admin）

#### 亮点（保持，属瑞士军刀正确资产）

| 能力 | 位置 / 信号 | 评价 |
|------|-------------|------|
| 无租户 → Onboarding 闭环 | 路由守卫 + `OnboardingView` | 正确，勿破坏 |
| 运营台空态 + 待办 | `AdminDashboardView` | 下一最优动作清晰 |
| 时间预设 5m–7d | 创建表单 | 高价值、轻量 |
| 发布前服务端门禁 | 发布检查 + Toast | **稳**的核心，优于堆 UI |
| 复制链接 / 二维码 / 海报入口 | 列表操作 | 传播闭环需要，但应收敛展示 |
| Admin 共享样式 + Modal 焦点陷阱 + Toast `aria-live` | `admin.css` / `AdminModal` / `ToastContainer` | B 端工程素养，保留 |

#### 断点（046b 仍成立，代码未充分兑现）

**断点 A — 创建仍是「专家配置台」**

- 单 Modal 长表单：基础 / 时间 / 模式 / 导流 / 裂变 / CTA / 问卷配置等同屏或长滚动。  
- 模板 `applyTemplate` 主要填 kind / experience / mode 等，**仍非「一键可发布草稿」**。  
- 奖品链路与活动编辑仍易形成「跳出 → 奖品页 → 回来」循环（046b 断点 1）。  

**断点 B — 列表操作认知过载**

单行可堆：复制链接、公开页、二维码、海报、数据、复制活动、编辑、发布、开奖、暂停、显示/隐藏、名单、恢复、重试邮件、取消、删除……  

行业最佳实践（且轻量）：**1 个主操作 + 2 个高频 + `⋯` 菜单**；按 `status` 过滤可见动作。

**断点 C — 体验类型 13 项下拉**

领域正确、对新手是术语墙。瑞士军刀做法：**模板锁定默认体验**；高级里再改，选项用中文名而非内部 enum 堆砌。

**断点 D — 与对外话术落差**

文案「3 分钟」；实测路径仍约 8–12 步（046b）。应用**步数/分钟验收**，而不是继续在 Landing 加码承诺。

#### 轻量最优改法（增量，不重写 Admin）

| 阶段 | 改动 | 不做 |
|------|------|------|
| **P0** | ① 导流 / 裂变 / CTA **默认折叠**为「高级配置」一个区块 ② 列表主按钮保留「复制链接 + 打开/编辑」；其余进 `⋯` ③ 体验类型：模板带入后高级才展示完整列表 | 不上完整 Wizard 框架库 |
| **P1** | ① 模板应用时：默认时间 +（抽奖）快速奖品/manual 免码策略与发布门禁对齐 ② 创建改为**页内 3～4 步**（可用现有 Modal 内 step state，不必新路由） ③ 可选：简易「预览公开页」新窗口 | 不上右侧实时预览引擎、不上独立活动详情巨页（可 P2 再拆路由） |
| **P2** | 活动详情轻页（概览 / 配置 / 参与者 / 结果 Tab）从 `AdminLotteryView` **抽离子组件**，先拆文件再美化 | 禁止一次性 3000 行重写 |

**验收（瑞士军刀 TTV）：**

- 新租户：**选「福利抽奖」模板 → 改标题 → 一键时间预设 → 快速奖品或跳过码池策略 → 通过发布检查 → 复制链接**，目标 **≤ 5 次关键点击、≤ 3 分钟**（可计时验收，不写进对外绝对承诺直至达标）。

### 3.3 L1 参与者（`/lottery/:slug`）

#### 亮点（保持）

- 深链单活动意图存在（`isDeepLinked`）  
- `GameRegistry` 可插拔，与 `experience_type` 解耦（012b 要求已落地）  
- 参与成功后裂变分享、中/未中 CTA、结果查询路径有设计  
- 身份：open 邮箱码 / registered / Logto 分支完整  

#### 结构性问题

**1. 一页混用「广场」与「单活动」（与 011 冲突）**

- 深链仍提供「返回全部活动」  
- 无 slug 的 `/lottery` 像活动广场  
- SaaS 正确心智：**运营者分享单链接 → 参与者只见该活动**  

轻量解法：深链模式隐藏「回全部」与多卡片列表；`/lottery` 无 slug 时改为引导「请使用活动链接」或仅「我的记录」（登录后），**不做广场运营**。

**2. 主路径摩擦**

展开 → 游戏 → 再参与/登录 → 验证码 → 成功弹窗偏「参与成功」而非结果语义。  

轻量目标路径：

```text
打开 slug → 看见活动名/奖品/状态
  →（需身份则）一次验证
  → 一次主 CTA
  → 动画（可选）
  → 明确：已参与待开奖 | 即时结果 | 已中/未中 + 下一步
```

**3. 游戏层信任风险（体验 P0；须按组件区分事实，禁止一刀切误判）**

##### 3.1 `WheelGame` 事实核对（2026-08-03 代码复审，**纠正初版不准确表述**）

**真实实现链路：**

```text
点击中心按钮
  → spinning=true，按钮文案曾为「抽奖中」
  → emit('play')（与动画同时）
  → 父组件 handleJoin → 后端 joinDraw
  → 客户端随机旋转约 4s（targetAngle 与中奖无关）
  → 结果弹窗：参与成功 / 裂变等（不展示「指针指向的奖品即你的奖」）
```

| 判断 | 结论 |
|------|------|
| 转盘是否用动画**展示/伪造中奖奖品**？ | **否**。扇区上的奖品名是奖池陈列；停止角随机，**没有**「对准真实中奖扇区」的结果演绎 |
| 数据是否诚实？ | **是**。中奖由后端开奖/结果接口决定，不由转盘决定 |
| 体验问题是什么？ | **语义暗示错误**：文案「开始抽奖 / 抽奖中」让用户以为「正在决定结果」，实际是「正在提交参与」 |

**因此：初版「不对准真实扇区 → 转盘是假的」不准确。**  
更准确的问题定义是：**参与动效被说成了开奖动效**。

**轻量修正（最优、低风险，禁止为此重做停扇算法）：**

1. 空闲按钮：**「参与抽奖」**（或「参与」），不写「开始抽奖」  
2. 动画 / `loading` 期间：**「提交中」**，不写「抽奖中」  
3. 结果弹窗：继续告知**参与/待开奖/结果**状态（按 `result_mode` 分支，见下）  
4. **不要**在定时/手动开奖活动上强行「对准真实扇区」——join 时往往**尚无中奖扇区可对**；强行对接会引入错误协议与灾难性返工  

仅当未来 `result_mode=instant` 且 API 返回可映射的奖项索引时，再评估停扇对齐（独立 P1/P2，单独立项）。

##### 3.2 其他组件（与转盘问题不同，勿混写）

| 组件 | 问题 | 用户感知 |
|------|------|----------|
| `ScratchGame` | 涂层下固定「已参与」，刮完再点参与 | 因果可能颠倒；需单独轻量理顺 |
| `CardGame` | 先翻牌再参与，背面统一礼物 | 玩具感；非「伪造中奖名单」 |
| `GameResultModal` | 以 join success + 裂变为主 | 定时开奖用户可能期待「中了什么/何时开奖」——属**文案/状态分支**，不是转盘造假 |

**行业铁律（必须写入实现约束）：**

> 动画只制造期待或表达「提交中」；**中奖与否、奖品、码**只由后端状态机决定。  
> UI 必须诚实表达：`可参与 | 提交中 | 已参与待开奖 | 开奖中 | 已中奖 | 未中奖(+安慰) | 已结束`。  
> **禁止**把「未对准扇区」误判为数据造假；也**禁止**在无即时结果时用停扇假装已开奖。

#### 轻量最优改法

| 优先级 | 改动 | 说明 |
|--------|------|------|
| **P0** | 深链 UI 收敛为单活动沉浸；主 CTA 随状态变文案 | 少改 API，多改模板条件渲染 |
| **P0** | **`WheelGame` 文案语义**：参与抽奖 → 提交中；**不改**旋转算法与 API | 最小 diff，可回滚 |
| **P0** | 刮卡/翻牌等：**禁止在 API 确认前把某奖品名宣称为「你的结果」** | 与转盘「仅语义」问题分开治理 |
| **P0** | `GameResultModal` 按 `result_mode` 分支文案：即时开奖 vs 定时/手动待开奖 | 不新做结果中心 |
| **P1+** | 仅 instant 模式评估 `targetIndex` 停扇 | **非**当前 join 主路径必做；无结果索引不动动画内核 |
| **P1** | 移动端：转盘宽度随屏、主按钮 ≥ 44px、规则折叠 | 用现有 CSS 变量 |
| **P2** | 租户 Logo/主色轻量白标（有 brand 字段再接） | 无数据不提前做主题引擎 |

**明确不做：** 新游戏品类、音效包、3D、直播开奖大屏（除非单客户付费定制）。

## 四、界面与设计系统（轻量视角）

### 4.1 已合格资产（勿推倒）

- `base.css`：色彩、圆角、阴影、时长、Admin 密度、断点  
- `admin.css`：工具栏 / 表格 / sticky / `prefers-reduced-motion` 等 primitives 唯一源  
- 暗色 `color-scheme`、表头不透字等生产踩坑沉淀  

### 4.2 差距与轻量对策

| 项 | 现状 | 轻量对策 | 重型反模式 |
|----|------|----------|------------|
| 图标 | Emoji 为主 | 保留 Emoji 作情绪；关键操作用文字按钮即可 | 上整套图标库重构 |
| 公开页品牌 | 平台工具感 | 单活动页加大标题与主色按钮即可 | 独立 C 端设计语言 |
| 营销 vs 工具 | 同套暗色 | Landing 可局部提亮，不强制双主题系统 | 双 Design Token 工程 |
| 组件重复 | 页内 form/modal | 抽 2～3 个共享（已有 AdminModal/Toast） | 自研组件库 |
| 巨型 SFC | 3k / 1.8k 行 | **按职责拆文件**（列表/表单/公开页） | 大爆炸重写 |

**视觉策略一句话：**

## 八、决策记录（ADR 风格，便于后续 Agent 遵守）

### ADR-055a-1：公开深链以单活动为唯一心智

- **决策：** `/lottery/:slug` 不提供活动广场导航；无 slug 不承担发现流量。  
- **原因：** 011 Option C；运营者传播模型是分享单链。  
- **后果：** `LotteryView` 深链分支简化；「我的记录」可次级入口存在。  

### ADR-055a-2：游戏为视觉层；语义先于停扇算法

- **决策：**  
  1. Game 不得在确认结果前把某奖品名宣称为「你的中奖结果」。  
  2. **`WheelGame` 当前 join 路径：随机旋转 = 参与动效，不是开奖演绎**；P0 只校正按钮/状态文案（参与抽奖 → 提交中 → 结果弹窗状态）。  
  3. **禁止**在尚无服务端奖项索引时实现「对准真实扇区」。  
  4. 仅 `result_mode=instant` 且 API 提供可映射结果时，才考虑 `play → API → animate(targetIndex)`。  
- **原因：** 信任与合规；避免把「语义问题」误升级为「重做抽奖动画协议」造成灾难。  
- **后果：** 转盘可继续随机旋转作氛围；文案必须说「提交/参与」而非「正在开奖决定」。  

### ADR-055a-3：配置渐进披露，不删高级能力

- **决策：** 导流/裂变/CTA 等保留，**默认折叠**；模板锁定常见 experience。  
- **原因：** 瑞士军刀折叠刀刃，而非锯掉刀刃。  
- **后果：** 专家仍可配置；新手 TTV 下降。  

### ADR-055a-4：不引入重型前端体系

- **决策：** 继续 Vue SFC + 现有 CSS Token；改造以拆分与状态机文案为主。  
- **原因：** 007 / 免费层与维护成本。  
- **后果：** 禁止「先上组件库再改体验」式大迁徙。  

### ADR-055a-5：对外话术与验收挂钩

- **决策：** 「3 分钟」仅在 P1 验收达标后作为可宣传语句；此前 Landing 可用「选模板即可开始」等无绝对时长承诺。  
- **原因：** 012b 禁止无数据承诺；诚实优于漏斗。

## 十、总结

1. **方向对：** SaaS 首页 + 深链活动 + 可插拔体验 + 发布门禁，符合活动引擎与瑞士军刀。  
2. **债在体验层：** 同屏配置过多、列表动作过多、参与页不够沉浸、**游戏语义/部分组件反馈**需分层治理、Landing 次 CTA 不诚实。  
3. **最优方案不是做大：** 折叠、收敛、深链单页、**文案级诚实化优先于动画协议重做**、模板可发布——全部可增量、可验收、不破坏后端领域模型。  
4. **执行顺序：** P0 止血 → P1 TTV → P2 拆分与白标；**任何时候不优先加新玩法皮肤。**  

> 瑞士军刀的锋利，来自**每一刃都收得干净、拔得出、用得上**；  
> 前端此刻该做的，是把已经做厚的刃**折回刀柄里**，让第一次打开的人只看见三步。
