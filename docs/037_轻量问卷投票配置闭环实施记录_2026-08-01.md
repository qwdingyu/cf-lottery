# 轻量问卷投票配置闭环实施记录

> 文档编号：037  
> 日期：2026-08-01  
> 范围：`activity_config`、问卷/投票发布闸门、公开提交校验、投票统计口径

## 一、顶层结论

本次没有继续堆玩法，而是把已经进入模板体系的问卷和投票补成最小可发布闭环。

抽奖、接龙、问卷、投票都仍然归属于“活动引擎”：租户配置活动规则，公开端收集参与，后端按规则校验，后台能够查看和复盘。问卷和投票不新建独立 `forms` / `votes` 重系统，统一复用 `lottery_draws.activity_config` 和 `activity_submissions`。

## 二、实施边界

已经完成：

1. `lottery_draws.activity_config`：版本化 JSON 配置字段。
2. `src/lib/activity-config.ts`：发布预检和公开提交共用的后端规则源。
3. 问卷配置：支持 `text/email/phone/textarea/select/radio/checkbox`。
4. 投票配置：支持固定选项、单选投票。
5. 公开提交：问卷答案和投票选项与 entry 同事务写入 `activity_submissions`。
6. 投票统计：按 `activity_submissions.payload_json.optionId` 聚合，并用 `activity_config.options` 映射展示名。
7. 管理端：创建/编辑/复制/模板入口会保存玩法配置。
8. 公开端：动态渲染问卷字段和投票选项，提交时携带 payload。

没有做：

1. 不做完整表单平台，不做拖拽式表单设计器。
2. 不做投票多选、排名投票、匿名投票结果公开等扩展规则。
3. 不做大规模 BI，只保留后台低频统计口径。
4. 不把投票选项塞入 `lottery_entries.identity_value`。

## 三、免费层约束下的设计原因

Cloudflare Workers Free + Turso/libSQL Free 的核心风险不是单个 JSON 字段本身，而是热路径上的大对象解析、全表扫描、频繁统计和额外写放大。

因此本次方案采用：

1. 单活动配置 JSON 有大小限制。
2. 问卷字段、字段选项、投票选项都有数量上限。
3. 公开提交只做当前活动单行配置解析和白名单校验。
4. 提交只新增一条 `activity_submissions` 写入，这是参与完成的一部分，不额外拆多表。
5. 投票 tally 是后台低频查询，允许数据库侧按当前活动聚合；不放在公开参与热路径。

## 四、关键风险修正

之前最危险的问题是投票统计按 `lottery_entries.identity_value` 分组。公开参与时 `identity_value` 是邮箱，继续这样上线会统计出“每个邮箱一票”，而不是“每个选项得票”。

本次已修正为：

```text
activity_config.options       定义合法选项
public submission.optionId    用户选择
activity_submissions.payload  持久化选择
admin tally                   按 payload.optionId 聚合
```

## 五、后续 TODO

1. 后台提交记录 UI：把 `payload_json` 按配置展示成人可读表格。
2. CSV 导出：分页导出 submissions，限制单次行数，避免 Worker 内存和 CPU 风险。
3. 投票结果展示：后台图表和公开结果页需单独设计公开开关。
4. E2E 测试：创建问卷/投票、发布、公开提交、后台查看闭环。
5. 配置版本迁移：如果未来扩展 `ActivityConfigV2`，必须兼容读取 V1，但开发期不做无止境兼容。
