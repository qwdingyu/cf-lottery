# 生产环境踩坑记录：登录 → L3 平台入口不可见

> 日期：2026-08-02
> 环境：https://lucky.eforge.xyz（Cloudflare Workers + Turso + Vue 3 SPA）

## 问题列表

### 1. 登录/注册 500 错误："服务器内部错误"

**现象**：任何用户名登录或注册都返回 `{"ok":false,"message":"服务器内部错误"}`，前端前端无法区分具体原因。

**排查过程**：

1. 怀疑是 Turso 数据库 schema 不匹配（`email_verified` 列缺失），经 PRAGMA 检查后发现列已存在。
2. 在 login 路由添加 try-catch 后，错误变为具体消息：`Failed query: insert into email_access_codes ... UNIQUE constraint`
3. 发现是 `email_access_codes` 表的**部分唯一索引** `UNIQUE(email, draw_id) WHERE used=0` 导致重复发送验证码时冲突。

**根因**：登录/注册时发送验证码前，未将同一邮箱的旧验证码（used=0）标记为已使用。新 INSERT 的 `(email, draw_id='', used=0)` 与旧记录冲突。

**解决方案**：发送验证码前先执行 `UPDATE email_access_codes SET used=1 WHERE email=? AND draw_id='' AND used=0` 标记旧码失效。

### 2. "无租户上下文"错误

**现象**：部分用户登录后调用 `/api/admin/me` 返回 `{"ok":false,"message":"无租户上下文"}`。

**排查过程**：

1. 检查 `requireTenantMember` 中间件，发现 `if (!tenantId)` 检查失败。
2. 追溯 JWT 签发：`tenantId = member?.tenantId || ""`，当 `tenant_members` 表无记录时 tenantId 为空。
3. 数据库查询发现 20 个用户没有对应的 `tenant_members` 记录——是注册流程三连 INSERT（users → tenants → tenantMembers）非原子操作导致的孤儿记录。

**根因**：注册时创建用户和租户分三次独立 INSERT，中间任何一次失败都会产生孤儿记录（有 user 没 tenant 或没 tenant_member）。

**解决方案**：
- 短期：为 20 个孤儿用户补充 tenant + tenantMembers 记录
- 长期：`withDbTransaction()` 事务包裹三连 INSERT，保证原子性

### 3. L3 平台运营菜单入口不显示

**现象**：后端 `/me` 接口正确返回 `platformRole: "platform_owner"`，但前端 L2 管理后台侧边栏不显示"平台运营"入口。

**排查过程**：

1. 确认后端 API 返回的 `platformRole` 字段正确（curl /api/admin/me）。
2. 检查前端 AdminLayout.vue，发现平台入口代码存在但 `isPlatformMember` 始终为 `false`。
3. 追踪 `isPlatformMember` 来源：来自 `useAdminAuth()` composable 的 `computed(() => !!platformRole.value)`。
4. 发现 `useAdminAuth()` 每次调用创建**独立的 ref 实例**——AdminLoginView 中的 `setPlatformRole()` 只更新了该实例的 ref，AdminLayout 调用 `useAdminAuth()` 获得的是一个**新实例**，其 `platformRole` ref 未初始化。

**根因**：`useAdminAuth()` 不是共享状态管理，每个组件调用获取独立的响应式引用。登录页写入的 `platformRole` 不会传播到布局页。

**解决方案**：AdminLayout 不使用 composable 的 `isPlatformMember`，改为直接调用 `readPlatformRole()` 从 localStorage 读取。`readPlatformRole()` 是纯函数，不依赖 ref 实例，每次读取都是最新值。

### 4. 系统配置参数归属混乱

**现象**：活动类型（activityKind）、互动体验（experienceType）、名额策略（allocationPolicy）被折叠到"高级设置"面板中，SaaS 用户无法直接修改。

**分析**：这三个参数本应是 L2 活动组织者的自主权，模板提供默认值但不限制选择。L3 平台通过 `enabled_activity_kinds` 控制可用范围，但具体选用哪个应由 L2 决定。

**解决方案**：移除"高级设置"折叠，`activityKind` / `experienceType` / `allocationPolicy` 始终可见。

## 架构经验

### Composable 不是 Store

```javascript
// ❌ 错误理解：以为 useAdminAuth() 是共享状态
const { isPlatformMember } = useAdminAuth()  // 每次调用创建新 ref

// ✅ 正确做法：需要跨组件共享的状态用 localStorage 读写
const isPlatformMember = ref(!!readPlatformRole())  // 直接从 localStorage 读
```

### 事务必须保证原子性

```javascript
// ❌ 注册时三次独立 INSERT，任何一次失败都会产生孤儿记录
await db.insert(users).values({...});
await db.insert(tenants).values({...});
await db.insert(tenantMembers).values({...});

// ✅ 事务包裹，同成同败
await withDbTransaction(db, async (tx) => {
  await tx.insert(users).values({...});
  await tx.insert(tenants).values({...});
  await tx.insert(tenantMembers).values({...});
});
```

### 部分唯一索引的坑

```sql
-- 这个索引只约束 used=0 的行，允许同一邮箱有多条 used=1 的记录
-- 但重复发送验证码时会冲突，需要先 UPDATE 标记旧码失效
CREATE UNIQUE INDEX idx_email_code_active
  ON email_access_codes(email, draw_id)
  WHERE used = 0;
```

### 参数分层原则

| 层级 | 控制内容 | 示例 |
|------|----------|------|
| L3 平台 | "能不能做"（开关/配额/限流） | enabled_activity_kinds / plan_limits / rate_limits |
| L2 组织者 | "怎么做"（活动参数自主选择） | activityKind / experienceType / participationMode |
| 模板系统 | "最佳实践预设"（不限制选择） | 默认值由模板填入但允许组织者修改 |
