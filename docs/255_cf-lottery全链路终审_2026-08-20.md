## 二、P0 — 资金与名额：直付秒杀「重新参与」后永久无法支付，且每次泄漏 1 个名额

**验证状态：✅ 属实（代码路径 + 无测试覆盖）**

### 链路

1. pending 订单超时 → `expireOverdueOrders` 释放名额、entry 置 EXPIRED
2. 用户重新参与 → `participation.ts:255-267` 活动级 CAS `activeParticipantCount + 1` 抢回 1 个名额，`:283` 把 entry 置为 RESERVED
3. 用户再次点支付 → `payment.ts:257` `retryable = existing != null && isRetryablePaymentOrderStatus(existing.status)`，最新单是 EXPIRED/CANCELLED → 恒为 true → `:365-367` 走 `retryPaymentOrder`
4. `payment-service.ts:499-511` `armPaymentOrderForRetry` 的 CAS 条件是 `paymentStatus = EXPIRED`，而 entry 此时是 RESERVED → `rowsAffected = 0` → `:512-514` 抛 "秒杀名额已被其他用户占用"

### 后果

- 事务回滚不超卖，但 ① entry 永久停在 RESERVED，用户永远无法完成支付；② `staleReservations` 清扫会排除"拥有任何订单行"的 entry，因此该名额永久泄漏，重复操作可把库存耗尽而零收入；③ 错误文案完全误导（是自己占的名额）

### 修法

`armPaymentOrderForRetry` 的 CAS 条件放宽为 `paymentStatus IN (EXPIRED, RESERVED)`，或 `joinDraw` 的 reopened 分支不改 RESERVED 而保持 EXPIRED。二者只能选一，需同步 `payment-service.test.ts:2610-2637` —— 现有测试只用裸 SQL 模拟"重新参与"，从未再次尝试支付，所以这条路径至今零覆盖。

## 三、P1 — 安全 / 反作弊（均已实测复现）

### P1-1 registered 用户可读取他人全部券码

**验证状态：✅ 属实（代码路径 + 现有测试恰好证明该机制）**

- `public-lottery.ts:1105` `if (draw.participationMode !== "registered")` —— registered 模式跳过 JWT.email ↔ body.email 一致性校验
- `public-lottery-helpers.ts:63-82` `resolveParticipantIdentity` 对 registered 只取 `payload.sub`，完全不看 body.email
- `public-lottery.ts:1353` `const couponMatchKey = identity.identityType === "user_id" ? email : identityValue;` —— 直接用请求体 email 作为券归属键
- `:1354-1363` 券查询位于 `if (entry ...)` 守卫之外，无参与记录也能查

**实测**：任意持有效 JWT 的注册用户，body 填受害者邮箱 → HTTP 200、`joined:false`、`coupons:["VICTIM-COUPON-1"]`。限速仅 `my-result:${ip}` 10/60s。核销侧仍有 `recipientEmail === verifiedEmail` 保护，但券码本身即价值凭证（可转卖/线下使用）。

**修法**：registered 分支忽略 body.email，用 `payload.sub → users.email` 作为 couponMatchKey；并把券查询移入 entry 守卫内。

### P1-2 /public/draws/:slug/join 无邮箱验证即可参与并计入邀请

**验证状态：✅ 属实（/join 无 OTP/JWT；前端不调 /join；仅 open 模式受影响）**

- `public-lottery.ts:1654-1750`，`:1665` 仅 `isValidEmail(email)`，无 OTP、无 JWT；`:1703` 把 body.refCode 原样传入 joinDraw
- 对比 access-code：跳过发码的 bypass 受系统开关 `enable_email_verification` 严格控制（`:815-870`，注释明写"生产务必开启"）。/join 无条件绕过了这个开关
- 前端全程只调 verify-join（grep 确认），因此这是一个无人看守的并行入口；`index.ts:341` 挂载 + `:227` cors `origin:"*"` → 公网可达

**实测**：单 IP、3 个一次性邮箱 → 分享者 `joinedCount` 0→3、`spinsLeft` 1→4、`spinsTotalGranted` 1→4。默认限速 10/min/IP，换 IP 即线性放大。

**边界（不夸大）**：`joinDraw` 会拦 registered（`participation.ts:109`）、roster（`:148`）、password（`:163-168`）、invite_code（`:173`），所以仅 open 模式受影响 —— 而 open 恰是拉新活动的主力模式。

**修法**：删除该端点，或与 access-code 共用同一 `enable_email_verification` 开关 + `participationMode === "open"` 硬限制。

### P1-3 引擎奖励条件 fail-open：conditions 写成对象 → 首次邀请即发奖

**验证状态：✅ 属实（含对已安装包 v3.4.10 的实测）**

`reward-distributor.js` 的 `_meetsRewardCondition`：`if (!Array.isArray(conditions) || conditions.length === 0) return true;` —— 非数组即视为无条件，直接发放。而 cf-lottery 侧 `referral-rewards-engine.ts:57-82` 的白名单校验完全不检查 conditions，`publish-check-service.ts:704-733` 也不检查；`admin-lottery.ts:841 / :1156` 的 promotionConfig 是任意 JSON 直接 stringify / 顶层 merge，无 schema 校验。

**实测**（node -e 直调 v3.4.10）：

| 配置 | 输出 | 判定 |
|------|------|------|
| `conditions: [{field:"totalJoinedCount",operator:"GTE",value:"3"}]`，实际邀请 1 | `[]` | ✅ 正确 |
| `conditions: {field:...}`（写成对象） | `[{rewardId:"invite_3",amount:"2"}]` | 🔴 邀请 1 人即发 3 人档奖励 |
| 字段名拼错 `joinedCount` | `[]` | 🟡 静默永不发放 |

**修法**：`normalizeReferralRewardDefs` 增加 conditions 必为数组 + `field ∈ {totalJoinedCount}` + `operator ∈ {GTE,GT,LTE,LT,EQ,NE}` 白名单；发布预检对非法 conditions 报 error（现在只在"全部条目无效"时才 warning）。

### P1-4 每日免费抽奖实际额度 = count + 1，且不受 maxSpinsPerEntry 约束

**验证状态：✅ 属实，但为有意设计（注释明确说明）**

- `spin-execution.ts:205-223` 先 `spinsLeft + count`（按日 CAS），`:227` 判定 `dailyFreeClaimed` 为真时跳过本次扣减 → 当日实际可抽 `count + 1` 次
- `:200-204` 注释明确故意不更新 `spinsTotalGranted`（同签到，docs/171 §11.4.2），否则会污染 `spin-quota.ts:108` 的 `roomTotal = maxSpins - granted`
- `spin-execution.test.ts:1306-1348` 已把该语义写进断言（maxSpins=2 + dailyCount=1 → 当日 3 次），因此这是有意设计而非笔误

**代价**：`maxSpinsPerEntry` 不是单人抽奖次数硬顶。长周期活动下单人可消耗的奖品次数无上限，奖品成本不可预算。签到同理（commands.ts 只加 spinsLeft；checkin-reward.ts 的 linear/step 在无 cap 配置时无上限）。

**修法**：引入活动级"累计免费次数上限"（如 `maxFreeSpinsTotal`），或让每日免费/签到也计入一个独立的 `spinsFreeGranted` 并在发放时校验总顶。至少必须在 L2 表单上给出"预计单人最大成本"的显式提示。

## 四、incentive-engine 集成专项

### 包版本核对

源码 `/Users/dingyuwang/0-X/2-node/rbb_nodejs/incentive-engine` 与 `node_modules/@usethink/incentive-engine` 均为 3.4.10，`reward-distributor.js` 逐字节相同（diff → SAME），无版本漂移。

### 调用契约正确

`referral-rewards-engine.ts:274-279` 传 `directParent: null, ancestors: []`；UI 生成 `type:'FIXED', target:'SOURCE'`（growth-config.ts:749-759），事件 `attrs.totalJoinedCount`（:268-271）与 `condition-evaluator.js` 的 `data.attrs?.[field]` 回退一致 —— 这条主路径是对的。

### 白名单放行三类"永不发奖"的合法配置（实测确认）

| 配置 | 引擎输出 | 原因 |
|------|---------|------|
| `type:"LEVEL"` | `[]` | `chain-calculator.js` 遍历 `ancestors=[]` |
| `target:"PARENT"`（任意 type） | `[]` | `direct-calculator.js` `if (!targetNode) return null` |
| `type:"DIRECT", target:"SOURCE", rate:"50"` | `amount:"0.5"` | cf-lottery `:321` `parseInt("0.5") = 0` → `grantBonusSpin` 的 `amount <= 0` 直接 false |

`REWARD_TYPE_WHITELIST` 含 LEVEL、`REWARD_TARGET_WHITELIST` 含 PARENT（:53-54），发布预检也不拦（无对应错误码）→ 配置发布"全绿"，运行时静默零发放，且因未标记幂等而每次归因都重算重试。**建议**：白名单收窄为 `{FIXED, CUSTOM} × {SOURCE}`，其余在预检报 error。

### bonus_coupon 数量语义失效

UI 允许 `3:bonus_coupon:5`（growth-config.ts:252 校验 rewardValue 1..1000），落库 `fixedAmount:"5"`，但 `reward-exits.ts:136-232` 的 `grantBonusCoupon` 完全不读 amount，恒发 1 张；`formatReferralRewardDefsText` 回读又显示 5 → 运营看到的和实际发的永久不一致。

### docs/254「三重防超发」表述过度

`markRewardIdsGranted`（:198-215）循环内任一 record CAS 失败即 return false，已写入的标记不回滚（同事务内后续仍会被提交），依赖的是"下次归因由出口 CAS 兜底"。这不是三层独立防护，而是两层强防护 + 一层 best-effort。文档应改为"两重强防护 + 幂等标记 best-effort"。

### 码池隔离缺失

`reward-exits.ts:145-157` 选券条件仅 `tenantId + status='available'` [+ label]，无 drawId → 为活动 B 导入的券可被活动 A 发走，仅靠 label 做软隔离。`draw-execution.ts:808` 的安慰券同构。

## 五、拉新

除 P1-2 外：

- **归因时点过早**：`participation.ts:1192-1195` 在 JOIN 时 `joinedCount + 1`。直付秒杀下 join 仅是预留，未付款/超时/取消都不回滚 —— `schema.ts:791` 的 `joinedCount` 只增不减，已发出的里程碑奖励也不追回。刷单成本 = 0。
- **自邀请仅防同一身份**：`participation.ts:1155, :1185`。同人换邮箱即绕过（配合 P1-2 完全自动化）。
- **分享落地页缺租户校验**：`public-lottery-share.ts:311` 按 shareCode 单键查询，不校验 URL 里的 slug 是否属于该 share；`:313` 点击计数用 `share.clickedCount + 1` 读改写 —— 并发丢失更新，与 `participation.ts:1194` 的 `sql\+1` 正确写法自相矛盾。
- **裂变字段名三处口径不一**：`participation.ts:826-827` 优先 `extraSpinsPerInvite/maxExtraSpins`；`draw-execution.ts:198` 只读 `extraEntriesPerInvite/maxExtraEntries`；`publish-check-service.ts:754-755` 只校验后者，而 `:745` 的冲突检查却读前者 → 用前者命名可绕过数值区间校验。另 `draw-execution.ts:202` 用 truthy `viral?.enabled`，`leaderboard-rewards.ts:106` 用严格 `=== true`，"false" 字符串在两处行为相反。
- **L2 配置能力受限**：rewardId 生成规则是 `invite_${requireCount}`（growth-config.ts:750），同一邀请数无法同时配 spin + coupon（后端按 rewardId 去重会丢一种，:231-236 注释已自承）。
- **漏斗数据可被污染**：`public-lottery.ts:569-641` 的 events 端点接受任意 entryId（仅长度 ≤80）、refCode、source/medium/campaign、2KB metadata，不校验 entryId 是否属于该 draw/租户，30/min/IP → L2 转化报表可被外部写脏。
