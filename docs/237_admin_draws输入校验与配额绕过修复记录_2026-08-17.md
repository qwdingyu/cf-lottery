# admin/draws 输入校验与配额绕过修复记录

## 背景

2026 年 8 月审查发现，活动编辑接口对时间、枚举和中奖人数的输入校验不完整。特别是 `Invalid Date` 参与比较时会产生 `NaN`，导致无效结束时间可能通过校验并写入数据库，公开参与流程可能因此长期无法结束。

同时，活动复制接口如果不重新检查租户活动数配额，可能绕过创建活动时的配额限制。

## 原因

1. 使用 `new Date(value) >= new Date(other)` 直接比较，没有先确认时间戳有限。
2. PATCH 使用 `??` 合并字段，无法区分“未传字段”和“显式传 null 清空”。
3. `coerceEnum` 对非法输入静默回退到默认值，隐藏了客户端或攻击者传入的错误。
4. `winnerCount` 仅做 `Number()` 转换，`NaN`、小数和越界值没有被统一拒绝。
5. 复制接口只检查源活动存在，没有在插入副本前重新读取当前租户用量。

## 排查过程

1. 审查 `src/routes/admin-lottery.ts` 的 POST、PATCH 和 copy 路由。
2. 对照 `src/services/lottery/draws.ts` 的创建服务校验，确认创建路径已有服务层兜底。
3. 使用正式 Vitest 回归测试验证无效时间、`drawAt: null`、非法枚举、脏 `winnerCount` 和编辑状态约束。
4. 运行 TypeScript、后端全量测试和前端构建验证未引入回归。

## 解决方案

- 新增有限时间戳解析函数，所有创建和编辑时间顺序校验先解析、再比较。
- PATCH 明确采用三态语义：未传保持原值、`drawAt: null` 清空、空字符串和非法时间拒绝。
- 新增严格 `parseEnum`，显式非法枚举直接返回 400；PATCH 未传字段保持数据库原值。
- 统一校验 `winnerCount` 为整数，范围为 0 至 9999，抽奖活动至少为 1。
- 复制活动前调用 `getTenantUsage` 检查 `maxActivities`。
- 新增安全回归测试，验证拒绝请求不会污染原数据库记录。

## 建议

- 后续新增活动类型或 PATCH 字段时，必须明确字段的三态语义和状态机可编辑范围。
- 不得用 `coerceEnum` 处理来自请求体的显式字段；默认值只能用于字段未传场景。
- 时间字段禁止直接参与比较，必须经过有限时间戳解析。
- 活动创建、复制等所有新增活动入口都必须经过同一套租户配额检查。
