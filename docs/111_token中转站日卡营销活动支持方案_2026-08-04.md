# cf-lottery 对 Token 中转站 QQ 群营销活动的支持方案（修正版）

> 文档编号：111（修正版）
> 创建时间：2026-08-04，修正于 2026-08-04
> 定位：把"QQ 群拉新 + 日卡额度 + 退群惩罚"的讨论碎片，整理成正式规则，映射到 cf-lottery 现有能力，给出可落地的三阶段方案
> 修正点：**兑换码的生成、面额、有效期、核销全部由中转站管理**——cf-lottery 不碰卡本身，只做"归因 + 奖励意图 + 处罚波及名单 + 事件中枢"
> 角色：产品架构师 + 营销技术顾问
> 结论一句话：**cf-lottery 不存余额、不发兑换码、不做 QQ 机器人，它做"规则引擎 + 归因引擎 + 事件中枢"，把别人要写几千行的营销反作弊系统，变成"配一个活动 + 接两个 Webhook"。**

## 一、场景还原：运营者到底想干什么

### 1.1 讨论内容整理

| 运营诉求（原话） | 翻译成规则 |
|:----------------|:----------|
| 群满了是 200 人，缺口是 170，发完为止 | 活动目标：拉新 170 人进 QQ 群，奖励池发完即止 |
| 注册送 200，拉一个送 100 | 注册奖励 200（平台余额）；每有效拉 1 人进群，奖励 100（日卡） |
| 100 的日卡兑换 / 送兑换卡 | 奖励是"日卡"——由**中转站生成兑换码**，面额 100 刀，可兑换成平台额度 |
| 必须得过期的 / 有效期七天兑换，过期作废 | **兑换码有效期由中转站决定并管理**（本修正版的核心边界） |
| 每天只能兑换 2 张 | 每人每天最多领/兑 2 张日卡（防屯屯鼠） |
| 每天只能兑换 300 次，总池子，也就是 150 人兑换 | 全平台每日奖励发放总量 300 次（2 张/人 → 约 150 人） |
| 退群的直接扣余额 | 退群事件 → 中转站作废其名下兑换码 + 扣余额 |
| 退出 QQ 的那家就会扣日卡 | 同上：退群者的日卡被收回 |
| 邀请的人额度也清 | 连带处罚：退群者的**邀请人**额度也被清 |
| 你不能薅了就跑，否则额度直接清 | 防羊毛核心：领了卡就跑 = 额度清零 |
| 他是机器人，退群立马监控 | QQ 群机器人实时检测退群 → 上报触发处罚 |

### 1.2 一句话本质

一套 **"规则驱动的激励发放 + 反作弊"** 系统，和 cf-lottery 的核心定位（规则驱动的参与与结果分配）**完全同构**。区别只是"结果"从奖品变成了**奖励意图 + 处罚指令**。

### 1.3 关键认知：两个系统，各管一半

```
┌──────────────────────────────┐      ┌──────────────────────────────┐
│  cf-lottery（活动引擎）        │      │  Token 中转站（账务+凭证）      │
│                              │      │                              │
│  · 归因：谁拉谁、拉了几个       │      │  · 兑换码生成/面额/有效期      │
│  · 规则：奖励条件、处罚波及名单   │◄────►│  · 余额账务、核销             │
│  · 限流：每日奖励发放配额        │ Webhook │  · 用户额度发放/扣减          │
│  · 事件中枢：入口(上报)+出口(通知)│      │  · QQ 群机器人（可自己接）     │
│  · 看板：拉新漏斗、处罚记录      │      │                              │
└──────────────────────────────┘      └──────────────────────────────┘
```

**为什么这样分？**
- 兑换码本质是"资金凭证"，跟余额、核销是同一套账务体系——**必须在中转站**，否则两边都要维护券状态，必然对不上账
- 邀请关系、奖励规则、处罚波及范围是"营销规则"——**在 cf-lottery**，因为这是活动引擎的本职，且多租户可复用
- cf-lottery 通过 Webhook 传达**奖励意图**和**处罚指令**，中转站负责**执行**，回传**结果**（可选）形成对账闭环

## 二、身份绑定：三键对齐（落地前置问题）

> 这是售前和联调阶段**必问的第一个问题**。如果三键不对齐，整个归因-奖励-处罚链路全断。

### 2.1 三键对齐表

| 键 | 来源方 | 格式 | 作用 |
|:---|:-------|:-----|:-----|
| **QQ 号** | QQ 群 / 机器人 | 数字字符串 | 退群检测的触发标识 |
| **中转站账号/邮箱** | 中转站账务系统 | 邮箱/用户名 | 兑换码发放目标、扣余额目标 |
| **lottery identityValue** | cf-lottery | email（默认）/ 自定义 | 活动参与、归因、黑名单 |

### 2.2 两种可行方案

| 方案 | 做法 | 优点 | 代价 |
|:-----|:-----|:-----|:-----|
| **A（推荐）中转站上报时直接带 account** | 退群上报 payload 同时带 `qq` + `account`；参与时 identityValue 用中转站账号 | 无额外映射表 | 中转站侧负责维护 QQ↔账号绑定 |
| **B cf-lottery 存映射** | 新增表 `identity_mappings` 存 QQ↔账号↔entryId | cf-lottery 内闭环 | 新表 + 数据同步复杂度 |

**建议选方案 A**：中转站自己维护 QQ↔账号的绑定（本就是他们账务系统的一部分），cf-lottery 只以中转站账号为唯一身份锚点。退群上报时带 account 字段，不想维护绑定的中转站可以直接传相同的值（QQ=account）。

### 2.3 售前 Checklist

- [ ] 确认对方系统的"用户唯一标识"是什么（邮箱 / 用户名 / 手机号）
- [ ] 确认 QQ 群机器人能否在退群事件中拿到"QQ + 账号"两个字段
- [ ] 确认参与时的 identityValue 使用中转站账号（一致）
- [ ] 确认同一账号可参与多次活动（不同 identityValue 会导致归因断裂）

## 三、修正后的职责划分矩阵

| 环节 | 谁负责 | 说明 |
|:-----|:-------|:-----|
| 分享链接 / 归因（谁拉谁） | **cf-lottery** | shareRecords + refCode，现成 |
| 奖励条件判定（拉 1 人 = $100） | **cf-lottery** | 活动规则引擎（activity_config 可配） |
| 每日奖励配额（2 张/人、300 次/天） | **cf-lottery** | 限流引擎，防"奖励意图"超发 |
| 兑换码生成 | **中转站** | 已有能力，cf-lottery 不重复造 |
| 兑换码面额 / 有效期 / 过期作废 | **中转站** | 用户明确：全部中转站管理 |
| 兑换码核销 / 余额发放 | **中转站** | 账务体系的一部分 |
| 退群检测 | **QQ 机器人**（中转站侧） | 平台只提供标准事件入口 API |
| 处罚波及名单（自己+邀请人+被邀请者） | **cf-lottery** | 靠归因关系算出名单，中转站可能没有完整邀请链 |
| 扣余额 / 作废兑换码（执行处罚） | **中转站** | 收到波及名单后执行 |
| 拉新漏斗 / 处罚审计 / 运营看板 | **cf-lottery** | activityEvents + 审计日志，现成 |

> **分工本质**：cf-lottery 输出"**该给谁发什么、该罚谁**"，中转站输出"**发没发、罚没罚**"。两边通过 Webhook + 回传 API 对账。

## 三、cf-lottery 现有能力映射（调整后）

| # | 活动需求 | cf-lottery 现有能力 | 代码位置 | 差距 |
|:-:|:--------|:-------------------|:---------|:-----|
| 1 | 拉一个人送 100（归因） | 分享裂变引擎：shareCode、refCode 归因、clicked/joined 计数、排行榜 | `shareRecords`（schema.ts）、`public-lottery-share.ts` | 无差距，直接可用 |
| 2 | 奖励意图通知中转站 | Webhook 投递（签名+重试+投递记录） | `webhookConfigs`/`webhookDeliveries`（admin-lottery-integrations.ts） | 需新增 `reward.earned` 事件类型 |
| 3 | 每日奖励配额（2 张/人、300 次/天） | 双闸门限流 `checkPublicRateLimit`：内存 Map 预过滤 + DB `checkDbRateLimit`（原子 INSERT…SELECT，并发安全、多实例可信） | public-lottery-helpers.ts + rate-limit.ts | 按 key 维度配两个限流点，框架现成 |
| 4 | 退群上报入口 | 租户 API Key（hash 存储） | `apiKeys`（admin-lottery-integrations.ts） | 缺"外部事件入口 API"，新增点 |
| 5 | 处罚波及名单（连带清零） | 归因关系已落库：shareRecords.sharerEntryId ↔ 新参与 entry | 同上 | 缺"按归因反查波及名单"规则，新增点 |
| 6 | 中转站执行结果回传 | `externalConversions` 外部事实回传 | schema.ts | 复用/扩展为 `reward.issued`、`penalty.executed` 回传 |
| 7 | 活动规则可配置 | activity_kind 扩展点 + activityConfig 版本化配置 | schema.ts 的 lotteryDraws | 玩法类型需新增 `quota_card`（长期项） |
| 8 | 防羊毛党 | 黑名单 `lotteryBlacklist` + IP 限流 + UNIQUE 身份约束 + 审计日志 | schema.ts | 现成，直接用于封号 |
| 9 | 运营复盘 | `activityEvents` 统一事实表 | schema.ts | 现成，发奖/处罚都写事件即可出漏斗 |

**修正后的结论更硬**：这个场景里 cf-lottery 连"发卡"都不用做，**90% 能力现成**，主要新增只有两个点——"退群事件入口 API"和"奖励/处罚 Webhook 事件定义"。

## 四、数据流设计（双向闭环）

### 4.1 拉新奖励链路

```
群友分享链接 ?ref=xxx
  → 新用户进入活动页 → 绑定中转站账号 → 参与（归因成功，joinedCount++）
  → cf-lottery 规则引擎判定：奖励条件达成 + 配额校验（2 张/人、300 次/天）
  → Webhook 通知中转站：reward.earned { account, inviter, amount: 100, eventId }
  → 中转站生成兑换码（面额/有效期自管）→ 发放给用户
  → 中转站回传 cf-lottery：reward.issued { eventId, code, expiresAt, status }（可选，用于对账和看板）
```

### 4.2 退群处罚链路

```
QQ 机器人检测到退群
  → POST /api/integrations/events（API Key 鉴权，幂等键防重报）
     { event: "member.left_group", payload: { qq, account, leftAt }, idempotencyKey }
  → cf-lottery 记录事件 + 查归因关系，计算波及名单：
     ① 退群者本人
     ② 退群者的邀请人（"邀请的人额度也清"）
     ③ 退群者邀请进来的人（防止其名下卡被连带薅走，开关可配）
  → Webhook 通知中转站：penalty.requested { targets: [...], reason, eventId }
  → 中转站执行：作废相关兑换码 + 扣余额
  → 中转站回传 cf-lottery：penalty.executed { eventId, revokedCodes: n }（可选）
  → 全部写入 activityEvents + 审计日志（运营可追溯"谁罚了谁"）
```

### 4.3 核心不变量

1. **cf-lottery 永远不产生"卡"**，只产生"奖励意图"和"处罚指令"，杜绝两边券状态不一致
2. **配额限流在 cf-lottery**（奖励意图超发会导致中转站多发卡，所以要在源头卡住）
3. **事件幂等**：机器人重报、Webhook 重试都不会重复发奖/重复处罚
4. **对账靠回传**：reward.issued / penalty.executed 回传后，两边事实对齐

## 五、落地方案：三阶段

### 阶段一：归因 + 奖励意图通知（现有能力拼装，1-2 天）

**目标**：跑通"分享 → 归因 → 通知中转站发卡"主链路，零新表。

1. 建活动（experienceType=submit，公开参与），活动页即"领卡落地页"：展示"进群送 $100 日卡"，用户输入中转站账号参与
2. 参与时带 refCode 归因（现成）→ 写 activityEvents
3. 新增规则判定：邀请达标 + 配额校验（rateLimitLog 两个 key：`reward:{account}` 每人每天 ≤ 2、`reward:global` 每天 ≤ 300）
4. 新增 Webhook 事件 `reward.earned`：通知中转站"该给谁发 $100 日卡了"，payload 带 eventId 供回传对账
5. 中转站回传 `POST /api/integrations/events`（新增事件类型 reward.issued）→ 平台记录，看板可展示"已发卡数"

### 阶段二：退群处罚闭环（新增 1 个事件 API + 1 条波及规则，2-3 天）

**目标**：把"退群扣余额、邀请人连带清零"自动化。

1. 新增外部事件入口：`POST /api/integrations/events`（API Key 鉴权 + 幂等键）
   ```json
   {
     "event": "member.left_group",
     "payload": { "groupId": "123456", "qq": "10001", "account": "user@example.com", "leftAt": "..." },
     "idempotencyKey": "leave-20260804-10001"
   }
   ```
2. 波及名单规则（activity_config 可配）：本人 + 邀请人 + 被邀请者
   > **技术注意**：`shareRecords.joinedCount` 是聚合计数器，**不存储被邀请者 entryId 明细**。波及名单中的"被邀请者"需通过 `activityEvents` 反查——退群者的 `shareCode` → `activityEvents.refCode` → 找到所有使用该 refCode 归因参与的 entryId 列表。查询方式：`SELECT entryId FROM activityEvents WHERE drawId=? AND refCode=? AND eventType='attributed_join'`。这是索引字段（`refIdx`），性能可观。
3. Webhook `penalty.requested` 通知中转站执行作废/扣余额；回传 `penalty.executed` 对账
4. 审计：活动事件 + 审计日志留痕

### 阶段三：玩法化（activity_kind=quota_card，约 1 周）

**目标**：从"拼装玩法"升级为"正式玩法"，规则全部可配置、可售卖。

1. 新增 activity_kind：`quota_card`（额度卡营销玩法），进玩法矩阵
2. 规则进 activityConfig（版本化 JSON）：
   ```json
   {
     "version": 1,
     "reward": { "perInviteAmount": 100, "currency": "USD", "issuer": "middleman" },
     "quota": { "perUserPerDay": 2, "globalPerDay": 300 },
     "registerReward": { "amount": 200, "channel": "middleman_api" },
     "penalty": {
       "revokeOwnOnLeave": true,
       "revokeInviterOnLeave": true,
       "revokeInvitedOnLeave": true
     },
     "integration": { "rewardWebhook": "reward.earned", "penaltyWebhook": "penalty.requested" }
   }
   ```
3. 管理端可视化配置：奖励面额/每日配额/惩罚开关/Webhook 地址，改规则不写代码
4. 运营看板：拉新漏斗（分享→进群→发卡→核销）、每日配额消耗、处罚记录、ROI

## 六、API / Webhook 契约汇总

| 方向 | 端点/事件 | 鉴权 | 说明 |
|:-----|:----------|:-----|:-----|
| 出站 | Webhook `reward.earned` | 签名 | 通知中转站发卡：{ account, inviter, amount, eventId } |
| 出站 | Webhook `penalty.requested` | 签名 | 通知中转站处罚：{ targets[], reason, eventId } |
| 入站 | `POST /api/integrations/events` | API Key | 外部事实回传：member.left_group / reward.issued / penalty.executed |
| 公开 | 活动页参与（带 refCode） | 公开 | 归因入口，现成 |

> 中转站侧只需要：接收 2 个 Webhook（发卡指令/处罚指令）+ 调用 1 个回传 API。**对面系统工作量极小**，这是方案能落地的前提。

## 七、专家建议：cf-lottery 内部是否需要"有效期"能力

> 用户问题：中转站的活动只是其一。针对**其他场景**，我们系统内是否需要增加有效期管理？以下是顾问分析。

### 7.1 核心原则

**有效期只加在"凭证类资产"上，不加在"事实类记录"上。**

| 类别 | 表 | 是否有有效期 | 判断 |
|:-----|:---|:-----------|:-----|
| 凭证类资产 | couponCodes（优惠券码池） | ✅ 有 expiresAt（导入可设） | 需补"到期处理"动作 |
| 凭证类资产 | prizeCodes（奖品卡密池） | ❌ **没有** | **最大缺口，见 7.3** |
| 凭证类资产 | redemptionCodes（平台兑换码） | ✅ 有 expiresAt（notNull） | 已完整 |
| 凭证类资产 | tenants.extraQuotaExpiresAt（租户额度） | ✅ 有 | 已完整 |
| 事实类记录 | activityEvents / auditLogs / shareRecords / externalConversions / webhookDeliveries | ❌ 无 | **正确**，事件和审计是永久事实，加了反而误导 |

### 7.2 其他场景逐一分析（是否值得加）

| 场景 | 典型玩法 | 需要有效期吗 | 优先级 |
|:-----|:---------|:-----------|:------:|
| 限时卡密奖品 | 奖品是"7 天会员卡""月卡""体验券" | **需要**：prizeCodes 现在管不了过期 | 🔴 P0 |
| 违规撤奖 | 中奖后作弊/违规，撤回已发卡密 | **需要**：新增 revoked 状态（券/码统一） | 🔴 P0 |
| 优惠券到期提醒 | 42a 已规划：到期前提醒用户使用 | **需要**：couponCodes 有 expiresAt，缺 cron | 🟡 P1 |
| 中奖领取窗口 | 中奖后 7 天不领取作废、顺延重抽 | **需要**：lottery_winners 缺"领取时限"概念 | 🟡 P1 |
| 活动时间窗 | 活动开始/结束时间 | 已有 startAt/endAt | ✅ 无需 |
| 分享链接时效 | 邀请链接是否限时 | 一般不需要（活动期内有效即可） | ⚪ 不做 |
| 奖励/处罚事件 | 活动事件、审计日志 | 不需要（永久事实） | ⚪ 不做 |

### 7.3 具体建议（分两层，避免过度设计）

**第一层（轻，建议近期做）——把"时效资产"维度补齐：**

1. **prizeCodes 增加 expiresAt**（可空，奖品级统一过期策略 or 卡密级单独过期）
   - 场景：活动奖品是限时卡密，管理端导入/生成卡密时可设过期时间；中奖者查结果时展示"请在 X 前兑换"
   - 表结构：加一列 `expires_at`，可空（空 = 永不过期，兼容现有卡密）
2. **券/码统一 revoked 状态**
   - couponCodes 状态机：available/reserved/issued/redeemed/expired → 补 `revoked`（退群收回、违规撤奖、运营人工作废）
   - prizeCodes 同样支持 revoked（中奖卡密被撤回）
   - 收益：**一个状态，覆盖所有"发了又收"的场景**——中转站退群清零、抽奖违规撤奖、运营人工纠错

**第二层（中，P1）——到期处理动作：**

3. **到期提醒 cron**：扫描即将过期的 couponCodes/prizeCodes → 提醒用户（邮件/站内）
4. **自动作废 cron**：扫描已过期未核销的凭证 → 标记 expired（当前靠查询时判断，落库更利于统计）
5. **中奖领取窗口**（可选）：lottery_winners 加 claimedAt + 窗口时限，超时作废顺延（配合 42a 的候补机制）

**不做清单：**
- 不给 activityEvents/auditLogs/shareRecords 加有效期（永久事实）
- 不做全量"资产台账"抽象（把所有凭证合并成一张表）——couponCodes/prizeCodes/redemptionCodes 语义不同，硬合并会破坏现有模块

### 7.4 与中转站场景的关系

中转站场景本身**不需要** cf-lottery 管有效期（兑换码有效期中转站自管）。但 7.3 的 revoked 状态和限时卡密能力，是**其他场景**的刚需，且实现成本低（一列 + 一个状态），做了之后"违规撤奖""限时奖品"都闭环。**建议纳入路线图，与中转站场景解耦推进。**

## 八、风险与边界

| 风险 | 应对 |
|:-----|:-----|
| 中转站没收到 reward.earned / penalty.requested | Webhook 重试机制现成（webhookDeliveries + nextRetryAt），失败投递管理端可见 |
| 机器人重复上报退群 | idempotencyKey 幂等（webhookDeliveries 已有 eventId 唯一约束可借鉴） |
| 中转站发了卡但没回传（对账缺口） | 回传是可选增强；主链路不依赖回传，看板数据以本地事件为准 |
| 同一 QQ 反复进群退群薅卡 | 黑名单（lotteryBlacklist）+ 事件幂等 + 退群即清，成本高于收益 |
| 配额规则被改出问题 | activityConfig 版本化 + publish-check 预检（复用现有发布预检框架） |
| 波及名单算错（误伤） | 名单明细进审计日志，运营可查可改；连带开关可配（revokeInvitedOnLeave 默认关） |

### 失败处置与对账 SOP

**场景一：reward.earned Webhook 失败（中转站没收到发卡通知）**
1. 系统自动重试（webhookDeliveries + nextRetryAt，现有机制）
2. 重试全部失败后：管理端显示"投递失败"列表，运营人工确认
3. 用户侧：**参与成功 ≠ 发卡成功**，参与成功页文案："奖励正在发放中，预计 5 分钟内到账，如有问题请联系客服"
4. 补发：运营确认后手动重投 Webhook（管理端操作），或中转站按 eventId 补发对账

**场景二：penalty.requested Webhook 失败（中转站没收到处罚通知）**
1. 同上自动重试
2. 处罚事件**不因 Webhook 失败而取消**——cf-lottery 事件已落库（activityEvents + 审计日志），处罚事实成立
3. 中转站未执行处罚 → 对账差异 → 中转站按 activityEvents 补执行
4. 合同要点：**"处罚以 cf-lottery 记录为准，中转站有义务在 X 小时内执行"**

**场景三：中转站发了卡但没回传 reward.issued**
- 回传是可选的，不影响主链路
- 看板以 activityEvents（reward.earned）为准，回传仅用于对账
- 运营可周期性对比 CF 侧事件数与中转站侧发卡数，偏差 >5% 时介入

## 九、结论

1. **修正后的边界更干净**：兑换码/有效期/余额全在中转站，cf-lottery 只输出"该给谁发什么、该罚谁"。**90% 能力现成**，新增只有"退群事件 API"和"奖励/处罚 Webhook 事件定义"两个点，对面系统只需收 2 个 Webhook + 调 1 个回传 API。
2. **内部有效期管理**：遵循"有效期只加在凭证类资产上"原则——`prizeCodes` 补 expiresAt（限时卡密奖品刚需）+ 券/码统一 revoked 状态（违规撤奖/退群清零），是第一层轻量改造；到期提醒/自动作废/领取窗口是第二层 P1。与中转站场景解耦，独立推进。
3. **商业价值**：`quota_card` 玩法化后是**可复制、可售卖的活动模板**——token 中转站是 020a 锁定的目标客户，其他中转站/社群可开同款活动（多租户优势）。
4. **落地顺序**：阶段一 1-2 天跑通归因+发卡通知 → 阶段二 2-3 天闭环退群处罚 → 阶段三玩法化沉淀；内部有效期改造可并行（prizeCodes expiresAt + revoked 约 1 天）。
