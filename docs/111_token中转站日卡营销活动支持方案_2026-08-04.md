# cf-lottery 对 Token 中转站 QQ 群营销活动的支持方案

> 文档编号：111
> 创建时间：2026-08-04
> 定位：把"QQ 群拉新 + 日卡额度 + 退群惩罚"的讨论碎片，整理成正式规则，映射到 cf-lottery 现有能力，给出可落地的三阶段方案
> 角色：产品架构师 + 营销技术顾问
> 结论一句话：**cf-lottery 不存余额、不做 QQ 机器人，它做"规则引擎 + 凭证中心 + 归因中心"，把别人要写几千行的营销反作弊系统变成"配一个活动 + 接两个 API"。**

---

## 一、场景还原：运营者到底想干什么

### 1.1 讨论内容整理

| 运营诉求（原话） | 翻译成规则 |
|:----------------|:----------|
| 群满了是 200 人，缺口是 170，发完为止 | 活动目标：拉新 170 人进 QQ 群，奖励池发完即止 |
| 注册送 200，拉一个送 100 | 注册奖励 200（平台余额）；每有效拉 1 人进群，奖励 100（日卡形式） |
| 100 的日卡兑换 / 送兑换卡 | 奖励以"日卡"发放——面额 100 刀、可兑换成平台额度的凭证 |
| 必须得过期的 / 有效期七天兑换，过期作废 | 日卡 7 天有效期，过期自动作废（不能囤） |
| 每天只能兑换 2 张 | 每人每天最多兑换 2 张日卡（防屯屯鼠） |
| 每天只能兑换 300 次，总池子，也就是 150 人兑换 | 全平台每日日卡兑换总量 300 次（2 张/人 → 约 150 人） |
| 退群的直接扣余额 | 退群事件 → 已发日卡全部作废 → 中转站同步扣余额 |
| 退出 QQ 的那家就会扣日卡 | 同上：退群者的日卡被收回 |
| 邀请的人额度也清 | 连带处罚：退群者的**邀请人**额度也被清 |
| 你不能薅了就跑，否则额度直接清 | 防羊毛核心：领了卡就跑 = 额度清零 |
| 他是机器人，退群立马监控 | QQ 群机器人实时检测退群 → 触发处罚 |

### 1.2 一句话本质

这是一套 **"规则驱动的激励发放 + 反作弊"** 系统，和 cf-lottery 的核心定位（规则驱动的参与与结果分配）**完全同构**。区别只是：
- 抽奖的"结果"是奖品；这里的"结果"是**日卡凭证 + 处罚动作**
- 抽奖的"参与"是抽一次；这里的"参与"是**进群 + 领卡**

### 1.3 关键认知：活动不是一次性抽奖，而是持续 7 天的"领卡战役"

```
时间线：
D1  用户通过群友分享链接进入活动页 → 绑定中转站账号 → 领第 1 张日卡（$100）
D2  用户再拉 1 人进群 → 归因成功 → 可再领 1 张
D3  ...每天最多 2 张，全平台每天最多 300 张
D7  未兑换的日卡过期作废
任意天 用户退群 → 机器人上报 → 名下未核销日卡全部作废 → 邀请人也连带 → 中转站扣余额
```

### 2.1 现有能力组合后的完整闭环（不新增任何大件）

```
┌────────────────────────── cf-lottery（规则引擎+凭证中心） ──────────────────────────┐
│                                                                                  │
│  ① 活动页（公开链接/白标嵌入）── 裂变归因引擎 ── ② couponCodes 日卡池 ── ③ 限流引擎   │

│                                                                                  │

│     QQ机器人上报退群             revoked/连带清零        reward.revoked 事件         │
└──────────────────────────────────────────────────────────────────────────────────┘
```

## 三、架构边界：平台做什么、坚决不做什么

### 3.1 平台做三件事

1. **规则执行**：谁邀请谁（归因）、谁符合领卡条件、谁违规（退群）→ 触发什么结果（发卡/作废/连带清零）
2. **凭证签发**：日卡 = 带面额、带有效期、带状态机的凭证（couponCodes），由平台生成、追踪、作废
3. **联动通知**：发卡/作废事件通过 Webhook 通知中转站，中转站负责**同步余额**

### 3.2 平台坚决不做的三件事

| 不做 | 原因 |
|:-----|:-----|
| 不存"余额/额度"账务 | 余额是中转站自己的资产。平台存了就成了账务系统，违背"小而美的瑞士军刀"定位，还引入对账复杂度 |
| 不做 QQ 机器人本体 | 机器人检测退群是 QQ 侧的事。平台只提供**标准事件入口 API**，任何渠道（QQ/Telegram/微信）的机器人都能对接 |
| 不做强制分享 | 规则可配，默认不强制，防损害体验和平台政策 |

### 3.3 边界契约（平台 ↔ 中转站）

```
平台侧                         中转站侧（外部）
─────────                     ─────────
发卡（reward.issued）    ────►   收到 → 给用户加额度
用户核销（redeem）      ◄────    用户在中转站用卡 → 调核销 → 平台标记 redeemed
作废（reward.revoked）  ────►   收到 → 扣减用户余额
退群事件上报            ◄────    QQ 机器人检测 → POST /api/integrations/events
```

**身份锚点（关键落地点）**：QQ 群场景下身份是 QQ 号，而券是发给中转站账号的。建议：
- 中转站把 `QQ 号 ↔ 中转站账号` 绑定关系维护在自己侧
- 用户领卡时必须提供中转站账号（identityValue 用中转站账号/邮箱）
- 退群上报用 QQ 号 → 平台通过活动事件里的绑定关系反查（或中转站在上报 payload 里直接带账号，最简单）

## 四、落地方案：三阶段

### 阶段一：凭证化日卡 + 领卡限流（现有能力拼装，1-2 天）

**目标**：先跑通"分享 → 领卡 → 限流"主链路，零新表。

1. **日卡池**：运营者在奖品管理里导入/生成一批日卡（复用 couponCodes 或 prizeCodes），`expiresAt = 领取时间 + 7 天`，面额写进 label/note
2. **领卡活动**：建一个活动（experienceType=submit，activityKind=lottery），活动页即"领卡落地页"——展示"进群送 $100 日卡"，用户输入中转站账号 + 邀请码（refCode）参与
3. **新增公开 API**：`POST /api/public/draws/:slug/redeem-card`
   - 入参：{ account, refCode? }
   - 校验顺序：活动开启 → refCode 归因（有则记录 attributed_join）→ **限流 1**：`daily_redeem:{account}` 每人每天 ≤ 2 → **限流 2**：`daily_redeem:global` 每天 ≤ 300 → 从池子 CAS 领取一张（available → issued，原子 UPDATE，防并发超发）
   - 写 `activityEvents`（eventType=reward_issued，refCode 关联邀请人）→ 审计日志
4. **限流复用**：`checkRateLimit` 现成，只是 key 和阈值从 activity_config 读，不写死

### 阶段二：退群处罚闭环（新增 1 个事件 API + 1 条处罚规则，2-3 天）

**目标**：把"退群扣余额、邀请人连带清零"自动化。

1. **新增外部事件入口**：`POST /api/integrations/events`（API Key 鉴权，复用 apiKeys 表）
   ```json
   {
     "event": "member.left_group",
     "payload": { "groupId": "123456", "qq": "10001", "account": "user@example.com", "leftAt": "2026-08-04T12:00:00Z" },
     "idempotencyKey": "leave-20260804-10001"   // 幂等，防机器人重报
   }
   ```
2. **处罚规则（可配置）**，顺序执行：
   - 查该账号名下 status=issued 且未过期的日卡 → 全部置 `revoked`（couponCodes 新增状态）
   - 查归因：该 entry 是被谁邀请的（shareRecords.sharerEntryId）→ 邀请人名下日卡**连带 revoked**（开关可配）
   - 查该账号邀请的所有人（joinedCount 明细）→ 其名下日卡**连带 revoked**（"邀请的人额度也清"）
   - 写 `activityEvents`（eventType=reward_revoked，metadata 记录原因/波及人数）
3. **Webhook 联动**：触发 `reward.revoked` 事件投递到中转站配置的 webhook（签名+重试现成）→ 中转站扣减余额
4. **幂等与审计**：idempotencyKey 去重 + 平台审计日志留痕（运营可追溯"谁罚了谁"）

### 阶段三：玩法化（activity_kind=quota_card，约 1 周）

**目标**：从"拼装玩法"升级为"正式玩法"，规则全部可配置、可售卖。

1. **新增 activity_kind：`quota_card`（额度卡兑换玩法）**，进玩法矩阵
2. **规则进 activityConfig**（版本化 JSON）：
   ```json
   {
     "version": 1,
     "card": { "faceValue": 100, "currency": "USD", "validDays": 7, "expirePolicy": "after_issue" },
     "redeemQuota": { "perUserPerDay": 2, "globalPerDay": 300 },
     "inviteReward": { "rewardPerInvite": 100, "capPerDay": 2 },
     "registerReward": { "amount": 200, "channel": "middleman_api" },
     "penalty": {
       "revokeOwnOnLeave": true,
       "revokeInviterOnLeave": true,
       "revokeInvitedOnLeave": true,
       "scope": "unredeemed_only"
     }
   }
   ```
3. **管理端可视化配置**：面额/有效期/每日配额/惩罚开关，改规则不写代码
4. **运营看板**：领卡漏斗（分享→进群→领卡→核销）、每日兑换消耗、惩罚记录、ROI（结合 externalConversions 回传的核销金额）

## 五、API 设计汇总

| 端点 | 鉴权 | 说明 |
|:-----|:-----|:-----|
| `POST /api/public/draws/:slug/redeem-card` | 公开 | 领卡：归因 + 双重限流 + CAS 领取 + 事件落库 |
| `POST /api/integrations/events` | API Key | 外部事件入口：退群上报（当前仅 member.left_group） |
| `POST /api/integrations/cards/:code/redeem` | API Key | 中转站核销日卡（issued → redeemed，可选，也可由中转站自管） |
| Webhook 出站 | 签名 | `reward.issued` / `reward.revoked` / `reward.expired`，通知中转站同步余额 |

## 七、风险与边界

| 风险 | 应对 |
|:-----|:-----|
| 同一 QQ 反复进群退群薅卡 | 黑名单（lotteryBlacklist）+ 事件幂等 + 退群即清已发卡，成本高于收益 |
| 并发抢卡超发 | 日卡领取用 CAS 原子 UPDATE（available→issued 带 WHERE 条件），参照 prizeCodes 领取逻辑 |
| 机器人重复上报退群 | idempotencyKey 幂等（webhookDeliveries 已有 eventId 唯一约束可借鉴） |
| QQ 号与账号绑定造假 | 领卡要求中转站账号 + 中转站侧绑定校验；平台只信上报，审计留痕 |
| 规则被改出问题 | activityConfig 版本化 + publish-check 预检（复用现有发布预检框架） |
| 中转站未收到 revoked | webhook 重试机制现成（webhookDeliveries + nextRetryAt），失败投递管理端可见 |

## 八、结论

1. **最大优势发挥点**：cf-lottery 的裂变归因、券生命周期、持久化限流、Webhook 联动、审计事实表——这五样正好是这套营销玩法的全部骨架，**80% 能力现成**，主要新增只有"领卡 API"和"退群事件 API"两个端点。
2. **商业价值**：这个玩法本身是可复制的活动模板——token 中转站正是 020a 文档锁定的目标客户（场景 B），"日卡营销玩法"可作为套餐售卖点，别的中转站/社群也能开同款活动（多租户优势）。
3. **落地顺序**：阶段一 1-2 天跑通主链路 → 阶段二 2-3 天闭环惩罚 → 阶段三玩法化沉淀为产品能力。
