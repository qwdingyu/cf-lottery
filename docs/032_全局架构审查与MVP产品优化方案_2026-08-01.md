# 全局架构审查与 MVP 产品优化方案

> 文档编号：032
> 日期：2026-08-01
> 定位：站在上帝视角的全局架构审查，聚焦业务逻辑优化和运营者体验提升。
> 原则：不推测、不假设，所有结论基于代码事实。

---

## 一、整体评价

三层路由分离干净、RBAC-lite 轻量合理、活动引擎骨架经受住了抽奖和接龙验证。**没有架构性灾难。** 但活动创建表单对运营者不够友好，"3 分钟搭建可复盘的活动"的产品承诺在执行层面有断层。

---

## 二、架构冗余分析

### 2.1 `admin-lottery.ts` 巨石文件（1815 行）

单个文件承载了活动 CRUD、奖品、成员、黑名单、Webhook、API Key、审计日志、模板、导出等全部租户后台能力。建议按领域拆分（见 §7），但不影响当前功能，留到最后处理。

### 2.2 `lottery-service.ts` 职责过宽（2042 行）

包含活动生命周期、开奖算法、邮件、Webhook、套餐额度、健康恢复、数据统计。邮件和 Webhook 逻辑后续可抽到独立 service 文件。

### 2.3 重复代码

| 函数 | 位置 |
|------|------|
| `defaultExperienceForActivity` | `lottery-service.ts`（导出）+ `admin-lottery.ts`（重复定义） |
| `defaultExperienceForParticipation` | `lottery-service.ts`（导出）+ `admin-lottery.ts`（重复定义） |
| `clampInteger` | `admin-lottery.ts`、`platform.ts`、`platform-redemption-codes.ts` 各有定义 |

## 三、活动创建表单 —— 对运营者不友好

当前表单暴露引擎内部参数（`activityKind`、`experienceType`、`resultMode`、`allocationPolicy`、`policyVersion`），运营者看到的是技术术语而非业务语言。模板系统已预填正确默认值，但这些参数仍展示在表单首屏。

**方案：** 折叠到"高级设置"面板，默认不展开。

---

## 四、MVP 变现模式 —— 通过 L3 系统配置优雅控制

### 4.1 新增配置项

| key | 类型 | 默认值 | 用途 |
|-----|------|--------|------|
| `enable_registration` | boolean | `true` | MVP 内测关闭注册；公测时打开 |
| `free_plan_max_webhooks` | integer | `1` | Free 套餐 Webhook 数量（给试用体验） |
| `enable_pricing_page` | boolean | `false` | MVP 期间不展示定价页 |

### 4.2 MVP 期间 Free 套餐调整

当前 free 档 `maxWebhooks: 0` 意味着免费用户完全无法体验"能接系统"的核心卖点。MVP 推广期间改为 `maxWebhooks: 1`，让用户验证价值后再付费升级。

---

## 五、运营者体验优化

### 5.1 模板弹窗移除"空白活动"
"空白活动"按钮从零开始创建，直接暴露所有引擎参数，与模板驱动设计的意图相悖。移除后，运营者不选模板时默认按"抽奖"创建。

### 5.2 LandingView 增加"查看示例活动"
潜在客户在注册前无法看到活动长什么样。增加 `/lottery/demo` 公开演示活动链接。

### 5.3 首次登录触发模板选择
注册→登录后进入空白运营台，用户不知道做什么。首次登录时自动弹出模板选择弹窗。

## 七、拆分方案（P2，最后执行）

```
src/routes/admin/
  draws.ts          ← 活动 CRUD（创建/编辑/发布/暂停/恢复/取消/复制/开奖）
  prizes.ts         ← 奖品 CRUD + 码池导入
  members.ts        ← 团队成员管理
  blacklist.ts      ← 黑名单
  settings.ts       ← Webhook/API Key/邀请码/名单/兑换码
  dashboard.ts      ← 运营台/模板/导出/数据/漏斗
```

每个文件挂在同一个 `adminLotteryRoute` 下，不改变路由结构。
