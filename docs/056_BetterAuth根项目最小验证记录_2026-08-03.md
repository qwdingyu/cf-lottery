> 日期：2026-08-03

> 结论：**最小技术验证通过，但还不足以立即删除 Logto；可以进入“参与端 Better Auth 小范围试点”阶段。**

## 一、验证范围

本次验证只做最小闭环，不接入正式业务路由：

- Better Auth 是否能在当前根项目安装。
- Better Auth 是否能和 Hono handler 一起工作。
- Better Auth 是否能使用当前技术栈里的 libSQL SQLite + Drizzle。
- 邮箱密码注册、登录、session 查询是否能跑通。
- Google provider 是否能生成 OAuth 授权 URL。

本次没有验证：

- 真实 Google OAuth 回调。
- Google Cloud production consent screen。
- 账号合并策略。
- 与现有 `users` / `lottery_entries` 业务表的正式映射。
- 前端 Vue 真实按钮与 cookie 跨域策略。

## 四、验证中发现的坑

### 1. npm 依赖解析需要注意

第一次执行：

```bash
npm install better-auth@1.6.25 @better-auth/drizzle-adapter@1.6.25
```

失败，原因是 npm peer dependency 解析 Better Auth 的 optional React peer 与 Drizzle optional 生态包时冲突。

可用安装方式：

```bash
npm install better-auth@1.6.25 --legacy-peer-deps
```

判断：
- 这是 npm peer dependency resolution 问题，不是运行时功能失败。
- 后续 CI 如果使用 `npm ci`，当前 lockfile 已固定，不需要每次 install 都带 `--legacy-peer-deps`。
- 但如果未来重新安装/升级依赖，可能还会遇到同类 peer 解析问题。

### 2. Better Auth 不是零 schema

最小运行也需要 4 张表：
- `user`
- `session`
- `account`
- `verification`

这意味着正式接入时不能只加一个 npm 包，还要决定：
- 是否独立保留 Better Auth 表；
- 是否映射到现有 `users` 表；
- 如何把 Better Auth `user.id` 接到 `lottery_entries.identity_value`。

### 3. Google 只验证到了“授权 URL 生成”

本地验证不能证明真实 Google 登录完全可用。

真实上线还必须完成：
- Google Cloud 项目
- OAuth consent screen
- Authorized JavaScript origins
- Authorized redirect URIs
- 生产域名
- 隐私政策与品牌信息
- 测试用户或 production verification

因此，不能因为 POC 通过就直接删除 Logto。

### 4. 生产 audit 视角当前通过

执行：

```bash
npm audit --omit=dev
```

结果：

```text
found 0 vulnerabilities
```

npm 仍提示全依赖树有 4 个 moderate vulnerabilities，但 `--omit=dev` 下没有生产漏洞。后续如果把 Better Auth 正式接入生产，应继续保留 audit 检查。

## 五、对是否替换 Logto 的判断

### 可以做的决策

可以进入下一阶段：

> 在参与端小范围接入 Better Auth，优先验证 Google 登录 / One Tap 替代邮箱验证码。

原因：
- 根项目技术栈兼容性已通过。
- Hono handler 能直接挂载。
- Drizzle/libSQL 能工作。
- Google provider 配置入口可用。

### 不能做的决策

现在不能直接删除 Logto。

原因：
- 真实 Google OAuth 回调未验证。
- 生产 Google Cloud 配置未验证。
- 现有 Logto 已嵌入管理端和参与端回调。
- Better Auth 用户表与现有业务用户表尚未设计映射。

---

## 六、推荐下一步

1. 保留 Logto 回退链路。
2. 新增 Better Auth 正式路由，但先只用于参与端。
3. 使用独立 Better Auth 表，不急着合并现有 `users` 表。
4. 参与成功时写入 `lottery_entries.identity_type = "user_id"`。
5. `identity_value` 使用 Better Auth `user.id`。
6. Google OAuth 真实回调跑通后，再决定是否迁移管理端。
7. 完成一轮真实活动验证后，再删除 Logto。

---

## 七、当前结论

Better Auth 的最小验证是成功的。

但这个成功只证明：
- 依赖能装；
- Hono 能挂；
- Drizzle/libSQL 能落库；
- session cookie 能工作；
- Google OAuth URL 能生成。

它还没有证明：
- Google 生产登录体验稳定；
- 反羊毛党能力已经充分；
- 可以立刻替换 Logto；
- 可以直接复用现有用户表。

因此，下一步应做“小范围参与端试点”，而不是“立即全量替换”。
