## 2. 核心功能闭环评估

### 闭环 1：发卡闭环（支付回调 → 发卡 → 用户查卡）✅

```
支付回调 → verifyCallback(验签) → 金额校验 → 事务(取卡密→标记 paid→entry paid)
  → 用户查询(POST payment-orders?email=) → 返回卡密
```

| 检查点 | 状态 | 证据 |
| --- | --- | --- |
| 回调验签 | ✅ | `provider.verifyCallback(params)` 由 cf-core Provider 实现 |
| 金额校验 | ✅ | `callback.amountCents !== order.amountCents` 严格比对 |
| 幂等 | ✅ | 事务内重新读取订单,已 paid 直接返回 |
| 事务边界 | ✅ | `withDbTransaction` 包裹(读取→取卡密→更新订单→entry) |
| 卡密不足 | ✅ | `paid_fulfillment_failed` 状态,运营后台可补发(retryPaymentFulfillment) |
| 卡密查询 | ✅ | 验证 email 与 entry 匹配后返回 prizeCode |

  → 支付弹窗/二维码 → 3.5s 轮询 GET payment-orders/:id → paid → 显示卡密

## 3. 发现的问题（按优先级）

### P1（需关注，不影响功能但需验证）

**P1-1 Stripe 回调验签路径未测试**
- 回调路由中 Stripe 的 webhook 处理用 `_raw_body` + `_stripe_signature` 参数传递给 Stripe Provider 的 `verifyCallback`。
- 此路径依赖 cf-core Stripe Provider 的 `verifyCallback` 实现正确解析这些参数。
- **风险**：真实 Stripe webhook 联调未测试（commit 明确标注 `Not-tested: 真实支付网关联调`），生产上线前必须用 Stripe CLI 或沙箱验证。
- 缓解：cf-core 0.4.17 的 Stripe Provider 已稳定，但集成验证不可跳过。

**P1-2 非 email 身份限制未文档化**
- `payment.ts` 创建订单时限制 `if (entry.identityType !== "email") return fail(...)`。registered 模式(user_id 身份)的用户不能使用直付秒杀。
- 发布预检(`publish-check-service.ts:119`)已校验此限制并给出错误提示，但未在 docs/131 或活动配置说明中记录。
- 影响：如果运营不了解此限制，创建 registered 模式的直付秒杀活动，会通过发布预检(校验在直付发布后)？让我确认——发布预检 119 行:"直付秒杀当前只支持 email 身份参与；registered 模式会导致已参与但无法下单"——这是**阻断发布**的 error 还是 warning？如果只是 warning，运营可能忽略。

### P2（体验优化，非功能缺失）

**P2-1 支付弹窗刷新后状态丢失**
- `paymentState` 为内存变量，未持久化(localStorage/IndexedDB)。用户刷新页面、关闭弹窗后重新进入，支付状态丢失。
- 用户需重新点击"去支付"创建新订单(或 retryPaymentOrder)。体验不连续，但功能可恢复。
- 改进：支付状态持久化到 sessionStorage，刷新后自动恢复轮询。

**P2-2 paid_fulfillment_failed 卡密不足引导缺失**
- 前端轮询检测到 `paid_fulfillment_failed` 时 toast 提示"发卡失败"，但未引导用户"请联系客服获取卡密"或"卡密将在 24 小时内补发"。
- 用户可能困惑（已扣款但未收到卡密）。
- 改进：卡密不足时显示引导文案 + 客服联系方式。

**P2-3 支付弹窗 QR 码渲染依赖 canvas**
- `syncPaymentQrCode` 使用 `QRCode` 库生成二维码。如果 QRCode 库加载失败或未注册，二维码不显示，用户只能使用 redirectUrl。
- 改进：redirectUrl 作为兜底，始终显示"点击跳转支付"按钮。

### P3（功能扩展，后续版本）

**P3-1 退款功能未实现**
- 运营后台无退款入口。如需退款（支付失败、卡密问题），需线下处理或依赖支付平台后台。
- 文档 §10 列为遗留决策，当前未实现。

**P3-2 支付对账**
- 无支付对账功能。订单状态与支付平台实际收款状态可能不一致（如支付平台回调成功但 DB 写入失败，或用户重复支付）。
- 改进：定时对账任务（每日检查 pending 订单 + 调用 Provider queryStatus）。
