## 2. 核心功能闭环评估

### 闭环 1：发卡闭环（支付回调 → 发卡 → 用户查卡）✅

```
支付回调 → verifyCallback(验签) → 金额/币种校验 → 事务(取卡密→标记 paid→entry paid)
  → 用户通过活动邮箱 OTP 找回订单 → Bearer 保护查询/直接展示卡密
```

| 检查点 | 状态 | 证据 |
| --- | --- | --- |
| 回调验签 | ✅ | `provider.verifyCallback(params)` 由 cf-core Provider 实现；异常被 `handlePaymentCallback` 收敛为“验签失败”，不会冒泡成 500 |
| 金额/币种校验 | ✅ | `amountCents` 严格比对；`callback.currency/order.currency` 归一为小写后比对，避免 EasyPay 返回 `CNY`、订单存 `cny` 时误判 |
| 幂等 | ✅ | 事务内重新读取订单,已 paid 直接返回 |
| 事务边界 | ✅ | `withDbTransaction` 包裹(读取→取卡密→更新订单→entry) |
| 卡密不足 | ✅ | `paid_fulfillment_failed` 状态,运营后台可补发(retryPaymentFulfillment) |
| 卡密查询 | ✅ | 已支付订单由 OTP 找回或短期 Bearer 查询返回 prizeCode；裸 email 不可列出订单 |

### 闭环 2：公开支付闭环（参与 → 创建订单 → 支付 → 轮询 → 显示卡密）✅

```
参与成功 → 显示"去支付" → POST payment-orders(entryId) → 返回 redirectUrl/qrCode
  → 支付弹窗/二维码 → 3.5s 轮询 GET payment-orders/:id → paid → 显示卡密
```

| 检查点 | 状态 | 证据 |
| --- | --- | --- |
| 创建订单 | ✅ | entryId 查找 + flashSale.paymentRequired 校验 |
| 重试支持 | ✅ | cancelled/expired 复用 retryPaymentOrder |
| pending 续期 | ✅ | 已有 pending 订单重新生成支付入口(不新增 DB 行) |
| 响应字段一致 | ✅ | 新建订单和 pending 续期都返回 `orderNo/status/amountCents/currency/provider`，前端不再依赖空 provider |
| 前端轮询 | ✅ | 3.5s 间隔,paid/paid_fulfillment_failed 停止 |
| 卡密展示 | ✅ | prizeCode 在支付弹窗渲染 |

## 3. 发现的问题（按优先级）

### P1（需关注，不影响功能但需验证）

**P1-1 EasyPay/ZPay 真实网关联调未完成**
- 当前 CNY 主力渠道是 cf-core 0.4.17 导出的 `easyPayFactory`，业务侧 Provider 名称统一为 `easypay`，ZPay 通过 `EASYPAY_API_BASE` 表达。
- 代码和单测已验证 Provider 选择、回调 fail-closed、币种大小写归一、自动发卡事务；但尚未用真实 EasyPay/ZPay 小额订单验证 `createPayment → notify callback → verifyCallback → 自动发卡`。
- **风险**：兼容易支付网关的字段命名、回调方式、支付类型配置可能因具体网关实例不同而有差异。
- 门禁：生产启用前必须完成一笔 EasyPay/ZPay 小额真实支付，确认回调能到达 `/api/payments/:tenantId/easypay/callback`，订单从 `pending` 进入 `paid`，卡密从 `available` 进入 `issued`。

**P1-2 支付配置 PUT/GET 脱敏占位缺少自动化回归**
- 实现上 `GET /api/admin/payment-config` 会用 `••••••••` 脱敏敏感字段，`PUT /api/admin/payment-config` 会识别占位符并保留 DB 原密文。
- 当前测试覆盖了配置自检、EasyPay 可用性、遗留 `usdt_trc20` 忽略、订单列表 Provider 来源，但没有覆盖“PUT 保存 → GET 脱敏 → PUT 占位符回写不覆盖原密文”的完整回归。
- **风险**：后续改动支付配置 UI 或字段映射时，可能误把占位符写成真实密钥或清空密钥。
- 建议：补一条 `admin-payment-config.test.ts` 自动化用例，替代手动验收。

**P1-3 Stripe 真实 webhook 未联调（仅在启用 Stripe 时阻断上线）**
- 回调路由中 Stripe webhook 使用 `_raw_body` + `_stripe_signature` 传递给 cf-core Stripe Provider。
- 如果当前租户只启用 EasyPay/ZPay，可不把 Stripe CLI 作为本轮上线门禁；一旦启用 Stripe，必须用 Stripe CLI 或沙箱验证 webhook。

### 已闭环项：非 email 身份限制

- `payment.ts` 创建订单会拒绝非 email entry。
- `publish-check-service.ts` 已将 registered 模式直付秒杀写入 `result.errors`，是阻断发布，不是 warning。
- docs/131 已记录“直付秒杀当前只支持 email 身份；registered 模式发布预检阻断”。该项不再作为 P1 风险。

### P2（体验优化，非功能缺失）

**P2-1 支付弹窗刷新后状态丢失**
- `paymentState` 为内存变量，未持久化(localStorage/IndexedDB)。用户刷新页面、关闭弹窗后重新进入，支付状态丢失。
- 用户需重新点击"去支付"创建新订单(或 retryPaymentOrder)。体验不连续，但功能可恢复。
- 改进：支付状态持久化到 sessionStorage，刷新后自动恢复轮询。

**P1-4 订单找回接口不能只凭裸邮箱**

- 原先按 `email` 列出活动订单会暴露参与/支付元数据，也无法直接安全授权后续卡密读取。
- 当前采用 OTP 保护的 `/payment-orders/recover`：用户先通过 `my-result` 验证活动邮箱，再找回已支付卡密或恢复待支付订单；单订单查询继续使用短期 Bearer。
- 前端查结果成功后对直付活动自动进入支付订单恢复流程，关闭支付弹窗后仍可再次通过 OTP 找回。

**P2-2 paid_fulfillment_failed 卡密不足引导缺失**
- 前端轮询检测到 `paid_fulfillment_failed` 时 toast 提示"发卡失败"，但未引导用户"请联系客服获取卡密"或"卡密将在 24 小时内补发"。
- 用户可能困惑（已扣款但未收到卡密）。
- 改进：卡密不足时显示引导文案 + 客服联系方式。

**P2-3 支付弹窗 QR 码渲染依赖 canvas**
- `syncPaymentQrCode` 使用 `QRCode.toDataURL` 生成二维码。如果 Provider 返回的是二维码内容而不是可打开 URL，且二维码渲染失败，页面会清空二维码。
- 当前已有 `redirectUrl` 按钮兜底，但只有 Provider 返回 `redirectUrl` 时才显示；如果某网关只返回二维码内容，则仍可能没有可点击支付入口。
- 改进：当 `qrCode` 是 URL 时额外显示“打开支付链接”；当 `qrCode` 是纯二维码内容且渲染失败时显示可理解的错误和刷新按钮。

### P3（功能扩展，后续版本）

**P3-1 退款功能未实现**
- 运营后台无退款入口。如需退款（支付失败、卡密问题），需线下处理或依赖支付平台后台。
- 文档 §10 列为遗留决策，当前未实现。

**P3-2 支付对账**
- 无支付对账功能。订单状态与支付平台实际收款状态可能不一致（如支付平台回调成功但 DB 写入失败，或用户重复支付）。
- 改进：定时对账任务（每日检查 pending 订单 + 调用 Provider queryStatus）。

## 7. 结论

**支付闭环（发卡、公开支付、运营、软释放）四个核心闭环均已实现且通过代码审查。** 当前可以采纳 131 的直付方向：在 cf-lottery 内做秒杀卡密直付，Provider 协议实现继续来自 `@usethink/cf-core/features/payment`，CNY 主渠道使用 `easypay`（ZPay 通过 `EASYPAY_API_BASE` 配置），区块链支付暂不进入当前直付自动发卡目录。

生产上线前必须优先完成 EasyPay/ZPay 小额真实支付联调。Stripe webhook 验证不是当前 EasyPay 主链路的阻断项，但启用 Stripe 租户前必须单独验证。非 email 身份限制已经是发布预检 error 且 docs/131 已记录，不再作为开放风险。
