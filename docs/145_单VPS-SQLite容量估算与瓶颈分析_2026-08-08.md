# 单 VPS + SQLite 容量估算与瓶颈分析

日期：2026-08-08
背景：审查核心链路后，需要回答"单 VPS 本地 SQLite 到底能支持多少用户和活动"

> **复核状态（2026-08-08）**：本文早期的容量数字是推导假设，不是本项目在目标 VPS 上的实测结果，不能作为发布门槛、SLA 或扩容承诺。`docs/147_SQLite容量基准测试与复核结论_2026-08-08.md` 与 `npm run benchmark:sqlite` 是后续测量的唯一基线；在目标 VPS 跑完完整场景前，本文中 TPS、RPS、用户数、运行周期和"翻倍"数字均只保留为待验证假设。

## 一、线上部署架构（已核实）

来源：`scripts/cf-lottery.service` + `docs/051_云服务器部署指南_2026-08-03.md`

```
用户 → Cloudflare DNS → nginx(:443 SSL) → Hono Server(:8787) → SQLite(file:./data/local.db)
```

| 组件 | 配置 | 来源 |
|------|------|------|
| 进程管理 | **systemd** `Type=simple`，单 Node 进程 | `scripts/cf-lottery.service:10-11` |
| 数据库 | 本地 SQLite `file:` URL；精确文件名由生产 `.env` 决定 | `src/server.ts:33`、部署指南 |
| 启动方式 | `tsx src/server.ts`；未启用 `tsx watch`，不是热重启模式 | `cf-lottery.service:11` |
| WAL 模式 | 每个本地请求连接都会尝试设置；实际部署状态需执行 `PRAGMA journal_mode` 验证 | `src/index.ts:184-189` |
| `busy_timeout` | 业务连接不设置，维持 SQLite 默认 0；由应用层异步、有界重试处理 BUSY | `src/db/client.ts:57-78`、`docs/147` |
| 写冲突兜底 | `withDbTransaction` 5 次重试（50ms 指数退避 ≈1.55s 总等待） | `src/db/client.ts:61-70` |
| 服务器规格 | 部署指南推荐 1C2G，保守按此估算 | `docs/051:27` |
| 每个业务动作 | 1 个事务 = 2~6 条 SQL；网络调用（支付下单）在事务外 | 代码走读确认 |

**关键修正**：systemd 只有一个 Node 进程，但 `src/index.ts` 在每个请求中创建 libSQL client。因此不存在多个 Node 进程竞争同一数据库文件的问题，却仍存在多个数据库连接的写锁竞争；不能把"单进程"误写成"单连接"。

## 二、瓶颈分层

每一层都有上限，按收紧程度排列：

### 2.1 第一层：SQLite 写锁（最硬瓶颈）

SQLite 一次只允许一个写事务。WAL 模式下读不阻塞写，但写仍然是串行化的。

```
基准数据（来自 SQLite 官方 benchmark 与行业公开实测数据）：
  WAL + SSD + synchronous=NORMAL：单条 INSERT/UPDATE 约 10,000~50,000 TPS
  但每个业务事务 2~6 条 SQL，且含复杂操作（COUNT 子查询等）
  保守取有效写事务：1,000~5,000 TPS
  再保守打 5 折（取下限）：500~1,000 事务/秒
```

**为什么保守取 500~1,000 而不是更高：**
- 业务事务含条件 INSERT 和子查询，比裸 INSERT 慢
- `busy_timeout` 未设置，`@libsql/client` 的多个并发事务仍可能撞 BUSY（虽然单进程下概率低）
- 服务器可能是 1 核低配，CPU 和 IO 资源有限

### 2.2 第二层：CPU（2 核估算）

Hono + Node.js 单机大约 500~2,000 RPS（保守取 500~1,000 RPS）。

大多数活动请求是读（SELECT 2~5 条），不占写锁，所以 CPU 决定日常并发能力。

### 2.3 第三层：数据量对 COUNT 查询的影响

`lottery_entries` 表按 `(tenant_id, draw_id, payment_status)` 索引，COUNT 子查询扫描该活动所有行：
- 5 万行：约 20~50ms（可接受）
- 10 万行：约 50~150ms（开始明显）
- 30 万行：约 200~500ms（不可接受，需改计数器）

### 2.4 第四层：磁盘空间

本地 SQLite 文件，单文件上限 140TB（官方），但实际推荐 <10GB。

按行估算：
- `lottery_entries`：每行约 200~400 字节，10 万行 ≈ 30MB
- `activity_events`：每行约 300~600 字节，增长最快（每次参与产生 2~3 条事件），100 万参与 ≈ 300 万行 ≈ 1~2GB
- `prize_codes`：每行约 200 字节，万级行数可忽略
- `payment_orders`/`attempts`：每行约 300 字节，万级

## 三、历史容量估算（未验证，不可作为运营承诺）

### 3.1 秒杀场景（最严苛）

秒杀参与 = 1 个写事务（CAS 计数器 + INSERT），完全吃写锁。

| 指标 | 保守估计 | 推导 |
|------|---------|------|
| 瞬时参与 TPS | **500~1,000 人/秒** | 写事务就是瓶颈 |
| 一场秒杀名额上限 | **5,000~20,000 个** | 10~40 秒抢完，再多的名额让用户等太久（超时 30 分钟，但体验差） |
| 同时支付回调 | 受限于同一写锁，回调会拖慢参与 | 支付回调也是 1 个写事务（4~5 条 SQL） |

**实际体验推演**：1 万人同时抢 1 万个名额，约 10~20 秒抢完。前 500 人秒抢到，后 9500 人排队等写锁，体验上"一直在转圈圈"。这是单 VPS + SQLite 的物理极限。

### 3.2 日常运营（非秒杀）

| 指标 | 保守估计 | 推导 |
|------|---------|------|
| 同时在线用户（浏览） | **500~1,000 人** | 2 核 CPU 约 500~1,000 RPS，用户每 5~10 秒操作一次 |
| 同时参与（非秒杀） | 200~500 人/秒 | 条件 INSERT 有 COUNT 子查询，比纯 SELECT 慢 |
| 单活动总参与人数 | **≤50,000 人** | 超过 5 万后 COUNT 子查询开始拖慢每次 join |
| 平台总活动数 | **500~1,000 个** | 数据量 2~3GB，索引 1~2GB，总计 <5GB |
| 租户数 | **50~200 个** | 多租户隔离 OK，但共享一个写锁 |
| 单活动奖项数 | 建议 ≤10 档 | instant spin 每档做一次 COUNT(winners) |

### 3.3 平台总容量

| 指标 | 保守估计 | 数据量 |
|------|---------|--------|
| 年参与量 | 50~100 万人次 | entries ~100 万行，events ~300 万行，合计 ~2GB |
| 安全运行周期 | **12~18 个月** | 之前无需架构变更 |
| 数据库安全体量 | **<3GB**（警告线） | 超过 5GB 后备份/迁移明显变慢，VACUUM 变慢 |

## 四、两个低成本优化（立竿见影）

### 4.1 `busy_timeout = 5000`（已撤回，不适用于当前本地驱动）

**复核结果**：这项改动已撤回。对当前 `@libsql/client@0.14.0` 的 file driver，`busy_timeout` 会在本地 `BEGIN IMMEDIATE` 锁等待中阻塞 Node 调用路径；10 并发 CAS 对照中，0ms 为 178.599ms，5000ms 为 47,003.975ms，正确性和重试次数没有改善。

**当前方案**：维持 SQLite 默认 `busy_timeout=0`，仅使用 `withDbTransaction` 的 5 次、50ms 起步异步指数退避。该等待由 `setTimeout` 让出事件循环，不会把整台单 Node 服务卡在原生锁等待中。详细测试条件和边界见 `docs/147_SQLite容量基准测试与复核结论_2026-08-08.md`。

### 4.2 非秒杀活动也改用计数器

**当前**：非秒杀活动的容量检查用 `INSERT ... WHERE (SELECT COUNT(*) FROM lottery_entries WHERE draw_id = ?) < maxParticipants`，每次 join 都做全活动 COUNT。

**建议**：对普通活动也使用 `activeParticipantCount` 计数器（与秒杀同一机制），消除 COUNT 子查询。

**限制**：普通活动、候补、取消、开奖等生命周期不与直付秒杀共享同一计数语义。这不是一行性能优化，必须先定义独立的不变量、补齐迁移回填和并发测试；不得用本节的历史数字推导"20 万+"容量。

## 五、预警线（什么时候必须换架构）

```
触发任一条件即考虑升级，不要等到爆炸：

1. 单场秒杀想 >5 万名额 / 瞬时 >2,000 TPS 写
   → 写锁是物理极限，需队列削峰（Redis 排队 + 异步落库）或迁 PostgreSQL

2. activity_events 超过 500 万行
   → 上归档任务（月归档到冷表/文件），否则索引膨胀拖慢所有查询

3. 单活动参与者想 >10 万人
   → COUNT 子查询 + 全量开奖加载都会超 1 秒，必须改用计数器

4. 需要多租户实时用量看板
   → 当前快照表已规避，但若需要实时数据，COUNT 仍是瓶颈

5. 数据库文件超过 5GB
   → 备份/迁移时间变长，VACUUM 需要数分钟
```

## 六、复核结论

1. SQLite 的单写者模型、直付秒杀 CAS 计数器和普通活动 COUNT 热路径都是代码事实。
2. 本文中的具体 TPS、RPS、容量、磁盘阈值和运行月份没有目标 VPS 的端到端压测证据，不能称为"完全够用"或"物理极限"。
3. `busy_timeout=5000` 已经经过对照基准并撤回；不能以 SQLite 内部阻塞等待替代 Node 应用层异步退避。
4. COUNT 热路径存在且应持续监控，但是否需要为普通活动引入另一个计数器，必须先用 `docs/147` 的数据和业务不变量做决定。

后续准入标准：先在实际 VPS 运行 `npm run benchmark:sqlite`，再补 Hono 公开参与、支付回调、发卡和事件上报的混合压测；只有同时满足正确性、p95/p99 和错误率目标，才可给出容量运营阈值。
