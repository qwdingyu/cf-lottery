> 文档编号：006
> 创建时间：2026-07-31

## 一、核心问题：谁会付费？

### 1.1 残酷的现实

005 号文档写了 Free/Pro/Enterprise 三档套餐，但需要直面一个核心问题：**抽奖 SaaS 本身不是一个能独立收费的产品。**

原因：

| 因素 | 说明 |
|------|------|
| 替代品太多 | Google Forms + 随机数生成器 = 免费；微信群发工具 + 截图 = 免费 |
| 使用频率低 | 一个企业一年办 1-2 次年会，不会为"抽奖"单独付费订阅 |
| 决策链短 | 社群运营/博主/老师自己就决定了，不会去申请预算 |
| 价值感知弱 | "抽奖"看起来太简单了，用户觉得不值钱 |
| 付费意愿低 | 抽奖是锦上添花，不是刚需 |

**结论：不要把 cf-lottery 定位为"卖抽奖功能的 SaaS"，这条路走不通。**

### 1.2 正确的商业模式

抽奖功能本身不是付费点，但抽奖作为**增值功能嵌入到更大的产品中**才有人买单：

| 真实场景 | 谁买单 | 为什么愿意付钱 | 定价模式 |
|---------|--------|-------------|---------|
| 企业年会/活动平台 | 活动策划公司 | 他们需要给客户提供"专业抽奖"服务 | 按活动收费 |
| 电商促销工具 | 电商 SaaS 平台 | 他们需要抽奖功能留住商家 | 平台抽成 |
| 培训机构 | 在线教育平台 | 课程打卡送礼品，增加完课率 | 按使用量 |
| 私域运营工具 | SCRM 系统 | 社群抽奖是私域运营标配功能 | 功能打包 |

**正确的产品定位：不是"抽奖 SaaS"，而是"抽奖引擎"——一个可嵌入、可白标、可 API 调用的抽奖能力组件。**

## 二、Free/Pro/Enterprise 三档套餐的修正

### 2.1 原方案的问题

| 维度 | 原方案 | 问题 |
|------|--------|------|
| 定价 | Free 免费 / Pro 按月 / Enterprise 按年 | 谁付月费？谁会为"抽奖"单独申请预算？ |
| 功能差异 | 活动数/参与人数/码数 | 这些差异不足以让用户付费，因为免费版已经够用了 |
| 目标用户 | 模糊的"租户" | 没区分个人用户、企业用户、平台用户 |

### 2.2 修正后的方案

**放弃三档通用套餐，改为按使用场景定价：**

| 方案 | 目标用户 | 定价 | 核心价值 |
|------|---------|------|---------|
| **开源版** | 开发者/自建 | 免费 | 自己部署，无限使用，无支持 |
| **托管版** | 个人用户/小团队 | 免费 | 注册即用，有活动数限制，带品牌标识 |
| **白标版** | 企业/活动公司 | 按年收费 | 去除品牌标识，自定义域名，优先支持 |
| **嵌入版** | SaaS 平台 | 按调用量 | API 接入，嵌入到第三方产品中，自定义 UI |

### 2.3 定价策略详解

#### 开源版（免费）
- 完整功能，无限制
- 自己部署到 Cloudflare Workers
- 社区支持（GitHub Issues）
- 价值：**开发者自建，零成本**

#### 托管版（免费）
- 单租户最多 5 个活动
- 单活动最多 500 参与者
- 带 "Powered by cf-lottery" 标识
- 邮件通知使用平台模板
- 价值：**个人用户零成本使用**

#### 白标版（¥1999/年）
- 无活动数限制
- 去除品牌标识
- 自定义邮件模板和发件人
- 自定义域名
- 优先技术支持
- 价值：**活动公司可以直接拿来服务客户，看起来像自己的产品**

#### 嵌入版（按量计费）
- API 调用次数收费（如 ¥0.01/次参与）
- 定制 UI 组件
- Webhook 回调
- 技术支持 SLA
- 价值：**SaaS 平台省去自研抽奖功能的成本，一个月几百块搞定**

### 2.4 为什么这个方案更可行

| 方案 | 付费的驱动力 | 用户画像 |
|------|------------|---------|
| 开源版 | 自己部署，无依赖 | 开发者、技术团队 |
| 托管版 | 即开即用，不用自己管 | 个人博主、社群运营、小商家 |
| 白标版 | 去除品牌，看起来像自研 | 活动策划公司、数字营销公司 |
| 嵌入版 | 嵌入到现有产品中 | 教育培训 SaaS、SCRM 厂商、电商平台 |

**白标版和嵌入版才是真正能产生收入的方向，因为用户不是"买抽奖"而是"省钱省时间"。**

## 三、产品定位的重新定义

### 3.1 原来（005 文档）

> 轻量、多租户、自助服务的抽奖 SaaS 平台

**问题：** 这是从技术角度定义的，不是从市场角度。

### 3.2 修正后

> **抽奖能力即服务（Lottery-as-a-Service）——可嵌入、可白标、可自己部署的抽奖引擎**

**三层含义：**

1. **可嵌入**——第三方平台通过 API/Webhook 集成抽奖功能，不用自己开发
2. **可白标**——活动公司拿来直接服务客户，看不出是第三方产品
3. **可自己部署**——开发者一键部署到自己的 Cloudflare 账号，数据完全自控

### 3.3 产品形态对比

| 形态 | 说明 | 收费模式 | 竞争力 |
|------|------|---------|-------|
| 独立网站 | 用户注册使用 | 免费（带广告/标识） | 低——替代品太多 |
| 白标服务 | 企业购买后贴牌 | 年费 | 高——省去自研成本 |
| API 服务 | 嵌入到第三方平台 | 按量计费 | 高——平台省功能开发时间 |
| 开源项目 | 开发者自部署 | 免费（社区） | 高——建立生态和口碑 |

## 四、005 文档中其他需要修正的问题

### 4.1 过度设计

| 原内容 | 问题 | 修正 |
|--------|------|------|
| 6 种角色（Owner/Admin/Operator/Viewer/Platform Owner/Support） | 多租户 SaaS 的典型陷阱——想太多 | MVP 只做 2 种：租户 Owner + 平台 Owner |
| 5 种开奖模式（manual/scheduled/instant/batch/weighted） | batch/weighted 短期内不会有人用 | MVP 只做 manual + scheduled |
| 3 种奖品模式（digital_link/physical） | 数字链接需要存储系统，实物需要地址收集系统 | MVP 只做 code + manual_fulfillment |
| 套餐管理 | 没人会付费买套餐 | 改为开源版 + 托管版 + 白标版 + 嵌入版 |

### 4.2 遗漏的关键功能

| 功能 | 重要性 | 说明 |
|------|--------|------|
| 活动复制 | P1 | 运营者经常需要创建相似的活动，复制功能减少重复操作 |
| 参与者黑名单 | P1 | 防止恶意参与（同一人多个邮箱参与同一活动） |
| 开奖结果公示页 | P1 | 中奖名单可公开查看，增加公信力 |
| 活动二维码生成 | P1 | 线下活动需要打印二维码供参与者扫码 |
| 多语言 | P2 | 005 文档写了 i18n 但没单独提 |

### 4.3 数据模型问题

| 原设计 | 问题 | 修正建议 |
|--------|------|---------|
| `lottery_draws.max_participants` 默认 5000 | 5000 人候选池全读入内存可能 OOM | 改为分批读取，每批 500 人 |
| 没有 `lottery_draws.template_id` | 无法支持活动模板 | 增加 `template_id` 字段，支持从模板创建 |
| 没有 `lottery_entries.banned` | 无黑名单功能 | 增加 `banned` 字段 |
| `prize_codes.status` 只有 available/issued | 缺少 expired/refunded | 增加 status 枚举值 |

### 4.4 API 设计问题

| 原设计 | 问题 | 修正 |
|--------|------|------|
| 所有列表 API 无分页参数 | 数据量大时 OOM | 所有 GET 列表接口必须支持 `limit` 和 `offset` |
| 导出 CSV 无异步支持 | 大活动导出可能超时 | 改为异步生成，先创建导出任务再下载 |
| 无批量操作 API | 运营者需要批量删除/发布活动 | 增加批量操作端点 |

## 五、总结

### 005 文档中正确的部分
- ✅ 多租户隔离设计
- ✅ 四种参与模式（open/roster/password/invite_code）
- ✅ 公平性验证机制
- ✅ 数据模型基础设计
- ✅ API 路由结构

### 需要修正的部分
- ❌ Free/Pro/Enterprise 三档套餐（不切实际）
- ❌ 过度设计的角色权限体系
- ❌ 过多的一步到位功能（batch/weighted 开奖等）
- ❌ 缺少黑名单、活动复制、二维码等关键功能
- ❌ 列表 API 无分页、导出无异步

### 最终建议

**cf-lottery 的定位应该是一个"抽奖引擎"（Lottery Engine），而不是"抽奖 SaaS"（Lottery SaaS）。**

- 开源免费，建立社区和口碑
- 托管版方便个人用户即开即用
- 白标版面向活动公司和平台方，这才是真正的收入来源
- 嵌入版面向 SaaS 平台，按量计费

不要试图靠"卖抽奖功能"赚钱——用户不会为这么简单的功能按月付费。要让用户觉得"省钱了"而不是"花钱了"。
