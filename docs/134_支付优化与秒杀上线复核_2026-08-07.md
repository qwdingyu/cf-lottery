## 2. 秒杀安全复核

### 已有防线

1. **硬截单防超卖**：参与写入使用条件 `INSERT ... WHERE COUNT(*) < cap`，秒杀优先采用 `flashSale.stockLimit`，再回退 `maxParticipants`。
2. **秒杀不走候补**：`signup_chain + waitlist` 对普通活动可放行，但秒杀活动明确不做候补，满额即拒绝。
3. **无名额 fail closed**：秒杀未配置有效名额时，后端容量条件为 `1 = 0`，不会因为前端漏配而超发。
4. **支付订单幂等**：`payment_orders.entry_id` 唯一，一条参与记录最多一张支付单；pending 可重生支付入口，paid 不重复发卡。
5. **卡密原子领取**：支付回调事务内领取一张 `available` 卡密并写 `issued`，重复回调不会重复发卡。
6. **区块链支付不进当前目录**：USDT/TRC20 暂不在当前直付自动发卡 catalog，避免确认策略不足导致误发卡。

### 仍需关注

1. **高并发 COUNT 成本**：当前硬截单语义正确，但每次参与都要按活动 COUNT。大流量秒杀后续应引入活动级计数快照或独立库存 CAS，以降低 Turso rows read 和热点写压力。
2. **机器人/羊毛党**：open + email 模式依赖 OTP/限流和邮箱唯一性，不等于强实名。高价值卡密活动应启用名单、邀请码、密码或注册模式；直付发卡目前注册模式会被发布预检阻断，直到 user_id 授权查询设计完成。
3. **未支付占位**：pending 订单 30 分钟懒过期并软释放，但同一 entry 不能重新参与。用户可以通过原订单继续支付或重试，运营上要接受“抢到名额但未支付”的窗口期。
4. **真实支付回调**：代码已处理验签、金额/币种、租户匹配和幂等，但 EasyPay/ZPay 具体网关仍必须真实联调。

## 3. 多次组织与灵活性

可以多次组织秒杀，推荐按“一个活动 = 一个秒杀场次”管理：

1. 新建活动配置不同 `publicSlug`、时间窗口、`flashSale.stockLimit`、价格和码池。
2. 每个活动独立 `drawId`，参与记录、支付订单、卡密领取都按 `tenantId + drawId` 隔离。
3. 同一租户可连续创建多场，如“12:00 场 / 20:00 场 / 周末场”。
4. 不建议在同一个已开放活动上频繁修改价格、币种、码池奖项或名额；历史订单按创建时金额执行，活动配置变更会增加运营解释成本。
5. 如需“循环秒杀/每日场”，后续应抽象为场次模板 + 自动克隆活动，而不是复用同一 `drawId` 反复清空数据。

## 4. 前端体验复核

当前主流程已经比较顺：

1. 用户参与成功后直接弹出支付单。
2. 支付单展示金额、订单号、状态、二维码和打开支付按钮。
3. 支付中自动 3.5 秒轮询；刷新页面后恢复订单并继续轮询。
4. 用户可手动点“刷新支付状态”，不必完全依赖自动轮询。
5. 支付成功后展示卡密；发卡失败时给出订单保留和联系主办方引导。

还可以继续打磨但不阻断灰度：

1. 二维码渲染失败时，如果 `qrCode` 本身是 URL，应提供可点击备用入口。
2. 支付弹窗可增加“已支付，刷新状态”主按钮权重，减少用户等待焦虑。
3. 管理端活动配置页的直付币种未来也应从后端已启用渠道动态生成；当前已移除 USDT，但仍是静态 CNY/USD/EUR。
4. 高价值活动应展示客服/主办方联系方式，目前只有通用“联系主办方”文案。

## 5. 上线门禁

生产前必须完成：

1. EasyPay/ZPay 小额真实支付，验证 `createPayment → notify callback → paid → issued → 用户查卡`。
2. 生产环境 `CREDENTIALS_ENCRYPTION_KEY` 为稳定的 64 位 hex，且上线后不得随意更换。
3. 支付回调公网地址可从网关访问，路径为 `/api/payments/:tenantId/easypay/callback`。
4. 直付活动码池数量大于等于可售名额。
5. `npx tsc --noEmit`、`npm run type-check:frontend`、`npx vitest run`、`npm run frontend:build` 全绿。

生产后建议先灰度一个租户、一场小额活动，确认订单、回调、发卡、人工补发、退款处理 SOP 后再放大。
