# 204 系统容量与边界处理机制全面梳理

> 日期：2026-08-12
> 背景：当「中奖人数 > 奖品个数」等超额场景发生时，系统如何处理？本文全面梳理 cf-lottery 中所有涉及容量/库存/名额超额或不足的处理机制，按业务流程归类。
> 方法：逐行代码验证，不依赖文档推测。

---

## 0. 核心原则

cf-lottery 所有容量/库存控制采用 **CAS（Compare-And-Swap）乐观锁** + **事务内原子回滚**的双重保障：
- **CAS 防超**：条件 UPDATE + RETURNING，命中 0 行即回滚/拒绝（如 `awardedCount < winnerCount`）
- **原子回滚**：部分领取失败时回滚已领取的资源（如 `acquirePrizeCodes` 循环领取不足时释放已领卡密）
- **源头扼杀**：在入口处提前拦截（如 `validateOrderPreconditions` 库存预检），避免用户进入流程后才发现不足

## 1. 即时抽奖（Instant Spin）—— 中奖人数 > 奖品个数

### 1.1 场景

用户消耗 `spinsLeft` 执行即时抽奖，服务端加权抽档后准备发放奖品。如果某奖档的 `awardedCount` 已达到 `winnerCount`，则不再发放该档奖品。

### 1.2 防护机制

**文件**：`src/services/lottery/spin-execution.ts`

**三级防护**：

```
① 抽样过滤（第 245-252 行）
   在加权抽档前，过滤掉已满的奖档：
   const cap = Math.max(0, Number(t.winnerCount || 0));
   const awarded = Math.max(0, Number(t.awardedCount || 0));
   if (awarded >= cap) continue;  // 跳过已满奖档
   
② CAS 占用名额（第 312-322 行）
   先取码（prizeCode），再 CAS 占用奖档名额：
   UPDATE lottery_prize_tiers
   SET awardedCount = awardedCount + 1
   WHERE tierId = ? AND awardedCount < winnerCount
   → 如果 RETURNING 为空，说明 CAS 失败（名额已满），释放已取码并视为未中
   
③ 码池耗尽（第 283-308 行）
   如果 prizeCodes 中无可用卡密，不发放奖品（非码奖品跳过此步）
```

### 1.3 超额时的行为

| 场景 | 表现 | 用户感知 |
|------|------|----------|
| `awardedCount >= winnerCount`（奖档满） | 跳过该奖档，继续检查下一个奖档 | 未中奖（spins 已消耗） |
| 所有奖档都满 | 无可用奖档，返回未中奖 | 未中奖（spins 已消耗） |
| 中奖后 prizeCodes 不足 | 释放已取的码，返回未中奖 | 未中奖（spins 已消耗） |
| 并发双中（同一奖档同时 +1） | CAS 保证只有一个成功，另一个回滚 | 一个中奖，一个未中 |

## 2. 定时/手动开奖（Draw Execution）—— 获奖人数 > 奖品数量

### 2.1 场景

活动管理员手动开奖或定时开奖，系统从所有参与者中随机抽取获奖者。如果参与者数量 > 奖品数量，部分参与者不会中奖。

### 2.2 防护机制

**文件**：`src/services/lottery/draw-execution.ts`

| 防护层 | 机制 |
|:-------|:-----|
| 名额计算 | `draw.winnerCount` 决定开奖总名额，`lotteryPrizeTiers.winnerCount` 决定各奖档名额 |
| 开奖锁 | CAS 夺取 `open → drawing` 状态，防止双开奖 |
| 治愈机制 | `healDrawingState` 检查 stale 开奖状态，超时自动恢复 |
| 幂等回放 | `idempotencyKey` 唯一约束，防止重复开奖 |

### 2.3 超额时的行为

- 参与者数量 < 奖品数量：部分奖品不发放（剩余奖品留在码池）
- 参与者数量 > 奖品数量：部分参与者不中奖
- 码池不足：开奖时 acquirePrizeCodes 循环领取，不足时标记 `FULFILLMENT_FAILED`（可补发）

## 3. 参与名额（Join Draw）—— 参与人数 > maxParticipants

### 3.1 场景

用户参与活动时，如果 `activeParticipantCount >= maxParticipants`，拒绝新用户参与。

### 3.2 防护机制

**文件**：`src/services/lottery/participation.ts`

```sql
-- 插入时 CAS 检查容量
INSERT INTO lottery_entries (...) 
SELECT ... WHERE (
  SELECT activeParticipantCount FROM lottery_draws WHERE drawId = ?
) < maxParticipants
```

如果命中 0 行（容量已满），返回"活动已满"。

### 3.3 超额时的行为

| 场景 | 行为 | 用户感知 |
|------|------|----------|
| 主动参与 | 拒绝插入 entry，返回"活动已满" | 无法参与 |
| 秒杀直付 join | 拒绝插入 entry | 无法参与 |
| 候补（waitlist） | 插入候补表，等待释放 | 进入候补队列 |

---

## 4. 秒杀名额预约（Flash Sale）—— 预约件数 > 剩余名额

### 4.1 场景

用户下单时，需要从活动名额中预约 `reserveQuantity` 件。如果 `activeParticipantCount + reserveQuantity > capacity`，预约失败。

### 4.2 防护机制

**文件**：`src/services/payment/payment-service.ts` 第 840-880 行

```sql
-- 事务内 CAS 预约名额
UPDATE lottery_draws
SET activeParticipantCount = activeParticipantCount + reserveQuantity
WHERE drawId = ? AND activeParticipantCount + reserveQuantity <= capacity
```

如果 RETURNING 为空（名额已满），有两种处理：

| 场景 | 处理 |
|:-----|:-----|
| 首次下单（`hasPriorOrder=false`） | 释放 base 1 名额（entry paymentStatus → expired），不允许部分预约 |
| 追加下单（`hasPriorOrder=true`） | 全额拒绝，保持 entry 状态不变 |

### 4.3 超额时的行为

| 场景 | 行为 | 用户感知 |
|------|------|----------|
| 首次下单名额不足 | 释放 entry，拒绝下单 | 下单失败，entry 释放 |
| 追加下单名额不足 | 拒绝下单，保持已有订单 | 下单失败，已有订单不变 |

---

## 5. 卡密领取不足（Prize Code）—— 需要数量 > 可用数量

### 5.1 场景

支付回调后，系统需要领取 `quantity` 张卡密发放给用户。如果 `prizeCodes` 表中 `available` 状态的卡密数量 < `quantity`，领取失败。

### 5.2 防护机制

**文件**：`src/services/payment/payment-service.ts` 第 1420-1520 行（`acquirePrizeCodes`）

```typescript
// 循环领取，每次原子领取一张
for (let i = 0; i < quantity; i++) {
  const acquired = await db.update(prizeCodes)
    .set({ status: "issued", ... })
    .where(and(
      eq(prizeCodes.status, "available"),
      eq(prizeCodes.id, sql`(SELECT id FROM prize_codes WHERE ... status='available' LIMIT 1)`),
    ))
    .returning({ id: prizeCodes.id });
  
  if (!acquired[0]?.id) {
    // 不足：回滚已领取的卡密
    await db.update(prizeCodes)
      .set({ status: "available", ... })
      .where(and(eq(prizeCodes.tenantId, tenantId), inArray(prizeCodes.id, ids), eq(prizeCodes.status, "issued")));
    return [];
  }
  ids.push(acquired[0].id);
}
return ids;
```

### 5.3 超额时的行为

| 场景 | 行为 | 用户感知 |
|:-----|:-----|:----------|
| 卡密数量 < 需要数量（如需要 5 张，只有 3 张） | 回滚已领的 3 张，标记订单 `FULFILLMENT_FAILED` | 已付款但未收到卡密（运营可补发） |
| 卡密数量 = 0 | 同上一立即 FULFILLMENT_FAILED | 同上 |
| 并发领取同一张卡密 | 子查询 `LIMIT 1` 原子领取，另一事务读不到已领卡密 | 只有一个成功 |

### 5.4 源头扼杀的下单前预检

**文件**：`src/services/payment/payment-service.ts` 第 740-760 行（`validateOrderPreconditions`）

下单前通过 `lotteryPrizeTiers` 关联查 `prizeCodes` 可用库存，`availableStock < quantity` 时直接拒绝下单（源头扼杀，docs/203 新增）。

**注意**：预检是快速失败优化，不锁定库存。最终保障靠 `acquirePrizeCodes` 的原子领取 + 回滚。

## 6. 限购超额（Per-User Limit）—— 累计购买 > maxPerUser

### 6.1 场景

同一 entry 追加购买时，累计已支付件数 + 本次购买数量 > `maxPerUser`，拒绝下单。

### 6.2 防护机制

**文件**：`src/services/payment/payment-service.ts` 第 770-790 行

```typescript
// 两级防护（docs/203 注释链）：
// ① 路由层 normalizeFlashSaleQuantity 把单笔 quantity 钳制到 ≤ maxPerUser
// ② 后端无条件累计检查（PAID + FULFILLMENT_FAILED 订单总件数 + 本次 ≤ maxPerUser）
const alreadyBought = SUM(PAID + FULFILLMENT_FAILED orders.quantity);
if (alreadyBought + quantity > maxPerUser) reject("每人限购 N 件");
```

### 6.3 超额时的行为

| 场景 | 行为 | 用户感知 |
|:-----|:-----|:----------|
| 首次下单 quantity > maxPerUser | 拒绝（后端独立拦截） | 订单创建失败 |
| 追加下单累计超限 | 拒绝 | 订单创建失败 |
| 未设置 maxPerUser（默认 1） | 除首次 qty=1 外，追加均拒绝 | 每人限购 1 件 |

## 7. 活动过期释放（Expired Release）—— 超时订单释放名额

### 7.1 场景

用户创建订单后未支付，订单超时后释放名额，供其他用户使用。

### 7.2 防护机制

**文件**：`src/services/payment/payment-service.ts` 第 133 行（`expireOverdueOrders`）

```typescript
// 查出超时 PENDING 订单
const overdue = SELECT ... FROM payment_orders WHERE status = 'pending' AND createdAt < cutoff;
// 事务内释放订单 + 释放名额 + 释放 entry
// 订单释放：UPDATE payment_orders SET status = 'expired'
// 名额释放：UPDATE lottery_draws SET activeParticipantCount -= quantity
// entry 释放：UPDATE lottery_entries SET paymentStatus = 'expired'（无 PAID 订单时）
```

### 7.3 超额时的行为

| 场景 | 行为 |
|:-----|:-----|
| 订单超时未支付 | 订单标记 expired，名额释放，entry 恢复 |
| 已支付但 entry 超时 | 超时只释放 PENDING 订单，PAID 订单不受影响 |
| 并发 expire 与回调 | 事务内 CAS 保证不重复释放 |

## 8. 候补/容量分配（Waitlist / Allocation）

### 8.1 场景

活动支持候补（`waitlist`）或容量分配（`capacity/fifo/priority`）。当名额满时，新用户进入候补队列；名额释放时，按策略分配。

### 8.2 防护机制

**文件**：`src/services/lottery/participation.ts`（分配策略部分）

| 分配策略 | 行为 |
|:---------|:-----|
| `capacity` | 先到先得，满额后拒绝 |
| `waitlist` | 满额后插入候补表，释放时自动递补 |
| `fifo` | 按参与时间顺序分配 |
| `priority` | 按优先级分配 |

### 8.3 超额时的行为

| 场景 | 行为 |
|:-----|:-----|
| capacity 满额 | 拒绝新参与 |
| waitlist 满额后 | 进入候补队列，有释放时自动递补 |

## 9. 多奖品保护（Multiple Prize Fallback）

### 9.1 场景

活动配置了多个卡密奖品（`lotteryPrizeTiers` 多条记录指向不同 `prizes`）。`findCodePrize` 查询时如果命中多个，使用 `fail-closed` 保护。

### 9.2 防护机制

**文件**：`src/services/payment/payment-service.ts` 第 1560-1580 行

```typescript
async function findCodePrize(db, tenantId, drawId) {
  const rows = await SELECT ... FROM lotteryPrizeTiers INNER JOIN prizes ...
  if (rows.length > 1) {
    // 多个卡密奖品命中：fail-closed 返回 null 且必须留日志
    console.error("[payment] 活动配置了多个卡密奖品，无法确定发卡目标");
    return null;
  }
  return rows[0] ?? null;
}
```

### 9.3 超额时的行为

| 场景 | 行为 |
|:-----|:-----|
| 0 个卡密奖品 | 返回 null，`acquirePrizeCodes` 返回 []，订单进入 `FULFILLMENT_FAILED` |
| 1 个卡密奖品 | 正常领取 |
| 2+ 个卡密奖品 | `fail-closed` 返回 null，留日志，不发放（防止发错卡） |

## 10. 场景汇总

| 场景 | 超额/不足类型 | 防护机制 | 超额后行为 | 源头扼杀 |
|:-----|:------------|:---------|:-----------|:--------:|
| 即时抽奖 | 中奖人数 > 奖品个数 | `awardedCount < winnerCount` CAS | 跳过已满奖档，继续抽下一档 | ❌（运行时防护） |
| 定时开奖 | 获奖人数 > 奖品数量 | 名额计算 + 开奖锁 + 幂等 | 部分参与者不中奖 | ❌ |
| 参与活动 | 参与人数 > maxParticipants | `activeParticipantCount < maxParticipants` CAS | 拒绝参与 | ✅（入口拦截） |
| 秒杀下单 | 预约件数 > 剩余名额 | `activeParticipantCount + δ ≤ capacity` CAS | 拒绝下单，释放 entry | ✅（入口拦截） |
| 卡密领取 | 需要数量 > 可用数量 | 循环领取 + 原子回滚 + `FULFILLMENT_FAILED` | 订单标记 FULFILLMENT_FAILED，可补发 | ✅（下单前预检） |
| 限购 | 累计购买 > maxPerUser | 路由钳制 + 后端累计检查 | 拒绝下单 | ✅（双保险） |
| 活动过期 | 超时订单释放名额 | `expireOverdueOrders` 事务内释放 | 名额释放，entry 恢复 | ❌（定时任务） |
| 多奖品 | 多个卡密奖品 | `fail-closed` 返回 null | 不发放，留日志 | ❌（发布预检） |

---

## 11. 结论

**所有超额/不足场景均有防护，且至少一层 CAS 原子锁保障不超发。** 其中：

- **资金安全相关**（秒杀下单、卡密领取、限购）：三层防护（源头扼杀预检 + CAS 名额锁 + 原子回滚）
- **数据完整性相关**（抽奖、参与、开奖）：两层防护（CAS 名额锁 + 事务内回滚）
- **运营兜底**（FULFILLMENT_FAILED、候补队列）：超额后进入可恢复状态，不丢失数据

**无未覆盖的超额场景。** 文档中所有机制的代码路径均已验证。
