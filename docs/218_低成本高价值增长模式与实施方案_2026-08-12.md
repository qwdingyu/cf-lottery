## 二、优先推荐 4 个模式

### 模式一：保底机制（Pity System） — 优先级 1

#### 现状

- `lottery_entries` 表无 `consecutive_no_win_spins` 字段（schema.ts:377 逐列核对）。
- `performInstantSpin`（spin-execution.ts:90）每次 `weightedPickTier`（spin-quota.ts:228）独立随机，不记忆历史。用户连续 N 次未中无任何补偿。
- 已存在「未中奖安慰券」，但那是活动结束后一次性发放，**不是即时抽奖的连续未中保护**，二者互补。

#### 设计（行业实践：抽卡 / 老虎机常见的「保底」机制）

- **配置**（`promotion_config` JSON）：
  ```json
  {
    "pity": {
      "enabled": true,
      "threshold": 10,
      "refIdPrefix": "pity"
    }
  }
  ```
  - `threshold`：连续未中达到该次数后，下一次 spin **必中奖**（触发档位为当前可抽的最高 sortOrder 档，即最低价值奖）。
  - 缺省 / 未配置 → 不启用，完全不影响现有路径。
- **Schema**：`lottery_entries` 新增 `consecutive_no_win_spins INTEGER NOT NULL DEFAULT 0`。
  - 迁移：`0061_lottery_entries_retention_growth.sql`（与每日免费抽奖合并为同一个迁移文件）。
- **逻辑插入点**（`performInstantSpin` 事务内，抽档之前）：
  1. 事务内读取 entry 最新 `consecutive_no_win_spins`（事务 BEGIN IMMEDIATE 串行化写锁，读到的值一致）。
  2. 满足 `pity.enabled && threshold >= 1 && consecutiveNoWin >= threshold && eligible.length > 0` → 将抽档结果锁定为 `eligible` 中 `sortOrder` 最大（最低价值档）。
  3. 之后走**完全相同**的 award 流程（码 CAS / 档位 CAS），零重复逻辑。
  4. 事务内更新计数器：`won=1` → 重置为 0；未中 → `+1`。
- **审计**：`spins_log` 写入 `refId: "pity:{threshold}"`（保底触发时），reason 沿用 `"spin"`，不新增枚举。

#### 边界说明

- 若保底档在并发下名额耗尽（award CAS 失败），本次视为未中、计数器继续累加——**奖池物理耗尽时无法强发**，属真实约束。
- 保底不改变奖项总量与概率配置，仅改变触发时序，不用改任何概率公式。

#### 成本与价值

| 维度 | 评估 |
|:----|:-----|
| 成本 | 极低：1 列 + 1 配置段 + 事务内约 20 行 |
| 价值 | 极高：直接消除 instant 模式最大用户痛点（连抽全空），显著提升留存 |
| 测试 | ≥3 例：未达阈值不触发；达阈值必中且计数器归零；未中时计数器累加 |

### 模式二：每日免费抽奖（Daily Free Spin） — 优先级 2

#### 现状

- `lottery_entries` 已有 `last_checkin_date` + `checkin_streak`，且签到用「原子条件 UPDATE」保证并发去重（commands.ts:575 `WHERE last_checkin_date IS NULL OR < today`）——**该并发安全模式已在生产验证**。
- 但签到是**社群 bot 功能**（chat 通道），走 `identity_type=platform_user_id` 的 entry；**公开活动页（web）的 spin 流程没有任何「每日免费」机制**。web 用户无每日回访动力。

#### 设计

- **配置**（`promotion_config` JSON）：
  ```json
  {
    "dailyFreeSpins": {
      "enabled": true,
      "count": 1
    }
  }
  ```
  - `count`：每天免费发放的次数（第 1 次 spin 由免费额度支付，不消耗已积累 spins）。
  - 缺省 / 未配置 → 不启用。
- **Schema**：`lottery_entries` 新增 `last_daily_free_spin_at TEXT`（YYYY-MM-DD，NULL=从未领取），与迁移 0061 合并。
- **逻辑插入点**（`performInstantSpin` 事务内，扣次之前）：
  1. 原子条件 UPDATE 领取免费次数：
     ```sql
     UPDATE lottery_entries
     SET spins_left = spins_left + :count,
         spins_total_granted = spins_total_granted + :count,
         last_daily_free_spin_at = :today
     WHERE id = :entryId AND tenant_id = :tenant
       AND (last_daily_free_spin_at IS NULL OR last_daily_free_spin_at < :today)
     ```
  2. `rowsAffected === 1` → 本次 spin **免费**（本次跳过扣次 UPDATE，直接走抽档）；`0` → 今日已领，正常扣次。
  3. `spins_log` 写入 `reason: "daily_free"`（**需扩展 SpinLogReason 枚举**），`refId: "daily_free:{drawId}"`。
- **并发安全**：与签到完全一致，WHERE 条件保证同一自然日内只有一个并发请求能领取成功。
- **与 maxSpinsPerEntry 的关系**：免费次数同时增加 `spinsLeft` 与 `spinsTotalGranted`，维持不变量 `left = granted - used`；是否希望免费次数计入活动硬顶由管理员开关配置决定（启用即代表接受）。

#### 成本与价值

| 维度 | 评估 |
|:----|:-----|
| 成本 | 极低：1 列 + 1 配置段 + 一次原子 UPDATE（约 15 行） |
| 价值 | 极高：web 用户每日回访 → 更多曝光 → 更多转化；模式已在签到侧验证 |
| 测试 | ≥3 例：首次领取成功；当日重复领取被拒（0 rows）；未配置时走原有扣次 |

### 模式三：排行榜奖励（Leaderboard Prize） — 优先级 3

#### 现状

- `share_records` 表已有 `joined_count`（有效邀请人数）、`sharer_entry_id`（分享人 entry），可排序（schema.ts:728）。
- `promotion_config.viral.leaderboardEnabled` 仅控制**前端是否展示**排行榜（viral-weight.ts:148 `isViralLeaderboardEnabled`），后端无排名奖励逻辑。
- `ViralLeaderboard.vue` 展示 Top5 + 我的排名——用户看得到名次，但没有为了名次竞争的理由。

#### 设计

- **配置**（`promotion_config.viral` 内新增，缺省不启用）：
  ```json
  {
    "viral": {
      "leaderboardEnabled": true,
      "leaderboardRewards": [
        { "rank": 1, "rewardType": "bonus_spin", "rewardValue": 3 },
        { "rank": 2, "rewardType": "bonus_spin", "rewardValue": 2 },
        { "rank": 3, "rewardType": "bonus_spin", "rewardValue": 1 }
      ]
    }
  }
  ```
  - 与里程碑阶梯互补：里程碑是**过程奖励**（每个 requireCount 到达即发），排行榜奖励是**结果奖励**（活动结束按名次发）。
- **Schema**：`share_records` 新增 `leaderboard_rewarded_at TEXT NOT NULL DEFAULT ''`（空串=未发放），保证幂等。
- **实现**：新增 `grantLeaderboardRewards(db, draw)`：
  1. 解析 `viral.leaderboardRewards`；空 → 直接返回。
  2. 按 `joined_count DESC, created_at ASC` 取前 N 名 shareRecords（N=最高 rank）。
  3. 对每个未发放的 shareRecord 按名次发放 spins → 更新 `spins_left`/`spins_total_granted`（不冲 `spins_viral_earned` 限额，因为这是运营奖励非裂变加次）；写入 `spins_log`（reason: `"viral"`，refId: `"leaderboard:{rank}"`）；写 `audit_logs`。
  4. CAS 更新 `leaderboard_rewarded_at` 防止并发重复发放；同事务、仅发未发放的。
- **触发时机**：
  - delayed/scheduled/manual：在 `performDraw` 成功收尾后调用（与 `grantLoserRewards` 同位置）。
  - instant：管理员关闭 / 开奖时显式调用（新增 admin endpoint `POST /draws/:id/leaderboard-rewards`），不在公开 spin 热路径执行。

#### 成本与价值

| 维度 | 评估 |
|:----|:-----|
| 成本 | 低：1 列 + 1 配置段 + 1 个服务函数 + 1 个 admin endpoint |
| 价值 | 中高：把「看看而已」的榜单变成竞争目标；与里程碑互补形成完整激励链 |
| 测试 | ≥4 例：正常发放 Top3；同活动重复调用幂等；未配置不动作；多租户隔离 |

### 模式四：分享引导时机优化（未中奖后的分享） — 优先级 4

#### 现状

- 参与成功弹窗 `GameResultModal.vue` 已有完整裂变分享卡片（`viral-enabled` 时展示邀请人数/进度/复制链接）。
- 「我的结果」弹窗（LotteryView.vue:1014）的分享引导 `shareYourLuck` 只出现在**中奖分支**（代码注释「分享你的好运」），**未中奖分支没有任何分享引导**（仅安慰券或「谢谢参与」）。
- 分享归因链路（`/share` API + `share_records`）已完整，无需后端改动。

#### 设计（纯前端）

- 在「我的结果」弹窗的**未中奖分支**增加诚实分享文案与按钮，例如「还差一点！邀请好友获得额外抽奖机会」，点击复用现有 `shareMyWin()` 链路。
- 门禁复用 `shouldShowInviteShareCta(drawStatus)`（public-helpers.ts:137）——活动终态（drawn/cancelled/closed）仍然不推分享。
- 文案走 i18n（新增 `lottery.shareAfterMiss` key），不承诺任何不存在的奖励（分享奖励由 `viral.extraSpinsPerInvite` 配置决定，文案只描述「获得额外抽奖机会」这一事实）。
- 不新增后端接口；不改变分享码生成逻辑。

#### 成本与价值

| 维度 | 评估 |
|:----|:-----|
| 成本 | 极低：纯前端 ~30 行 + i18n key |
| 价值 | 中高：把分享时机从「参与后 / 中奖后」扩展到「未中奖后」（情绪高点后的二次引导） |
| 测试 | 前端组件测试 + 现有 /share 集成测试覆盖 |

## 四、不做清单（明确不做的原因）

| 模式 | 为什么不做 |
|:-----|:-----------|
| 拼团 / 团购 | 多人协作 + 时间窗 + 退款分摊，复杂度 >3 天；现有批发阶梯价已覆盖「多件优惠」 |
| 独立积分体系 | 活动积分已与抓转文档治理约定冲突；spins 次数体系已足够，引入积分会与 spins 混淆 |
| 跨活动累计 / 等级 | 活动级隔离是核心设计原则，跨活动累计破坏隔离审计 |
| 看广告得抽奖 | 广告 SDK 集成 / 合规 / 收益分成等非技术成本高 |
| 多奖池 / 多投入口 | 改动 `weightedPickTier` 核心算法，风险高，收益不确定 |
| 活动后问卷 | 收益低；`survey` 类型已有但未大规模使用 |
