# COUNT 统计误判踩坑记录

> 文档编号：025  
> 日期：2026-08-01  
> 状态：踩坑复盘  
> 背景：在适配 Cloudflare Workers Free + Turso/libSQL Free 时，将“数据库 COUNT 会增加 Turso rows read 和响应延迟”误归因成“直接消耗 Worker CPU”，导致对统计代码的判断过度保守。

---

## 零、依据与边界

本记录只固化当前工程决策，不替代官方限制文档。涉及具体额度时必须重新核对官方页面：

- Cloudflare Workers Limits：`https://developers.cloudflare.com/workers/platform/limits/`
- Turso Plans / Usage：`https://docs.turso.tech/billing/plans`、`https://docs.turso.tech/billing/usage`

当前工程判断：

1. Worker CPU time 关注 Worker 代码实际执行 CPU 的时间；等待数据库网络 I/O 不应被归类为 Worker CPU 热点。
2. Turso/libSQL 的 `rows read`、`rows written`、数据库侧聚合计算和响应延迟是 `COUNT` 的主要约束。
3. 免费层数字会变化，文档可以记录“决策口径”，不要把某个日期的额度数字当成永久事实。

## 一、踩坑总览

| # | 问题 | 根因 | 影响 | 修正 |
|---|------|------|------|------|
| 1 | 把数据库 `COUNT` 风险错误归到 Worker CPU | 混淆 CPU time 与数据库 I/O/计算 | 误判后台统计为高 CPU 风险 | 明确：数据库等待不计 Worker CPU，但消耗 Turso rows read 并增加延迟 |
| 2 | 过度收缩后台低频统计 | 没有区分公开热路径和管理后台低频查询 | 仪表盘累计参与人数被占位化 | 恢复后台低频累计参与人数统计 |
| 3 | “禁止 COUNT”口径过粗 | 没有按索引、频率、数据规模、业务用途分级 | 后续开发容易误删有价值的数据面板 | 建立 COUNT 使用分级准则 |

## 二、事实澄清

### 2.1 Cloudflare Workers CPU

Cloudflare Workers 的 CPU time 计算 Worker 代码主动执行 CPU 的时间。等待 `fetch()`、KV、数据库请求等网络 I/O 不计入 CPU time。

因此：

```text
await db.select().from(...).where(...)
```

等待数据库响应的时间，不应简单归为 Worker CPU 消耗。

### 2.2 Turso rows read

Turso 的 rows read 是数据库侧资源计量。`COUNT(*)`、聚合、无索引查询、范围查询会按数据库实际扫描/触达的行计入 rows read。它的主要风险是：

1. 消耗 Turso 免费层 rows read 配额。
2. 增加数据库计算和请求响应时间。
3. 在公开高频路径上随流量线性放大。

### 2.3 正确结论

```text
COUNT 不是“绝对不能用”。
COUNT 也不是“主要消耗 Worker CPU”。
COUNT 的风险取决于：是否索引命中、扫描范围、调用频率、是否在公开热路径、是否用于强一致额度控制。
```

## 三、COUNT 使用分级准则

| 场景 | 是否允许 | 原因 | 实施要求 |
|------|:--:|------|---------|
| 单活动容量检查：`tenant_id + draw_id` | 允许 | 范围被单活动限制，且有唯一索引前缀支撑 | 只用于活动自身容量，不升级为租户累计额度 |
| 后台低频概览：租户累计参与人数 | 允许 | 低频管理查询，业务价值高 | 必须按 `tenant_id` 过滤，后续接快照表优化 |
| 活动详情数据面板：单活动事件汇总 | 允许 | 租户主动查看，范围是单活动 | 限制 draw_id，必要时分页或缓存 |
| 公开活动页每次访问实时聚合 | 不允许 | 高频访问，容易放大 rows read | 使用活动已有计数字段、缓存或隐藏 |
| 用户参与 `joinDraw()` 中租户级累计 COUNT | 不允许 | 公开热路径，且随参与行数增长 | 用快照表/计数器做套餐用量，不在事务内扫租户全量 |
| 平台运营全租户全表统计 | 不允许直接做 | 扫描面太大 | 定时预聚合、分页巡检、离线报表 |

## 四、本次代码修正

已恢复：

1. `/api/admin/stats` 返回租户累计参与人数：

```text
usage.participants
totalParticipants
```

2. `AdminDashboardView.vue` 的“参与人数用量”从 `0 / ∞` 占位改为读取后台统计值。

仍保持：

1. `joinDraw()` 不做租户级累计参与人数实时 `COUNT`。

3. 租户累计参与人数如果未来要作为强额度，必须先做 `tenant_usage_snapshots` 或写时计数器。

## 五、以后避免再犯

### 5.1 判断资源风险时必须拆成三类

1. **Worker CPU 风险**：高迭代加密、大循环、大 JSON、CSV 拼接、同步排序。
2. **数据库 rows read/write 风险**：COUNT、聚合、无索引、宽范围扫描、索引过多导致写放大。
3. **产品热路径风险**：公开访问、用户参与、Webhook 回调、登录注册等高频入口。

不能把三者混成一句“会超 CPU”。

### 5.2 删除统计前必须回答四个问题

1. 这个统计是在公开热路径、后台低频页，还是定时任务？
2. 查询是否有 `tenant_id` 和必要的业务维度过滤？
3. 当前业务规模下扫描行数是否可接受？
4. 它是展示型数据，还是强一致额度/计费依据？

只有强一致额度和公开高频路径需要优先改成快照/计数器。后台展示型数据可以先保留，但要标注未来优化路径。

### 5.3 文档口径

以后文档中禁止使用模糊说法：

```text
错误：COUNT 会导致 Worker CPU 超限。
正确：COUNT 的数据库等待不计 Worker CPU，但会消耗 Turso rows read、增加数据库计算和响应延迟；是否允许取决于路径频率和扫描范围。
```

## 七、本次误伤判断

结论：**删除后台仪表盘累计参与人数统计属于误伤；删除/禁止公开参与热路径中的租户级累计 `COUNT` 不属于误伤。**

判断理由：

| 代码路径 | 频率 | 用途 | 正确处理 |
|----------|------|------|----------|
| `/api/admin/stats` 租户累计参与人数 | 管理后台低频 | 展示型概览 | 恢复，标注 rows read/延迟成本 |
| `AdminDashboardView.vue` 参与人数卡片 | 管理后台低频 | 展示型概览 | 恢复读取 `usage.participants` |
| `joinDraw()` 用户参与 | 公开热路径 | 参与写入与容量控制 | 只允许单活动容量检查，禁止租户累计 `COUNT` |
| 未来账单/强额度 | 后台/系统级 | 计费和强一致限制 | 必须使用快照表或写时计数器 |

这条结论以后不能再简化为“COUNT 能用”或“COUNT 不能用”。正确说法是：**后台低频、索引过滤、展示型 `COUNT` 可以保留；公开热路径、全租户扫描、强额度/账单依据必须预聚合。**
