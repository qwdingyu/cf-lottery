# 197 SSH 频繁断开导致部署卡顿的根因与一键部署方案

> 日期：2026-08-11
> 类型：踩坑记录（背景 / 原因 / 排查过程 / 解决方案 / 建议）

---

## 一、背景

VPS（38.47.198.72，日本机房，Debian 13）部署 cf-lottery 时，SSH 会话**频繁被远端关闭**（`Connection closed by remote host` / `Connection reset by peer` / `Broken pipe`）。每次部署需要人工反复重连，**耗时 30 分钟以上**，严重拖慢发布节奏。

典型现象：
- `scp` 上传报 `Connection closed by remote host`（文件可能已完整到达或半包，无法确认）
- `ssh` 执行 npm install 等长命令时，会话在数十秒后断开
- 断开无规律，重试可能成功也可能再次断开

---

## 二、原因

排查结论：**非资源问题，是 sshd 配置 + 网络链路双重因素**。

### 2.1 主要因素：sshd `MaxStartups` 并发连接限制

```ini
# /etc/ssh/sshd_config
MaxStartups 3:80:10
```

`MaxStartups 3:80:10` 的含义：
- 允许 **3 个**未认证的并发 SSH 连接；
- 超过 3 个后，**80% 的概率拒绝**新连接（防暴力破解机制）；
- 硬上限 **10 个**。

部署时本地会发起**多个短 SSH 会话**（mkdir、上传、状态检查……），若与并行开发进程（其他 agent / 用户终端 / 监控脚本）的 SSH 会话叠加，未认证连接数瞬时超过 3，新连接即被拒绝或概率性拒绝——表现为"连接被远端关闭"。

### 2.2 次要因素：跨国网络链路波动

日本机房到本地的网络链路存在间歇性丢包/重置，长连接（npm install 动辄 30-60 秒）更容易在链路波动时被中断。本地 `~/.ssh/config` 未配置保活参数时，空闲连接被服务端回收。

### 2.3 排除项（已检查）

| 项 | 结果 |
|----|------|
| 内存 | available 2.4Gi（3.8Gi 总量），充足，非 OOM |
| 负载 | 0.34，极低 |
| ClientAliveInterval | 120s（服务端主动探测，正常） |

---

## 三、排查过程

1. **收集断连模式**：连续部署 3 次，记录断连环节——上传（scp/cat+ssh）与 npm install 期间均发生；
2. **排除资源问题**：`free -h`（内存充足）、`uptime`（负载低）——排除 OOM / 高负载；
3. **检查 sshd 配置**：`grep -E "MaxStartups|ClientAlive" /etc/ssh/sshd_config` → 发现 `MaxStartups 3:80:10`，为并发连接限制的根因；
4. **验证重试可行性**：SSH 命令失败后立即重试通常成功（幂等命令安全）——确认是瞬态拒绝而非持续封禁；
5. **设计对抗方案**：既然 SSH 本身不可靠，从「减少对长连接的依赖」入手——上传自动重试、远端长任务后台化、验证轮询化。

---

## 四、解决方案

### 4.1 核心：一键部署脚本 `scripts/deploy-to-vps.sh`（已重写，2026-08-11）

**用法（替代手动 SSH 三步操作）**：

```bash
# 前提：先构建
bash scripts/build-for-vps.sh

# 一键部署（自动完成：打包 → 上传 → VPS 后台部署 → 轮询验证）
VPS_SSH_KEY=~/.ssh/jp_72_scp-key bash scripts/deploy-to-vps.sh
```

**脚本的三大抗断连机制**：

| 机制 | 实现 | 效果 |
|------|------|------|
| **SSH 保活参数** | 统一 `SSH_OPTS`（`ServerAliveInterval=30, ServerAliveCountMax=10, ConnectTimeout=15, TCPKeepAlive=yes`） | 降低空闲断开概率 |
| **上传自动重试 + 大小校验** | cat+ssh pipe，最多重试 3 次，每次校验远端文件大小 = 本地大小 | 半包/断连自动重传，杜绝"假成功" |
| **远端长任务 nohup 后台化** | 解压 + `npm install --omit=dev` + 维护 timer + `systemctl restart` 全部放入 `nohup bash -c '...'` | **SSH 断开不影响部署继续执行**，本地立即返回 |
| **轮询验证** | 每 10 秒检查 `systemctl is-active` + health，最长 6 分钟，成功才退出 | 无需人工 SSH 确认 |

**部署结果输出**：
```
✅ 部署成功（第 N 次轮询）
   health: {"ok":true,"db":true,"dbError":false}
   远端日志: /tmp/cf-lottery-deploy-<时间戳>.log
```

### 4.2 辅助：本地 `~/.ssh/config` 保活（已配置）

```ssh-config
Host 38.47.198.72
  User root
  IdentityFile ~/.ssh/jp_72_scp-key
  ServerAliveInterval 30
  ServerAliveCountMax 10
  TCPKeepAlive yes
  ConnectTimeout 15
```

### 4.3 可选：VPS 侧 sshd 优化（建议执行，需谨慎）

```bash
# 在 VPS 上执行（root）：
# 1. 修改前先备份并检查语法
cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak
sed -i 's/^MaxStartups.*/MaxStartups 10:30:100/' /etc/ssh/sshd_config
sshd -t && systemctl restart sshd
```

> ⚠️ 风险：修改 sshd_config 前务必 `sshd -t` 验证语法，改错可能导致无法 SSH 登录。
> 已修改后效果：并发未认证连接上限从 3 提高到 10，显著降低部署/多会话时的拒绝概率。

---

## 五、建议

1. **部署一律走 `scripts/deploy-to-vps.sh`**，不要手动 SSH 长连接部署——这是本轮踩坑的最直接教训；
2. **上传用 cat+ssh pipe**（该 VPS 的 scp 会间歇性报错），且必须做文件大小校验；
3. **VPS 侧建议执行 §4.3 的 sshd 优化**，从源头降低并发连接拒绝；
4. **保留 `local-deploy-vps.sh`**（构建+上传分离场景）——它已同步增强上传重试与校验；
5. 若未来仍遇到断连，优先检查 `journalctl -u ssh -n 50` 与 `ss -tlnp | grep :22`，确认是否为连接数峰值触顶。
