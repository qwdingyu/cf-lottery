# 一次性Web访问令牌与跨平台身份绑定

> 日期：2026-08-10  
> 定位：卡密 Web 找回 + QQ/Telegram 身份合并

---

## 1. 背景

### 1.1 卡密私聊失败的闭环断裂

卡密奖品通过私聊投递后，若私聊失败（用户关闭临时会话、适配器异常），用户无法找回卡密。  
此前 `/我的卡密` 命令（Phase A）已实现群内重发，但私聊仍失败时用户彻底无路可走。  
**Web 找回路径缺失构成 P0 闭环断裂。**

### 1.2 跨平台身份隔离

Phase B 为每个 QQ/Telegram 用户创建独立的 `users` + `authIdentities` 记录。  
但同一人同时使用 QQ 和 Telegram 时，两个平台身份指向不同的 `users.id`，  
导致卡密、参与记录等数据无法跨平台聚合。

---

## 2. 解决方案

### 2.1 一次性 Web 访问令牌

**核心思想**：Bot 在 `/我的卡密` 命令中生成一次性 Web 链接，  
用户点击链接即可在浏览器中查看卡密，无需登录。

**设计决策：**
- 令牌明文使用 `crypto.randomUUID()`（36 字符，高熵）
- 库中存储 SHA-256 哈希，防库泄漏后直接窃取可用令牌
- 一次性（`used=1`）+ 短时效（5 分钟），双重安全边界
- 令牌只在私聊消息中下发，不写进群回复（防群内截胡）
- 仅当私聊发送失败时，路由层才将 `accessUrl` 追加到群回复作为降级

**数据流：**
```
用户发送 /我的卡密
  → executeCardCodeCommand
    → 生成 access_tokens 记录（SHA-256(token), userId, expiresAt）
    → 私聊消息中包含：卡密 + 访问链接
    → 返回 { accessUrl, privateMessages }
  → 路由层（platform-qq.ts）
    → 尝试私聊发送（含链接）
    → 私聊失败 → 将 accessUrl 追加到群回复
    → 用户点击链接 → 浏览器打开 AccessCardCodesView
      → GET /api/public/access/card-codes?token=xxx
        → consumeAccessToken: 验证哈希 + 未过期 + 未使用 → 标记已使用
        → 查询 authIdentities → 查询 lotteryEntries → 查询 lotteryWinners
        → 返回卡密列表
```

### 2.2 跨平台身份绑定

**核心思想**：通过 6 位绑定码，让用户在两个平台完成身份关联。

**流程：**
```
1. 用户在 QQ 群发送 /绑定
2. Bot 生成 6 位绑定码，10 分钟有效
3. 用户复制绑定码，在 Telegram 群发送 /绑定 XXXXXX
4. Bot 验证绑定码：
   - 码有效、未过期、未使用
   - 禁止同一平台自我绑定
   - 检查是否已指向同一用户
5. 合并：更新 authIdentities.userId 为发起方用户的 id
6. 尝试清理孤儿用户行
7. 返回绑定成功
```

**安全约束：**
- 绑定码 6 位高熵字符（A-Z 排除 I/O 等易混淆，2-9 排除 0/1），36^6 ≈ 2.2B 种组合
- 10 分钟有效期，一次性使用
- 用户必须能在两个平台分别发送消息（ownership proof）
- 只重写 `authIdentities.userId`，不迁移 `lotteryEntries`（保持存量 UNIQUE 约束）

## 3. 数据模型

### 3.1 access_tokens

| 列 | 类型 | 说明 |
|----|------|------|
| id | TEXT PK | UUID |
| user_id | TEXT NOT NULL | 关联 users.id |
| token_hash | TEXT NOT NULL | SHA-256 哈希，UNIQUE |
| purpose | TEXT DEFAULT 'card_code' | 用途扩展位 |
| expires_at | TEXT NOT NULL | ISO 过期时间 |
| used | INTEGER DEFAULT 0 | 是否已使用（一次性） |
| created_at | TEXT | 创建时间 |

### 3.2 platform_bindings

| 列 | 类型 | 说明 |
|----|------|------|
| id | TEXT PK | UUID |
| code | TEXT NOT NULL | 6 位绑定码，UNIQUE |
| source_provider | TEXT NOT NULL | 发起方平台（qq/telegram） |
| source_provider_user_id | TEXT NOT NULL | 发起方平台用户 ID |
| source_user_id | TEXT NOT NULL | 发起方 users.id（合并目标） |
| expires_at | TEXT NOT NULL | ISO 过期时间 |
| used | INTEGER DEFAULT 0 | 是否已使用 |
| created_at | TEXT | 创建时间 |

## 5. 安全审计

### 5.1 访问令牌安全

| 攻击面 | 防护 |
|--------|------|
| 令牌泄露（URL 被他人截获） | 一次性 + 5 分钟短时效 + 仅私聊下发 |
| 令牌枚举（遍历 UUID） | 128 位熵，不可枚举 |
| 库泄漏后令牌被窃 | 库中存 SHA-256 哈希，不可逆 |
| 并发重复消费 | CAS 式 `used=0` 条件 UPDATE |

### 5.2 绑定安全

| 攻击面 | 防护 |
|--------|------|
| 绑定码被他人盗用 | 6 位高熵 + 10 分钟时效 + 一次性 |
| 绑定码暴力枚举 | 10 分钟内 2.2B 种组合，不可暴力 |
| 恶意绑定（A 绑定 B 的号） | 须同时在两个平台发消息（ownership proof） |
| 重复绑定 | 已检查目标 identity 是否已存在 |
| 跨平台绑定 | 禁止同一平台自我绑定 |

## 6. 闭环验证

### 6.1 卡密私聊失败 → Web 找回

```
用户关闭临时会话
  → Bot 私聊发送失败
  → 路由层捕获异常
  → 将 accessUrl 追加到群回复
  → 用户点击链接
  → 浏览器打开卡密页
  → 一次性令牌被消费
  → 用户看到完整卡密
```

### 6.2 跨平台身份合并

```
用户使用 QQ 参与活动并中奖
  → 用户也使用 Telegram
  → 用户发送 /绑定（QQ 群）
  → 获取绑定码
  → 在 Telegram 群发送 /绑定 <code>
  → 两个身份合并到同一 users.id
  → 在任一平台可查看所有卡密
```

## 7. 注意事项

1. **APP_ORIGIN 环境变量**：必须配置 `APP_ORIGIN`，否则无法生成完整访问链接（降级为纯私聊）
2. **Phase B 前置**：访问令牌依赖 `userId`（Phase B 已关联），若 `provisionPlatformUser` 失败则降级
3. **绑定不会迁移存量数据**：`lotteryEntries` 仍使用 `identityType + identityValue`，不受绑定影响
4. **绑定不可撤销**：当前版本不支持「解绑」，合并后如需分离需走数据库运维
5. **前端构建**：访问页是独立路由，无需 JWT，无需后端渲染
