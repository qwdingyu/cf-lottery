## 三、需要纠正的判断（与上一轮评审的差异）

以下三项在初次评审中被误判，现根据代码事实修正。

### 3.1 游戏组件 Math.random() —— 严重性降级

**原判断：** P0 信任灾难，前端伪结果。

**代码事实（完整数据流）：**

```
步骤 1: 用户点击转盘
  → WheelGame.vue:136  emit('play')
  → WheelGame.vue:138  const targetIndex = Math.floor(Math.random() * props.prizes.length)
  → spinAnimation(targetIndex)  ← 转盘转动 4 秒后停止在随机位置

步骤 2: 同时（事件总线）
  → LotteryView.vue:199  @play="handleJoin(draw.id)"
  → LotteryView.vue:801  showLoginModal = true

步骤 3: 用户输入邮箱 + 验证码
  → LotteryView.vue:859  POST /api/public/draws/:slug/verify-join
  → public-lottery.ts:309  路由处理
  → public-lottery.ts:367  joinDraw(db, slug, email, ...)

步骤 4: 后端处理（lottery-service.ts:1172）
  → 校验资格（名单/密码/邀请码/黑名单/时间）
  → 插入 lottery_entries（事务内）
  → activityKind !== "signup_chain" 时返回 { joined: true }
  → *** 不产生任何 outcome ***
  → 返回 data.outcome === undefined

步骤 5: 前端展示
  → LotteryView.vue:876  if (data.outcome) { ... }  ← 条件为 false
  → LotteryView.vue:885  showToast('参与成功')  ← 无奖品信息
```

**关键事实：**
- `joinDraw` 对抽奖活动（`activityKind === "lottery"`）**从不即时产生结果**
- 前端 toast 显示"参与成功"，不含任何奖品信息
- 实际开奖由 `performDraw`（手动触发或 Cron 定时）单独执行
- 轮盘动画与业务结果之间**没有因果链路**——不是"动画选 A 但后端给 B"，而是"动画选 X 但后端根本没给结果"

**正确判断：** 这是 **UX 混淆问题**，不是数据正确性问题或信任灾难。用户看到转盘停止在"大奖"位置，但提示"参与成功"，产生认知落差。严重级别：**P2 UX 优化**。

**证据链：**
- `WheelGame.vue:136-138` — 动画目标随机
- `LotteryView.vue:870-885` — 结果展示逻辑
- `lottery-service.ts:1319-1322` — 非接龙活动不产生 outcome
- `lottery-service.ts:1050-1059` — defaultResultModeForActivity 对 lottery 返回 manual/scheduled

## 四、代码事实确认的差距

### ❌ 4.1 模板 `resultMode: "instant"` 与实际行为不一致

**严重级别：** 数据语义不一致，可能导致运营者误解。

**代码证据：**

```typescript
// src/lib/activity-templates.ts:38
// 大转盘抽奖模板
defaults: {
  activityKind: "lottery",
  resultMode: "instant",    // ← 标注为即时出结果
}

// src/lib/activity-templates.ts:56
// 刮刮卡抽奖模板
defaults: {
  activityKind: "lottery",
  resultMode: "instant",    // ← 同样标注为即时
}
```

```typescript
// src/services/lottery-service.ts:997
// createDraw 存储 resultMode 到数据库
const resultMode = data.resultMode || defaultResultModeForActivity(activityKind, drawTrigger);
// 模板传入 "instant" 为 truthy 值，resultMode = "instant" 被写入 DB

// src/services/lottery-service.ts:1319-1322
// joinDraw 中——对 lottery 活动不检查 resultMode 字段
if (draw.activityKind !== "signup_chain") {
  return { joined: true, entryId, activityKind: draw.activityKind, attribution };
  // 无任何即时开奖逻辑
}
```

```typescript
// src/services/lottery-service.ts:1050-1059
// 默认值计算：lottery 永远是 manual 或 scheduled
function defaultResultModeForActivity(activityKind, drawTrigger) {
  if (activityKind === "claim") return "instant";
  return drawTrigger === "scheduled" ? "scheduled" : "manual";
  // lottery 永远不会返回 "instant"
}
```

**影响：** 选择"大转盘抽奖"或"刮刮卡抽奖"模板创建的活动，数据库 `result_mode = "instant"`，但参与时无即时开奖行为。运营者在后台看到 `resultMode: "instant"` 会困惑。

`RESULT_MODES` 集合（`admin-lottery.ts:63`）包含了 `"instant"`，说明系统设计上预留了这个模式，但 `joinDraw` 代码路径从未实现它。

**推荐修复：**
- 方案 A（最小改动）：将两个抽奖模板的 `resultMode` 改为 `"manual"`
- 方案 B：在 `joinDraw` 中实现 lottery 的 `instant` 模式——参与成功后立即调用 `performDraw`。但需注意事务边界和超时风险，不推荐当前阶段做。

## 七、架构评价总结

### 做对了的

1. **安全地基扎实。** L2/L3 路由分离、RBAC-lite 中间件、CAS 扣减、crypto 随机——所有 P0 安全边界已闭环。
2. **骨架抽象正确。** activity_kind / participation_mode / experience_type / result_mode 四个独立维度 + 五层骨架（activity → participant → outcome → event → promotion），被抽奖和接龙两个完整实现验证有效。
3. **游戏组件可插拔架构。** GameRegistry 允许增加新体验类型不改 LotteryView，Submit/Reveal/Form/Scratch/Card/Grid 各组件职责清晰。
4. **资源约束认知清晰。** `run_worker_first: ["/api/*"]`、热路径不做全租户 COUNT、快照表替代实时聚合——对 Cloudflare Workers Free + Turso Free 的约束有精准应对。
5. **不做重型系统。** 没有权限矩阵表、没有自定义角色、没有内置支付——这些决策在当前阶段都是正确的。
6. **模板驱动创建。** 从 LandingView 到 AdminLotteryView 的模板选择流，已经实现了"先选目标再选玩法"的产品愿景。

### 需要继续投入的

1. **运营确定性六闸门**中，"能复盘"和"能承接"两个闸门完成度最低（40%/30%），这是下一步产品化的重点。
2. **模板 resultMode 不一致**尽管影响面小，但会让运营者和未来开发者困惑，应尽早修正。
3. **轮盘动画 UX**在抽奖手动开奖模式下不会造成数据错误，但在用户认知层面有优化空间。

### 一句话总结

> 系统已完成的不是"抽奖工具"，而是"可托管运营的活动引擎骨架"。安全地基、路由隔离、模板系统、游戏可插拔架构均为行业最佳实践的务实落地。下一步关键不是加玩法，而是补齐"能复盘、能承接、发布预检"三个产品化体验，让骨架上的肉足以支撑运营者的确定性需求。

## 附录 B：游戏组件接口约定

所有游戏组件的统一接口定义在 `frontend/src/components/games/types.ts`：

```typescript
// Props
interface GameProps {
  prizes: PrizeItem[]    // 渲染用奖品列表
  disabled?: boolean     // 是否禁用交互
}

// Emits
interface GameEmits {
  play: []               // 用户触发操作，父组件调用后端 API
}
```

生命周期：`挂载渲染奖品 → 用户操作 → emit('play') → 父组件调用 API → 展示结果`

关键约束（GameRegistry.ts:15-16）：
> 游戏动画是纯视觉，不决定中奖结果（结果由后端决定）

当前轮盘/老虎机组件的 `Math.random()` 违反了这个接口约定的**精神**（虽未违反字面条文，因为 emit('play') 仍然会触发后端调用）。接口设计是正确的，但动画实现没有体现"等后端结果再展示"的意图。
