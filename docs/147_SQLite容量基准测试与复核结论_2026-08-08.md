# SQLite 容量基准测试与复核结论

日期：2026-08-08

## 一、目的与边界

本文为 `docs/145_单VPS-SQLite容量估算与瓶颈分析_2026-08-08.md` 的证据补充与复核结论。

新增正式脚本：`scripts/benchmark-sqlite-capacity.mjs`。

执行命令：

```bash
npm run benchmark:sqlite
```

脚本只创建系统临时目录下的本地 SQLite 数据库，默认结束即删除。它不读取 `.env`，不连接 Turso、生产 VPS、支付网关或其他外部服务。

脚本启动时会输出 Node、操作系统、架构、逻辑 CPU 核数、`availableParallelism()`、CPU 型号、总内存、启动时可用内存和可选的 `BENCHMARK_LABEL`。在目标机器上建议使用标签保存环境身份，例如：

```bash
BENCHMARK_LABEL=2c2g-vps npm run benchmark:sqlite -- --busy-timeout-ms=0 --cas-requests=500
```

`os.totalmem()` 和 CPU 信息用于确认测试环境，不等于可直接使用的应用配额；若 VPS 运行在容器或存在 cgroup 限制，还必须同时记录容器内存限制和磁盘类型。

本脚本当前只覆盖两个数据库级问题：

1. `lottery_entries` 的活动维度 `COUNT(*)` 是否走现有覆盖索引，以及不同单活动行数下的 p50/p95/p99。
2. 直付秒杀的 `active_participant_count` 条件 UPDATE（CAS）加 entry INSERT，在多连接竞争下是否出现超发、漏写或超过重试上限。

它**不**代表完整 HTTP 吞吐，也不覆盖鉴权、限流、活动读取、支付下单、支付回调、卡密领取、活动事件上报、日志和 nginx。因此脚本输出不能直接转换为生产 RPS、在线人数、年度容量或上线承诺。

## 二、可复现参数

默认参数：

```text
--rows=10000,50000,100000
--count-iterations=50
--cas-requests=500
--busy-timeout-ms=0
```

`--busy-timeout-ms=0` 是有意默认值，用来观察应用层 `withDbTransaction` 风格的 5 次、50ms 指数退避。`busy_timeout` 是连接级 PRAGMA；当前服务每个请求都会创建 libSQL client，评估 5000ms 时必须让每个 CAS 连接单独设置，不能只在种子连接上设置。

推荐在目标 VPS 分两组运行，输出保存到运维记录后再比较：

```bash
npm run benchmark:sqlite -- --busy-timeout-ms=0 --cas-requests=500
npm run benchmark:sqlite -- --busy-timeout-ms=5000 --cas-requests=50
```

第二组先从 10 并发开始。busy_timeout 可能把立即失败改为长时间等待，必须观察脚本总耗时、p95/p99、错误数和重试数，不能只看 TPS。

## 三、2026-08-08 开发机基线

环境：

```text
Node.js v24.14.0
@libsql/client 0.14.0
本地临时 SQLite 文件，WAL，开发机硬件
```

这不是 1C2G VPS，也没有运行 Hono 服务；以下数字只用于反驳未经实测的绝对延迟断言，并作为以后同机回归对照。

### 3.1 COUNT 基线

数据模型使用项目同名表、项目相关字段和三条现有索引：

```text
idx_entries_unique(tenant_id, draw_id, identity_type, identity_value)
idx_entries_identity(tenant_id, identity_type, identity_value)
idx_entries_tenant_draw_payment_status(tenant_id, draw_id, payment_status)
```

`EXPLAIN QUERY PLAN` 对三组数据均返回：

```text
SEARCH lottery_entries USING COVERING INDEX idx_entries_tenant_draw_payment_status
(tenant_id=? AND draw_id=?)
```

原始结果：

| 单活动 entries | p50 | p95 | p99 | 最大值 |
|---:|---:|---:|---:|---:|
| 10,000 | 0.684ms | 1.080ms | 1.098ms | 1.098ms |
| 50,000 | 4.202ms | 5.958ms | 6.353ms | 6.353ms |
| 100,000 | 8.296ms | 10.506ms | 11.236ms | 11.236ms |

160,000 条合成 entries 加三个相关索引后，SQLite 主文件为 68,493,312 字节，约 428.083 字节/entry。此数字不包含完整业务所有表、真实邮箱和 payload 长度、WAL 峰值、空闲页、备份副本或活动事件，因此不能用作磁盘配额。

**结论**：项目当前的 `COUNT(*) WHERE tenant_id = ? AND draw_id = ?` 会命中覆盖索引，确实随单活动行数增长而增长，但“5 万行必然 20~50ms、10 万行必然 50~150ms、30 万行必然不可接受”并非已被代码或这次实测证明。目标 VPS 的结果仍需独立测量。

### 3.2 直付秒杀 CAS 基线

负载模型：500 个独立 libSQL client 同时对同一个活动执行以下短事务，并采用最多 5 次、50ms 指数退避：

1. `UPDATE lottery_draws SET active_participant_count = active_participant_count + 1 ... AND active_participant_count < capacity`
2. 成功后 INSERT 一条 `payment_status='reserved'` 的 entry。
3. 事务提交。

结果：

| 指标 | 结果 |
|---|---:|
| 并发请求 | 500 |
| 成功 | 500 |
| 超卖/漏写 | 0 |
| 数据库 `active_participant_count` | 500 |
| 持久化 entries | 500 |
| 总耗时 | 1,335.248ms |
| 完成速率 | 374.462 次/秒 |
| 成功请求 p50 | 884.256ms |
| 成功请求 p95 | 1,043.683ms |
| 成功请求 p99 | 1,058.889ms |
| 中位重试次数 | 2 |
| 总重试次数 | 998 |

**结论**：CAS 不变量在这次微基准中成立，没有超发或丢写；但高并发下确实出现大量锁竞争和约 0.88 秒的中位端到端等待。这个结果说明“写锁排队是核心风险”是正确方向，却不能证明任何 VPS 能稳定达到 500 或 1,000 TPS。

## 四、busy_timeout 的审查结论

通过新建本地 libSQL client 查询，默认 `PRAGMA busy_timeout` 返回 0；SQLite 新库初始 `journal_mode` 为 `delete`，执行 WAL PRAGMA 后变为 `wal`。这验证了两个实现事实：

1. WAL 是数据库文件状态，需要在实际 VPS 的真实库上查询确认，不能仅凭源码称为“线上已验证”。
2. busy_timeout 是连接级设置。因为当前中间件每个请求创建 client，必须评估每个连接的设置和排队行为。

同一开发机、相同 10 并发 CAS、相同 5 次 50ms 指数退避的完整对照如下：

| busy_timeout | 成功/错误 | 总耗时 | p50 | 总重试 |
|---:|---:|---:|---:|---:|
| 0ms | 10 / 0 | 178.599ms | 165.461ms | 18 |
| 5000ms | 10 / 0 | 47,003.975ms | 46,990.733ms | 18 |

原因不是 SQLite 的正确性变化，而是当前 `@libsql/client@0.14.0` file driver 的 `execute()` 和 `BEGIN IMMEDIATE` 在 JavaScript 调用路径中同步调用原生 SQLite；连接级 busy_timeout 会把锁等待放到单 Node 事件循环中。应用层仍会在超时后执行原有的重试，因此两层等待叠加，未减少重试次数。

**可采纳结论**：`busy_timeout=5000` 不适用于当前“每请求新建本地 libSQL client + 单 Node 进程 + 应用层异步重试”的架构，已从 `src/index.ts` 撤回。保留默认 0 和 `withDbTransaction` 的有界异步退避；未来若更换驱动、连接模型或运行时，必须重新基准，不可复用本结论。

## 五、对 docs/145 的最终判定

可采纳：

1. SQLite 同一时刻只有一个写事务，直付秒杀和支付回调会竞争写锁。
2. 直付秒杀的活动级 CAS 计数器避免了热路径活动 COUNT，且状态机需要继续保证 `reserved/pending/paid/expired` 与计数器一致。
3. 普通活动的 COUNT 是持续性能观察点，不应等到增长后才建立测量。

不可采纳为事实或上线承诺：

1. SQLite 10,000~50,000 TPS、项目 500~1,000 TPS、Node 500~2,000 RPS。
2. 单场名额、同时在线人数、租户数、年度参与量、12~18 个月安全周期。
3. COUNT 在固定行数上的绝对毫秒值。
4. busy_timeout 的固定收益和“系统余量翻倍”。
5. SQLite 理论文件上限等同于单 VPS 的可运营容量。

## 六、后续正式测试矩阵

在实际 VPS 上执行并保存原始 JSON 输出，之后才能设运营红线：

| 优先级 | 场景 | 正确性断言 | 性能指标 |
|---|---|---|---|
| P0 | CAS 500 并发，busy_timeout 0ms | 无超卖、计数器=entries、无未处理错误 | p50/p95/p99、完成率、重试数 |
| P0 | CAS 10/50/100 并发，busy_timeout 5000ms | 同上 | 仅用于新驱动/新连接模型评估；当前 file driver 已判定不采用 |
| P0 | 公开 join + 订单创建 + 支付回调 + 卡密领取混合 | 一单一 entry、一尝试一回调、无重复发卡 | 成功率、p95/p99、BUSY、错误率 |
| P1 | 10 万、30 万、100 万 entries 的普通活动 join | 不超人数、不误候补 | COUNT 计划、p95、事务时长 |
| P1 | 活动事件 page_view/start/completed 混合写入 | 事件不丢失、不影响参与正确性 | 表增长、写等待、磁盘/WAL 增长 |
| P1 | 备份、恢复、WAL checkpoint、VACUUM | 可恢复且校验通过 | 时间、峰值磁盘空间、锁影响 |

只有 P0 通过，才讨论单场秒杀名额和流量阈值；只有 P0/P1 连续运行通过，才讨论 PostgreSQL、队列或独立支付服务的迁移时机。
