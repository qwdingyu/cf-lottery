# 全局产品架构风险与免费层容量评估

> 文档编号：027
> 日期：2026-08-01
> 审查定位：站在 SaaS 平台、增长玩法、导流变现、平台运营、安全边界和 Cloudflare Workers Free + Turso/libSQL Free 资源约束的全局视角，给出可落地的判断。
> 审查边界：本次不修改业务代码；只基于当前仓库文档、当前工作区代码事实和官方限制文档做判断。本文不承诺未验证的性能数字，不声称未闭环能力已经完成。

---

## 一、最终结论

`cf-lottery` 作为“多租户、可白标、可嵌入的轻量活动引擎 SaaS”方向是成立的，但它现在还不能被当作开放式大流量生产 SaaS 使用。

当前最适合的定位是：

```text
小而美的活动引擎
  先服务小团队、社群、课程、门店、本地活动、B2B 获客
  用抽奖、接龙、资料领取、问卷、领券、预约、投票等轻量玩法形成留资和导流闭环
  用模板、导出、白标、嵌入、Webhook、平台运营后台收费
  不做电商、广告交易、复杂 CRM、复杂权限矩阵、佣金结算
```

必须直说：

1. **产品方向可变现，但不是靠“抽奖本身”变现。** 用户付费点在省运营时间、降低人工出错、留资导出、品牌展示、嵌入外部系统、Webhook/API 集成和平台托管能力。
2. **Cloudflare + Turso Free 只能支持受控内测、小规模客户和早期商业验证。** 它不是无限生产底座。真正开放注册、公开推广、承接爆款活动前，必须准备付费层或客户自有部署方案。
3. **当前最大上线风险不是玩法数量不够，而是安全边界、资源边界、平台运营闭环还没完全闭合。** 继续加玩法之前，必须先把 RBAC-lite、平台后台、静态资源路由、限流、事件写入治理和用量快照打牢。
4. **不要为了未来扩展引入重系统。** 当前最佳实践是冻结活动引擎的稳定抽象，只做轻量能力门禁和可观测运营后台；不要做数据库权限矩阵、租户自定义角色、内置支付商城或复杂营销自动化。

## 二、官方约束和本次估算口径

截至 2026-08-01 复核的官方口径：

| 项目 | 官方事实 | 对本项目的影响 |
|------|----------|----------------|
| Cloudflare Workers Free requests | 100,000 requests/day | 这是免费层最直接的硬上限，静态资源和 API 是否都进 Worker 会极大影响容量 |
| Cloudflare Workers Free CPU | 10 ms/request | 不能在请求内做高 CPU 计算、大 JSON 拼装、大 CSV、大循环、复杂排序、高成本密码 KDF |
| Cloudflare Workers memory | 128 MB/isolate | 不能一次性加载大候选池、大导出、大日志全集 |
| Cloudflare Workers subrequests | 50/request | 一个接口不能拆成大量远程调用 |
| Worker CPU 计量 | 等待网络、KV、数据库等 I/O 不计入 CPU time | `COUNT` 不是直接烧 Worker CPU，但会烧 Turso rows read 和增加延迟 |
| Turso Free | pricing 页结构化数据显示 Free: 100 databases、5GB storage、500M monthly rows read、10M monthly rows written | rows read/write/storage 任何一项超限都可能阻断数据库使用 |
| Turso rows read | 被查询触达的行会计入，不只是返回行；聚合函数会扫描被考虑的行 | `COUNT`、聚合、无索引、全表扫描必须按路径频率治理 |
| Turso rows written | 写表和索引更新都会计入 | 事件表、参与表、结果表、Webhook 投递表会共同放大写入 |

参考：

- Cloudflare Workers Limits: https://developers.cloudflare.com/workers/platform/limits/
- Cloudflare Workers SPA routing: https://developers.cloudflare.com/workers/static-assets/routing/single-page-application/
- Turso Pricing: https://turso.tech/pricing
- Turso Usage and Billing: https://docs.turso.tech/help/usage-and-billing.md

本文所有容量结论都是“估算模型”，不是线上承诺。真正上线前必须用真实请求日志、Workers Metrics、Turso rows read/write 数据和压测结果校准。

## 三、当前系统功能面：事实与缺口

### 3.1 已经具备的基础骨架

从当前代码和文档看，系统已经不是单纯抽奖工具，已经具备活动引擎雏形：

| 模块 | 当前事实 | 判断 |
|------|----------|------|
| 租户与用户 | 有 `tenants`、`users`、`tenant_members` | 多租户基础成立 |
| 活动主模型 | `lottery_draws` 已包含 `activity_kind`、`participation_mode`、`experience_type`、`result_mode`、`allocation_policy`、`policy_version`、`promotion_config` | 顶层抽象方向正确 |
| 抽奖 | 活动 CRUD、候选人、开奖、奖品、卡密、邮件通知基础存在 | 第一个玩法基础可用，但仍需安全/体验回归 |
| 接龙 | `signup_chain`、顺序/容量/候补相关逻辑已有基础 | 第二玩法方向正确，但还不是完整运营闭环 |
| 资格模式 | open/roster/password/invite_code 基础存在 | 能覆盖轻量活动常见准入 |
| 导流 | `promotion_config`、事件记录、分享归因、外部转化表基础存在 | 可以支撑导流闭环，但反作弊和外部回传治理不足 |
| Webhook/API Key | 表和投递/重试基础存在 | 能作为付费点，但需要可视化、失败告警、幂等文档 |
| 平台能力 | 工作区已有 `/api/platform/system-config`、`/api/platform/redemption-codes` 草案 | 方向对，但当前前后端和 migration 未完全闭环 |
| 运营配置 | `system_config` 和套餐额度配置基础存在 | 能做轻量 SaaS 运营后端的起点 |

### 3.2 不能误判为“已经完成”的能力

这些能力有字段、表或局部代码，但还不能对外宣称完整：

| 能力 | 为什么不能宣称完成 | 上线前最低要求 |
|------|--------------------|----------------|
| 平台后台 | 前端仍有 `/admin/system-config`、`/admin/redemption-codes` 调用残留，后端迁移到 `/api/platform/*` 尚未完全闭环 | L2/L3 路由、前端菜单、测试、migration 全部对齐 |
| RBAC-lite | 中间件草案存在，但角色枚举、默认角色、路由接入和回归测试仍需核验 | `/api/admin/*` 查 `tenant_members`，`/api/platform/*` 查 `platform_members` |
| 平台成员表 | `schema.ts` 有 `platform_members`，当前 migrations 未看到对应建表文件 | 补正式 migration，否则部署后平台路由会运行时失败 |
| 兑换码平台管理 | 平台路由草案存在，但生成码使用 `Math.random()`，列表空筛选 `.where(and(...conditions))` 可能有实现风险 | 安全随机、唯一冲突重试、分页、审计、测试 |
| 资料领取/问卷/预约/投票/签到 | 主要是枚举和默认规则，缺公开端、管理端、结果层和测试闭环 | 每个玩法按 vertical slice 做完整闭环 |
| 事件归因 | 有事件表和基础上报，但公开事件写入容易被滥用 | 限流、采样、去重、字段长度限制、来源治理 |
| 商业计费 | 有 plan/quota 字段和兑换码基础，不等于商业计费系统 | 先做套餐权益和用量快照，不做支付/退款/发票 |
| 白标/嵌入 | 有 brand_config 基础，不等于白标产品 | 自定义文案、品牌隐藏、嵌入脚本、域名策略需分阶段 |

## 四、真实用户需求和产品适配度

### 4.1 最适合的首批客户

| 客户类型 | 高频任务 | 本系统适配度 | 付费意愿来源 |
|----------|----------|--------------|--------------|
| 社群运营 | 抽奖、报名接龙、候补、资料领取、群活动 | 高 | 节省人工统计和导出时间 |
| 课程/培训 | 报名、预约、资料领取、问卷、签到 | 高 | 名单、导出、通知、复盘 |
| 本地门店 | 领券、预约、到店核销、评价收集 | 中高 | 导流到店和核销审计 |
| B2B 增长 | 白皮书领取、试用码、问卷、预约演示 | 高 | 留资、Webhook、CRM 回传 |
| SaaS/开发者工具 | 内测码、候补名单、功能投票、活动页嵌入 | 高 | 嵌入、API、Webhook、白标 |
| 展会/线下活动 | 签到、抽奖、资料领取、现场投票 | 中高 | 快速部署和现场稳定 |

不适合当前阶段强行服务的客户：

| 客户类型 | 原因 |
|----------|------|
| 超大品牌营销活动 | 免费层请求、反作弊、风控、SLA、合规都不够 |
| 电商平台 | 商品、订单、支付、退款、库存不是当前产品内核 |
| 复杂企业权限客户 | 租户自定义角色、组织架构、审批流会把系统做重 |
| 内容社区/UGC 评选平台 | 内容审核、举报、版权、评论治理过重 |
| 分销返佣平台 | 佣金、结算、税务、风控不应进入当前内核 |

### 4.2 用户真正要买的不是“玩法”，而是运营确定性

抽奖、接龙、问卷这些只是入口。付费用户实际买的是：

1. **快速创建**：模板、复制、二维码、默认规则。
2. **少出错**：资格校验、去重、容量、候补、码池、防重复发放。
3. **能复盘**：浏览、开始、完成、CTA、分享、外部转化。
4. **能承接**：未中奖/候补/提交成功后的 CTA、资料、优惠、下一活动。
5. **能接系统**：Webhook、API Key、导出、外部转化回传。
6. **能托管运营**：平台方能看租户、套餐、用量、失败任务和异常。

因此产品文案和路线不应强调“炫酷抽奖动画”，而应强调“低成本活动获客和权益分配引擎”。

## 五、低成本高价值玩法优先级

### 5.1 核心玩法梯队

优先做共享骨架最高、能直接带来留资/导流/付费价值的玩法：

| 优先级 | 玩法 | 当前架构匹配度 | 用户价值 | 成本判断 | 是否建议进入基线 |
|--------|------|----------------|----------|----------|------------------|
| P0/P1 | 抽奖 | 已有基础 | 福利、传播、权益分配 | 已投入 | 是，第一个稳定模板 |
| P1 | 接龙/报名 | 已有基础 | 社群/课程/活动报名 | 低 | 是，第二个稳定模板 |
| P1 | 资料领取 | 高 | B2B 留资、课程资料、白皮书 | 低 | 是，最适合商业化验证 |
| P1 | 问卷/调研 | 高 | 用户研究、满意度、报名补充信息 | 低 | 是，复用表单 |
| P2 | 领券/核销 | 中高 | 门店/私域导流和到店转化 | 中 | 是，但必须有码池和核销审计 |
| P2 | 限量预约 | 中 | 咨询、课程、门店服务预约 | 中 | 是，先做单资源/单时段 |
| P2 | 投票评选 | 中 | 社群传播、内容评选 | 中 | 可做，但必须限频防刷 |
| P2 | 签到/打卡 | 中 | 复访和训练营运营 | 中 | 可做，先做轻量周期签到 |
| P2 | 候补名单 | 高 | 把满额损失转成潜在客户 | 低中 | 应与接龙/预约一起做 |
| P2 | 审核申请 | 中高 | 内测、试用、白名单、加群申请 | 中 | 可做，复用 outcome |
| P2 | 内测码发放 | 中高 | SaaS/游戏/课程试用 | 中 | 可做，复用 claim/code pool |

### 5.2 适合做成“体验皮肤”的玩法

这些不要改变后端结果模型，只作为 `experience_type`：

| 体验 | 后端本质 | 注意事项 |
|------|----------|----------|
| 转盘 | 抽奖结果展示 | 前端不能自己决定中奖结果 |
| 刮刮卡 | 即时 reveal | 后端先给 outcome，前端只负责揭晓 |
| 翻牌 | reveal/card | 前端视觉随机不等于业务随机 |
| 九宫格 | reveal/grid | 不新增独立玩法主链路 |
| 盲盒 | claim/lottery + reveal | 必须有结果审计 |
| 排队页 | signup_chain/waitlist | 后端返回序号和状态 |
| 日历 | reservation | 先做单资源，后做多资源 |
| 表单 | survey/claim/approval | 字段 schema 要版本化 |

### 5.3 近期不要做的重玩法

| 方向 | 为什么危险 |
|------|------------|
| 积分任务中心 | 会变成营销自动化平台，规则爆炸 |
| 自建商城/支付 | 偏离活动引擎，订单/退款/库存/风控成本过高 |
| 广告交易市场 | 没有流量规模和供需两端，短期是假命题 |
| 分销佣金 | 结算、税务、作弊、争议处理过重 |
| 内容社区 | UGC 审核、版权、举报、评论治理过重 |
| 租户自定义权限 | 会把 RBAC-lite 推向重型权限产品 |

## 六、变现方案：能落地的和不该碰的

### 6.1 最现实的收费结构

推荐采用“托管 SaaS + 受控免费层 + 专业版 + 团队版 + 私有/客户自有部署”的组合：

| 套餐 | 目标客户 | 可收费权益 | 资源策略 |
|------|----------|------------|----------|
| Free | 试用、小活动 | 少量活动、少量参与、带平台品牌、基础模板 | 严格限额，防止免费层被打爆 |
| Pro | 个人运营者、小团队 | 更多活动/参与量、去品牌、模板、二维码、导出 | 仍可共享平台资源，但限制单活动峰值 |
| Team | 课程/社群/B2B 团队 | 成员协作、Webhook、API Key、外部转化回传、更多保留期 | 必须有用量快照和失败投递看板 |
| White-label | 机构/代理 | 品牌、嵌入、独立域名、隐藏平台标识 | 建议付费 Workers/Turso 或独立部署 |
| Enterprise/Private | 大客户 | 自有 Cloudflare/Turso、SLA、定制模板、支持 | 不应跑在平台 Free 资源上 |

### 6.2 最容易成交的付费点

| 付费点 | 为什么能卖 | 实施成本 |
|--------|------------|----------|
| 活动模板库 | 直接节省创建时间 | 低 |
| 活动复制/二维码 | 高频刚需 | 低 |
| 导出 CSV | 运营复盘刚需 | 中，注意流式/分页 |
| 去品牌/白标 | 客户愿意为专业形象付费 | 中 |
| 自定义字段表单 | 留资核心价值 | 中 |
| Webhook/API | B2B 和 SaaS 客户强需求 | 中 |
| 外部转化回传 | 证明导流价值 | 中 |
| 成员协作 | 团队版收费点 | 中 |
| 数据保留期 | 可作为套餐差异 | 低中 |
| 平台额度码 | 可用于代理/人工售卖 | 中 |

### 6.3 不建议近期变现的方向

| 方向 | 结论 |
|------|------|
| 广告分成 | 没有流量规模前不可行，且会伤害用户体验 |
| GMV 抽佣 | 没有订单闭环，无法证明交易金额 |
| 自建支付 | 会把产品拖进电商和财务系统 |
| 高级反作弊包 | 没有足够数据前先不要产品化 |
| AI 自动营销 | 当前不是核心痛点，成本和可信度都不合适 |

## 七、免费层容量评估

### 7.1 当前配置下的最大风险

当前 `wrangler.jsonc` 配置：

```json
"assets": {
  "directory": "./public",
  "binding": "ASSETS",
  "html_handling": "none",
  "not_found_handling": "none",
  "run_worker_first": true
}
```

当前静态资源事实：

```text
public 文件数：562
public 体积：16M
dist 体积：1.6M
```

这意味着最大风险不是 Turso 先爆，而是静态资源请求也可能大量进入 Worker，消耗 Workers Free 的 100,000 requests/day。

对于 Vue SPA，Cloudflare 官方更推荐 `assets.not_found_handling = "single-page-application"`，并可用 `run_worker_first: ["/api/*"]` 让 API 进 Worker、静态资源走资产服务。当前全量 `run_worker_first: true` 适合需要 Worker 先鉴权/注入的场景，但对公开活动页这种高访问入口非常危险。

### 7.2 单个参与者的请求模型

一个公开活动参与者的实际 Worker 请求数取决于静态资源是否进 Worker：

| 场景 | 估算 Worker 请求/参与者 | 说明 |
|------|--------------------------|------|
| 静态资源不进 Worker，API 优化 | 3-5 | 活动加载、事件上报、参与提交、结果查询/CTA |
| 静态资源不进 Worker，但事件较多 | 5-8 | page_view、started、completed、cta、share 等都写事件 |
| 静态资源也进 Worker，首次访问 | 10-40+ | 首屏 HTML、JS、CSS、字体、图片、图标、chunk 都可能消耗请求 |
| 重复访问且缓存命中 | 3-8 | 取决于浏览器/CDN 缓存和事件上报 |

因此容量必须按两个版本估算。

### 7.3 Workers Free 容量估算

官方硬上限：100,000 requests/day。

建议先做预算切分：

```text
总请求预算：100,000/day
公开活动 API：60,000/day
管理后台/API：10,000/day
Cron/Webhook/系统：5,000/day
安全缓冲/静态资源/异常流量：25,000/day
```

在这个预算下：

| 模型 | 公开参与者请求数 | 建议日参与完成量 | 风险 |
|------|------------------|------------------|------|
| 理想 API-only | 4 次/人 | 约 15,000 人/日 | 需要静态资源不进 Worker，事件节制 |
| 稳健模型 | 6 次/人 | 约 10,000 人/日 | 比较适合受控活动 |
| 事件较多 | 8 次/人 | 约 7,500 人/日 | 需要事件采样/合并 |
| 静态资源也进 Worker | 15-20 次/人 | 约 3,000-5,000 人/日 | 当前配置更接近这个风险区 |
| 首访资源很多 | 30+ 次/人 | 约 2,000 人/日以内 | 容易被一次传播打满 |

保守结论：

1. **当前免费层安全运营目标应设为 1,000-3,000 完成参与/日。**
2. **修正静态资源路由、减少事件写入后，可尝试 5,000-10,000 完成参与/日。**
3. **15,000 完成参与/日是理想上限附近，不适合作为 SLA 或销售承诺。**
4. **100,000 参与/日级别必须付费和做架构升级。**

### 7.4 Turso Free 容量估算

官方 pricing 页当前显示 Free: 500M monthly rows read、10M monthly rows written、5GB storage。

在查询都有索引、公开热路径不做全租户统计、后台聚合低频的前提下，Turso 通常不是第一个瓶颈。更可能先被 Workers 100,000 requests/day 限制住。

粗略写入模型：

| 行为 | 可能写入 |
|------|----------|
| 参与成功 | `lottery_entries` 1 行 |
| 非抽奖/接龙结果 | `activity_outcomes` 0-1 行 |
| 事件记录 | `activity_events` 1-5 行 |
| 分享归因 | `share_records` 更新 + `activity_events` 0-1 行 |
| Webhook | `webhook_deliveries` 0-N 行 |
| 外部转化 | `external_conversions` 0-1 行 |

按 2-6 rows written/参与者估算：

| 月参与完成量 | rows written 估算 | 判断 |
|--------------|-------------------|------|
| 50,000/月 | 100,000-300,000 | 很安全 |
| 300,000/月 | 600,000-1,800,000 | 写入仍可控 |
| 1,000,000/月 | 2,000,000-6,000,000 | 接近需要治理事件和索引写放大 |
| 2,000,000/月 | 4,000,000-12,000,000 | 可能超过 Free 写入额度 |

但 Workers Free 每月理论请求约 3M。如果每人 4-8 个 Worker 请求，月参与完成量通常在 375,000-750,000 的理论区间内；考虑管理后台、静态资源、异常流量后，实际应低于这个数。因此在优化良好的情况下，**请求数通常先成为瓶颈，Turso rows written 是第二瓶颈**。

rows read 的危险来自三个地方：

1. 公开热路径做累计 `COUNT`、全租户统计或无索引查询。
2. 平台后台频繁做全表 COUNT/聚合。
3. 事件表、Webhook 表、外部转化表增长后仍直接扫大范围。

`docs/025_COUNT统计误判踩坑记录_2026-08-01.md` 的结论必须继续执行：

```text
后台低频、索引过滤、展示型 COUNT 可以保留；
公开热路径、全租户扫描、强额度/账单依据必须预聚合。
```

### 7.5 免费层可服务规模建议

| 阶段 | 建议规模 | 前提 |
|------|----------|------|
| 开发内测 | 5-20 个租户，每租户 1-3 个活动，每活动 50-300 人 | 当前免费层可承受，主要验证闭环 |
| 受控 Beta | 20-50 个租户，总参与 1,000-3,000 人/日 | 必须修 P0 安全和静态资源路由 |
| 小规模商业 | 50-100 个低频租户，总参与 3,000-10,000 人/日 | 必须有用量观测、限流、事件治理 |
| 单次活动峰值 | 5,000-10,000 人/日 | 需要预热、压测、静态资源不进 Worker、事件节制 |
| 开放式 SaaS | 不建议只靠 Free | 需要付费计划、流量隔离、滥用治理和升级策略 |
| 大客户/爆款活动 | 不应跑平台 Free | 使用客户自有 Cloudflare/Turso 或平台付费资源 |

这个表应作为销售和运营红线，不能把免费层能力包装成无限扩容。

## 八、风险清单：按上线阻断程度排序

### 8.1 P0：发布前必须处理

| 风险 | 当前证据 | 可能后果 | 最小处理原则 |
|------|----------|----------|--------------|
| L2/L3 权限混用 | docs/026 已确认 `/api/admin/system-config`、`/api/admin/redemption-codes` 属错位入口；当前前端仍调用旧 admin 路径 | 租户管理员触达平台能力，或平台页不可用 | `/api/admin/*` 只做租户；`/api/platform/*` 只做平台；前后端和测试同时对齐 |
| `platform_members` migration 缺失 | `schema.ts` 有表，当前 migrations 列表未见 `platform_members` 建表 | 部署后平台路由运行时失败 | 补正式 migration 和种子/首个 owner 创建方式 |
| 兑换码安全随机 | `src/routes/platform-redemption-codes.ts` 使用 `Math.random()` 生成平台额度码 | 额度码可预测，造成额度被盗用 | 使用 Web Crypto，唯一冲突重试，生成上限和审计 |
| 兑换码兑换并发 | docs/026 已指出先读 `usedCount` 再 update 可能超发 | 额度码超发，影响收费和信任 | 条件更新/CAS：只在 `used_count < max_uses` 时更新 |
| 静态资源 Worker-first | `wrangler.jsonc` 为 `run_worker_first: true`，`public` 有 562 文件 | 静态资源耗尽 Worker 日请求额 | SPA 资源走资产服务，只让 `/api/*` 进 Worker |
| 公开事件滥写 | `/api/public/draws/:slug/events` 可记录事件，当前看到内存限流和字段治理但缺持久强限流 | bot 可刷爆 rows written 和请求数 | 对事件上报做持久限流、采样、去重、字段长度和事件白名单 |
| 前端伪结果 | docs/014 仍列 P0.4：游戏组件不能展示伪中奖奖品；当前 `WheelGame.vue`、`LuckyWheel.vue` 有 `Math.random()` 视觉随机 | 用户以为前端决定中奖，产生信任灾难 | 前端随机只允许做动画，不允许决定业务结果 |

### 8.2 P1：上线前强烈建议处理

| 风险 | 影响 | 建议 |
|------|------|------|
| 内存限流不是多实例强保证 | Workers 多 isolate/多 PoP 下内存 Map 不能全局一致 | 登录、注册、参与、事件至少做轻量持久窗口 |
| 后台大导出/大 CSV | 10ms CPU 和 128MB 内存不适合一次性生成大文件 | 分页导出、限制条数、异步导出或分批下载 |
| 平台统计全表 COUNT | 平台后台低频可以用，但规模上来会吃 rows read | 快照表优先，实时 COUNT 兜底 |
| Webhook 重试放大 | Cron 每 5 分钟，跨租户扫描和外部 fetch 可能放大 | 限制 tenantLimit/perTenantLimit，失败退避和告警 |
| CORS `origin: ["*"]` | 当前 API 跨域过宽 | 公共读可宽，管理/平台写接口应限制来源或加强 token/CSRF 策略 |
| cf-shop 残留 | 前端 i18n 和系统配置仍有订单、支付、卡密等残留 | 产品认知混乱，维护者误接旧业务 |
| 观测不足 | 没有清晰看到每路由请求数、CPU、wall time、rows 消耗 | 上线后无法知道瓶颈在哪 |

### 8.3 P2：规模化前处理

| 风险 | 建议 |
|------|------|
| 多租户数据增长后冷热不分 | 按活动/租户/时间分页，做数据保留策略 |
| 合规隐私 | 明确收集 email/phone/IP hash/事件/外部转化的用途、保留、删除 |
| 邮件送达率 | Resend 配额、退信、失败重试和租户自定义发件域要纳入运营 |
| 白标自定义域名 | 不要一开始全自动，先人工开通和文档化 |
| 高并发名额争抢 | 免费层先用 DB 条件更新；大规模活动再考虑 Durable Objects 或付费架构 |
| 单数据库多租户 | 早期简单，但大客户可迁移到独立数据库/客户自有部署 |

## 九、简单 SaaS 平台运营后端：最小闭环

平台运营后端不要做成大而全的管理系统。第一版只需要让平台方能运营、止损、定位问题、手工处理客户。

### 9.1 L3 平台后台必须有的模块

| 模块 | 最小能力 | 为什么必须有 |
|------|----------|--------------|
| 租户列表 | 搜索、状态、套餐、创建时间、活动数、参与数摘要 | 不然无法运营 SaaS |
| 租户详情 | 基本信息、套餐、最近活动、最近错误、用量 | 支持和排障需要 |
| 套餐调整 | 修改 plan、额外活动额度、额外参与额度、到期时间 | 早期人工售卖和补偿 |
| 平台额度码 | 生成、列表、状态、使用记录、备注 | 支撑不接支付的早期商业化 |
| 系统配置 | 注册开关、默认套餐、限流参数、邮件配置可见性 | 运营开关 |
| 用量快照 | 按日/月读取活动数、参与数、事件数、Webhook 数 | 账单和容量治理基础 |
| 失败投递 | Webhook/email 失败列表和重试 | 客户支持刚需 |
| 平台审计 | 谁改了配置、套餐、额度码 | 避免内部误操作 |

### 9.2 明确不做的运营后台能力

| 不做项 | 原因 |
|--------|------|
| 财务账单系统 | 初期可人工收费或外部支付，内部只记录套餐权益 |
| 租户自定义角色 | 复杂且低频 |
| 全局数据大屏 | 容易全表扫描，先做分页列表和快照 |
| 自动风控判罚 | 初期规则和数据不足 |
| 工单系统 | 用外部工具承接 |

## 十、下一阶段路线：统一规划，分步实施

### 10.1 阶段 0：发布闸门

目标：先避免灾难。

必须完成：

1. RBAC-lite 闭环：`/api/admin/*`、`/api/platform/*`、前端路由、测试、migration 对齐。
2. 静态资源路由改成 SPA 推荐模式，只让 API 进 Worker。
3. 平台额度码安全随机、唯一重试、CAS 兑换、审计。
4. 公开事件上报限流和写入治理。
5. 修正游戏组件“前端随机只做动画”的业务口径。
6. 建立最小观测：按路由记录请求量、耗时、错误；定期查看 Turso rows read/write。

验收标准：

```text
租户管理员不能访问平台能力
平台成员不能绕过平台门禁
静态资源不再大量消耗 Worker 请求
公开参与热路径没有全租户 COUNT
兑换码不会超发
前端不会展示伪业务结果
```

### 10.2 阶段 1：受控 Beta

目标：用最少玩法验证真实需求和付费意愿。

推荐只稳定四类模板：

1. 抽奖。
2. 接龙/候补。
3. 资料领取。
4. 问卷/调研。

配套能力：

1. 模板复制和二维码。
2. 导出。
3. 基础事件漏斗。
4. Webhook 投递。
5. 平台运营最小后台。
6. 用量快照设计和初版。

### 10.3 阶段 2：小规模商业化

目标：开始收钱，但不承诺大客户 SLA。

推荐套餐：

```text
Free: 严格限制活动数和参与量，带品牌
Pro: 去品牌、更多活动、更多参与、导出、模板
Team: 成员协作、Webhook/API、外部转化、更多数据保留
White-label: 人工开通，建议付费资源或客户自有部署
```

必须增加：

1. 租户用量快照。
2. 平台审计。
3. 事件采样/保留策略。
4. 邮件失败补偿。
5. 客户支持排障视图。

### 10.4 阶段 3：规模化和架构升级

触发条件：

1. 日 Worker 请求稳定超过 50,000。
2. 单次活动峰值超过 5,000-10,000 参与。
3. Turso rows read/write 月用量超过 Free 的 50%。
4. 有付费客户要求白标、域名、SLA、独立数据。

升级路径：

| 问题 | 升级方向 |
|------|----------|
| Worker 请求不够 | Workers Paid，拆静态资源，API 限流 |
| rows read 增长 | 快照表、预聚合、索引治理、分页 |
| rows written 增长 | 事件采样、批量/异步、保留期清理 |
| 高并发名额 | DB CAS 优先；更高峰值考虑 Durable Objects |
| 大客户隔离 | 独立 Turso DB 或客户自有 Cloudflare/Turso |
| 导出大文件 | R2/异步导出/分页下载 |

> 这个系统要做的是“低成本活动获客与权益分配引擎”，用轻量玩法帮助租户完成留资、参与、结果、导流、归因和集成闭环；免费层只用于验证和小规模运营，任何会导致安全边界不清、资源不可控或产品变重的能力都必须延后或拒绝。
