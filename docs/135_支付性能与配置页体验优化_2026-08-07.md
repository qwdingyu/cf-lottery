# 135 支付性能与配置页体验优化

> 日期：2026-08-07  
> 范围：直付秒杀容量统计、支付下单失败软释放、公开端支付兜底、管理端支付配置页体验  
> 结论：本轮按“紧急程度 + 低成本高价值”优先优化，不引入独立库存表，先修复现有链路的性能和体验短板。

## 1. 本轮优化项

| 优先级 | 项 | 处理 |
| --- | --- | --- |
| P0 | 直付秒杀软释放后仍被总 COUNT 拦截 | 参与截单统计与公开进度统一排除 `payment_status='expired'` 的 entry |
| P0 | 支付下单/重试失败没有真正释放名额 | `cancelPaymentOrder` 将 entry 标记为 `expired`，后续重试再置回 `pending` |
| P1 | 秒杀 COUNT 热路径缺复合索引 | 新增 `idx_entries_tenant_draw_payment_status(tenant_id, draw_id, payment_status)`，匹配容量统计与进度查询 |
| P1 | 支付配置页字段全量铺开、视觉重心错误 | 借鉴 cf-shop 支付页：渠道卡片 + 关键事实 + 自检摘要 + 配置弹窗，敏感字段不常驻展示 |
| P2 | 二维码内容是 URL 时缺兜底入口 | `qrCode` 为 http(s) URL 时展示“打开二维码链接”备用入口 |
| P2 | 发卡失败没有直接联系方式 | 读取公开系统配置 `support_email`，在 `paid_fulfillment_failed` 中提供 mailto 联系入口 |

## 2. 秒杀 COUNT 性能边界

本轮没有直接新增库存计数表，原因是独立库存 CAS 会引入新的迁移、回补、补偿和运营修复入口，属于上线前较高风险改造。

当前方案仍保留单条 `INSERT ... SELECT ... WHERE COUNT(*) < cap` 的并发安全语义，但补上两个低成本收益：

1. COUNT 走 `tenant_id + draw_id + payment_status` 复合索引，减少高并发秒杀时的 rows read。
2. 直付秒杀只统计未释放的占位，避免过期/失败支付继续占库存。

后续如果单场并发明显超过 Turso 当前承载，应再做 `draw_inventory_counters` 或独立库存服务，用 CAS 原子扣减替代 COUNT。

## 3. 支付配置页设计原则

支付配置页是运维型表单，不应把所有密钥字段铺满页面。新页面按 cf-shop 的信息架构处理：

1. 列表态只展示渠道名、启用状态、配置完整度、币种、网关、回调和首条自检问题。
2. 编辑态进入弹窗，避免密钥输入框常驻在主页面。
3. 易支付是当前主力渠道，保留支付宝/微信/QQ 分段选择，默认方式必须属于启用方式。
4. 页面仍使用 cf-lottery 当前后端接口 `/api/admin/payment-config`，没有把 cf-shop 的余额支付、充值和删除接口复制进来。
