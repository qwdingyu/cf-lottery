# 084 查结果弹窗：UI 摩擦、邮箱 OTP 与 cf-auth 身份闭环分析

日期：2026-08-04  
范围：用户端「查询我的结果」弹窗（截图场景）及整条身份链路  
原则：只写代码证据；不把「已登录/已参与」幻觉成「已能无 OTP 查结果」。

---

## 1. 截图现象（用户感知）

深色弹窗：

- 顶部装饰票券图 / 标题「查询我的结果」
- 邮箱已预填（如 `zthinkai@gmail.com`）
- 一行：「邮箱验证码」输入 + 「发送验证码」
- 说明文案：点发送到邮箱，填后查询（开奖后也可发码）
- **底部巨大浅蓝主按钮「查询」**（高度接近半屏视觉权重）

用户自然疑问：

1. 这个查询按钮是不是太丑 / 比例失调？  
2. 已经 cf-auth 授权、已经参加过抽奖，为何还要邮箱 + 验证码？  
3. 这是否阻碍丝滑操作？

---

## 2. 结论先说

| 问题 | 结论 |
| --- | --- |
| 按钮丑不丑 | **是**：主 CTA 过高、装饰过重、信息层级弱；像「表单还没填完却放了一个占半屏的空查询」 |
| 为何还要邮箱+OTP | **对 open 系邮箱身份：后端故意要求**，防「只知道别人邮箱就读中奖卡密」的枚举；**不是**前端多余 |
| 已 cf-auth 是否应免 OTP | **参与（verify-join）可以**；**查结果（my-result）对 email 身份目前没有** 同等 Bearer 免 OTP — 这是 **真实产品断层**，用户抱怨合理 |
| 已参与是否应免 OTP | **否（仅凭「本机记过邮箱」）**。sessionEmail 只是本标签会话提示，**不是**密码学证明；谁都能改输入框里的邮箱 |
| registered 模式 | **已丝滑**：JWT 直查，打开弹窗即 `queryMyResult()`，无邮箱 OTP |

一句话：

> **丑是 UI 问题；「还要验证码」一半是正确安全设计，一半是「参与已认 cf-auth、查结果不认」的不一致，需要 P0 对齐而不是删掉 OTP 防枚举。**

## 3. 身份与入口矩阵（证据）

### 3.1 参与模式决定身份键

| `participation_mode` | 参与时 identity | 查结果证明方式（现状） |
| --- | --- | --- |
| `registered` | `user_id` = JWT `sub` | **仅 JWT**；前端打开即查；access-code purpose=query 拒邮箱码 |
| `open` / `roster` / `password` / `invite_code` | `email` 字符串 | **邮箱 + 6 位 OTP**（`verifyEmailAccessCode`）；无 JWT 免 OTP 分支 |

`resolveParticipantIdentity`（`public-lottery-helpers.ts`）：

- registered → 必须 Bearer，返回 `user_id`  
- 其它 → **只**把 body.email 当身份，**不读** Authorization

### 3.2 参与路径：cf-auth 已能免 OTP

`POST .../verify-join`：

- Bearer 业务 JWT 且 `payload.email === body.email` → `bearerIdentityVerified` → **跳过邮箱 OTP**  
- 设计意图（注释）：IdP 已认证，省 Resend

open 系参与弹窗还有「或 · cf-auth 登录」可选加速（`cfAuthEnabled`）。

### 3.3 查结果路径：email 身份（**085 已对齐 Bearer 免 OTP**）

> **勘误（2026-08-04 / docs/085、097）：** 下文「没有 Bearer 免 OTP」为审查当时快照。  
> **现状：** `POST .../my-result` 已对 open 系实现与 verify-join 同策略——业务 JWT.email 与 body.email 一致（或 body 空用 JWT.email）可免 OTP；不一致不授信仍走 OTP。registered 仍仅 JWT sub。

历史描述（保留作决策背景，**勿当现行代码**）：

`POST .../my-result`（审查时）：

- `identityType === "email"` → 必须 email + code，且 `verifyEmailAccessCode`  
- 审查时**没有**「Bearer email 一致则跳过 OTP」的分支（与 verify-join 不对称）——**已由 085 修复**  
- registered → JWT，无码

`purpose=query` 的 access-code：

- 已参与 / drawn 仍可发码（docs/077 修复「开奖后查不到」）  
- 即使 `enable_email_verification=false`，**query 仍发码**（注释：my-result 靠 OTP 防枚举）  
- registered query：直接 400「请直接查询，无需邮箱验证码」

### 3.4 前端会话 ≠ 服务端证明

| 前端状态 | 存哪 | 含义 | 能否单独换 my-result 结果 |
| --- | --- | --- | --- |
| `sessionEmail` | sessionStorage | 本标签参与/查询过的邮箱提示 | **否**；只预填；改邮箱仍要 OTP |
| `registeredToken` | sessionStorage | 业务 JWT | **是**（registered） |
| cf-auth 后业务 JWT | 参与流程可有 | verify-join 免 OTP | **查结果 email 路径未带/未认** |

`openMyResult`：

- 预填 `sessionEmail`  
- **仅** `participationMode === 'registered' && registeredToken` 时自动查询  
- open 系：永远进入「邮箱 + 发码 + 大查询按钮」表单

因此截图场景高度符合：**open 系 + 本机记得邮箱 + 未走 registered JWT 自动查**。

## 4. 为何不能「已参加就直接出结果」（安全）

中奖接口返回的是 **prizeCode / secret / 安慰券**，属于高价值秘密。

若 my-result 仅凭：

- 客户端声称的 email，或  
- 「我本地 session 写过已参与」  

则攻击者可以对任意邮箱批量查询：未参与 / 未中 / **中奖码**。  
限流只能减慢，不能替代 **证明你控制该邮箱（或持有绑定该邮箱的 IdP 会话）**。

故：

| 证明手段 | 强度 | 丝滑度 | 现状 |
| --- | --- | --- | --- |
| 邮箱 OTP | 强（控制收件箱） | 差（切邮箱 App） | open 系 my-result **唯一** |
| 业务 JWT（email 一致） | 强（cf-auth/登录签发） | 好 | verify-join **有**；my-result **无** |
| registered JWT sub | 强 | 最好 | my-result **有** |
| sessionEmail | 无 | — | 仅 UX 预填 |
| 「已参与」前端 flag | 无 | — | 不可作鉴权 |

**已参加抽奖**只说明历史上某次证明过；**查结果是另一次读秘密**，默认应再证明（或复用未过期的强会话）。

## 5. 环节拆解：用户路径上的每一次摩擦

### 环节 A — 入口文案「查询我的结果」

- 已参与用户期望：「我的结果」一键展开，而不是再走登录表单感。  
- 未参与用户：需要防枚举，表单合理。  
- **现状**：两种人同一套 open 表单（除 registered）。

### 环节 B — 邮箱预填

- 有 `sessionEmail` 时减少输入 → 好。  
- 副作用：用户以为「系统已认出我」→ 对仍要 OTP **预期落差最大**（截图正是此态）。

### 环节 C — 发送验证码

- 077 之前：开奖后/已参与发不了码 → 更差。  
- 077 后：purpose=query 可发 → **闭环正确**，但仍是异步邮件成本与等待。  
- 文案偏长、偏运维口吻，增加「这很麻烦」的感受。

### 环节 D — 填 6 位码

- 有 `autocomplete=one-time-code` 等触控优化（参与侧更完整；查结果也有 numeric/otp 属性）→ 合格。  
- 与「发码」横排：小屏可接受；视觉上次按钮与主按钮抢戏。

### 环节 E — 巨大「查询」主按钮（UI）

证据：`.join-modal-primary` 复用 + 弹窗 `text-align`/`padding 32px` + 票券装饰。

问题：

1. **层级颠倒**：未发码/未填码时，主按钮已是视觉中心，但真正下一步应是「发送验证码」或「一键用登录态查询」。  
2. **尺寸**：min-height 44px 合理，但全宽 + 浅蓝实心 + 上下大留白 → 像空态占位，**不精致**。  
3. **装饰**：🎫/票券与抽奖结果弱相关，占垂直空间，挤说明文案。  
4. **无进度态分区**：未区分「待发码 / 待填码 / 可查询 / 已登录一键查」。  
5. **与参与弹窗不一致**：参与侧有 cf-auth 分区、验证后「一键继续」；查结果 open 侧 **没有**「已用 cf-auth？一键查」入口。

**判断：是的，当前查询主按钮设计偏丑、偏「半成品表单」。** 不是不能有主按钮，而是 **状态机 UI 缺失** 导致它永远像一块巨大的死按钮。

### 环节 F — cf-auth 已授权却仍 OTP

若用户参与时走了 cf-auth → 应持有 **业务 JWT（email 在 payload）**：

- 再参与：verify-join 可免 OTP  
- 再查结果：**前端 queryMyResult 对非 registered 不带 Bearer**；**后端 my-result 即使带了也不免 OTP**

→ **双端断层**。用户说「已经 cf-auth 了为什么还要验证码」在工程上 **成立**。

若用户参与时只走了邮箱 OTP、从未 cf-auth：

- 只有 sessionEmail → **仍应 OTP 或重新 OAuth** 才能读码；抱怨「已参加」不足以取消证明。

### 环节 G — 开奖邮件已发过结果

- 中奖用户可能邮箱里已有码；公开页再查是二次获取。  
- 产品上仍需要页内查（邮件丢了、安慰奖、未中确认）。  
- 不能因「可能发过邮件」去掉页内鉴权。

### 环节 H — 与「我的记录」顶栏

- 顶栏 `sessionEmail || registeredUsername` 显示「已登录感」。  
- 加深「系统认识我」与「查还要码」的矛盾。  
- 应用文案区分：**「本机会话」≠「已验证登录」**（open 系尤其）。

- **064**：公开参与 **不依赖** cf-auth；OTP 与 cf-auth 是平行选项。  
- **077**：修的是「能发查询码」，**刻意不改** my-result 鉴权模型。

## 7. 最佳实践建议（分层，防灾难）

### 7.1 安全底线（不可破）

1. 匿名仅凭 email 字符串 **不可** 返回 prizeCode。  
2. sessionStorage / local flag **不可** 当证明。  
3. 限流保留；query 发码保留防枚举（对无 JWT 用户）。  
4. registered 继续禁止邮箱 OTP 绕过 user_id。

### 7.2 P0 — 身份对齐（高杠杆丝滑）

**目标：凡参与时已能用的强会话，查结果必须同等可用。**

1. **my-result（email 身份）** 对齐 verify-join：  
   - `Authorization: Bearer` 且 `payload.email` 规范化后等于请求 email（或直接用 payload.email 作 identity）→ **跳过 OTP**，仍限流。  
2. **前端 openMyResult / queryMyResult**：  
   - 若存在业务 JWT（cf-auth 交换后或登录后，open 系也应持久化同一套 token，而不是只写 sessionEmail）：  
     - 带 Bearer 自动查；  
     - 成功则不展示 OTP 表单。  
3. **若仅有 sessionEmail、无 JWT**：  
   - 预填邮箱 + **主路径改为「发送验证码」**；  
   - 次路径：「用 cf-auth 一键查询」（有 IdP 时）。  
4. 单测：Bearer 免 OTP 查中奖；错误 email 与 token 不匹配仍拒；无 token 无码拒。

### 7.3 P0/P1 — UI 状态机（解决「丑」与误导）

不要永远渲染「大查询」。按状态切换：

| 状态 | 主按钮 | 次要 |
| --- | --- | --- |
| 有 JWT | 无表单或轻量「正在查询…」 | 关闭 |
| 有邮箱无码 | **发送验证码**（主色） | cf-auth 一键查 |
| 已发码 | **查看结果**（主色，enabled） | 重发冷却 |
| 无邮箱 | 先聚焦邮箱，主按钮 disabled 或「继续」 | |

视觉：

- 去掉或缩小票券装饰；标题下用一行状态：「验证邮箱以查看奖品码」  
- 主按钮高度与参与弹窗主 CTA 对齐（约 44–48px），**不要**视觉半屏  
- 主色与活动页强调色一致（现浅蓝与页内琥珀主按钮不统一）  
- 说明改短：「验证码发到该邮箱，用于保护中奖信息」

### 7.4 P1 — 已参与用户的「结果就绪」

- drawn + 本机有 JWT/强会话：卡片上 **直接展示「查看我的奖品」→ 一跳出结果**，不进空表单。  
- drawn + 仅 sessionEmail：文案改为「验证邮箱后查看」，避免「查询」公文腔。  
- 列表「我的记录」与单活动结果共用同一鉴权，避免两套心智。

### 7.5 明确不做

- 不因「已参加」去掉所有证明。  
- 不把 enable_email_verification=false 扩展为 my-result 免 OTP（077 已强调 query 仍要码）。  
- 不在无 JWT 时用「上次 OTP 未过期自动带上」却不让用户感知（可做「同码复用」但须仍持有码）。  
- 不为了好看把主按钮做成假可点（无码仍 400）。

## 8. 推荐话术（对内/对用户）

**对内：**  
open 系查结果慢，不是运营配置错了，是 **读秘密接口与参与接口鉴权不对称 + 表单 UI 未按会话态分流**。

**对用户（有 JWT 后）：**  
「已登录，正在获取你的结果…」

**对用户（无 JWT）：**  
「为保护中奖信息，请验证邮箱（约 30 秒）」+ 可选「使用统一登录更快查询」。

## 10. 总答用户三问

1. **查询按钮丑吗？**  
   **是**——过大、过空、层级不对；应随状态变成「发送验证码 / 查看结果 / 自动查询中」，并统一视觉语言。  

2. **为何还要邮箱+验证码？**  
   **对未持有强会话的 open 邮箱身份：必须**，否则中奖码可被邮箱枚举；**对已 cf-auth/业务 JWT 的用户：当前仍要是实现缺口，不应是最终产品。**  

3. **是否阻碍丝滑？**  
   **阻碍**。registered 已顺；open + 仅 sessionEmail 必然有一步证明；open + 已有 cf-auth **不应再阻**——应用 P0 对齐。  

**本文为分析，未改业务代码。**
