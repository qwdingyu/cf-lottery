# 不实施优化项的技术论证与正确替代方案

> 背景：对 docs/154 中 P1-1（performDraw 分批抽取）和 P3-1（Dashboard 预聚合）进行逐行代码审查后，确认这两个优化项在**当前和可预见的未来数据量下不应实施**。本文档记录论证过程，防止后续开发者误入歧途。

---

## 1. P1-1 `performDraw` 分批抽取

### 1.1 文档描述的问题与实际代码的出入

docs/154 描述：

> 2. **裂变加权场景**：`weightedPool` 展开权重（一个 entry 权重可达 1+100），展开后数组可能达到数百万元素，每个元素包含完整 entry 对象 + 权重数字，内存占用呈倍数增长

**实际代码中不存在"展开"行为。** `weightedSampleUnique` 使用**加权累积和按权无放回**算法，不展开 bag：

```typescript
// 文件：src/services/lottery/viral-weight.ts:76-123
// pool 长度 = 参与人数，不是 参与人数 × 权重
const pool = items.map(row => ({
  item: row.item, weight: Math.max(1, ...)
}));

// 每轮通过累积和选择，不展开
while (picked.length < n && pool.length > 0) {
  let total = 0;
  for (const row of pool) total += row.weight;
  let r = u * total;
  for (let i = 0; i < pool.length; i++) {
    r -= pool[i]!.weight;
    if (r < 0) { idx = i; break; }
  }
  pool.splice(idx, 1);
}
```

**内存：O(N) 而不是 O(N×weight)**。10 万参与者：
- `entries` 数组：~10 万 × 300 字节 ≈ 30 MB
- `weightedPool` 数组：~10 万 × 200 字节 ≈ 20 MB
- `inviteMap` Map：~10 万 × 100 字节 ≈ 10 MB
- 总计：**~60 MB**，单活动完全可接受。

### 1.2 真正的瓶颈

`weightedSampleUnique` 的 `pool.splice(idx, 1)` 是 **O(N) 的数组元素移动**。在 while 循环里每抽一个中奖者执行一次 → **O(winners × entries)**。

| 场景 | 参与人数 | 中奖人数 | splice 次数 | 预估耗时 |
|:-----|:---------|:---------|:------------|:--------|
| 普通活动 | 1,000 | 10 | 10 次 | < 1ms |
| 大型活动 | 50,000 | 100 | 100 次 | 5ms |
| 极端活动 | 100,000 | 1,000 | 1,000 次 | 50ms |
| 极致边缘 | 100,000 | 10,000 | 10,000 次 | 1-2s |

**注意**：开奖的 `totalWinners` 是活动配置的 `winnerCount`，通常不超过几百。1,000 以上中奖者的活动极其罕见。所以 `weightedSampleUnique` 的 CPU 瓶颈在现实中几乎不会触发。

### 1.3 为什么「分批抽取到数据库」是错误方向

| 维度 | 当前算法 | 数据库分批抽取的风险 |
|:-----|:---------|:---------------------|
| **公平性** | Fisher-Yates / 加权累积和，CSPRNG，严格无放回 | `ORDER BY random() LIMIT 1` 不是无放回——需要用 `NOT IN` 排除已中者，查询随中奖人数增加越来越慢 |
| **可复现性** | seed → SHA-256 hash → 可验证（docs/109） | 分批抽取的多次查询不可复现 |
| **事务一致性** | 整个抽奖在同一个事务 + 锁码路径下 | 分批抽取需要在应用层维护「已抽到第几批」的状态，进程崩溃后无法恢复 |
| **原子锁码** | 子查询 `UPDATE ... WHERE id = (SELECT ... LIMIT 1)` 单语句完成 | 分批抽取 + 锁码需要跨批次协调，增加 TOCTOU 窗口 |
| **复杂度** | 90 行纯函数，无状态、无副作用 | 需要批次游标、部分失败处理、幂等恢复、与现有事务集成 |

### 1.4 正确的优化方式（如果将来真的需要）

**不要重构算法，只优化数据结构的操作效率。**

`pool.splice(idx, 1)` 是 O(N)。改成"末尾交换后 pop"就是 O(1)：

```typescript
// 修改前：pool.splice(idx, 1)  — O(N)
// 修改后：末尾交换后 pop      — O(1)
const last = pool[pool.length - 1]!;
pool[idx] = last;
pool.pop();
```

**改动量：1 行。风险：0（不改变算法逻辑）。收益：O(winners × entries) → O(winners)。**

这是唯一推荐的优化路径。如果将来真的遇到 10 万参与 + 1000 中奖导致开奖慢 1 秒，**改这一行即可**，不要碰分批抽取。

### 1.5 触发条件与决策树

```
是否遇到 performDraw 超时或 OOM？
├─ 否 → 不实施。当前算法是正确的，不要为不存在的性能问题引入风险。
└─ 是 → 检查参与人数和中奖人数：
    ├─ 参与 < 10 万 → 不可能是这里的问题，排查其他原因（死锁、网络等）
    └─ 参与 ≥ 10 万 且 中奖 ≥ 1000 →
        └─ 改 splice → pop（1 行，10 分钟，0 风险）
        └─ 如果仍不够：给 weightedSampleUnique 加「大池分块」策略
        └─ ❌ 永远不要：改成数据库分批抽取
```

## 2. P3-1 Dashboard 预聚合

### 2.1 文档描述的问题与实际代码的出入

docs/154 将 Dashboard 列为 P3（低优先级），触发条件为"运营者 > 50 人"。评级合理，但提议的"预聚合"方案是过度设计。

### 2.2 当前 Dashboard 查询的索引覆盖分析

Dashboard 端点（`src/routes/admin-lottery.ts:95`）执行 8 个查询：

| # | 查询 | 表 | 过滤条件 | 索引 | 是否覆盖 |
|:--|:-----|:---|:---------|:-----|:--------|
| 1 | COUNT(status) | `lottery_draws` | `tenantId=? AND status=?` | `idx_draws_tenant_status` (tenantId, status, createdAt) | ✅ 索引覆盖 |
| 2 | COUNT(draft) | `lottery_draws` | 同上 | 同上 | ✅ 同上 |
| 3 | COUNT(drawn) | `lottery_draws` | 同上 | 同上 | ✅ 同上 |
| 4 | COUNT(due) | `lottery_draws` | `status='open' AND drawAt≤now` | `idx_draws_due` (status, drawAt) | ✅ 索引覆盖 |
| 5 | COUNT(failed) | `lottery_winners` | `tenantId=? AND notificationStatus='failed'` | `idx_winners_notification_status` (tenantId, notificationStatus) | ✅ 索引覆盖 |
| 6 | ROI SUM(amountCents) | `external_conversions` | `tenantId=? AND occurredAt≥?` | `conversionDrawIdx` (tenantId, drawId, conversionType, createdAt) — **occurredAt 不在索引中** | ⚠️ 需查表过滤 |
| 7 | ROI GROUP BY conversionType | `external_conversions` | 同上 | 同上 | ⚠️ 同上 |
| 8 | 库存预警（open draws + inventory LEFT JOIN） | `lottery_draws` + `prizes` + `prizeCodes` | `tenantId=? AND status='open'` | `idx_draws_tenant_status` | ✅ 索引覆盖 |

**唯一未完全覆盖的是 ROI 查询**（`occurredAt` 不在索引中）。但 `external_conversions` 表的数据量天然很小（转化数远少于参与数，一个活动可能只有几十到几百笔转化），所以这不是问题。

### 2.3 为什么「预聚合」是过度设计

#### 2.3.1 复杂度代价

预聚合需要：
1. **新表** `dashboard_snapshots`（或类似结构）—— 存储预计算的快照数据
2. **定时聚合逻辑** —— Cron 或 triggered 任务，定期重新计算
3. **快照 vs 实时不一致处理** —— 运营者看到的 Dashboard 可能是 5 分钟前的数据，但活动列表是实时的，这个不一致会造成困惑
4. **失效处理** —— 如果 Cron 挂了，Dashboard 就显示过期数据

#### 2.3.2 收益分析

- 当前 8 个查询 + 1 个 inventory LEFT JOIN，全部在 1-50ms 内完成
- 即使运营者 > 50 人，这些查询的并发累积也不到 1 TPS（每人每 30 秒看一次 = 50/30 ≈ 1.7 TPS）
- 1.7 TPS 的索引 COUNT 查询对 SQLite 来说毫无压力

#### 2.3.3 真正的替代方案（如果将来真的需要）

**加一个索引即可，不要搞预聚合。** 在 `external_conversions` 上加 `(tenantId, occurredAt)` 索引，覆盖 ROI 查询的 `WHERE tenantId=? AND occurredAt>=?`，把 O(N) 表过滤降到 O(log N)。

Drizzle schema 改动（`src/db/schema.ts` 的 `externalConversions` 定义中新增）：

```typescript
conversionOccurredIdx: index("idx_external_conversions_occurred").on(
  t.tenantId, t.occurredAt
),
```

**这就是全部需要的优化。** 不需要预聚合、不需要快照表、不需要 Cron。成本 5 分钟，0 风险。

### 2.4 触发条件与决策树

```
Dashboard 响应时间是否 > 200ms？
├─ 否 → 不实施。当前查询已索引覆盖，不需要预聚合。
└─ 是 → 定位慢查询：
    ├─ 慢在 COUNT(draws) / COUNT(winners) / COUNT(due) →
    │   └─ 检查索引是否被删除或未迁移（极少发生）
    │   └─ 如果数据量确实极大（百万级活动），考虑物化视图
    │   └─ ❌ 不要预聚合——这些 COUNT 可以在 1 秒内完成
    └─ 慢在 ROI 查询 →
        └─ 加 `(tenantId, occurredAt)` 索引（5 分钟，0 风险）
        └─ ❌ 不要预聚合——一个索引能解决的问题不需要 Cron
```

## 3. 常见误区总结

| 误区 | 真相 | 来源 |
|:-----|:-----|:------|
| "`weightedPool` 展开权重导致内存爆炸" | 代码用的是累积和算法，不展开 bag。内存 O(N) 不是 O(N×weight) | `viral-weight.ts:76-123` |
| "分批抽取到数据库更高效" | 数据库 `ORDER BY random()` 在大表上更慢（全表扫描 + 排序），且无法保证无放回公平性 | 理论分析 + SQLite 查询计划 |
| "预聚合可以解决 Dashboard 性能问题" | 当前查询已全部索引覆盖，唯一弱点是 ROI 的 `occurredAt` 过滤，加一个索引即可解决 | `admin-lottery.ts:95` + schema 索引分析 |
| "P1-1 是 P1 必须尽快做" | 实际瓶颈是 `pool.splice` O(N)，改成 O(1) pop 即可。分批抽取是错误方向 | `viral-weight.ts:116` 逐行审查 |
| "P3-1 是 P3 可以以后做" | 评级正确，但预聚合方案错误。需要时加索引而不是搞快照 | schema 索引分析 |

## 5. 已实施与明确不实施的优化项（2026-08-08 补充）

在 docs/154 基础上，对剩余优化点逐项评估后，实施其中 3 项、明确不实施 2 项。本节点记录决策，避免重复分析。

### 5.1 已实施

#### P2-2 邮件有界并发发送

**问题**：`sendWinnerNotifications`（draw-execution.ts）与 `sendLoserConsolationEmails` 用 `for...of + await` 串行发送。1000 位中奖者约 7 分钟，1000 封安慰邮件约 7 分钟。

**方案**：新增 `src/lib/concurrency.ts` 的 `runBounded` 有界并发执行器（默认 5 路），两个发送循环改为并发。Resend free 计划约 2 req/s，5 路足以保持吞吐且不超限流。

**改动**：
- 新增 `src/lib/concurrency.ts` + `src/lib/concurrency.test.ts`（7 个用例）
- `draw-execution.ts`：`sendWinnerNotifications` / `sendLoserConsolationEmails` 改用 `runBounded`

**关键点**：每个 winner 独立处理自己的错误（一个失败不影响其他）；`sent`/`failed` 计数为同步操作，无并发竞态；跳过逻辑（已发送/超重试）返回 `null` 不计入。

**收益**：1000 中奖者 ≈ 7min → ≈ 1.5min（5 路并发）。

#### P3-1 `Buffer.from` → `btoa/atob`（CF Workers 兼容）

**问题**：`admin-lottery-helpers.ts` 的 `encodeDrawCursor`/`decodeDrawCursor` 用 `Buffer.from`，在 Cloudflare Workers 无 Node Buffer 环境抛错。

**方案**：改为原生 `btoa`/`atob`（Node 18+ 与 CF Workers 均支持）。本地测试库不依赖 Buffer，测试通过。

**备注**：当前生产默认 VPS（Node），Buffer 也可用；此改动是为潜在的 Workers 回退部署消除隐患，零风险。

#### P3-3 ROI `occurredAt` 索引

**问题**：ROI 查询 `WHERE tenantId=? AND occurredAt>=?` 中 `occurredAt` 不在任何索引中，需回表过滤。

**方案**：在 `external_conversions` 上加 `(tenantId, occurredAt)` 索引（docs/155 §2.3.3 已有论证）。

**改动**：
- `src/db/schema.ts`：`externalConversions` 新增 `conversionOccurredIdx`
- `migrations/0042_external_conversions_occurred_index.sql`（UP/DOWN）

注意：**必须显式运行 `npm run db:migrate`** 才会在生产库生效。

### 5.2 明确不实施

#### P3-2 `processDueDraws` 并行化

**建议不实施**。`processDueDraws` 串行处理到期活动，若并行化会引入锁竞争：多个 worker 同时操作同一批活动，需要加锁或 CAS 防重复开奖，复杂度与风险远大于收益。当前串行已足够（单 worker Cron 触发）。

#### P4 前端 bundle 分块

**建议不实施**。当前前端 bundle < 500KB，VPS 部署下首屏加载 < 1s，分块带来的收益可忽略，反而增加路由懒加载复杂度。
