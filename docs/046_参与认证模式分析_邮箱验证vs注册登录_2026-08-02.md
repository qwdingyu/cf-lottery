# 参与认证模式分析：邮箱验证 vs 注册登录

日期：2026-08-02
状态：**已实施（2026-08-02）——registered 参与模式后端+前端已上线，含安全审查修复**

## 一、问题提出

当前 cf-lottery 有两套独立认证体系：

| 轨道 | 对象 | 认证方式 | 入口 |
|------|------|----------|------|
| 公开参与轨 | 活动参与者（L1） | 邮箱 + 验证码 | `/lottery/:slug` |
| 管理后台轨 | 租户管理员（L2/L3） | 用户名 + 密码 + JWT | `/admin/login` |

用户提出：如果参与者也是注册用户，是否可以直接用账号密码登录参与，跳过邮箱验证码？
进一步问：这个选择是否应该由活动组织者（L2）自主决定？

## 二、行业分析

### 行业对标

| 平台 | 参与认证方式 | 是否可选 |
|------|-------------|----------|
| Gleam.io | 邮箱/社交账号登录 可选 | ✅ 组织者可配 |
| Rafflecopter | 邮箱 + 可选登录 | ✅ 组织者可配 |
| Typeform | 默认无认证，可开启"需登录" | ✅ 表单级配置 |
| Google Forms | 可设"仅限组织内用户" | ✅ 表单级配置 |

**行业一致模式：参与门槛是活动级配置，由组织者决定，不是系统强制的。**

### 场景分析

| 场景 | 最佳认证 | 为什么 |
|------|----------|--------|
| 商场抽奖（公开拉新） | 邮箱 + 验证码 | 路人不会为了一次抽奖注册账号 |
| VIP 会员回馈 | 账号密码登录 | 已注册用户，无需等邮箱 |
| 公司内部活动 | 两种均可 | 取决于组织者偏好 |
| 线上裂变传播 | 邮箱 + 验证码 | 降低参与门槛 = 提高传播率 |
| 付费社群专属 | 需注册登录 | 确保只有会员能参与 |

**结论：不能一刀切。组织者需要根据活动目标选择参与门槛。**

## 三、架构设计

### 当前 participation_mode 字段

```typescript
PARTICIPATION_MODES = new Set(["open", "roster", "password", "invite_code"])
```

| 值 | 含义 | 认证方式 |
|----|------|----------|
| `open` | 公开参与 | 邮箱验证码 |
| `roster` | 限定名单 | 邮箱白名单 + 验证码 |
| `password` | 访问密码 | 密码 + 邮箱验证码 |
| `invite_code` | 邀请码 | 邀请码 + 邮箱验证码 |

### 建议新增

| 值 | 含义 | 认证方式 |
|----|------|----------|
| **`registered`** | **需注册登录** | **JWT 认证（复用管理后台登录态）** |

### 设计原则

1. **`participation_mode` 职责不变**：描述"谁可以参加"——它本身就应该是这个语义
2. **`registered` 是 `participation_mode` 的自然扩展**：不是"认证方式"配置，而是"参与资格"的一种
3. **不引入新字段**：复用 `participation_mode`，不新增 `auth_method` 或 `registration_required`
4. **前端感知模式切换 UI**：`registered` 模式下展示登录/注册入口，替代邮箱输入框

### 数据流对比

```
open 模式（当前）：
  用户 → 输入邮箱 → 收验证码 → 输入验证码 → joinDraw(email)

registered 模式（新增）：
  用户 → 登录/注册 → JWT 签发 → joinDraw(userId)
```

### 与 045 文档的关系

045 文档提出"注册不建租户 + 引导创建"。`registered` 模式依赖注册用户体系，但与"是否建租户"是两个独立维度：

| 维度 | 045 关注 | 本文关注 |
|------|----------|----------|
| 租户创建 | 注册是否自动建租户 | 不相关——参与者不需要租户 |
| 用户认证 | 管理员多租户切换 | 参与者用什么方式证明身份 |

**两个文档互不冲突。** 注册用户无论是否有租户，都可以参与 `registered` 模式的活动。

### 与 045 文档的关联（重要）

045 文档定稿"注册不建租户 + 引导创建"（团队版实施）。**registered 模式放大了噪音租户问题的影响面**：
参与者为了参与活动而注册（前端引导跳 `/admin/register`），注册强制建租户 → 每个抽奖参与者都会变成租户 owner 并拥有管理台入口。

**建议：团队版实施 045 方案 C 时，把"注册不建租户"与 registered 模式一并落地**，
否则噪音租户会从管理端扩散到公开参与端。
