# 045 注册强制建租户与多租户切换缺陷分析与根治方案

日期：2026-08-02
状态：**已定稿为决策记录——当前不改代码，团队版实施时按方案 C 执行**
相关代码：`src/routes/auth.ts`、`src/middleware/auth.ts`、`frontend/src/composables/useAdminAuth.ts`

## 一、背景

"添加团队成员"功能存在设计缺陷：被添加的成员登录后进入自己的租户，无法访问团队租户。
此前提出用 `POST /switch-tenant`（多租户切换）修复，但引入"一人多租户"管理复杂度。

本文档经二次审查（含代码现状核查 + 行业对标）后定稿。审查结论：
**方案 B（switch-tenant 降级为边缘兜底）方向对一半，不是最优；修正为方案 C 定稿。**

## 二、代码现状核查（2026-08-02 实查）

| 事实 | 状态 |
|------|------|
| 注册强制建租户 | `auth.ts` `/register` 事务：users + tenants + tenantMembers(owner) |
| 登录返回 `tenants[]` | 已有（多租户用户返回全部） |
| switch-tenant API | **后端半成品**：API 存在，前端从未调用、无切换 UI |
| 前端租户上下文 | **完全没有**：只存 token + platformRole，tenantId 全在 JWT 里 |
| 成员管理 API | **根本不存在**：无添加/邀请/移除成员端点，`tenantMembers` 只在测试 seed |
| requireTenantMember | 已存在：校验 JWT tenantId + 成员关系，空 tenantId 返回 403"无租户上下文" |

**关键推论：团队成员功能后端+前端均未实现，"缺陷"从未真正影响用户。**
switch-tenant 是当时为未来成员功能提前打的地基，只打了一半。

## 三、根因分析

### 3.1 病根：注册强制创建租户

```ts
await withDbTransaction(db, async (tx) => {
  await tx.insert(users).values({ id: userId, username, email, passwordHash, emailVerified: 0 });
  await tx.insert(tenants).values({ id: tenantId, name: username }); // ← 强制每人建租户
  await tx.insert(tenantMembers).values({ tenantId, userId, role: "owner" });
});
```

**注册强制给每个人创建租户**，连锁反应：
1. 每个用户天然是某租户 owner → 登录默认进"自己的租户"
2. 被邀请加入他人租户 → 必然"一人多租户"
3. 多租户 → 需区分上下文 → 被迫发明 switch-tenant

**结论：注册自动送租户 = "噪音租户"，是错误的数据模型假设。**

### 3.2 行业对标：组织切换器是标配，不是兜底

行业主流 SaaS（Slack / Notion / Linear / Figma / Stripe）一致模式：

| 模式 | 行业做法 |
|------|---------|
| 组织创建 | **显式创建**（workspace/org），不是注册附赠品 |
| 注册后引导 | **onboarding 引导创建组织**是标准流程 |
| 一人多组织 | **正常态**（Slack 用户平均属于多个 workspace），不是边缘情况 |
| 组织切换器 | **标配 UX**（Workspace Switcher），不是兜底功能 |
| 默认进入 | 最近使用的组织 |

**修正结论：多租户不该被当"复杂"，该被当"标准能力"。**
真正要消除的是注册自动送的噪音租户，不是多租户本身。

## 四、方案对比

### 方案 A：保留注册建租户 + switch-tenant（现状，治标）

| 维度 | 评估 |
|------|------|
| 复杂度 | 高：默认多租户，且每个用户有噪音租户 |
| 团队成员场景 | 可用，但成员登录先进自己的租户，需手动切换 |
| 用户心智 | "为什么我平白多一个租户？" |
| 结论 | ❌ 保留噪音租户，不解决根因 |

### 方案 B：注册不建租户 + switch-tenant 降级边缘（首版方案，部分正确）

| 维度 | 评估 |
|------|------|
| 注册不建租户 | ✅ 符合行业实践，消除噪音租户 |
| switch-tenant 降级边缘 | ❌ 违背行业实践：切换器是标配，不是边缘 |
| 结论 | ❌ 方向对一半，不是最优 |

### 方案 C：注册不建租户 + 引导创建 + 标准切换器（定稿方案，最优）

**核心原则：租户显式创建（onboarding 引导），多组织切换器是标准能力。**

| 维度 | 评估 |
|------|------|
| 注册不建租户 | ✅ 消除噪音租户，根治数据模型错误 |
| 首次登录引导创建租户 | ✅ 行业标准 onboarding |
| switch-tenant 保留 + 标准切换器 UI | ✅ 行业标配，一人多组织是正常态 |
| 默认进入最近使用的租户 | ✅ localStorage 记忆上次切换 |
| 用户心智 | "我创建的租户 + 我加入的团队" 清晰 |
| 结论 | ✅ 定稿 |

## 五、方案 C 详细设计

### 5.1 用户生命周期

```
注册（只建 user，无租户）
  → 首次登录：无租户 → onboarding 引导"创建你的第一个租户"
  → 主动创建租户（复用现有建租户逻辑）
  → 或被邀请加入团队租户
  → 后续：管理页出现组织切换器（可切换创建的/加入的租户）
```

### 5.2 改动清单（团队版实施时执行）

**后端（`src/routes/auth.ts`）**

1. `/register`：删除 `tenants`、`tenantMembers` 插入，事务只保留 users
2. `/login`：无租户时 `tenantId` 返回 `""`，响应增加 `needsTenant: true`
3. 新增 `POST /tenant`：用户显式创建自己的租户（校验无租户或允许多租户，产品定）
4. `/switch-tenant`：保留，作为标准切换能力；建议响应增加所有租户列表供前端渲染切换器

**前端**

5. 登录适配 `needsTenant` → onboarding 引导页："创建你的第一个租户"
6. **路由守卫闭环**：无租户用户访问 `/admin/*` 重定向到引导页（否则撞 `requireTenantMember` 的 403"无租户上下文"）
7. AdminLayout 增加**组织切换器 UI**（多租户用户可见，单租户用户隐藏）
8. localStorage 记录最近使用的 tenantId，登录默认进入

**测试**

9. 更新注册/登录/p0-flow 等受影响的测试断言
10. 新增：注册不建租户、登录空租户引导、显式创建租户、多租户登录默认租户、切换租户后权限隔离

### 5.3 数据迁移

- 存量用户：注册时已建租户，本身就是 owner → 无需迁移，逻辑天然兼容
- 无需数据回填，纯逻辑兼容

### 5.4 风险评估（修正版：整体中等，可控）

| 改动点 | 风险 | 说明 |
|--------|------|------|
| `/register` 删租户插入 | 🟢 低 | 事务缩小，无副作用 |
| `/login` 空租户处理 | 🟡 中 | 返回结构变化，新增"无租户用户"系统状态 |
| 新增"创建租户"API | 🟢 低 | 纯增量 |
| 前端 onboarding 引导页 | 🟡 中 | 新页面 + 路由守卫拦截无租户状态 |
| 前端组织切换器 UI | 🟡 中 | AdminLayout 加切换入口 |
| 测试更新 | 🟡 中 | 注册/登录/p0-flow 断言失效需同步改 |
| 存量数据兼容 | 🟢 低 | 老用户有租户，逻辑天然兼容 |
| **最大坑：无租户用户访问 L2 路由** | 🔴 高（必须闭环） | 路由守卫必须把无租户用户挡在引导页外，否则体验断裂 |

**结论：整体风险中等，可控；核心改动集中在注册/登录两处，回滚只需恢复 `/register` 的 3 行事务。**

**当前（2026-08-02）：方案 C 已实施上线。**（原决策"团队版时做"因 registered 参与模式上线提前触发——噪音租户影响面扩大，详见下方补充。）

| 2 | `/login` 新增 `needsTenant`（无租户为 true） | 4117fc4 |
| 3 | `/create-tenant` 显式创建租户（事务 + 重签 JWT + 租户名 2-30 字符校验） | 4117fc4 + 审查收尾 |
| 4 | `/verify-email` 返回 `needsTenant`（与 login 对齐） | 审查收尾 |
| 5 | OnboardingView 引导创建租户（"稍后再说"允许离开返回首页） | 4117fc4 + 审查收尾 |

| 7 | **路由守卫闭环（§5.4 最大坑）**：已登录无租户用户访问 /admin 重定向 onboarding（JWT 解析 tenantId，排除 /platform 与 onboarding 自身） | 审查收尾 |

**实施审查发现与修复（2026-08-02）：**

| 问题 | 修复 |
|------|------|
| **路由守卫缺口（§5.4 预判的最大坑）**：无租户用户直接访问 /admin 撞后端 403"无租户上下文" | 守卫新增 `!jwtTenantId(adminToken)` → 重定向 Onboarding（排除 /platform 与 onboarding 自身防死循环） |
| **AdminRegisterView 注册 verify 后直接跳 /admin**：新注册用户 100% 无租户，必撞 403 | verify-email 返回 needsTenant；前端按 needsTenant 跳 onboarding |
| **OnboardingView"稍后再说"卡死**：只报错不能离开（registered 参与者等无管理需求用户被困） | 改为跳转首页 '/'，后续访问 /admin 时守卫再次引导 |
| create-tenant 缺 name 长度校验 | 补 2-30 字符校验（与前端 maxlength=30 对齐） |

**验证：`npx tsc --noEmit` 0 errors；`npx vitest run` 147/147 passed（含 verify-email needsTenant、create-tenant 长度校验等新增用例）。**

**与原决策的关系：**
- "团队版时做"的触发条件提前成立（registered 上线放大噪音租户），故提前实施
- 成员管理 API（团队协作）仍未实现，属团队版剩余工作
- 组织切换器 UI（方案 C 第 7 步）尚未做——switch-tenant API 已存在，前端切换入口待团队版补
