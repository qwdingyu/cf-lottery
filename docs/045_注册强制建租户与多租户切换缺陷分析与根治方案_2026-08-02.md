# 045 注册强制建租户与多租户切换缺陷分析与根治方案

日期：2026-08-02
状态：方案评审中（暂不实施）
相关代码：`src/routes/auth.ts`、`frontend/src/composables/useAdminAuth.ts`

## 一、背景

"添加团队成员"功能存在设计缺陷：被添加的成员登录后进入自己的租户，无法访问团队租户，
导致团队成员协作功能形同虚设。

此前提出用 `POST /switch-tenant`（多租户切换）修复，但该方案引入了"一人多租户"的
管理复杂度。本文档重新分析根因，论证 switch-tenant 是治标不治本，并提出从源头根治的方案。

## 二、根因分析

### 2.1 病根：注册强制创建租户

`auth.ts` `/register` 中的事务逻辑：

```ts
await withDbTransaction(db, async (tx) => {
  await tx.insert(users).values({ id: userId, username, email, passwordHash, emailVerified: 0 });
  await tx.insert(tenants).values({ id: tenantId, name: username }); // ← 强制每人建租户
  await tx.insert(tenantMembers).values({ tenantId, userId, role: "owner" });
});
```

**注册强制给每个人创建租户**，带来的连锁反应：

1. 每个用户天然是某个租户的 owner → 登录默认进"自己的租户"
2. 用户被邀请加入他人租户 → 必然变成"一人多租户"
3. 一人多租户 → 必须区分"当前上下文" → 被迫发明 switch-tenant
4. switch-tenant 又要改登录响应、JWT 签发、前端租户上下文管理

**结论：switch-tenant 是用复杂度掩盖错误的数据模型假设。**
"注册即拥有租户"把"租户"从**显式的组织行为**降级成了**注册的副产品**。

### 2.2 switch-tenant 引入的复杂度

- 登录必须返回 `tenants[]`，前端维护"当前租户上下文"
- 切换租户要重新签发 JWT（`tenantId` 写死在 token 里）
- 前端所有管理页都要感知"当前在哪个租户"
- 用户心智负担："我为什么有两个租户？哪个是我该用的？"
- 权限校验链路变长（成员表查询 + 租户上下文双重校验）

## 三、方案对比

### 方案 A：保留注册建租户 + switch-tenant（治标）

| 维度 | 评估 |
|------|------|
| 复杂度 | 高：默认多租户，切换是主流程 |
| 团队成员场景 | 可用，但成员登录先进自己的租户，需手动切换 |
| 用户心智 | "一人多租户"是默认状态，困惑 |
| 改动量 | 登录、JWT、前端上下文、切换 API 全链路 |
| 数据迁移 | 无 |

### 方案 B：注册不建租户，租户显式创建（治本，推荐）

核心原则：**租户是显式创建的组织行为，不是注册附赠品。**

| 维度 | 评估 |
|------|------|
| 复杂度 | 低：默认单租户，切换降级为边缘兜底 |
| 团队成员场景 | 成员登录直接进入加入的租户，无感 |
| 用户心智 | 绝大多数用户只有 1 个租户 |
| 改动量 | 注册删 2 行 + 新增"创建租户"API + 登录空租户引导 |
| 数据迁移 | 老用户已有租户不受影响；新注册用户走新流程 |

## 四、推荐方案 B 详细设计

### 4.1 新用户生命周期

```
注册（只建 user，无租户）
  → 首次登录：无租户 → 引导创建租户 / 提示等待被邀请
  → 主动"创建租户"（复用现有建租户逻辑）
  → 或被邀请加入团队租户
  → 之后：单租户使用，无需切换
```

### 4.2 改动清单

**后端（`src/routes/auth.ts`）**

1. `/register`：删除 `tenants`、`tenantMembers` 两条插入，事务只保留 users 插入
2. `/login`：无租户时 `tenantId` 返回 `""`，响应增加 `needsTenant: true` 标志
3. 新增 `POST /tenant`（或并入租户管理路由）：用户显式创建自己的租户
   - 校验用户当前无租户（或允许创建多个，作为边缘能力）
   - 事务：建 tenant + 建 owner membership
4. `/switch-tenant` **保留但降级**：仅作为"自己建了租户 + 又被邀请"的边缘兜底，不再承担主流程职责

**前端**

5. 首次登录检测 `needsTenant` → 引导页："创建你的第一个租户"（或"等待团队邀请"）
6. 管理页租户上下文：默认单租户，不再强制展示切换 UI；有多个租户时才出现切换入口

### 4.3 数据迁移

- 存量用户：注册时已建租户，本身就是 owner → 无需迁移，逻辑天然兼容
- 存量"被邀请成员"：其 own 租户保留，登录默认进入的唯一租户判定需与前端引导逻辑对齐
- 无需数据回填，纯逻辑兼容

### 4.4 风险与回滚

| 风险 | 缓解 |
|------|------|
| 新用户注册后无租户，可能流失 | 首次登录引导足够明确（创建租户是主按钮） |
| 存量用户多租户（own + 受邀）登录默认进哪个 | 保持现状：进第一个租户；切换入口仅对多租户用户显示 |
| 团队版"成员不建租户"的计费边界变化 | 属产品决策，本方案只动技术实现，计费规则另行评估 |
| 回滚 | 代码改动集中在注册/登录两处，`/register` 恢复 3 行事务即可回滚 |

## 五、验收标准

1. 新用户注册 → 登录 → 无租户 → 引导创建租户成功，进入管理台
2. 用户 A 注册并创建租户 → 添加成员 B（B 注册但未建租户）→ B 登录直接进入 A 的租户，可管理活动
3. 多租户用户（own + 受邀）登录默认进第一个租户，可切换
4. 存量用户（已有租户）登录行为与改造前一致
5. `npx tsc --noEmit`、`npx vitest run` 全部通过
6. 补充单元测试：注册不建租户、登录空租户引导、显式创建租户、多租户登录

## 六、遗留问题（待产品决策）

- 团队版计费：成员是否计入租户"席位"？成员创建的租户是否占用独立额度？
- 是否允许用户显式创建多个租户（多品牌运营），还是限制一人一租户？
- 邀请制（`enable_registration = false`）下，新用户无注册入口时如何加入团队？（当前成员添加依赖对方已注册）
