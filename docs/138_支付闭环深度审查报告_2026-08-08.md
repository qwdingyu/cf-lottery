## 1.竞争与锁

| 路径 | 并发保护 | 结论 |
| --- | --- | --- |
| createPaymentOrder | 事务内 `UPDATE lottery_entries SET payment_status=pending WHERE ... AND payment_status=""`(CAS 乐观锁) | ✅ 无重发订单 |
| handlePaymentCallback | `withDbTransaction` + 事务内重新读取订单状态,已 paid 直接返回 | ✅ 幂等 |
| expireOverdueOrders | 事务内读取+更新,WHERE status=pending | ✅ 无脏写 |
| acquirePrizeCode | `UPDATE prize_codes SET status=issued WHERE status=available LIMIT 1 RETURNING id`(原子更新) | ✅ 原子取卡 |

**潜在风险**:prize_codes 的 atomic UPDATE 在 SQLite 中无 MVCC 问题,并发安全。但卡密不足时 `paid_fulfillment_failed` 需要运营补发。

## 2.超发/漏发

| 场景 | 处理 | 结论 |
| --- | --- | --- |
| 卡密超发 | `prize_codes.status=available → issued` 原子取一条;卡密不足 → paid_fulfillment_failed,不静默 paid+null | ✅ |
| 订单超时 | expired + entry payment_status=expired,claimed 排除;expired 订单收支付回调 → paid_late_needs_refund(落库不补卡) | ✅ |
| 重复回调 | 幂等:事务内已 paid/paid_fulfillment_failed/paid_late_needs_refund 订单直接返回 | ✅ |
| 创建订单重试 | cancelled/expired 订单通过 retryPaymentOrder 复用原 orderId,不建多条记录 | ✅ |
| 支付网关已收单但本地不确定 | `shouldCancelOrderAfterCreateFailure(err)` 判断确定性失败才取消;不确定失败保留 pending | ✅ |

## 3.查询效率

| 查询 | 索引 | 结论 |
| --- | --- | --- |
| payment_orders 按 entryId | UNIQUE(entry_id) | ✅ |
| payment_orders 按 tenantId + createdAt | idx_payment_orders_tenant | ✅ |
| payment_orders 按 status | idx_payment_orders_status | ✅ |
| lottery_entries 按 drawId + payment_status | idx_entries_payment_status(0032) | ✅ |
| lottery_entries 按 tenant_id + draw_id + payment_status | idx_entries_tenant_draw_payment_status(0033) | ✅ |
| 首页活动矩阵 aggregate COUNT | 单次 GROUP BY drawId 聚合,非 N+1 | ✅ |
| 系统配置读取 | 每次创建订单/发布预检时读 1 行(systemConfig 主键扫描) | 可接受 |

**性能瓶颈**:expireOverdueOrders 每次创建订单时扫描所有 pending+过期的订单(无 tenant_id+createdAt+status 复合索引)。建议加索引 `idx_payment_orders_tenant_pending_expiry(tenant_id, status, created_at)`。当前数据量小可接受。
