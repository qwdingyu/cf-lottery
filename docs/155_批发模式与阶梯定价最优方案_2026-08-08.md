# 155 批发模式与阶梯定价最优方案

> 日期：2026-08-08
> 基于 docs/141 的购买件数与批发模式分析，给出完整实现方案
>
> ⚠️ **2026-08-08 审查勘误**：本文档原始方案存在**3 个灾难性漏洞**，**不能直接实施**。
> 详见 `docs/157_批发模式方案审查_漏洞与灾难风险_2026-08-08.md`。
> **核心修正**：不要修改全局 UNIQUE 索引，不要修改 `payment_orders.entry_id` 唯一约束，

> 不能先买 3 件再追加 5 件——如需追加功能，需 V2 独立存储，不能碰全局约束。

## 1. 业务定位

### 1.1 什么是批发模式

批发模式是**允许同一用户在同一次活动中购买多件商品**的批量采购模式。与秒杀的核心区别：

| 维度 | 秒杀 (flash-sale-rush) | 批发 (bulk-purchase) |
|------|------------------------|---------------------|
| 限购 | 1 件/人（UNIQUE 约束） | 不限购（可购多件） |
| 价格 | 固定一口价 | 阶梯定价（买越多越便宜） |
| 库存 | 限量（stockLimit CAS） | 限量（stockLimit CAS） |
| 订单 | 1 entry = 1 order | 1 entry = N orders |
| 入口 | 转盘/秒杀壳 | 独立选购页 |
| 转化路径 | 秒杀→支付 | 选购→阶梯价→支付 |

### 1.2 与现有活动类型的关系

```
lottery_draws.activity_kind 枚举：
  lottery       ← 抽奖（现有）
  signup_chain  ← 接龙（现有）
  checkin       ← 签到（现有）
  claim         ← 秒杀/领取（现有）
  wholesale     ← 批发（新增，本文档）
```

**`wholesale` 不替代 `claim`，而是 `claim` 的批量变体**。两者共享：
- 支付基础设施（`paymentOrders`、`paymentOrderAttempts`）
- 卡密发放（`prizeCodes`→`acquirePrizeCode`）
- 活动生命周期（`open`→`drawn`→`cancelled`）
- 参与隔离（`tenantId` 多租户）

差异仅在**参与模式**（同一用户可购多件）和**定价**（阶梯）。

## 2. 核心设计原则

### 原则 1：不破坏现有秒杀

现有秒杀（`paymentRequired=true, maxPerUser=1`）是生产已验证的闭环。批发模式作为**独立 activity_kind**，其代码路径与秒杀共享底层基础设施，但参与逻辑分支独立——确保秒杀稳定性不受影响。

### 原则 2：不使用 UNIQUE 约束做限购

`lottery_entries` 的 `idx_entries_unique` 是同一身份同一活动的去重防线。批发模式需要"同一身份可多次购买"，因此：

- **秒杀**：保留 UNIQUE 约束（天然 1 件/人）
- **批发**：去掉 UNIQUE 约束，改为**代码层校验 + 活动级库存 CAS**

### 原则 3：阶梯定价是配置，不是代码

阶梯定价（`tieredPricing`）作为 `promotion_config` 的独立节点（与 `flashSale` 同级），由 `promotion_config` 中的 `bulk` 节点承载：

```json
{
  "bulk": {
    "enabled": true,
    "stockLimit": 1000,
    "tiers": [
      { "minQty": 1,  "priceCents": 9900, "label": "单件 ¥99" },
      { "minQty": 3,  "priceCents": 8900, "label": "3件起 ¥89/件" },
      { "minQty": 10, "priceCents": 7900, "label": "10件起 ¥79/件" }
    ],
    "currency": "cny",
    "title": "Token 周卡",
    "showStock": true
  }
}
```

**为什么不做 `flashSale` 扩展而是独立节点**：
- `flashSale` 的语义是"限时抢购"，`bulk` 的语义是"批量采购"——两者是不同商业场景
- 底层 `promotionConfig` 是 JSON 对象，允许多个节点并存，互不干扰
- 未来可以同时开启 `flashSale`（秒杀导流）+ `bulk`（批发导流），运营灵活

## 3. 架构设计

### 3.1 数据模型

#### 3.1.1 Schema 迁移（最小改动）

**1. `lottery_entries`：添加 `quantity` 列**

```sql
-- 为批发模式新增购买数量字段（默认 1，兼容现有秒杀）
ALTER TABLE lottery_entries ADD COLUMN quantity INTEGER NOT NULL DEFAULT 1;
```

**为什么不用 "去掉 UNIQUE 约束 + 代码校验" 方案**（docs/141 方案 A）：
- 去掉 UNIQUE 约束暴露了所有 activity_kind 的安全风险——秒杀也必须依赖代码校验
- 加 `purchase_seq` 列使 UNIQUE 约束变为 `(tenant_id, draw_id, identity_type, identity_value, purchase_seq)`，自动抵御歧义
- 秒杀仍然 `purchase_seq=0`，UNIQUE 约束天然生效；批发 `purchase_seq=1,2,3...` 每笔记录唯一

**2. `payment_orders`：去掉 `entry_id` UNIQUE 约束**

```sql
-- 当前：entry_id TEXT NOT NULL UNIQUE
-- 改为：entry_id TEXT NOT NULL（非唯一）
-- 一个 entry 可以对应多笔支付订单（批量购买，分批支付）
-- 普通秒杀仍然 1 entry = 1 order，业务层保证
DROP INDEX IF EXISTS idx_payment_orders_entry_id;  -- 如果有的话
-- 注意：entry_id 在 schema.ts 中是用 .unique() 定义的，
-- 迁移实际是去掉 "unique()" 再创建普通索引
```

**3. `payment_orders`：新增 `quantity` 与 `unit_price_cents` 列**

```sql
ALTER TABLE payment_orders ADD COLUMN quantity INTEGER NOT NULL DEFAULT 1;
ALTER TABLE payment_orders ADD COLUMN unit_price_cents INTEGER NOT NULL DEFAULT 0;
```

**一期推荐方案**：`payment_orders` 加 `quantity` 列（最小改动），V2 再做 `order_items` 支持混合商品。

#### 3.1.2 索引设计

| 表 | 索引 | 用途 |
|----|------|------|
| `lottery_entries` | `UNIQUE(tenant_id, draw_id, identity_type, identity_value, purchase_seq)` | 参与去重（秒杀 purchase_seq=0 天然 1 件） |
| `lottery_entries` | `INDEX(tenant_id, draw_id, payment_status)` | 活动级容量计数 |
| `payment_orders` | `INDEX(tenant_id, draw_id, entry_id)` | 按 entry 查询订单列表 |
| `lottery_draws` | `INDEX(tenant_id, status, created_at)` | 已有，不变 |

### 3.2 配置解析层

新增 `src/lib/bulk-config.ts`，与 `flash-sale-config.ts` 同级：

```typescript
// 阶梯定价档位
export type BulkTier = {
  minQty: number;           // 最小件数（1, 3, 10, ...）
  priceCents: number;       // 单价（分，该档位每件价格）
  label: string;            // 展示文案，如 "3件起 ¥89/件"
};

export type BulkConfig = {
  enabled: boolean;
  stockLimit: number | null;    // 总库存上限
  tiers: BulkTier[];
  currency: string;
  title: string;
  showStock: boolean;
};

export type BulkRuntime = BulkConfig & {
  claimed: number;           // 已售件数
  remaining: number | null;  // 剩余件数
  progressPercent: number;
};

export type BulkParseResult = {
  config: BulkConfig | null;
  issues: Array<{ code: string; message: string }>;
};

// 根据选购数量计算适用单价
export function calculateTieredPrice(
  config: BulkConfig,
  quantity: number,
): { unitPriceCents: number; tierIndex: number } {
  // 按 minQty 降序遍历，取第一个满足 quantity >= minQty 的档位
  const sorted = [...config.tiers].sort((a, b) => b.minQty - a.minQty);
  for (const tier of sorted) {
    if (quantity >= tier.minQty) {
      return { unitPriceCents: tier.priceCents, tierIndex: config.tiers.indexOf(tier) };
    }
  }
  // 至少有一个档位（minQty=1），兜底
  return { unitPriceCents: config.tiers[0]!.priceCents, tierIndex: 0 };
}
```

### 3.3 参与流程（`joinDraw` 分支）

在 `participation.ts` 的 `joinDraw` 中，当 `draw.activityKind === "wholesale"` 时：

```typescript
if (draw.activityKind === "wholesale") {
  return await handleWholesaleJoin(tx, draw, params);
}
```

`handleWholesaleJoin` 的核心逻辑：

```
1. 解析 bulkConfig（从 promotionConfig）
2. 校验 bulkConfig.enabled === true
3. 解析前端传入的 quantity（选购数量）
4. 校验 quantity >= 1 且为整数
5. 计算阶梯单价（calculateTieredPrice）
6. 活动级库存 CAS（activeParticipantCount + quantity <= effectiveMax）
   → 注意：这里是 +quantity，不是 +1
7. 写入 entry（quantity 字段记录购买件数）
8. 返回 entryId + quantity + unitPriceCents + totalCents
```

**关键设计决策**：批发模式是**一条 entry 记录 N 件**，还是**一条 entry 记录 1 件 + 重复 N 次**？

| 方案 | 优点 | 缺点 |
|------|------|------|
| 一条 entry 记录 N 件 | 数据库行数少，order 直接关联 | 需要新增 quantity 字段 |
| 重复 N 条 entry | 复用现有 schema | 行数爆炸，退款/查询复杂 |

**推荐方案**：一条 entry 记录 N 件，`lottery_entries` 新增 `quantity` 列（默认 1，兼容现有秒杀）。

### 3.4 支付流程

#### 3.4.1 下单

`createPaymentOrder` 接收 `quantity` 参数：

```typescript
// 计算总价
const totalCents = unitPriceCents * quantity;

// 写入 payment_orders 时携带 quantity + unitPriceCents
await tx.insert(paymentOrders).values({
  id,
  tenantId: input.tenantId,
  drawId: input.drawId,
  entryId: input.entryId,
  quantity,           // 新增
  unitPriceCents,     // 新增（阶梯后的单价）
  amountCents: totalCents,
  ...
});
```

#### 3.4.2 发卡

`acquirePrizeCode` 在当前逻辑中按 `quantity` 发放：

```typescript
// 当前：领取 1 个码
// 批发：领取 quantity 个码
const prizeCodes: string[] = [];
for (let i = 0; i < quantity; i++) {
  const code = await acquirePrizeCode(tx, tenantId, drawId);
  if (!code) break;   // 码池不足，部分发放不可接受
  prizeCodes.push(code);
}
```

**注意**：**卡密不足时不允许部分发放**。要么全部发完，要么订单进入 `fulfillment_failed` 等待运营补发。这是 docs/131 的既有原则（`paid_fulfillment_failed` 不释放名额，运营补发后复查）。

#### 3.4.3 退款

退款按 `quantity * unitPriceCents` 计算，与单件退款逻辑一致（只是金额不同）。

### 4.1 混合购买（V2）

同一订单支持多种商品（不同 SKU）。需要 `order_items` 表：

```json

  "bulk": {
    "enabled": true,
    "skus": [
      {
        "skuId": "token-weekly",
        "title": "Token 周卡",
        "tiers": [
          { "minQty": 1, "priceCents": 9900 },
          { "minQty": 3, "priceCents": 8900 }
        ]
      },
      {
        "skuId": "token-monthly",
        "title": "Token 月卡",
        "tiers": [
          { "minQty": 1, "priceCents": 29900 },
          { "minQty": 3, "priceCents": 25900 }
        ]
      }
    ]
  }
}
```

### 4.2 定时抢购叠加（V2）

批发模式叠加限时抢购（`flashSale` + `bulk` 同时启用）：

```json
{
  "flashSale": { "enabled": true, "sessionLabel": "12:00场", ... },
  "bulk": { "enabled": true, "tiers": [...], ... }
}
```

运营可在同一活动中同时开启"秒杀倒计时"和"批发选购"——用户可以先抢一张秒杀价，再追加批发价购买更多。但 V1 不建议同时启用（复杂度高）。

| 风险 | 等级 | 缓解措施 |
|------|------|---------|
| 去掉 `entry_id` UNIQUE 后并发重复下单 | 中 | 幂等性 key（已有 `idempotencyKey` 机制） |

| 现有秒杀回归 | 低 | 独立 activity_kind，现有代码路径不变 |

## 6. 与现有架构的兼容性

### 6.1 不影响

- 现有秒杀（`activityKind=claim`）：代码路径不变，schema 变动不影响
- 现有抽奖（`activityKind=lottery`）：不涉及支付，不受影响
- 现有接龙/签到：不涉及支付，不受影响
- 多租户隔离：所有查询带 `tenantId`，新表继承该原则
- 支付回调：`handlePaymentCallback` 按 `quantity` 发卡，兼容现有回调逻辑

### 6.2 需要适配

- `payment_orders` 的 `entry_id` UNIQUE 约束去掉后，要确保幂等性（通过 `idempotencyKey` 或 `currentAttemptId`）
- `activeParticipantCount` 的 CAS 从 `+1` 变为 `+quantity`，所有调用点需审计
- 公开活动详情接口需返回 `bulk` 配置（与 `flashSale` 同级）

## 7. 总结与建议

### 7.1 最优方案

1. **activity_kind 独立**：新增 `wholesale` 作为独立活动类型，与 `claim` 共享支付基础设施
2. **阶梯定价为配置**：`promotionConfig.bulk` 节点，不新增表
3. **最小 schema 改动**：`lottery_entries` 加 `quantity` 列，`payment_orders` 加 `quantity` + `unitPriceCents`，去掉 `entry_id` UNIQUE
4. **库存 CAS 支持批量**：`activeParticipantCount + quantity` 代替 `+1`
5. **发卡按量发放**：`acquirePrizeCode` 循环调用 `quantity` 次，全部成功或全部失败

### 7.2 不建议的方案

- **不新增 `order_items` 表**（V1 过度设计，V2 可选）
- **不修改 `flashSale` 配置结构**（保持语义独立，不耦合）
- **不允许多个 SKU 混合购买**（V1 只做单 SKU 批量，复杂度可控）
- **不修改现有秒杀流程**（确保生产稳定性）

### 7.3 收益预估

| 指标 | 当前 | 实施后 |
|------|------|--------|
| 单用户单活动购买上限 | 1 件 | 不限（按库存和阶梯定价） |
| 订单均价 | 固定 | 阶梯递减（鼓励批量） |
| 运营灵活性 | 只能秒杀 | 秒杀 + 批发双模式 |
| 代码复杂度 | — | 低（3 个文件新增，5 个文件修改） |
