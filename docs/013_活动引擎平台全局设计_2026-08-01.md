# cf-lottery 活动引擎平台全局设计

> 文档编号：013  
> 创建时间：2026-08-01  
> 定位：面向 SaaS 平台的活动引擎总设计，不限于抽奖  
> 目标：在不推翻 MVP 的前提下，提前冻结可持续扩展的顶层抽象

## 一、结论先行

cf-lottery 不应被定义成“抽奖 SaaS”，而应被定义成：

> **一个多租户、可白标、可嵌入的活动引擎平台。**

抽奖只是第一种玩法。接龙、报名、投票、问卷、预约、签到、候补、审核、领券、抽签分配等，才是同一套后端骨架上的不同活动模式。

如果只围绕抽奖来设计，后续加入接龙、报名、投票时很容易推翻：

- 资格模式会被玩法绑死。
- 结果模型会被“中奖”绑死。
- 统计模型会被“参与人数”绑死。
- 页面模型会被“游戏动画”绑死。
- 商业模式会被“单次活动导流”绑死。

正确做法是先冻结平台抽象，再往上挂具体模式。

## 二、平台顶层抽象

### 2.1 一句话抽象

每一个活动都可以描述成：

```text
谁可以参加
  -> 参与者提交什么
  -> 平台如何验证资格
  -> 平台如何分配结果
  -> 平台如何通知、导流、归档、统计
```

### 2.2 五层结构

#### 1. 租户层

负责组织、品牌、成员、权限、配额、账单、风控策略。

#### 2. 活动层

负责活动模板、标题、时间、状态、规则版本、可见性、主题、语言。

#### 3. 参与层

负责资格校验、表单输入、验证码、名单、邀请码、外部校验、重复提交控制。

#### 4. 结果层

负责随机分配、顺序分配、手动确认、定时处理、票选结果、预约确认、候补转正等。

#### 5. 运营层

负责通知、导流、分享、二维码、埋点、导出、审计、复盘、模板复制。

### 2.3 三个必须冻结的稳定维度

#### `activity_kind`

活动是什么业务，不是页面长什么样。

建议值：

- `lottery`
- `signup_chain`
- `vote`
- `survey`
- `reservation`
- `checkin`
- `claim`
- `approval`
- `assignment`
- `waitlist`

#### `participation_mode`

谁能参加，如何验证资格。

建议值：

- `open`
- `roster`
- `password`
- `invite_code`
- `unique_code`
- `approval`
- `external_check`

#### `experience_type`

用户看到什么交互。

建议值：

- `submit`
- `wheel`
- `slot`
- `scratch`
- `card`
- `list`
- `form`
- `ballot`
- `calendar`
- `queue`

这三个维度不要互相推导。它们是独立配置。

## 三、接龙是否属于同类

结论：**属于同类，而且应当优先纳入平台核心。**

### 3.1 接龙和抽奖共用的能力

- 活动创建。
- 时间窗口。
- 名单/密码/邀请码/公开入口。
- 重复参与控制。
- 容量控制。
- 导出。
- 通知。
- 审计。
- 多租户隔离。
- 品牌页和分享页。

### 3.2 接龙和抽奖的差异

抽奖的结果是“随机分配”。

接龙的结果是“顺序占位”或“按规则占位”。

也就是说，接龙不是随机结果，而是：

```text
参与者按时间/名单/规则依次占坑
```

因此接龙应建模为：

- `activity_kind = signup_chain` 或 `reservation`
- `result_mode = ordered_assignment`
- `slot_policy = first_come_first_served | priority | approval`

### 3.3 接龙最适合的场景

- 活动报名接龙。
- 课程名额接龙。
- 社群福利排队。
- 现场名额领取。
- 讲座/沙龙座位预订。
- 试用名额申请。
- 内测/公测资格占位。
- 群内收集信息接龙。

接龙的商业价值通常不低于抽奖，因为它更贴近真实业务流程，且更容易进入“持续使用”而不是“一次性活动”。

## 四、哪些模式应纳入平台核心

### 4.1 第一梯队：低成本高价值

这些模式和抽奖共享度高，适合优先纳入同一骨架。

| 模式 | 与抽奖共享什么 | 价值 | 复杂度 |
|---|---|---:|---:|
| 抽奖 | 资格、结果、通知、导出、审计 | 高 | 低 |
| 接龙 / 报名接龙 | 资格、容量、顺序、通知、导出 | 高 | 低 |
| 预约 / 名额预约 | 时间、容量、确认、提醒、候补 | 高 | 中 |
| 投票 / 评选 | 资格、去重、统计、公示 | 高 | 低 |
| 问卷 / 调研 | 表单、资格、导出、统计 | 高 | 低 |
| 签到 / 打卡 | 资格、重复控制、奖励、提醒 | 高 | 低 |
| 候补 / 排队 | 容量、顺序、转正、通知 | 高 | 中 |
| 审核 / 内测资格 | 资格、人工审核、通知、导出 | 高 | 中 |
| 领券 / 资料领取 | 资格、发放、追踪、通知 | 高 | 中 |

### 4.2 第二梯队：可以做，但要守住边界

| 模式 | 为什么可做 | 风险 |
|---|---|---|
| 抽签分组 / 分班 | 仍是分配问题 | 规则版本复杂 |
| 任务型活动 | 可复用事件和奖励 | 容易滑向营销自动化 |
| 邀请参与 | 可复用分享与归因 | 容易刷量和作弊 |
| 排行榜 | 提升传播 | 容易把平台拖向游戏化社区 |
| 公示名单 | 增强公信力 | 涉及隐私和撤回机制 |

### 4.3 不建议纳入核心

这些会把系统拖进重域，不适合作为平台核心能力。

- 支付/收款。
- 电商库存。
- 商品 SKU 管理。
- 购物车/下单/发货。
- 广告交易市场。
- 社交内容流。
- 复杂评论系统。
- 多方直播互动。
- 需要强审核的开放社区。

如果未来真要接这些域，应该通过集成方式连接外部系统，而不是把它们内建进活动引擎。

## 五、统一后端骨架

### 5.1 建议的稳定模块

#### 1. `tenant`

租户、成员、角色、配额、风控、品牌。

#### 2. `activity`

活动主表，保存 kind、participation_mode、experience_type、状态、规则版本、时间窗口、品牌配置。

#### 3. `participant`

参与者身份和参与记录。

#### 4. `outcome`

结果记录，抽奖是 winner，接龙是 slot assignment，投票是 vote tally，预约是 reservation，审核是 approval。

#### 5. `asset`

活动页图片、Logo、推广卡片、二维码、导流配置。

#### 6. `notification`

邮件、短信、站内通知、Webhook。

#### 7. `event`

埋点、出站点击、分享、导出、异常。

#### 8. `audit`

操作日志、规则变更、开奖结果、人工处理记录。

### 5.2 推荐的数据关系

```text
tenant 1 -> N activity
activity 1 -> N participant
activity 1 -> N outcome
activity 1 -> N notification
activity 1 -> N event
activity 1 -> N audit
```

所有玩法都应该落到这组关系上，只是 `outcome` 的解释不同。

### 5.3 状态机建议

活动状态建议固定为：

```text
draft -> published -> open -> processing -> completed -> archived
```

必要时补充：

- `paused`
- `cancelled`
- `failed`

不要为每个玩法再造一套状态机。玩法差异应体现在 `outcome` 和 `policy`，不是状态总数。

## 六、简单但不重构的 SaaS 后端

### 6.1 运营后台只保留六个一级域

1. 租户与成员。
2. 活动模板与活动列表。
3. 参与与结果。
4. 导流与通知。
5. 审计与日志。
6. 系统配置。

不要把后端切成电商式的多个大模块，否则后面每个新玩法都要重复做一遍 CRUD。

### 6.2 两类接口

#### 管理端 API

面向运营者，支持创建、编辑、发布、暂停、开奖、导出、复制、模板化。

#### 公开端 API

面向参与者，支持访问活动、验证资格、提交、查看结果、接收通知、跳转导流。

### 6.3 一个活动一个协调单元

对于会并发写入的活动结果处理，建议使用“每活动一个协调单元”的思路，避免多实例并发破坏顺序和幂等。

在 Cloudflare 生态里，这类场景适合用 Durable Objects 之类的协调能力来串行化单活动关键步骤；异步通知和非关键统计可以走队列或后台任务。

这不是要求一定现在改架构，而是要求**数据模型从一开始就允许这种实现**，不要把结果处理做成无状态纯 HTTP 直写。

## 七、玩法目录：哪些和抽奖类似

下面是更完整的玩法目录。这里的“类似”指的是：可共享活动骨架、资格系统、通知系统、导流系统和审计系统。

### 7.1 高相似，建议纳入核心

#### 抽奖

随机分配结果，最容易理解，也是最适合做平台入口的第一模式。

#### 接龙 / 报名接龙

顺序占位或按规则占位。和抽奖共享最多基础设施，且更接近真实业务。

#### 预约 / 名额预约

本质是“按时间窗口和名额规则占位”，适合课程、沙龙、体验课、门店活动。

#### 投票 / 评选

本质是资格校验 + 去重 + 计票 + 公示，适合活动评选、候选人投票、作品评审。

#### 问卷 / 调研

本质是表单收集 + 导出 + 统计，导流可以作为答题后承接页。

#### 签到 / 打卡

本质是持续参与记录 + 结果统计 + 奖励触发，适合课程、训练营、私域运营。

#### 候补 / 排队

本质是名额满后自动进入候补序列，和接龙非常接近。

#### 审核 / 内测资格

本质是报名后人工/半自动审核，适合内测、公测、活动白名单。

#### 领券 / 资料领取

本质是资格校验 + 发放结果 + 追踪，不需要电商全链路。

### 7.2 中相似，适合后续扩展

#### 抽签分组 / 分班

和抽奖类似，但结果是分组而非单个赢家。

#### 任务型活动

做任务换资格，适合裂变，但容易滑向营销自动化。

#### 邀请参与

和公开分享相关，但必须有反作弊和归因窗口。

#### 排行榜

可作为活动附加层，但不要把平台核心变成“榜单社区”。

#### 公示名单

适合作为抽奖和评选的结果页，但要配套隐私和撤回策略。

### 7.3 不同类，不建议纳入核心

#### 拼团 / 砍价 / 秒杀

这些会把平台拉进支付、库存、订单、价格和售后域。

#### 电商导购

会把活动引擎变成商品系统的一部分，不适合当前路线。

#### 社区内容流

会把平台拖向内容审核、互动社区和推荐系统。

#### 广告交易

会把平台拖进品牌投放、计费和合同结算。

## 八、推荐的模式优先级

### P0

- 抽奖。
- 接龙。
- 预约。
- 问卷。
- 投票。
- 签到。

### P1

- 候补。
- 审核。
- 领券。
- 抽签分组。
- 公示名单。

### P2

- 任务型活动。
- 邀请型活动。
- 排行榜。
- 外部 API 校验。

这个顺序的意义是：先做共享骨架最多、最接近真实 SaaS 使用频率的模式，再往外扩。

## 九、什么必须在现在冻结

如果不想在后面推翻重来，下面这些必须现在冻结。

### 9.1 冻结顶层模型

- `activity_kind`
- `participation_mode`
- `experience_type`
- `result_mode`
- `policy_version`
- `promotion_config`

### 9.2 冻结跨模式能力

- 多租户隔离。
- 成员与角色。
- 名单导入。
- 邀请码。
- 验证码。
- 审计日志。
- 导出。
- 通知。
- 分享与导流。
- 规则版本。

### 9.3 冻结不可逆边界

- 不把支付做进活动核。
- 不把商品做进活动核。
- 不把内容社区做进活动核。
- 不把结果动画当结果本身。
- 不把 UTM 当完整归因系统。

## 十、建议的落地路线

### 第一阶段

把抽奖、接龙、预约这三类模式统一到同一个活动骨架上。

### 第二阶段

补问卷、投票、签到、候补、审核、领券。

### 第三阶段

做白标、API、Webhook、模板市场和更完整的统计。

### 第四阶段

再决定是否接支付、订单、库存或广告域。

## 十一、最终建议

如果目标是一个长期可扩展的 SaaS 平台，最稳妥的结论是：

1. **抽奖不是产品本体，只是首个入口玩法。**
2. **接龙是同一类能力，应该尽早纳入核心。**
3. **活动平台的核心不是“游戏”，而是“规则驱动的参与与结果分配”。**
4. **先冻结稳定抽象，再做玩法扩展，避免后续推翻重做。**
5. **优先扩展高频、低复杂、强复用的模式，不要先碰支付、库存、广告和社区。**
