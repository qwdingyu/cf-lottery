# 191 Hono 框架性能评估与本地 SQLite 连接瓶颈分析

> 日期：2026-08-10
> 背景：cf-lottery 最初面向 Cloudflare Workers 选型 Hono，现生产部署为 VPS + systemd + 本地 SQLite（docs/126、docs/145）。需要判断「沿用 Hono」是否构成性能瓶颈、有无换框架必要。
> 方法：真实压测（wrk）+ 进程内受控对照实验，**全部基于本地 SQLite**（VPS 生产形态），不使用远程 Turso 数据作为评估依据。
> 结论先行：**Hono 不是瓶颈；瓶颈在 DB 中间件的每请求 createClient（35.6× 于连接复用）；无需换框架**。

---

## 1. 测试环境与方法

| 项 | 值 |
|----|----|
| 机器 | macOS 本机，8 核，Node v24.14.0 |
| 运行形态 | `tsx src/server.ts`（**与 VPS 生产一致**：systemd ExecStart 即 tsx） |
| 数据库 | 本地 SQLite（`file:/tmp/cf-lottery-bench.db`，WAL，25 个迁移后 schema 最新） |
| 压测工具 | wrk（-t4 -c50，10s/6s），每端点 3 轮取中位数 |
| 测试数据 | 1 公开活动 + 1 奖档 + 1000 卡密 + 1 entry |

> ⚠️ 实测踩坑记录（重要，避免后续误读数据）：应用运行时 DB 中间件读 `TURSO_URL`（而非 `DATABASE_URL`）。本机 `.env` 中 `TURSO_URL` 指向远程 Turso，若启动时未显式覆盖，压测会**连错库**：迁移用 `DATABASE_URL`（正确新库）、运行时查询用 `.env` 远程/旧库 → 大量 `Failed query` → 假 404/500。**启动基准服务的正确姿势**：
> ```
> TURSO_URL=file:/tmp/cf-lottery-bench.db TURSO_TOKEN= DATABASE_URL=file:/tmp/cf-lottery-bench.db PORT=8799 npm run dev:local
> ```

## 2. 实测数据（本地 SQLite）

### 2.1 HTTP 层吞吐（wrk，3 轮取中位数，负载 load≈2.4 时）

| 端点 | 路径含义 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 中位数 |
|------|----------|:---:|:---:|:---:|:---:|
| `GET /api/health` | 纯框架+中间件栈（无业务查询，但含每请求 createClient） | 538 | 562 | 578 | **~562 req/s** |
| `GET /api/public/draws/:slug` | DB 读（活动详情 + 参与数 COUNT，2 次查询） | 348 | 345 | 333 | **~345 req/s** |
| `GET /api/public/home-activities` | DB 读（列表 + 聚合 COUNT，3 次查询） | 356 | 345 | 355 | **~355 req/s** |

关键观察：**health（无业务查询）与 DB 读接口吞吐几乎同量级（562 vs 345）**——说明公共瓶颈不在查询逻辑，而在每个请求必经的**连接创建**。

### 2.2 进程内受控对照（Node 直连，排除 HTTP 干扰）

| 场景 | 单次耗时 | 相对基线 |
|------|:---:|:---:|
| A. 复用单个连接 SELECT | 0.037 ms | 1× |
| B. 每请求 createClient + SELECT + close（**当前生产行为**） | **1.317 ms** | **35.6×** |
| C. 复用连接 + 每请求 `PRAGMA journal_mode=WAL` + SELECT | 0.066 ms | 1.8× |

**结论闭合**：health 每请求实测 ~1.78ms（1/562s），其中 createClient 占 1.32ms（**74%**）——中间件的每请求建连就是本地 SQLite 形态的最大瓶颈，与 HTTP 层数据完全吻合。

### 2.3 对照：远程 Turso 形态（仅作对比，不作评估依据）

远程 Turso 下 health 曾实测 6.7k~9.1k req/s（createClient 为网络客户端，不阻塞本地 CPU；无本地文件 I/O）。**此数据仅说明「框架层远未到上限」，本地 SQLite 部署不适用该数字**。

---

## 3. 瓶颈定位

```
请求 → CORS → 安全头 → body-limit → 慢日志 → [DB 中间件: createClient 1.32ms ← 瓶颈] → 业务查询 0.04~0.1ms → 响应
```

| 环节 | 单请求成本 | 占比 |
|------|:---:|:---:|
| Hono 框架 + 中间件（不含建连） | ~0.4 ms | ~22% |
| **createClient（本地 SQLite 打开连接 + 初始化）** | **1.32 ms** | **~74%** |
| 业务 DB 查询（2~3 次 SELECT） | 0.04~0.1 ms | ~4% |

**框架开销占比 <25%**，且与框架无关的部分（连接创建）主导了延迟。**换 Express/Fastify/原生 Node 均无法消除该瓶颈**——它存在于 DB 中间件设计，而非 HTTP 框架。

---

## 4. 结论：是否需要换框架？

**不需要。** 理由：

1. **框架不是瓶颈**：业务查询路径中框架开销 <25%，换框架收益上限 <25% 且引入迁移风险（破坏 Workers 双平台兼容、路由/中间件重写、回归成本）。
2. **Hono 是双平台架构的正确选择**【架构事实】：`src/index.ts`（Worker 入口）与 `src/server.ts`（Node 入口）共用同一 `app` 实例（docs/167 嫁接层），换框架等于放弃 Cloudflare Workers 兼容位。
3. **瓶颈可修且修复成本极低**：DB client 改为进程级单例（见 §5），预期 DB 读接口吞吐提升 3~5 倍，远大于换框架收益。
4. **行业对照**【行业常识】：Hono 在 Node 上简单路由可达 1 万+ req/s（本项目含 6 个中间件 + 建连仍有 562），属于轻量框架第一梯队；Express 同级测试通常低于此。

## 5. 优化建议（低成本高收益，P1）

### 5.1 核心改动：DB client 进程级缓存（单例）—— ✅ 已实施（2026-08-10）

`src/index.ts` 的 DB 中间件此前**每请求**执行 `createClient({ url, authToken })`（见 §2.2 场景 B，35.6× 成本）。已实施修复：

```typescript
// src/index.ts：getCachedDbClient（已导出，含单元测试 src/index-db-cache.test.ts）
// - 按 (url, token) 键缓存 libsql client，进程级单例
// - 并发首请求用 pending Promise 防抖，只创建一次连接
// - createClient 抛异常时不缓存，下次请求重试（保持原 dbInitError 语义）
// - WAL PRAGMA 移至建连时执行一次（持久化，无需每请求）
const dbClientCache = new Map<string, Client>();
const dbClientPending = new Map<string, Promise<Client>>();
export async function getCachedDbClient(url: string, token?: string): Promise<Client> { ... }
```

**实测效果（同一台机器，修复前后各 3 轮取中位数，本地 SQLite）**：

| 端点 | 修复前 | 修复后 | 提升 |
|------|:---:|:---:|:---:|
| `GET /api/health` | ~562 req/s | **~8,860 req/s** | **15.8×** |
| `GET /api/public/home-activities` | ~355 req/s | **~1,017 req/s** | **2.9×** |
| `GET /api/public/draws/:slug` | ~345 req/s | **~635 req/s** | **1.8×** |

**回归验证**：全量 vitest 81 文件 1050 测试通过（含新增 `src/index-db-cache.test.ts` 7 用例：缓存命中/隔离/并发防抖/多凭据 + DB 中间件 health 语义回归）。测试走 `TURSO_URL:""` 分支或独立测试 app，不受缓存影响。

### 5.2 次要优化（按需）

| 项 | 说明 | 优先级 |
|----|------|:---:|
| 静态页 1.2~1.7k req/s | serveStatic 逐请求读盘；加 `Cache-Control` 头 + 浏览器缓存即可 | P2 |
| 生产用 esbuild bundle 替代 tsx | dist/server.js 已由 build-for-vps.sh 产出，VPS systemd 却用 tsx；换成 dist 可再提 10~30%（JIT vs 解释执行）【行业常识，需实测】 | P2 |
| 多进程 | Node 单线程，`cluster` 按核数起进程可线性扩展吞吐（注意 SQLite 单写者：写路径不线性，读路径可） | P3 |

### 5.3 规模判断（是否现在做）

- 当前业务规模下 ~350 req/s 的 DB 读吞吐**够用**（docs/145/147 容量估算：SQLite 单 VPS 支撑数万参与者量级）；
- **触发条件**：广告激励玩法上线（`/api/miniapp/ad-reward` 高频上报）+ 公开活动页流量增长，或监控出现 p99 延迟上升时执行 §5.1（改动 <30 行，含测试半天内可完成）。
