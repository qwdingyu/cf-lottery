# 活动引擎 SaaS 顶层复审与玩法矩阵

> 文档编号：019  
> 日期：2026-08-01  
> 审查对象：009、010、013、014、015、016、017、018 文档及当前代码实现  
> 角色定位：专家顾问视角，面向长期 SaaS 平台，而不是单一 MVP  
> 重要约束：本文不使用未经验证的市场规模、转化率、GMV、ROI 数字；凡涉及代码现状均基于当前仓库事实。

## 一、最终判断

cf-lottery 最优定位不是“抽奖系统”，也不只是“导流小游戏”，而是：

> **多租户、可白标、可嵌入、可集成的轻量活动引擎 SaaS。**

抽奖只是第一种活动外壳。接龙、预约、投票、问卷、签到、领券、候补、审核、资料领取、内测申请、抽签分组等，本质都是：

```text
租户配置规则
  -> 用户按资格参与
  -> 平台产生或记录结果
  -> 平台导流、通知、统计、审计
  -> 租户复盘并复用模板
```

因此，平台的核心不是“转盘动画”或“抽奖公平性”本身，而是：

> **规则驱动的参与、资格、容量、结果、导流、追踪和运营闭环。**

如果继续只围绕抽奖加功能，后续扩展接龙、预约、问卷、投票时会被迫重写：

- 参与资格。
- 结果表。
- 前端状态机。
- 导流追踪。
- 运营后台。
- 套餐配额。
- 统计指标。

当前代码已经有良好基础，但仍需要在平台层面收口，防止“每加一个玩法就复制一套流程”。

## 二、当前仓库事实

### 2.1 已经做对的部分

当前代码已经具备活动引擎 SaaS 的雏形：

| 能力 | 当前证据 | 判断 |
|---|---|---|
| 多租户 | `tenants.plan/status/brand_config`，`tenant_members` | 已有基础 |
| 活动抽象 | `lottery_draws` 已包含 `activity_kind`、`participation_mode`、`experience_type`、`result_mode`、`allocation_policy`、`policy_version`、`promotion_config` | 方向正确 |
| 统一结果层 | `activity_outcomes` 已存在，可承载接龙/预约/候补/审核等非抽奖结果 | 方向正确 |
| SaaS 配额 | `free/pro/team/enterprise` 计划和活动数、单活动人数、成员、Webhook 配额已在服务层出现 | 已形成基础约束 |
| 接龙闭环 | `signup_chain` 已能按顺序分配、容量拒绝或候补 | 已有第一个非抽奖 vertical slice |
| 导流 | `promotion_config`、`product_link`、`coupon_codes`、`share_records` 已存在 | 有基础，不等于完整归因 |

| 白标 | `brand_config` 已在租户表中存在 | 有基础 |

关键代码事实：

- 活动主表字段已从抽奖扩展到活动引擎维度：`src/db/schema.ts` 中 `lottery_draws` 包含 `activityKind`、`participationMode`、`experienceType`、`resultMode`、`allocationPolicy`、`policyVersion`、`promotionConfig`。
- 非抽奖结果表已存在：`activity_outcomes` 用 `outcome_type/status/sequence_no/assignment_no/result_label/metadata_json` 表达接龙、预约、候补、审核等结果。
- 配额逻辑已存在：`PLAN_LIMITS` 覆盖 `maxActivities`、`maxParticipantsPerActivity`、`maxMembers`、`maxWebhooks`。
- 公开端已能返回 `activityKind`、`allocationPolicy`、`promotionConfig`，并在 `signup_chain` 下返回 outcome。

### 2.2 必须纠正的认知

文档 018 中“8 个模块已全部覆盖”的结论需要细化：

```text
有表 / 有字段 / 有接口
  不等于
  已经形成完整平台能力
```

当前更准确的表述是：

| 模块 | 当前状态 | 真实判断 |
|---|---|---|
| tenant | 有租户、成员、品牌、套餐字段 | 缺平台级租户运营后台、套餐变更审计、用量账单化 |
| activity | 有统一字段 | 主表仍叫 `lottery_draws`，可先兼容，但领域语言需要逐步上移到 activity |
| participant | 有 entries、名单、邀请码、验证码、黑名单 | 缺通用表单 schema、字段校验、分活动提交结构 |
| outcome | 有 `activity_outcomes` | 抽奖仍走 `lottery_winners`，需要长期收口到统一 outcome 视角 |
| promotion | 有外链、优惠券、分享记录 | 缺曝光/点击/参与/转化事件表，不能证明成交或核销 |
| notification | 有邮件中奖通知 | 缺通用通知任务、失败重试、模板管理、Webhook 投递记录 |
| event | 有分享点击记录 | 缺统一事件模型和漏斗统计 |
| audit | 有 audit_logs | 需要覆盖所有人工干预、套餐变更、规则变更、结果变更 |

### 2.3 当前最危险的架构泄漏

这些不是“必须立刻大重构”，但必须纳入下一阶段修正，否则未来会推翻：

1. **抽奖语义仍在核心接口泄漏。**  
   `lottery_draws`、`lottery_entries`、`lottery_winners` 命名仍以 lottery 为中心。MVP 可以保留表名，但对外接口、服务层和文档应逐步采用 activity/entry/outcome 语言。

2. **非抽奖活动不能被 `winnerCount` 校验绑住。**  
   2026-08-01 已完成第一步修正：`createDraw()` 仅对 `lottery` 强制 `winnerCount >= 1`，接龙、问卷等非抽奖活动可以按自身 `result_mode` 创建。后续扩展新玩法时仍需坚持这一规则。

3. **`experience_type` 枚举必须支撑活动引擎设计。**  
   2026-08-01 已完成第一步修正：管理路由白名单补充了 `list/calendar/form/ballot/quiz/checkin/queue/reveal/grid`。后续新增体验只能作为展示皮肤，不得决定资格和结果。

4. **`result_mode` 默认值不能由前端兜底。**  
   2026-08-01 已完成第一步修正：服务层按 `activity_kind` 推导默认 `result_mode`，管理路由不再用 `body.resultMode || body.drawTrigger` 把接龙等非抽奖活动压回 `manual`。

5. **Webhook 已有 delivery 与 Cron 重试基础，但仍未形成完整运营能力。**
   2026-08-01 已完成 `webhook_deliveries`、签名、投递记录、重试状态、事件幂等键、管理端查询/重试、Worker Cron 到期重试调度和服务层测试。后续仍需失败告警和租户侧可视化。

6. **分享裂变已有有效邀请基础，但还不是完整反作弊裂变。**
   2026-08-01 已完成服务端 join attribution：只有通过 `ref` 带来的新参与者成功入库后，才递增 `share_records.joined_count` 并写入 `attributed_join`。后续仍需归因窗口、反作弊、同设备/同身份限制和奖励上限。

7. **UTM 只能证明来源，不能证明成交。**  
   没有目标系统回传时，只能说“出站点击”“访问来源”，不能说“成交”“GMV”“ROI”。

## 三、行业最佳实践抽象

本文只引用稳定、可验证的实践，不引用商业夸张数字。

### 3.1 多租户 SaaS 的核心是租户隔离和租户上下文

SaaS 平台必须把 tenant context 作为请求、数据、审计、配额和权限的第一约束。租户隔离不是只靠 UI 隐藏数据，而是后端查询、写入、索引、审计都必须带 tenant。

当前代码已经普遍传递 `tenantId`，这是正确方向。下一步要加强：

- 所有管理端查询必须带 `tenant_id`。
- 所有事件、通知、Webhook、导出、审计都必须带 `tenant_id`。
- 平台管理员跨租户操作必须写审计，不能静默绕过租户边界。

### 3.2 导流归因必须分层

最佳实践不是“一个外链 + UTM 就等于转化闭环”，而是分三层：

| 层级 | 回答的问题 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| UTM/source | 用户从哪来 | 来源、媒介、活动 | 不能证明成交 |
| 平台事件 | 用户在活动页做了什么 | 曝光、参与、完成、点击、分享 | 不能证明外部订单 |
| 外部回传 | 目标系统发生了什么 | 注册、核销、下单、付费 | 需要 API/Webhook/导入 |

所以平台看板必须避免把点击包装成成交。正确指标命名应是：

- `page_view`
- `participation_started`
- `participation_completed`
- `outcome_assigned`
- `cta_impression`
- `cta_click`
- `share_created`
- `share_click`
- `attributed_join`
- `external_conversion_reported`

### 3.3 SaaS 变现先卖平台能力，再卖流量

当前阶段不应把平台设计成广告交易系统。更稳妥的变现顺序：

1. 免费版：限制活动数、参与人数、团队成员、Webhook。
2. 专业版：更多活动、更高参与上限、导出、品牌配置、基础统计。
3. 团队版：多成员、角色、模板、审计、批量运营、更多 Webhook。
4. 企业版：白标、自定义域名、API、Webhook、私有化或专属支持。
5. 服务收入：模板搭建、运营代配置、企业集成、数据迁移。

原因：平台能力可以在低规模时收费；CPM/CPA/CPS 需要规模、反作弊、合同、结算、外部转化回传，不适合作为第一收入模型。

### 3.4 高并发结果分配需要活动级协调

接龙、预约、候补、抢名额、即时中奖都存在并发写入。当前 D1 事务和唯一约束可覆盖 MVP，但长期应保持“每活动一个协调单元”的设计空间。

在 Cloudflare 架构中，Durable Objects 适合承载每个活动的强一致协调：顺序分配、名额扣减、候补转正、重复提交幂等等。现在不必立刻迁移，但数据模型必须允许未来把关键写路径迁移到活动级 coordinator。

## 四、顶层平台设计

### 4.1 一句话模型

每个活动都是：

```text
Activity = Rule + Entry + Qualification + Outcome + Promotion + Event + Audit
```

其中：

- `Rule`：活动规则、时间、容量、字段、奖品/权益、版本。
- `Entry`：参与者提交记录。
- `Qualification`：资格校验，开放、名单、密码、邀请码、唯一券码、审核、外部校验。
- `Outcome`：结果，中奖、顺序名额、候补、预约确认、投票计数、审核通过、资料领取。
- `Promotion`：导流目标、CTA、优惠券、下一活动、外部链接。
- `Event`：曝光、参与、点击、分享、回传。
- `Audit`：谁在什么时候改了什么规则、结果、配额、成员、配置。

### 4.2 稳定内核模块

建议把平台长期收敛为 11 个内核模块：

| 模块 | 职责 | 当前是否已有基础 | 下一步 |
|---|---|---:|---|
| tenant | 租户、状态、品牌、套餐 | 是 | 增加平台运营后台、套餐变更日志 |
| user/team | 用户、成员、角色 | 是 | 增加角色权限矩阵和成员邀请 |
| activity | 活动主模型、生命周期、模板 | 是 | 建立 generic activity interface，弱化 lottery 命名 |
| rule/policy | 活动规则、容量、字段、版本 | 部分 | 增加规则 JSON schema 和版本校验 |
| qualification | 资格校验 | 部分 | 抽成统一资格管线 |
| entry | 参与记录和提交数据 | 是 | 增加通用 form submission |
| outcome | 统一结果 | 部分 | 抽奖也逐步映射到 outcome |
| reward/benefit | 奖品、券码、资料、权益 | 部分 | 避免电商库存化，只保留发放/核销 |
| promotion | 导流配置、CTA、渠道 | 部分 | 统一 promotion_config 和事件 |
| event/analytics | 事件、漏斗、归因 | 弱 | 新增 activity_events |
| notification/integration | 邮件、Webhook、API | 部分 | 增加 delivery/retry/signature |

### 4.3 必须冻结的维度

这些维度要稳定，后续只加枚举值，不改语义：

| 维度 | 说明 | 建议值 |
|---|---|---|
| `activity_kind` | 活动业务类型 | `lottery`、`signup_chain`、`reservation`、`vote`、`survey`、`checkin`、`claim`、`approval`、`waitlist`、`quiz`、`contest`、`assignment` |
| `participation_mode` | 资格入口 | `open`、`roster`、`password`、`invite_code`、`unique_code`、`approval`、`external_check`、`member_only` |
| `experience_type` | 交互皮肤 | `submit`、`wheel`、`slot`、`scratch`、`card`、`list`、`calendar`、`form`、`ballot`、`quiz`、`checkin`、`queue`、`reveal` |
| `result_mode` | 结果产生方式 | `manual`、`scheduled`、`instant`、`ordered_assignment`、`capacity_assignment`、`vote_tally`、`review_decision`、`no_result` |
| `allocation_policy` | 分配策略 | `capacity`、`waitlist`、`fifo`、`priority`、`random`、`weighted_random`、`approval` |
| `promotion_goal` | 导流目标 | `external_link`、`coupon`、`lead_capture`、`next_activity`、`download`、`contact_sales`、`offline_redeem` |
| `reward_policy` | 权益发放 | `none`、`single_code`、`unique_code_pool`、`manual_fulfillment`、`external_fulfillment` |
| `visibility_policy` | 公示策略 | `private`、`masked_public`、`public`、`admin_only` |
| `risk_policy` | 防刷策略 | `basic`、`strict`、`manual_review`、`external_risk` |

关键原则：

- `activity_kind` 不决定页面皮肤。
- `experience_type` 不决定结果。
- `participation_mode` 不决定导流。
- `result_mode` 不决定奖品。
- `promotion_goal` 不进入商品、订单、库存域。

### 4.4 统一生命周期

建议长期统一为：

```text
draft
  -> published
  -> open
  -> closed
  -> processing
  -> completed
  -> archived
```

旁路状态：

```text
paused
cancelled
failed
```

当前代码里的 `drawn/drawing` 可以保留兼容，但平台层应映射为：

| 当前抽奖状态 | 平台语义 |
|---|---|
| `draft` | `draft` |
| `open` | `open` |
| `drawing` | `processing` |
| `drawn` | `completed` |
| `paused` | `paused` |
| `cancelled` | `cancelled` |

不要为投票、接龙、预约、问卷分别新建状态机。

## 五、抽奖、接龙及类似玩法总清单

下面列举的是“低成本、高价值、符合当前架构”的玩法。这里的“类似抽奖/接龙”指共享以下能力：

- 多租户活动创建。
- 公开链接/二维码。
- 资格校验。
- 参与记录。
- 容量或去重。
- 结果或确认。
- 通知、导出、审计。
- 导流 CTA。
- 事件追踪。

### 5.1 第一梯队：应纳入平台核心

| 玩法 | activity_kind | result_mode | 本质 | 为什么低成本高价值 | 优先级 |
|---|---|---|---|---|---:|
| 抽奖 | `lottery` | `manual/scheduled` | 随机抽取 | 当前已有，强传播，易理解 | P0 |
| 即时抽奖 | `lottery` | `instant` | 参与即出结果 | 可玩性强，适合导流页 | P1 |
| 接龙/报名接龙 | `signup_chain` | `ordered_assignment` | 顺序占位 | 和抽奖共享骨架，业务高频 | P0 |
| 名额预约 | `reservation` | `capacity_assignment` | 时间/名额确认 | 课程、门店、沙龙常见 | P1 |
| 候补排队 | `waitlist` | `ordered_assignment` | 满额后排队 | 接龙自然扩展，提高转化承接 | P1 |
| 领券/权益领取 | `claim` | `instant` | 资格通过后发放 | 直接连接转化，不需订单系统 | P1 |
| 资料领取 | `claim` | `instant/no_result` | 留资后下载 | B2B 获客价值高，实现轻 | P1 |
| 问卷/调研 | `survey` | `no_result` | 表单收集 | 成本低，运营高频使用 | P1 |
| 投票/评选 | `vote` | `vote_tally` | 去重计票 | 传播强，适合社群/活动 | P1 |
| 签到/打卡 | `checkin` | `instant/no_result` | 持续参与记录 | 提升复访和活动留存 | P1 |
| 审核/白名单 | `approval` | `review_decision` | 人工或半自动确认 | 适合内测、试用、私域活动 | P1 |
| 抽签分组/分班 | `assignment` | `random/ordered_assignment` | 分配到组 | 和 outcome 机制高度一致 | P1 |

### 5.2 第二梯队：适合做成模板或扩展玩法

| 玩法 | 本质 | 建议实现方式 | 风险 |
|---|---|---|---|
| 盲盒/开箱 | 即时揭晓皮肤 + outcome | `experience_type=reveal` 或 `card` | 不能前端伪造结果 |
| 刮刮乐 | 即时揭晓皮肤 | `experience_type=scratch` | 结果必须后端决定 |
| 幸运九宫格 | 互动皮肤 | `experience_type=grid` | 不要让动画决定奖品 |
| 转盘/老虎机/翻牌 | 互动皮肤 | 只作为 experience | 已符合 010 思路 |
| 答题抽奖 | 答题资格 + 抽奖 | `quiz` + `lottery` outcome | 需要题库与判分 |
| 测验/打分 | 表单 + 分数 outcome | `quiz` | 题库复杂度需控制 |
| 作品征集 | 表单/上传 + 审核/投票 | `contest` | 涉及内容审核 |
| 提名/推荐 | 表单 + 后续评选 | `survey/vote` | 防刷和隐私 |
| 活动 RSVP | 报名确认 | `reservation` | 和接龙相近 |
| 现场签到码 | 验码签到 | `checkin` | 需要防代签 |
| 邀请解锁 | 有效邀请触发权益 | promotion/risk policy | 需要反作弊 |
| 分享加次数 | 分享后增加资格 | referral policy | 不能只按点击奖励 |
| 拼手气红包式权益 | 随机权益发放 | `lottery/claim` | 不做支付红包 |
| 限量试用申请 | 申请 + 审核 + 名额 | `approval/reservation` | 需要审核后台 |
| 等待名单 | 候补 + 转正通知 | `waitlist` | 需要转正流程 |
| 课程选座/排号 | 容量分配 | `reservation` | 多场次时需 slot 模型 |
| 线下核销券 | 领取 + 核销 | `claim` | 需要核销审计 |
| 会员福利领取 | 资格 + 发放 | `claim` | 需要外部会员校验 |
| 内测码发放 | 申请 + 码池 | `approval/claim` | 码池防超发 |
| 新品试用招募 | 留资 + 审核 | `approval/survey` | 隐私合规 |

### 5.3 第三梯队：可做，但不要进入平台核心

| 玩法 | 为什么可做 | 为什么不进核心 |
|---|---|---|
| 排行榜冲榜 | 增强传播 | 容易变成游戏社区，需要反作弊 |
| 任务型活动 | 可提升参与深度 | 容易滑向营销自动化平台 |
| 邀请裂变竞赛 | 可带拉新 | 风控、作弊、奖励结算复杂 |
| 作品社区 | 可承接评选 | 内容审核和社区治理重 |
| 直播抽奖 | 活动引擎可支持结果 | 直播互动链路是另一产品域 |

### 5.4 不建议纳入当前核心

这些能力会把平台拖进重系统，不适合作为活动引擎核心：

- 支付。
- 商品 SKU。
- 购物车。
- 订单。
- 库存。
- 发货。
- 售后。
- 佣金结算。
- 广告交易市场。
- 内容社区流。
- 复杂评论系统。

可以通过外部链接、API、Webhook、导入导出集成，但不要内建到 activity core。

## 六、引流、导流、可玩性、变现的统一闭环

### 6.1 用户侧闭环

```text
看到分享/二维码/渠道链接
  -> 打开活动页
  -> 完成参与动作
  -> 获得结果/确认/权益/候补位置
  -> 看到自然 CTA
  -> 点击外链/领取券/下载资料/进入下一活动
  -> 平台记录事件
```

关键原则：

- 先完成用户来参加活动的核心任务，再展示导流。
- 导流 CTA 要和活动结果自然相关。
- 未中奖、候补、审核中也要有承接，不要让用户“空手离开”。
- 不能用强制跳转破坏参与体验。

### 6.2 租户侧闭环

```text
选择模板
  -> 配置规则和导流
  -> 发布活动
  -> 分享链接/二维码
  -> 看参与和结果
  -> 导出/通知/复盘
  -> 复制模板继续运营
```

租户真正愿意为 SaaS 付费的，不是单个抽奖动画，而是：

- 更快创建活动。
- 更安全地控制资格和名额。
- 更清楚地看到参与和点击。
- 更方便地导出和通知。
- 更专业的品牌呈现。
- 团队多人协作。
- 可复制复用的运营模板。

### 6.3 平台侧闭环

```text
免费租户注册
  -> 创建第一批活动
  -> 触达套餐配额
  -> 升级专业/团队/企业版
  -> 使用白标、Webhook、API、模板
  -> 形成持续活动运营
```

平台变现应围绕 SaaS 权限与用量，而不是先幻想广告抽成。

## 七、简单但可持续的 SaaS 后端

### 7.1 租户后台最小闭环

租户后台不要只是活动 CRUD，至少要有：

| 一级域 | 必备能力 |
|---|---|
| 工作台 | 活动状态、参与趋势、待处理、套餐用量 |
| 活动 | 创建、编辑、发布、暂停、复制、归档、模板化 |
| 参与 | 参与列表、筛选、导出、黑名单、名单/邀请码 |
| 结果 | 中奖、接龙名额、候补、审核、核销、手工修正 |
| 导流 | 外链、CTA、优惠券、下一活动、渠道参数 |
| 事件 | 曝光、参与、完成、点击、分享、转化回传 |
| 通知 | 邮件、Webhook、失败重试、模板 |
| 团队 | 成员、角色、邀请、操作审计 |
| 品牌 | Logo、颜色、公司名、自定义域名预留 |
| 套餐 | 当前计划、用量、限制、升级提示 |

### 7.2 平台运营后台最小闭环

平台方需要一个简单但完整的 SaaS 运营后台：

| 一级域 | 必备能力 |
|---|---|
| 租户管理 | 租户列表、状态、套餐、创建时间、最近活跃 |
| 套餐与配额 | plan、feature、quota、usage、超限记录 |
| 活动监管 | 活动总量、异常活动、投诉/黑名单 |
| 系统配置 | 邮件、Webhook、限流、功能开关 |
| 模板运营 | 官方模板、行业模板、启停、排序 |
| 风控 | IP/身份异常、刷量、重复参与、分享异常 |
| 投递监控 | 邮件失败、Webhook 失败、重试队列 |
| 审计 | 租户操作、平台操作、规则变更、结果变更 |
| 支持 | 查看租户状态、只读诊断、受控人工处理 |

平台后台的原则：

- 平台管理员可以诊断，但不能无审计地改租户业务数据。
- 套餐变更、配额调整、结果修正必须写 audit。
- 系统配置和租户配置要分层，避免一个租户配置影响全局。

### 7.3 建议新增或强化的数据模型

当前不必一次全部实现，但应按这个方向预留：

| 表/模型 | 作用 | 优先级 |
|---|---|---:|
| `activity_events` | 统一事件：view/start/submit/outcome/cta_click/share/external_conversion | P0/P1 |
| `activity_templates` | 活动模板，支持复制和行业预设 | P1 |
| `activity_form_fields` 或 `activity_form_schema` | 问卷、报名、申请的通用字段 | P1 |
| `webhook_deliveries` | 投递记录、签名、重试、失败原因 | P1 |
| `tenant_usage_snapshots` | 按日/月记录用量，支持套餐和账单 | P1 |
| `feature_entitlements` | 套餐功能开关，避免硬编码扩散 | P1 |
| `activity_slots` | 预约多时段/多名额 | P2 |
| `review_tasks` | 审核流任务和决策 | P2 |
| `reward_grants` | 奖品、券码、资料、权益发放统一记录 | P2 |
| `external_conversions` | 外部系统回传转化事件 | P2 |

当前 `PLAN_LIMITS` 硬编码可以作为 MVP，但长期应把“套餐定义”和“租户订阅/权益”抽成稳定接口。即使短期仍写死，也要让业务代码只调用 `getTenantUsage()` / `getTenantPlanLimits()`，不要到处散落 plan 判断。

## 八、分阶段实施路线

### 阶段 0：立即修正，防止 MVP 变未来债务

目标：不做大重构，修正会阻碍扩展的抽象泄漏。

必须做：

1. 扩展 `EXPERIENCE_TYPES`：加入 `list/calendar/form/ballot/quiz/checkin/queue/reveal/grid`。✅ 已完成
2. 创建活动时按 `activity_kind` 默认 `result_mode`，不要由路由层强行传 `manual`。✅ 已完成
3. `winnerCount` 校验只对 `lottery` 或需要赢家数量的活动生效。✅ 已完成
4. PATCH `accessPassword` 时必须 hash，不能把明文写回。✅ 已完成
5. 文档 014/018 更新为“基础覆盖/能力完成”两层状态。✅ 已完成

验收：

- 抽奖现有测试不回退。
- 接龙不依赖前端显式传 `resultMode=list/ordered_assignment` 才正确。
- 新增一个非抽奖活动不需要新增 winners 语义。

### 阶段 1：完成活动引擎内核

目标：让新增玩法只需要配置 activity_kind、form、policy、outcome，不再复制主流程。

必须做：

1. 统一资格校验管线：open、roster、password、invite_code、unique_code、approval。
2. 统一 outcome 写入接口：assignment、waitlist、review、claim、vote、checkin。
3. 新增 `activity_events`，记录最小漏斗。
4. 建立 `activity_templates`，把抽奖、接龙、预约、问卷、投票做成模板。
5. Webhook 进入 delivery 模型，有签名、重试、失败记录。✅ 基础已完成；Cron 周期性调度已补，告警待补

验收：

- 新增“资料领取”玩法时，不需要新建一套参与表。
- 新增“预约”玩法时，不需要重写公开端参与流程。
- 看板可以区分参与、完成、CTA 点击，不夸大为成交。

### 阶段 2：扩展高复用玩法

目标：补齐低成本高价值玩法库。

优先顺序：

1. 接龙稳定化：候补转正、导出、通知。
2. 预约：单时段容量，多时段以后再做。
3. 问卷/资料领取：通用表单 schema。
4. 投票/评选：去重计票、公示隐私。
5. 签到/打卡：按天/场次重复控制。
6. 审核/白名单：review task。
7. 领券/权益：reward grant + coupon code pool。

验收：

- 每个玩法都有 tenant、activity、entry、outcome、event、audit。
- 管理端操作路径一致。
- 公开端状态机一致。

### 阶段 3：形成 SaaS 经营能力

目标：平台可运营、可收费、可支持团队客户。

必须做：

1. 平台级租户管理后台。
2. 套餐、配额、功能开关、用量快照。
3. 成员邀请、角色权限、审计完善。
4. 白标配置升级，自定义域名预留。
5. API Key 权限范围和调用日志。
6. Webhook delivery/retry/signature。✅ 基础已完成；Cron 周期性调度已补，告警待补
7. 模板市场或官方模板库。

验收：

- 平台管理员能看到租户用量和异常。
- 租户能理解为什么被限制，以及如何升级。
- 企业客户能使用白标/API/Webhook。

### 阶段 4：外部生态集成

目标：只连接外部域，不把外部域吞进核心。

可做：

- 支付订阅系统集成。
- CRM/表单系统集成。
- 电商平台优惠券/商品页集成。
- 外部会员系统校验。
- 自定义 Webhook 和 API 回传。

仍然不建议：

- 自建完整电商。
- 自建广告交易。
- 自建内容社区。

## 九、最优产品组合

### 9.1 MVP 稳定后第一批主推模板

面向大多数租户，建议先内置这些模板：

| 模板 | 对应玩法 | 目标用户 | 导流方式 |
|---|---|---|---|
| 新用户抽奖 | 抽奖 | 电商、私域、品牌 | 未中奖券、商品页、下一活动 |
| 报名接龙 | 接龙 | 社群、课程、活动 | 加群、资料、付款外链 |
| 限量名额预约 | 预约 | 门店、沙龙、课程 | 预约确认、到店提醒 |
| 资料领取 | claim/survey | B2B、教育、咨询 | 留资后下载、联系销售 |
| 投票评选 | vote | 社群、校园、品牌 | 分享拉票、结果公示 |
| 每日签到 | checkin | 训练营、课程、社群 | 连续签到奖励 |
| 内测申请 | approval | SaaS、新品、工具 | 审核通过发码 |
| 优惠券领取 | claim | 电商、门店 | 领券后跳转 |

### 9.2 最推荐的增长闭环

```text
模板化活动
  -> 二维码/链接分享
  -> 参与/领取/预约
  -> 结果页 CTA
  -> 事件追踪
  -> 模板复制复用
  -> 套餐升级
```

这条闭环同时服务：

- 用户的可玩性。
- 租户的导流。
- 平台的变现。
- 后续 SaaS 扩展。

### 9.3 不同客户的优先玩法

| 客户类型 | 首推玩法 | 原因 |
|---|---|---|
| 电商/品牌 | 抽奖、领券、投票、签到 | 容易导流到商品页和复购 |
| 教育/课程 | 报名接龙、预约、签到、资料领取 | 高频活动和名额管理 |
| B2B SaaS | 资料领取、内测申请、问卷、预约演示 | 留资和销售线索清晰 |
| 社群/私域 | 接龙、投票、签到、福利领取 | 运营高频、低成本 |
| 线下门店 | 预约、签到、核销券、抽奖 | 到店和核销闭环 |
| 活动会务 | RSVP、签到、抽奖、评选 | 会前会中会后都可用 |

## 十、当前代码的下一步建议

### 10.1 最高优先级

1. **修正 activity 默认逻辑。**  
   让 `signup_chain`、`reservation`、`survey`、`vote` 即使由 API 直接创建，也能得到正确 `result_mode` 和 `experience_type`。

2. **把 outcome 作为非抽奖活动主结果。**  
   不再为每个非抽奖玩法新建 winners 语义。

3. **建立 activity_events。**  
   2026-08-01 已完成基础表、公开事件上报接口、公开端 page_view/participation_started/participation_completed/cta_click 自动埋点、分享点击写入、服务端 attributed_join 归因、管理端汇总和服务层测试。后续仍需归因反作弊、外部转化回传和漏斗可视化。

4. **补 Webhook delivery。**  
   2026-08-01 已完成投递记录、签名、失败状态、管理端查询/重试、Worker Cron 到期重试调度和服务层测试；下一步补失败告警和租户侧可视化。

5. **更新 014/018 状态文档。**  
   避免团队误以为“已有表”就是“能力完成”。

### 10.2 不建议现在做

1. 不要先做支付、订单、库存。
2. 不要做复杂广告分成。
3. 不要做内容社区。
4. 不要为每个玩法写独立路由、独立状态机、独立统计。
5. 不要把动画当业务结果。

### 10.3 建议的工程边界

下一阶段可以不改表名，但需要在代码组织上逐步建立更稳定的接口：

```text
activity-service
  createActivity()

  joinActivity()
  decideOutcome()
  listOutcomes()
  recordEvent()

qualification-service
  verifyParticipation()

  waitlist()
  approve()

promotion-service
  buildCta()

  getLimits()
  enforceQuota()
```

先让接口变深，再决定是否拆文件。不要为了“看起来架构好”而做空抽象。

## 十一、最终执行建议

如果只选一条路线，最优方案是：

1. 保持抽奖稳定，用它作为获客入口。
2. 把接龙作为第一个正式非抽奖模式稳定下来。
3. 继续补 Webhook 失败告警、归因反作弊和外部转化回传，让导流和集成可证明。
4. 用模板方式扩展预约、问卷、投票、签到、领券、审核。
5. 用套餐/配额/白标/API/Webhook 变现，不先碰广告交易和电商核心。
6. 逐步把服务层语言从 lottery 提升到 activity，但不为了改名破坏 MVP。

最关键的顶层原则：

> **MVP 可以小，但抽象不能短视。玩法可以逐步加，但平台内核必须统一。**
