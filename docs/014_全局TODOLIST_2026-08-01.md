## 七、容量评估与运营红线（027 §7 + §13）

### 7.1 免费层容量估算

| 模型 | 日参与完成量 | 前提 |
|:----:|:-----------:|------|
| 安全运营目标 | 1,000-3,000 人/日 | 修正静态资源路由、事件治理后 |
| 稳健目标 | 5,000-10,000 人/日 | 静态资源不进 Worker，API 优化，事件节制 |
| 理想上限 | 约 15,000 人/日 | 不适合作为 SLA 或销售承诺 |
| 需付费升级 | 100,000 人/日 | 必须 Workers Paid + 架构升级 |

### 7.2 运营红线

```text
P0 安全边界未闭合，不开放注册。
静态资源仍全量 Worker-first，不做公开传播。
没有事件写入治理，不鼓励 viral 分享。
没有平台运营后台，不做正式托管 SaaS。
没有用量快照，不把租户累计参与数作为强计费依据。
日完成参与目标先按 1,000-3,000 控制。
单活动 10,000+ 参与必须提前压测和人工监控。
接近 50,000 Worker 请求/日时准备付费升级。
Turso rows read/write 到 Free 50% 时必须启用快照、采样和保留治理。
```

## 八、实施建议（按 027 §10 阶段对齐）

### 8.1 阶段 0：发布闸门（当前）

1. RBAC-lite 闭环：`/api/admin/*`、`/api/platform/*`、前端路由、测试、migration 对齐。
2. 静态资源路由改成 SPA 推荐模式，只让 API 进 Worker。
3. 平台额度码安全随机、唯一重试、CAS 兑换、审计。
4. 公开事件上报限流和写入治理。
5. 修正游戏组件"前端随机只做动画"的业务口径。
6. 建立最小观测：按路由记录请求量、耗时、错误；定期查看 Turso rows read/write。

验收标准：

```text
租户管理员不能访问平台能力
平台成员不能绕过平台门禁
静态资源不再大量消耗 Worker 请求
公开参与热路径没有全租户 COUNT
兑换码不会超发
前端不会展示伪业务结果
```

### 8.2 阶段 1：受控 Beta（完成 P1 后）

1. 资料领取/问卷 vertical slice：先做通用表单 schema、提交记录、导出和基础统计。
2. 接龙稳定化：候补转正、通知、导出。
3. 平台运营后端最小闭环：租户列表、套餐调整、平台额度码查询、用量快照读取、失败投递查询。
4. 外部转化治理：来源校验、API Key scope、调用日志、回传导入。
5. Webhook 租户侧可视化和失败告警。

### 8.3 阶段 2：小规模商业化（P2 完成后）

1. 平台运营后台最小版：租户、套餐、兑换码、用量快照、失败投递、系统配置、平台审计。
2. 领券/核销：唯一码池、领取记录、核销入口。
3. 分享裂变反作弊：有效邀请、冷却窗口、IP/设备/身份去重、异常来源治理。
4. 预约、投票/调研、签到/打卡按共享骨架依次扩展。

### 8.4 阶段 3：规模化架构升级（触发条件）

触发条件：日 Worker 请求稳定超 50,000 / 单活动峰值超 5,000-10,000 参与 / Turso 月用量超 Free 50% / 有付费客户要求 SLA。

升级路径：Workers Paid → 快照表/预聚合 → 事件采样/批量 → DB CAS 仍不足时引入 Durable Objects → 大客户独立 Turso DB → R2 异步导出。
