## 1. 结论先行（执行摘要）

**结论：该功能在微信小程序上有真实的整合优势，值得做；但必须先拍板三个决策，且要认清一个核心约束。**

### 1.1 三个必须提前拍板的决策

| # | 决策 | 选项 | 推荐 |
|---|------|------|------|
| D1 | 小程序形态 | A. 原生小程序（uni-app）/ B. H5 网页 / C. 小程序 web-view 壳 | **A 原生小程序** |
| D2 | 广告主体归属（收益归谁） | 平台自营 / 租户白标 / 混合 | **平台自营起步，预留白标** |
| D3 | 广告平台 | 微信流量主 / 穿山甲 H5 / 优量汇 H5 | **微信流量主（原生）** |

### 1.2 核心约束（必须诚实面对）

【官方确认】微信小程序**原生环境**的广告变现只有一条合规路径：**微信广告（流量主）**。
- 穿山甲、优量汇等第三方平台**不提供**微信小程序原生 SDK（微信生态封闭）；
- 小程序 `web-view` 内嵌 H5 **无法调用**原生激励视频广告组件；
- 第三方 H5 广告代码塞进 web-view 存在运营规范违规风险。

因此「接入主流广告平台」在微信小程序生态内 = **接入微信广告（流量主）**；穿山甲等平台只在 **H5 形态**下可选。

### 1.3 优势清单（一句话版）

- **流量红利**：微信月活超 13 亿，小程序免安装、即点即玩、分享卡片裂变，与抽奖活动的传播属性天然契合；
- **身份红利**：openid 是微信侧唯一稳定身份，天然防「一人多号刷奖」，比 QQ/Telegram 群身份更适合做抽奖资格认证；
- **变现红利**：激励视频是微信流量主中 eCPM 最高的广告位类型之一，且官方对单用户每日观看次数有限制（天然防刷）；
- **代码复用红利**：【架构事实】本项目已有完整的 spins 次数体系 + 签到闭环 + 即时抽奖闭环 + 平台适配层，后端只需扩展 `reason="ad_reward"` 一个枚举 + 新增一个小程序平台适配器，工作量集中在「新前端工程 + 广告接入」而非重建后端。

### 1.4 一句话风险提示

广告收入直接结算给「小程序主体」，与 cf-lottery 的**多租户 SaaS 模式存在结构性矛盾**（详见 §4.3 成本核算）；且「看广告免费拿卡密」若卡密有真实采购成本，单靠广告收入**无法回本**——必须把广告激励定位为「获客/活跃工具」而非「卡密成本覆盖手段」。

## 2. 行业全景（上帝视角）

### 2.1 微信小程序广告变现生态

【官方确认】微信小程序广告通过「流量主」机制变现：

| 项 | 现状 |
|----|------|
| 开通主体 | 小程序运营方（个人 / 企业主体均可，部分广告类型受主体类型限制）【行业常识】 |
| 开通门槛 | 累计独立访客（UV）≥ 1000 且无违规记录（官方指引提及，具体以公众平台最新规则为准）【需复核】 |
| 广告位类型 | banner、插屏、激励视频、格子广告、视频广告（小程序内视频流）、原生模板 |
| 激励视频 API | `wx.createRewardedVideoAd({ adUnitId })`，返回**页面级单例**；`onLoad` / `onError` / `onClose(res.isEnded)`；`show()` 返回 Promise；`load()` 手动拉取【官方确认】 |
| 单用户限制 | **每个用户每天可观看激励视频广告的次数有限**（官方文档明确）【官方确认】——这是防刷的天然第一道防线 |
| 结算 | 月度结算，与主体绑定收款账户，需达起付门槛（行业惯例约 100 元）【需复核】 |

关键 API 语义（【官方确认】）：

```
const ad = wx.createRewardedVideoAd({ adUnitId: 'xxxx' })
ad.onLoad(() => { /* 拉取成功 */ })
ad.onError((err) => { /* 拉取失败，可 load() 重试 */ })
ad.show().then(() => {
  ad.onClose((res) => {
    if (res.isEnded) { /* 完整观看，发放激励 */ }
    else { /* 中途退出，不发放 */ }
  })
})
```

**重要事实**：激励视频的「看完判定」完全发生在**客户端**（`onClose.isEnded`），微信流量主**不提供服务端验证回调**（区别于穿山甲/优量汇 App 端的 server-side callback）。这意味着后端只能信任客户端上报，防刷必须靠「服务端限流 + 每日上限」兜底（详见 §7.5）。

### 2.2 主流广告平台可用性矩阵

| 广告平台 | 微信小程序原生 | H5 网页（含 web-view 内嵌） | 备注 |
|----------|:---:|:---:|------|
| 微信广告（流量主） | ✅ 唯一合规路径 | ❌ 不提供 H5 广告位（公众号流量主是另一体系） | 结算给小程序主体 |
| 穿山甲（字节） | ❌ 无微信小程序原生 SDK | ✅ 有 H5/Web 激励视频 | 抖音/头条系小程序才是其主场 |
| 优量汇（腾讯广告联盟） | ❌ | ✅ 有 H5 广告 | 与微信广告同集团，但小程序内不适用 |
| 百度联盟 | ❌ | ✅ H5 广告 | 填充率与单价通常低于前两者 |
| 快手联盟 | ❌ | ⚠️ 部分支持 | 以 App 端为主 |

> 结论：**若走原生小程序 → 只有微信流量主一个选择（但它是这个生态里最主流、填充率最高的）**；
> 若走 H5 形态 → 才能实现「多广告平台聚合」（穿山甲 + 优量汇 + 百度），但代价是失去小程序原生能力（支付、分享卡片、订阅消息、激励视频的官方防刷）且 H5 广告单价/填充率显著低于小程序原生激励视频【行业常识】。

### 2.2.1 补充发现：uni-ad 聚合（DCloud 官方）—— 原生小程序内的「多平台竞价」路径

【官方确认，2026-08-10 GitHub 调研补充】uni-app 官方提供 **uni-ad 广告聚合平台**（DCloud 出品），可显著改变 D1 决策的取舍：

- **多平台竞价**：uni-ad 聚合穿山甲、优量汇、快手等广告平台，自动竞价分层，优先展示出价最高的广告——即**微信小程序原生环境下也能实现「接入多个主流广告平台」**（通过 uni-ad 中转，而非直接接各平台 SDK）；
- **微信小程序支持**：uni-ad 激励视频在微信小程序端支持（uni-app 3.4.8+），但**仅支持组件方式** `<ad-rewarded-video>`，不支持 API 方式（`uni.createRewardedVideoAd` 在微信端走的是微信流量主原生广告位）；
- **服务器回调（关键能力）**：uni-ad 激励视频支持**服务器回调**，官方文档明确「**客户端监听不可信赖，不能根据客户端通知来给用户发激励，需云端监听（服务器回调）后发放奖励**」——这直接升级了本方案 §7.4 的防刷设计（微信流量主原生路径无服务端回调，uni-ad 路径有）；
- **收益结算**：收益经 uni-ad 结算给开发者（而非各广告平台直结），需在 uni-ad 后台绑定主体/收款信息；
- **限制建议**：uni-ad 官方建议限制单用户每日激励视频观看次数（如 **15 次左右**），与 §7.5 防刷设计一致。

> 落地注意：uni-ad 服务器回调的接收端默认为 uniCloud 云函数（`uniAdCallback`），**回调能否直接配置为外部自定义 URL 直达 cf-lottery 后端需向 DCloud 官方核实**（若不可，则需 uniCloud 云函数转发到 VPS，属于新增的中间链路）。已列入 §10 待核实清单。

### 2.3 广告激励玩法（网赚模式）行业实践

【行业常识】「签到 + 看视频/看广告 + 抽奖/领金币」是微信小程序生态最成熟的变现组合之一：

- **典型链路**：用户被奖励吸引 → 每日签到（养成习惯）→ 看激励视频（平台赚广告费）→ 抽奖/兑换（用户获得感）→ 分享裂变（拉新）
- **代表品类**：网赚类小程序、工具类小程序（WiFi、清理、翻译）、小说/短剧小程序、电商抽奖插件
- **关键运营指标**：激励视频 eCPM、人均观看次数（per-user daily cap）、次日留存、分享率、提现/兑换成本
- **平台立场**：微信官方鼓励「激励视频 + 虚拟奖励」模式（本质是广告主为你的用户奖励买单），打击的是「虚假奖励」「诱导分享」「机刷广告」三类违规（见 §2.4）

### 2.4 合规红线（微信小程序运营规范）

【行业常识，需复核最新《微信小程序运营规范》原文】以下行为是广告激励玩法的高危雷区：

| 违规类型 | 具体表现 | 后果 |
|----------|----------|------|
| 诱导分享 | 「分享后才能看广告/抽奖」「分享到 3 个群解锁」 | 封禁分享能力 / 下架 |
| 虚假奖励 | 承诺的卡密/奖品实际不发放或货不对板 | 用户投诉、下架、清退流量主 |
| 广告欺诈 | 机刷观看、模拟器刷广告、群控设备 | 流量主清退 + 广告费追回 |
| 诱导点击广告 | 「点击广告后必中大奖」等话术 | 广告位受限 |
| 未成年保护 | 面向未成年人诱导观看广告 / 抽奖 | 审核拒绝 / 下架 |
| web-view 违规 | web-view 内嵌页面投放与主体无关的广告 | 该 web-view 能力受限 |

> 方案设计（§6-§7）将以上述红线为约束，特别是「看广告获得的奖励必须真实可发放」「不得强制分享」。

## 4. 整合优势分析（诚实评估）

### 4.1 真实优势

**1) 用户触达与转化路径最短**
- 微信内分享卡片 → 点击直接打开小程序（免下载、免注册），对比现有 QQ 群助手命令、Telegram bot、邮件 OTP，小程序是**离微信用户最近**的互动形态；
- 抽奖类活动在微信生态的传播效率（社交裂变系数）显著高于站外 H5【行业常识】。

**2) openid 是最适合抽奖资格认证的身份**
- openid 稳定、唯一、无法伪造（需 appid+secret 换 session_key），天然防「同人多号」；
- 对比现状：web 端靠 email OTP（可批量注册小号）、QQ 群靠 QQ 号（可开小号），openid 的「一人一身份」是这三者里最强的。

**3) 广告变现与「发卡密」形成付费闭环**
- 激励视频收入可覆盖「免费发卡密」的边际成本（针对数字卡密）；
- 用户「看广告 → 得次数 → 抽奖 → 得卡密」链路中，广告主为卡密买单，平台/租户零现金支出获客。

**4) 与现有架构的契合度极高**【架构事实】
- spins 体系 + 签到闭环 + 即时抽奖 + 卡密发放全部现成，后端新增成本集中在「广告上报 + 小程序 API」两个薄层；
- 平台适配层（adapter-factory）的存在说明项目从第一天就是为「多平台入口」设计的，小程序只是第 3 个入口。

**5) 微信支付能力（远期）**
- 现有「免费次数耗尽 → 付费加次/秒杀」漏斗（docs/171 §9）可无缝迁移到小程序内微信支付，转化率通常高于站外 H5 支付【行业常识】。

### 4.2 必须正视的约束与矛盾

**约束 1：广告收益归属与 SaaS 多租户的结构性矛盾（最重要）**

微信广告结算给「小程序主体」的收款账户。cf-lottery 是多租户 SaaS，必须回答：
- 小程序主体是谁？平台方？还是租户方？
- 广告收入归谁？谁承担「免费送卡密」的成本？
- 若归租户：每个租户需自己注册小程序 + 开通流量主 + 配置广告位，平台只提供技术能力（白标模式）；
- 若归平台：平台自营一个小程序承载所有租户活动，广告收入进平台账户，平台用广告费补贴卡密成本（聚合流量模式）。

**约束 2：单用户每日激励视频次数有官方上限**【官方确认】
- 微信对单用户每日激励视频观看次数有限制，意味着「看广告无限刷次数」不可能，产品上要设计合理的每日上限并如实告知用户。

**约束 3：无服务端广告验证回调**
- 无法像 App 端那样用 server-side callback 验证「确实看完」，防刷只能靠客户端上报 + 服务端限流（§7.5）。好在**伪造「看完」只骗取抽奖次数，不骗取广告费**（广告费按微信侧有效播放结算，微信风控拦截机刷），平台损失可控。

**约束 4：审核与合规成本**
- 小程序需提审（首次 1-7 天【行业常识】），广告激励玩法涉及「虚拟支付」「抽奖」类目，审核较严格；流量主资质（UV≥1000）本身是冷启动门槛。

**约束 5：卡密成本核算（§4.3）决定了玩法边界**
- 若卡密有真实采购成本（如月卡、激活码），广告收入几乎不可能覆盖；只有边际成本≈0 的卡密（优惠券、体验码、虚拟权益）才能「看广告免费送」。

### 4.3 商业模式成本核算（关键分析）

以激励视频单次观看收入估算（【行业常识】参考区间，实测为准）：

```
单次观看收入 = eCPM / 1000
  行业参考：网赚/工具类激励视频 eCPM ≈ 20~100 元/千次（新账号无用户标签可能低至 5~15 元）
  → 单次观看 ≈ 0.005 ~ 0.10 元，中性估算 ≈ 0.03 元/次
```

三种玩法形态的盈亏模型：

| 玩法 | 每次观看奖励 | 用户抽中卡密的成本 | 盈亏判断 |
|------|-------------|-------------------|----------|
| 看 1 次广告 = 抽 1 次，奖池含实体/高价卡密 | 1 次 | 卡密成本 5~50 元，中奖率 100% 时需 166~1666 次观看回本 | ❌ 严重亏损，不可行 |
| 看 1 次广告 = 抽 1 次，奖池为**低价虚拟卡密**（优惠券/体验码，边际成本≈0）+ 少量高价奖品（低概率） | 1 次 | 高价奖品靠低中奖率控制成本（如 1% 中奖率 × 50 元 = 期望成本 0.5 元/次 > 0.03 元/次，仍亏损） | ⚠️ 高价奖品需极低概率或独立付费池 |
| **看广告得次数 + 抽奖，卡密成本≈0，高价奖品走「付费抽/邀请解锁」** | 1 次 | 广告收入 ≈ 0.03 元/次，覆盖次数成本与低价奖品，高价奖品另设付费墙 | ✅ **推荐形态** |

**结论**：「看广告免费发送卡密」要成立，必须满足：
1. 卡密以**数字虚拟、边际成本≈0** 的类型为主（软件体验码、会员体验、优惠券、积分）；
2. 高价值奖品不放广告奖池，或中奖概率低到期望成本可被广告收入覆盖；
3. 广告收入本质是「补贴获客与活跃成本」，不是「卡密成本」的来源——这是产品定位的底线认知。

## 5. 关键决策（需产品方拍板）

### 决策一：小程序形态（D1）

| 维度 | A. 原生小程序（uni-app） | B. H5 响应式页面（复用现有前端） | C. 小程序 web-view 壳 + H5 |
|------|------------------------|-------------------------------|---------------------------|
| 广告能力 | ✅ 微信流量主激励视频（最优单价） | ✅ 可接穿山甲/优量汇/百度 H5（单价/填充率较低） | ❌ web-view 无法用原生激励视频；第三方 H5 广告有合规风险【官方确认+行业常识】 |
| 身份 | ✅ wx.login code2Session 拿 openid | ❌ 需自建微信 OAuth（网页授权，依赖已认证服务号） | ⚠️ 依赖 H5 授权，链路长 |
| 支付 | ✅ wx.requestPayment 原生微信支付 | ⚠️ H5 支付（JSAPI 需服务号） | ⚠️ 同 H5 |
| 分享裂变 | ✅ 小程序分享卡片（最强裂变） | ❌ 普通链接 | ❌ 分享 H5 链接，丢失卡片能力 |
| 订阅消息（中奖通知） | ✅ 小程序订阅消息 | ❌ | ❌ |
| 审核 | ⚠️ 需提审（类目合规） | ✅ 无需审核 | ⚠️ 需提审 |
| 冷启动 | ⚠️ 流量主需 UV≥1000 | ✅ 无门槛 | ⚠️ 同 A |
| 开发成本 | 中（新前端工程，复用后端 API） | 低（现有前端加移动端适配） | 低 |

**【建议】选 A：原生小程序（uni-app 编译）**。理由：
1. 广告单价与填充率是玩法生命线，微信流量主激励视频是唯一高收益路径；
2. 分享卡片 + 订阅消息（中奖通知）+ openid 身份 + 微信支付，四个原生能力都是抽奖玩法的核心体验；
3. B 方案的「多广告平台聚合」收益被 H5 广告的低单价抵消，且失去小程序生态位。
4. 唯一代价：需通过小程序审核 + 满足流量主 UV≥1000 冷启动（可先用 web 活动页导流到小程序，或用 H5 形态过渡冷启动期，见 §8 P2 备注）。

### 决策二：广告主体归属（D2）

| 模式 | 主体 | 广告收入 | 卡密成本 | 适用阶段 |
|------|------|----------|----------|----------|
| 平台自营 | 平台注册小程序 | 归平台 | 平台补贴 | MVP，验证玩法 |
| 租户白标 | 租户注册小程序 | 归租户 | 租户承担 | 产品成熟后开放 |
| 混合 | 平台小程序 + 租户频道 | 平台 + 租户分成 | 协商 | 规模运营 |

**【建议】平台自营起步（模式 1），架构上预留白标（模式 2）**：
- 平台自营可以：统一提审、统一流量主资质、统一广告位配置、跨租户聚合流量提高 eCPM 标签质量；
- 架构预留：`adRewardPolicy` 配置挂活动/租户维度，小程序前端通过 API 获取「当前活动归属的平台/租户主体」与对应 adUnitId，未来切换主体时后端配置即可，前端零改动。

### 决策三：广告平台（D3）

**【建议】MVP 只接微信流量主**；广告适配层（§7.4）抽象 `ad-provider` 接口，为未来 H5 形态接穿山甲/优量汇预留扩展位（与 `adapter-factory.ts` 同样的注册制模式）。

### 7.2 后端 API 设计（契约级）

所有接口：`Content-Type: application/json`，鉴权 `Authorization: Bearer <小程序JWT>`。

**1) 登录（静默）**
```
POST /api/miniapp/login
Body: { code: "wx.login 返回的临时 code" }
流程：code2Session(appid, secret, code) → openid → upsert users + auth_identities(provider=wechat) 
      → 签发自签 JWT（sub=本地 users.id，携带 wechatOpenid 声明）
Resp: { token, isNewUser, openid }   // openid 不落日志，仅内部使用
安全：code 一次性，10 分钟内有效；后端持有 appid/secret，前端不接触
```

**2) 活动详情（公开，免鉴权）**
```
GET /api/public/draws/:slug?experience=miniapp
Resp: { draw: {...}, adReward: {...}, checkin: {...} }  // 含 adRewardPolicy 脱敏配置
```

**3) 签到**
```
POST /api/miniapp/checkin
Body: { drawId, publicSlug }
逻辑：复用 executeCheckinCommand 的原子条件 UPDATE（spinsLeft += grantSpinCount, lastCheckinDate=today）
Resp: { ok, granted, spinsLeft, streak, message }
```

**4) 广告看完上报（核心新接口）**
```
POST /api/miniapp/ad-reward
Body: { drawId, publicSlug, watchId }   // watchId 由前端在广告 onClose(isEnded=true) 后生成（uuid）
服务端校验链：
  ① JWT 鉴权 → 解析 entry（tenantId 隔离，跨租户拒绝）
  ② 活动 adRewardPolicy.enabled 且 rewardPerAd>0
  ③ 频率控制：rate_limit_log 按 key=ad_reward:{openid}:{date} 计数 < dailyAdCap
  ④ 间隔控制：按 key=ad_reward:{openid} 最近一条记录距 now ≥ minIntervalSeconds
  ⑤ 幂等：spinsLog 查 reason=ad_reward 且 refId=watchId 是否已存在（防重放）
  ⑥ 全部通过 → 事务：spinsLeft += rewardPerAd + 写 spinsLog(reason=ad_reward, refId=watchId)
      + 写 activity_events(eventType=reward_earned, source=wechat_miniapp, medium=ad_reward)
Resp: { ok, granted, spinsLeft, todayCount, dailyCap }
防重放说明：watchId 幂等键 + spinsLog 唯一约束（见 §7.5）
```

**5) 抽奖**
```
POST /api/miniapp/spin
Body: { drawId }
逻辑：复用 performInstantSpin（CAS 扣次 → 加权抽档 → CAS 发码 → 写 winners）
Resp: { ok, spinsLeft, result: { tier, prize, isCodePrize } }   // 卡密不直接返回明文
```

**6) 我的卡密**
```
GET /api/miniapp/my-prize?drawId=
Resp: { prizes: [{ tierName, prizeName, codeStatus, maskedCode, fullCode? }] }
安全：复用 docs/179 一次性令牌思路——列表脱敏，查看明文需二次授权（或仅显示一次）
```

### 7.4 广告适配层（ad-provider 抽象）

目标：未来可接穿山甲 H5 / 优量汇 / 其他平台，仿 `src/services/platform/adapter-factory.ts` 的注册制：

```typescript
// src/services/ad/ad-provider.ts（新增）
export type AdProviderName = "wechat_traffic" | "csj_h5" | "ylh_h5";

export interface AdRewardProvider {
  readonly name: AdProviderName;
  /** 校验一次观看是否有效（微信流量主：仅客户端上报，返回 true；未来带 server callback 的平台：调平台回调验证） */
  verifyWatch(input: { tenantId: string; drawId: string; openidHash: string; watchId: string }): Promise<{ ok: boolean; reason?: string }>;
  /** 上报事件给平台（可选：部分平台需要广告展示/观看回传） */
  reportEvent?(event: AdProviderEvent): Promise<void>;
}

// 工厂：AD_PROVIDER_FACTORIES: Record<string, (config) => AdRewardProvider>
// 配置来源：activityConfig.adReward.provider + 平台级 secret（如微信 appid/secret）
```

**诚实说明（防刷的边界）**：
- 微信小程序激励视频存在**两条接入路径**，直接影响 `verifyWatch` 的实现强度：

| 路径 | 接入方式 | 服务器回调 | verifyWatch 实现 |
|------|----------|:---:|------------------|
| A. 微信流量主原生 | `uni.createRewardedVideoAd({ adUnitId })`（微信流量主广告位） | ❌ 无 | 仅「配额 + 幂等 + 频率」服务端校验，信任 `onClose.isEnded` |
| B. uni-ad 聚合 | `<ad-rewarded-video adpid>` 组件（uni-ad 聚合穿山甲/优量汇/快手竞价）【官方确认】 | ✅ 有（默认 uniCloud 中转，自定义 URL 待核实） | 升级为「服务器回调校验（trans_id 防重放）+ 客户端上报比对」，官方明确应以此为准发奖励 |

- **推荐：MVP 以路径 A 为主（简单、收益直结微信），预留路径 B 升级位**——当 `adRewardPolicy` 配置 `provider="uni_ad"` 且回调链路打通后，`verifyWatch` 自动切换为回调校验，接口签名不变（与 `adapter-factory.ts` 注册制同构）；
- 风险兜底（路径 A 下）：伪造观看只骗取抽奖次数（成本=1 次抽奖的期望奖品成本），不骗取广告费（微信按有效播放与风控结算），损失可控且在 `dailyAdCap` 上限内。

### 7.5 防刷设计（广告激励核心风险）

| 层 | 防线 | 实现 |
|----|------|------|
| 微信侧 | 官方单用户每日观看次数限制【官方确认】 | 无需实现，天然存在 |
| 平台建议 | uni-ad 官方建议单用户每日激励视频 **≤ 15 次左右**（超出后广告商不投放、cpm 下降）【官方确认】 | 作为 `dailyAdCap` 默认值参考 |
| 服务端-频率 | 每日上限 `dailyAdCap` | `rate_limit_log` 按 `ad_reward:{userId}:{date}` 计数 |
| 服务端-间隔 | `minIntervalSeconds` 防连点 | 最近一次记录时间戳比对 |
| 服务端-幂等 | watchId 防重放 | `spinsLog(refId=watchId)` 或 `ad_reward_events` 唯一索引 |
| 服务端-身份 | openid 绑定 entry | entry 按 `identityType=wechat_openid` + openid 唯一（复用 `idx_entries_unique`） |
| 服务端-回调（路径 B） | uni-ad 服务器回调 + trans_id 防重放【官方确认】 | 回调验签 → 校验 userId/extra → 发奖励；客户端上报仅作兜底比对 |
| 服务端-配额 | 单活动广告奖励总量上限（可选） | `activityConfig.adReward.dailyGlobalCap`，控制租户整体成本 |
| 风控（远期） | 设备指纹/行为分析 | 预留字段，MVP 不做 |

### 7.6 身份与合规

- **登录**：`wx.login` → code → 后端 `code2Session` 换 `openid + session_key`（appid/secret 只存后端环境变量，复用 `CREDENTIALS_ENCRYPTION_KEY` 加密存储模式）；
- **手机号**：`button open-type="getPhoneNumber"`（企业主体小程序可用）→ 后端 `getPhoneNumber` 解密，用于报名类/roster 活动，MVP 可不做；
- **隐私协议**：小程序需配置《用户隐私保护指引》（收集 openid、抽奖记录、广告观看记录），`app.json` 声明 `requiredPrivateInfos`；
- **类目**：抽奖/卡密发放类目建议「工具 > 信息查询」或「商业服务」，提审时需说明玩法（避免被判定为博彩/虚拟支付违规——**严禁现金/实物高价奖品抽奖涉及「赌博」判定，奖品以卡密/虚拟权益为主是安全边界**）【行业常识，需结合类目审核实际】；
- **未成年人**：抽奖活动设置年龄提示或按微信策略限制（广告激励对未成年人的展示有平台侧策略）。

### 7.7 前端工程（uni-app）

**为什么不用现有 Vue Web 代码直接改？**
- 【架构事实】现有前端是浏览器环境（Vue Router、sessionStorage、DOM 游戏组件），小程序运行环境是 WXML/自定义组件，两者运行时 API 不同；
- 强行用 `uni-app` 复刻整个 `LotteryView.vue` 不划算（管理后台、i18n、桌面布局都不需要搬进小程序）。

**【建议】新建轻量 uni-app 工程（Vue 3 语法），只做 5 个页面**：
- 技术栈：`uni-app + Vue 3 + TypeScript + Vite`（HBuilderX 或 CLI 工程均可）；
- 广告组件封装：`src/utils/ad-reward.ts` 封装 `uni.createRewardedVideoAd`（uni-app 已封装 wx API），统一 `showAd(): Promise<{ isEnded }>`；
- API 层：`src/api/miniapp.ts` 封装 6 个接口（login/checkin/ad-reward/spin/my-prize/draws）；
- 游戏壳：转盘用 `uni-app` 的 canvas 或 CSS 动画实现（约 300 行），不移植现有 Vue 组件；
- 状态：`pinia`（uni-app 支持），存储 token/spinsLeft/openidHash；
- 编译：`npm run build:mp-weixin` 产出微信小程序包 → 微信开发者工具上传提审。

**前端防刷提示**：`onClose` 必须判断 `res.isEnded === true` 才允许调 `ad-reward` 接口；`show()` 失败（拉取失败/已达平台上限）时提示用户稍后再试，不发放。

### 13.2 从开源项目确认的关键实现模式（直接采纳）

1. **广告位 ID 由服务端下发**（ChatGTP-uni）：`uni.createRewardedVideoAd({ adUnitId: ad.adId })`，adId 来自后端任务接口——验证并强化了 docs/189 §6.3 `adRewardPolicy.adUnitId` 由后端配置的设计，前端零硬编码；
2. **任务模型**（ChatGTP-uni）：`type(0=看广告/1=分享)`、`dailyLimit`、`giveFrequency`、`platform`——与 §6.3 的 `rewardPerAd/dailyAdCap` 配置语义完全同构；
3. **广告失败重试范式**（ChatGTP-uni + wot-design-uni）：`show().catch → onLoad 重试 → 仍失败 toast「广告拉取失败」`——前端体验兜底；
4. **本地标记仅用于免广告体验、不用于发奖判定**（wot-design-uni 的 `freeAdTime` 可被清 storage 重置）——印证 §7.5「发放判定必须走服务端」；
5. **uni-ad 服务器回调 + trans_id 防重放**（unidocs-zh 官方文档）——§7.4 路径 B 的权威依据，官方明确「客户端监听不可信赖」。

### 13.3 复用边界（防止「重复造轮子」变「引入包袱」）

- **只复用 UI 与接入范式**：转盘壳、广告封装、任务页骨架；
- **不复用业务状态**：次数/签到/中奖/卡密一律以 cf-lottery 后端为准（前端不存可信奖励状态，防刷边界 §7.5）；
- **不移植**：现有 Vue Web 前端代码（运行时不兼容，§7.7）、各开源项目自带的私有后端（卡密/抽奖逻辑 cf-lottery 已完备）。
