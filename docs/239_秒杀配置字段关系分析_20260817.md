# 秒杀配置字段关系分析（2026-08-17）

## 三个字段的定义

| 编号 | 字段名 | 存储位置 | 前端表单 | 语义 | 运行时使用 |
|------|--------|---------|---------|------|-----------|
| ① | `stockLimit` | `promotion_config.flashSale.stockLimit` | `form.flashSaleStockLimit` | **活动级总名额上限**（整场秒杀最多可卖份数） | `resolveEffectiveStockLimit` 优先；`activeParticipantCount < effectiveMax` CAS 截单；进度条/剩余名额展示均以此为准 |
| ② | `maxParticipants` | `draws.max_participants` | `form.maxParticipants` | **活动级参与上限（回退值）** | stockLimit 为空时回退 |
| ③ | `tiers.winnerCount` | `lottery_prize_tiers.winnerCount` | 直付批发模式 tiers 的"可售份数" | 抽奖：中奖名额；直付秒杀：**商品 SKU 的展示份数（不参与截单）** | 抽奖：`performDraw` 按此名额抽选；直付秒杀：**不参与截单、不参与卡密扣减** |

## 关系分析

### ① stockLimit vs ② maxParticipants：语义重复

```
stockLimit=6, maxParticipants=200 → 发布预检 warning（不阻断）
效果：进度条显示"已抢 2/6"，截单到 6 人截止，但"名额"显示 200
运营常见误解："我设了 200 个名额，为什么 6 个人就截单了？"
```

- `resolveEffectiveStockLimit`：stockLimit 优先，maxParticipants 回退
- **二者同时存在时，maxParticipants 是"死配置"**（不参与任何运行时逻辑）
- 不一致时仅 warning 不阻断 → 运营容易忽略

### ① stockLimit vs ③ tiers.winnerCount：维度不同但缺乏约束

```
stockLimit=6, tiers.winnerCount=10（可售份数）
效果：截单到 6 单，商品显示"可售 10 份"但只卖了 6 份
```

- stockLimit 是**活动级总名额**，tiers.winnerCount 是**商品级展示份数**
- 直付秒杀下单时：`activeParticipantCount CAS` 按 stockLimit 截单，**不扣减 tiers.winnerCount**
- 预检只检查"卡密奖品池总库存 ≥ stockLimit"（`payment.fulfillment.codes.insufficient`），**不检查 tiers.winnerCount 与 stockLimit 的关系**
- **tiers.winnerCount 在直付秒杀中是"虚假字段"**——展示给运营配置，但不参与运行时截单和卡密扣减

### ③ tiers.winnerCount 在直付秒杀中的真实角色

直付秒杀的发卡流程：
1. 下单 → `activeParticipantCount CAS`（按 stockLimit）
2. 支付成功 → `reservePrizeCodes`（按 `order.quantity` 件数扣减卡密，不按 tiers.winnerCount）
3. 商品绑定只决定"发什么奖品"（卡密奖品池），不决定"发多少份"

所以 tiers.winnerCount 在直付秒杀中**完全不参与**截单或发卡，纯展示字段。

## 约束建议

### 方案 A（推荐，改动最小）：pubish-check 升级为 error

将 `flash_sale.stock.mismatch` 从 **warning 升级为 error**（阻断发布），同时自动对齐 maxParticipants：

```ts
if (flashParsed.config.stockLimit != null && flashParsed.config.stockLimit > 0) {
  // stockLimit 生效时，自动对齐 maxParticipants 避免运营误解（docs/226）
  if (draw.maxParticipants !== flashParsed.config.stockLimit) {
    add(result.errors, "promotion", "flash_sale.stock.mismatch",
      `秒杀 stockLimit=${flashParsed.config.stockLimit} 与 maxParticipants=${draw.maxParticipants} 不一致，请将名额上限改为 ${flashParsed.config.stockLimit} 后重新发布`);
  }
}
```

### 方案 B（推荐，更彻底）：直付秒杀下隐藏 tiers.winnerCount

直付批发模式下，tiers 的"可售份数"字段改为只读（显示"由卡密库存决定"），不接收运营输入。这样：
- 消除"商品可售份数"与"截单名额"的混淆
- 超卖防护完全由 `卡密总库存 ≥ stockLimit` 保证

### 方案 C（远期）：stockLimit 与 maxParticipants 合并

将 stockLimit 提升为活动的唯一"名额上限"字段，秒杀启用时 maxParticipants 自动跟随 stockLimit；
非秒杀活动继续使用 maxParticipants。消除两个字段的冗余。

## 实施记录（2026-08-17）

### 方案 C 温和版（已实施 ✅）

**红线：运行时不动**——`resolveEffectiveStockLimit` 的 stockLimit 优先逻辑未改（存量数据行为不变）。

| 层 | 改动 |
|----|------|
| 创建路由 | 秒杀启用且 `stockLimit > 0` 时，`maxParticipants` 自动跟随 `stockLimit`（`effectiveMaxParticipants`）；仍走 createDraw 套餐配额校验（超额被拒属预期收紧） |
| 编辑路由 | 基于「合并后的 promotionConfig」（顶层键级 merge）解析 `stockLimit`，`maxParticipantsUpdate` 自动跟随；仅当请求体未显式传 `maxParticipants` 时联动 |
| 发布预检 | `flash_sale.stock.mismatch` 从 warning **升级为 error**（阻断发布），兜底 API 直写 / 旧数据不一致 |
| 前端 | 秒杀启用时 `maxParticipants` 输入框**只读**（hint 显示"参与上限自动跟随展示名额上限（当前 N）"）；watch 联动 `form.maxParticipants = flashSaleStockLimit` |
| 测试 | 创建联动（stockLimit=6→maxParticipants=6）、留空不联动（200 保持）、PATCH 联动、超配额拒绝、预检 error 阻断、截单原子性（一致配置） |

**验证**：tsc 0；vitest 1352 passed；vue-tsc 0；build 成功。

### 方案 B（已实施 ✅）：直付批发模式「可售份数」只读

| 层 | 改动 |
|----|------|
| 前端 | 直付批发模式（`isDirectBulkFlashSale`）下，tiers 的 winnerCount 输入框替换为**只读**显示"`{availableCount} 张`"（卡密库存），title 提示"可售份数由卡密库存决定"；表头"可售份数"改为"卡密库存" |
| 文案 | zh：`adminWholesaleStockReadonlyHint`"可售份数由卡密库存决定（发布预检自动校验 ≥ 秒杀名额）"；en 对应 |
| 运行时 | 直付批发发卡本就按订单件数从奖品池取卡（不读 tier.winnerCount），只读化不影响任何运行时逻辑 |
