# 177 签到随机事件 P2 实现（randomBonus）

> 日期：2026-08-10
> 定位：在签到基础奖励（固定 + 递增）之上，用小概率额外增加 spins，增加签到惊喜感
> 来源：docs/172 §6 P2 规划 + docs/175 §2.4 设计

## 1. 背景

签到体系已实现：
- P0：连续签到递增（4 种模式：daily/linear/step/cycle）
- P1：spins 流水日志审计

P2 randomBonus 是签到体系最后一块拼图——在基础奖励之上，用概率触发的"彩蛋"增加用户签到惊喜感，驱动 DAU。

参考真寻 Bot 的随机事件机制（docs/172 §1.3）：34% 概率掉落道具或额外金币，66% 概率普通奖励。

## 2. 设计

### 2.1 配置结构

```typescript
dailyCheckinPolicy: {
  grantSpinCount?: number;           // 固定奖励（旧字段）
  rewardConfig?: CheckinStreakConfig; // 递增配置（P0）
  randomBonus?: RandomBonusConfig;    // 随机奖励（P2，新增）
}

type RandomBonusConfig = {
  enabled: boolean;       // 是否启用
  probability: number;    // 触发概率（0.0~1.0，例如 0.2 = 20%）
  bonusRange: {           // 触发时额外 spins 区间
    min: number;
    max: number;
  };
};
```

### 2.2 计算逻辑

```
总奖励 = 基础奖励（固定值 + 递增） + 随机 bonus（概率触发）

基础奖励 = computeBaseReward(...)  // 原有逻辑不变
if randomBonus?.enabled && random() < probability:
  bonus = randomInt(bonusRange.min, bonusRange.max)
  总奖励 += bonus
```

关键设计决定：
- **随机 bonus 在基础奖励之上叠加**，不影响递增/封顶计算
- **使用同一个 random01 随机源**，与基础奖励的区间随机共享一个随机函数
- **不记录 spins_log 的额外类型**——随机 bonus 作为签到奖励的一部分写入，reason 仍为 `checkin`，不增加审计复杂度

### 2.3 前端 UI

在 QQ 群助手编辑面板的"签到奖励模式"下方新增"随机额外奖励"区域：

```
[复选框] 启用随机奖励
  触发概率: [0.2]    (0.0~1.0, step=0.05)
  额外奖励下限: [1]  (0~100)
  额外奖励上限: [3]  (0~100)
```

默认值：enabled=false, probability=0.2, min=1, max=3

## 5. 设计原则

### 5.1 向后兼容
- 不传 `randomBonus` 参数时行为不变
- `computeCheckinReward` 签名附加第 6 个可选参数
- 现有 `spins_log` 流水不增加新 reason 类型（随机 bonus 合并为 `checkin`）

### 5.2 防御式解析
- `parseRandomBonus` 对非法概率（>1.0 或 <0）、非法范围（max < min）返回 undefined
- `toProbability` 只接受 0.0~1.0 的值
- 非法配置不影响基础奖励计算

### 5.3 不引入新概念
- 不引入道具系统
- 不引入"好感度"或"累计属性"
- 随机 bonus 仅作为签到奖励的"彩蛋"，不增加 spins_log 的 reason 类型

### 6.7 方案升级：彻底删除手动输入 botId，改为 self_id 自动发现（2026-08-11 追加）

**背景**：初始实现中，botId 由运营在管理端手动输入（纯数字校验 5~20 位），存入 `adapterConfigJson`，仅作展示用。代码审查时提出质疑：是否需要运营手动输入一个运行时已知的值？

**分析**：查阅 NapCat/OneBot 源码发现 `OneBotEvent.self_id = core.selfInfo.uin`（`packages/napcat-onebot/event/OneBotEvent.ts`），每个上报事件都携带 bot 登录 QQ 号。而当前平台从未读 `self_id`。Manual entry 是 Webhook 系统的反模式。

**初始折中方案**（保留手动输入，self_id 覆盖）：在 `targets.ts` 新增 `syncInboundBotIdentity`，入站时自动回填/覆盖 botId。运营仍可手动预填，但系统最终以 self_id 为准。

**最终方案**（彻底删除手动输入）：既然 self_id 是运行时权威来源，保留手动输入就是冗余的——运营可能填错号、忘记更新、或填一个根本不存在的 bot。去掉手动输入后：
- 运营零输入，botId 在第一条入站消息时自动出现
- 永远展示真正在干活的 bot，不可能 typo
- 管理端 UI 更简洁（删除输入框和 label/hint 文案，保留表格列只读展示）

**变更文件**：
1. `src/routes/admin-lottery-platform.ts`：`validateQQAdapterConfig` 移除 botId 校验；PATCH 路径合并已有 botId 避免编辑 baseUrl 时覆盖丢失
2. `frontend/src/views/admin/AdminQqAssistantView.vue`：删除 botId 输入框、`form.botId`、`fillFormFromTarget` 回填、`saveTarget` 写入
3. `frontend/src/i18n/zh-CN.ts` / `en.ts`：删除 `labelBotId`/`hintBotId`/`placeholderBotId`，保留 `colBotId`
4. `admin-lottery-platform.test.ts`：删除 3 条手动输入 botId 测试，新增 2 条（手动输入被忽略 + PATCH 保留 botId）
5. `platform-qq.test.ts`：4 条 self_id 自动回填测试保留不变
