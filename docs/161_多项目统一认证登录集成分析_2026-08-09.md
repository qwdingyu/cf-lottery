## 二、统一认证的架构选择

### 方案 A：使用 cf-auth（auth.eforge.xyz）作为统一 IdP ✅ 推荐

```
                   ┌─────────────────┐
                   │  auth.eforge.xyz │  ← 统一身份提供商（IdP）
                   │  (cf-auth)       │
                   └────────┬────────┘
                            │ OAuth 2.0 + PKCE
          ┌─────────────────┼─────────────────┐
          ▼                 ▼                 ▼
   ┌────────────┐   ┌────────────┐   ┌──────────────┐
   │ cf-lottery │   │  cf-shop   │   │ zhizhuan    │
   │ (已有)     │   │ (需新增)   │   │ (需新增)    │
   └────────────┘   └────────────┘   └──────────────┘
```

**核心原则**：
- 每个项目是独立的 OAuth **RP（Relying Party）**，各自在 cf-auth 注册 OAuth Client
- 每个项目有自己的本地用户/会话模型，与 cf-auth 数据库解耦
- 统一认证只解决"你是谁"，不解决"你能做什么"（RBAC 在各项目本地）
- 用户一次登录，各项目独立授权

### 方案 B：共享 cf-lottery 的用户数据库 ❌ 不推荐

各项目直接读 cf-lottery 的 users 表 → 深度耦合，违背"多租户、可白标"定位。

### 方案 C：转发到 cf-lottery 的 /admin/login 页面 ❌ 不推荐

cf-shop/zhizhuan 的 admin 登录跳转到 cf-lottery 的登录页 → 破坏品牌独立性，引入单点故障。

## 三、各项目实施路径

### 3.1 cf-shop：admin 侧新增 cf-auth OAuth

#### 后端改动

**新增路由**（参考 `src/routes/customer-auth.ts` 的 cf-auth 段，但走 admin 会话）：

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/admin/cf-auth/meta` | 返回 OAuth 元数据（无 secret） |
| POST | `/api/admin/cf-auth/exchange` | 交换 code → session JWT（用 ADMIN_TOKEN 派生签名） |

**exchange 流程**：
1. 验证 OAuth state cookie（CSRF 防护）
2. `exchangeAuthorizationCode` → `fetchCfAuthUserInfo` 获取用户信息
3. 用 `getAdminSessionJwtSecret(ADMIN_TOKEN)` 签发 session JWT（8h TTL）
4. 返回 session JWT 给前端

**为什么不需要新建用户表**：
- cf-shop 的 admin 模型是单 ADMIN_TOKEN，没有"admin 用户"概念
- cf-auth OAuth 认证通过后，**任何已认证的 cf-auth 用户都能成为 cf-shop 管理员**
- 这是最小改动方案，安全前提是 cf-auth 的注册门槛

**安全考量**：
- **管理员邮箱白名单**：`CF_AUTH_ADMIN_EMAILS` 环境变量控制，已实现（见第七章）
- 白名单是管理员统一认证的**唯一准入控制**，不允许未经白名单配置的登录

#### 前端改动

**`AdminLoginView.vue`**：添加"统一认证"按钮（参考 cf-lottery 的 AdminLoginView.vue）
- 顶部：`useCfAuthLogin` 检测 `cfAuthEnabled`
- 启用时显示"使用统一认证登录"按钮
- 点击后：`startCfAuthLogin('/admin')` 跳转 cf-auth
- 回调后：exchange → `setToken(sessionJWT)` → 进入后台

**新增 `AuthCallbackView.vue`**（或复用已有回调页）：
- 读取 URL 中的 `code`
- 调用 `/api/admin/cf-auth/exchange` 交换
- 存储 session JWT 到 localStorage
- 重定向到管理后台

### 3.2 zhizhuan web-saas：admin 侧新增 cf-auth OAuth

#### 现状分析

zhizhuan 的 ops 认证是**无状态令牌**模式，与 cf-lottery/cf-shop 的 admin 模式有本质不同：
- ops token 是一个静态服务端密码，由运维人员持有
- 没有"用户"概念，只有"操作者备注"字段用于审计

#### 建议方案

**短期（最小改动）**：在 ops 登录页增加 cf-auth 统一认证选项
- 新增 `/api/admin/auth/cf-auth/meta` 和 `/api/admin/auth/cf-auth/exchange` 端点
- exchange 成功后，将 cf-auth 用户信息映射为 ops session（签发 ops token 或 session cookie）
- 前端 ops 登录页增加"统一认证"按钮

**长期**：将 ops 认证迁移到基于 cf-auth 的用户模型，废弃静态 OPS_TOKEN

#### 特殊考虑

zhizhuan 的 ops 认证与 cf-shop 不同：
- cf-shop 的 ADMIN_TOKEN 已经是"管理员凭证"，加 cf-auth 只是增加一种登录方式
- zhizhuan 的 OPS_TOKEN 是"运维人员共享令牌"，没有用户身份，加 cf-auth 可以建立个别化身份

## 五、推荐优先级

1. **cf-shop admin 统一认证** → 改动最小，收益最大，有现成代码可复用
2. **zhizhuan web-saas ops 统一认证** → 需要先确认 ops 前端登录页位置

## 六、安全边界

- **OAuth state CSRF 防护**：每个项目独立维护 state cookie，互不干扰
- **client_secret 永不下发浏览器**：仅服务端持有
- **PKCE S256**：强制使用，防止授权码拦截
- **会话隔离**：cf-lottery 的 JWT 不能用于 cf-shop 的 API，反之亦然
- **回退能力**：各项目保留原有的登录方式，统一认证不可用时不影响运营

## 七、管理员邮箱白名单（2026-08-09 补充实施）

### 背景

初版实现中，任何通过 cf-auth 认证的用户都能成为管理员（cf-shop）或运营人员（zhizhuan web-saas），存在严重安全风险。

### 安全模型

引入 `CF_AUTH_ADMIN_EMAILS` 环境变量（逗号分隔的邮箱白名单）：

- **空白名单** = 拒绝所有统一认证登录（安全默认，防止误部署）
- **白名单已配置**：仅允许白名单中的已验证邮箱登录
- `email_verified === false` 的 IdP 用户被拒绝（即使邮箱在白名单中）
- 邮箱比较**忽略大小写**

### 实施位置

| 项目 | 文件 | 检查点 |
|------|------|--------|
| cf-shop | `src/routes/admin.ts` | POST `/api/admin/cf-auth/exchange` |
| zhizhuan web-saas | `src/app/api/admin/auth/cf-auth/exchange/route.ts` | POST handler |

### 新增函数

- `readCfAuthAdminEmailWhitelist(env: { CF_AUTH_ADMIN_EMAILS?: string }): string[]`
  - 位于 cf-shop 的 `src/lib/cf-auth-oauth.ts` 和 zhizhuan 的 `src/server/auth/cf-auth-oauth.ts`
  - 纯函数，解析逗号分隔的邮箱列表，返回小写数组

### 测试覆盖

**cf-shop**（vitest）：
- 空白名单 → 403 + `ADMIN_EMAIL_WHITELIST_UNSET`
- 邮箱不在白名单 → 403 + `ADMIN_EMAIL_NOT_ALLOWED`
- email_verified = false → 403
- 正常白名单通过 → 200 + sessionToken
- 大小写不敏感匹配 → 200

**zhizhuan**（Node test runner）：
- `readCfAuthAdminEmailWhitelist` 纯函数 7 个 case（空、单邮箱、多邮箱、大小写、空格、空元素）

### 配置文件

白名单在新部署时必须配置，否则统一认证登录被拒绝：
- `.dev.vars.example`（cf-shop）：添加 `CF_AUTH_ADMIN_EMAILS` 注释
- `.env.example`（zhizhuan）：添加 `CF_AUTH_ADMIN_EMAILS` 注释
