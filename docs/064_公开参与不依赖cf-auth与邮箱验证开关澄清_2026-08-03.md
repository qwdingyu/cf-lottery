# 064 公开参与不依赖 cf-auth 与邮箱验证开关澄清

> 日期：2026-08-03  
> 触发：外部审查建议「`enable_email_verification=false` 时公开参与依赖 cf-auth；应在 access-code 探测 IdP 不可用则自动回退发码」

---

## 一、审查项原文（摘要）

> 公开活动参与（`enable_email_verification=false`）依赖 cf-auth 完成身份认证。如果 cf-auth 不可用且邮件验证码关闭，用户无法参与。建议在 access-code 端点检测 cf-auth 可用性，不可用时自动回退到邮件验证码。

---

## 二、结论：**驳回**（前提错误；按建议改会制造安全/产品灾难）

| 断言 | 代码事实 |
|------|----------|
| false 时依赖 cf-auth | **否**。`public-lottery.ts` access-code 在 `emailBypass` 分支直接 `joinDraw(..., email, "email")`，**不读** `CF_AUTH_*`，**不要求** Bearer |
| 无 cf-auth 无法参与 | **否**。open 系 UI 主路径是「发验证码 / 免码直参」；cf-auth 按钮仅 `v-if="cfAuthEnabled"` 可选 |
| 应探测 IdP 再自动回退发码 | **不做**。关闭邮箱验证是运营**显式**选择的弱身份模式；自动「再发码」与开关语义矛盾，且探测外站增加延迟/故障面，可能在生产误开弱身份时掩盖问题 |

### 真实身份矩阵（公开参与）

| `participation_mode` | `enable_email_verification` | 身份怎么立 |
|----------------------|----------------------------|------------|
| open / roster / password / invite | **true**（默认） | access-code 发 OTP → verify-join；**可选** Bearer 业务 JWT（email 一致）跳过 OTP |
| open / roster / password / invite | **false** | access-code **直接 join**（仅邮箱字符串；弱身份） |
| registered | 任意 | **必须** 业务 JWT（用户名密码登录或 cf-auth exchange 后的 token）；与邮箱开关无关 |

cf-auth 角色：

- **可选加速**：open 系已 OAuth 的用户可免 OTP（省 Resend）。
- **registered / 管理端** 的外部 IdP 来源之一（另有邮箱密码）。
- **不是** `enable_email_verification=false` 的前提条件。

---

## 三、若按错误建议实现会怎样

1. **语义崩坏**：配置写「关闭邮箱验证」，运行时又静默发码 → 运维无法推理。  
2. **安全假象**：生产误关验证时，系统若「探测 cf-auth 失败就发码」可能掩盖配置错误；若探测「成功」却仍走弱身份，审查目标也达不到。  
3. **性能/稳定性**：每次 access-code 打 IdP health → 公开热路径耦合外站。  
4. **registered 仍无法靠发码救**：该模式禁止 email OTP 绕过（防 open→registered 残留码攻击）。

---

## 四、正确运维建议

1. **生产**：`enable_email_verification=true`（默认）。  
2. **仅** Resend/邮件不可用的**测试**环境可临时 `false`，接受「谁填邮箱谁参与」。  
3. 需要强身份时用 `participation_mode=registered` 或开启邮箱 OTP，而不是「关 OTP + 依赖 cf-auth」。  
4. cf-auth 不可用时：open+OTP 仍可用；registered 改用用户名密码登录。

---
