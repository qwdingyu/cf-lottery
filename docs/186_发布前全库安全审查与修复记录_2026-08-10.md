## 1. 事务与锁基础设施（所有并发结论的判定前提）

- `withDbTransaction`（`src/db/client.ts`）委托 `@usethink/cf-core`，实现为 **BUSY 时整体重跑事务回调**（重试上限 5 次 + 50ms 指数退避）。
- drizzle libsql 默认 `client.transaction()` → `BEGIN IMMEDIATE`（写锁在 BEGIN 处获取）。
- 差异：**VPS 本地 SQLite（file:）** 的 BEGIN 是 eager，BUSY 在 `transaction()` 调用即失败、回调未执行，重试干净；**Turso 远程（hrana）** 的 BEGIN 是 lazy，BUSY 在第一条语句处抛错、此时 JS 闭包可能已前移（触发 F2）。

## 2. 并发安全关键点结论（用户最关心的"超发/漏发/重复中奖"）

| 关键点 | 结论 | 依据 |
|---|---|---|
| 防 double-join | ✅ 安全 | UNIQUE(tenant,draw,identity_type,identity_value) + 条件 INSERT + 冲突 catch |
| 防 double-win（delayed） | ✅ 安全 | CAS 夺取 status open→drawing + winners/drawn 同事务 |
| 防 double-win（instant） | ✅ 安全 | 扣次 CAS + awardCount CAS + 卡密子查询原子锁 + 幂等键唯一 |
| 奖品库存/名额扣减 | ✅ 安全 | 条件原子 UPDATE + rowsAffected 检查 |
| 卡密跨租户/重复发放 | ✅ 安全 | 所有取码均带 tenantId + status='available' CAS |
| spin 剩余次数负数/虚高 | ✅ 已修复 | CAS `WHERE spins_left>=1`；响应值事务内重读 |
| 邮件/webhook 失败回滚 | ✅ 不回滚 | 全部 fire-and-forget + catch |
| 定时清理误删活跃 | ✅ 安全 | 按 createdAt 过滤，与活跃记录无交集 |

## 5. admin 后台运营与参数闭环审查（子代理 C）

### 系统配置参数盘点（关键问题）
- **后端 42 项配置中，5 个 group 共 15 项在前端任何分区均不可见**（邮件通知/抽奖设置/营销邮件/秒杀/支付），其中 `email_from_name` 等"定义了但改了不生效"（后端读 env 不读 system_config）。
- **死配置**：`platform_name`、`demo_public_slug`、`enable_pricing_page`、`r2_public_url`、`r2_prize_image_bucket` 后端 0 读取、前端 0 使用。
- **改不起效**：`email_from_name`（后端读 env）、`marketing_*` 系列（前端不可见）。

### 参数闭环断点（3 条）
1. **链路 1 `rate_limit_join_per_minute`**：后端生效但前端不可见 → "生效但改不了"。
2. **链路 2 `community_feature_enabled`**：可改、可强制、可查，但无可回滚历史（仅 PUT 审计，无变更历史表）。
3. **链路 3 签到 `randomBonus`**：配置→执行闭环完整，但"本次改了什么"不可追溯。

### L2/L3 能力缺口（对照完整子代理报告精确修正）
- **L2 租户管理员**（已具备：活动生命周期含 **copy**`POST /draws/:id/copy`、运营数据导出、奖品/卡密、黑名单、成员、集成、社群绑定、审计查看）。真实缺口：
  1. **活动级参与限流不存在**：只有平台全局 `rate_limit_join_per_minute`（且前端不可见），租户不能对单个活动设"每人参与次数/频率/IP 策略"。
  2. **并发人数控制不存在**：全仓无 `maxConcurrent` 概念，只有容量上限 `maxParticipants`，无法控制"同时在线/瞬时并发"。
  3. **转盘概率无可视化**：只有权重输入框，无"各奖项中奖概率占比"展示/换算面板。
  4. **数据导出无统一入口**：后端有多个导出端点但前端按钮散落，无"参与者/中奖/汇总"一键打包导出。
  5. **活动级"开奖前锁定"缺失**：无活动级"开奖前 N 分钟锁定参与"配置（全局提醒窗口写死 ±5 分钟）。
- **L3 平台运营者**：
  1. **无全局公告/站内信能力**：无法向租户/用户广播。
  2. **无跨租户只读视图**：只能 impersonate 模拟登录查看租户活动，无"以平台身份直接查看某租户活动/中奖名单"的只读路由。
  3. **身份角色隔离仍未落地**：users 表无 role 字段，路由按 tenantId 硬过滤（详见既有 docs/178 记忆），且 `platform.ts:711` 数据清理审计 `actorRole` 硬编码为 operator。
  4. **配置无版本/回滚**：审计只记 key 不记新旧值，无法回答"上次是谁改的、改成多少"。
  5. **前端 stub 与后端脱节**：`sendTestEmail`、数据清理按钮在配置页为"点了没反应"的 stub，真实实现是独立页面。

## 7. 踩坑记录（供参考）

- **Telegram/NapCat 出站调用必须设置 fetch 超时**，否则 webhook 入站处理会被第三方 API 不可达无限挂起（Workers 触发 CPU 超时、VPS 占用连接）。测试环境应 mock 全局 fetch，不能依赖真实网络。
- **HTTP 状态码是前端与后端的发布契约**：改变（如 409→400）会破坏前端分支判断，必须同步排查前端依赖。
- **事务 BUSY 重试会整体重跑回调**，回调内引用的外部闭包变量（计数器/Set）不会回滚，必须声明在回调内部，否则产生静默漏发。
- **定时清理的保留窗口必须覆盖所有使用该表的业务窗口**，否则短窗口清理会击穿长窗口配额（F1）。
