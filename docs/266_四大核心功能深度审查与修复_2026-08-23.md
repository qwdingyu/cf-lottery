## 二、已修复问题

### 2.1 P0 — 排行榜 tie-break 规则不一致

**问题**：公开榜和奖励发放使用不同的 tie-break 规则，导致用户看到的排名与实际获得的奖励不一致。

| 场景 | tie-break 规则 | 位置 |
|------|---------------|------|
| 公开榜（`buildViralLeaderboardRanking`） | entryId 字典序 | `viral-weight.ts:233` |
| 奖励发放（`grantLeaderboardRewards`） | firstSharedAt 先到先得 | `leaderboard-rewards.ts:160` |

**影响**：同票时用户在排行榜看到自己排第 3，但奖励发放按 firstSharedAt 计算实际排第 4，少拿一份奖励。反之亦然。

**修复**：
1. 在 `viral-weight.ts` 提取 `compareViralLeaderboard` 共用比较函数
2. 统一规则：邀请人数降序 → 同票 firstSharedAt 升序（先到先得）→ 兜底 entryId 字典序
3. `buildViralLeaderboardRanking` 和 `grantLeaderboardRewards` 均调用同一函数
4. 新增 4 个单元测试覆盖边界场景

**修改文件**：
- `src/services/lottery/viral-weight.ts`：新增 `compareViralLeaderboard` 函数
- `src/services/lottery/leaderboard-rewards.ts`：import + 排序调用替换
- `src/services/lottery/viral-weight.test.ts`：新增 `describe("compareViralLeaderboard tie-break 统一")`

### 2.2 P1 — SHARE_RECORDS_HARD_LIMIT 截断聚合

**问题**：`aggregateSharerData` 用 `LIMIT 1000` 查询分享记录后，再用 JS `reduce` 计算 `SUM(joinedCount)`。若单个分享者有 ≥1000 条记录，SUM 仅覆盖前 1000 行，`totalJoined` 被低估。

**影响**：里程碑阶梯基于 `totalJoined` 计算（如「邀请 10 人得 5 次」），被低估会导致用户达到实际门槛但系统判定未达标，漏发奖励。

**修复**：
1. 用独立 SQL `SUM(joinedCount)` 精确计算 `totalJoined`，不受 LIMIT 影响
2. LIMIT 仅保护 row-level 查询（`grantedSet` + `recordIds`），防止内存膨胀
3. `totalJoined` 为 0 时提前返回 null（优化路径）

**修改文件**：
- `src/services/lottery/referral-rewards-engine.ts`：`aggregateSharerData` 函数重构

## 六、整体安全评估

### 6.1 并发安全

- **CAS 乐观锁**：关键路径全部使用 CAS（joinDraw、grantBonusSpin、leaderboardRewardedAt、spinsLeft）
- **事务原子性**：performDraw winners 写入与状态更新在同一事务
- **UNIQUE 约束兜底**：lotterySpins idempotency + lotteryWinners spinUnique + prizeCodes status CAS

### 6.2 幂等性

- 抽奖：idempotencyKey 三重保护（预读 + 事务内 + UNIQUE + catch 回查）
- 奖励发放：rewardMilestonesGranted JSON 数组标记
- 排行榜奖励：leaderboardRewardedAt CAS 标记
- 邀请归因：joinedCount 原子递增

### 6.3 随机公平性

- 所有随机路径使用 `crypto.getRandomValues()`（CSPRNG）
- performDraw 生成 seed + SHA-256 hash 可验证
- weightedSampleUnique 无放回抽样，高权重者不会占满名额
