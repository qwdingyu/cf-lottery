# docs/272：用户级邀请码——参与前即可分享

## 背景

活动页面的「复制分享链接」按钮默认不带 `?ref=`，用户必须先参与活动才能生成带归因的分享链接。这造成一个**鸡生蛋问题**：新用户看到活动想分享给朋友，但没有分享链接可用，裂变链路断裂。

## 问题分析

### 原有链路

1. 用户打开活动页 → 看到「复制分享链接」
2. 点击 → 复制的是裸链接（无 `?ref=`）
3. 只有用户**参与活动后**，系统才为该用户创建 shareRecord，生成带 `?ref={shareCode}` 的专属链接

### 痛点

- 分享按钮始终可见，但点击后复制的是无归因的裸链接
- 用户无法在参与前邀请好友——即使口头分享了活动，好友通过链接进入时也没有归因
- 活动冷启动阶段（无人参与时），裂变链路完全断裂

## 方案设计

### 核心思路：用户级固定邀请码

在用户**注册时**生成一个**8 位唯一邀请码**，绑定在 `users.invite_code` 字段上，所有活动通用。

### 为什么不用活动级/本地存储方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| **活动级邀请码** | 精确归因 | 需要用户先参与才能生成，鸡生蛋问题未解决 |
| **localStorage 生成** | 无需后端 | 每次访问生成新码，同一用户跨设备/浏览器码不一致；清理浏览器后丢失 |
| **用户级固定码** ✅ | 注册即有，所有活动通用 | 存量用户需要 migration 补码（NULL 兼容） |

### 邀请码设计

- **长度**：8 位
- **字符集**：`ABCDEFGHJKMNPQRSTUVWXYZ23456789`（34 字符，去掉 `0O1IL` 避免易混淆）
- **生成方式**：`crypto.getRandomValues`（Web Crypto API，密码学安全随机）
- **唯一性**：数据库 UNIQUE 约束（SQLite UNIQUE 对 NULL 不冲突，存量用户 NULL 不碰撞）
- **碰撞概率**：34^8 ≈ 1.78 × 10^12 种组合，实际使用量级远低于此

## 技术实现

### 数据库

```sql
-- migrations/0067_user_invite_code.sql
ALTER TABLE users ADD COLUMN invite_code TEXT;  -- 允许 NULL，存量用户兼容
CREATE UNIQUE INDEX idx_users_invite_code ON users(invite_code);
```

> ⚠️ SQLite UNIQUE 对 NULL 不冲突，多个 NULL 值共存不违反约束。

### 后端

#### 1. 用户注册时生成邀请码

```typescript
// src/routes/auth.ts
const inviteCode = generateUserInviteCode();
await db.insert(users).values({ id: userId, username, email, passwordHash, emailVerified: 0, inviteCode });
```

同步更新：`platform/user-provision.ts`（平台创建用户）、`idp-user-provision.ts`（IdP 用户同步）。

#### 2. `/api/auth/me` 返回 inviteCode

```typescript
// src/routes/auth.ts — /me 端点
inviteCode: user.inviteCode || "",  // NULL 安全降级为空字符串
```

#### 3. 分享链接降级链（`handleCopyPublicLink` 三级路径）

```
路径 1：已参与（有 entryId）→ POST /share 生成活动级专属链（精确归因）
路径 2：未参与但已登录 → GET /auth/me → ?ref={inviteCode}（用户级归因）
路径 3：未登录 → 裸活动链（无归因）
```

#### 4. 双阶段归因（解决"推荐人尚未加入"的鸡生蛋）

当推荐人 A 通过用户级邀请码分享活动，好友 B 经 `?ref={A.inviteCode}` 参与时：

**场景 1：A 已加入该活动**
→ `recordAttributedJoin` 查 `users.invite_code` → 找到 A → 查 A 的 entry → 创建 shareRecord + attributed_join 事件

**场景 2：A 尚未加入该活动**
→ 写入 `pending_user_attributed_join` 活动事件
→ 当 A 后来加入时，`joinDraw` 调用 `resolvePendingUserAttributions` → 解析 pending 事件 → 创建 shareRecord → 删除 pending 事件

### 前端

```typescript
// frontend/src/views/LotteryView.vue — handleCopyPublicLink
// 路径 2：未参与但已登录
if (registeredToken.value) {
  const meRes = await fetch(`${API_BASE}/auth/me`, {
    headers: { Authorization: `Bearer ${registeredToken.value}` },
  })
  const meData = await meRes.json()
  if (meData.ok && meData.user?.inviteCode) {
    const shareUrl = `${origin}/lottery/${slug}?ref=${meData.user.inviteCode}`
    await writeClipboardText(shareUrl)
    return
  }
}
```

## 关键决策记录

### 为什么 invite_code 默认 NULL 而非空字符串？

SQLite UNIQUE 约束对空字符串 `''` 会冲突（多个用户都是 `''`），但对 NULL 不冲突。新用户注册时由代码生成唯一码写入，存量用户的 NULL 不违反约束。

### shareCode 合成格式

`resolvePendingUserAttributions` 创建 shareRecord 时使用合成 shareCode：`uc_{userId8}_{drawId6}_{shareId6}`，避免与活动级 share 码的 UNIQUE 约束冲突。

### 自邀请检测

`resolvePendingUserAttributions` 会检测推荐人 identity 与被邀请人 identity 是否一致（支持 email/user_id 跨类型比较），自邀请不计入 joined_count。
