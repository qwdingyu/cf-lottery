# RBAC 大改发布前审查与修正记录

> 文档编号：028
> 日期：2026-08-01
> 背景：代码已按 024、026 文档实施三层用户体系和 RBAC-lite。本次审查目标是确认是否偏离核心功能、是否破坏抽奖/接龙/导流等核心链路，并修复发布前会造成灾难的隐患。

---

## 一、最终审查结论

当前方向没有偏离核心定位：

```text
cf-lottery = 多租户、可白标、可嵌入的活动引擎平台
抽奖 = 第一种玩法
核心能力 = 规则驱动的参与、结果分配、导流和运营闭环
```

本次实施中，`/api/admin/*` 和 `/api/platform/*` 的边界总体符合 026 基线：

- `/api/admin/*` 保持租户后台语义，必须有 `tenantId`，并通过 `tenant_members` 校验。
- `/api/platform/*` 承载平台后台语义，必须通过 `platform_members` 校验。
- 系统配置和平台额度码已迁出错误的 admin 命名空间。
- 公开参与链路没有引入平台权限查询，符合 Cloudflare Workers Free + Turso Free 的成本约束。

但本次审查发现并修复了 5 个发布前高风险点。

---

## 二、已修复的高风险点

### 1. 普通性能索引误写成唯一索引

位置：

- `src/db/schema.ts`
- `migrations/0017_fix_non_unique_runtime_indexes.sql`

问题：

`prize_codes`、`lottery_draws` 的查询索引在 Drizzle schema 中被写成 `uniqueIndex`。这会在后续生成迁移时把普通性能索引变成唯一约束，导致：

- 同一奖品同一状态下无法批量导入多条码。
- 同一租户同一状态下无法快速创建多个活动。
- 同一开奖时间无法安排多个活动。

修正：

- 改回普通 `index()`。
- 新增 `0017_fix_non_unique_runtime_indexes.sql`，显式 drop 错误索引并重建普通索引。

### 2. 邮箱验证码唯一约束会阻塞二次发码

位置：

- `src/db/schema.ts`
- `migrations/0017_fix_non_unique_runtime_indexes.sql`
- `src/services/auth-and-public.test.ts`

问题：

旧索引 `UNIQUE(email, draw_id, used)` 只允许同一邮箱同一活动存在一条 `used=1` 历史验证码。第二次发验证码时，系统会先把旧未用验证码改成 `used=1`，如果历史中已有 `used=1`，就会触发唯一冲突。

修正：

只保留“同一邮箱同一活动最多一条未使用验证码”的部分唯一索引：

```sql
CREATE UNIQUE INDEX IF NOT EXISTS idx_email_code_active
  ON email_access_codes(email, draw_id)
  WHERE used = 0;
```

已补测试：同一邮箱重复获取验证码时，保留两条历史记录，但只有一条 `used=0`。

### 3. 租户成员管理路由重复定义

位置：

- `src/routes/admin-lottery.ts`
- `src/routes/platform-rbac.test.ts`

问题：

`/api/admin/members` 出现两套实现。虽然 Hono 通常命中先注册的路由，但重复定义会造成维护者误改死代码，未来也容易出现权限逻辑分叉。

修正：

- 删除重复成员管理路由。
- 只保留一套带配额、自我删除保护、RBAC-lite 门禁的实现。
- 补 `PATCH /members/:userId` 的明确实现。
- 已补回归测试验证：租户 `owner` 在套餐额度允许时，仍可通过 `POST /api/admin/members` 把已注册用户添加为团队成员。

### 4. 租户角色可写入任意字符串

位置：

- `src/routes/admin-lottery.ts`
- `src/routes/platform-rbac.test.ts`

问题：

成员添加和角色修改曾允许写入任意 `role`，例如 `operator`、`member`。这会破坏 026 基线中冻结的 `owner/admin/viewer` 模型，也会让用户被写成无法通过 `requireTenantMember()` 的角色。

修正：

- 新增 `TENANT_MEMBER_ROLES = owner/admin/viewer`。
- 添加和修改成员角色时统一校验。
- 禁止 owner 修改自己的角色，避免自我降权后租户后台无人可管。

### 5. 兑换码兑换不是事务闭环

位置：

- `src/routes/admin-lottery.ts`

问题：

兑换码原本先 CAS 标记使用，再更新租户额度，再插入兑换记录。任一后续写入失败，都会留下“码已使用但额度未到账”的半成功状态。

修正：

- 使用 `withDbTransaction()` 包住：查码、CAS 递增、租户加额、兑换记录。
- 业务错误用 `RedeemError` 返回明确状态码。
- 事务内不做邮件、HTTP 等外部 I/O，符合 Workers 免费层短事务原则。

说明：

- 租户侧兑换入口没有删除，仍为 `POST /api/admin/redemption-codes/redeem`。
- 平台侧发码、列表、统计不属于租户后台，已按 026 基线保留在 `/api/platform/redemption-codes`。

### 6. 导出 CSV 上限检查参数传反

位置：

- `src/routes/admin-lottery.ts`

问题：

导出 CSV 时新增了 `MAX_EXPORT_ROWS = 10000` 限制，但调用 `getDrawEntriesCount(db, drawId, tenantId)` 时曾出现 `tenantId/drawId` 传反的风险。两个参数都是 string，TypeScript 无法发现。

修正：

- 已改为正确顺序：`getDrawEntriesCount(db, drawId, tenantId)`。
- 该接口仍保持最大 10,000 行，避免在 Workers Free 的 10ms CPU / 128MB 内存约束下生成过大 CSV。

## 三、并行进入的持久化限流代码审查

本轮审查期间，工作区出现了 `src/lib/rate-limit.ts` 和 `auth.ts` 中的数据库级限流接入。该方向是合理的，因为内存 `Map` 在多 Worker isolate / 多 PoP 下不是全局一致。

但必须补齐闭环：

- 已新增 `migrations/0018_rate_limit_log.sql`，避免部署后 `no such table: rate_limit_log`。
- 已在 `runScheduledMaintenance()` 中调用 `cleanExpiredRateLimits()`，避免日志表只写不清。
- 当前只接入登录/注册低频接口，符合免费层资源约束。

明确限制：

- 不应直接把所有公开事件上报、页面浏览、参与开始等热路径全部写入 `rate_limit_log`。
- 如后续需要公开热路径持久化限流，必须先按活动规模估算 Turso rows written，并优先按 `ipHash + slug + minute bucket` 做低基数聚合。

## 四、Cloudflare + Turso 免费层约束复核

截至 2026-08-01 官方文档核对：

- Cloudflare Workers Free：100,000 requests/day、10ms CPU/request、128MB memory、50 subrequests/request。
- Cloudflare 文档明确：等待网络请求、KV 读取或数据库查询不计入 Worker CPU time，但请求仍会受整体运行、连接和资源限制影响。
- Turso rows read 的口径更接近“row scan”，`COUNT`、聚合、缺索引扫描会消耗 rows read；rows written 包括 insert/update。

因此当前策略是：

- 后台权限查询可以接受：后台低频，每次多一次主键/组合索引查表，换取成员移除后立即失效。
- 公开参与热路径不能挂平台/RBAC 查询。
- 统计 `COUNT` 不是 Worker CPU 主要风险，但会影响 Turso rows read 和响应延迟。
- 公开事件与限流写入必须克制，避免 rows written 被滥写打爆。

参考：

- Cloudflare Workers Limits: https://developers.cloudflare.com/workers/platform/limits/
- Turso Usage & Billing: https://docs.turso.tech/help/usage-and-billing

## 六、剩余风险与发布前建议

### 1. 平台写操作审计仍未完整闭环

`/api/platform/system-config` 和 `/api/platform/redemption-codes/batch` 已有平台权限门禁，但平台级审计日志仍未单独落表。当前不建议用 `tenant_id='__platform__'` 污染租户审计表。

建议：

- 后续新增 `platform_audit_logs`，只记录平台写操作。
- 字段保持轻量：`id, actor_user_id, action, target_type, target_id, metadata_json, created_at`。

### 2. 首个 platform_owner 初始化入口仍需确认

目前 `platform_members` 有表和权限中间件，但上线前必须有可控的首个平台 owner 创建方式。

建议：

- 开发/首次部署用受控 SQL 或一次性运维命令写入。
- 不建议开放公开注册成为 platform_owner。

### 3. 公开事件上报仍依赖内存限流

这符合当前免费层成本约束，但不具备全局强一致防刷能力。上线早期可以接受，前提是：

- Cloudflare WAF / Turnstile / 简单 IP 规则作为外层保护。
- 活动事件接口保留白名单、字段长度限制和低价值事件采样策略。

### 4. 大规模 CSV 导出仍是后台低频能力

当前限制 10,000 行是正确方向。未来如果租户活动规模超过这个级别，应改为分页导出或异步任务，不要在单个 Worker 请求里生成大文件。

---

## 七、本次结论

这次大改的核心方向成立：三层用户体系、RBAC-lite、平台/租户路由分离没有偏离活动引擎 SaaS 的核心功能。

但发布前必须保留本次修正：

1. 普通索引不能写成唯一索引。
2. 邮箱验证码只能唯一约束未使用记录。
3. 租户成员角色必须冻结为 `owner/admin/viewer`。
4. 成员路由必须只有一套实现。
5. 兑换码兑换必须事务闭环。
6. 新增表必须有 migration，并有清理策略。

以上修正属于基线修正，不是无止境兼容，也不是打补丁式退让。
