# 167 嫁接层顶层设计：平台抽象与 Webhook 统一体系

> 日期：2026-08-09（修正版 2026-08-09）
> 定位：在 cf-lottery 中构建租户内置的 QQ 群增长助手与平台适配层，
>       把 /签到 /抽奖 /分享 /排行榜 /我的奖品 做成 SaaS 开箱即用能力
> 范围：**仅限 cf-lottery**，不涉及 cf-shop
> 方法：基于 cf-lottery 现有 webhook 代码（integration.ts）扩展，
>       吸收 zhenxun_bot 的渲染库和调度器，参考 qqbot 的意图路由设计
> 修正说明：基于 2026-08-09 对 cf-lottery 关键代码路径的代码级审查，更正了架构定位、模板引擎选择、平台适配模式；
>       二次修正：明确 QQ 群命令是每个租户的内置功能，不要求租户逐条创建命令

## 0. 核心结论

**cf-lottery 的 webhook 系统已经完成了 60% 以上的工作**——事件定义、入队、签名、投递、重试、审计、入站事件处理全部完整实现。
但面向 SaaS 用户，这一层不能暴露成“请租户自己配置命令/自己理解 webhook”的开发者工具。
剩下的核心工作不是做一个通用 Bot 平台，而是把 QQ 群增长场景产品化：
**租户只需要绑定 QQ 群、选择活动、打开内置功能开关，系统自动提供 /签到 /抽奖 /分享 /排行榜 /我的奖品。**

**不需要推翻 cf-lottery 的 webhook 系统，也不需要在外部独立部署“业务嫁接服务”。QQ 适配层是 cf-lottery 内部的路由与服务扩展，共用同一个 SaaS 后端进程；但 QQ 登录态、NapCat/OneBot 实例不默认集中部署在我们的 VPS。P0 默认是租户自托管 QQ 适配器，平台只提供回调 URL、每群密钥、二维码/一键配置向导；平台托管只作为白名单/代运营模式。接口名保持 `qq-adapter`，避免把业务绑定死在 NapCat。**

### 0.1 SaaS 用户视角的产品原则

| 原则 | 解释 | 对开发的约束 |
| --- | --- | --- |
| 内置优先 | `/签到` `/抽奖` `/分享` `/排行榜` `/我的奖品` 是系统内置能力 | 不允许设计成“租户逐条创建命令映射表” |
| 配置最少 | 租户只配置“哪个群绑定哪个活动、启用哪些内置功能” | 管理端必须有默认值，一键启用 |
| 租户级连接 | QQ 连接信息属于某个租户/群绑定 | `QQ_ADAPTER_*`、`QQ_INBOUND_TOKEN` 不放全局环境变量 |
| 活动驱动 | 命令围绕当前绑定活动执行，不让租户理解 API 路径 | 通过 `platformTargets` 解析 active draw |
| 数据入库 | 群内行为必须进入 cf-lottery 的参与、分享、开奖、转化、审计模型 | 禁止使用 qqbot 的 JSON 文件作为生产状态 |
| 身份可审计 | QQ 用户在活动内成为 `identityType=qq` 的参与者 | 身份解析必须在平台命令服务层完成，不能伪造公开 API 的 email/OTP 流程 |
| 不暴露复杂性 | Webhook、NapCat、OneBot 是内部实现 | SaaS 页面展示“QQ 群助手”，不是“Webhook 嫁接层” |

### 1.2 真正缺失的（基于代码审查修正）

| 缺口 | 当前状态 | 需要做什么 |
| --- | --- | --- |
| **平台消息模板** | 投递的是原始 JSON payload | 每个事件类型 + 每个平台专用的消息模板（文本+卡片） |
| **平台适配器连接器** | Webhook 只能投递到 HTTP URL | 建立 `sendMessage(platform, targetId, message)` 函数；P0 桥接 QQ/NapCat，Telegram 后续扩展 |
| **内置命令路由** | 入站事件已实现（webhook 回调），但无 `/签到` `/抽奖` 等 QQ 命令处理 | 解析 QQ 群消息 → 匹配系统内置命令 → 按租户群绑定找到活动 → 调用平台命令服务 |
| **平台身份解析** | 公开 API 主要按 email/JWT/OTP 处理；QQ 群天然使用 QQ 号 | 在平台命令服务层使用 `identityType=qq`、`identityValue=QQ号` 创建/查询活动参与者 |
| **租户-群-活动绑定** | 无平台侧配置 | 新增独立绑定表，不扩展 `webhookConfigs` 承担平台目标 |
| **平台投递审计** | `webhookDeliveries` 只描述 HTTP URL 投递 | 新增平台消息投递记录，记录 targetId/messageId/状态/重试 |
| **SaaS 默认功能开关** | 无租户级默认启用体验 | 内置功能默认提供，租户只选择启用/禁用和绑定活动 |

| 原文档断言 | 实际代码 | 修正 |

## 3. 核心接口设计

### 3.1 平台抽象接口

> 修正要点：cf-lottery 全部使用函数式模式（integration.ts 无 class 定义）。平台适配器也用函数式，
> 不引入 class。模板语法沿用 `{{variable}}` 变量替换，不引入 Handlebars；QQ 纯文本输出策略必须单独确认。

```typescript
// ============================================================
// 平台抽象接口（函数式，对齐 cf-lottery 现有 integration.ts 风格）
// ============================================================

/** 平台标识（早期只实现 qq，telegram 为扩展目标） */
type PlatformType = "qq" | "telegram";

/** 平台目标：一个平台上的具体接收目标 */
interface PlatformTarget {
  id: string;
  tenantId: string;
  platform: PlatformType;
  targetId: string;      // QQ 群号 / Telegram Chat ID
  targetName: string;
  activeDrawId: string;  // 当前绑定活动；管理端可切换
  activePublicSlug: string;
  assistantEnabled: boolean;
  adapterDeploymentMode: "tenant_hosted" | "managed";
  adapterProvider: "napcat" | "onebot";
  adapterConfigJson: string;     // P0 只保存 baseUrl；token 等敏感字段等租户级加密闭环完成后再接入
  inboundSecretHash: string;     // 每个群绑定独立生成，只存哈希；编辑时留空不变，填写新密钥则覆盖哈希
  builtinCommands: BuiltinCommandConfig;
  createdAt: string;
  updatedAt: string;
}

/** 系统内置命令开关。租户只能启停和改文案，不能改变命令语义。 */
interface BuiltinCommandConfig {
  checkinEnabled: boolean;     // /签到
  spinEnabled: boolean;        // /抽奖
  shareEnabled: boolean;       // /分享
  leaderboardEnabled: boolean; // /排行榜
  myPrizeEnabled: boolean;     // /我的奖品
  helpEnabled: boolean;        // /帮助
  dailyCheckinPolicy?: {
    /**
     * 每日签到奖励。
     * P0 建议等价为“参与/补充 activityEvents”，若要增加抽奖次数，必须走正式 spins quota 逻辑，
     * 不得只在平台层维护独立积分。
     */
    grantSpinCount?: number;
  };
  replyOverrides?: Record<string, string>;
}

/** 平台消息：平台适配器的输出 */
interface PlatformMessage {
  platform: PlatformType;
  targetId: string;
  type: "text" | "image" | "card";
  text?: string;
  imageUrl?: string;
  cardData?: Record<string, unknown>;
  buttons?: Array<{ text: string; action: string; url?: string }>;
}

/** 平台适配器（函数式，非 class） */
type PlatformAdapter = {
  readonly platform: PlatformType;
  send(message: PlatformMessage): Promise<{ messageId: string }>;
  sendBatch(messages: PlatformMessage[]): Promise<Array<{ messageId: string }>>;
};

/**
 * 平台适配器注册表：platform → adapter
 * 通过此表路由，新增平台只需实现 send/sendBatch 并在注册表登记。
 */
const platformAdapters: Record<PlatformType, PlatformAdapter> = {
  qq: qqAdapter,         // → NapCatQQ HTTP API
  telegram: telegramAdapter, // → Telegram Bot API（P3 扩展）
};

/** 入站事件：来自平台的用户操作（NapCatQQ 消息事件 → 统一结构） */
interface InboundEvent {
  platform: PlatformType;
  sourceId: string;         // QQ 群号 / Telegram Chat ID
  userId: string;           // 用户在该平台的 ID
  eventType: "message" | "command" | "callback" | "member_join" | "member_leave";
  text?: string;
  command?: string;         // 命令名（如 /checkin）
  args?: string[];          // 命令参数
  raw?: unknown;            // 原始数据
}

/** 租户内置命令：固定集合，不从数据库动态新增任意命令。 */
type BuiltinPlatformCommand =
  | "checkin"
  | "spin"
  | "share"
  | "leaderboard"
  | "my_prize"
  | "help";

/** 统一事件（cf-lottery webhook 出站 payload 的结构） */
interface UnifiedEvent {
  id: string;
  type: string;
  createdAt: string;
  tenantId: string;
  data: Record<string, unknown>;
}

/** 事件 → 平台目标映射。注意：这是平台投递配置，不扩展 webhookConfigs。 */
interface PlatformEventRoute {
  eventType: string;           // cf-lottery 事件类型
  targetId: string;            // platform_targets.id
  templateId?: string;
  active: boolean;
}

/** 平台投递审计。HTTP webhook 仍使用 webhookDeliveries，平台消息使用独立表。 */
interface PlatformDelivery {
  id: string;
  tenantId: string;
  platformTargetId: string;
  platform: PlatformType;
  targetId: string;            // QQ 群号
  eventId?: string;
  eventType?: string;
  command?: BuiltinPlatformCommand;
  payloadJson: string;
  status: "pending" | "sent" | "failed";
  attemptCount: number;
  providerMessageId?: string;
  lastError?: string;
  nextRetryAt?: string;
  createdAt: string;
  updatedAt: string;
}

/** 消息模板（用 interpolate，不用 Handlebars） */
interface MessageTemplate {
  id: string;
  platform: PlatformType;
  eventType: string;
  template: string;            // interpolate 模板（{{var}}）
  messageType: "text" | "card";
  isDefault: boolean;
}
```

### 3.2 数据模型边界（必须遵守）

| 表/模型 | 用途 | 设计约束 |
| --- | --- | --- |
| `webhookConfigs` / `webhookDeliveries` | 外部 HTTP webhook | 保持 HTTP URL 语义，不新增 QQ 群字段 |
| `platformTargets`（新增） | 租户绑定的平台目标，如 QQ 群 | 保存 `tenantId/platform/targetId/activeDrawId/builtinCommands` |
| `platformDeliveries`（新增） | 平台消息投递审计 | 保存发送状态、NapCat/OneBot 返回 messageId、重试信息 |
| `lotteryEntries` | 活动参与者 | QQ 群参与使用 `identityType=qq`、`identityValue=QQ号` |
| `shareRecords` | 分享码与邀请归因 | `/分享` 必须复用现有 share 逻辑，不新建平台侧分享表 |
| `activityEvents` | 增长漏斗与审计 | 群内命令必须记录 source=`qq_group`、medium=`platform_command` |

**禁止项**：
- 禁止让租户手动创建 `/签到`、`/抽奖`、`/分享` 等命令映射。
- 禁止把 QQ 群号塞进 `webhookConfigs.url` 或用伪 URL 表示平台目标。
- 禁止生产使用 qqbot 的 `scores.json` / `riddle_state.json` 这类文件状态。
- 禁止平台命令直接伪造公开 API 的 email/OTP 请求；平台命令应进服务层，复用业务函数和数据库约束。

## 4. 从 zhenxun_bot 和 qqbot 吸收什么

> 修正要点：聚焦嫁接层直接需要的组件。AI 层（LLM 适配器/MCP/RAG）是 P2-P3，不在本轮 MVP 范围内。
> 因为 cf-lottery 的核心是抽奖活动引擎，AI 对话能力是锦上添花，不是必需。

### 4.1 从 qqbot 吸收（MIT 许可证，安全）

| 组件 | 吸收方式 | 价值 | 优先级 |
| --- | --- | --- | --- |
| **意图路由**（intent_router.py） | 只参考匹配策略，TypeScript 化固定命令识别 | 命令识别快速稳定；P0 只识别内置命令，不做任意意图平台 | P0 |
| **内容过滤器**（content_filter.py） | 参考设计 | 过滤敏感内容，合规需要 | P1 |
| **权限管理**（permission.py） | 参考设计 | 群管理员/黑名单/权限分级 | P0 |
| **游戏签到/排行榜原型**（game_handler.py） | 参考玩法，不迁移存储 | 证明群内轻互动有效；生产状态必须进入 cf-lottery 数据库 | P0 |

### 5.3 平台身份规则

QQ群内置命令必须使用平台身份参与活动：

```text
identityType = "qq"
identityValue = String(user_id)
displayName = QQ 昵称（可选，来自 NapCat get_stranger_info / 群成员资料）
source = "qq_group"
medium = "platform_command"
campaign = platformTargets.id 或绑定活动的运营活动名
```

这与公开网页的 email/JWT/OTP 身份流是两条入口。公开 API 当前主要通过 `email`、业务 JWT、验证码解析身份；
因此平台命令不应通过构造 `{ identityType: "qq", identityValue }` 直接调用公开 HTTP 路由来“碰运气”。
正确做法是在 `PlatformCommandService` 内部复用现有服务函数，确保多租户隔离、幂等、限流、开奖和卡密发放仍由 cf-lottery 的正式业务层负责。

## 6. 消息模板系统

> 修正要点：cf-lottery 已使用 `interpolate()`（来自 `@usethink/cf-core/features/email`），
> 轻量 `{{variable}}` 替换，无代码执行风险。不需要引入 Handlebars。
> 注意：`interpolate()` 面向邮件模板时带 HTML 安全语义；QQ 纯文本投递前必须确认不会把 `&`、`<`、`>` 等显示成 HTML 实体。
> 若实际输出会转义成实体，应新增 `renderPlatformTextTemplate()`，只复用变量替换规则，不复用 HTML 输出策略。

### 6.1 模板格式

使用 `interpolate(template, data)`，模板语法为 `{{variableName}}`：
- 只支持顶层变量替换，不支持 `{{#each}}` 循环
- 循环逻辑在代码中处理（`data.map().join('\n')` 后传入模板）
- QQ 文本发送前必须做长度、换行和敏感字段处理；不要把卡密等敏感字段直接塞进群消息模板

### 6.2 模板示例

## 7. 平台适配器实现指南

### 7.1 QQ 适配器（基于 NapCatQQ，函数式）

> 修正要点：cf-lottery 是函数式代码库，适配器也用函数创建，不引入 class。
> Telegram 适配器是 P3 扩展，此处仅给出接口占位。

```typescript
// src/services/platform/qq-adapter.ts
import type { PlatformMessage } from "./types";

/** NapCatQQ HTTP API 客户端（轻量封装） */
export function createNapCatClient(env: { napcatUrl: string; napcatToken?: string }) {
  async function request(path: string, body: Record<string, unknown>) {
    const res = await fetch(`${env.napcatUrl}${path}`, {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        ...(env.napcatToken ? { Authorization: `Bearer ${env.napcatToken}` } : {}),
      },
      body: JSON.stringify(body),
    });
    if (!res.ok) throw new Error(`NapCatQQ ${path} failed: ${res.status}`);
    return res.json();
  }
  return {
    sendGroupMessage(groupId: string, text: string) {
      return request("/send_group_msg", { group_id: groupId, message: text });
    },
    sendGroupImage(groupId: string, url: string) {
      return request("/send_group_msg", { group_id: groupId, message: `[CQ:image,file=${url}]` });
    },
    // 群成员列表（用于 /roster 白名单校验）
    getGroupMemberList(groupId: string) {
      return request("/get_group_member_list", { group_id: groupId });
    },
  };
}

// src/services/platform/adapters.ts
import type { PlatformAdapter } from "./types";
import { createNapCatClient } from "./qq-adapter";

/** 创建 QQ 适配器 */
export function createQQAdapter(env: { napcatUrl: string; napcatToken?: string }): PlatformAdapter {
  const napcat = createNapCatClient(env);
  return {
    platform: "qq",
    async send(message: PlatformMessage) {
      if (message.type === "image" && message.imageUrl) {
        const res = await napcat.sendGroupImage(message.targetId, message.imageUrl);
        return { messageId: String(res.message_id || crypto.randomUUID()) };
      }
      // 默认文本
      const res = await napcat.sendGroupMessage(message.targetId, message.text || "");
      return { messageId: String(res.message_id || crypto.randomUUID()) };
    },
    async sendBatch(messages) {
      const results = [];
      for (const m of messages) results.push(await this.send(m));
      return results;
    },
  };
}
```

### 7.2 入站命令处理（QQ 群 → 平台命令服务）

> 重要约束：这里不直接调用公开 HTTP API。公开 `/api/public/draws/:slug/verify-join`、`/spin`、`/my-result`
> 有 email/JWT/OTP 身份策略；平台命令应在服务层复用业务函数，显式使用 QQ 身份。

```typescript
// src/services/platform/inbound.ts
import type { DbType } from "../../db/client";
import type { InboundEvent, BuiltinPlatformCommand } from "./types";

const BUILTIN_COMMANDS: Record<string, BuiltinPlatformCommand> = {
  "/签到": "checkin",
  "/抽奖": "spin",
  "/分享": "share",
  "/排行榜": "leaderboard",
  "/我的奖品": "my_prize",
  "/帮助": "help",
};

/** 处理一条 QQ 群消息事件 → 解析租户群绑定 → 执行系统内置命令 → 返回回复 */
export async function handleInboundEvent(
  db: DbType,
  event: InboundEvent,
): Promise<{ reply: string } | null> {
  if (event.eventType !== "message" || !event.text) return null;
  const command = BUILTIN_COMMANDS[event.text.trim()];
  if (!command) return null;

  const target = await getActivePlatformTarget(db, {
    platform: event.platform,
    targetId: event.sourceId,
  });
  if (!target || !target.assistantEnabled) {
    return { reply: "当前群未绑定活动，请管理员先在后台启用 QQ 群助手。" };
  }

  return executeBuiltinPlatformCommand(db, {
    tenantId: target.tenantId,
    platformTargetId: target.id,
    drawId: target.activeDrawId,
    publicSlug: target.activePublicSlug,
    command,
    user: {
      identityType: "qq",
      identityValue: event.userId,
      displayName: extractSenderDisplayName(event.raw),
    },
    source: {
      platform: event.platform,
      groupId: event.sourceId,
      raw: event.raw,
    },
  });
}
```

`executeBuiltinPlatformCommand()` 的内部职责：

| 命令 | 服务层职责 |
| --- | --- |
| `checkin` | 查找或创建 `lotteryEntries(identityType=qq)`；记录签到/参与事件；如配置奖励次数，更新正式抽奖次数，不维护独立积分 |
| `spin` | 校验活动为 instant lottery；调用 `performInstantSpin()`；使用稳定幂等键（建议 `platformTargetId:drawId:userId:dateOrMessageId`） |
| `share` | 确保 QQ 用户已有 entry；仅当 `promotionConfig.viral.enabled=true` 时复用/创建 `shareRecords`；返回 `/lottery/{slug}?ref={shareCode}` |
| `leaderboard` | 使用与 `viral-leaderboard` 同源的 `aggregateViralInviteCounts()` + `buildViralLeaderboardRanking()`，按 `shareRecords.joinedCount` 生成群内 Top5；看榜不自动创建参与记录 |
| `my_prize` | 用 QQ entry 查询结果、卡密、中奖列表；群内默认只展示摘要，敏感卡密建议私聊发送或提示去网页查看 |
| `help` | 根据 `platformTargets.builtinCommands` 返回当前群可用命令 |

## 8. 部署与集成

### 8.1 推荐部署方式（修正版）

> 修正要点：嫁接层不独立部署，也不作为独立桥接服务。它是 cf-lottery 内部新增的路由和服务模块，
> 与现有 cf-lottery 共用同一 VPS 进程。NapCatQQ 是唯一的外部进程。

```
1. cf-lottery（VPS 进程）
   - 新增：src/services/platform/（适配器 + 模板 + 入站处理）
   - 新增：src/routes/platform-qq.ts（入站收口端点）
   - 新增：platformTargets / platformDeliveries（租户群绑定 + 平台投递审计）
   - 复用现有：integration.ts（HTTP webhook 引擎）、activityEvents、shareRecords、lotteryEntries
   - 复用现有：/api/integration/events（退群处罚等入站回调）

2. QQ 适配器运行模式（二选一，默认推荐 tenant_hosted）
   - tenant_hosted：租户自托管 NapCat/OneBot；cf-lottery 提供回调 URL、密钥和配置二维码
   - managed：平台托管 QQ 机器人实例；只适合试点或代运营，平台承担账号风控、登录态、封号与客服责任
   - 禁止把不同 SaaS 租户的 QQ adapter URL/token/inbound token 放到全局 `.env`；这些配置必须归属于 `platformTargets`

3. Telegram Bot（P3 扩展）
   - 此轮不实现，仅保留 PlatformAdapter 接口占位
```

### 8.2 QQ 适配器部署模式（必须先定边界）

| 模式 | 用户体验 | 技术可行性 | 风控/商业风险 | 建议 |
| --- | --- | --- | --- | --- |
| `managed` 平台托管 | 租户无需提供 QQ 配置；平台在 VPS 上运行机器人账号，租户只绑定群 | 技术上可行：平台维护 NapCat/OneBot 实例或账号池 | 高：非官方协议账号可能风控/封禁；平台代持 QQ 登录态有责任边界；多租户共用账号容易串群、限频、投诉 | 只做受控试点、代运营、白名单客户；每客户/每业务线尽量独立机器人账号 |
| `tenant_hosted` 租户自托管 | 租户自己运行 NapCat/OneBot，平台给回调 URL 和密钥 | 技术上稳定：租户实例向 cf-lottery 上报，cf-lottery 再回调租户实例发消息 | 中：租户承担 QQ 账号风控；平台只负责 SaaS 能力和数据闭环 | 默认推荐；通过扫码/向导降低配置复杂度 |
| 官方 QQ Bot（后续） | 租户按官方渠道授权或平台应用代运营 | 需确认腾讯开放平台最新规则 | 低到中：合规更好，但审核、能力和成本不确定 | 中长期补充，不阻塞 P0 |

**结论**：
- “所有 QQ 机器人都部署在我们的 VPS、不用租户配置”可以做，但不能无脑作为默认商业模式。
- 集中部署在我们的 VPS 的技术可行性取决于是否能做到“每客户独立 QQ 账号、独立 NapCat/OneBot 进程、独立限频、独立密钥、独立审计”；如果只是多个租户共用一个机器人账号或一组全局配置，商业上风险过高，容易串群、被投诉、被风控，不能作为 SaaS 默认交付。
- P0 默认应支持 `tenant_hosted`，同时保留 `managed` 字段用于平台代运营试点。
- 无论哪种模式，连接配置都归属于 `platformTargets` 的某个租户/群绑定，不放全局环境变量。
- 入站密钥必须每个绑定独立生成，只存哈希；创建/重置时明文只展示一次。编辑绑定时可填写新密钥覆盖，输入框不回显旧密钥，留空不更新。
- P0 不保存 NapCat/OneBot 访问 token。租户自托管出站投递仅支持 `baseUrl`，需要通过内网、IP 白名单、反向代理或 VPN/Tunnel 控制访问面；等租户级密钥加密、解密投递、前端不回显、审计闭环完成后再打开 token 存储。

### 8.3 SaaS 配置体验（修正版）

管理端应提供“QQ 群助手”页面，而不是要求用户填写 JSON：

1. 选择活动：从当前租户的活动列表中选择一个 `publicSlug`。
2. 选择部署模式：默认 `tenant_hosted`，平台代运营客户可选 `managed`。
3. 绑定 QQ 群：填写群号或通过扫码/回调自动识别 `targetId`，系统保存到 `platformTargets`。
4. 打开功能：默认启用 `/签到` `/抽奖` `/分享` `/排行榜` `/我的奖品` `/帮助`，不可删除，只能关闭。
5. 选择展示策略：中奖卡密默认私聊或网页查看；群内只发摘要，避免泄露。
6. 系统生成该群专属上报地址、入站密钥和一键复制配置；二维码/扫码自动写入 NapCat/OneBot 配置作为后续增强，未落地前不得写进验收口径。

## 10. 关键设计决策（修正版）

> 修正要点：Handlebars → interpolate，AI 引擎 → 移除（P2-P3），部署方式 → 内嵌到 cf-lottery。

| 决策 | 选项 | 选择 | 理由 |
| --- | --- | --- | --- |
| 嫁接层部署方式 | 独立服务 / 内嵌到 cf-lottery | **内嵌到 cf-lottery** | 减少部署复杂度，同进程通信避免网络延迟，与现有 webhook 引擎直接集成 |
| 消息模板引擎 | Handlebars / EJS / interpolate | **interpolate 语法规则 + 平台文本渲染器** | cf-lottery 已有 `interpolate()` 变量替换规则；QQ 纯文本需确认 HTML 实体问题，不引入可执行模板引擎 |
| 平台适配器风格 | class / 函数式 | **函数式**（createAdapter） | 对齐 cf-lottery 现有代码风格（integration.ts 全部函数式），无 class 继承复杂性 |
| 平台适配器注册 | 静态配置 / 动态发现 | **静态配置**（Record<PlatformType, PlatformAdapter>） | 早期平台数少（只有 QQ），简单可靠，类型安全 |
| 事件路由存储 | 扩展 webhookConfigs / 独立平台表 | **独立 platformTargets/platformDeliveries** | webhookConfigs 保持 HTTP webhook 语义；平台群绑定和投递审计独立 |
| 入站处理方式 | 租户自定义命令 / 系统内置命令 | **系统内置命令** | SaaS 用户只绑定群和活动，不需要理解命令到 API 的映射 |
| 身份处理 | 公开 API 伪造参数 / 平台服务层身份 | **平台服务层 `identityType=qq`** | 避免绕过 email/JWT/OTP 公开路由安全语义，同时保留审计 |
| QQ 部署模式 | 平台全托管 / 租户自托管 / 官方 Bot | **默认租户自托管，保留平台托管试点** | 全托管技术可行但风控和账号责任高；自托管更适合 SaaS 默认交付 |
| 入站密钥 | 全局密钥 / 每群密钥 | **每个 platformTarget 独立密钥，只存哈希** | 防止一个密钥泄漏后伪造所有租户群事件 |
| AI 引擎 | 本轮引入 / 后续按需 | **后续按需引入（P2-P3）** | cf-lottery 核心是抽奖活动引擎，AI 对话不是 MVP 必需，不阻塞上线 |

## 11. 风险与注意事项（修正版）

| 风险 | 等级 | 缓解措施 |
| --- | --- | --- |
| 平台 API 限频（QQ 消息频率限制） | 中 | 消息队列 + 限速器，批量发送间隔控制（500ms/条） |
| 消息模板注入攻击 | 低 | `interpolate` 无代码执行能力；QQ 纯文本需额外确认 HTML 实体显示问题 |
| NapCatQQ 连接故障 | 中 | 适配器熔断降级（文本消息替代图片），重试连接 |
| Webhook 重复投递 | 低 | cf-lottery 已有去重机制（eventId + deliveryId 唯一约束） |
| QQ 号风控（频繁发消息） | 中 | 控制消息频率，使用合并转发减少单条消息数 |
| 许可证污染（AGPL-3.0） | 高 | **只参考设计不复制代码**，zhenxun_bot 的渲染库/调度器只参考接口设计，实现必须自研 |
| 入站命令绕过身份验证 | 高 | 不直接调用公开 email/OTP API；平台服务层显式使用 QQ 身份、校验群绑定和租户归属 |
| 租户配置复杂导致卖不动 | 高 | 内置命令 + 一键启用；租户只选活动、绑群、开关功能 |
| webhookConfigs 被平台字段污染 | 中 | 平台目标和平台投递使用独立表，HTTP webhook 保持原语义 |
| 卡密在群内泄露 | 高 | `/我的奖品` 默认群内只发摘要；卡密走私聊或网页查看，后台可配置 |
| 平台托管 QQ 账号集中风控 | 高 | 平台托管只做白名单/代运营；默认租户自托管；每客户独立账号和频控策略 |
| 租户自托管配置门槛高 | 中 | 通过二维码配置、向导、一键复制和连通性测试降低复杂度 |
