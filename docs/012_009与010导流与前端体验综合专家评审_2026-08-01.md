# 009 与 010 号方案综合专家评审：导流、可玩性、增长与多租户 SaaS

> 文档编号：012  
> 评审日期：2026-08-01  
> 评审对象：`docs/009_导流模式实现方案_2026-08-01.md`、`docs/010_前端体验升级方案_2026-08-01.md`  
> 关联文档：005、006、007、008、011  
> 评审定位：产品战略 + SaaS 架构 + 用户体验 + 数据归因 + 风险控制  
> 结论性质：本文件是基于当前仓库事实与公开规范的专家建议，不是法律意见，也不替代目标市场的合规审查。

## 一、结论先行

### 1.1 总判断

009 和 010 的方向有价值，但不能按原文直接作为最终产品方案上线。

- 009 的“商品链接字段、参与后展示、复用管理端模式”适合做 MVP，但“UTM 就等于统计”“3 小时完成”“商品链接天然安全”“未来直接加点击计数器”等判断过于乐观。
- 010 的“可插拔游戏组件”有利于视觉迭代，但把参与资格模式直接映射成游戏类型是错误的领域建模：`open`、`roster`、`password`、`invite_code` 描述的是“谁可以参加、如何验证”，不是“用户应该玩什么”。
- 当前代码已经实现了一部分 009/010，且有些实现只是视觉层或配置层，并没有形成真实的结果、转化、反作弊和审计闭环。
- 变现不应从“向参与者卖广告流量”起步。更稳妥的商业路径是：免费/自部署建立使用面，向活动公司、品牌运营团队和其他 SaaS 平台销售白标、嵌入、API、Webhook、批量能力和支持服务。

### 1.2 四项必须采纳的决策

1. **把“参与资格”和“游戏体验”拆成两个独立维度。**  
   `participation_mode` 保留为资格校验；新增 `experience_type` 或等价配置，允许 `open + wheel`、`open + scratch`、`roster + wheel` 等组合。默认体验必须能在无动画、低性能和键盘环境下完成。

2. **把导流定义为一个可配置的“推广目的地模块”，而不是商品系统。**  
   MVP 继续使用单个配置字段是合理的，但必须有严格的结构校验、URL 协议限制、长度限制、展示位置、披露文案和追踪策略。不要引入商品库存、价格同步和订单系统。

3. **把 UTM、平台事件和最终成交明确分层。**  
   UTM 只能把目标站点的访问归入某个活动或创意；它不能自动产生平台点击数、优惠券核销数或 GMV。没有目标站点事件、Webhook 或归因协议时，不得在管理端展示“转化率”“优惠券使用”“预估 GMV”等貌似精确的数据。

4. **在扩展玩法和裂变前，先保证结果可信、路径低摩擦、数据可审计。**  
   游戏动画只负责制造期待，不负责决定结果。中奖结果、奖品分配、分享奖励和优惠券发放都必须由后端状态机和审计记录决定。

### 1.3 不能继续保留的表述

以下表述应从后续文档和产品文案中删除或改成假设：

- “覆盖 90% 场景”
- “3 分钟创建活动”
- “UTM 参数即可统计点击和转化”
- “分享后自动获得额外参与次数”
- “未中奖自动发优惠券”
- “四种参与模式天然对应四种游戏”
- “CPS/CPA/CPM 可以直接作为平台收入”
- 文档 008 中的 `80% / 12% / 8% / 3%` 漏斗数字

这些内容当前没有仓库数据、客户访谈、实验结果或第三方合同支持。可以作为待验证假设，不能作为产品承诺、收入预测或行业事实。

## 二、事实审计：当前代码到底已经有什么

以下结论来自当前工作区代码，不是对方案的猜测。

### 2.1 009 的商品导流已经部分落地

当前已经存在：

- `src/db/schema.ts` 中的 `lottery_draws.productLink`，以 JSON 文本保存 `{ url, title, imageUrl, price }`。
- `src/routes/admin-lottery.ts` 中对 `productLink` 的草稿活动更新处理。
- `src/routes/public-lottery.ts` 中公开活动返回 `productLink`。
- `frontend/src/views/admin/AdminLotteryView.vue` 中的导流配置表单。
- `frontend/src/views/LotteryView.vue` 中参与后展示商品卡片，并在客户端拼接 UTM。

因此，009 里的“扩展字段、增加接口、增加表单、增加卡片”已经不是待实施计划。后续重点应转为安全性、数据定义、体验和验证，而不是重复搭建同一套 UI。

当前仍然没有看到完整的平台级导流闭环：

- 没有 `lottery_clicks` 或等价事件表。
- 没有平台侧商品曝光事件定义。
- 没有优惠券实体、唯一券码发放、核销回传和退款/过期状态。
- 没有分享关系、分享点击、有效邀请和反作弊数据模型。
- 没有目标站点订单或转化 Webhook，因此不能在本平台可靠计算 GMV。

### 2.2 010 的游戏引擎目前更接近“视觉组件集合”

当前已经存在：

- `frontend/src/components/games/GameRegistry.ts`
- `WheelGame.vue`
- `SlotGame.vue`
- `ScratchGame.vue`
- `CardGame.vue`
- `GameResultModal.vue`

但当前接口和行为与 010 的描述仍有明显差异：

- 游戏组件主要发出 `play`，没有统一、可靠的 `result` 事件。
- `WheelGame`、`SlotGame`、`ScratchGame`、`CardGame` 都存在客户端随机展示或随机动画逻辑，但参与/开奖结果仍由后端决定。
- `ScratchGame` 和 `CardGame` 会在用户提交前展示一个随机奖品名称，容易让用户误以为那就是自己的结果。
- `GameResultModal` 当前表达的是“参与成功”，不是“中奖结果”；这与真正的即时开奖玩法不同。
- `LotteryView.vue` 仍然把活动列表、深链活动页、参与者记录和登录态混在同一页面中。

因此，当前不能把这些组件宣传为“已经完成的可插拔游戏引擎”。更准确的定义是：

> 一个由统一注册表加载的参与动画层，尚未形成独立的玩法协议、结果协议和无障碍协议。

### 2.3 当前实现中需要直接修复的工程风险

#### A. 游戏映射使用了错误的领域维度

当前 `GameRegistry.ts` 的映射近似为：

```text
open        -> wheel
invite_code -> slot
password    -> scratch
roster      -> card
```

这会造成三个问题：

1. 同一种资格模式无法测试不同玩法，无法做 A/B 测试。
2. 用户会把“访问密码”“名单抽奖”误解成特定游戏规则。
3. 未来新增 `instant`、分批开奖或外部资格校验时，注册表会继续被迫承担不属于它的业务含义。

应改为：

```text
participation_mode: open | roster | password | invite_code
experience_type: submit | wheel | scratch | slot | card
result_mode: scheduled | manual | instant
```

三者可以组合，但不能互相推导。

#### B. 客户端视觉不能产生“伪中奖”

游戏组件可以随机选择扇区、卡片或滚动位置来播放动画，但必须满足：

- 组件不展示未经后端确认的“你中了某奖品”。
- 动画目标只能是中性状态，或由服务端返回的结果驱动。
- 在 `manual` / `scheduled` 活动中，动画结束文案应是“已参与，等待开奖”。
- 只有 `instant` 活动在后端完成结果分配后，才可以展示中奖/未中奖结果。
- 任何客户端随机数都不能进入奖品分配、中奖概率或分享奖励计算。

#### C. 互动控件不应使用只支持鼠标的 `div`

转盘中心、老虎机拉杆、卡片和刮刮区域都需要：

- 可聚焦、可键盘触发的按钮或等价语义控件。
- 明确的 `aria-label`、`aria-disabled` 和状态播报。
- 不依赖颜色、声音或拖动作为唯一结果提示。
- 为触摸、鼠标、键盘和辅助技术提供等价路径。

W3C WCAG 2.2 明确覆盖键盘可用性、交互动画、指针目标尺寸和状态表达。动画组件还应响应 `prefers-reduced-motion`，并提供立即显示结果的替代路径。

#### D. 迁移文件不能把 UP/DOWN 当成条件语法

`migrations/0004_product_link.sql` 当前同时包含：

```sql
ALTER TABLE lottery_draws ADD COLUMN product_link TEXT NOT NULL DEFAULT '{}';
ALTER TABLE lottery_draws DROP COLUMN product_link;
```

中间的 `-- UP` 和 `-- DOWN` 只是注释。按当前 `drizzle.config.ts` 和 `local-deploy.sh` 的执行方式，不能假定迁移器会因为注释而跳过第二条语句。该文件必须改成只包含可执行的正向迁移，并在影子数据库上验证：

1. 空库初始化。
2. 已完成 0001、0002、0003 的数据库升级。
3. 重复执行时的失败行为。
4. 回滚是否由单独的人工流程处理，而不是混在正向迁移文件中。

这是导流功能上线前的阻断项。

#### E. 公开链接和内部 ID 必须严格区分

公开 API 通过 `public_slug` 查询活动，但前端部分复制链接逻辑使用变量名 `drawId`，容易把内部 ID 和公开 slug 混用。公开分享链接、UTM campaign、二维码内容都应明确使用公开活动标识或独立的 campaign key，不应暴露内部数据库 ID。

此外，UUID 前 8 位不应直接描述为“不可枚举”。它可以降低直接猜测概率，但仍需配合足够长的随机标识、限流、活动状态检查和错误响应策略。高价值活动不能只依赖短 slug 保密。

## 三、对 009 导流方案的专业评审

### 3.1 009 做对了什么

#### 1. 不引入商品主数据系统

cf-lottery 的核心任务是活动、参与、开奖和奖品发放，不是维护商品目录、库存、价格、订单和售后。单活动关联一个外部目的地，能覆盖：

- 电商商品页。
- 品牌落地页。
- 课程报名页。
- 社群或公众号入口。
- 下载页、预约页、活动报名页。

这符合“小而美”的边界，也符合白标/嵌入场景中“由客户系统负责商品”的分工。

#### 2. 导流不阻塞参与

商品卡片放在参与成功后，比把用户先强制跳转到商品页更合理。参与者至少先完成自己的核心任务，不会因为广告或导流过早打断活动。

#### 3. 复用管理端模式

表单分区、草稿编辑、Toast、复制链接、批量管理等已有模式应继续复用。复用既有 UI 模式比再引入新的商品管理抽象更稳妥。

### 3.2 009 的核心缺陷与修正

#### 缺陷 1：把“导流”简化成一个 URL

一个 URL 只能解决“跳到哪里”，不能解决：

- 展示给谁。
- 在什么时候展示。
- 是否需要披露商业关系。
- 是否需要用户同意行为追踪。
- 是否区分活动、渠道、创意和按钮。
- 目标页面是否仍然有效。
- 目标站点是否允许被外部嵌入或追踪。

建议保留单字段，但把它升级为有版本的配置对象：

```ts
type PromotionConfigV1 = {
  version: 1
  enabled: boolean
  kind: 'destination'
  placement: 'after_join' | 'after_result' | 'both'
  destination: {
    url: string
    title: string
    imageUrl?: string
    priceText?: string
    currency?: string
  }
  ctaLabel?: string
  disclosureText?: string
  tracking: {
    enabled: boolean
    campaignKey: string
    contentKey?: string
  }
}
```

MVP 不需要新建商品表，但需要服务端校验：

- 只允许 `https`；是否允许 `http` 要由部署环境和租户策略决定。
- 拒绝 `javascript:`, `data:`, `vbscript:` 等危险协议。
- URL、标题、价格、图片地址和披露文案限制长度。
- 图片地址同样只允许安全协议，必要时限制图片域名。
- 不允许把未清洗的 URL 原样反射到 HTML 或开放重定向。
- 保存时记录配置版本，前端对未知版本安全降级。

#### 缺陷 2：UTM 被当成平台统计系统

Google Analytics 的官方文档把 UTM 定义为用于识别引荐活动的 URL 参数，并说明数据会进入目标站点的流量来源报告。由此可以得到：

- UTM 适合帮助商家在自己的分析系统里识别活动来源。
- UTM 不会自动告诉 cf-lottery “点击了多少次”。
- UTM 不会自动告诉 cf-lottery “购买了多少单”。
- 没有跨域、订单事件或 Webhook，平台不能可靠计算收入。

因此，009 的 MVP 可以提供“带规范 UTM 的出站链接”，但管理端只能展示：

```text
已配置推广链接
已生成活动归因参数
```

不能在没有事件数据时展示：

```text
点击 1,234 次
转化率 12.3%
优惠券已使用 89 张
预估 GMV ¥23,456
```

#### 缺陷 3：不能把参与者身份放入 UTM

008 建议把 `entry_id` 写入 `utm_content`。即使 `entry_id` 不是邮箱，它仍可能成为跨系统关联参与者行为的标识；在不同法域下可能被视为可链接的个人数据或带来不必要的隐私风险。

默认策略应是：

- `utm_source=lottery`
- `utm_medium=draw`
- `utm_campaign=<公开的活动 campaign key>`
- `utm_content=<创意或按钮 key，可选>`

不要把邮箱、手机号、内部用户 ID 或可长期关联个人的 token 放入目标域名 URL。若确实需要“某个参与者点击了什么”的归因，应先定义目的、保存期限、用户告知/同意、匿名化方式和删除流程，再使用短期、不可逆或受控的 opaque token。

#### 缺陷 4：导流卡片不能承诺价格真实有效

`price` 是租户填写的展示文本，不是实时价格。必须在 UI 上使用“活动配置的展示价”或由租户提供的文案，避免暗示平台验证过价格、库存或优惠有效期。

如果未来需要实时价格和库存，应该接入外部商品系统或通过 Webhook 同步，不应在抽奖表里逐步演化出半套商品系统。

#### 缺陷 5：未中奖优惠券不是一个静态字符串

把同一优惠券码发给所有未中奖者会产生：

- 共享码泄露。
- 使用次数不可控。
- 无法区分发放、领取和核销。
- 不能处理过期、撤销、退款和补发。
- 不能证明优惠券带来的真实订单。

正确的 MVP 选择只有两个：

1. **不做自动优惠券，只展示客户提供的统一活动口令，并明确这是外部商家的规则。**
2. **做唯一券码池。** 每个参与者最多获得一条码，码必须有 `available / reserved / issued / redeemed / expired / revoked` 等状态，并通过目标系统或人工导入回传核销状态。

不要把“优惠券”写成 `productLink` 的附属字段，也不要在没有库存和核销协议时宣称“自动发放”。

### 3.3 导流的推荐产品结构

建议把导流拆成三个层次：

#### 层 1：目的地配置，P0

- 一个安全的外部 URL。
- 标题、图片、展示价格和 CTA。
- 展示位置：参与成功后、结果后、两者。
- 可选披露文案。
- 规范化 UTM。

#### 层 2：平台事件，P1

只有在需要平台看板时再增加：

```text
promotion_impression
promotion_click
outbound_open
```

事件至少包含 `tenant_id`、`draw_id`、事件类型、时间、匿名会话标识、版本和来源，不默认保存原始邮箱。事件需要去重、限流、保留期限和导出规则。

#### 层 3：真实转化，P2

通过以下任一方式才能展示“转化”：

- 目标商家的订单 Webhook。
- 目标站点 SDK/事件回传。
- 可验证的优惠券核销接口。
- 合同约定的第三方归因平台。

否则只展示“点击”或“出站打开”，不展示成交和 GMV。

## 四、对 010 前端体验方案的专业评审

### 4.1 010 做对了什么

#### 1. 认识到抽奖需要情绪曲线

抽奖的可玩性不是装饰，而是帮助用户理解流程、等待结果和记住活动品牌。转盘、刮刮卡、老虎机和翻牌可以服务不同的品牌气质与活动场景。

#### 2. 统一结果弹窗是正确方向

无论使用什么动画，结果区都应该统一处理：

- 当前状态。
- 奖品名称。
- 兑换或领取方式。
- 开奖时间。
- 查询入口。
- 分享入口。
- 导流入口。

#### 3. 动画和服务端结果分离是必须的

`GameRegistry.ts` 的注释已经表达了“动画不决定中奖结果”，这个原则必须提升为正式接口约束和测试要求。

### 4.2 010 的关键错误：把资格模式当成玩法模式

参与模式和游戏体验应分别回答两个问题：

| 问题 | 配置 |
|---|---|
| 谁可以参加、怎样证明资格 | `participation_mode` |
| 用户看到什么互动、如何完成动作 | `experience_type` |
| 结果什么时候产生 | `result_mode` |
| 结果由谁决定 | 后端开奖服务 |

推荐组合示例：

| 场景 | 资格模式 | 玩法体验 | 结果模式 |
|---|---|---|---|
| 粉丝福利 | `open` | `wheel` | `scheduled` |
| 企业年会 | `roster` | `wheel` 或 `card` | `manual` |
| 社群口令 | `password` | `scratch` 或 `submit` | `scheduled` |
| 会员福利 | `invite_code` | `slot` 或 `wheel` | `instant` |
| 展会扫码 | `open` | `submit` 或 `wheel` | `instant` |

不能因为是名单模式就强制卡片，也不能因为是密码模式就强制刮刮卡。活动运营者应根据品牌和活动目标选择体验。

### 4.3 推荐的公开端状态机

公开端不应只围绕“点按钮后弹窗”设计，而应明确状态：

```text
unavailable
  -> eligible
  -> verifying
  -> ready_to_play
  -> submitting
  -> entered
  -> awaiting_draw
  -> result_available
  -> claimed / redirected
```

不同 `result_mode` 的终态不同：

- `manual` / `scheduled`：进入 `awaiting_draw`，动画完成后只说明“参与成功”。
- `instant`：服务端提交成功并完成结果分配后进入 `result_available`。
- 已参与的用户：始终可以重新打开活动页查看当前状态，不重复消耗资格。
- 失败、超时、活动暂停、活动已满：必须有可恢复的错误状态，不要只显示通用“网络错误”。

### 4.4 各玩法的具体修正

#### 大转盘

适合作为默认展示，但必须：

- 奖品扇区只是活动奖项展示，不能让用户以为客户端决定中奖。
- 中奖概率、奖项库存和服务端结果不能由 canvas 逻辑推断。
- 允许“直接完成参与”的无动画路径。
- 对长奖品名使用可读的列表或辅助文本，不只绘制到 canvas。

#### 刮刮卡

刮开前不能展示随机生成的“奖品名称”作为底层结果。应展示：

```text
刮开后查看参与结果
```

或者在后端返回结果后再显示“已参与/中奖/未中奖”。刮开动作应是视觉反馈，不应先在客户端决定奖品。

#### 轮盘/老虎机

槽位滚动必须是后端结果的视觉表达，不能随机滚动出与最终结果不一致的奖项。没有结果时应显示中性符号或活动奖品预览。

#### 卡片翻转

卡片数量、奖品名称、翻牌动作和实际抽奖结果要区分。若翻牌只是“选择一个动画入口”，应明确告知；否则用户会理解为“我选中的卡片就是中奖卡片”。

### 4.5 分享裂变的正确设计

“分享一次就增加次数”不是可靠的增长机制，容易带来刷量、群 spam、虚假参与和公平性争议。

建议采用以下规则：

1. 分享只是生成链接，不立即发奖励。
2. 奖励触发条件是“新参与者通过分享链接进入并完成资格验证”。
3. 同一设备、邮箱、手机号、邀请码和活动参与记录需要去重。
4. 邀请者和被邀请者都要看到奖励上限、触发条件和异常处理规则。
5. 奖励应优先是一次性额外机会或非现金权益，且有上限。
6. 被邀请者必须知道这是带奖励的推荐关系。
7. 结果页分享文案必须区分“已参与”和“已中奖”，不能在开奖前生成“我中奖了”的虚假文案。
8. 不能把现有 `invite_code` 直接当成社交裂变模型。邀请码是资格凭证，推荐关系还需要分享链接、归因窗口、有效参与和反作弊状态。

## 五、行业需求与用户痛点

### 5.1 运营者真正愿意解决的问题

抽奖本身通常是低频动作，用户真正愿意付费或持续使用的价值集中在：

- 10 分钟内创建活动并发布链接/二维码。
- 不需要开发人员就能配置名单、邀请码、奖品和开奖时间。
- 参与者手机端少步骤、不卡顿、不强制注册平台账号。
- 开奖结果可解释、可审计、可导出。
- 卡密和奖品发放不重复、不丢失、有重发机制。
- 可以复制活动、复用模板和品牌素材。
- 多个客户活动之间隔离，活动公司能管理多个租户或客户空间。
- 能知道活动带来了多少有效参与和出站访问，而不是只有一个模糊的“参与人数”。

### 5.2 三类核心客户

#### A. 一次性活动组织者

例如 HR、展会运营、社群主、老师。痛点是上手和可靠性，付费频次通常需要验证。对他们，模板、二维码、现场大屏、手动开奖和导出比复杂游戏数量更重要。

#### B. 持续运营的品牌/商家

他们关心重复活动、品牌定制、商品导流、优惠券核销、转化数据和外部系统集成。对他们，单个 URL 不够，需要事件、Webhook、模板和权限。

#### C. 活动公司或其他 SaaS 平台

他们关心白标、自定义域名、多客户空间、API、批量创建、审计、限额和 SLA。这个群体更可能为“省研发和交付时间”付费，而不是为一个转盘动画付费。

### 5.3 参与者的底线

参与者通常不是 cf-lottery 的付费客户，但决定活动是否传播：

- 看到什么奖品、谁主办、何时开奖必须清楚。
- 参与后不能被强迫点击商品或关注账号才能查看结果。
- 不应默认把活动邮箱加入营销名单。
- 不能在客户端先展示一个看似中奖、提交后又变成另一个结果。
- 需要移动端可用、低带宽可用、无动画可用。
- 规则、抽奖资格、奖品数量和结果查询方式要易于找到。

## 六、最优产品方案

### 6.1 产品定位

建议采用双层定位：

> 对终端运营者：快速创建、可信开奖、低摩擦参与的活动工具。  
> 对 B2B 客户：可白标、可嵌入、可审计的抽奖与活动互动引擎。

不建议把产品首页定位成消费者抽奖广场。消费者广场需要持续内容供给、审核、反作弊、流量运营、投诉和商业化能力，会把项目从工具拖成平台。

### 6.2 核心产品边界

#### 保留

- 活动生命周期、时间窗口、手动/定时开奖。
- 公开、名单、密码、邀请码等资格模式。
- 卡密和人工发放奖品。
- 可靠的公开活动页、二维码、复制链接。
- 统一结果状态和中奖通知。
- 商品/落地页目的地配置。
- 活动复制、模板、导出和审计。
- 白标/嵌入所需的稳定 API 边界。

#### 暂缓

- 平台广告位。
- 面向消费者的抽奖广场。
- 复杂排行榜。
- 观看广告解锁机会。
- 多供应商商品同步。
- 没有外部核销协议的“自动优惠券”。
- 用 CPS/CPA/CPM 做收入承诺。

### 6.3 版本分层

#### P0：可信、可用、可测量

- 修正迁移。
- `participation_mode` 与 `experience_type` 解耦。
- 统一活动页状态机。
- 游戏组件不再产生伪奖品提示。
- 商品链接服务端校验和配置版本。
- UTM 规范化，但不虚构点击/成交数据。
- 基本出站事件或明确声明“由目标站点统计”。
- 键盘、触摸、无动画、移动端和错误恢复。
- 公开规则、主办方、奖品、开奖时间和隐私告知。
- 多租户读写隔离测试。

#### P1：提升留存与交付效率

- 活动模板和复制。
- 二维码和现场投屏模式。
- 参与者结果查询凭证。
- 唯一优惠券码池和核销状态。
- Webhook、事件导出和基础看板。
- 白标 logo、颜色、域名和邮件模板。
- 更细的权限和团队协作。

#### P2：平台化与商业化

- API/SDK 嵌入。
- 多客户工作空间。
- 分批开奖、即时开奖、分层概率和高级风控。
- 归因平台连接。
- 广告主/品牌合作模块。
- 成交分成或按效果收费。

## 七、推荐数据和接口演进

### 7.1 活动表增加独立的体验配置

最小改法：

```sql
experience_type TEXT NOT NULL DEFAULT 'submit'
promotion_config TEXT NOT NULL DEFAULT '{}'
```

如果不希望继续增加字段，也可以把体验配置作为版本化 JSON，但不能把它隐含在 `participation_mode` 中。

### 7.2 导流配置的验证边界

服务端在创建、编辑和发布时都要校验，不要只相信 HTML `type="url"`：

```text
1. 解析 URL。
2. 仅允许明确的安全协议。
3. 限制 URL 长度和重定向策略。
4. 校验标题、图片、价格文案长度。
5. 规范化 UTM 字段并拒绝身份信息。
6. 发布前检查活动已配置合法目的地。
7. 目标地址变化时允许草稿重新编辑，已发布活动保留历史快照。
```

### 7.3 事件模型

在确有看板需求时再增加事件表，建议与业务事实分开：

```text
promotion_events
  id
  tenant_id
  draw_id
  event_type
  anonymous_session_key
  entry_id nullable
  campaign_key
  content_key nullable
  occurred_at
  metadata_json
```

建议默认不保存 `entry_id`，只有在有明确归因目的并完成隐私评估时才启用。事件表必须有：

- 幂等键或去重策略。
- 速率限制。
- 数据保留期限。
- 租户查询和导出权限。
- 聚合统计优先于明细展示。

### 7.4 结果与奖品发放

游戏体验不应直接写奖品。正确链路是：

```text
用户提交资格
  -> 服务端校验活动和身份
  -> 写入 entry
  -> 根据 result_mode 决定是否立即开奖
  -> 写入 winner / reward
  -> 更新活动状态
  -> 异步通知
  -> 记录审计
```

“未中奖奖励”也必须走 reward 状态机，不应由前端根据 `winner=false` 直接拼出优惠券。

## 八、增长与变现设计

### 8.1 推荐的增长飞轮

```text
模板/二维码快速创建
  -> 活动发布和参与
  -> 可信结果与可导出记录
  -> 运营者复制活动
  -> 更多活动数据和模板
  -> 更快交付给下一个客户
```

参与者裂变只是可选的第二飞轮：

```text
已参与
  -> 自愿分享
  -> 新用户完成有效参与
  -> 受限额外权益
```

不要把“分享次数”当成核心北极星指标。它很容易被刷，也不等于新用户、有效参与或成交。

### 8.2 推荐北极星指标

早期更适合关注：

- 活动创建到发布成功率。
- 发布后首个有效参与的时间。
- 有效参与完成率。
- 活动复制率和 30 天复用率。
- 开奖成功率和通知成功率。
- 参与者结果查询成功率。
- 商品卡片点击率（仅在有事件数据时）。
- 每租户每月完成活动数。
- 白标/API 客户的接入成功率。

不要把页面浏览量、分享按钮点击量或动画完成量直接当作业务价值。

### 8.3 推荐变现阶梯

#### 免费/开源层

- 自部署或低额度托管。
- 核心抽奖闭环。
- 带平台标识。
- 基础导出和基础模板。

#### 白标层

- 去除平台标识。
- 自定义域名、品牌、邮件和活动页。
- 多客户空间。
- 更高参与量和更长日志保留。
- 人工支持和 SLA。

#### 嵌入/API 层

- API、SDK、Webhook。
- 批量创建活动。
- 服务端结果回调。
- 自定义 UI 或无头模式。
- 按调用量、活动量或客户空间收费。

#### 效果收费层

只有在拥有稳定的目标站点事件、订单核验、归因窗口和合同条款后，才考虑 CPA、CPS 或收入分成。没有这些条件时，按效果收费会把平台置于无法证明结果的争议中。

## 九、隐私、披露和合规边界

本项目可能处理邮箱、手机号、参与记录、IP 哈希、分享关系和出站行为。至少需要以下产品级开关和文案能力：

1. 事务性通知与营销订阅分开，不因输入邮箱参与抽奖而默认加入营销名单。
2. 说明收集哪些数据、用于什么目的、保存多久、如何查询或删除。
3. 对出站追踪和分享奖励使用清晰的活动规则与隐私说明。
4. 运营者配置了商业推广或品牌合作时，在活动页和分享文案中提供不易忽略的披露。
5. 针对地区、年龄、购买条件、奖品价值、抽奖规则、税务和广告披露进行法域审查。
6. 对外链、图片、品牌文案和奖品描述保留租户责任声明与平台审核/举报机制。
7. 高价值活动需要人工复核、异常参与标记、结果审计和争议处理流程。

FTC 关于社交媒体商业关系披露的公开指导强调，经济或其他有价值的品牌关系应在推荐内容附近清楚披露；这类原则可作为“分享奖励、品牌推广、赞助活动”界面设计的参考，但目标市场仍需单独确认适用规则。

## 十一、验证计划

### 11.1 工程测试

- 导流配置 schema 单元测试。
- URL 协议、重定向、长度和 JSON 版本兼容测试。
- UTM 保留原始 query 参数、统一大小写和拒绝身份标识测试。
- `experience_type` 与 `participation_mode` 任意组合测试。
- 游戏动画目标与后端结果一致性测试。
- `prefers-reduced-motion`、键盘、触摸和窄屏测试。
- 多租户读写、公开 slug、越权访问和聚合统计测试。
- 开奖、邀请码 CAS、容量限制和重复提交并发测试。

### 11.2 产品实验

至少用真实数据验证以下假设：

1. 参与成功后展示商品卡片，是否提升合格出站点击，而不是只增加误触。
2. 转盘动画相对静态提交，是否提升完成率，是否增加等待和退出。
3. 邮箱验证码带来的防刷收益，是否值得其对移动端转化的损耗。
4. 分享奖励带来的有效新参与，是否超过异常参与和支持成本。
5. 模板和复制是否比新增游戏类型更能提升租户复用。

实验必须设置清晰的对照组、指标定义、样本窗口和停止条件。没有实验前，不要使用文档 008 中的漏斗数字作为预测。

## 十三、最终建议

本项目下一阶段不应继续堆叠更多游戏，而应按以下顺序推进：

```text
先修迁移和安全边界
  -> 解耦资格与体验
  -> 统一参与/等待/结果状态
  -> 修正导流配置与数据口径
  -> 补齐无障碍、移动端和反作弊
  -> 用真实实验验证动画、分享和导流
  -> 再建设优惠券、Webhook、白标和 API
```

最优的 MVP 不是“玩法最多”，而是：

> 运营者能快速发布，参与者愿意完成，结果可信可查，导流数据说得清楚，租户之间互不影响，之后可以平滑嵌入更大的 SaaS。
