# 开发期架构基线与轻量权限最终方案

> 文档编号：026
> 创建时间：2026-08-01
> 定位：作为 cf-lottery 后续开发的基准文档，冻结 SaaS 三层用户、轻量授权、平台运营后端和玩法扩展方式。
> 结论级别：基线决策。开发期发现旧实现与本文冲突时，直接迁移或删除错误入口，不做无意义兼容。

---

## 一、最终结论

当前最优方案不是完整 RBAC，也不是在现有 `/api/admin/*` 上继续兼容平台功能，而是：

```text
L1 普通参与者：/api/public/*
L2 租户后台：  /api/admin/* + /admin/*
L3 平台后台：  /api/platform/* + /platform/*
System 任务：  /api/cron/*

数据模型：
  users             只表示登录身份
  tenant_members    表示租户内成员和租户角色
  platform_members  表示平台运营成员和平台角色

权限模型：
  RBAC-lite / Capability Gate
  路由入口做能力门禁
  权限常量写在代码里
  不做数据库权限矩阵
```

这版基线要解决的核心问题是：**在 Cloudflare Workers Free + Turso/libSQL Free 约束下，保证安全边界清晰，同时不把系统做成臃肿的权限产品。**

## 二、官方约束核对

截至 2026-08-01 核对：

| 平台 | 当前核对值 | 设计影响 |
|------|------------|----------|
| Cloudflare Workers Free | 100,000 requests/day | 公开热路径必须少请求、可缓存、少往返 |
| Cloudflare Workers Free | CPU time 10 ms/request | 不在请求内做高 CPU 密码 KDF、大 JSON、CSV、大循环、复杂排序 |
| Cloudflare Workers Free | Memory 128 MB | 不把候选池、导出文件、日志全集一次性放内存 |
| Cloudflare Workers Free | Subrequests 50/request | 一个接口不能拆成大量远程调用 |
| Turso Free | pricing 页标注 Free: 100 databases、5GB storage、500M monthly rows read、10M monthly rows written | 具体数字未来可能变化，代码按 rows read/write 可控原则设计 |

关键口径：

1. Worker CPU time 只计算 Worker 代码实际执行 CPU 的时间。
2. 等待 Turso 数据库网络 I/O 不计入 Worker CPU time。
3. 数据库 `COUNT`、聚合、无索引扫描的主要风险是 Turso rows read、数据库侧计算和响应延迟。
4. Turso pricing 页说明 rows read/written 是 compute proxy，每个被触达的行都会计入，不只是返回给应用的行。
5. Free plan 任一 quota 超限可能阻断数据库使用，因此不能把免费层当无限生产环境。

参考：

- Cloudflare Workers Limits: https://developers.cloudflare.com/workers/platform/limits/
- Turso Pricing: https://turso.tech/pricing
- Turso Usage & Billing: https://docs.turso.tech/help/usage-and-billing.md

## 三、当前代码事实

已经核对到的关键事实：

| 位置 | 事实 | 风险 |
|------|------|------|
| `src/middleware/auth.ts` | 工作区已有 `requireTenantMember()` / `requirePlatformMember()` 草案，但尚未形成完整闭环 | 必须按 026 基线修正后再接入路由 |
| `src/middleware/auth.ts` | 草案中租户默认角色含 `member`，且组合条件写法未沿用项目常见的 `and(eq(), eq())` | 租户角色只允许 `owner/admin/viewer`；Drizzle 条件必须按现有可测试写法实现 |
| `src/index.ts` | 当前挂载 `/api/admin/system-config` | 系统配置被放在租户后台命名空间 |
| `src/routes/admin-system-config.ts` | 只使用 `requireAuth` | 任意租户管理员可读写全局配置 |
| `src/routes/admin-lottery.ts` | `/redemption-codes`、`/batch`、`/stats` 在 admin 路由下 | 平台额度码发行能力错放在租户后台 |
| `src/routes/admin-lottery.ts` | `/redemption-codes/redeem` 是租户兑换 | 应保留为 L2 能力 |
| `src/routes/admin-lottery.ts` | 兑换码先读 `usedCount` 再 update | 并发下可能超发 |
| `src/db/schema.ts` | `tenant_members.role` 已存在 | 可承载轻量租户角色 |
| `src/db/schema.ts` | 工作区已出现 `platformMembers` 草案，但未看到对应 migration，且默认角色为 `operator` | 必须改为显式写入 `platform_operator` 等平台角色，不能把租户 `operator` 残留带入平台模型 |
| `src/routes/admin-lottery.ts` | 已出现 `operator` 字符串 | 开发期应清理为 `admin`，不要长期兼容同义角色 |
| `frontend/src/router/index.ts` | `/admin/config`、`/admin/redemption-codes` 已存在 | 前端也混用了 L2/L3 |

这说明问题不是“缺一个复杂权限系统”，而是“路由语义和授权门禁没有分层”。

## 四、必须冻结的设计原则

### 4.1 不背开发期兼容包袱

兼容只允许出现在三类地方：

1. 已执行数据库 migration。
2. 已对外发布且客户正在使用的公开 API。
3. 已存在业务数据，必须迁移或读兜底。

当前未上线的后台接口、前端菜单、平台能力错误入口，直接删除或迁移到目标结构。不要为了错误路径写 wrapper、alias、fallback、双入口。

### 4.2 `/api/admin/*` 永远表示租户后台

规则：

1. 必须有 `tenantId`。
2. 查询必须按 `tenantId` 过滤。
3. 不允许为了平台后台移除 `tenantId` 条件。
4. 不允许平台账号通过 `/api/admin/*` 做跨租户操作。

### 4.3 `/api/platform/*` 永远表示平台后台

规则：

1. 必须查 `platform_members`。
2. `status != active` 一律 403。
3. 跨租户访问必须显式传 `tenantId` 或明确分页条件。
4. 平台写操作必须写审计日志。
5. 平台读列表必须分页，默认 50，最大 200。

### 4.4 `users` 只表示登录身份

禁止把平台角色和租户角色塞进 `users.role`。一个用户未来可以同时是：

```text
某租户 owner
另一个租户 viewer
平台 platform_support
```

如果把这些压成一个全局 role，后续一定会污染授权逻辑。

## 五、轻量权限模型

### 5.1 数据表

只新增一张平台成员表：

```sql
CREATE TABLE platform_members (
  user_id TEXT PRIMARY KEY,
  role TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'active',
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

平台成员创建时必须显式写入 `platform_owner`、`platform_operator` 或 `platform_support`。不建议给平台角色设置 `operator` 这种模糊默认值，因为它会和历史租户角色残留混淆。

租户成员沿用 `tenant_members`，角色只保留：

| 角色 | 能力 |
|------|------|
| `owner` | 租户内全部能力，含成员管理和危险操作 |
| `admin` | 活动、奖品、黑名单、Webhook/API Key |
| `viewer` | 只读数据面板和活动查看 |

平台角色只保留：

| 角色 | 能力 |
|------|------|
| `platform_owner` | 平台成员、系统配置、套餐、额度码、租户状态 |
| `platform_operator` | 租户查看、额度码发行、用量和失败投递 |
| `platform_support` | 只读支持视图，默认不能写配置和额度 |

### 5.2 中间件

```text
requireAuth()
  只做 JWT 验证
  注入 userId、tenantId

requireTenantMember(allowedRoles)
  用于 /api/admin/*
  按 tenant_id + user_id 主键查 tenant_members
  校验 role 是否命中

requirePlatformMember(allowedRoles)
  用于 /api/platform/*
  按 user_id 主键查 platform_members
  校验 status = active 和 role 是否命中
```

资源判断：每个后台请求增加 1 次主键或组合索引查询是可以接受的。后台低频、敏感度高，安全收益高于 rows read 成本。公开参与链路不引入这类权限查询。

### 5.3 能力常量

权限不要做数据库矩阵，直接用代码常量表达：

```typescript
export const TENANT_CAPABILITIES = {
  "admin.draw.read": ["owner", "admin", "viewer"],
  "admin.draw.write": ["owner", "admin"],
  "admin.member.write": ["owner"],
  "admin.audit.read": ["owner", "admin"],
} as const;

export const PLATFORM_CAPABILITIES = {
  "platform.config.write": ["platform_owner"],
  "platform.redemption.write": ["platform_owner", "platform_operator"],
  "platform.tenant.read": ["platform_owner", "platform_operator", "platform_support"],
} as const;
```

默认拒绝。没有明确声明 capability 的敏感路由不能放行。

### 5.4 明确不做

以下设计不进入当前基线：

| 不做项 | 原因 |
|--------|------|
| `permissions` 表 | 对当前系统过重，会引入运行时权限查询和缓存失效问题 |
| `role_permissions` 表 | 当前角色很少，代码常量更清晰 |
| `user_roles` 表 | 租户成员和平台成员已经覆盖真实关系 |
| 租户自定义角色 | 会把产品拖成权限配置平台 |
| 每按钮数据库权限 | 前端不是安全边界，且浪费 rows read |
| `tenantId = null` 平台账号 | 会污染现有服务层的租户隔离 |
| `__platform__` 特殊租户 | 会污染统计、套餐、审计、用量 |
| Worker 全局内存缓存权限 | 多实例不一致，禁用用户不能可靠生效 |

## 六、路由和前端基线

### 6.1 后端路由

| 路由 | 定位 | 处理 |
|------|------|------|
| `/api/admin/system-config` | 错误入口 | 删除挂载，测试验证 404 |
| `/api/platform/system-config` | 平台配置 | 新增，必须 `platform_owner` |
| `/api/admin/redemption-codes` | 错误的平台发码入口 | 删除管理语义 |
| `/api/admin/redemption-codes/batch` | 错误的平台发码入口 | 删除，测试验证 404 |
| `/api/admin/redemption-codes/stats` | 错误的平台统计入口 | 删除，平台统计迁移 |
| `/api/platform/redemption-codes` | 平台额度码 | 新增，发行和查询必须审计 |
| `/api/admin/redemption-codes/redeem` | 租户兑换 | 保留，修复 CAS |

### 6.2 前端路由

| 路由 | 处理 |
|------|------|
| `/admin/config` | 删除 |
| `/admin/redemption-codes` | 删除平台发码页 |
| `/platform/config` | 新增平台配置页 |
| `/platform/redemption-codes` | 新增平台额度码页 |
| `/admin/*` | 只保留租户后台菜单 |
| `/platform/*` | 只保留平台后台菜单 |

实现时可以复用底层 Vue 组件和样式，但用户可见路由树必须分开。

## 七、平台运营后端最小闭环

MVP 稳定后，平台运营后端只做轻量闭环：

| API | 第一阶段能力 | 资源规则 |
|-----|--------------|----------|
| `/api/platform/tenants` | 租户列表、状态、套餐 | 分页，默认 50，最大 200 |
| `/api/platform/tenants/:id/summary` | 单租户摘要 | 优先快照，缺失时低频 COUNT 兜底 |
| `/api/platform/system-config` | 全局配置 | 写操作仅 `platform_owner` |
| `/api/platform/redemption-codes` | 额度码发行、列表、统计 | 生成数量上限，写审计 |
| `/api/platform/usage-snapshots` | 用量快照读取 | 不扫公开热路径大表 |
| `/api/platform/audit-logs` | 平台审计查询 | 时间范围 + 分页 |
| `/api/platform/webhook-deliveries` | 失败投递查询和重试 | 重试显式确认，限制批量 |

不要在第一版做：

1. 财务账单系统。
2. 租户自定义权限。
3. 平台无审计 impersonation。
4. 全库实时大看板。
5. 大 CSV 同步导出。

## 八、玩法扩展基线

抽奖只是第一种玩法。后续玩法必须复用同一活动引擎骨架：

```text
activity       活动定义
entry          参与记录
outcome        结果分配
event          行为事件
promotion      导流配置
```

低成本、高价值、符合当前架构的玩法优先级：

| 玩法 | activity_kind | 价值 | 是否适合当前架构 |
|------|---------------|------|------------------|
| 抽奖 | `lottery` | 强吸引、强分享 | 已作为第一玩法 |
| 接龙/报名 | `signup_chain` | 线下活动、课程、社群常用 | 已有基础，优先稳定 |
| 候补名单 | `waitlist` | 名额稀缺、可制造转化 | 与接龙同源 |
| 预约 | `reservation` | 咨询、体验课、探店 | 复用容量分配 |
| 资料领取 | `claim` | 获客表单、下载资料 | 成本低，导流强 |
| 问卷/调研 | `survey` | 收集线索和偏好 | 复用表单 schema |
| 投票 | `vote` | 互动传播 | 复用 entry + tally |
| 签到/打卡 | `checkin` | 复访和社群活跃 | 复用事件层 |
| 审核报名 | `approval` | B2B、课程、社群准入 | 复用 result_mode |
| 竞猜/测验 | `quiz` | 游戏化互动 | 先做轻量题目，不做复杂题库 |
| 阶梯奖励 | `milestone` | 分享裂变和任务达成 | 需反作弊后再做 |

玩法准入规则：

1. 能复用五层骨架才允许加入。
2. 不为单一玩法新增一套主链路。
3. 不让玩法决定权限体系。
4. 不在公开热路径做全局统计。
5. 第一个新增玩法应优先稳定 `signup_chain`，因为它和抽奖一样都是“参与 + 结果/名额分配”模型。

## 九、实施顺序

### P0：先定安全边界

1. 新增 `platform_members`。
2. 新增 `requireTenantMember()`、`requirePlatformMember()`。
3. 删除 `/api/admin/system-config` 挂载，新增 `/api/platform/system-config`。
4. 删除 `/api/admin/redemption-codes` 平台管理入口，新增 `/api/platform/redemption-codes`。
5. 保留 `/api/admin/redemption-codes/redeem`，改为 CAS 条件更新。
6. 清理租户角色 `operator`，统一为 `admin`。
7. 前端删除 `/admin/config`、`/admin/redemption-codes` 平台页，新增 `/platform/*`。
8. 补 403、404、并发兑换测试。

### P1：平台最小运营闭环

1. `/api/auth/me` 返回 tenant role、platform role、capabilities。
2. 平台租户列表和单租户摘要。
3. 平台审计日志。
4. 用量快照表设计和读取接口。
5. 统计接口耗时观测。

### P2：玩法和商业化扩展

1. 接龙稳定化。
2. 资料领取/问卷 vertical slice。
3. 预约、投票、签到按共享骨架扩展。
4. 导流归因治理和反作弊。
5. 唯一券码池和核销能力。

## 十、验收标准

| 场景 | 期望 |
|------|------|
| 任意用户访问 `/api/admin/system-config` | 404 |
| 租户管理员访问 `/api/platform/system-config` | 403 |
| 平台成员访问 `/api/platform/system-config` | 按角色返回 200 或 403 |
| 任意用户调用 `/api/admin/redemption-codes/batch` | 404 |
| 租户管理员兑换额度码 | 走 `/api/admin/redemption-codes/redeem` |
| 并发兑换超过 `maxUses` | 不超发 |
| viewer 执行租户写操作 | 403 |
| 非平台成员访问 `/api/platform/*` | 403 |
| 平台成员禁用后访问 `/api/platform/*` | 403 |
| 平台列表 `limit=10000` | 被限制到最大 200 |
| `/api/admin/*` 查询 | 必须按 JWT `tenantId` 过滤 |

## 十一、最终红线

1. 不做完整 RBAC。
2. 不做无止境兼容。
3. 不把平台后台塞进 `/api/admin/*`。
4. 不把平台角色塞进 `users`。
5. 不用 `tenantId = null` 或 `__platform__`。
6. 不在公开热路径做租户级累计 `COUNT`。
7. 不在 Worker Free 热路径做高 CPU 操作。
8. 不为单一玩法推翻活动引擎骨架。

这份文档作为后续开发基准。后续代码、TODO、测试和前端路由都应向本文收敛。
