## 二、设计初衷：为何本地编译而非服务器编译

### 2.1 核心原因

| 因素 | 本地编译 | 服务器编译 |
|------|----------|------------|
| **TypeScript** | 开发机已安装 tsc/vue-tsc，秒级检查 | VPS 需安装 devDependencies（typescript、vue-tsc 等），增加 200MB+ 磁盘占用 |
| **Node.js 版本耦合** | esbuild 打包后生成纯 ES 模块，与 Node 版本解耦 | 编译工具链依赖特定 Node 版本，升级 VPS Node 风险高 |
| **npm install 时间** | 本地开发已安装，0 秒 | VPS 每次部署需 `npm install`（包括 devDeps），耗时 30-60 秒 |
| **原子部署** | 单文件 `dist/server.js` + `public/`，部署即生效 | 编译失败会导致服务不可用（旧文件被部分覆盖） |
| **网络稳定性** | 构建在本地完成，上传仅需传输 512KB 压缩包 | `npm install` 在 VPS 上执行需外网访问 npm registry，网络波动导致部署失败 |
| **安全性** | 私钥/凭证仅在 `.env` 中，不参与构建 | VPS 上 `.npmrc` / git credentials 增加攻击面 |

### 2.2 esbuild 打包策略

- **入口**：`src/server.ts`
- **输出**：单文件 `dist/server.js`（ESM，Node 20+）
- **external 排除**：`@libsql/client`（原生 SQLite 绑定不能打包）、`dotenv`
- **不混淆**：默认不启用（`--obfuscate` 可选用，但会增加体积）

```
npx esbuild src/server.ts \
  --bundle --platform=node --target=node20 --format=esm --minify \
  --external:@libsql/client --external:dotenv \
  --outfile=dist/server.js
```

### 2.3 部署包内容

`cf-lottery-deploy-YYYYMMDD-HHMMSS.tar.gz` 包含：
- `dist/server.js` — 后端单文件（~488KB）
- `public/` — 前端静态资源（vite build 产物）
- `package.json` / `package-lock.json` — 用于 VPS 上 `npm ci --omit=dev`
- `migrations/` — SQL 迁移文件（供 server.js 启动时自动执行）
- ~~`ecosystem.config.json`~~ — **已废弃，不再打包（2026-08-08 改用 systemd）**

## 四、systemd 服务定义

文件路径：`/etc/systemd/system/cf-lottery.service`

```ini
[Unit]
Description=cf-lottery Hono Node Server (RP of cf-auth)
After=network.target

[Service]
Type=simple
User=root
Group=root
WorkingDirectory=/root/cf-lottery
EnvironmentFile=/root/cf-lottery/.env
Environment=PATH=/root/.nvm/versions/node/v24.18.0/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
Environment=HOST=127.0.0.1
ExecStart=/root/.nvm/versions/node/v24.18.0/bin/node /root/cf-lottery/dist/server.js
Restart=always
RestartSec=5
TimeoutStopSec=20
MemoryMax=512M
NoNewPrivileges=yes
PrivateTmp=yes
ProtectHome=read-only
ProtectSystem=full
ReadWritePaths=/root/cf-lottery/data

[Install]
WantedBy=multi-user.target
```

## 五、数据库架构

### 5.1 本地 SQLite

```
TURSO_URL=file:./data/data.db
TURSO_TOKEN=
```

- **为什么不用 Turso Cloud**：VPS 单实例部署，SQLite 本地文件零延迟，无需网络往返；Turso Cloud 增加延迟和外部依赖
- **数据目录**：`/root/cf-lottery/data/data.db`（systemd `ReadWritePaths` 限定写入范围）
- **备份**：`/root/cf-lottery/backups/` 目录存有定期备份脚本

### 5.2 迁移机制

**server.js 启动时自动执行**，无需手动干预。代码位于 `src/server.ts`：

```typescript
const migrateClient = createClient({ url: DB_URL, authToken: process.env.TURSO_TOKEN });
const applied = await applyPendingMigrations(migrateClient);
console.log(`[migrate] 数据库 schema 已是最新（本地 SQLite）`);
```

迁移文件位于 `migrations/` 目录，命名规范：`NNNN_描述.sql`
- UP 段：新增功能
- DOWN 段：回滚逻辑
- 已执行的文件自动跳过（通过 `_migrations` 跟踪表）

## 六、完整部署步骤

### 6.1 前置条件（一次性）

- [ ] VPS 已安装 Node.js v24（nvm）
- [ ] VPS 已安装 Nginx 并配置好反向代理
- [ ] `/root/cf-lottery/` 目录存在
- [ ] `.env` 文件已配置（`TURSO_URL=file:./data/data.db` 等）
- [ ] systemd 服务文件已创建并 enable
- [ ] 本地有 SSH 私钥（通过 `VPS_SSH_KEY` 环境变量传入，禁止写入仓库）

### 6.2 每次部署步骤

**步骤 1：本地构建 + 上传**

```bash
# 在项目根目录执行
VPS_SSH_KEY=~/.ssh/jp_72_scp-key bash local-deploy-vps.sh
```

此脚本自动完成：
1. 迁移文件唯一性检查（防编号冲突）
2. tsc 类型检查
3. vue-tsc 模板类型检查
4. vite 前端构建 → `public/`
5. esbuild 后端打包 → `dist/server.js`
6. tar.gz 打包
  7. 通过 `cat + ssh pipe` 上传到 VPS `/root/`（避开部分 VPS 的 scp 连接重置问题）

**步骤 2：VPS 侧部署**

```bash
ssh -i ~/.ssh/jp_72_scp-key root@38.47.198.72
cd /root/cf-lottery

# 解压新版本（覆盖 dist/、public/、migrations/、package*.json）
tar -xzf /root/cf-lottery-deploy-*.tar.gz

# 安装/更新运行时依赖
npm ci --omit=dev

# 重启服务（启动时自动执行数据库迁移）
systemctl restart cf-lottery

# 验证
systemctl status cf-lottery
curl -s -o /dev/null -w "%{http_code}" https://lucky.eforge.xyz/
```

**步骤 3：验证**

```bash
# 确认服务启动成功
journalctl -u cf-lottery -n 5
# 预期输出：
# [migrate] 数据库 schema 已是最新（本地 SQLite）
# [server] cf-lottery on http://localhost:8787
# [server] platform: local

# 确认站点可访问
curl -I https://lucky.eforge.xyz/
```

### 6.3 回滚步骤

```bash
# 1. 列出历史备份
ls /root/cf-lottery/backups/
# 2. 恢复旧版本 dist/server.js
cp /root/cf-lottery/backups/dist-server-YYYYMMDD-HHMMSS.js /root/cf-lottery/dist/server.js
# 3. 重启
systemctl restart cf-lottery
```

## 七、关键设计决策

| 决策 | 选择 | 原因 |
|------|------|------|
| 进程守护 | systemd | Linux 原生，无需额外安装，崩溃自动重启，日志集成 journald |
| ~~PM2~~ | **已废弃（2026-08-08）** | 额外依赖，与 systemd 冲突（双进程争用端口导致 475 次崩溃重启） |
| 数据库 | 本地 SQLite | 零网络延迟，单文件备份简单，VPS 单实例够用 |
| 编译器 | esbuild | 比 tsc 快 100x，tree-shaking，单文件输出 |
| 部署粒度 | 全量 tar.gz | 避免增量文件遗漏，保持 VPS 文件结构简洁 |
| 迁移 | 启动时自动 | 消除手动步骤，避免部署后忘记执行迁移 |
| 环境变量 | `.env` + systemd EnvironmentFile | 与 Node.js 生态一致，不硬编码到 systemd 文件 |

## 九、故障排查

### 服务启动失败

```bash
# 查看完整日志
journalctl -u cf-lottery -n 50 --no-pager

# 常见错误：
# 1. 端口占用 → 检查是否有残留进程：ss -tlnp | grep 8787
# 2. 数据库迁移失败 → 检查 data/data.db 权限和完整性
# 3. .env 配置缺失 → 检查 TURSO_URL 和 JWT_SECRET
# 4. Node 版本不匹配 → 检查 nvm 版本：node -v
```

### 数据库损坏

```bash
# 检查并修复
cd /root/cf-lottery
sqlite3 data/data.db "PRAGMA integrity_check;"
# 预期输出：ok

# 从备份恢复
cp backups/data-YYYYMMDD.db data/data.db
systemctl restart cf-lottery
```
