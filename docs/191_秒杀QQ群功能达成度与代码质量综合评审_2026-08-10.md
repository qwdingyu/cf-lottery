### 设计目的达成（全部落实）
- **防超卖**：活动级 CAS 计数器 + 闭环节拍（join→+1→支付→取消/过期→-1）
- **未支付不白嫖**：performDraw 只选 PAID；spin 拒绝非 PAID；lottery+直付发布红线
- **卡密不足不静默**：acquirePrizeCodes 全量领取失败回滚 → FULFILLMENT_FAILED → 管理端补发
- **回调幂等**：attempt 状态幂等 + CAS + 流水号唯一索引 三层防护
- **过期释放**：30 分钟超时软释放，stale reservation 清理

### 已知限制（均为文档化设计决策，非缺陷）
1. 只支持 `claim` 活动类型直付（lottery+paymentRequired 被红线阻断，纵深防御 docs/166）
2. 只支持 email 身份参与（registered 模式发布时阻断，等待 user_id 授权查询设计）
3. 退款需人工（状态机 LATE_NEEDS_REFUND 已预留，无 Provider 退款 API 调用）
4. 生产前需 EasyPay/ZPay 小额真实支付联调（docs/134 §5）

## 5. 踩坑记录

- **事件模板体系"定义了大部分、接入了少数"**：模板定义 ≠ 功能实现，审查时需以"调用点 + 测试覆盖"为准绳，模板定义只是预留。判断事件是否该接入的准则：**命令已有实时 reply 反馈的（签到/分享）不要接入异步推送，否则刷屏**；运营主动推送场景（发布/开奖/中奖）才值得接入。
- **代码质量审查要区分"堆砌"与"合理的大函数"**：performDraw/joinDraw 是大而内聚的线性流程，拆分会破坏事务连续性——不是所有大文件都要拆；用"是否有多个关注点 + 拆分是否破坏上下文"判断，而非只看行数。
