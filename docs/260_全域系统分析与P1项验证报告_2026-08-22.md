### P1-1: grantBonusCoupon 空收件人烧券

**状态: ✅ 已修复**

**验证位置**: `src/services/lottery/reward-exits.ts:222-227`

```typescript
// docs/259 P1-1 修复：空收件人时【不消耗券码】。
// 此前空 recipientEmail 仍把券 CAS 置 issued：券从池子消失、幂等标记写入"已发放"、
// 但 my-result / my-rewards / redeem 全部按 recipientEmail 精确匹配 → 券永久不可见
// （用户拿不到、运营无法重发，真券被静默烧掉）。
// 修复：直接返回 0（不取码、不置 issued、不写幂等标记）→ 调用方视为"本次未发放"，
// 保持 rewardId:N 部分标记语义（发 0 张不写标记），补货/修复收件人后下次归因可续发。
if (!recipientEmail) {
  logWarn("reward-exits", "bonus_coupon_skip_no_recipient",
    JSON.stringify({ tenantId, drawId, sharerEntryId, rewardId, couponLabel: couponLabel || "" }));
  return 0;
}
```

**修复方式**: 空收件人时直接返回 0，不消耗券码、不置 issued、不写幂等标记。
**影响范围**: 所有 bonus_coupon 出口路径。
**测试覆盖**: 无独立单元测试，但 `referral-rewards-engine-isolation.test.ts` 有券码发放隔离测试。

### P1-3: shouldShowViralPanel 三处重复判定逻辑 + 条件不一致

**状态: ✅ 已修复**

**验证位置**:
1. `frontend/src/components/ViralLeaderboard.vue:291` — `const viralOn = computed(() => shouldShowViralPanel(props.viralConfig))`
2. `frontend/src/components/games/GameResultModal.vue:233` — `return shouldShowViralPanel(props.viralConfig)`
3. `frontend/src/views/LotteryView.vue:2394` — `function shouldShowViralPanel(draw) { return shouldShowViralPanelBase(getDrawViral(draw)) }`

**三处实现对比（经代码核验）**:

| 组件 | 判定条件 | 差异说明 |
|------|---------|---------|
| ViralLeaderboard `viralOn` | `viral.enabled === true \|\| referralRewardDefs.length > 0` | 无前置条件 |
| LotteryView `shouldShowViralPanel` | `viral.enabled === true \|\| referralRewardDefs.length > 0` | 与 ViralLeaderboard **条件完全一致** |
| GameResultModal `viralEnabled` | **`inviteShareAllowed && entryId`** && `(viral.enabled \|\| referralRewardDefs.length > 0)` | **多了两个前置条件** |

**关键差异**：GameResultModal 额外加了 `inviteShareAllowed`（活动已开奖/取消时禁用）和 `entryId`（无 entry 时禁用）两个安全门。ViralLeaderboard 和 LotteryView 没有这两个约束。

**具体风险**：
1. 活动已开奖（status=drawn）时，ViralLeaderboard 仍会渲染（因为只看 viral.enabled 或 referralRewardDefs），但 GameResultModal 的结果弹窗中不展示里程碑进度。**UI 行为不一致**。
2. 未参与活动的用户（无 entryId）打开 ViralLeaderboard，仍能看到排行榜；但 GameResultModal 中不展示。语义上 ViralLeaderboard 的行为可接受（公开排行榜），但与 GameResultModal 不对称。

**已有统一函数但未引用**: `frontend/src/views/lottery/viral-leaderboard-ui.ts:28` 导出 `isViralFeatureEnabled`，被 `shouldShowViralLeaderboard()` 使用。但三个组件各自内联实现，未引用此公共函数。

**验证位置**:
- 后端 zod 校验：`src/lib/promotion-config-schema.ts:73` — `referralRewardDefsSchema = z.array(...)` ✅ 完整
- 后端运行时校验：`src/lib/promotion-config-schema.ts:90` — `validateReferralRewardDefs()` ✅ 完整
- 后端运行时剔除：`src/services/lottery/referral-rewards-engine.ts` — `normalizeReferralRewardDefs()` ✅ 完整
- **前端 3 处消费方已统一为 `ReferralRewardDef[]`**：
  - `frontend/src/views/lottery/types.ts:177` — `export interface ReferralRewardDef { ... }`
  - `frontend/src/views/lottery/types.ts:82` — `referralRewardDefs?: ReferralRewardDef[]`
  - `frontend/src/components/ViralLeaderboard.vue:249` — `referralRewardDefs?: ReferralRewardDef[]`
  - `frontend/src/components/games/GameResultModal.vue:164` — `referralRewardDefs?: ReferralRewardDef[]`

**分析**: 后端有完整的 zod schema + 运行时 normalize 双重校验，功能正确性无问题。但前端 3 处消费方全部声明为 `unknown[]`，导致：
1. IDE 无法提供字段自动补全和类型检查
2. 重构后端字段时前端无编译期保护
3. 新人阅读代码时无法通过类型推断配置结构

**结论**: 后端校验已到位，但前端类型安全完全缺失。功能上无风险（后端兜底），但代码质量和开发体验为零。应定义明确的 `ReferralRewardDef` 接口替代 `unknown[]`。

## 五、关键架构优势

1. **三层防超发架构**: 幂等标记 → 出口 CAS → 总量约束
2. **事务边界清晰**: joinDraw 内参与+归因+奖励原子执行
3. **事件溯源**: activityEvents 统一 21 种事件类型（含 cta_impression）
4. **多租户隔离**: 所有查询带 tenantId
5. **三态隔离**: entry/order/attempt 状态独立
6. **预占-确认两阶段卡密**: 下单 reserved → 回调 issued → 超时释放
7. **CAS 乐观锁全面覆盖**: 9+ 个 CAS 点
8. **fail-closed 批量删除**: 有支付订单的活动拒绝删除
9. **确定性/不确定失败分类**: 防止资金黑洞
