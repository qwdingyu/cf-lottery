## 三、P0-1：直付秒杀「重新参与」后永久无法支付 + 每次泄漏 1 个名额

### 3.1 名额记账模型（先立公理，再谈缺陷）

秒杀名额计数器 `lottery_draws.active_participant_count` 记的是**份数（unit）**，不是人数。既有实现的记账公理：

| 动作 | 计数器变化 | 代码位置 |
|------|-----------|---------|
| `joinDraw` 首次占位 | `+1`（基础 1 份） | `participation.ts` 条件 INSERT |
| `joinDraw` 过期后重新参与（reopen） | `+1`，entry `EXPIRED → RESERVED` | `participation.ts:255-267`（活动 CAS）、`:283`（entry CAS） |
| `createPaymentOrder` 建单 | `+ (hasPriorOrder ? quantity : quantity - 1)` | `payment-service.ts:930-947` |
| `expireOverdueOrders` 超时 | entry 被释放为 EXPIRED → 释放 `quantity`；entry 仍活跃 → 释放 `quantity - 1` | `payment-service.ts:279-292` |
| `staleReservations` 清理 | 每条释放 `1`（且**排除任何存在订单行的 entry**） | `payment-service.ts:189-199, :295-308` |
| `cancelPaymentOrder` 取消 | 释放 `quantity` + entry → EXPIRED | `payment-service.ts:360-361, :411-420` |
| `armPaymentOrderForRetry` 重试 | 先 CAS `+quantity`，再要求 entry 必须为 `EXPIRED` | `payment-service.ts:482-497, :499-511` |

**推论（关键）**：`EXPIRED` 的 entry 占 **0 份**；`RESERVED` 的 entry 占 **1 份**。`armPaymentOrderForRetry` 之所以敢 `+quantity`，前提正是「entry 处于 EXPIRED，即当前占 0 份」。

### 3.2 缺陷时序

```
① 用户 join 直付秒杀      → count +1，entry=RESERVED
② 建单 quantity=1        → reserve = 1-1 = 0，entry=PENDING（净占 1 份）
③ 超时 expireOverdueOrders → 释放 1 份，entry=EXPIRED（净占 0 份），order=EXPIRED（可重试）
④ 用户再点「参与」        → reopen 分支 count +1，entry=RESERVED（净占 1 份）✅ 此步正确
⑤ 用户点「支付」          → routes/payment.ts:257 判定 existing 可重试
                          → armPaymentOrderForRetry：
                             (a) CAS count + 1 ≤ capacity      ← 重复占用（④已占 1 份）
                             (b) entry CAS 要求 EXPIRED         ← 实际是 RESERVED，rowsAffected=0
                             (c) throw「秒杀名额已被其他用户占用」→ 事务回滚
```

**后果两条**：
1. **功能死锁**：`routes/payment.ts:365-367` 只要 `existing` 可重试就永远走 `armPaymentOrderForRetry`，entry 永远是 `RESERVED`，用户**永久无法支付**（刷新、重进、换 provider 均无效）。
2. **名额泄漏**：④ 的 `+1` 已提交且不会回滚；`staleReservations` 因 `:189-199` 排除「存在任何订单行的 entry」而无法回收 → 该份数**永久泄漏**，售罄阈值被虚高占用。

事务回滚保证了**不会超卖**（(a) 的 +1 与 (c) 同事务），这是唯一的不幸中之幸。

### 3.3 回归测试盲区

`payment-service.test.ts:2610-2637` 覆盖了「过期后重新参与可再建单」，但**从未在 reopen 之后调用支付重试**，因此该缺陷不被任何测试捕获。

### 3.4 三种错误修法（先自证伪，避免造成灾难）

| 错误修法 | 为什么会造成灾难 |
|---------|----------------|
| **A. 把 entry CAS 放宽为 `IN (EXPIRED, RESERVED)`，其余不动** | `payment-service.ts:482-497` 的容量 CAS 在 entry rearm **之前**且固定 `+quantity`。RESERVED 已占 1 份，再 `+quantity` → **重复占用 1 份**，`quantity=1` 时相当于把一个人算成两份，直接**超卖**（售罄早到、或计数器长期虚高） |
| **B. reopen 分支不把 entry 改回 RESERVED，保持 EXPIRED** | `participation.ts:283` 的 `occupy` CAS（`WHERE paymentStatus = EXPIRED`）会变成**恒真守卫**，同一 entry 可被反复 reopen，每次 `+1` 且无任何状态变化去拦截 → 名额**无界泄漏** |
| **C. 让 `routes/payment.ts` 在 entry=RESERVED 时改走 `createPaymentOrder`** | `createPaymentOrder` 的 `allowedPriorStatuses`（`payment-service.ts:940-947`）在 `hasPriorOrder=true` 时是 `[PAID, PENDING]`，RESERVED 不在其中 → 依然失败；若强行放宽，`reserveQuantity` 会取 `quantity`（有历史订单分支）→ 与 ④ 的 `+1` **重复占用** |

### 3.5 采纳方案

在 `armPaymentOrderForRetry` 事务内**先读 entry 当前 `paymentStatus`，按状态决定补占份数**，与 `createPaymentOrder:940-947` 已有的「基础 1 份」约定完全同构：

```
entryStatus = EXPIRED   → 需补占 quantity     （当前占 0 份）→ CAS +quantity → rearm CAS WHERE EXPIRED
entryStatus = RESERVED  → 需补占 quantity - 1 （当前已占 1 份）→ 若 >0 才 CAS → rearm CAS WHERE RESERVED
其他状态（NONE/PENDING/PAID） → 明确报错，不做任何补占
```

**正确性论证**：
1. **不超卖**：两分支补占后「entry 净占份数 == quantity」恒成立；`quantity=1 && RESERVED` 时补占 0，跳过容量 CAS（既不虚占也不需要容量）。
2. **不少占**：`quantity>1 && RESERVED` 时补占 `quantity-1`，与 `createPaymentOrder` 首单口径一致。
3. **并发安全**：容量 CAS 与 rearm CAS 同事务；rearm CAS 的 `WHERE paymentStatus = <读到的那个状态>` 是乐观锁，若期间被 `expireOverdueOrders` / 他人改动 → `rowsAffected=0` → 抛错回滚，容量增量一并回滚（与现状同构，不引入新失败模式）。
4. **不放宽任何安全门**：`PAID` 仍拒绝重试（避免重复收款），`NONE` 仍拒绝（无占位不得凭空重试）。
5. **回收路径不变**：修复后 entry 可正常进入 `PENDING`，后续超时由 `expireOverdueOrders` 按既有 `toReleaseSet` 记账释放，泄漏源头消失。

### 3.6 回归测试（RED → GREEN）

新增 `payment-service.test.ts`：`join → 建单 → expireOverdueOrders → joinDraw 重新参与 → retryPaymentOrder`
- 断言 1：重试**成功**返回新 attempt（修复前抛「秒杀名额已被其他用户占用」）
- 断言 2：`active_participant_count == 1`（修复前为 1 但 entry 卡死；错误修法 A 会得到 2）
- 断言 3：entry `paymentStatus == pending`

## 四、P1-1：registered 模式可读取他人优惠券码（越权读）

### 4.1 证据链

| 位置 | 事实 |
|------|------|
| `public-lottery.ts:1105` | `if (draw.participationMode !== "registered")` —— registered 模式**跳过** Bearer 邮箱一致性校验，`bearerEmailVerified` 恒为 `false` |
| `public-lottery.ts:1135-1151` | OTP 校验只对 `identityType === "email"` 生效；registered 的 `identityType` 是 `user_id`（`public-lottery-helpers.ts:68-80`），**不校验任何邮箱归属** |
| `public-lottery.ts:1353` | `const couponMatchKey = identity.identityType === "user_id" ? email : identityValue;` —— 这里的 `email` 直接来自**请求体** `body.email`（`:1084`） |
| `public-lottery.ts:1354-1364` | 用该 key 查 `couponCodes.recipientEmail` 且 `status='issued'`，返回**明文券码** |

**攻击成立条件**：持任意合法业务 JWT（本租户任意注册用户即可）+ 知道受害者邮箱 → `POST /public/draws/:slug/my-result { email: "victim@x.com" }` → 返回受害者在该活动下全部 issued 券码。限流仅 10 次/分钟/IP（`:1079`），可枚举。

**注意**：这是 docs/254 §9.1 修复「registered 查不到自己的券」时引入的副作用——把匹配键从 `identityValue` 改成了**未经验证的请求体 email**，修好了可用性但打开了越权读。

### 4.2 采纳方案

`user_id` 身份的匹配键**必须由服务端从 JWT 反查**，不接受请求体：

```
identityType === "user_id" → SELECT users.email WHERE users.id = identity.identityValue
                             → couponMatchKey = 该 email（小写 trim）；查不到 → 无券（[]）
identityType === "email"   → couponMatchKey = identityValue（已过 OTP / JWT 一致性校验）
```

**论证**：
1. 与发券端口径完全一致——`reward-exits.ts:165-189`（`grantBonusCoupon`）对 `user_id` 身份存的就是 `users.email`，故可用性不回退（docs/254 §9.1 的修复目标保持达成）。
2. 与本文件既有先例一致——`/coupons/redeem` 在 `:1896-1906` 已经是「验 JWT → 查 `users.email` → 再比对」，本修复只是把同一范式补到 `my-result`。
3. 请求体 `email` 在 registered 分支彻底失去授权语义 → 越权读被根除；攻击者即使伪造 `email` 也只会拿到自己的券。
4. 不影响 `open` 系（`email` 身份路径完全未改）。

### 4.3 回归测试

`auth-and-public.test.ts`：registered 活动下给 A、B 各发一张 issued 券 → 用 **A 的 JWT** 请求 `my-result { email: B.email }` → 断言返回 `coupons` 只含 A 的券、不含 B 的券（修复前会返回 B 的券码）。

## 五、P1-2：`/join` 快捷参与绕过邮箱验证码开关（刷量 / 刷邀请奖励）

### 5.1 证据链

| 位置 | 事实 |
|------|------|
| `public-lottery.ts:810-819` | 平台开关 `system_config.enable_email_verification`：**未配置 = 走正常发码流程**，注释明示「生产务必 true」。仅当显式为 `"false"` 时 `access-code` 才允许免码直参 |
| `public-lottery.ts:1654-1667` | `/public/draws/:slug/join` 只做 `isValidEmail` 格式校验，**完全不读该开关**，也不需要任何 OTP / JWT |
| `public-lottery.ts:1703` | 该端点把 `body.refCode` 原样传入 `joinDraw` → 触发归因 `joinedCount+1`（`participation.ts:1192-1195`）→ 触发四条邀请奖励路径（含 `processReferralRewardsEngine`） |
| 前端检索 | `frontend/src` **无任何调用**该端点（仅 `verify-join` / `access-code`）；后端仅 `auth-and-public.test.ts:1079` 用它验证 registered 兜底 |

**风险**：攻击者用任意邮箱字符串批量参与并携带自己的 `?ref=`，把邀请数刷到里程碑档位，套取 `bonus_spin` / `bonus_coupon`。唯一约束是限流（默认 10 次/分钟/IP，`:115-118`），而**每次换邮箱即绕过身份级限流**（`checkPublicIdentityRateLimit` 以 email 为键）。

`password` / `roster` / `invite_code` / `registered` 四种模式由 `joinDraw` 服务层兜底拦截（`participation.ts:109, :148, :163-168, :173`），故**实际受影响的只有 `open` 模式**——但 open 正是拉新主战场。

### 5.2 采纳方案

让 `/join` 遵守与 `access-code` **同一个**开关语义：

```
读 system_config.enable_email_verification
value === "false"（显式关闭）→ 保持免码快捷参与（测试环境 / 无 Resend 场景，与 access-code:819 一致）
否则（未配置或 "true"）      → 400 拒绝，提示走验证码流程
registered 模式              → 不做此拦截，仍交由 joinDraw 服务层报「需登录」
```

**论证**：
1. **不引入新语义**：复用既有平台开关与既有默认值（未配置=需验证），修复后 `/join` 与 `access-code` 行为自洽，消除「一个门上锁、另一个门敞开」。
2. **不破坏任何现网调用**：前端零调用；唯一使用它的测试是 registered 分支，而 registered 被显式排除在拦截之外，测试语义不变。
3. **不误伤测试环境**：显式 `enable_email_verification=false` 的环境行为完全不变。
4. **失败模式安全**：读配置异常时按「未配置」处理 → 拒绝（fail-closed），而非放行。

### 5.3 回归测试

`auth-and-public.test.ts`：open 活动 + 未配置开关 → `/join` 断言 400 且无 entry 落库；写入 `enable_email_verification=false` → `/join` 断言 200 且 entry 落库。

## 六、P1-3：引擎 `conditions` fail-open —— 首次邀请即命中「邀请 3 人」档

### 6.1 引擎行为取证（源码 == 安装版 3.4.10）

`reward-distributor.js` `_meetsRewardCondition`：

```js
const conditions = def.conditions;
if (!Array.isArray(conditions) || conditions.length === 0) return true;   // ← 非数组 = 无条件放行
```

`condition-evaluator.js` 事实（逐行确认）：
- `_resolveField:52`：`data.attrs?.[field] ?? data[field] ?? 0` —— **字段不存在返回 0**，不报错
- `_evaluateCompare:70-88`：算子仅 `GTE/GT/LTE/LT/EQ/NE`，未知算子 → `false`；排序类算子在「实际值或期望值非数值」时 → `false`
- `evaluateCondition:131`：`!condition.type` → `false`；`type` 未知 → `false`；节点类型仅 `COMPARE/AND/OR/NOT`
- `direct-calculator.js`：`calculateDirect/Fixed/Custom` 首行 `if (!targetNode) return null`
- `chain-calculator.js`：`ancestors=[]` → 返回 `[]`

### 6.2 实证矩阵（`node -e` 直连安装版引擎）

事件固定为 `{ sourceNodeId:"S", eventValue:"1", attrs:{ totalJoinedCount:1, activityKind:"lottery" } }`，`directParent:null, ancestors:[]`（与 `referral-rewards-engine.ts:264-279` 完全一致）：

| 用例 | 配置 | 引擎输出 | 判定 |
|------|------|---------|------|
| A | `FIXED/SOURCE`，`conditions:[{totalJoinedCount GTE "3"}]` | `[]` | ✅ 正确拦截 |
| B | 同上但 `conditions` 写成**普通对象**（非数组） | `[{rewardId:"invite_3", amount:"2"}]` | 🔴 **fail-open：第 1 个邀请就发「邀请 3 人」奖** |
| C | 字段名笔误 `joinedCount` | `[]` | 🟡 永久不发，无任何提示 |
| D | `type:"LEVEL", target:"SOURCE"` | `[]` | 🟡 死配置（`ancestors` 恒空） |
| E | `type:"DIRECT", target:"PARENT", rate:"100"` | `[]` | 🟡 死配置（`directParent` 恒 null） |
| F | `type:"DIRECT", target:"SOURCE", rate:"50"` | `amount:"0.5"` | 🟡 `parseInt("0.5")=0`（`referral-rewards-engine.ts:321`）→ 不发 |

### 6.3 现有校验缺口

`normalizeReferralRewardDefs`（`referral-rewards-engine.ts:57-82`）只校验 `rewardId` 唯一、`type`/`target`/`rewardExit` 白名单、`FIXED` 必须有 `fixedAmount>0`，**完全不校验 `conditions`**。而 `admin-lottery.ts:841` / `:1156` 把 `promotionConfig` 当任意对象直接 `JSON.stringify` / 顶层合并，**无 schema 校验**——L3/API 直写即可构造用例 B。

### 6.4 采纳方案

在 `normalizeReferralRewardDefs` 中补 `conditions` 严格校验（非法 → 该条 def 直接剔除）：

1. `conditions` 允许缺省或空数组（= 无条件，语义合法：邀请 1 人即得；幂等标记保证只发一次）；**但若存在且不是数组 → 剔除**（根除 fail-open）。
2. 每个节点递归校验（深度上限 5，防深树 DoS）：
   - 显式 `type` 必须 ∈ `{COMPARE, AND, OR, NOT}`；`AND/OR/NOT` 的 `children` 必须是非空数组且逐个合法。
   - `COMPARE`（含无 `type` 的叶子，引擎会自动包装成 COMPARE）：`field` 必须 ∈ cf-lottery 实际提供的字段白名单 `{totalJoinedCount, activityKind, eventValue, eventType}`（对齐 `referral-rewards-engine.ts:264-272`，杜绝用例 C）；`operator` 必须 ∈ `{GTE,GT,LTE,LT,EQ,NE}`；排序类算子的 `value` 必须是**可解析数值**（否则引擎恒 false，等于死配置）。
3. 收窄 `type`/`target` 组合白名单：仅保留 `FIXED/SOURCE`、`DIRECT/SOURCE`、`CUSTOM/SOURCE`（杜绝用例 D、E 的死配置）。
4. `DIRECT/SOURCE` 要求 `rate` 能使 `pct(eventValue, rate)` 取整后 ≥ 1 不可静态判定，故改为在发布预检给出**明确 warning**（杜绝用例 F 的静默为 0）。

### 6.5 引擎侧再确认（防止「校验收窄」本身造成灾难）

| 组合 | 引擎实际行为（源码位置） | 收窄决定 |
|------|------------------------|---------|
| `DIRECT/SOURCE` | `reward-distributor.js:75-94` **内联**计算 `pct(eventValue, rate)`，**不应用** `skipRankZero` | ✅ 保留 |
| `FIXED/SOURCE` | `:107-126` 内联固定金额，不应用 `skipRankZero` | ✅ 保留（UI 唯一产出） |
| `CUSTOM/SOURCE` | `:138-145` + `resolveCustomAmount`（`amount` / `amountFrom` 可 JSON 配置） | ✅ 保留 |

## 七、P1-4：每日免费实际发放 `count + 1` 次

### 7.1 事实

`spin-execution.ts:206-223` 领取成功时 `spinsLeft += count` 并置 `lastDailyFreeSpinAt = today`；`:227` 的扣次 CAS 被 `if (!dailyFreeClaimed)` **整体跳过** → 当日首抽既拿到 `+count`，又**不消耗**本次。用户当日净得 `count + 1` 次。

L2 配置文案（`frontend/src/i18n/zh-CN.ts:1356-1357`）为「每日免费次数 / 每日免费发放次数（1-10）」，即运营预期 `count=1` 时用户每天多 1 次；实际每天多 2 次，**长期奖池消耗为预期的 2 倍**（`count=1` 时）。

被 `spin-execution.test.ts:1306-1348` 锁定（`expect(r1.spinsLeft).toBe(2)`，注释「初始 1 + 免费 1，本次未扣」）——属**既定实现**但与配置语义不符，本轮判定为缺陷。

### 7.2 与「不计入 maxSpinsPerEntry」的区分（不动的部分）

`spin-execution.ts:200-204` 明确记录：每日免费**不写** `spinsTotalGranted`，理由是避免污染 `spin-quota.ts:108` 的 `roomTotal = maxSpins - granted`（否则裂变/里程碑奖励会被每日免费顶满而锁死）。这是**有充分论证的既定设计**，本轮**不改**。

### 7.3 采纳方案

领取成功后**不再跳过扣次**（`count` 已包含当次），并把流水拆为两条以保持 `spinsLeft = Σdelta` 审计恒等式：

```
claim: spinsLeft += count（reason=daily_free, delta=+count, balanceAfter=领取后余额）
deduct: spinsLeft -= 1     （reason=spin,        delta=-1,     balanceAfter=最终余额）
```

**论证**：
1. **不可能扣穿**：claim 在同一事务内已 `+count`（`count ≥ 1`），随后 `WHERE spinsLeft >= 1` 的 CAS 必然命中；SQLite `BEGIN IMMEDIATE` 单写者串行化，无交错窗口。
2. **不影响 `spinsLeft=0` 仍可享免费**：事务前无任何 `spinsLeft` 预检（`spin-execution.ts:105-177` 只校验活动/entry/支付），额度判定全在 CAS，故 `spinsLeft=0 + 每日免费` 路径依然成立。
3. **不改上限语义**：仍不写 `spinsTotalGranted`，§7.2 的既定设计原样保留。
4. **审计更强**：修复后流水可完整重放余额，而现状「免费当次无消耗流水」会让 `Σdelta` 与余额在语义上依赖隐含约定。
5. **测试同步**：`spin-execution.test.ts:1306-1348` 的期望值随语义更新（首抽后 `spinsLeft=1`、`daily_free` 行 `balanceAfter=2`、新增 `spin` 行 `delta=-1`），并补断言「当日总可抽次数 = 初始 + count」。

## 十四、P2-9 复核：原描述纠错与真实缺陷（2026-08-20，提交 `8cc2514` / `2f5bc03`）

### 14.1 先纠正本报告自身的错误

第 296 行原写作「`validateOrderPreconditions` 取 `tiers[0]` 作为**单价**，未按数量匹配阶梯」，并给出「复用 `resolveTierPrice(quantity)`」的方案。**逐行读代码后确认这条描述是错的**，纠正如下：

- `src/services/payment/payment-service.ts` 中**不存在** `resolveTierPrice` 函数；
- `validateOrderPreconditions` 第 3 步里的 `tiers` 是 **`lotteryPrizeTiers`（奖档）**，用途是**卡密库存预检**，与单价无关；单价一致性由第 1b 步 `unitPriceCents * quantity === amountCents` 独立校验；
- 阶梯定价本身没有缺陷：`src/lib/flash-sale-config.ts` 的 `parsePricingTiers`（:122-149）返回前按 `minQuantity` 升序 `sort`，`calculateFlashSalePrice`（:253-273）遍历取最后一个满足 `minQuantity <= quantity` 的档位，**确实是按数量匹配的**。

原描述把 `lotteryPrizeTiers`（奖档）与 `pricingTiers`（价格阶梯）混为一谈。此处记录以防后续照着错误结论改代码。

### 14.2 真实缺陷：预检与发卡用了两套卡密奖品解析器

| 位置 | 解析方式 | 是否过滤 `prizes.active` | 多命中行为 |
|------|---------|------------------------|-----------|
| 下单预检（旧） | `lotteryPrizeTiers ... LIMIT 1`（**无 `orderBy`**）取任意一行，再单独查该行奖品是否 `prizeType='code'` | ❌ 否 | 取到哪行算哪行 |
| 发卡侧 `findCodePrize` | 内联 `prizes` 且要求 `prizeType='code' AND active=1` | ✅ 是 | 命中多行 → fail-closed 返回 `null` + `console.error` |

三条实际后果（均已用测试固化，先 RED 取证）：

1. **多奖档活动预检整体失效**：活动同时有「实物奖档 + 卡密奖档」时，无 `orderBy` 的 `LIMIT 1` 可能取到实物奖档 → `prizeType !== 'code'` → 跳过整个库存检查。此时只剩事务内 `reservePrizeCodes` 兜底（`createPaymentOrder` 第 1106 行，`reservedCodeIds.length < quantity` 时 `throw "卡密库存不足"`），订单会回滚，**钱没损失，但源头预检形同虚设、错误文案退化**（用户看不到「可用 0 件，需要 1 件」）。RED 证据：`Expected "可用 0 件，需要 1 件" / Received "卡密库存不足"`。
2. **停用奖品的码池被算作库存**：旧预检无 `active` 过滤，`active=0` 的卡密奖品码池会被计入可用库存。
3. **真正的「付了钱拿不到货」缺口**：`findCodePrize` 在「多个 active 卡密奖品」与「卡密奖品全部停用」两种脏配置下都返回 `null`；而 `reservePrizeCodes` 把 `null` 解释为「非卡密活动，无需预占」（第 1905 行注释）并返回 `null`，调用方于是跳过预占 → **订单创建成功、`provider.createPayment` 已调用、用户可以付款**；回调时 `acquirePrizeCodes` 同样拿到 `null` 返回 `[]` → 必然 `FULFILLMENT_FAILED`，只能靠退款兜底。RED 证据：旧实现下断言输出含 `status: "pending"` 与 `payResult`，即订单确实已创建并进入支付流程。

### 14.3 修复方案与边界

抽出唯一解析器 `resolveCodePrizeForDraw(db, tenantId, drawId)`，返回四态判别联合：

- `none` —— 活动没有任何卡密奖档（虚拟/链接/邀请等玩法）→ **跳过库存预检，语义与旧实现一致**；
- `unique` —— 唯一可用卡密奖品 → 按该 `prizeId` 统计 `available`，保留原文案 `库存不足（可用 X 件，需要 Y 件）`；
- `inactive` —— 有卡密奖档但奖品全部 `active=0` → **付款前拒绝**「活动的卡密奖品已停用，暂不可下单」；
- `ambiguous` —— 多个 `active` 卡密奖品 → **付款前拒绝**「活动配置了多个卡密奖品（N 个），无法确定发卡目标，请联系运营调整奖品配置」。

`findCodePrize` 改为该解析器的薄封装，**保留原有 fail-closed 语义与 `console.error` 日志**，因此 `reservePrizeCodes` / `acquirePrizeCodes` / 回调链路行为不变——缺口是在**下单入口**关闭的（符合本报告一贯的「源头扼杀」原则）。

顺带修正 `findCodePrize` 的一处误判：原实现按 **行数** 判断歧义，而多个奖档指向**同一个**卡密奖品（一等奖/二等奖共用同一码池）是合法配置，会被误当 `ambiguous` 导致整个活动发不出卡。现按 `prizeId` 去重后再判断。

**刻意不做的事**：不改 `reservePrizeCodes` 对 `null` 的解释（区分「无卡密奖」与「解析失败」需要改其返回契约，影响回调与重试三条链路，超出本项范围）；不改发布预检（`publish-check-service` 已有多卡密奖品阻断）。

## 十五、R-1：重试路径缺卡密库存预检与预占（2026-08-20，提交 `a8ae7a3` / `15c1153`）

### 15.1 缺陷事实（逐行核对结论）

`validateOrderPreconditions`（下单前的活动/名额/库存统一预检）在整个 `payment-service.ts` 中**只有一处调用点** —— `createPaymentOrder` 第 981 行。

`retryPaymentOrder`（:1190）走的是另一条路：`armPaymentOrderForRetry`（:424）在同一事务内只做三件事：

1. 校验活动状态与时间窗；
2. 名额容量 CAS 补占（`activeParticipantCount`）；
3. 把 `entry` 从 `expired`/`cancelled` 重新置为占位态。

**全程没有碰 `prize_codes`**。而超时（`expireOverdueOrders`）与取消（`cancelPaymentOrder`）在关单时**已经调用 `releaseReservedPrizeCodes` 把预占码退回 `available`**。

于是「超时 → 重试」这条最常见的用户路径出现资金洞：重试只补名额、不补卡密，`provider.createPayment` 照常返回支付信息，用户可以正常付款，回调时 `confirmPrizeCodes` 找不到属于本单的 `reserved` 码，退化到 `acquirePrizeCodes` 也无库存 → **必然 `FULFILLMENT_FAILED` + 退款**。比 P2-9 更严重：P2-9 需要运营配错奖品才触发，R-1 只需要码池被其他用户抢完（秒杀的常态）。

### 15.2 修复

在 `armPaymentOrderForRetry` 的名额补占成功之后（同一事务内、`quantity` 已在作用域），复用 §14.3 的 `resolveCodePrizeForDraw`：

- `ambiguous` / `inactive` → 直接 `throw`，事务回滚，名额补占一并撤销（fail-closed，与下单入口同文案）；
- `unique` → 先统计本单已持有的 `reserved` 码数量，只补 `needQuantity = quantity - held` 这个差额（**幂等**：重复重试或部分预占仍在时不会超额占用）；

`none` 分支不做任何事，非卡密玩法行为不变。

### 16.1 R-2：多个奖档共用同一码池时库存校验漏判（该拦没拦）

## 十七、营销承诺兑现链路：券池与安慰券的四处缺口（2026-08-20）

本轮审查方向从「下单/发卡」转到**促活与营销的奖励兑现出口**：邀请奖励券（`bonus_coupon`）、未中奖安慰券（`activityConfig.loserReward`）、排行榜奖励（`grantLeaderboardRewards`）。这三条都属于「对用户已经作出的承诺」，一旦静默不发，损失的是信任而不只是一次发放。

结论：发现 4 项缺口（R-7…R-10），全部已修。其中 3 项只改发布预检，不动运行时发放语义；1 项只改报告口径，不动发放行为。

### 17.1 R-7：`bonus_coupon` 券池预检从不查库存（提交 `52dba95` / `a43bf29`）

原实现（`publish-check-service.ts` 旧 :773-774）：只要某条 `referralRewardDefs` 的 `rewardExit === "bonus_coupon"`，就**无条件**追加一条 warning「请确保租户已导入优惠券码池（coupon_codes），否则奖励静默不发」，从头到尾**没有一次查询 `coupon_codes`**。

危害不是"少查一次库"，而是**预检公信力**：已导足券的租户每次发布都被同一条提示打扰，运营被训练成「这条 warning 可以忽略」——等到真的没券时，同一条提示照样被忽略，邀请奖励静默零发放。这类"恒亮告警"比没有告警更糟。

修复：按 `couponLabel` 聚合使用同一券池的 `rewardId`，循环结束后每个池查一次 `COUNT(status='available')`，仅在为 0 时提示，并给出真实张数、池标识与受影响的 rewardId 列表；同一 label 的多个奖励合并成一条。

取码口径与运行时严格对齐（这是本项的关键，口径分叉会造成反向误报）：
- `grantBonusCoupon`（`reward-exits.ts:198-205`）与 `grantLoserRewards`（`draw-execution.ts:823-828`）都只按 `tenant_id + status='available'` 过滤；
- `couponLabel` 为空时**不加** label 条件（取任意券），因此预检也必须按"租户全部可用券"统计，不能按 `label=''` 统计；
- 两处运行时都**不看 `expires_at`**，所以预检也不加过期过滤——宁可与运行时同错，不可两套口径。

### 17.2 R-8：安慰券（`activityConfig.loserReward`）零预检（提交 `52dba95` / `a43bf29`）

`loserReward` 此前在任何地方都没有发布期校验：`lib/activity-config.ts` 的 `validateActivityConfigForPublish` 只校验 `operational.*` 与 survey/vote 玩法，未知键一律忽略。后果是两个静默失败：

1. **即时开奖活动配安慰券 = 永不生效的死配置。** `grantLoserRewards` 的唯一调用点是 `performDraw`（`draw-execution.ts:407`），而 `performDraw` 对即时结果模式直接抛「即时开奖活动请使用 spin，不能统一开奖」（`:69-79`）；spin 链路（`spin-execution.ts`）对 `coupon_codes` **零引用**（已 grep 确认）。运营在即时活动上开了安慰券，界面无任何异常，一张券都不会发。
2. **券池空/label 写错 → 开奖时静默零发放。** 运行时对券池耗尽是"发到耗尽为止、不失败回滚"的容错设计，因此不会有任何错误暴露给运营。

修复（两条，判定严格镜像运行时）：
- `activity_config.loser_reward.instant_not_supported`：**error**。与既有 `promotion.referralRewardDefs.bonus_spin.not_instant`、`promotion.dailyFree.delayed_not_supported` 同级——死配置一律 fail-closed 拦在发布之前。
- `activity_config.loser_reward.pool_empty`：**warning**。券是运营可在开奖前补导的资源，不应阻断发布。
- 启用判定用 truthy（`!loserReward.enabled` 的等价否定），与运行时 `if (!loserReward?.enabled) return` 完全一致；未启用时预检完全沉默。

### 17.3 R-10：未指定 `couponLabel` 会跨批次抽走别的券（提交 `bd1f2a1` / 测试同批）

`coupon_codes` 是**租户级共享池**（`admin-lottery-integrations.ts:228-231` 的导入 API 只写 `{id, tenantId, code, label, expiresAt}`，从不写 `draw_id`），而两个发券出口在 `couponLabel` 为空时都不加 label 过滤。于是：租户为「双十一专场」导入的带 label 券，会被一个没配 `couponLabel` 的活动按 `created_at` 顺序发走，且**发完才发现**。

刻意不在运行时收窄（不改成强制 `label = ''`）：既有配置里"空 label + 只导了带 label 券"的组合正在正常发券，收窄会让它们立刻静默停发——修一个隐患换一个更急的故障，不划算。改为发布期把事实讲清楚：

- `promotion.referralRewardDefs.bonus_coupon.label_unset` / `activity_config.loser_reward.label_unset`，均为 warning；
- **只在租户确实存在带 label 的可用券时才提示**（`label != ''` 的 `COUNT`），否则这个风险不存在，提示就是新的噪音——避免重蹈 R-7 的覆辙；
- 提示里给出会被占用的真实张数，运营可据此决定是补 label 还是接受共享。

### 17.4 R-9：排行榜发放报告在事务内累加，BUSY 重跑会翻倍（提交 `09ed1c0` / `27fc53e`）

`grantLeaderboardRewards`（`leaderboard-rewards.ts`）把 `result.granted++` / `result.skipped++` / `result.details.push(...)` 写在 `withDbTransaction` 回调**内部**。而 `src/db/client.ts` 的 `withDbTransaction` 委托 cf-core，在 `SQLITE_BUSY/LOCKED` 时**整体重跑回调**（`retries=5`、`baseDelayMs=50`）：第一次尝试 granted、重跑因 `leaderboardRewardedAt` 已标记走 skipped，同一个分享者在报告里出现两次。

这与 `draw-execution.ts:238-245` 已记录的「F2 修复」是同一个陷阱（闭包状态不随事务回滚）。影响面：`admin-lottery-draw-ops.ts:968` 直接把该报告 `return ok(c, result)` 给后台，`draw-execution.ts:425` 也用 `granted` 写日志——运营看到的发放条数会多于真实发放，据此重跑或对账都会被误导。**发放本身由 CAS 保证幂等，不会多发 spins**，因此这是报告口径缺陷而非资金缺陷。

修复：回调改为只返回 `GrantVerdict = { status, rewardValue }`，报告在事务外累加。测试用 `vi.hoisted` 开关 + `db/client` 透传 mock 模拟"回调被执行两次"，断言 1 个分享者恰好 1 条明细、`granted + skipped = 1`、实发仍为一次；开关关闭时完全透传真实实现，同文件其余 48 例不受影响。

### 17.5 本轮排除的两个"疑似缺陷"（记录以免重复走弯路）

1. **`leaderboardRewardedAt = ''` 的 CAS 是否有 NULL 盲区**：不是。`src/db/schema.ts:800` 与 `migrations/0062_share_records_leaderboard_reward.sql:3` 均为 `NOT NULL DEFAULT ''`，不存在 NULL 行绕过 CAS。
2. **"为活动 B 导入的专属券被活动 A 发走"（`grantBonusCoupon` 里 `CASE WHEN drawId = ...` 的优先级排序）**：该排序在当前代码里是**死逻辑**——导入 API 从不写 `draw_id`，`drawId` 只在发券时回填，因此不存在"专属券"。真实可达的同类风险是空 `couponLabel`，即 R-10。
