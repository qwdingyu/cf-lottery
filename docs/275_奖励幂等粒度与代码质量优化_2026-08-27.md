# 275 奖励幂等粒度与代码质量优化

日期：2026-08-27
关联：docs/272（用户级邀请码）、docs/274（奖励系统深度审查修复）

## 背景

用户级邀请码（docs/272）上线后，奖励归因的幂等键存在粒度缺陷：

- 用户级邀请码是**固定值**（8 位大写安全字符），同一邀请人对所有好友 `refCode` 恒定。
- 若幂等键只有 `(sharer, eventType, refCode)`，同一邀请码的第 2 个及以后好友会被静默吞掉
  （返回 `reward_sent`），违背 `perInviteAmount`"每邀请一份"语义。
- `perUserPerDay` 配额的存在即证明同一邀请人日内多次发放是预期行为。

因此引入 `joinerEntryId`（被邀请人 entryId）把幂等粒度收敛到"每次邀请"。

## 一、P1 修复：joinerEntryId 幂等粒度

### 1.1 幂等键扩展

`triggerRewardEarned` 的幂等检查从 `(tenantId, drawId, entryId, eventType, refCode)`
扩展为可选追加 `json_extract(metadataJson, '$.joinerEntryId')`：

- **传了 joinerEntryId（正常归因路径）** → 按"每次邀请"判重：
  同一邀请码的多个不同好友各自独立发放；同一好友重复归因（reissue 重放/脏路径）仍被拦截。
- **未传（reissue 补发路径）** → 回退 `(sharer, refCode)` 粒度防重复写入（docs/274 原意）。

### 1.2 joinerEntryId 传递链路

```
recordAttributedJoin 返回 joinerEntryId
  → maybeTriggerReward attribution 类型含 joinerEntryId
  → triggerRewardEarned options.joinerEntryId
  → 幂等 SQL json_extract 匹配
```

- `recordAttributedJoin` 两个 `attributed: true` 返回路径都带 `joinerEntryId: input.entryId`。
- `resolvePendingUserAttributions` 的 `ResolvedPendingAttribution` 类型含 `joinerEntryId`，
  pending 解析路径同样按好友维度发奖。
- `settleRewardByPercent` / `cancelRewardPending` 用 `joinerMetaEq`/`joinerMetaNull` 精确匹配。

### 1.3 reissue 补发路径

`admin-lottery.ts` 的 reissue 端点从失败事件 metadata 读取 `joinerEntryId` 传入
`triggerRewardEarned`，补发幂等按"每次邀请"粒度判重——同一邀请码下好友 X 已成功
不再误拦好友 Y 的补发；历史失败事件无该字段时回退粗粒度，保守防重复发放。

### 1.4 幂等前置

幂等检查移到配额消耗之前：如果请求因幂等被拒绝，不应消耗 `perUserPerDay`/`globalPerDay` 配额，
防止重复请求耗尽配额。

## 二、代码质量优化（最佳实践）

### 2.1 提取 parseRewardConfig()

`triggerRewardEarned` 原约 170 行，其中活动配置解析（mode/金额/货币/配额）约 40 行。
提取为独立的 `parseRewardConfig(activityConfig)` 纯函数：

- 返回 `ParsedRewardConfig | null`（无有效 reward 配置返回 null，调用方静默跳过）。
- 宽容解析：JSON 非法返回 null；`mode` 缺省兼容为 `fixed`；`Number()` 防御字符串/非法值。
- 货币来源优先级：`reward.currency > flashSale.currency > "cny"`。
- 主函数只保留幂等、配额、事件写入、webhook 入队等副作用逻辑，职责更清晰、可单测。

### 2.2 提取 getOrCreateShareRecord()

两个归因路径（即时归因 `recordAttributedJoin` / pending 批量解析
`resolvePendingUserAttributions`）的 shareRecord 查找/创建逻辑重复，提取为公共函数：

- 按 `(tenantId, drawId, sharerEntryId)` 查找（docs/275 P0：用户级邀请码固定值，
  按 shareCode 查找会 UNIQUE 冲突）。
- 已存在 → 累加 `joinedCount`；不存在 → 创建合成 shareCode。
- **修复前缀不一致**：原即时归因路径用 `referrerUser.id.slice(0,8)`，
  pending 路径用 `referrerInviteCode.slice(0,8)`。统一为 `inviteCode` 前缀，
  保证两个路径生成的 shareCode 格式一致。

### 2.3 recordAttributedJoin 显式返回类型

新增 `AttributedJoinResult` 判别联合类型，替代隐式推断：

```ts
type AttributedJoinResult =
  | { attributed: false }
  | { attributed: false; selfInvite: true; refCode: string; shareRecordId?: string }
  | { attributed: false; pending: true; refCode: string; referrerUserId: string }
  | { attributed: true; refCode: string; shareRecordId: string; sharerEntryId: string; joinerEntryId: string };
```

调用方 `maybeTriggerReward` 通过 `if (!attribution.attributed || !attribution.sharerEntryId)`
窄化后安全访问 `sharerEntryId`/`shareRecordId`/`joinerEntryId`。

### 2.4 空 catch 块补充 logWarn

两处空 catch（签到奖励配置解析、裂变配置解析）补充 `logWarn`，避免静默吞错。

### 2.5 消除 as any

`options.submissionPayload` 类型为 `Record<string, unknown>`，访问 `_idempotencyKey`
无需 `as any`，直接 `String(options.submissionPayload._idempotencyKey || "")`。

### 2.6 backfill 脚本修复

- 注释 `32^8 ≈ 1.1×10^12` 修正为 `31^8 ≈ 8.5×10^11`（字符集为 31 字符）。
- 新增迁移预检：确认 `users.invite_code` 列存在，未运行 0067 迁移时明确报错退出。

### 2.7 测试修复

- 修复 `getActivityEventSummary(db, TENANT, "nonexistent")` 用真实 drawId。
- 补充奖励断言（reward_earned 计数、joinerEntryId 粒度）、pending 删除验证、
  旧格式 pending 兼容测试。

### 2.8 审查补充修复（P2-3：旧格式 pending 解析后 percent 结算 refCode 口径）

**问题**：旧格式 pending（refCode=userId）被 legacyUserId 兼容逻辑解析后，
`resolvePendingUserAttributions` 写 attributed_join 用 `evt.refCode`（userId），
而 `maybeTriggerReward` 触发奖励时用 `userRow.inviteCode`，导致 reward_pending 的
refCode 与 attributed_join 不一致。`settleRewardByPercent` 从 attributed_join 读
refCode 匹配 reward_pending 会失败，percent 奖励无法结算。

**修复**：`resolvePendingUserAttributions` 写 attributed_join 时 refCode 统一用
`referrerInviteCode`（而非 `evt.refCode`），保证结算链路口径一致。新格式 pending
（refCode=inviteCode）无行为变化；旧格式 pending 统一为 inviteCode。

**补充测试**：
- `parseRewardConfig` 直接单测（非法 JSON / 无配置 / 金额<=0 / 货币优先级 / quota 缺失 / 字符串容错）
- P2-3 回归：旧格式 pending 解析后 percent 可正常结算
- `cancelRewardPending` 多好友粒度：好友 X 已结算不拦截好友 Y 的取消
- reissue 端点 joinerEntryId 粒度：从失败事件 metadata 读取 joinerEntryId，
  同一 refCode 下好友 X 已补发不误拦好友 Y

## 四、踩坑记录

### 4.1 幂等键粒度不对称

**背景**：直接归因路径与 pending 路径的 refCode 口径不一致（直接存 inviteCode，
pending 存 userId），导致同一邀请人的多个好友在两条路径的幂等行为不对称。

**原因**：旧实现 pending 事件 refCode 存 userId，直接路径存 inviteCode。

**解决**：P1 修复统一 pending 路径 refCode 存 inviteCode，并引入 joinerEntryId
把幂等粒度收敛到"每次邀请"。

**建议**：涉及幂等键的字段口径必须全局统一，跨路径对齐后再扩展粒度。

### 4.2 getOrCreateShareRecord 并发首次归因的幂等性（知情记录）

**背景**：`getOrCreateShareRecord` 是 read-then-insert 非原子：
先 `SELECT ... WHERE (tenantId, drawId, sharerEntryId)` 判空，读不到再 INSERT。

**风险**：并发下两个请求同时命中「判空」分支，会各 INSERT 一条 shareRecord
（shareCode 含随机 UUID 片段，不撞 `idx_share_code` 唯一约束，不会整体 500）。

**实际影响评估**：
- 排行榜 / 裂变统计按 `sharerEntryId` 聚合（`SUM(joinedCount)`），冗余行统计**正确**。
- 唯一偏差：`leaderboardRewardedCount`（bonus_coupon 已发张数）track 在单条记录上，
  并发首次归因产生多行时可能跨行不同步——发券有 CAS + leaderboardRewardedCount 差额续发，
  属可自愈的小偏差，不构成超发/丢券。

**为何风险极低**：SQLite 单写者 + 写事务独占 + `busy_timeout`，并发写事务串行化，
第二个事务 BEGIN 时通常已能看到第一个事务 COMMIT 的行 → 走累加而非 INSERT。
冗余窗口仅存在于交叉读提交间隙，实际几乎不可达。

**保留为知情记录**：不属于本次回归（旧两路径同为此 pattern），window 极窄、影响可自愈，
故不改写为依赖 `(tenant,draw,sharer)` 唯一约束的 `INSERT ... ON CONFLICT`——
那反而会在共享库并发写时引入意外的 UNIQUE 冲突错误路径。

**建议**：若未来迁移到支持行级并发的 Turso/Hrana 分区，或出现确诊的统计偏差，
再考虑为 `share_records` 增加 `(tenant_id, draw_id, sharer_entry_id)` 唯一约束
并将 `getOrCreateShareRecord` 升级为 upsert 语义。
