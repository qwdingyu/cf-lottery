# 141 秒杀购买件数与批发模式分析

> 日期:2026-08-08
> 论证代码与业务逻辑,分析购买件数(1件/不限购)和批发模式的技术可行性

## 1. 购买件数分析

### 当前机制(代码验证)

| 层级 | 文件/行 | 机制 |
| --- | --- | --- |
| DB 约束 | `schema.ts:320` | `UNIQUE INDEX idx_entries_unique ON lottery_entries(tenant_id, draw_id, identity_type, identity_value)` |
| 配置字段 | `flash-sale-config.ts` | `maxPerUser: number`(默认 1) |
| 消费逻辑 | 无 | `maxPerUser` 在后端无任何消费(joinDraw 不读取,只有 frontend form display) |

**结论**:当前的"限购"是 DB 层强制的——同一 email 无法参与同一活动两次。配置文件中的 `maxPerUser` 字段未生效。

### 改动规模

| 需求 | 改动内容 | 规模 |
| --- | --- | --- |
| **1件**(当前默认) | 无需改动 | 0 |
| **不限购** | ① 去掉 `lottery_entries` UNIQUE 约束(迁移) | 大 |
| **不限购** | ② 去掉 `payment_orders` UNIQUE(entry_id) | 中 |
| **不限购** | ③ `maxPerUser` 改为代码层校验(`SELECT COUNT(*)`) | 中 |
| **不限购** | ④ `active_participant_count` 语义改为"已购件数" | 中 |
| **不限购** | ⑤ `paid_late_needs_refund` 需适配多订单 | 中 |

**改动评估**:5-7 天,中等风险。核心是去掉 UNIQUE 约束并改为代码校验。

### 建议

- **1件**:满足需求,不修改
- **不限购**:需要变更 schema 约束(UNIQUE → 代码校验),作为独立版本规划

## 2. 批发模式分析

### 业务定位

批发模式是不限购、价格略高于秒杀的批量采购模式。它与秒杀的区别:

| 属性 | 秒杀(fash-sale-rush) | 批发(bulk-purchase) |
| --- | --- | --- |
| 库存 | 限量(stockLimit,UNIQUE 限 1 件/人) | 不限购(每人可购多件) |
| 价格 | 低价(引流) | 高于秒杀(成交) |
| 转化路径 | 免费转盘→秒杀 | 秒杀→批发(CTA 导流) |
| activity_kind | claim | claim(可新增 wholesale) |

### 技术实现(方案 A——推荐)

去掉 `lottery_entries` 的 UNIQUE 约束,改为代码层校验。批发活动配置 `maxPerUser=0`(不限购)。

**schema 迁移**:
```sql
DROP INDEX IF EXISTS idx_entries_unique;
CREATE UNIQUE INDEX IF NOT EXISTS idx_entries_unique ON lottery_entries(tenant_id, draw_id, identity_type, identity_value, created_at);
```
(注:保留 UNIQUE 但多加 `created_at` 字段使每次参与都是唯一组合)

**代码校验(joinDraw)**:
```ts
if (draw.maxPerUser > 0) {
  const exited = await db.select({ count: count() }).from(lotteryEntries).where(duplicateCheck).limit(1);
  if (exited.count >= draw.maxPerUser) return { joined: false, reason: "exceeded_max_per_user" };
}
```

### 评估

| 维度 | 评估 |
| --- | --- |
| schema 迁移 | 1 个(in place,不丢失数据) |
| 代码改动 | joinDraw + payment_orders 约束 + 新模板 |
| 前端 | 新模板 + 不限购展示 |
| 风险 | 中等(UNIQUE 约束是核心安全机制) |
| 工期 | 5-7 天 |

### 建议

1. **当前阶段不实施**。秒杀功能刚完成,优先上线验证闭环。
2. 可在 `activity_kinds` enum 中预留 `wholesale` 值,作为后续版本的基础。
3. 批发模式概念好,但需独立迭代窗口——建议在 131 之后的版本中实施。

## 3. 多次论证

### 论证 1:UNIQUE 约束的必要性

Q:是否可以简单地去掉 UNIQUE 约束?
A:UNIQUE 约束是参与去重的最后防线。若去掉,必须用代码层校验替代。joinDraw 是热路径,加 COUNT 查询会增加一次 SELECT,但只是主键扫描,可接受。

### 论证 2:批发与秒杀的关系

Q:批发是否能通过现有秒杀变种实现?
A:否。秒杀是"限量+抢",批发是"不限购+批量"。两者 DB 约束不同(UNIQUE vs 代码校验),需要独立的参与逻辑。

### 论证 3:工期与优先级

Q:这是否与当前上线需求冲突?
A:当前秒杀+支付闭环已通过审查(574 全绿)。批发是概念阶段,不能阻塞上线。建议在 131 后版本中实施。
