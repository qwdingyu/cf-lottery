## 三、🔴 高危问题（建议立即修复）

### 3.1 邮箱验证码可暴力破解 → 账号接管（测试证实 ✅）

| 项 | 内容 |
|----|------|
| 位置 | `src/routes/auth.ts:171`（`POST /verify-email` 端点）；`auth.ts:68`（`hashCode` 无盐 SHA-256） |
| 证据 | `/verify-email` 端点**没有任何限流**（对比 `/register` 有内存+DB 双层限流，`auth.ts:84/97`）。验证码 6 位数字（100 万组合）、10 分钟有效、无盐 SHA-256 存储 |
| 影响 | 验证码猜中后该端点立即置 `emailVerified=1` 并签发 7 天 JWT（`auth.ts:209`）→ **完全接管目标账号**（可登录、建租户、管理活动、领奖） |
| 验证状态 | **已测试证实**：连续猜测 30 次错误验证码无任何 429，对照组 `/register` 连续 5 次出现 429 |
| 修复建议 | ① 对 `/verify-email` 加"邮箱 + IP"双维度限流（如 10 次/15 分钟/邮箱）；② 失败次数达到上限即作废当前验证码并删除记录；③ 验证码 hash 加盐（`SHA-256(email + code + salt)` 或直接存明文对比+短时 TTL） |

### 3.2 密码存储用 HMAC-SHA256（单次迭代）+ 弱密码策略（代码确认）

| 项 | 内容 |
|----|------|
| 位置 | `src/routes/auth.ts:376`（`hashPassword`）；`:51`（`getPasswordPepper`）；`:110-114`（密码策略） |
| 证据 | 当前格式 `hmac_sha256_v1:{salt}:{hmac}`，HMAC 为快速哈希、**无迭代**；pepper 用 `PASSWORD_PEPPER || JWT_SECRET`（签名密钥与密码哈希密钥共用）；密码策略仅"8 位 + 字母 + 数字" |
| 影响 | 数据库 + pepper 泄露后可离线暴力破解（HMAC 每秒可试 10⁹ 级，8 位弱密码小时级可破）；pepper fallback 到 JWT_SECRET 进一步放大 |
| 验证状态 | 代码走读确认（格式可见）；"弱"属设计评估，无法用测试证明"弱" |
| 修复建议 | ① 去掉 pepper 对 JWT_SECRET 的 fallback，单独强制 `PASSWORD_PEPPER`；② 密码策略提升（≥12 位 + 特殊字符）；③ 评估在 Workers 上使用 PBKDF2 提高迭代（Web Crypto 原生支持，代码已有 legacy 实现）——注意免费层 10ms CPU 限制，需实测迭代数上限 |

### 3.3 平台模拟登录完全失效 + 会话固定隐患（代码确认）

| 项 | 内容 |
|----|------|
| 位置 | 写入方 `frontend/src/router/index.ts:166-168`；读取方 `frontend/src/composables/useAdminAuth.ts:26-40`；后端签发 `src/routes/platform.ts:276` |
| 证据 | 路由守卫写入 localStorage 的格式是 `{ value, expiresAt }`，而 `parseStoredToken` 只接受 `{ token, expiry }`——格式不匹配，解析后走"格式不匹配"分支直接返回 `''` → **模拟登录实际永远失效**；同时该入口对任意 JWT 不校验 `impersonated` 声明、不校验平台身份，任何人可构造 `/admin?token=<任意JWT>` 诱导点击写入会话（会话固定，修复格式后即成可利用漏洞） |
| 影响 | L3 平台运营者模拟登录功能失效；一旦格式修复，未加校验即成为会话固定攻击点 |
| 验证状态 | 代码走读确认（前后端两处格式对比）；前端逻辑无测试覆盖 |
| 修复建议 | ① 写入格式统一为 `{ token, expiry }`（`useAdminAuth.setToken` 为准）；② 模拟登录 token 必须校验 `impersonated === true` 且当前用户为活跃平台成员（后端重新验证或 JWT 声明校验） |

### 3.4 开奖一致性缺陷：失败残留后活动永久自锁（测试证实 ✅）

| 项 | 内容 |
|----|------|
| 位置 | `src/services/lottery-service.ts:1749`（CAS open→drawing）；`:1863` 起（事务内锁码+winners 写入）；`:1984`（`status=drawn` 更新在**事务外**）；`:2054`（catch 分支回滚 `open`） |
| 证据 | winners 写入与状态更新不原子。若"事务提交成功但 drawn 更新失败"→ catch 把状态回滚为 `open`，此时 winners 已存在、奖品码已锁定 |
| 影响 | 下次开奖：重新随机抽取必然可能选中已中奖者 → 插入 winner 触发 `UNIQUE(tenantId, drawId, entryId)` 冲突 → 事务回滚 → 再次回滚 open → **活动永久无法开奖**。`healDrawingState`（`:2254`）只处理 `drawing` 状态，救不了 `open` |
| 验证状态 | **已测试证实**：模拟"winners 已写入 + 状态回滚 open"后，第二次开奖必然失败（rejects），活动状态停留在 open，winners 残留 |
| 修复建议 | ① 把 winners 写入与 `status=drawn` 更新放进**同一事务**；② 或 catch 分支先检查 winners 是否存在，存在则补 `drawn` 而非回滚 `open` |

### 3.5 `/result` 端点邮箱枚举（隐私泄露，代码确认）

| 项 | 内容 |
|----|------|
| 位置 | `src/routes/public-lottery.ts:735`（`POST /draws/:slug/result`） |
| 证据 | 该端点**无需验证码、无限流**，输入任意邮箱即可探测"是否参与某活动、是否中奖"；同文件 `my-result`（`:539`）需要验证码，标准不一致 |
| 影响 | 参与者名单可被枚举，活动参与/中奖状态泄露（隐私 + 社会工程素材） |
| 验证状态 | 代码走读确认 |
| 修复建议 | 与 `my-result` 对齐：要求验证码或缩短返回粒度（仅返回"是否中奖"布尔，不返回 join/时间细节），并加 IP 限流 |

## 六、✅ 做得好的地方（保持，勿回归）

1. **租户隔离**：几乎所有查询带 `tenantId` 条件（全量核查仅 1 处漏写且不可利用）；L2/L3 RBAC 中间件每次查库校验，成员移除即时生效（`middleware/auth.ts`）。
2. **媒体上传防护最扎实**：magic bytes 校验（拒 SVG/GIF）、声明 content-type 与实际签名比对、key 正则防路径遍历、`nosniff` + ETag（`media.ts` / `media-image.ts`）。
3. **平台审计完整**：L3 所有写操作（member 增删改、impersonate、tenant 更新、webhook retry、data cleanup）均写 `platform_audit_logs` 且与业务同事务（`platform.ts`）。
4. **开奖防双发设计方向正确**：CAS `open→drawing` + `healDrawingState` 超时治愈（`lottery-service.ts:2254`），仅需补 #3.4 的边界缺口。
5. **测试基线健康**：153 个测试覆盖注册/登录/开奖/配额/RBAC/媒体，`tsc` 0 错误。
6. **细节到位**：webhook HMAC 签名、活动事件白名单、验证码过期清理、CSV 导出公式注入防护、公开页不暴露内部 ID。
