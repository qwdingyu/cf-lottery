# 订单超时 / 产品导流 / 邀请流程 闭环分析（2026-08-20）

## 一、订单超时释放（cron）

### 配置层级

| 配置项 | scope | 默认 | 范围 | 配置方 |
|--------|-------|------|------|--------|
| `payment_order_timeout_minutes` | `admin`（L2） | 30 分钟 | 1-120 | L2 租户管理员（系统配置页）|

**配置位置**：`src/lib/system-config-definitions.json:555`
**入口**：`src/index.ts:90-136`（cron 维护任务 → 逐租户调用 `expireOverdueOrders`）
**定时器**：VPS systemd timer，每 5 分钟触发

### 释放链路

```
Cron 每 5 分钟 → expireOverdueOrders(db, tenantId) →
  ① 查询 pending 订单（createdAt < datetime('now', -N minutes)）
  ② 订单 → expired（status='expired'）
  ③ 支付尝试 → expired（attempt 状态）
  ④ entry 处理（三路分支）：
     a) 有 PAID/FULFILLMENT_FAILED 订单 → entry 恢复为 paid（保留有效履约）
     b) 有其他有效订单（非超时非终态）→ entry 保持 pending（不释放）
     c) 无其他有效订单 → entry 释放为 expired（可重新参与）
  ⑤ 超时订单的卡密 → releaseReservedPrizeCodes（reserved→available）
  ⑥ 名额 → decrementActiveFlashSaleCount（activeParticipantCount 扣减）
  ⑦ 残留预占（有 reserved entry 但无订单）→ 直接 expired
```

**关键文件**：`src/services/payment/payment-service.ts:155-355`
**生产验证**：活动 `8c5515ed` 的订单 `644f4126`（13:27 创建，30 分钟超时）已正常 expired 释放

### 闭环确认

✅ 订单超时 → 释放卡密（回池可复用） → 释放名额（activeParticipantCount 递减） → entry 可重新参与 → **已形成完整闭环**

## 二、产品导流（活动 → 导流链接）

### 数据流

```
创建活动（admin 表单）→ 配置 productLink（url/title/price/imageUrl）
  → 存入 promotionConfig（或 productLink 字段）
  → 公开端展示
```

### 展示位置

**1. 结果弹窗导流卡（中奖/未中奖）**
- 文件：`frontend/src/views/LotteryView.vue:1070-1110`
- 函数：`getResultCta(draw, mode)` → 读取 `promotionConfig.cta.after_win` / `promotionConfig.cta.after_loss`
- 展示：`<a :href="url" target="_blank" rel="noopener noreferrer">` 按钮跳转
- 条件：仅 lottery 类型（`myResultFamily === 'lottery'`）

**2. 店铺 API 商品卡**
- 文件：`src/routes/public-lottery-helpers.ts:235-270`
- 函数：`productFromPublicConfig(draw)` → 读取 `flashSale.imageUrl > productLink?.imageUrl > destination?.imageUrl`
- 用途：店铺页 `/shop/:slug` 展示秒杀活动的商品卡片

**3. 秒杀商品卡（活动页）**
- 文件：`frontend/src/views/lottery/flash-sale-merchandising.ts:30-60`
- 优先级：`flashSale.imageUrl > productLink?.imageUrl > prizes[].imageUrl`
- 注意：docs/245 已移除 productLink 回退，秒杀商品图片独立于导流配置

### 闭环缺口

| 环节 | 状态 | 说明 |
|------|------|------|
| 导流配置（创建表单） | ✅ | `adminProductLink` 字段 |
| 导流卡展示（结果弹窗） | ✅ | 中奖/未中奖后展示 |
| 点击跳转 | ✅ | `target="_blank"` 跳转 |
| **转化追踪** | ❌ | 无点击/购买统计，`activityEvents` 无 `click_traffic` 事件 |
| **点击统计** | ❌ | 无曝光/点击率数据 |
| **秒杀导流** | ⚠️ | 秒杀商品图已与 productLink 解耦，但秒杀结果区无导流卡 |

### 最优方案

在 `activityEvents` 表增加 `click_traffic` 事件类型，记录导流点击：

```ts
// 用户点击导流卡时写入
await db.insert(activityEvents).values({
  drawId, entryId, tenantId,
  eventType: "click_traffic",
  refCode: ctaUrl,  // 导流目标 URL
  createdAt: now,
});
```

## 三、邀请流程（裂变）

### 数据流

```
活动创建 → 配置 viral.enabled（不限于 lottery）
  → 用户参与 → 生成专属邀请链接（含 refCode）
  → 分享给好友 → 好友点击参与（带 refCode）
  → 邀请归因 → 奖励发放
  → 排行榜展示
```

### 实现细节

**1. ViralLeaderboard 渲染条件**
- 文件：`frontend/src/views/LotteryView.vue:456`
- 条件：`getDrawViral(draw)?.enabled` → 读取 `promotionConfig.viral.enabled`
- **不限于 lottery 类型**（任何 activityKind 都可启用）

**2. 邀请归因**
- 文件：`src/services/lottery/participation.ts:480-530`
- 函数：`recordAttributedJoin(tx, { ... refCode })`
- 记录：`shareRecords`（聚合计数）+ `activityEvents`（明细事件）
- 归因方式：`refCode` 在分享链接中传递，参与时写入 entry

**3. 邀请奖励机制**
- 文件：`src/services/lottery/spin-quota.ts:91-145`
- 函数：`computeViralSpinGrant({ maxSpinsPerEntry, extraSpinsPerInvite, maxExtraSpins, ... })`
- **限 lottery**：因为奖励是"额外抽奖次数"（spins），对 flash_sale/claim/ signup_chain 无意义
- 阶梯奖励：`evaluateReferralMilestones`（邀请人数达标时一次性发放）

**4. 邀请排行榜**
- 组件：`frontend/src/components/ViralLeaderboard.vue`
- 展示：邀请人数排行，不限于 lottery（由 `viral.enabled` 控制）

### 闭环缺口

| 环节 | 状态 | 说明 |
|------|------|------|
| 邀请链接生成 | ✅ | 参与后生成 |
| 好友归因 | ✅ | `refCode` + `recordAttributedJoin` |
| **奖励机制** | ⚠️ | **仅 lottery**：`computeViralSpinGrant` 依赖 spins 机制 |
| 排行榜 | ✅ | `ViralLeaderboard` 不限 lottery |
| **秒杀/领券邀请** | ❌ | 无奖励出口（加权票对秒杀无意义） |

### 最优方案

扩展奖励机制，按 `activityKind` 分支：

| 活动类型 | 当前奖励 | 建议奖励 |
|---------|---------|---------|
| lottery | 额外加权票/次数 | 保留 |
| flash_sale | 无 | 邀请送优惠券/折扣码 |
| claim | 无 | 邀请送额外领取次数 |
| signup_chain | 无 | 邀请送优先名额 |

**实现思路**：`computeViralSpinGrant` 改为按 `activityKind` 分支，flash_sale/claim 时调用新的奖励发放函数（如 `grantViralDiscount`），而非 spins 逻辑。
