## 一、评审结论

**交互设计 85 分，视觉呈现 55 分。** 用户感知的"low"不来自流程，而来自三笔具体的债：

| 债 | 表现 | 影响 |
|---|---|---|
| 素材债 | 游戏组件全部用 emoji（🎁💎🏆❓✨）当奖品 | 奖品像假的 → 平台不可信 → 转化率杀手 |

## 三、关键设计决策

### 1. 品牌色为什么是琥珀金而不是蓝
- 琥珀金（`#f59e0b`/`#fbbf24`）符合"抽奖/好运"品类心智，且在暗色底上对比度好
- 全局 `btn-primary` 的蓝色（`--tg-btn: #60a5fa`）是 Telegram 体系色，C 端主转化按钮需要更强的行动号召力
- **分工红线**：`--brand*` 只用于 C 端（landing/lottery/games），`--admin-accent` 只用于 `/admin` 后台。base.css 里有注释明确这条边界，防止后台色再次泄漏到 C 端
- 秒杀的玫红（`#e11d48`/`--shop-sale-*`）作为**品类语义色**保留——促销红是全球电商共识，不与品牌金统一

### 2. 奖品图为什么只改 SlotGame 和 WheelGame，不动 CardGame/GridGame
- **SlotGame/WheelGame** 的 reel/扇面直接渲染 `prizes.name`（真实奖品名），emoji 是"奖品占位符"，必须换成真图
- **CardGame/GridGame** 的 🎁/❓ 是**中性氛围符号**（docs/055a 明确"不宣称中奖奖品"），卡背翻面≠中奖。把它们改成奖品图反而违反诚实设计——用户会误读"翻到哪张=中哪个"
- 数据链路：`shellPrizeItems[i].imageUrl` 与 `shellLabels[i]` 索引一一对应（prize-shell-display.ts 的索引对齐不变量，docs/128），游戏组件按索引取图天然安全

### 3. WheelGame canvas 图片加载策略
- `watch(props.prizes)` 一次性预加载全部图片到 `prizeImages` 缓存
- 单张就绪即重绘（扇面 ≤8 个，重绘成本可忽略），避免等待全部加载导致的长时间无图
- 加载失败 `onerror` 置 null，该扇面回退为纯文字，不影响其他扇面

### 4. 旧体系删除前做了什么验证
- 全文 grep 确认 `draw-card`/`chip-*`/`page-header`/`record-row`/`prize-showcase` 等类在模板中零引用
- 发现 `vote-option`/`survey-field`/`checkbox-stack` **只在旧体系里定义**且 LotteryView 模板在用 → 单独补回这 4 个类的定义，避免误删
- 删除后 `vue-tsc` + 全量 vitest 通过，确认无运行时引用
