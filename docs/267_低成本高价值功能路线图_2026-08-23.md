## 二、功能推荐（按 高频使用 × 痛点 × 低成本 × 高价值 排序）

### 🥇 P0：每日签到（checkin）— 1-2 天

**高频使用**：日活留存的核心手段，用户每天回来点一下
**痛点**：目前 checkin 活动类型已注册但无独立逻辑，用户无法真正"签到"
**低成本**：~80% 基础设施已就绪

**已有的基础设施**：
- `ACTIVITY_KINDS` 已包含 `"checkin"`（`admin-lottery.ts:67`）
- GameRegistry 已注册 `checkin → SubmitGame` 映射（`GameRegistry.ts`）
- `isCheckinSignedToday()` 前端函数已实现（`joined-session.ts:264`），测试覆盖（`joined-session.test.ts:124`）
- `joinDraw` 每次参与写入 `lottery_entries` 表，`joinedAt` 字段记录参与时间
- 里程碑引擎可复用（连续签到 N 天触发奖励）

**需要新增**：
- 后端：签到 streak 计算函数（查 joinedAt 历史，计算连续天数）— ~50 行
- 前端：签到日历组件（月视图 + 签到标记 + streak 高亮）— 复用 Canvas 基础设施
- 奖励配置：连续签到 3/7/14/30 天自动发奖 — 复用 `referralRewardDefs` 里程碑引擎

**风险**：低。所有数据写入路径已存在，只需增加计算和展示层。

---

### 🥇 P0：限量领取（claim）— 1-2 天

**高频使用**：资料领取/优惠券发放/试用申请，B2B 场景高频
**痛点**：claim 活动类型已注册但无独立逻辑
**低成本**：~90% 基础设施已就绪

**已有的基础设施**：
- `ACTIVITY_KINDS` 已包含 `"claim"`（`admin-lottery.ts:67`）
- GameRegistry 已注册 `reveal → RevealGame` 映射（`GameRegistry.ts`）
- `prizeCodes` 表 + CAS 原子扣减已实现（`schema.ts:283`，`spin-execution.ts` 中的子查询 UPDATE）
- `capacityClause` 容量控制已实现（`participation.ts:366`）
- `RevealGame.vue` 已有揭晓/领取交互

**需要新增**：
- 配置化：管理员设置总量（maxParticipants）+ 每人限领（maxPerUser）— 已有字段
- 前端：领取页面微调（RevealGame 已有揭晓交互，可能只需文案调整）
- 后端：几乎不用改，`joinDraw` 已支持容量控制

**风险**：极低。几乎纯配置化，无需写新代码。

---

### 🥇 P0：投票/问卷（vote/survey）— 2-3 天

**高频使用**：用户互动 + 数据收集，运营调研必备
**痛点**：vote/survey 已注册但无统计后端，用户填了但运营看不到结果
**低成本**：~70% 基础设施已就绪

**已有的基础设施**：
- `ACTIVITY_KINDS` 已包含 `"vote"` 和 `"survey"`（`admin-lottery.ts:67`）
- GameRegistry 已注册 `ballot → FormGame` 和 `form → FormGame`（`GameRegistry.ts`）
- `FormGame.vue` 已有表单提交交互（字段渲染 + 提交）
- `activityConfig.options` 已支持自定义选项（`LotteryView.vue` 中渲染选项列表）
- `activityConfig.fields` 已支持自定义字段

**需要新增**：
- 后端：投票/问卷结果统计 API（GROUP BY 选项，COUNT）— ~80 行
- 前端：结果可视化（饼图/柱状图）— 复用 canvas-utils
- 管理端：结果查看面板（AdminLotteryView 新增 Tab）

**风险**：低。表单交互已建好，缺统计和展示。

---

### 🥈 P1：管理后台数据看板增强 — 3-5 天

**高频使用**：运营每天都要看数据
**痛点**：当前 Dashboard 数据维度单一，缺少参与趋势和转化漏斗
**低成本**：~60% 数据已存在于数据库

**已有的基础设施**：
- `lottery_entries` 表有 `createdAt`（参与时间）
- `lottery_spins` 表有 `createdAt`（抽奖时间）+ `reason`（来源）
- `activityEvents` 表有 `eventType` + `createdAt`（事件流）
- `shareRecords` 表有 `joinedCount`（裂变数据）
- `auditLogs` 表有 `action` + `createdAt`（操作日志）

**需要新增**：
- 参与趋势 API（按日/周/月 GROUP BY createdAt）— ~100 行
- 转化漏斗 API（访问→参与→中奖→领奖）— ~80 行
- 裂变效果面板（邀请率、病毒系数）— 复用 aggregateViralInviteCounts
- spins_log 查询 API + 展示页面（闭环之前发现的缺口）

**风险**：低。纯读操作，不影响业务逻辑。

---

### 🥈 P1：排行榜奖品配置增强 — 2-3 天

**高频使用**：排行榜是裂变的核心激励
**痛点**：当前排行榜奖励只支持 bonus_spin 类型，无法按名次发不同奖品
**低成本**：~50% 配置结构已存在

**已有的基础设施**：
- `leaderboardRewards` 配置已在 `promotionConfig.viral` 中（`viral-weight.ts`）
- `normalizeLeaderboardRewards` 已实现归一化（`leaderboard-rewards.ts:28`）
- `grantLeaderboardRewards` 已实现发放（`leaderboard-rewards.ts:95`）
- `rewardType` 当前仅支持 `"bonus_spin"`

**需要新增**：
- 扩展 `rewardType` 支持 `"bonus_coupon"` — 修改 `LeaderboardRewardConfig` 类型 + 归一化逻辑
- 管理端 UI：排行榜奖品配置表单（按名次行配置）— 复用 AdminLotteryView 表单模式
- 发放逻辑：`grantLeaderboardRewards` 内部根据 rewardType 分发到 `grantBonusSpin` 或 `grantBonusCoupon`

**风险**：低。已有完整的发放框架，只需增加一个出口分支。

---

### 🥈 P1：签到日历可视化 — 3 天

**高频使用**：签到体验的核心差异化
**痛点**：签到只是"点一下"，缺少视觉反馈和连续天数激励
**低成本**：~40% 基础设施已就绪（签到数据 + Canvas 工具）

**已有的基础设施**：
- `isCheckinSignedToday()` 前端函数（`joined-session.ts:264`）
- `lottery_entries.joinedAt` 记录每次参与时间
- `canvas-utils.ts` 绘图基础设施

**需要新增**：
- 签到日历组件（月视图 + 签到标记 + 连续天数高亮）— ~200 行 Vue 组件
- 签到 streak API（查历史 joinedAt，计算连续天数）— ~50 行
- 前端 streak 展示（连续签到 7 天徽章等）

**风险**：低。纯前端展示 + 简单后端计算。

---

### 🥉 P2：可嵌入 Widget — 5-7 天

**高价值**：第三方网站嵌入活动，平台分发能力质变
**已有的基础设施**：
- 公开路由 `/lottery/:slug` 已存在
- CORS 已配置
- 前端组件已模块化（GameRegistry + 各游戏组件）

**需要新增**：
- Web Component 封装（`<cf-activity>` 自定义元素）
- 嵌入代码生成器（管理端一键生成 `<script>` 标签）
- 跨域通信（postMessage API）

---

### 🥉 P2：活动模板市场 — 5-7 天

**高价值**：一键创建活动，降低使用门槛
**已有的基础设施**：
- 模板系统已存在（`experienceType` + `promotionConfig` 组合）
- `ACTIVITY_KINDS` 9 种类型 + 13 种体验 = 117 种理论组合

**需要新增**：
- 模板库 UI（预设配置 + 预览）
- 一键克隆（复制 promotionConfig + experienceType）
- 模板分类（营销/互动/调研）

## 四、技术风险评估

| 风险 | 等级 | 说明 |
|------|------|------|
| 签到并发（同一用户同时签到两次） | 低 | `joinDraw` 已有 UNIQUE 约束兜底 |
| 领取超卖（限量发放超发） | 低 | `prizeCodes` CAS + `capacityClause` 双重保护 |
| 投票刷票（同一用户多次投票） | 低 | `maxPerUser` + UNIQUE 约束已实现 |
| 看板查询性能（大数据量 GROUP BY） | 中 | 需要索引优化，建议加 `createdAt` 复合索引 |
| Widget 跨域安全 | 中 | 需要 CSP 策略 + 输入净化 |

## 五、与现有功能的闭环关系

```
签到（P0）→ 连续签到奖励 → 复用里程碑引擎 → /my-rewards 展示
领取（P0）→ 限量发放 → 复用 prizeCodes CAS → 管理端查看
投票（P0）→ 结果统计 → 新增统计 API → 管理端结果面板
看板（P1）→ 数据驱动决策 → 复用已有表 → 前端图表
排行榜增强（P1）→ 按名次发奖 → 复用 grantLeaderboardRewards → /my-rewards 展示
签到日历（P1）→ 签到体验 → 复用签到数据 → 前端日历组件
```

每个功能都不是孤立的，而是形成"参与→奖励→展示→运营"的完整闭环。
