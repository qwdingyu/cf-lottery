## 二、两边能力对照（代码事实，非臆造）

### 2.1 cf-shop「用户级推广码」（docs/054、056、059）

| 维度 | 事实 |
| --- | --- |
| 触发 | **支付成功** `markPaidAndIssue` 后自动一邮一码 |
| 码生命周期 | 跨订单、跨商品；`referral_codes.owner_contact` UNIQUE |
| 激励 | 可选 **余额返佣**（`referral_reward_enabled`，默认关） |
| 归因对象 | **订单成交**（金额、卡密交付） |
| 前台 | `/refer` + member OTP/JWT；复制商品链 `?ref=` |
| 依赖 | 订单、余额账本、发卡、支付闭环 |

schema 层：`referral_codes`、`referral_events`、`referral_rewards`、余额 type=`referral_reward`。

### 2.2 cf-lottery 已有「参与级裂变」（docs/041、schema）

| 维度 | 事实 |
| --- | --- |
| 触发 | **参与成功** → `POST .../share` 生成 `share_records` |
| 码生命周期 | **绑定某次 entry + 某活动**；`shareCode` 全局 unique |
| 激励 | 同活动 **额外参与次数 / 开奖加权**（`promotionConfig.viral`） |
| 归因对象 | **点击 + 归因参与**（`joinedCount`）；可选 `external_conversions` 回传成交 |
| 前台 | 参与成功弹窗裂变卡；中奖后分享（未终态） |
| 依赖 | 无订单、无余额、无「全员账户」 |

schema 明确：**不包含** products、orders、cards、**referral**、voucher、storefront（`src/db/schema.ts` 文件头）。

### 2.3 一句话差异

```text
shop 推广码 = 用户资产（成交后）→ 带货成交 → 可选分钱
lottery 分享码 = 活动会话资产（参与后）→ 拉新参与 → 同场次数/权重
```

二者解决的漏斗终点不同：**成交金额 vs 活动参与**。

## 三、拉新 / 推广 / 促活：是否「需要」shop 式推广码？

### 3.1 拉新（更多人第一次进来）

| 手段 | lottery 现状 | 是否缺 shop 码 |
| --- | --- | --- |
| 专属链接 `?ref=` | ✅ share / ref 归因 | 不缺 |
| 参与后立刻可分享 | ✅ GameResultModal | 不缺 |
| 中奖背书分享 | ✅ shareYourLuck（未终态） | 不缺 |
| 跨活动「我的永久推广主页」 | ❌ 无 | **可选产品**，非主路径刚需 |

活动引擎的拉新主杠杆是 **单场活动链接半径**，不是「注册成码主再铺货」。  
shop 码的价值建立在 **复购与商品货架** 上；lottery 默认无货架。

### 3.2 推广（运营放大）

| 手段 | lottery 现状 | 说明 |
| --- | --- | --- |
| 活动级 viral 配置 | ✅ 次数/上限/排行榜开关 | 运营可控 |
| 导流外链 after_win/loss | ✅ promotionConfig CTA | 导到 shop/表单/社群 |
| 外部成交回传 | ✅ external_conversions + refCode | **不**内嵌订单 |
| 排行榜 UI | ⚠️ API 有、组件未挂载 | 应补齐自家能力，不是抄 referral |

### 3.3 促活（让人再来 / 再参与）

| shop 促活逻辑 | lottery 是否同构 |
| --- | --- |
| 余额可花、再下单 | 无余额账户 → **不同构** |
| 佣金流水驱动回访 `/refer` | 无分佣 → 抄来是空壳 |
| 多商品持续分销 | 活动有结束态；drawn 后应停邀请（docs/103） |

lottery 促活应对齐：

- 同场：额外次数、候补转正通知、查结果回访  
- 跨场：租户品牌下 **新活动触达**（邮件/OG/运营再开一场），不是「永久分销码」

### 3.4 若强行集成 shop 推广码，会引入什么？

1. **订单/余额/支付** 或与 shop 的跨系统 SSO + 结算对账  
2. **羊毛与自邀请**：无成交锚点时，「注册即码」极易刷  
3. **与现有 share_records 双码体系**：运营与用户都困惑（entry 码 vs 用户码）  
4. **违背抽取边界**：schema 已刻意剔除 referral  

成本远高于「多一个按钮」。

## 四、判定（产品结论）

| 问题 | 结论 |
| --- | --- |
| **现在有没有业务必要集成 cf-shop 用户级推广码？** | **没有。** |
| 理由 | 拉新/推广主路径已被 **活动级 share + viral + 外链导流 + 外部转化回传** 覆盖；shop 码服务的是 **成交分佣**，lottery 主 KPI 是 **参与与规则结果**。 |
| 何时才值得重新评估？ | 同时满足：① 租户要 **跨多场活动、跨月** 的固定码主身份；② 有清晰 **结算**（余额/提现/对账到 shop 订单）；③ 现有 viral 在真实数据上证明「次数激励不够、需要现金激励」。 |
| 近期更该做的增长事 | ① 挂载或砍掉 `ViralLeaderboard`（闭环自家配置）；② 强化 after_win 导流到 shop 的 `?ref=` **由 shop 侧归因**；③ 外部转化 API 运营手册；④ 勿在 drawn 后推邀请。 |

### 推荐协作方式（集成边界）

```text
✅ 推荐：lottery 活动页 CTA → shop 商品 URL（可带 UTM / shop 自己的 ref）
         shop 成交后用 shop 的 referral；lottery 用 external_conversions 回传展示
❌ 不推荐：在 lottery 内复制 referral_codes + 余额返佣
❌ 不推荐：参与即发「全员永久推广码」而无成交锚点
```
