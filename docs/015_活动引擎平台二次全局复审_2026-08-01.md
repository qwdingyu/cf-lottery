# cf-lottery 活动引擎平台二次全局复审

> 文档编号：015  
> 日期：2026-08-01  
> 复审对象：`009_导流模式实现方案_2026-08-01.md`、`010_前端体验升级方案_2026-08-01.md`、`012_009与010导流与前端体验综合专家评审_2026-08-01.md`、`013_活动引擎平台全局设计_2026-08-01.md`  
> 结论：cf-lottery 应按“多租户活动引擎 SaaS”设计，而不是按“抽奖工具”设计

## 一、结论先行

1. **抽奖只是首个入口玩法，不是产品本体。**  
   产品本体应是一个可白标、可嵌入、可扩展的活动引擎。

2. **接龙和抽奖属于同一类平台能力。**  
   它们共享活动创建、资格校验、容量控制、导流、通知、导出、审计、统计等骨架，只是结果语义不同。

3. **不要让“玩法外壳”反向绑死后端。**  
   转盘、老虎机、刮刮卡、翻牌只是 `experience_type`，不能决定资格、结果和商业规则。

4. **后端应先冻结稳定抽象，再扩展玩法。**  
   后续新增模式应尽量只改配置和 outcome 解释，不要再为每种玩法新造一套主流程。

## 二、当前仓库事实

基于当前代码与已有文档，平台抽象已经开始正确收敛：

- `lottery_draws` 已有 `activity_kind`、`participation_mode`、`experience_type`、`result_mode`、`policy_version`、`promotion_config`。
- `productLink` / `promotionConfig` 已覆盖轻量导流，不需要先建商品系统。
- 前端游戏注册表已从“资格模式决定游戏”转向“体验类型决定展示”。
- 这说明平台已经从“单一抽奖页”走向“活动引擎骨架”，方向正确。

但仍有一个关键风险：

- 现有 `lottery_winners` 仍然偏“抽奖赢家”语义。
- 如果后续接龙、预约、候补、审核、投票都各自再长一套表，平台会重新碎片化。

因此，下一步应该补的是**统一 outcome / assignment 层**，而不是继续把抽奖语义加厚。

## 三、平台顶层抽象

### 3.1 建议冻结的稳定维度

| 维度 | 含义 | 建议值示例 |
|---|---|---|
| `activity_kind` | 活动业务类型 | `lottery` `signup_chain` `reservation` `vote` `survey` `checkin` `claim` `approval` `assignment` `waitlist` |
| `participation_mode` | 谁能参加、怎么验证 | `open` `roster` `password` `invite_code` `unique_code` `approval` `external_check` |
| `experience_type` | 用户看到什么交互 | `submit` `wheel` `slot` `scratch` `card` `list` `calendar` `queue` `reveal` |
| `result_mode` | 结果什么时候、如何产生 | `manual` `scheduled` `instant` `ordered_assignment` |
| `allocation_policy` | 容量和顺序如何处理 | `fifo` `priority` `approval` `capacity` `waitlist` |
| `policy_version` | 规则版本 | `1`, `2`, `3` ... |
| `promotion_config` | 导流与外链配置 | 版本化 JSON |

### 3.2 设计原则

- `activity_kind` 只描述业务语义，不描述页面。
- `participation_mode` 只描述资格，不描述玩法外观。
- `experience_type` 只描述前端皮肤，不决定最终结果。
- `result_mode` 只描述结果产生方式，不决定是否导流。
- `promotion_config` 只管导流，不进入商品、库存、订单域。

## 四、接龙是否属于同类

结论：**属于，而且应该尽早纳入核心。**

### 4.1 为什么同类

接龙和抽奖共用的能力很高：

- 活动创建与复制。
- 开始/结束时间。
- 名单、密码、邀请码、公开入口。
- 容量控制和重复提交控制。
- 导流展示。
- 通知和提醒。
- 导出和审计。
- 多租户隔离和权限控制。

### 4.2 核心差异

- 抽奖的结果是随机分配。
- 接龙的结果是顺序占位、规则占位、或容量占位。

所以接龙更适合建模为：

- `activity_kind = signup_chain` 或 `reservation`
- `result_mode = ordered_assignment`
- `allocation_policy = fifo | priority | approval | capacity | waitlist`

### 4.3 接龙最常见的业务落点

- 报名接龙。
- 名额接龙。
- 课程/讲座预约。
- 社群福利排队。
- 内测资格占位。
- 现场席位预订。
- 资料收集接龙。

## 五、哪些玩法应纳入平台核心

下面按“低成本、高价值、和当前架构高度复用”排序。

### 5.1 P0：应尽快纳入核心

| 玩法 | 本质 | 为什么适合 |
|---|---|---|
| 抽奖 | 随机分配结果 | 当前已验证，最容易起量 |
| 接龙 / 报名接龙 | 顺序占位 | 与抽奖共享骨架，业务频率高 |
| 预约 / 名额预约 | 时间 + 容量控制 | SaaS 客户很常见，复用性强 |
| 投票 / 评选 | 去重 + 统计 | 导流和传播都容易做 |
| 问卷 / 调研 | 表单 + 统计 | 成本低，适合运营日常使用 |
| 签到 / 打卡 | 重复控制 + 激励 | 适合活动留存和复访 |
| 领券 / 领取资料 | 资格 + 发放 | 转化闭环清晰 |
| 审核 / 白名单 | 人工确认资格 | 适合内测、社群、品牌活动 |
| 候补 / 排队 | 容量耗尽后的补位 | 和预约、接龙天然连通 |
| 抽签分组 / 分班 | 规则分配 | 和抽奖共享 outcome 机制 |

### 5.2 P1：建议补充，但不要喧宾夺主

| 玩法 | 说明 | 风险点 |
|---|---|---|
| 答题 / 测验 | 正确率或分数驱动结果 | 需要题库和判分规则 |
| 任务型活动 | 完成任务后解锁资格或奖励 | 容易滑向复杂营销系统 |
| 邀请裂变 | 邀请带来额外资格或次数 | 反作弊和风控要求高 |
| 排行榜 / 冲榜 | 提升传播和留存 | 容易把产品拉向游戏社区 |
| 公示名单 | 增强透明度 | 需要隐私和撤回策略 |
| 资料领取 / 试用申请 | 以领取代替购买 | 很适合轻量 SaaS 获客 |
| 资格申请 / 内测报名 | 审核后放行 | 适合 B 端产品和品牌活动 |

### 5.3 适合做成“体验皮肤”的交互

这些不是 `activity_kind`，只是外层视觉和动效：

- 转盘。
- 老虎机。
- 刮刮卡。
- 翻牌。
- 开箱 / 盲盒。
- 队列列表。
- 日历选择。
- 卡片揭晓。
- 卷轴揭示。

原则只有一条：**皮肤负责好玩，不负责决定结果。**

## 六、哪些玩法不应进入核心

以下能力应作为外部集成或后续独立域，不要塞进活动核：

- 支付。
- 订单。
- 库存。
- SKU。
- 发货。
- 售后。
- 广告交易市场。
- 内容社区。
- 复杂评论系统。
- 直播互动。

原因很简单：这些域会把活动引擎拖进重电商/重内容系统，后续很难保持轻量和白标能力。

## 七、推荐的统一后端骨架

### 7.1 建议模块

1. **tenant**  
   租户、成员、角色、配额、品牌、风控。

2. **activity**  
   活动主表，承载规则版本、时间窗口、状态、类型、可见性。

3. **participant**  
   参与者身份、资格、提交记录、重复参与控制。

4. **outcome / assignment**  
   统一承载抽奖结果、接龙占位、预约确认、投票结果、审核通过等。

5. **promotion**  
   导流配置、展示位置、落地页、追踪参数。

6. **notification**  
   邮件、短信、站内信、Webhook。

7. **audit**  
   操作日志、规则变更、开奖结果、人工干预。

8. **event**  
   曝光、点击、分享、导出、异常事件。

### 7.2 最重要的关系

```text
tenant 1 -> N activity
activity 1 -> N participant
activity 1 -> N outcome
activity 1 -> N notification
activity 1 -> N event
activity 1 -> N audit
```

如果后面新增玩法，优先让它们落到这组关系里，而不是单独再开一套业务表。

## 八、简单但可持续的 SaaS 运营后台

“简单”不等于只有活动 CRUD。运营后台至少要能让租户完成创建、发布、观察、复盘和复用。

### 8.1 租户侧后台

建议最小闭环包含：

- 活动列表、搜索、状态筛选、复制活动。
- 活动创建向导和规则校验。
- 参与记录、结果记录、导出。
- 奖品/领取配置，但不扩展成商品库存系统。
- 导流配置、二维码、公开链接、渠道参数。
- 通知记录和失败重试。
- 活动事件和基础漏斗数据。
- 操作审计和人工处理记录。
- 成员、角色、租户级权限。

### 8.2 平台运营后台

平台管理员需要独立于租户管理员，至少具备：

- 租户列表、状态、套餐、配额。
- 活动数量、参与量、异常率、通知失败率。
- 黑名单、限流、风险事件。
- 模板和功能开关。
- 系统配置、邮件配置、Webhook 配置。
- 工单或人工干预入口。

平台后台不应该直接绕过租户权限修改业务数据。人工处理也要写入审计。

### 8.3 套餐和配额

第一版不需要复杂计费引擎，但应提前保留这些概念：

- `plan`：套餐。
- `quota`：活动数、参与人数、成员数、导出次数、Webhook 次数等配额。
- `usage`：按租户、活动和时间记录用量。
- `feature_flag`：按套餐或租户打开能力。

这样后续增加付费能力时，可以先做“限制和升级”，不需要重写租户模型。

## 九、导流、增长与变现闭环

### 9.1 推荐的增长闭环

```text
创建活动
  -> 分享公开链接 / 二维码
  -> 用户参与
  -> 结果或确认页
  -> 展示品牌、商品、资料或下一活动
  -> 记录曝光、点击、分享、回访
  -> 租户复制模板继续运营
```

导流应该是活动完成后的自然下一步，不应该在用户完成核心任务前强制跳转。

### 9.2 归因要分三层

1. **来源标记**：UTM 或等价参数，回答“用户从哪来”。
2. **平台事件**：曝光、点击、分享、参与、完成，回答“平台发生了什么”。
3. **外部转化**：订单、核销、注册、付费，必须由目标系统回传或通过明确集成获得。

没有外部回传时，平台只能展示访问和点击，不能把它们命名为成交、核销或 GMV。

### 9.3 推荐的变现顺序

优先销售平台能力，而不是把平台伪装成广告交易平台：

- 免费版：限制活动数和参与量，用于获客。
- 专业版：更多活动、品牌配置、数据导出、通知能力。
- 团队版：成员、角色、审批、模板、审计、批量运营。
- 企业版：白标、自定义域名、API、Webhook、私有化支持。
- 服务收入：实施、迁移、定制集成、运营支持。

不建议一开始依赖 CPM、CPA、CPS 或“平台抽成”。这些模式需要规模、反作弊、合同和外部转化数据，不能靠一个 UTM 参数成立。

### 9.4 裂变必须是可选能力

邀请、分享奖励、额外次数都可能促进传播，但必须同时具备：

- 明确的奖励规则。
- 有效邀请定义。
- 重复设备、身份、IP 和异常行为检测。
- 奖励发放状态。
- 撤销和人工复核。

不能把“分享按钮被点击”直接当成有效邀请，也不能把分享奖励写死在抽奖主流程中。

## 十、推荐实施顺序

### 第 1 阶段：冻结平台骨架

- 冻结活动核心抽象。
- 保持抽奖稳定。
- 完成租户、成员、角色、配额、审计、活动生命周期。
- 让接龙和预约共享同一套创建、参与、结果、通知、导流流程。

### 第 2 阶段：补齐高复用玩法

- 补问卷、投票、签到、候补、审核、领券、抽签分组。
- 统一导出、审计、统计。

### 第 3 阶段：形成 SaaS 能力

- 上模板市场、白标、API、Webhook、运营报表。
- 做多租户运营后台的标准化能力。
- 增加套餐、配额、用量和功能开关。

### 第 4 阶段：外部域集成

- 只在确有业务需要时，再考虑支付、订单、库存、广告等外部域集成。

## 十一、对 009 / 010 的最终裁决

### 009 导流

方向对，但要继续收敛为“版本化导流配置”，不要演化成商品系统。

### 010 前端体验

方向对，但要明确：游戏只是体验层，不能把参与资格和游戏样式捆成一体。

### 当前最重要的补洞

1. 接龙不是边缘玩法，应该纳入核心。
2. 活动结果不能只围绕“中奖”建模。
3. 玩法皮肤和业务语义必须彻底分离。
4. 导流要保留，但不要反客为主。

## 十二、建议直接纳入下一轮的玩法清单

如果只列一份“应该优先做”的名单，我建议是：

- 抽奖。
- 接龙 / 报名接龙。
- 预约 / 名额预约。
- 投票 / 评选。
- 问卷 / 调研。
- 签到 / 打卡。
- 候补 / 排队。
- 审核 / 白名单。
- 领券 / 领取资料。
- 抽签分组 / 分班。
- 答题 / 测验。
- 资格申请 / 内测报名。

这组玩法的共同点是：

- 低成本。
- 复用同一后端骨架。
- 很容易进入 SaaS 客户的日常运营。
- 不需要先碰支付、库存、售后和社区。

## 十三、结论

cf-lottery 的正确定位不是“抽奖 SaaS”，而是“活动引擎 SaaS”。

抽奖和接龙只是第一批高复用玩法。  
真正要冻结的是：多租户、活动语义、资格语义、结果语义、导流配置、通知、审计、统计。  
只要这些层稳定，后续再加玩法时就不需要推翻重来。
