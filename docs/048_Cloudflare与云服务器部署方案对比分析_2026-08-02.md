# 048 Cloudflare 与云服务器部署方案对比分析

日期：2026-08-02
状态：评审稿（暂不改代码）
相关文件：`src/index.ts`、`src/bindings.ts`、`src/routes/media.ts`、`wrangler.jsonc`、`local-deploy.sh`、`package.json`

## 一、背景

测试过程中发现 Cloudflare Free 层存在硬性限制。需要评估：
1. 改为云服务器部署，代码需要多大改动？
2. 是否可能 Cloudflare + 服务器双平台兼容？
3. 最优方案是什么？

## 二、Cloudflare Free 硬性限制盘点

| 维度 | 免费额度 | 对当前项目的影响 |
|------|---------|-----------------|
| Workers 请求数 | 100,000 请求/天 | 日均 10 万请求，MVP 阶段足够；营销爆发期可能触顶 |
| Workers CPU 时间 | 10ms CPU/请求（默认） | 密码哈希已用 HMAC-SHA256（低 CPU）规避；COUNT 聚合已规避 |
| Workers 内存 | 128MB（实际约 1MB 限） | 已做请求体 100KB 闸门、媒体 2MiB 上限 |
| 定时任务 | 每天最多 1,000 次调度 | 当前 `*/5 * * * *`（每天 288 次）在限额内 |
| R2 存储 | 10GB 免费 | 媒体存 cf-shop 共用 bucket，够用 |
| Cron Triggers | 3 个 Worker、每个最多 3 个 cron | 当前 1 个 cron，无压力 |
| Turso 免费层 | 行数/存储/连接数有限 | 已做快照表、限流日志定期清理、数据保留策略 |
| 静态资源 | Workers 资产网络（run_worker_first 已配） | JS/CSS/字体不消耗请求额度 ✓ |

**结论：当前 MVP 负载远未触顶，硬限制更多是"成长天花板"而非"当前障碍"。**

## 三、代码库平台依赖面盘点（量化）

### 3.1 平台无关（无需改动）✅

| 层 | 说明 |
|----|------|
| Hono 框架 | 官方支持 multi-runtime（Workers/Node/Bun/Deno），`app.fetch` 签名一致 |
| 数据库（Turso/libSQL） | `@libsql/client` 走 HTTP 协议，**服务器可直接连同一个远程 Turso**，零改动 |
| Drizzle ORM | 基于 libsql 驱动，平台无关 |
| 邮件（Resend） | HTTP API，平台无关 |
| Web Crypto | `crypto.subtle`/`getRandomValues`/`randomUUID` Node 18+ 原生支持 |
| `atob`/`btoa` | Node 16+ 支持 |
| 业务路由 | auth/public/admin/platform/integration 全部是纯 Hono handler（仅读 `c.env`/`c.req`），平台无关 |
| vitest 测试 | 用 `app.request()`，无平台耦合 |
| 前端 | Vue SPA 构建产物，任何静态托管均可 |

### 3.2 平台绑定（需适配）⚠️

| # | 绑定点 | 位置 | Workers 形态 | 服务器形态 | 改动量 |
|---|--------|------|-------------|-----------|--------|
| 1 | `c.env.*` 读取 | auth/public/admin/platform/index（约 20 处） | env bindings | `process.env` 注入 | 小：Node 入口注入 env 即可，路由代码不动 |
| 2 | `c.executionCtx.waitUntil` | index.ts:266（scheduled）、media.ts:128（边缘缓存） | Workers 异步延续 | Node 无此 API | 小：抽 `waitUntil(c, task)` helper，Node 端 fire-and-forget |
| 3 | `c.env.ASSETS.fetch` | index.ts:250-257（SPA 静态资源） | Workers 资产网络 | 静态文件服务（fs/express static） | 中：入口层换实现 |
| 4 | `c.env.LOTTERY_MEDIA`（R2） | media.ts 全文件（上传/读取/缓存） | R2 bucket | 本地磁盘 / S3 / OSS | 中：抽存储抽象（`MediaStore` 接口） |
| 5 | `scheduled` + cron | index.ts:266 + wrangler.jsonc triggers | Cron Triggers | node-cron / 系统 crontab | 小：**已有 `/api/cron/draw`、`/api/cron/maintenance` 手动入口（CRON_SECRET 认证），服务器直接用 crontab 调 HTTP 即可，零代码改动** |
| 6 | `CF-Connecting-IP` | auth/public（8 处，未抽 helper） | Workers 真实客户端 IP | `X-Forwarded-For`（反代后） | 小：抽 `getClientIp(c)`，双平台读取 |
| 7 | 类型层 | bindings.ts（`Fetcher`/`R2Bucket`/`ExecutionContext`） | @cloudflare/workers-types | Node 无这些类型 | 小：Bindings 字段改可选 + Node 兜底类型 |
| 8 | 部署脚本 | wrangler.jsonc / local-deploy.sh | `wrangler deploy` | pm2/systemd/Docker + Nginx | 部署层，非代码 |

### 3.3 量化结论

- **业务代码（路由/服务/测试）：约 90% 零改动**（Turso + Hono 是最大的兼容资产）
- **需改动：约 5-8 个文件、~300 行适配代码**（入口层 + 媒体层 + IP helper + 类型 + 新 server 入口）
- **数据库/邮件/测试：零改动**（同一远程 Turso、同一 Resend、同一 vitest）

## 四、云服务器部署改动量评估（方案 A）

| 改动项 | 内容 | 工作量 |
|--------|------|--------|
| 新增 `server.ts` | `@hono/node-server` serve(app) + env 注入（process.env）+ 静态中间件 | 1 个新文件 ~80 行 |
| 新增 `lib/platform.ts` | `getClientIp` / `waitUntil` / 静态资源读取 / env 读取 4 个适配函数 | 1 个新文件 ~60 行 |
| `media.ts` 改造 | R2 API → `MediaStore` 接口（本地磁盘实现 + R2 实现） | 中，~100 行 |
| `bindings.ts` 类型 | Fetcher/R2Bucket/ExecutionContext 改可选 | 小 |
| cron | 系统 crontab 调 `/api/cron/maintenance`（已存在） | 部署配置 |
| 静态资源 | Nginx 托管 frontend/dist 或 express static | 部署配置 |
| 域名/HTTPS | 服务器证书 + 反代 | 运维 |

**总评估：2 个新文件 + 3 处改造，约 1-2 天工作量。核心业务代码不动。**

## 五、双平台兼容方案（方案 B，推荐架构）

**思路：Hono 本来就是 multi-runtime 框架，保持同一套 app，加一层平台适配，两边各一个入口。**

```
src/
  index.ts      ← Workers 入口（现状保留，改造成调用适配层）
  server.ts     ← Node 入口（新增）
  lib/platform.ts ← 平台适配层（新增，双平台差异全部收敛于此）
  routes/*.ts   ← 业务路由（不动，只读 c.env / 适配层 helper）
```

**适配层设计（lib/platform.ts）：**

```ts
// 1. IP 获取：Workers 用 CF-Connecting-IP，服务器用 X-Forwarded-For
export function getClientIp(c: Context<AppEnv>): string {
  return c.req.header("CF-Connecting-IP")
    || c.req.header("X-Forwarded-For")?.split(",")[0]?.trim()
    || "unknown";
}

// 2. 异步延续：Workers 用 executionCtx.waitUntil，Node 直接执行
export function waitUntil(c: Context<AppEnv>, task: Promise<unknown>): void {
  const ctx = c.get("executionCtx");
  if (ctx?.waitUntil) { ctx.waitUntil(task); return; }
  void task.catch(err => console.error("[waitUntil] failed:", err));
}

// 3. 静态资源：Workers 用 ASSETS binding，Node 读文件系统
// 4. 媒体存储：Workers 用 R2，Node 用本地磁盘/S3 —— MediaStore 接口
// 5. env：Workers 用 c.env，Node 入口注入 process.env
```

**双平台可行性结论：完全可行。** 理由：
1. Hono 官方 multi-runtime 设计（`serve(app)` 是官方导出）
2. Turso 是远程数据库——**这是最大的解耦资产**，两边连同一个库
3. scheduled 已有 HTTP 手动入口——服务器 crontab 直接复用
4. 前端 SPA 产物不依赖平台

## 六、方案对比与推荐

| 方案 | 改动量 | 成本 | 风险 | 适合 |
|------|--------|------|------|------|
| A. 纯云服务器 | 1-2 天 | 服务器 ~¥50-100/月 | 运维自担（HTTPS/备份/监控/安全） | 需要稳定 SLA、高并发、可横向扩展 |
| B. Cloudflare + 服务器双兼容 | 1-2 天（同 A，多一个入口） | Workers 免费 + 按需服务器 | 两套部署需维护 | **渐进迁移、灰度、成本弹性** |
| C. 维持纯 Cloudflare | 0 | 免费 | 免费层上限（100k req/天、R2 10GB、Turso 限额） | MVP 阶段、流量未爆发 |

### 推荐：方案 C（现在）+ 方案 B 的适配层（预留）

**分阶段路线：**

1. **当前（MVP）**：维持 Cloudflare + Turso。免费层限制对当前负载绰绰有余，且代码已 90% 平台无关——**不急于迁移**。
2. **本迭代（低优先）**：仅做两个低成本前置改造，为未来迁移铺路：
   - 抽 `getClientIp` helper（8 处 `CF-Connecting-IP` 重复 → 1 处收敛，顺带消除重复）
   - 抽 `lib/platform.ts` 适配层（waitUntil/env/静态资源），业务路由不再直接触平台 API
3. **触发迁移的时机**（任一成立再动手）：
   - 单日请求量持续 > 50k（逼近免费层 100k 上限的 50%）
   - R2 媒体存储 > 5GB
   - Turso 免费层行数/连接触顶
   - 需要稳定 SLA（99.9%+）或企业客户合规要求
4. **迁移时**：新增 `server.ts` 入口 + crontab 调 `/api/cron/*` + Nginx 静态托管，**业务代码零改动**（因前置适配层已就位）。

## 七、风险与注意点

| 风险 | 说明 | 缓解 |
|------|------|------|
| 双平台环境差异 | `c.env` 注入、IP 头、waitUntil 语义 | 全部收敛到 lib/platform.ts，单点维护 |
| 媒体存储迁移 | R2 对象 → 本地磁盘/S3 | MediaStore 接口抽象，迁移只换实现 |
| 服务器安全 | 需自管 HTTPS/防火墙/备份 | Nginx + 证书自动化（certbot）+ 定时快照 |
| Turso 单点 | 两个平台都依赖远程 Turso，Turso 挂了都挂 | Turso 高可用是产品承诺；可加只读副本 |
| 定时任务一致性 | Workers cron vs crontab 可能双跑 | 明确"二选一"启用；cron 幂等（processDueDraws 有状态机保护） |
| 免费层真实瓶颈 | 100k req/天 vs 10ms CPU | 前者是硬上限，后者已通过低 CPU 算法规避 |

## 八、结论

1. **云服务器部署改动量：约 1-2 天，2 个新文件 + 3 处改造，业务代码 90% 不动。** 核心原因是 Hono（multi-runtime）+ Turso（远程 DB）+ Resend（HTTP API）三者天然平台无关。
2. **双平台兼容：完全可行**，通过 lib/platform.ts 适配层收敛全部平台差异，Workers 入口（index.ts）与 Node 入口（server.ts）共享同一套 app。
3. **最优方案：当前维持 Cloudflare（方案 C），预留适配层（方案 B 的 lib/platform.ts），触发阈值时平滑迁移。** 不建议现在全面迁移——免费层对 MVP 足够，迁移是 1-2 天的低成本操作，等流量信号出现再做不迟。
