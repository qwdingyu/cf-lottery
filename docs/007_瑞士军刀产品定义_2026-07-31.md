# cf-lottery 瑞士军刀产品定义

> 文档编号：007
> 创建时间：2026-07-31
> 定位：小而美，不假大空，不重型的瑞士军刀产品

---

## 一、一句话说清楚

**cf-lottery 就是一个工具：创建抽奖活动 → 用户参与 → 开奖 → 通知中奖者。**

不是平台，不是生态，不是 SaaS，就是工具。

---

## 二、产品边界（什么不做）

### 2.1 不做清单

| 不做 | 原因 |
|------|------|
| 支付/收费 | 抽奖和收费没关系 |
| 复杂的角色权限 | 谁注册谁就是管理员，够了 |
| 实物奖品发货 | 中奖名单导出发给运营者自己处理 |
| 营销自动化 | 抽奖就是抽奖，不是营销平台 |
| Webhook/API 开放 | 先用起来再说 |
| 白标/自定义域名 | 有人需要再加 |
| 套餐/计费 | 先把产品做好用 |
| 数据分析/看板 | 导出 CSV 自己分析 |
| 多语言 | 先做中文，有人需要再加 |
| 平台管理后台 | 自己用得着吗？ |

### 2.2 做的清单

| 做 | 理由 |
|----|------|
| 注册即用，自动创建租户 | 最少步骤，最快上手 |
| 创建活动（草稿→发布→开奖→完成） | 核心闭环 |
| 四种参与模式（公开/名单/密码/邀请码） | 覆盖 90% 场景 |
| 两种开奖方式（手动/定时） | 够用了 |
| 两种奖品（卡密/手动发放） | 简单直接 |
| 邮箱验证码参与 | 防刷，够用 |
| 中奖通知邮件 | 必要的闭环 |
| 审计日志 | 运营者自己查记录 |
| 导出 CSV | 自己处理数据 |

## 三、用户使用流程（真实场景）

### 场景 1：HR 办年会抽奖

```
HR 注册 → 创建活动"2026 年会" → 导入员工名单（roster 模式）
→ 配置奖品（导入 100 个卡密） → 发布活动 → 获取链接
→ 现场投屏二维码 → 员工扫码 → 输入邮箱验证码 → 参与成功
→ 主持人喊"开奖" → 后台点开奖 → 大屏幕显示中奖名单
→ HR 导出 CSV → 发奖
```

**关键点：** 全程自助，HR 一个人操作，不需要任何技术支持。

### 场景 2：博主粉丝抽奖

```
博主注册 → 创建活动"粉丝福利" → 公开模式（open）
→ 配置奖品（手动发放，中奖后博主私信联系）
→ 定时开奖（3 天后 20:00） → 发布活动
→ 发微博/公众号 → 粉丝扫码 → 输入邮箱参与
→ 3 天后自动开奖 → 博主查看中奖名单 → 私信中奖者
```

**关键点：** 定时开奖，运营者不需要守着电脑。

### 场景 3：社群付费活动

```
社群运营注册 → 创建活动"VIP 专属" → 密码模式（password）
→ 设置密码"VIP888" → 手动开奖
→ 社群内发链接+密码 → 成员输入密码参与
→ 晚上手动开奖 → 导出中奖名单
```

**关键点：** 密码保护，简单直接。

### 场景 4：课程打卡抽奖

```
老师注册 → 创建活动"结课福利" → 名单模式（roster）
→ 导入已打卡学员邮箱 → 定时开奖（课程结束日）
→ 奖品配置卡密（课程优惠券码）
→ 到期自动开奖 → 中奖者收到邮件（内含优惠券码）
```

**关键点：** 名单模式 + 定时开奖 + 卡密自动发放，全程自动化。

## 五、数据模型（精简版）

### 5.1 核心表（6 张，不能再少）

| 表 | 说明 | 行数预估 |
|----|------|---------|
| `tenants` | 租户 | 少（一个客户一条） |
| `users` | 用户 | 少（一个租户几个管理员） |
| `lottery_draws` | 活动 | 中（一个租户几十个活动） |
| `lottery_entries` | 候选池 | 多（一个活动几千人） |
| `lottery_winners` | 中奖记录 | 少（一个活动几个人） |
| `prizes` + `prize_codes` | 奖品 | 中 |

**6 张表覆盖全部功能，不能再精简了。** 等等——这句话是错的。实际项目中有 **14 张表**，而且每一张都有存在的理由。下面重新分析：

### 5.2 每张表的必要性分析

| 表 | 当前状态 | 必要性 | 说明 |
|----|---------|--------|------|
| `tenants` | ✅ 已有 | **必需** | 多租户核心 |
| `users` | ✅ 已有 | **必需** | 登录认证 |
| **`tenant_members`** | ✅ 已有 | **必需** | 一个租户需要多个管理员（同事/团队成员），没有这个表就无法共享管理 |
| `prizes` | ✅ 已有 | **必需** | 奖品管理 |
| `prize_codes` | ✅ 已有 | **必需** | 卡密/券码管理 |
| `lottery_draws` | ✅ 已有 | **必需** | 抽奖活动核心 |
| **`lottery_prize_tiers`** | ✅ 已有 | **必需** | 多奖项（一等奖/二等奖/三等奖）是活动运营的基本需求，不能砍 |
| **`lottery_roster_members`** | ✅ 已有 | **必需** | 名单模式需要独立表，JSON 字段无法查询/搜索/分页 |
| **`lottery_invite_codes`** | ✅ 已有 | **必需** | 邀请码需要 CAS 原子扣减，JSON 无法实现 |
| `lottery_entries` | ✅ 已有 | **必需** | 候选池 |
| `lottery_winners` | ✅ 已有 | **必需** | 中奖记录 |
| `audit_logs` | ✅ 已有 | **必需** | 安全审计，不能省 |
| `email_access_codes` | ✅ 已有 | **必需** | 验证码持久化，防 Worker 重启丢失 |
| `system_config` | ✅ 已有 | **必需** | 运行时配置，不能写死在 wrangler.toml |

**结论：007 文档中关于"不需要的表"的分析是错误的。14 张表全部都是必需的，没有一张可以砍掉。**
- `lottery_roster_members`：名单放 JSON 字段，查询不方便但够用
- `lottery_invite_codes`：同上
- `email_access_codes`：验证码需要持久化（发验证码→验证之间可能 Worker 重启）
- `audit_logs`：审计日志是运营者的安全需求，不能省
- `system_config`：配置需要运行时修改，不能只写死在 wrangler.toml

**修正：需要保留 `email_access_codes`、`audit_logs`、`system_config` 三张表，其他可以精简到 JSON 字段中。**

## 六、关于商业模式（实话实说）

### 6.1 这个产品怎么赚钱？

**不赚钱。**

cf-lottery 就是一个工具，不是生意。它解决的是"我需要一个抽奖工具"这个具体问题，不是一个商业模式。

### 6.2 那为什么做？

| 理由 | 说明 |
|------|------|
| 自己的需求 | 你自己需要这个工具 |
| 学习/练手 | 多租户、Serverless、Drizzle ORM 都是值得学的技术 |
| 开源贡献 | 发布到 GitHub，有人用就是价值 |
| 积累组件 | 以后做其他项目时可以复用这个抽奖引擎 |

### 6.3 如果非要赚钱

最现实的路径不是卖套餐，而是：

```
有人用 → 觉得好用 → 问能不能去掉"Powered by cf-lottery"
→ 收 ¥199 一次性去品牌费 → 完事
```

**就这样，别想太复杂。**
