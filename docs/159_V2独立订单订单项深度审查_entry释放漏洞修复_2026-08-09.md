## 2. 🔴 灾难性 Bug 1：cancelPaymentOrder 错误释放已支付 entry

### 背景

`cancelPaymentOrder` 在支付网关创建失败时被调用，释放名额和 entry。

### 原因

第 286-307 行只检查该 entry 是否有其他 **PENDING** 订单：
```typescript
eq(paymentOrders.status, PAYMENT_ORDER_STATUS.PENDING)
```

### 漏洞场景

1. 用户购买 2 件 → 支付成功 → 订单 A（PAID），entry → paid
2. 用户再次购买 3 件（批发）→ entry → pending，订单 B（PENDING）
3. 支付网关创建失败（确定性异常）
4. `cancelPaymentOrder` 检查是否有其他 PENDING 订单 → 订单 A 是 PAID（不是 PENDING）→ 未找到
5. **entry 被释放为 expired** → 订单 A 的已发卡履约被掩盖，用户无法再次下单

### 修复

改用 `notInArray` 排除终态，检查所有非终态订单（含 PAID、FULFILLMENT_FAILED）：
- 有 PAID/FULFILLMENT_FAILED 订单 → entry 恢复为 PAID
- 有其他 PENDING 订单 → entry 保持 PENDING
- 无其他有效订单 → entry 释放为 EXPIRED

## 3. 🔴 灾难性 Bug 2：expireOverdueOrders 错误释放已支付 entry

### 原因

与 Bug 1 相同，但发生在超时清算路径。原代码（第 202-210 行）无条件释放所有 pending entry：
```typescript
await tx.update(lotteryEntries)
  .set({ paymentStatus: EXPIRED })
  .where(and(..., eq(lotteryEntries.paymentStatus, PENDING)))
```

### 修复

改为显式多步查询（避免相关性子查询在 drizzle-orm UPDATE 中不可靠）：
1. 查有 PAID/FULFILLMENT_FAILED 订单的 entry → 恢复为 PAID
2. 查有其他有效订单（非超时 PENDING）的 entry → 保持 PENDING
3. 其余 entry → 释放为 EXPIRED
4. 所有超时订单容量统一释放

## 6. 追加优化（同日续审）

### 6.1 cancelPaymentOrder limit(1) 非确定性

原实现查询 `otherActive` 订单时用 `.limit(1)` 且无排序。当 entry 同时存在
PAID 和 PENDING 订单时会非确定性地选中 PENDING，掩盖 PAID 履约。改为与
expireOverdueOrders 一致的两步显式检查：先查 PAID/FULFILLMENT_FAILED 恢复
paid，再查 PENDING 保持 pending，最后才释放 expired。

### 6.2 expireOverdueOrders 命名

`keepPendingEntryIds` 实际保护的是所有非终态有效订单，重命名为
`keepActiveEntryIds`，避免误导。

### 6.3 retryPaymentFulfillment 容忍已 paid entry

多订单场景下，当 entry 已因其他订单 PAID（其中一个先补发成功），补发当前
订单会因 `paidEntry` 更新 0 行抛"参与记录状态已变化"。改为显式检查 entry 状态：
- PAID → 跳过 entry 更新（已正确）
- PENDING → 推进为 paid
- 其他 → 抛异常

## 8. 🔴 灾难性 Bug 3：cancelDraw 错误释放已支付 entry（活动取消路径）

### 背景

`cancelDraw`（`src/services/lottery/draws.ts`）在运营取消活动时执行清理。原实现
按 `entry.paymentStatus ∈ [RESERVED, PENDING]` 无条件把 entry 置为 EXPIRED，
并只按「释放的 entry 条数」回收容量。

### 原因与 Bug 1 同源

多订单模型下，`entry.paymentStatus = PENDING` **不代表「未收款」**。用户可能：
1. 首次购买 1 件 → 支付成功 → 订单 A（PAID），entry → paid
2. 再次批发购买 3 件 → 订单 B（PENDING），entry → **pending**（回到 pending）
3. 运营取消活动 → `cancelDraw` 看到 entry = pending → 释放为 EXPIRED

结果：**订单 A 的已支付履约被 EXPIRED 掩盖**，用户无法找回已付款获奖，且
退款/补发审计链丢失。与 Bug 1/Bug 2 完全同类。

### 第二个问题：容量回收按 entry 条数而非订单数量

原实现 `activeParticipantCount - releasedEntries.length`：对批发订单
（quantity=3）只回收 1，留下 2 个幽灵容量。容量语义应为
`1(join base) + sum((qty-1) 首单) + sum(qty 续单)`，取消时应回收
`sum(过期订单 qty) + 1(纯 RESERVED, 无订单)`。

### 修复

1. 先查 PENDING 订单及其 `quantity`（用于容量回收）
2. 查有 PAID/FULFILLMENT_FAILED 订单的 entry → **恢复为 PAID（不释放）**
3. 其余受保护 entry（纯 RESERVED / 仅 PENDING 且无 PAID 订单）→ 释放 EXPIRED
4. 容量回收 = `过期 PENDING 订单 quantity 之和` + `被释放的纯 RESERVED entry 数`

### 回归测试

`src/services/lottery-service.test.ts` 新增：
- entry 有 PAID 订单 A（qty=1）+ PENDING 批发订单 B（qty=3）
- 取消后：entry 保持 `paid`（不掩盖订单 A）、订单 A 保持 `paid`、订单 B → `expired`
- 容量只释放订单 B 的 3 件，订单 A 的 1 件仍占用（`activeParticipantCount = 4 → 1`）

### 一并修复的遗留问题

- `payment-service.ts` `createPaymentOrder` 中 `[FULFILLMENT_FAILED, LATE_NEEDS_REFUND]
  .includes(status)` 触发 TS 元组推断严格性错误（`string` 不能赋给字面量联合），
  用 `as string[]` 修复，恢复 `npx tsc --noEmit` 0 error。
- 修正上轮误写的测试断言：`paid_fulfillment_failed 订单未补发完成前…` 原断言
  `activeParticipantCount = 3`，但 FULFILLMENT_FAILED 检查发生在容量预约**之前**，
  容量保持 seedBatchFlow 初始值 **1**，已更正。
