## 1. 讨论背景

### 1.1 触发问题

在 Phase C-1（一次性 Web 访问令牌 + 跨平台身份绑定，docs/179）实现完成后，团队提出一个根本性问题：

> **「QQ 群是一个有效的聚集地，通过 /绑定 命令，是否可以直接在 user 表自动创建一条记录？或者无论进行任何操作之前都检查 user 表，如果没有就自动注册一个？」**

这个问题的本质是：**我们是否需要 /绑定 这个命令？或者说，跨平台身份合并是否可以更自动化？**

### 1.2 当前架构现状

在 Phase B（docs/176 §3.4）中，`inbound.ts` 第 58-68 行已经实现了**自动注册**：

```
用户发送任何命令（/签到、/抽奖、/绑定、/帮助……）
  → handleInboundPlatformEvent 先调用 provisionPlatformUser
    → 检查 authIdentities(provider, providerUserId) 是否存在
    → 不存在 → 自动创建 users + authIdentities 记录
    → 存在 → 复用已有记录（幂等）
  → 再将 userId 注入命令上下文，执行具体命令逻辑
```

**关键事实：** 每个 QQ/Telegram 用户在第一次发送任何命令时，已经自动获得了 `users.id`。这不是 `/绑定` 的功能，而是 Phase B 的自动注册。

### 1.3 厘清概念：注册 vs 合并

| 概念 | 说明 | 由谁实现 | 状态 |
|------|------|---------|------|
| **自动注册** | 平台用户首次交互时，自动创建 `users` + `authIdentities` 记录 | Phase B（`provisionPlatformUser`） | ✅ 已实现 |
| **跨平台合并** | 同一人使用 QQ 和 Telegram 产生两个 `users.id`，需要合并为一个 | Phase D（`/绑定` 命令） | ⚠️ 提前实现中 |

**自动注册已经回答了用户的问题。** `/绑定` 解决的是另一个问题。

### 1.4 为什么自动注册不能替代合并？

```
张三在 QQ 群发 /签到
  → provisionPlatformUser 创建 users.id = UUID-A
  → authIdentities: { provider: "qq", providerUserId: "123456", userId: "UUID-A" }

张三在 Telegram 群发 /签到
  → provisionPlatformUser 创建 users.id = UUID-B（新记录！）
  → authIdentities: { provider: "telegram", providerUserId: "789012", userId: "UUID-B" }
```

**系统无法自动知道 QQ 的张三和 Telegram 的张三是同一人。** 必须用户主动证明。

## 2. 行业最佳实践对照

### 2.1 跨平台身份关联的四种常见方案

| 方案 | 代表系统 | 前置条件 | 用户体验 | 评价 |
|------|---------|---------|---------|------|
| **OAuth 账号关联** | Telegram Login Widget, Discord OAuth, Google/Facebook Login | 需要有 Web 登录（Phase C） | 点击授权 → 自动绑定，无需手动输入 | **行业金标准** |
| **邮箱关联** | 绝大多数 Web 应用 | 用户有邮箱 | 登录邮箱 → 验证 → 绑定 | 简单可靠，但需要邮箱 |
| **6 位绑定码** | 部分游戏/工具（如 Steam 手机令牌绑定） | 无 Web 登录 | 复制码 → 粘贴到另一个平台 | 非标准，权宜之计 |
| **管理员手动合并** | 企业级后台 | 管理员操作 | 后台操作 | 不可扩展，仅用于异常处理 |

### 2.2 为什么行业标准是 OAuth 关联？

主流系统（Auth0、Cognito、Keycloak、Better Auth）的身份关联模式：

1. **用户有一个主账号**（通常是 `users.id`），所有业务引用这个主键
2. **外部身份（OAuth provider）与主账号关联**，通过 `authIdentities` / `account` 表
3. **关联方式**：用户在 Web 端登录主账号 → 进入设置 → 点击「关联 QQ」→ 跳转 OAuth 授权 → 回调完成绑定

**这种模式依赖 Web 登录（Phase C）的先决存在。**

### 2.3 绑定码方案在行业中的定位

绑定码方案在以下场景中被使用，但**都不是主流**：
- Steam 手机令牌绑定：6 位码 + 一次性 + 短时效（与我们的方案类似）
- 部分游戏内跨平台关联（如原神绑定 TapTap/PSN 需要手动输入验证码）
- 企业级 2FA 恢复码

这些场景的共性是：**没有 OAuth 通道可用，或者用户不在浏览器环境中。**

## 3. 三种方案详细对比

### 3.1 方案 A（当前方案）— 保留 /绑定，用绑定码合并

**核心逻辑：**
```
QQ 群发 /绑定 → 得 6 位码 → Telegram 群发 /绑定 XXXXXX → 合并 authIdentities.userId
```

**实现内容：**
- `platform_bindings` 表：存绑定码（6 位高熵）
- `generateBindingCode`：生成码，10 分钟有效
- `consumeBindingCode`：消费码，CAS 并发防护，合并 authIdentities
- 尝试清理孤儿用户行（不保证成功，非阻塞）

**优点：**
- 现在就能用，不依赖 Phase C
- 用户主动操作，隐私安全可控
- 6 位码 + 10 分钟 + 一次性，安全边界足够

**缺点：**
- 用户体验差：需要手动复制码，在另一个平台输入
- 非行业标准：将来 Phase C 完成后可能需要废弃
- 合并是部分的：只改 `authIdentities.userId`，`lotteryEntries` 不受影响（仍按 identityType+identityValue 查询）
- 孤儿用户清理脆弱：外键约束可能导致清理失败
- 额外维护成本：需要保留 `platform_bindings` 表及定时清理

### 3.2 方案 B（更优但更重）— 优先做 Phase C 的 Web 登录，走 OAuth 关联

**核心逻辑：**
```
Phase C 完成 → 用户 Web 登录 → 设置页面关联 QQ/Telegram → OAuth 授权 → 绑定
```

**前置条件：**
- Phase C 完成（Web 登录，含 QQ 互联 OAuth / Telegram Login Widget 接入）
- cf-auth 扩展（docs/178 已论证「现阶段不加入」）
- 域名部署 + 企业资质审核（QQ 互联需要企业资质）

**优点：**
- 行业标准，用户体验好
- 一次接入，长期可用
- 不需要独立的绑定码表，复用 OAuth 的 `account` 表

**缺点：**
- 工作量不确定：QQ 互联 OAuth 需要企业资质审核（可能耗时 1-2 周甚至更长）
- Telegram Login Widget 需要域名部署
- cf-auth 的扩展需要最小侵入设计，避免破坏 Better Auth 语义
- 如果 Phase C 排期在 2-3 个月后，用户在这期间无法跨平台查看卡密

### 3.3 方案 C（最轻量）— 不做 /绑定，只保留一次性令牌

**核心逻辑：**
```
砍掉 /bind 命令和 platform_bindings 表
卡密 Web 找回只靠一次性访问令牌（accessUrl）
QQ 和 Telegram 各自独立 users.id，不合并
```

**优点：**
- 零额外工作量（P0 已经闭环，一次性令牌已实现）
- 没有孤儿用户清理问题
- 不需要维护 `platform_bindings` 表
- 代码更少，复杂度更低

**缺点：**
- 用户无法跨平台查看同一份数据
- 如果用户 QQ 中奖后切换到 Telegram，无法在 Telegram 查看到 QQ 获得的卡密
- 需要用户记住：看 QQ 卡密用 QQ 群，看 Telegram 卡密用 Telegram 群
- 不符合「One User」的长期愿景（docs/176 的统一账号体系目标）

### 3.4 对比总结

| 维度 | 方案 A（代码绑定） | 方案 B（Phase C 优先） | 方案 C（不做绑定） |
|------|-------------------|----------------------|-------------------|
| **P0 闭环** | ✅ 已闭环 | 🔄 依赖 Phase C 排期 | ✅ 已闭环 |
| **跨平台数据聚合** | ✅ 基础支持 | ✅ 最佳 | ❌ 不支持 |
| **用户体验** | ⚠️ 手动复制码 | ✅ OAuth 一键关联 | N/A |
| **行业标准** | ⚠️ 非标准 | ✅ 金标准 | N/A |
| **实现复杂度** | ⚠️ 中等 | 🔴 高（含 Phase C） | ✅ 零 |
| **维护成本** | ⚠️ 有（清理表、保留代码） | ✅ 低 | ✅ 零 |
| **长期可废弃性** | ⚠️ 需标记为过渡方案 | ✅ 长期方案 | N/A |
| **依赖** | 无 | Phase C + QQ 互联资质 + 域名 | 无 |
| **可逆性** | ⚠️ 可废弃但需迁移数据 | ✅ 不可逆 | ✅ 随时可加 |

## 4. 决策：方案 A

### 4.1 决策理由

**基于现有条件，决定采用方案 A（保留 /绑定，用绑定码合并）。** 理由如下：

**理由 1：Phase C 的排期不确定。**
- QQ 互联 OAuth 需要企业资质审核，时间不确定
- cf-auth 的扩展需要谨慎设计，不能急于一时
- 如果 Phase C 在 2-3 个月后落地，用户在这期间无法跨平台操作

**理由 2：P0 已闭环，但 P1 的跨平台需求真实存在。**
- 一次性访问令牌（P0）已经解决了卡密 Web 找回的问题（docs/179 §2.1）
- 但用户确实有「QQ 抽奖 → Telegram 查卡密」的场景需求
- 绑定码方案虽然不完美，但能解决这个真实需求

**理由 3：方案 A 与方案 C 不是互斥的。**
- 即使采用方案 A，如果未来发现 /bind 使用率很低，随时可以废弃
- `platform_bindings` 表新增的负担很小（一张表 + 一个定时清理任务）
- 选择方案 A 保留了后续转向方案 C 的灵活性

**理由 4：方案 B 的时机未到。**
- docs/178 已明确论证：Phase C 前 cf-auth 不得加入 QQ/Telegram 身份逻辑
- 强行提前 Phase C 会带来架构风险（Better Auth 语义污染、OAuth 与 Bot 身份混淆）
- 方案 B 应该是 Phase C 完成后的「自然升级」，而不是现在强行推进

### 4.2 决策约束

**我们选择方案 A，但必须遵守以下约束：**

1. **明确标记 /绑定 为过渡方案。** 代码注释、文档、README 中都要标明：
   - 「此方案在 Phase C（Web 登录）完成后，将被 OAuth 关联取代」
   - 不在 /绑定 上投入过多打磨（UI 优化、交互增强等）

2. **不得过度设计。** 绑定码 6 位 + 10 分钟 + 一次性就够了，不需要：
   - 不需要多轮重试/码过期提醒
   - 不需要解绑功能（合并后如需分离走数据库运维）
   - 不需要绑定码的 UI 界面（纯 Bot 文本交互）

3. **P0 与 P1 职责分离。** 一次性访问令牌（P0）和 /绑定（P1）是独立功能：
   - 即使 /绑定 被废弃，一次性令牌继续工作
   - 一次性令牌不依赖 /绑定 的任何逻辑

4. **Phase C 完成后重新评估。** 当 Phase C 就绪时，评估：
   - /bind 的使用率：如果使用率低，直接废弃
   - 用户迁移方案：已绑定的用户如何处理

### 4.3 否决的方案

**方案 C（不做绑定）被否决的原因：**
- 不符合 docs/176 的统一账号体系长期目标
- 放弃「One User」愿景，用户数据割裂
- 如果未来用户量增长，补回来成本更高

**方案 B（Phase C 优先）被否决的原因：**
- 时机不成熟：Phase C 的前置条件（企业资质、cf-auth 扩展、域名部署）均未就绪
- docs/178 已明确论证 cf-auth 现阶段不得加入 QQ/Telegram 身份逻辑
- 为了一个 P1 功能冒 Phase C 的架构风险，不值得

## 5. 方案 A 的实施边界

### 5.1 要做什么

- ✅ `/绑定` 命令（无参数 → 生成码，带参数 → 消费码）
- ✅ `platform_bindings` 表（存绑定码，6 位高熵，10 分钟有效，一次性）
- ✅ `binding.ts` 服务（生成/消费/清理）
- ✅ `isBuiltinCommandEnabled` 中 /bind 恒 true（用户级工具，不随群开关关闭）
- ✅ `bindEnabled` 配置项（恒 true 但保留字段，维持接口一致性）
- ✅ 安全约束：禁止同一平台自我绑定，禁止重复绑定，ownership proof

### 5.2 不做什么

- ❌ 绑定码的 UI 界面（纯 Bot 文本交互，不做前端页面）
- ❌ 解绑功能（合并后不可撤销，需分离走数据库运维）
- ❌ 绑定码过期提醒（用户自己关注时效）
- ❌ 绑定码多轮重试（一次性失败即失败）
- ❌ 迁移 `lotteryEntries` 数据（保持 identityType+identityValue 约束）
- ❌ 在 cf-auth 加入 QQ/Telegram 身份逻辑（保持 Phase C 的纯净边界）

### 5.3 已知限制

1. **合并是部分的。** `lotteryEntries` 仍按 `identityType + identityValue` 查询，不随绑定迁移。
   - 影响：用户查看参与记录时，QQ 参与的记录和 Telegram 参与的记录仍然是两行
   - 但不影响卡密查看（通过 `authIdentities.userId` 关联）
   - 若未来需要统一查询，需在 Phase C 或后续迭代中处理

2. **孤儿用户清理不保证成功。** `binding.ts` 尝试删除旧的 `users` 行，但：
   - 如果旧用户有外键引用（如 `lotteryEntries`、`paymentOrders` 等），删除会失败
   - 失败时降级处理，不影响绑定主流程
   - 孤儿用户行不会影响功能，只是数据冗余

3. **绑定不可撤销。** 当前版本不支持解绑操作。
   - 合并后如果需要分离，必须走数据库运维手动修改 `authIdentities.userId`
   - 这是设计选择：解绑场景极少，不值得为它增加复杂度

## 6. 与 Phase 规划的关系

### 6.1 Phase 调整

docs/178 的 Phase 规划需要更新：

| Phase | 范围 | 原计划 | 当前状态 | 调整说明 |
|-------|------|--------|---------|---------|
| Phase A | `/我的卡密` 命令 | 已实现 | ✅ 已实现 | 无变化 |
| Phase B | QQ/Telegram 身份关联 `users` 表 | 已实现 | ✅ 已实现 | 无变化 |
| Phase C-1 | 一次性 Web 访问令牌 | 新增 | ✅ 已实现 | 新增阶段，解决 P0 |
| Phase C-1 | 跨平台身份绑定（/绑定） | 新增 | ✅ 已实现（过渡方案） | 提前实现了 Phase D 的部分内容 |
| Phase C | Web 端 QQ/Telegram 登录入口 | 规划中 | 🔄 规划中 | 不变 |
| Phase D | 跨平台身份合并 | 远期 | ⚠️ 部分提前实现 | /绑定 作为过渡方案，Phase C 完成后用 OAuth 替代 |

### 6.2 Phase C 后的过渡计划

当 Phase C（Web 登录）完成后，跨平台身份合并的推荐路径：

1. **Phase C 完成 Web 登录**（email OTP + QQ 互联 OAuth + Telegram Login Widget）
2. **用户登录 Web 账号**（通过邮箱或 QQ 互联）
3. **在设置页面关联另一个平台**（OAuth 授权）
4. **/绑定 命令标记为「已废弃」**（保留兼容，但不再推荐使用）
5. **`platform_bindings` 表进入只读/维护模式**（不再新增记录，已有记录可查询）
6. **未来清理：** 确认无活跃绑定后，可删除 `platform_bindings` 表和相关代码

### 6.3 风险登记

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| Phase C 延期导致 /绑定 长期使用 | 中 | 用户体验差，非标准方案长期存在 | 标记为过渡方案，限制投入 |
| 绑定码被滥用（暴力枚举） | 低 | 恶意绑定 | 6 位高熵（2.2B 组合）+ 10 分钟 + 一次性，不可暴力 |
| 绑定后需要解绑 | 低 | 用户诉求无法满足 | 文档说明，走数据库运维 |
| 孤儿用户数据膨胀 | 低 | 数据库冗余 | 不影响功能，可定期清理 |
| Phase C 完成后 /绑定 废弃但数据迁移复杂 | 低 | 历史绑定数据需处理 | 绑定数据量小，可一次性迁移 |

## 7. 讨论记录

### 7.1 关键问题与回答

**Q：是否可以在 user 表自动创建记录，而不需要 /绑定？**
A：**已经在做了。** Phase B 的 `provisionPlatformUser` 会在用户第一次发任何命令时自动创建 users 记录。/绑定 解决的是合并问题，不是注册问题。

**Q：为什么不能自动合并 QQ 和 Telegram 的身份？**
A：系统无法自动知道两个平台的用户是同一人。必须用户主动证明（ownership proof）。绑定码是最轻量的证明方式。

**Q：方案 A 和方案 C 哪个更轻量？**
A：方案 C 更轻量（零额外工作），但放弃了跨平台数据聚合的长期目标。方案 A 增加了少量复杂度，但保留了「One User」愿景。

**Q：如果 Phase C 永远不做怎么办？**
A：/绑定 方案作为过渡方案，即使 Phase C 不做，也能独立工作。只是用户体验不如 OAuth 关联好。
