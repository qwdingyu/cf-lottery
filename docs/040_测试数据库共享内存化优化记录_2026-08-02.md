# 测试数据库共享临时库优化记录

## 背景

测试用例曾经在多个文件中各自创建 libSQL 文件库，并手写大量 `CREATE TABLE`/`ALTER TABLE`。这会造成三个问题：

1. 本地目录残留大量 `test-*.db` 文件，排查和清理成本高。
2. 测试 DDL 和生产 migrations 双维护，schema 漂移后测试不能真实反映新环境风险。
3. 不同测试文件各自初始化数据库，执行慢且容易把历史字段兼容逻辑堆进测试。

## 最终方案

1. `src/test-setup.ts` 作为唯一测试数据库入口。
2. 测试库使用系统临时目录下的进程级 libSQL 文件库，例如 `/tmp/cf-lottery-vitest-<pid>.db`，在单个 Vitest 进程内共享。
3. 初始化时只执行 `migrations/`，不在业务测试文件维护建表脚本。
4. `clearTestData()` 负责清空业务表并恢复默认系统配置。
5. `vitest.config.ts` 设置 `fileParallelism: false`，避免同一共享库在文件并发下互相污染。
6. `src/test-db-usage-sanity.test.ts` 扫描业务测试文件，禁止重新出现 `CREATE TABLE`、`ALTER TABLE`、`createClient(` 和 `file:test-*`。

## 本次修正

1. `src/routes/p0-flow.test.ts` 改为使用 `getTestDb()` + `clearTestData()`。
2. `src/services/lottery-service.test.ts` 改为使用共享库，并在每个用例前清库后播种基础租户、用户和成员。
3. `src/test-setup.ts` 从项目根目录 `test-shared.db` 切换为系统临时目录进程级文件库，并在进程退出时清理。
4. 清理根目录历史遗留的 65 个测试 `.db` 文件。

## 约束和注意事项

1. 共享临时库只在当前 Vitest 进程内使用；每次 `vitest run` 会重新从 migrations 初始化一次，这是可接受的测试启动成本。
2. 不要把测试库固定回项目根目录共享文件。当前方案按进程生成临时库，避免多个独立 Vitest 进程抢同一个 SQLite 文件锁。
3. 新增数据库字段必须先补 migration，再改 schema 和测试。测试库不会接受业务测试文件里的临时建表兼容。
4. 如需特殊测试数据，只能插入业务行；不能在测试文件里创建或修改表结构。

## 验证口径

完成标准不是“测试通过”而已，还必须满足：

1. `rg 'CREATE TABLE|ALTER TABLE|DROP TABLE|createClient\\(|file:test-' src/**/*.test.ts src/test-setup.ts` 只允许命中 `src/test-setup.ts` 和规范测试。
2. 根目录不再产生 `test-*.db`、`publish-check-test-*.db`、`test-shared.db`。
3. `npm run test`、`npm run type-check:all`、`npm run frontend:build` 全部通过。
