# 奖品系统多模式设计与闭环审查报告

> 文档编号：032
> 创建时间：2026-08-01
> 定位：审查当前奖品系统支持的模式、参数闭环情况，给出最优的多模式奖品设计方案。
> 审查原则：以当前代码为准，逐项核对每个参数是否形成闭环，不推测、不假设。

---

## 一、当前奖品系统现状（代码核验）

### 1.1 数据模型

```sql
-- prizes 奖品定义表
prizes (
  id, tenant_id,
  name,            -- 奖品名称
  description,     -- 奖品描述
  image_url,       -- 奖品图片 URL
  value_text,      -- 奖品价值说明（如 "50 USDT"）
  prize_type,      -- 奖品类型：code | manual_fulfillment
  fulfillment_note,-- 发放说明
  total_count,     -- 奖品总数量
  used_count,      -- 已发放数量
  active,          -- 是否启用
  created_at, updated_at
)

-- prize_codes 卡密码池
prize_codes (
  id, tenant_id, prize_id,
  code,            -- 卡密/兑换码
  secret,          -- 附加密钥（可选，如卡密的密码）
  note,            -- 备注
  status,          -- available | issued | expired
  winner_id,       -- 发放给哪位中奖者
  issued_at,       -- 发放时间
  created_at
)
```

### 1.2 当前支持的奖品类型

| 类型 | 代码值 | 发放方式 | 适用场景 | 状态 |
|:----:|:------:|:---------|:---------|:----:|
| 卡密/券码 | `code` | 中奖后从码池取一个码自动发放 | 兑换码、激活码、优惠券 | ✅ 已实现 |
| 手动发放 | `manual_fulfillment` | 中奖后手动联系发放 | 实物奖品、礼品、线下服务 | ✅ 已实现 |

### 1.3 当前支持的卡密导入方式

| 导入方式 | 实现 | 状态 |
|:---------|:-----|:----:|
| **文本框粘贴**（每行一个） | `AdminPrizesView.vue` 导入弹窗，textarea 每行一个码，支持 `code:secret` 格式 | ✅ 已实现 |
| 批量 API | `POST /api/admin/prizes/:id/codes/import`，接收 `{ codes: [{code, secret}] }` | ✅ 已实现 |
| 自动生成卡密 | 未实现 | ❌ 缺失 |
| CSV 文件上传 | 未实现 | ❌ 缺失 |

### 1.4 参数闭环审查（逐项核验）

| 字段 | 创建 | 导入 | 发放 | 展示 | 闭环状态 |
|:-----|:----:|:----:|:----:|:----:|:--------:|
| `name` | ✅ 输入 | — | — | ✅ 展示 | ✅ 闭环 |
| `description` | ✅ 输入 | — | — | ✅ 展示 | ✅ 闭环 |
| `image_url` | ✅ 输入/上传 | — | — | ✅ 展示 | ✅ 闭环 |
| `value_text` | ✅ 输入 | — | — | ✅ 展示 | ✅ 闭环 |
| `prize_type` | ✅ 输入 | — | — | ✅ 展示 | ✅ 闭环 |
| `fulfillment_note` | ⚠️ 有字段 | — | — | ❌ 前端未使用 | ❌ **断裂** |
| `total_count` | ❌ 默认0 | ❌ 不更新 | — | ⚠️ 前端展示0 | ❌ **断裂** |
| `used_count` | ❌ 默认0 | — | ❌ 不更新 | ⚠️ 前端展示0 | ❌ **断裂** |
| `active` | ⚠️ 默认1 | — | — | ❌ 无启用/禁用UI | ❌ **断裂** |
| `prize_codes.status` | — | ✅ available | ✅ issued | ✅ 展示 | ✅ 闭环 |

**关键断裂：**
1. `total_count` 和 `used_count` 从未更新——导入码后奖品总数仍为 0，发放后已用数仍为 0。运营者无法知道码池剩余量。
2. `fulfillment_note` 有字段但前端从未展示。
3. `active` 无启用/禁用操作，无法下架奖品。

## 二、最优奖品模式设计方案

### 2.1 奖品类型扩展（6 种模式）

| 类型 | 代码值 | 发放方式 | 适用场景 | 数据要求 |
|:----:|:------:|:---------|:---------|:---------|
| 卡密/券码 | `code` | 中奖后从码池取一个自动发放 | 兑换码、激活码、优惠券 | 需导入码池 |
| **虚拟资料** | `virtual` | 中奖后自动发放"链接+密码" | 电子文档、白皮书、资料包、课程 | 需配置链接+密码（或自动生成） |
| **链接奖品** | `link` | 中奖后自动发放专属链接 | 优惠链接、专属通道、邀请链接 | 需配置链接 |
| **自动生成码** | `auto_generate` | 系统自动生成随机码发放 | 批量卡密、内测码、邀请码 | 需设置数量+格式 |
| 实物奖品 | `manual_fulfillment` | 中奖后手动联系发放 | 实物、礼品、线下服务 | 无 |
| **即时发放** | `instant` | 参与即发放（不抽奖） | 人人有奖、进群链接、打卡奖励 | 需配置发放内容 |

### 2.2 卡密批量导入的 4 种模式

| 模式 | 操作方式 | 适用场景 | 状态 |
|:-----|:---------|:---------|:----:|
| **① 文本粘贴** | textarea 每行一个码，支持 `code:secret` | 已有卡密列表 | ✅ 已实现 |
| **② 文件上传** | 上传 .csv/.txt，自动解析 | 大量卡密（几百上千个） | ❌ 待实现 |
| **③ 自动生成** | 指定数量+前缀+长度，系统生成随机码 | 无现成卡密 | ❌ 待实现 |
| **④ 虚拟资料** | 粘贴"链接+密码"，系统自动生成唯一访问码 | 电子资料发放 | ❌ 待实现 |

### 2.3 推荐实现优先级

#### P0（必须，影响运营确定性）

**① 修复 total_count / used_count 闭环**

```typescript
// importPrizeCodes 中：导入成功后更新 prizes.total_count
await db.update(prizes)
  .set({ totalCount: sql`total_count + ${codes.length}`, updatedAt: now })
  .where(eq(prizes.id, prizeId));

// 发放码时（performDraw）：更新 prizes.used_count
await db.update(prizes)
  .set({ usedCount: sql`used_count + 1`, updatedAt: now })
  .where(eq(prizes.id, tier.prizeId));
```

**② 前端展示码池余量**

奖品管理列表显示：`已用/总数`（如 `3/100`），让运营者知道剩余量。

#### P1（重要，多场景支持）

**③ 自动生成卡密**

前端在导入弹窗中增加"自动生成"Tab：
```
生成数量: [100]
码前缀:  [LUCKY-]
码格式:  [8位随机]（字母数字去易混淆字符）
生成结果: 直接写入码池
```

后端新增 `POST /api/admin/prizes/:id/codes/generate`：
```typescript
{ count: 100, prefix: "LUCKY-", codeLength: 8, secretLength: 0 }
```
使用 `crypto.getRandomValues()` 生成，保证随机性。

**④ 文件上传导入**

前端在导入弹窗中增加"文件上传"按钮：
```
接受 .txt / .csv 文件
每行一个码，支持 "code" 或 "code,secret" 或 "code:secret"
自动解析并导入
```

#### P2（增强，虚拟资料场景）

**⑤ 虚拟资料奖品（virtual）**

在奖品创建弹窗中增加"虚拟资料"类型配置：
```
资料链接: [https://example.com/whitepaper.pdf]
访问密码: [自动生成] 或 [手动设置]
发放方式: 中奖后自动发送链接+密码
```

实现方式：复用 `prize_codes` 表，`code` 存访问码，`secret` 存链接。中奖后返回给用户。

## 三、场景适配表

| 场景 | 推荐模式 | 操作步骤 | 注意事项 |
|:-----|:---------|:---------|:---------|
| **Telegram 社群抽奖** | `code`（卡密） | 导入卡密 → 配置奖项 → 开奖 | 卡密码池要充足，避免中奖后无码 |
| **B2B 白皮书领取** | `virtual`（虚拟资料） | 配置资料链接 → 参与者提交邮箱 → 自动发放 | 链接建议用短链+密码，防爬取 |
| **课程/训练营报名** | `manual_fulfillment` | 配置课程奖品 → 中奖后手动联系 | 建议填 fulfillment_note 说明联系方式 |
| **内测码发放** | `auto_generate` | 设置数量 → 自动生成 → 参与发放 | 码格式要避免易混淆字符（0/O, 1/l） |
| **进群邀请** | `instant`（即时发放） | 配置群链接 → 参与即发放 | 适合人人有奖，需限流防刷 |
| **优惠券核销** | `code`（卡密） | 导入优惠码 → 中奖发放 → 线下核销 | 码要有核销状态跟踪 |
| **实体礼品** | `manual_fulfillment` | 配置礼品 → 中奖后收地址 | 需人工介入，注意时效 |

## 四、注意事项

### 4.1 安全

1. **卡密生成必须用 `crypto.getRandomValues()`**，不能用 `Math.random()`（文档 026 已明确）。
2. 码池中码被发放后立即标记 `issued`，防止重复发放（CAS 条件更新已实现）。
3. 虚拟资料链接应设置访问密码或短时效，防止爬虫盗取。

### 4.2 性能

1. 批量导入（几百上千个码）应分批写入，避免单请求超时。
2. 码池查询走 `(tenant_id, prize_id, status)` 索引，不要全表扫描。

### 4.3 数据一致性

1. `total_count` = 初始导入数 + 自动生成数 - 作废数。
2. `used_count` = 已发放数。
3. 剩余可用 = `total_count - used_count`（需修正代码实现）。

| 编号 | 断裂点 | 修复方案 | 优先级 |
|:----:|:-------|:---------|:------:|

## 六、结论

当前奖品系统已支持**卡密（code）**和**手动发放（manual_fulfillment）**两种类型，且**文本框批量导入**（每行一个码，支持 `code:secret`）已实现。

**关键缺口：**
1. `total_count`/`used_count` 参数闭环断裂（运营者无法看到码池余量）
2. 缺少自动生成卡密、文件上传、虚拟资料等便捷模式

**最优方案：** 先修复 P0 参数闭环（F-01/F-02），再补充 P1 便捷模式（自动生成/文件上传），最后实现 P2 虚拟资料。

**不建议做的：** 不做复杂的奖品 SKU 体系、不做库存预警自动化、不做奖品组合（多选奖品）——这些超出活动引擎的轻量定位。
