# 194 多项目 DB 连接模式对比与共享提取评估

> 日期：2026-08-11
> 背景：在 cf-lottery 实施 `getCachedDbClient` 修复（docs/191 §5.1）后，评估是否将该方法提取到 `@usethink/cf-core` 共享库，供 cf-auth、cf-shop、zhizhuan 复用。
> 方法：逐一检查四个项目的 DB 连接管理方式（代码验证），从创建时机、传递方式、每请求开销、Workers 兼容性四个维度对比。
> 结论：**不建议提取到 cf-core**——cf-auth 的架构从根本上避免了该问题，cf-shop 已自行实现，zhizhuan 不适用，仅 cf-lottery 需要且已实现。

## 2. 四种模式的详细分析

### 2.1 cf-auth：启动时创建 + 闭包传递（最优模式）【代码验证】

**关键文件**：`cf-auth/src/app.ts` 第 88-93 行、`cf-auth/src/db/client.ts`

```typescript
// app.ts —— 启动时一次性创建
export async function createApp(options: CreateAppOptions = {}) {
  const env = options.env ?? ({} as Bindings);
  // 只在 createApp() 时执行一次，不是每请求
  const { createDbFromUrl } = await import("./db/client");
  const { client, db } = createDbFromUrl({
    url: config.databaseUrl,
    authToken: config.databaseAuthToken,
  });
  // 路由通过闭包引用 resources.db，不经过中间件
  // 如：resources.db.select(...) 直接调用
  return { app, resources: { db, ... } };
}
```

**特点**：
- **创建时机**：`createApp()` 启动时，应用生命周期内仅一次
- **传递方式**：闭包引用（`resources.db`），路由处理函数直接访问
- **每请求开销**：**0**——无中间件操作，无 Map 查找，无 Promise 解析
- **env 来源**：`options.env`（启动时固定，来自 server.ts 或 Worker 入口）
- **连接数**：应用生命周期内 1 个连接，无缓存逻辑

**优势**：不需要任何连接缓存——架构上避免了"每请求 createClient"问题。

### 2.2 cf-lottery：中间件 + 缓存池（修复后模式）【代码验证】

**关键文件**：`cf-lottery/src/index.ts`（`getCachedDbClient` 函数 + DB 中间件）

```typescript
// 修复后：缓存池 + 中间件
const dbClientCache = new Map<string, Client>();
const dbClientPending = new Map<string, Promise<Client>>();

export async function getCachedDbClient(url: string, token?: string): Promise<Client> {
  const key = `${url}|${token || ""}`;
  // 缓存命中直接返回
  const cached = dbClientCache.get(key);
  if (cached) return cached;
  // 并发防抖：只创建一次
  let pending = dbClientPending.get(key);
  if (!pending) { ... }
  return pending;
}

// 中间件每请求执行（但 client 已缓存复用）
app.use("*", async (c, next) => {
  const url = getEnv(c, "TURSO_URL");
  if (url) {
    const client = await getCachedDbClient(url, getEnv(c, "TURSO_TOKEN"));
    c.set("db", createDb(client));
  }
  await next();
});
```

**特点**：
- **创建时机**：首请求时创建，后续请求从缓存获取
- **传递方式**：中间件注入（`c.set("db", db)` → 路由 `getDb(c)`）
- **每请求开销**：Map 查找 + Promise 解析（微秒级，可忽略）
- **env 来源**：`c.env.TURSO_URL`（请求级，Workers 支持动态）
- **连接数**：缓存池中按 (url, token) 键存储，实践中 1 个

**为什么设计成中间件模式**：`index.ts` 是模块级初始化（`new Hono()` + 注册路由），DB 连接依赖 `c.env` 在请求时注入，所以设计成了中间件模式。但实际 Workers 环境中 `c.env` 在 isolate 内固定，理论上也可以改成启动时创建模式。

### 2.3 cf-shop：中间件 + 自行实现 isolate 级缓存【代码验证】

**关键文件**：`cf-shop/src/db/database.ts`

```typescript
// 自行实现的 isolate 级缓存（与 cf-lottery 的 getCachedDbClient 思路一致）
let _cachedUrl: string | undefined;
let _cachedToken: string | undefined;
let _cachedClient: Client | undefined;
let _cachedDb: DbType | undefined;

export function initDatabase(env: { TURSO_URL?: string; TURSO_TOKEN?: string }) {
  const url = env.TURSO_URL;
  if (!url) throw new Error("TURSO_URL is required");
  // 同 URL + 同 token 直接返回缓存实例
  const token = env.TURSO_TOKEN || "";
  if (_cachedClient && _cachedDb && _cachedUrl === url && _cachedToken === token) {
    return { client: _cachedClient, db: _cachedDb };
  }
  const client = createClient({ url, authToken: env.TURSO_TOKEN });
  const db = createDb(client);
  _cachedUrl = url; _cachedToken = token; _cachedClient = client; _cachedDb = db;
  return { client, db };
}
```

**特点**：与 cf-lottery 的 `getCachedDbClient` 思路一致，但实现更简单（无并发防抖）。注释明确写了"节省 ~1ms CPU"。

### 2.4 zhizhuan：不使用 `@libsql/client`【代码验证】

zhizhuan 的 `package.json` 中没有 `@libsql/client` 或 `drizzle-orm` 依赖，使用其他数据库方案（如 Prisma 或 TypeORM），不适用 `getCachedDbClient` 优化。

## 3. 三种模式对比

| 维度 | **cf-auth（启动时创建）** | **cf-lottery（中间件+缓存池）** | **cf-shop（中间件+变量缓存）** |
|------|:---:|:---:|:---:|
| **创建时机** | 启动时 1 次 | 首请求时创建，后续缓存 | 首请求时创建，后续缓存 |
| **传递方式** | 闭包引用 `resources.db` | 中间件 `c.set("db", db)` | 中间件 `c.set("db", db)` |
| **每请求开销** | **0**（无中间件操作） | Map 查找 + Promise 解析（微秒级） | if 判断 + 变量读取（纳秒级） |
| **env 来源** | `options.env`（启动时固定） | `c.env.TURSO_URL`（请求级） | `c.env.TURSO_URL`（请求级） |
| **连接数** | 1 个（单例） | 缓存池按 key 存储（实践 1 个） | 缓存变量（实践 1 个） |
| **并发安全** | 无需（启动时单线程） | pending Promise 防抖 | 无防抖（首请求并发重复创建，浪费 1 个连接） |
| **Workers 兼容** | ✅ env 在 `createApp()` 时注入 | ✅ c.env 请求级读取 | ✅ c.env 请求级读取 |
| **代码量** | 无额外代码 | ~30 行 | ~20 行 |
| **复杂度** | 最低 | 中 | 低 |

## 4. 为什么 cf-auth 不需要连接缓存

**核心原因**：cf-auth 的架构从根本上避免了"每请求 createClient"问题。

cf-auth 的 `createApp()` 是一个**工厂函数**，接收 `env` 参数后一次性完成所有初始化（DB 连接、邮件发送器、策略缓存等），然后通过 `resources` 对象 + 闭包将 `db` 注入到路由处理函数中。路由函数直接使用 `resources.db`，不需要从 `c.env` 读取 URL，不需要经过任何中间件。

cf-lottery 的 `index.ts` 是**模块级初始化**（模块顶层 `new Hono()` + 注册路由），DB 连接依赖 `c.env` 在请求时通过中间件注入。虽然 Workers 环境中 `c.env` 在 isolate 内固定，但设计上保留了请求级动态读取的能力。

**结论**：cf-auth 不需要连接缓存，因为它的架构设计从一开始就避免了这个问题。这不是"cf-auth 做得更好"或"cf-lottery 做得更差"的区别，而是两种架构设计范式的差异——**工厂函数模式 vs 模块级初始化模式**。

## 5. 提取到 cf-core 的评估

### 5.1 收益分析

| 潜在收益 | 是否成立 | 说明 |
|----------|:---:|------|
| 减少重复代码 | ❌ | 仅 cf-lottery 需要（已实现）；cf-shop 已有（`database.ts`）；cf-auth 不需要；zhizhuan 不适用 |
| 统一连接管理规范 | ❌ | 三种模式的差异源于架构设计范式不同，不是连接管理方式不同，统一无意义 |
| 降低维护成本 | ❌ | 提取到 cf-core 需要：导出类型定义 → 增加测试覆盖 → 版本发布 → 三个消费方同步升级。维护成本远高于各项目 20-30 行自行实现 |
| 修复潜在性能问题 | ❌ | 只有 cf-lottery 修复了，cf-auth 没有此问题，cf-shop 已自行修复 |

### 5.2 成本分析

| 成本项 | 说明 |
|--------|------|
| **职责边界破坏** | cf-core 当前是纯工具库（export helpers / schemas / types），`getCachedDbClient` 是有状态的进程级连接池管理器——引入有状态模块改变 cf-core 的职责边界 |
| **类型暴露** | 需要导出 `Client` 类型，增加 `@libsql/client` 依赖的暴露面 |
| **测试覆盖** | 需要单元测试（缓存命中/隔离/并发防抖）+ 集成测试（真实 libsql 连接），跨项目测试配置复杂 |
| **版本管理** | cf-core 的版本号与 cf-lottery/cf-auth/cf-shop 的发布节奏耦合，升级需要协调 |
| **文档成本** | 需要写使用文档、迁移指南 |

### 5.3 综合评估

```
收益：几乎为零（仅 cf-lottery 需要，且已实现）
成本：中等（职责边界破坏 + 测试 + 版本 + 文档）
结论：不建议提取
```

## 6. 结论与建议

### 6.1 结论

**不建议将 `getCachedDbClient` 提取到 `@usethink/cf-core` 共享库。** 理由：

1. **cf-auth 不需要**——它的"启动时创建 + 闭包传递"架构从根本上避免了每请求 createClient 问题；
2. **cf-shop 已有**——`database.ts` 中自行实现了 isolate 级缓存，与 cf-lottery 的 `getCachedDbClient` 思路一致；
3. **zhizhuan 不适用**——不使用 `@libsql/client`；
4. **唯一需要此优化的 cf-lottery 已实现**——`getCachedDbClient` 已通过测试和 VPS 验证。
5. **提取到 cf-core 的维护成本远大于收益**——职责边界破坏、测试覆盖、版本管理、文档成本。

### 6.2 建议

1. **各项目保持现有模式不变**——cf-auth 的启动时创建模式、cf-lottery 的缓存池模式、cf-shop 的变量缓存模式，各自工作良好；
2. **新项目参考 cf-auth 的工厂函数模式**——如果新项目使用 `@libsql/client` 且部署在 VPS/Node 环境，优先采用"启动时创建 + 闭包传递"模式，彻底避免每请求 createClient 问题；
3. **如果未来 cf-core 需要导出 DB 连接工具**——应设计为**无状态的工厂函数**（如 `createDbFromUrl(options)`，不缓存连接），让消费方自行管理连接生命周期，保持 cf-core 的纯工具库职责。当前 cf-auth 的 `db/client.ts` 已经导出了 `createDbFromUrl`——这个模式就是正确的。
