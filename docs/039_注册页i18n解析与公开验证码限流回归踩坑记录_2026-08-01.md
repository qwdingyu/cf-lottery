# 注册页 i18n 解析与公开验证码限流回归踩坑记录

## 背景

在 Cloudflare Workers + Turso 免费组合下，我们在修复公开验证码限流和注册流程配置化时，顺手暴露了两个真实问题：

1. `public-lottery.ts` 的验证码接口限流代码被改坏，导致 Worker 构建失败。
2. 管理后台注册页的邮箱 placeholder 放在 `vue-i18n` 文案里，且包含裸 `@`，导致页面渲染时报 `SyntaxError: 10`。
3. 注册链路依赖 `users.email_verified`，但仓库迁移目录曾缺少对应 migration，导致测试库按 migrations 重建后和 `schema.ts` 不一致。

## 原因

1. `public-lottery.ts` 中 `access-code` 接口的 `if (!checkRateLimit(...))` 结构被破坏，少了条件判断，直接留下悬空 `return`。
2. `vue-i18n` 会把 `@` 当作消息语法的一部分解析，`your@email.com` 这种写法不适合直接放进翻译目录。
3. `t(key, {}, { default })` 也会把 `default` 当作 i18n message 编译；如果 default 来自后端配置定义，里面出现邮箱、URL、Webhook payload 示例等普通文本，同样可能触发运行时 SyntaxError。
4. Cloudflare 线上旧哈希资源可能仍可访问，用户浏览器如果还持有旧 HTML 或旧 SPA 运行态，会继续加载旧 `index-*.js`，因此修复后必须用线上真实浏览器验证当前 HTML 引用的新包。
5. Drizzle schema 不是数据库事实来源；Cloudflare/Turso 新环境、测试库、生产库最终都只能依赖 `migrations/` 形成结构。只改 `schema.ts` 不补 migration 会制造“线上碰巧可用、本地或新库必炸”的隐患。

## 排查过程

1. 先用 `npm run type-check:all`、`npm run test`、`npm run frontend:build` 复现问题。
2. 通过 `wrangler deploy` 的打包报错定位到 `src/routes/public-lottery.ts:252`。
3. 通过浏览器控制台的 `SyntaxError: 10`，结合注册页模板和 `frontend/src/i18n/*`，确认是 `emailPlaceholder` 文案触发了 `vue-i18n` 解析错误。
4. 2026-08-02 复查线上 `https://lucky.eforge.xyz/admin/login?redirect=/admin`：当前 HTML 已引用新包 `/assets/index-BircteWc.js`，用户报错中的 `/assets/index-h2l3MR7E.js` 仍被 Cloudflare 命中缓存但不是当前 HTML 入口。
5. 用 Playwright 打开线上登录页、切换注册、填写 `codex_*@example.com` 邮箱并提交，接口返回 `200 {"ok":true,...}`，页面进入验证码步骤，未出现 `SyntaxError: 10`。
6. 跑全量测试时发现共享测试库缺少 `users.email_verified`，反查 `migrations/` 确认没有任何 `ALTER TABLE users ADD COLUMN email_verified`，定位为 schema 与 migration 漂移。

## 解决方案

1. 恢复 `public-lottery.ts` 的验证码限流判断，并让它读取 `rate_limit_access_code` 系统配置。
2. 将注册页邮箱 placeholder 改为不含 `@` 的普通文案。
3. 把 i18n 里所有裸 `@` 示例改成安全表达。
4. 增加 `src/i18n-message-sanity.test.ts`，使用 `@intlify/message-compiler` 真实编译消息目录，让裸 `@`、非法花括号、非法 linked message 等语法问题在测试阶段直接失败。
5. `ConfigField.vue` 不再把后端系统配置定义作为 `t(..., { default })` 传入编译器；翻译 key 存在时使用翻译，不存在时直接展示后端原文，避免后端普通文本被前端 i18n 语法误伤。
6. 新增 `migrations/0024_users_email_verified.sql`，把注册链路依赖的邮箱验证状态纳入正式迁移；测试库和新部署环境统一从 migrations 得到该列。

## 建议

1. 所有进入 `vue-i18n` 的字符串都默认按“会被语法解析”处理，不要把邮箱、链接、Handle 直接原样塞进去。
2. 业务限流配置化时，要保留最小静态测试，避免条件分支被误删后才在部署阶段暴露。
3. 对 Worker 入口和公开路由的改动，最好配一个能直接跑的回归测试，别只靠人工点页面。
4. 对用户报告的线上哈希文件名，要同时检查“当前 HTML 引用”和“旧哈希资源是否仍可访问”；两者不一致时，优先判断是否为旧浏览器会话或缓存，再做真实浏览器复现。
5. 不要用 `t(key, {}, { default: userOrServerText })` 渲染不受控文本。正确做法是先用 `te(key)` 判断翻译是否存在，不存在就把普通文本直接绑定到模板。
6. 每次新增 `schema.ts` 字段必须同步新增 migration，并至少用“空库跑 migrations + 一条读写该字段的测试”验证。不要让生产库手工改动成为唯一事实来源。
