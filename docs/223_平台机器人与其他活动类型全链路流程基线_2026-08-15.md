# 223 平台机器人（QQ/Telegram）与其他活动类型全链路流程基线

> 日期：2026-08-15
> 状态：流程基线，后续开发、UI 调整、测试和运营手册均以本文为准。
> 范围：QQ 群助手与 Telegram Bot 的入站-命令-出站闭环；除秒杀/批发（docs/222）外的全部活动类型
> （lottery 抽奖、signup_chain 报名链、waitlist 候补、reservation 预约、claim 领取、checkin 签到、
> approval 审批、vote 投票、survey 问卷）从定义、参与、结果到结束的闭环。
> 关联：docs/167、docs/168、docs/170、docs/173、docs/174、docs/176、docs/179、docs/180、docs/222。

## 1. 本文的目的

docs/222 已固定秒杀/批发流程。本平台还有两套高频业务没有统一的流程基线：

1. **QQ 群助手 / Telegram Bot**：群成员用 `/命令` 参与活动、签到、抽奖、查卡密，涉及入站鉴权、
   平台身份、命令开关、出站投递的完整闭环；
2. **其他活动类型**：抽奖、报名链、候补、预约、领取、签到、审批、投票、问卷——它们共享
   同一个参与主路径（joinDraw），但结果产生方式、容量语义、表单提交各不相同。

不先固定这两套流程，后续修 UI/接口时会出现：命令开关与业务函数不一致、平台身份无法恢复、
投票/问卷提交结构与后端校验不符、签到按本地/UTC 日期漂移等同类灾难。

本文所有描述均基于当前代码事实（`src/services/platform/*`、`src/services/lottery/*`、
`src/lib/activity-utils.ts`、`src/routes/public-lottery.ts`），不引入尚未实现的设想。

## 2. 平台机器人总体架构

### 2.1 双平台共用一套命令服务

QQ 与 Telegram 不各自实现业务逻辑，共用 `src/services/platform/` 下的统一命令服务：

```text
QQ 群消息 ──► platform-qq.ts  POST /message ──┐
                                             ├─► handleInboundPlatformEvent (inbound.ts)
Telegram ──► platform-telegram.ts POST /message ─┘        │
                                                          ▼
                                             recognizeBuiltinCommand（识别 /命令）
                                                          │
                                             getActivePlatformTarget（群/会话 → 租户+活动）
                                                          │
                                             isCommunityFeatureEnabled（L3 全局开关）
                                                          │
                                             provisionPlatformUser（平台身份建档，失败降级）
                                                          │
                                             executeBuiltinPlatformCommand（9 个命令 handler）
                                                          │
                                             enqueuePlatformEvent / enqueuePrivatePlatformMessage
                                                          ▼
                                             dispatchPlatformDeliveries（维护 cron 批量投递）
```

关键事实（代码核实）：

- 两个平台的路由都是 `POST /message`，用**共享密钥鉴权**（入站密钥哈希对比），不走平台后台 JWT；
  - QQ：`Authorization: Bearer <token>` 或 `X-CF-Lottery-Platform-Token` header；
  - Telegram：官方 `X-Telegram-Bot-Api-Secret-Token` header（query `secret` 仅兼容旧 webhook）；
- QQ 入站只接受 `message_type = group` 的群消息；Telegram 支持群组（chatId 以 `-100` 开头）与
  用户聊天气（正数 ID）两种目标；
- Telegram 的非消息更新（callback_query、channel_post 等）直接忽略并返回 200，避免 webhook 重试风暴；
- 命令服务不硬编码平台名，`identityType` 由 `event.platform` 动态推导（`qq` / `telegram`）；
- 涉及卡密的回复默认**群内脱敏**，完整卡密走私聊或一次性 Web 访问令牌（docs/179），不能发到公开群聊；
- **私聊卡密防窃**：私聊发送统一入 `platform_deliveries` 异步投递；私聊失败时群回复**不再追加**一次性
  accessUrl——否则群内先看到的人可抢先点击并一次性消费掉访问链接（防群内先点者窃卡）。

### 2.2 命令集合（固定，不允许租户动态新增）

| 命令 | 标识 | 默认启用键 | 业务函数 | 说明 |
|---|---|---|---|---|
| `/签到` | checkin | checkinEnabled | checkin-reward.ts | 每日签到 + 连续奖励 + 发 spins |
| `/抽奖` | spin | spinEnabled | performInstantSpin | 即时抽奖（instant 活动） |
| `/分享` | share | shareEnabled | viral-weight.ts | 生成分享链接 + 裂变加次 |
| `/排行榜` | leaderboard | leaderboardEnabled | viral-weight.ts | 邀请排行榜 |
| `/我的奖品` | my_prize | myPrizeEnabled | 查中奖/卡密 | 查询我的奖品 |
| `/秒杀` | flash | flashEnabled | `executeFlashCommand` | 购买承接链接引导；不在机器人内创建参与、订单或支付 |
| `/我的卡密` | card_code | myCardCodeEnabled | 查卡密 | 我的卡密（脱敏 + 链接） |
| `/帮助` | help | 恒可用 | renderHelpReply | 帮助 |
| `/绑定` | bind | 恒可用 | binding.ts | 跨平台身份绑定（docs/179） |

执行约束（代码核实）：

- 命令未启用 → 回复“当前群未启用 /xxx”；
- 群已绑定但未选择活动 → 友好提示，不抛“活动不存在”；
- `help`/`bind` 不参与启用开关（恒可用）；
- 所有命令的意外异常统一兜底回复“系统繁忙”，防止 500 导致用户收不到回复（Silence 问题）；
- 未注册 handler 的命令 fail closed（不允许被误调用）。

### 2.3 入站鉴权与身份

**群绑定与密钥**（代码核实）：

- 每个平台目标（QQ 群 / Telegram 会话）在后台绑定：`platform`、`targetId`、`inboundSecretHash`、`activeDrawId`、`activePublicSlug`、`builtinCommands`；
- 入站时用 `timingSafeEqualString` 比较入站 token 的哈希，防止时序攻击；
- QQ 端 NapCat 上报的 `self_id` 自动回填/覆盖公证人 botId（运行时权威真值，docs/177 批次2），失败静默跳过不阻塞。

**平台身份建档（Phase B，docs/176 §3.4）**：

- 自动将平台身份（provider + providerUserId）关联到本地 `users` 表；
- 失败时降级不阻断命令执行，userId 留空，命令走 `identityType/identityValue`；
- `findPlatformEntryId` 按 `(tenantId, drawId, identityType, identityValue)` 查最近一条 entry，供 /签到 /抽奖 /我的奖品 等命令复用。

**跨平台身份绑定（docs/179）**：

- `/绑定` 生成一次性绑定码，把 QQ/Telegram 身份关联到同一本地账号；
- 绑定后命令可恢复跨平台参与的同一 identity（裂变归因、卡密查询不串号）。

### 2.4 出站投递

- 命令结果经 `enqueuePlatformEvent` / `enqueuePrivatePlatformMessage` 写入 `platform_deliveries`（status=pending）；
- 维护 cron（`src/index.ts:95`）调用 `processPendingPlatformDeliveriesForAllTenants` 批量投递；
- 按 `platform` 分发到 `qq-adapter.ts`（NapCat HTTP API）或 `telegram-adapter.ts`（Bot API）；
- 私聊消息（完整卡密）走 `private_message` 投递，群消息默认脱敏；
- 投递失败记录 `lastError` 与 `attemptCount`，重试有上限；失败超限后进入人工排查。

### 2.5 社群功能全局开关（docs/174）

- L3 平台运营者可全局暂停社群功能；
- 关闭后**存量绑定**也必须停止响应命令（业务层闭环，不仅靠路由 403）；
- 命令执行前在入站层再次校验 `isCommunityFeatureEnabled`。

### 2.6 群人数上限（docs/180 §3.3）

- 命令分发前 `enforceGroupMemberCap` 校验；新成员超限拒绝，存量成员放行。

## 3. 各平台命令闭环

### 3.1 `/签到`（QQ + Telegram 共用）

```text
群消息 /签到
  → recognizeBuiltinCommand("checkin")
  → 校验 checkinEnabled 开关
  → findPlatformEntryId（找 entry；未参与 → 先 ensurePlatformEntry 建立 entry）
  → computeCheckinReward（今日是否已签、连续天数、随机事件）
  → 领取奖励：连续签到递增 spins（docs/173）+ 随机事件（docs/177）
  → recordActivityEvent("daily_checkin") + recordSpinLog
  → 回复签到成功/已签过/连续天数/获得 spins
```

代码事实：

- 签到按 `todayStr()`（本地时区，`src/lib/date-utils.ts`）计算“今日”，与公开端每日免费同源；
- 签到活动的 entry 唯一约束用 `identity_value` 追加日期后缀（`checkinDateSuffix`），允许每日签到但禁止同一天重复；
- 奖励发放走正式 `recordSpinLog`（spins 流水审计），不直接改余额字段。

### 3.2 `/抽奖`（instant 活动）

```text
群消息 /抽奖
  → 校验 spinEnabled 开关
  → findPlatformEntryId / ensurePlatformEntry
  → performInstantSpin（复用公开端同一结果机，docs/116）
  → 中奖：原子锁码 → recordSpinLog → 回复脱敏结果（卡密走私聊/链接）
  → 未中：回复结果 + 剩余次数
```

代码事实：

- 复用 `spin-execution.ts` 的 `performInstantSpin`，与公开端完全一致（保底、每日免费、卡密池、并发安全全部生效）；
- 保底/每日免费/里程碑等增长配置对 bot 抽奖同样生效（同一函数）；
- 卡密回复默认群内脱敏。

### 3.3 `/分享` 与 `/排行榜`

```text
/分享 → 生成分享链接（buildPublicSharePath）+ 返回分享语
/排行榜 → aggregateViralInviteCounts（与公开排行榜同一聚合函数）
```

代码事实：

- 排行榜与开奖权重共用 `aggregateViralInviteCounts`，避免“榜上人数 ≠ 开奖权重”静默分叉；
- 分享归因写入 `activityEvents("attributed_join")`，与公开端同源。

### 3.4 `/我的奖品` 与 `/我的卡密`

```text
/我的奖品 → 查 lotteryWinners / 奖品码（脱敏）
/我的卡密 → 查已发卡密 → 群内脱敏 + 生成一次性 Web 访问令牌链接（generateAccessToken, docs/179）
```

代码事实：

- 完整卡密不进群聊，通过 `generateAccessToken` 生成一次性查看链接；
- 令牌一次性、有时效（docs/179），防群内泄漏。

### 3.5 `/秒杀`（购买承接链接）

```text
/秒杀
  → 校验 flashEnabled 与 purchaseConfig.url
  → 返回 purchaseConfig.label + purchaseConfig.url
  → 用户在浏览器打开链接
  → 若链接是本系统公开活动页：才进入公开页的参与、支付和履约流程
```

代码事实与边界：

- 机器人命令不调用 `joinDraw`，不创建 `lottery_entries`、`payment_orders`，也不直接处理支付或卡密；
- `admin/draws` 已经完整承载秒杀/批发活动定义：`claim + flash_sale` 的展示导流、站内直付单件和站内直付多件，公开活动页负责身份验证、参与、下单、支付与履约；
- 平台目标保存 `activeDrawId` 和 `activePublicSlug`，它们用于其他群命令和活动消息投递；`/秒杀` 在没有显式外链时，会读取当前绑定活动并生成该活动的公开页链接；
- 只有活动仍为公开 `open` 状态、可见且启用了 `flash_sale` 壳时，才允许作为默认承接目标。活动暂停、隐藏、替换或不是秒杀活动时，机器人不会继续生成旧活动链接；
- `purchaseConfig.url` 是显式外部承接覆盖：保存和执行时均要求安全的 `http/https` URL，拒绝本机地址、脚本协议和含用户名/密码的 URL。它仍可覆盖绑定活动，因此必须在后台按“外部覆盖”而不是活动事实来源理解。

**当前代码的规范性结论**：`/秒杀` 是“平台目标级的浏览器购买承接命令”，不是机器人直付 API。它可以把用户带到本系统公开秒杀页，也可以带到外部商城；但这两种承接都必须在活动创建中有完整、可发布的活动定义，不能由机器人链接替代。

**后续改造的强制规则**：

1. 不得把机器人直接接入邮箱 OTP、支付订单或卡密履约链路；这会绕开公开页已实现的身份和订单安全边界。
2. 若 `/秒杀` 服务于绑定活动，默认链接必须由服务端根据 `activePublicSlug + APP_ORIGIN` 生成，且仅在该活动仍可公开承接时返回。
3. 若必须保留外部链接，必须显式建模为“外部承接覆盖”，服务端校验安全 URL，并在后台清楚展示其覆盖的活动与风险；不得把自由文本 URL 伪装成活动事实来源。
4. 外部覆盖不会随活动暂停、结束或换场自动失效；运营启用覆盖前必须确认这是有意绕过默认活动承接，而不是临时复制链接。

### 3.6 `/绑定`

```text
/绑定 → generateBindingCode（生成一次性绑定码）→ 用户到网页端完成跨平台关联
```

代码事实：绑定码一次性、有时效（docs/179），绑定成功后命令按同一本地账号恢复身份。

## 4. 其他活动类型闭环

### 4.1 活动类型 → 默认体验 → 默认结果模式（代码事实，`activity-utils.ts`）

| activityKind | 默认体验 | 默认结果模式 | 结果产生方式 |
|---|---|---|---|
| lottery | wheel | manual / scheduled | performDraw 统一开奖 |
| signup_chain | list | ordered_assignment | 按报名顺序分配 |
| waitlist | queue | ordered_assignment | 按候补顺序分配 |
| reservation | calendar | capacity_assignment | 按容量分配 |
| claim | reveal | instant | 即时领取 |
| checkin | checkin | no_result | 无结果分配（每日签到） |
| approval | form | review_decision | 运营审批决定 |
| vote | ballot | vote_tally | 计票展示 |
| survey | form | no_result | 无结果分配（统计展示） |

### 4.2 参与主路径（所有类型共用 joinDraw）

```text
公开 POST /draws/:slug/verify-join（或 join）
  → 时间窗校验（startAt/endAt）
  → 身份校验：Bearer JWT 免 OTP / 邮箱验证码核销
  → participationMode 分支：open / roster / password / invite_code
  → 容量检查：秒杀走活动级计数器 CAS；普通活动走条件 INSERT（maxParticipants）
  → 插入 lottery_entries（UNIQUE(identity_type, identity_value, draw_id) 防重复参与）
  → 裂变归因：refCode → shareRecords.joinedCount +1 + activityEvents("attributed_join")
  → vote/survey：validateSubmissionPayload 校验并存储提交内容
  → checkin：identity_value 追加日期后缀（每日一签）
  → 返回 entryId + 结果模式 + instant 时的 spins 字段
```

代码事实：

- `vote`/`survey` 的提交在 `validateSubmissionPayload`（`activity-config.ts`）校验：
  - vote：必须选择合法的 optionId；
  - survey：逐字段校验（必填、长度、选项白名单、邮箱格式），最大提交体积 `MAX_SUBMISSION_BYTES`；
- 已参与重复提交返回 409（“您已参与此活动”），由 `UNIQUE` 约束兜底；
- 秒杀售罄透传 `soldOut: true` + `code: "flash_sale.sold_out"`（docs/222 §8 边界）。

### 4.3 结果产生（按结果模式分支）

#### 4.3.1 instant（claim、lottery+instant）

- 参与即返回结果；抽奖类走 `performInstantSpin` 结果机（docs/116）；
- 结果当场落库（lotteryWinners / 卡密 issued），无需统一开奖。

#### 4.3.2 manual / scheduled（lottery）

```text
performDraw（draw-execution.ts）
  → 拒绝 instant（防双结果机）
  → CAS 原子夺取开奖权（open → drawing）
  → 生成随机种子 + SHA-256 记录（公平性可验证）
  → 候选池：直付秒杀（paymentRequired）只允许 PAID entry 进入（纵深防御）
  → 裂变加权（按权无放回）或等权 Fisher-Yates（randomSelect）
  → 事务内写入 winners + 原子锁码（子查询 UPDATE + returning 消除 TOCTOU）
  → 邮件通知（失败不回滚开奖）
  → 排行榜奖励自动发放（docs/218 模式三）
  → drawing 卡死活动：healDrawingState 治愈（回滚 open 重试 或 判定已 drawn）
```

#### 4.3.3 ordered_assignment（signup_chain / waitlist）

- 按报名/候补顺序分配名额，不抽奖；
- `acceptsWaitlist`：signup_chain 与 waitlist 且 allocationPolicy=waitlist 才允许候补；
- 候补不占容量（满额后排队），秒杀不做候补（满即拒）。

#### 4.3.4 vote_tally（vote）

- 结果模式 = 计票展示；参与提交 optionId 落库；
- 无“开奖”动作，前端展示票数统计（`activityConfig.kind === "vote"` 的 options 聚合）。

#### 4.3.5 no_result（survey / checkin）

- 无结果分配；survey 只收集问卷数据，checkin 只记录每日签到；
- 展示由前端按提交内容/签到记录渲染。

#### 4.3.6 review_decision（approval）

- 参与提交待运营审批，结果由审批决定。

#### 4.3.7 capacity_assignment（reservation）

- 按容量占用；满即拒，不候补。

### 4.4 结果查询

```text
POST /draws/:slug/my-result（邮箱+验证码）
POST /draws/:slug/result（弱会话）
GET  /draws/:slug（公开详情，promotionConfig 脱敏）
```

代码事实：

- 公开详情 `sanitizePublicPromotionConfig` 剔除内部激励参数（保底阈值、每日免费、里程碑、排行榜奖励明细），防用户精确推算；
- `my-result` 与 `result` 都受公开限流（10 次/分钟/IP 等）；
- 卡密与订单号展示复用同一数据源（docs/102），区分中奖卡密与直付订单号。

### 4.5 活动结束

```text
手动取消：cancelDraw（admin 端）
到期结束：endAt 后拒绝新参与/新订单；存量 pending 订单在允许的活动状态下可恢复支付
暂停/恢复：PAUSED ↔ OPEN（暂停期间可恢复已有 pending 订单，不能创建新订单）
```

代码事实：

- 时间窗校验在参与入口（joinDraw）与支付创建（payment-service）双层执行；
- 活动结束不删除数据，仅停止新参与；存量订单按支付/履约状态继续收尾（docs/222 §11.1）。
- `open` / `paused` 活动按是否已有 `entry`、订单或结果记录分层：三者均不存在时，允许修正完整配置，
  适用于“候选池为空”等零参与活动；一旦任一事实存在，只允许修改标题、说明、结束时间延长、展示开关、
  预计参与数和外部承接链接。活动类型、参与模式、体验、结果模式、开始时间、容量、支付/奖项/裂变配置
  均不可变。后台编辑入口必须按此分层展示说明，不能暗示增长配置等已锁定字段仍可保存。进行中活动的紧急下架必须走 `pause` / `cancel`，不能通过 `visible=0` 让公开列表消失而
  持有链接的用户仍处于参与或支付流程。
- 大转盘的视觉反馈必须遵守“服务端确认后播放、动画完成后提示”：提交中只允许轻量等待反馈；
  delayed/manual/scheduled 只表达“参与成功”，不能把停留扇区解释为中奖；instant 必须使用服务端返回的奖品索引，
  并在转盘停稳后再展示真实中奖或未中奖提示。
- 即时转盘的每个扇区必须是用户可理解的权益/奖品名称；卡密是履约凭据，不应作为唯一的扇区文案，
  更不能在用户不知道额度或权益内容时暗示其价值。此类场景优先使用明确的卡密领取/结果查询流程，
  或在活动定义中补齐奖品说明、价值文案和使用限制后再启用即时转盘。

## 5. 活动事件体系（全链路审计）

事件类型（`activityEvents`，代码事实）：

| 事件 | 含义 |
|---|---|
| participation_completed | 参与完成 |
| participation_cancelled | 参与取消 |
| outcome_assigned | 结果已分配 |
| cta_impression / cta_click | 导流 CTA 展示/点击 |
| share_created / share_click | 分享创建/点击 |
| attributed_join | 归因加入（裂变） |
| external_conversion_reported | 外部转化上报 |
| reward_earned | 奖励意图已生成（通知中转站发卡） |
| penalty_requested | 处罚请求已发起 |
| ext:member.left_group | 外部事件：退群上报 |
| ext:reward.issued | 外部事件：中转站回传发卡确认 |
| ext:penalty.executed | 外部事件：处罚执行确认 |
| ext:reward.redeemed | 外部事件：兑换码核销确认（docs/114） |
| daily_checkin | 平台签到 |

代码事实：

- 事件表带 `(tenantId, drawId, eventType, createdAt)` 复合索引，用于波及名单/处罚反查（docs/114）；
- `shareRecords.joinedCount` 是聚合计数不存明细，退群波及名单用 `activityEvents("attributed_join")` 反查；
- Webhook 投递（`enqueueWebhookEvent → dispatchWebhookDelivery`）与平台投递（`enqueuePlatformEvent → dispatchPlatformDeliveries`）是两套独立队列，互不阻塞。

## 10. 最终验收标准

以下问题全部回答“是”才算闭环：

- QQ 与 Telegram 是否共用同一套命令语义与业务函数？
- 入站是否共享 token 鉴权且不伪造公开 email/OTP API？
- 卡密是否默认群内脱敏，完整码只走私聊/一次性链接？
- L3 全局关闭后存量绑定是否停止响应？
- /绑定 后跨平台身份是否可恢复？
- 各活动类型的默认体验/结果模式是否与 `activity-utils.ts` 一致？
- vote/survey 提交是否经 `validateSubmissionPayload` 校验？
- instant 活动是否只用 spin 结果机、拒绝 performDraw 双开奖？
- 直付秒杀开奖候选池是否只允许 PAID entry？
- 公开详情是否脱敏内部激励参数？
- 活动事件是否全程可审计（参与/结果/分享/归因/转化/处罚/签到）？
- 多租户之间是否互不看到、占用、投递对方的数据？

本文所定义的状态、字段来源、参与与结果口径，与 docs/222 共同构成活动引擎的完整流程基线，
后续 UI、API、测试和运营文档均以此为准。
