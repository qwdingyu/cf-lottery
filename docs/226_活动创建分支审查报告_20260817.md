## 发现的问题

### 🔴🔴 P0 灾难级漏洞（已用测试验证，2026-08-17）

#### P0: PATCH 时间校验被 Invalid Date 绕过——已发布活动可被永久开放参与

**文件：** `src/routes/admin-lottery.ts:921-928`（PATCH /draws/:id 时间校验段）

**问题：** PATCH 用 `new Date(startAt) >= new Date(endAt)` 比较时间顺序，但**没有先校验日期合法性**。`new Date("")` / `new Date("not-a-valid-date")` 得到 Invalid Date，任何与 NaN 的比较（`NaN >= x`）恒为 `false` → **校验静默通过**。

**已验证的攻击路径（测试 `src/routes/patch-time-validation.test.ts`）：**
1. 创建 lottery 活动 → 发布（open）→ 有用户参与（hasLifecycleFacts=true）
2. `PATCH /api/admin/draws/:id` 传 `{ endAt: "" }` 或 `{ endAt: "not-a-valid-date" }`
3. `LIVE_SAFE_FIELDS` 白名单**包含 endAt**（设计意图：允许延长），且 `new Date("").getTime() < currentEnd` = `NaN < currentEnd` = false → 校验通过
4. **DB 中 endAt 被写入 `""` 或 `"not-a-valid-date"`（测试确认）**
5. 参与流程 `now > new Date("")` = `now > Invalid Date` = false → **活动永久开放参与，永远不会结束**
6. 该活动已发布（open），**不再经过发布预检**（预检只拦 draft → open）→ 无安全网

**同源问题：**
- `startAt` 同样可被写入无效值（`now < new Date("")` = false → 参与无开始限制）
- `drawAt` 清空（`body.drawAt = null`）时，`body.drawAt ?? draw.drawAt` 会取旧值参与校验，导致"想清空开奖时间却被旧 drawAt 误拦截"（边界 bug）
- 若同时清空 startAt 和 endAt，活动在**任意时间**都可通过时间窗口校验

**修复建议（必须）：**
1. PATCH 校验时间前，先验证 `startAt/endAt/drawAt` 为合法 ISO 时间（与 createDraw 的 `Number.isNaN(start.getTime())` 校验一致）
2. 空字符串/非法值直接 400 拒绝
3. drawAt 清空逻辑改为显式 `"drawAt" in body` 判断，不用 `??` 合并旧值

**公开端影响确认：** `resolvePublicJoinWindow` 对 Invalid Date 的防御（`Number.isNaN` 检查）恰好**帮了攻击者的忙**——无效时间被视为"无时间限制"，返回 `canJoin: true`。joinDraw 内部 `now > new Date("")` 同样不拦截。**完整攻击链已确认。**

**修复建议（必须）：**
1. PATCH 校验时间前，先验证 `startAt/endAt/drawAt` 为合法 ISO 时间（与 createDraw 的 `Number.isNaN(start.getTime())` 校验一致）
2. 空字符串/非法值直接 400 拒绝
3. drawAt 清空逻辑改为显式 `"drawAt" in body` 判断，不用 `??` 合并旧值

**风险等级：** 🔴🔴 **P0。已发布活动可被一键破坏参与时间约束；修复后支持通过 PATCH 合法时间值直接覆盖恢复。**

### 🔴 严重问题（可能导致数据错误或运营事故）

#### P1: 复制接口绕过活动配额和白名单

**文件：** `src/routes/admin-lottery.ts:618-693`

**问题：** POST /draws/:id/copy 直接 `db.insert(lotteryDraws)`，**不调用 `enforceTenantActivityQuota`**，**不检查 `enabled_activity_kinds`**。租户可无限复制活动绕过 maxActivities 限制（免费版最多 10 个活动，复制可无限创建）。

**影响：**
- 活动数量配额完全失效（L3 运营通过 `plan_free_max_activities` 设的硬上限被绕过）
- 已关闭的活动类型（如 `enabled_activity_kinds` 中去掉 `signup_chain`）仍可被复制
- 直付秒杀活动复制后引用同一 prize pool → 发布预检会拦截共享卡密池，但配额已无意义

**修复建议：** 复制接口先调用 `getTenantUsage` 校验活动数量配额，再检查 `enabled_activity_kinds`。

**风险等级：** 🔴 **P1。配额保护失效，但不会直接破坏已有活动。**

---

#### P2: `coerceEnum` 静默降级——非法枚举值不报错

**文件：** `src/routes/admin-lottery.ts` 共 14 处使用 coerceEnum

**问题：** `coerceEnum(value, allowed, fallback)` 在 value 不在 allowed set 中时**静默返回 fallback**，不报错。

**举例：** API 调用 `POST /admin/draws` 传 `activityKind: "hacker"` → 后端静默降级为 `"lottery"`，创建了一个 lottery 活动。用户以为创建了自定义类型，实际是 lottery。

**影响范围：** activityKind、participationMode、experienceType、drawTrigger、resultMode、allocationPolicy 全部使用 coerceEnum。

**修复建议：** coerceEnum 改为非法值抛错（400 Bad Request），或提供 `coerceEnumStrict` 版本。前端框选不存在非法值，但 API 直接调用和未来 SDK 集成会遇到。

**风险等级：** ⚠️ 高。用户可能因误解而创建错误类型，发布后才发现。

---

#### P2: `winnerCount` 缺少校验导致 NaN 入库

**文件：** 
- `src/routes/admin-lottery.ts:741` 创建时：`winnerCount: body.winnerCount !== undefined ? Number(body.winnerCount) : defaultWinnerCount`
- `src/routes/admin-lottery.ts:944` 编辑时：`...(body.winnerCount !== undefined ? { winnerCount: Number(body.winnerCount) } : {})`

**问题：** `Number(body.winnerCount)` 对字符串 `"abc"` 返回 `NaN`。`createDraw` 中 `NaN < 1` 为 `false` → 不触发校验 → `NaN` 存入数据库。

**影响：** 
- lottery 活动 NaN 入库后，发布预检 `validateLotteryPrizes` 中 `draw.winnerCount !== tierWinnerTotal` 为 `true`（NaN 不等于任何数字），但**只产生 warning**，不阻断发布。
- 实际开奖时 `totalWinners = tiers.length > 0 ? tiers.reduce(...) : draw.winnerCount`。有 tiers 时用 tiers 总和，无影响。无 tiers 时无法通过发布预检（"必须至少配置一个奖项"）。

**修复建议：** 创建和编辑时对 winnerCount 使用 `normalizeOptionalPositiveInteger`（与 maxParticipants 一致）。

**风险等级：** ⚠️ 中高。目前被 tiers 安全网兜底，但若未来发布预检流程变更，可能产生灾难。

### 🟡 中等问题（运行安全但语义矛盾或数据脏）

#### P3: PATCH 可任意切换 activityKind

**文件：** `src/routes/admin-lottery.ts:933`

**问题：** PATCH 允许 draft 活动任意切换 activityKind，例如 `lottery → signup_chain` 或 `signup_chain → lottery`。中间状态数据不一致：

- lottery → signup_chain：tiers 数据残留（不 active 但占用存储）
- signup_chain → lottery：无 tiers，发布预检拦截（"必须至少配置一个奖项"）
- **危险场景**：lottery + instant + maxSpinsPerEntry=3 → PATCH 改为 signup_chain → maxSpinsPerEntry 残留 3（spin 端点拒绝非 lottery，无灾难）

**修复建议：** PATCH 修改 activityKind 时，应联动清理或重置相关字段（如 maxSpinsPerEntry、resultMode 等关联默认值）。

**风险等级：** ⚠️ 中。发布预检提供安全网，但持久化数据会脏。

---

#### P4: `lottery × resultMode` 任意组合均可创建

**文件：** `src/routes/admin-lottery.ts:720-722`

**问题：** 创建时 `resultMode` 只做 `coerceEnum` 校验，不限制与 activityKind 的交叉组合。以下组合创建成功：

- `lottery + resultMode="no_result"`（语义矛盾：抽奖但无结果）
- `lottery + resultMode="vote_tally"`（语义矛盾：抽奖但按投票统计）
- `lottery + resultMode="ordered_assignment"`（语义矛盾）

**运行时行为：** `performDraw` 只拒绝 `instant`，其他 mode 全部按 lottery 抽奖逻辑执行（随机抽取）。resultMode 字段对 lottery 类型**实际上不改变行为**，只影响语义。

**修复建议：** 创建时对 lottery 限制 resultMode 只能为 `manual/scheduled/instant`，其他 mode 抛错或 fallback 到默认。

**风险等级：** ⚠️ 中低。不产生灾难，但运营者可能被语义误导。

---

#### P5: 非 lottery 活动创建时 `maxSpinsPerEntry` 检查不周全

**文件：** `src/services/lottery/draws.ts:191-197`

**问题：** `createDraw` 中 `maxSpinsPerEntry` 只在 `activityKind === "lottery" && resultMode === "instant"` 时强制校验。非 lottery 活动（如 claim + instant）不校验，`maxSpinsPerEntry` 强制为 0。

**影响：** spin 端点拒绝非 lottery（`draw.activityKind !== "lottery"`），`maxSpinsPerEntry=0` 无影响。但 route 层允许非 lottery 传 `maxSpinsPerEntry=5` → `createDraw` 中非 lottery 强制 0 → 脏数据。

**修复建议：** 路由层收到非 lottery 的 `maxSpinsPerEntry` 时返回 400 提示。

### 🔵 设计问题（非紧急但值得关注）

#### P6: `coerceEnum` 设计哲学——静默 vs 显式

coerceEnum 的静默降级是"容错但误导"的设计。在前后端联调紧密时（前端下拉框 + 后端的模板端点），不会产生非法值。但未来开放 API 给第三方集成时，静默降级会掩盖错误。

建议：维护一个 `coerceEnum` 兼容版本 + 新增 `strictEnum` 用于需要严格校验的字段。

#### P7: 模板 defaults 是"前端驱动"后端不应用

模板定义在 `src/lib/activity-templates.ts`，但后端 `POST /draws` 不会读取模板。模板的默认值完全由前端 `AdminLotteryView` 读取后回填到 body。如果前端漏传，后端使用 `coerceEnum` 的默认值或 `createDraw` 的默认值，**不是模板默认值**。

这与"后端是权威校验"的原则一致（前端负责 UX，后端负责正确性），但可能导致模板创建时某些模板特定字段（如 winnerCount=0、maxParticipants=100）未回填时被系统默认值覆盖。

#### P8: enabled_activity_kinds 不拦截已创建草稿的发布

L3 运营者在 `system_config` 中设置 `enabled_activity_kinds` 后，创建路由会拦截新创建。但已创建的草稿（如 `signup_chain` 在 L3 关闭后）仍可发布——`buildPublishCheckForDraw` 不检查 `enabled_activity_kinds`。

建议：发布预检增加对 `enabled_activity_kinds` 的检查，与创建路由一致。

## 总结

**发现 1 个 P0 灾难级漏洞 + 2 个严重问题 + 6 个中等问题。**

**P0（必须立即修复）**：PATCH 时间校验被 Invalid Date 绕过——已发布活动传 `endAt=""` / 非法时间可被写入 DB，导致**活动永久开放参与、永不结束**。公开端 `resolvePublicJoinWindow` 和 `joinDraw` 均不拦截无效时间（视为无限制），**完整攻击链已验证**。发布预检不兜底（已发布活动不再预检）。修复后支持通过 PATCH 合法时间值覆盖恢复，已污染的旧数据不会永久锁定。

**严重问题**：
1. **P1: 复制接口绕过配额**——`POST /draws/:id/copy` 不调用 `enforceTenantActivityQuota`，租户可无限复制绕过 maxActivities 限制
2. **P2: coerceEnum 静默降级**——非法 activityKind 静默变成 lottery，用户可能创建错误类型
3. **P3: winnerCount 无校验可存 NaN**——创建/编辑均未用 normalize 函数

**其余问题（P4-P9）**：不产生运行时灾难，发布预检和路由层对关键路径有充分保护。

**建议立即执行**：修复 P0 漏洞（PATCH 时间合法性校验），随后修复 P1（复制配额）与 P2/P3。

### 生产恢复指引

若生产环境已存在被旧 P0 漏洞写入的非法时间（`start_at` / `end_at` / `draw_at` 为空串或非 ISO 串），修复后的 PATCH 提供以下恢复路径：

- **有参与/订单/中奖事实的进行中活动**：直接 PATCH 一个合法的新 `endAt`（或 `startAt`）。旧值已污染时，"只能延长"比较会被跳过，合法新值直接覆盖修复。
- **草稿活动**：在 PATCH 请求体中同时提供合法的 `startAt` 和 `endAt` 即可覆盖脏值。
- **批量修复**：如需一次性修复多笔活动，可通过管理端批量接口或直接 SQL 更新（确保新值为合法 ISO 8601）。

注意：若某活动的 `startAt` 和 `endAt` 同时被污染，且运营只修复其中一个字段，PATCH 会返回 400 并要求提供另一个字段的合法值。这是有意设计——不允许静默保留任何非法时间。

### 防御性结论

- `parseWinnerCount` 已显式拒绝 `null` 和空字符串，避免 `Number("") === 0` 掩盖请求错误。
- `draw_default_winner_count` 读取后已钳制到 `1–9999`；错误配置不会阻塞全部创建，也不会产生超范围默认值。
- 后续如修改卡密履约条件，必须同时验证预占不足、available 兜底、部分履约和重试四条路径，不得只替换比较符号。

当前仍需持续关注的非 P0 项：activityKind 与 resultMode 的业务组合约束、发布时对 enabled_activity_kinds 的二次校验，以及草稿切换活动类型后的配置清理。这些不应与已修复的 P0 输入校验混为一谈。
