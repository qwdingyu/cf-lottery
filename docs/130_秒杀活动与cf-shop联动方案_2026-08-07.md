# 130 秒杀活动与 cf-shop 联动方案（历史方案）

> 日期：2026-08-07  
> 状态：已被 docs/131「cf-lottery 内接支付」方向取代；本文仅保留 flashSale 体验壳、名额截单和导流版实现依据。  
> 关联：docs/009 导流模式、docs/128 全链路转化闭环、docs/027 产品边界、docs/131 秒杀卡密多租户直付方案

## 0. 评审结论

130 不应作为后续产品方向继续推进：它的核心前提是 **lottery 不接支付、支付和发卡在 cf-shop 完成**，已经与 2026-08-07 新决策冲突。

但本文不建议直接删除，原因有三点：

1. 当前代码、测试、注释仍多处引用 `docs/130`，包括 `flashSale.stockLimit` 原子截单、发布预检和前端秒杀体验壳。
2. `flashSale` 的名额门禁、售罄透传、前端刷新机制仍是 131 直付方案的前置能力。
3. 直接删除会丢失“旧导流版为什么不做真支付”的历史边界，后续排查代码注释时容易断链。

处理方式：**保留为历史实现记录，不再把 cf-shop 导流作为目标闭环；新增支付闭环以 docs/131 为准。**

## 1. 定位（各司其职）

| 系统 | 职责 | 不做 |
|------|------|------|
| **cf-lottery** | 秒杀**活动体验**：分场/倒计时、限量名额、已抢进度、「抢」交互、参与登记、结果分配、导流 CTA | **不做支付、购物车、订单、余额、真实商品库存账本** |
| **cf-shop** | **真实购买闭环**：商品、库存、下单、支付、发卡/履约 | 不做活动引擎式秒杀玩法矩阵 |

联动一句话：**lottery 负责「抢到资格/名额 + 把人送到店」；shop 负责「付钱买到货」。**

## 2. 为什么不在 lottery 做真秒杀下单

1. lottery 无支付能力（项目铁律与现状）。
2. 真秒杀下单依赖商品 SKU、库存锁、支付幂等、退款——属于 shop 主闭环。
3. lottery 已有 `maxParticipants` 容量锁、`promotion_config.destination` 导流、`external_conversion` 回传，足够做「抢名额 + 跳转购买」。

## 3. 数据落点（不新增表）

配置落在 `lottery_draws.promotion_config` JSON 的 `flashSale` 节点（与 `viral` / `experience` / `destination` / `ctas` 并列），避免迁移。

```json
{
  "version": 1,
  "destination": {
    "url": "https://shop.example.com/p/sku-xxx",
    "title": "去购买"
  },
  "flashSale": {
    "enabled": true,
    "sessionLabel": "12:00场",
    "stockLimit": 100,
    "maxPerUser": 1,
    "showCountdown": true,
    "showProgress": true,
    "showStock": true,
    "ctaLabel": "抢"
  },
  "ctas": {
    "after_win": { "url": "https://shop.example.com/p/sku-xxx", "title": "去下单" },
    "after_loss": { "url": "https://shop.example.com/", "title": "去逛逛" }
  }
}
```

运行时「已抢/剩余」不另存表：

- **名额上限**：优先 `flashSale.stockLimit`；未配则回退 `lottery_draws.max_participants`。
- **已抢人数**：`lottery_entries` 计数（公开端已有 participantCount 逻辑）。
- **进度**：`claimed / stockLimit * 100`（封顶 100）。

活动时间仍用 `start_at` / `end_at`（与现有发布预检一致）。

## 4. 体验与玩法维度

| 字段 | 推荐值 | 说明 |
|------|--------|------|
| `activity_kind` | `claim`（模板默认） | 抢到的是「资格/领取权」，不是 shop 订单；也可用 `lottery` 做「抢中奖资格」但需配奖项 |
| `experience_type` | `flash_sale` | 前端 `FlashSaleGame` 壳 |
| `result_mode` | `instant` | 参与即登记结果（claim）或后续 spin（若 lottery+instant） |
| `participation_mode` | `open` / `registered` 等 | 与现有一致，不互相推导 |

**铁律**：体验壳只负责 UI 与 emit `play`；资格校验与写入仍走现有 `join` 主路径（docs/055a）。

### 用户路径

1. 运营创建「限时抢购」模板 → 配置 `destination` 指向 cf-shop 商品页 → 设置 `maxParticipants` / `flashSale.stockLimit` → 发布。  
2. 用户打开公开页 → 看到倒计时/进度/「抢」→ 点抢 → 现有 join 流程（条件 INSERT 原子占名额）。  
3. 名额满 → API `soldOut` → 前端 toast「已抢光」并刷新 remaining。  
4. 参与成功 → 结果区 / CTA 跳转 shop 下单（lottery **不**收钱）。  
5. shop 成交后可选回调 `POST /api/integration/conversions`（已有）归因 GMV。

### 原子扣减说明（无独立库存表）

```text
INSERT INTO lottery_entries (...)
SELECT ...
WHERE (SELECT COUNT(*) FROM lottery_entries WHERE draw_id=?) < effectiveCap
```

- `effectiveCap` = `flashSale.stockLimit` 优先，否则 `maxParticipants`。
- 与邀请码 CAS 同事务；并发下 `rowsAffected=0` → 售罄，不超发。
- 这是**活动名额**锁，不是 shop SKU 库存。

## 6. 明确不做（本阶段）

- lottery 内支付、SKU、购物车、退款。
- 独立秒杀库存表、分场多 SKU 场次表（可用多活动 + sessionLabel 模拟）。
- 伪造「已抢 48%」的虚假进度（进度必须来自真实 entry 计数）。
