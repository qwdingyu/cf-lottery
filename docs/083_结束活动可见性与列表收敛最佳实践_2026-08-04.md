# 083 结束活动可见性与列表收敛：最佳实践（对照 cf-shop）

日期：2026-08-04  
范围：活动「结束/过期」后如何避免用户端与运营台持续展示脏列表；隐藏 vs 状态 vs 归档  
对照：`../cf-shop` 的 `lottery_draws.visible` 与 `listPublicDraws` / `getPublicDrawDetail`  
原则：**只写有代码证据的结论，不臆造已实现能力。**

---

## 1. 问题本质

运营与测试会积累大量 **已开奖（drawn）/ 已取消（cancelled）/ 时间已过但 status 仍为 open 的活动**。  
若列表与公开页不做收敛：

- 用户端长期看到「已结束」卡片，转化与信任下降；
- 管理台「全部状态」默认塞满历史，找当前活动成本高；
- 测试脏数据与真实履约数据混在一起。

用户直觉是「结束了就能藏」——工程上必须拆清 **三个独立轴**，否则会把状态机、时间窗、展示策略揉成一团，产生幻觉式 API。

---

## 2. 三个独立轴（最佳实践核心）

| 轴 | 含义 | 谁决定 | 典型字段 | 改变它会怎样 |
| --- | --- | --- | --- | --- |
| **A. 生命周期 status** | 业务上「能不能参与/开奖/取消」 | 状态机 + CAS | `status` | 改变允许的写操作；审计强 |
| **B. 时间窗** | 「现在是否在参与时段内」 | `start_at` / `end_at`（+ 可选 `draw_at`） | 时间字段 | 参与校验拒绝；**不等于**自动改 status |
| **C. 公开展示 visible** | 「用户面要不要看到这条」 | 运营显式开关（或受控策略） | `visible` 0/1 | 列表/详情对公众消失；**管理端仍可见**；数据与中奖记录保留 |

再加一个 **运营台列表偏好**（不算第四数据轴，是查询默认值）：

| D. 管理列表默认范围 | 默认只看「进行中 + 草稿」等 | 查询参数 / 前端默认 filter | 不改数据，只改 `WHERE` |

**铁律：A / B / C 不能互相推导。**

- `endAt` 已过 **不自动** 等于 `drawn` 或 `cancelled`（开奖可能尚未执行；非 lottery 玩法可能没有 drawn）。
- `drawn` **不自动** 等于对用户隐藏（很多活动要公示结果一段时间）。
- `visible=0` **不等于** 删除、不等于取消、不等于改结果。

这与项目已有原则一致：`participation_mode` / `experience_type` / `result_mode` 独立；可见性也应是独立展示策略（文档 019c 的 `visibility_policy` 方向一致，当前实现粒度可先用布尔 `visible`）。

## 3. 证据：cf-shop 已落地的正确模型

### 3.1 数据

`cf-shop` `lottery_draws.visible INTEGER NOT NULL DEFAULT 1`（schema + 迁移 ADD COLUMN）。

### 3.2 写路径

`PATCH /admin/lottery/draws/:id`：

- **draft**：可改业务字段（含可选 visible）；
- **drawn**：**仅允许** body 只含 `visible`（切换用户端是否展示）；禁止改时间/奖品等已定事实；
- 其它 status：禁止编辑；
- 审计：`lottery_draw_update_visibility`。

设计意图（shop 源码注释）：开奖后可隐藏公示，但不可改已确定字段。

### 3.3 读路径（公众）

- `listPublicDraws`：`status IN ('open','drawn','drawing') AND visible = 1`
- `getPublicDrawDetail`：`visible !== 1` → 当作不存在（返回 null）；status 非 open/drawn/drawing 同样不可见

管理端 `listAdminDraws`：**不过滤 visible**，隐藏活动在后台仍完整可见。

### 3.4 前端

- 管理列表展示「用户可见 / 已隐藏」；
- **仅 drawn** 提供「隐藏/显示」；
- 确认文案强调：已开奖只能改可见性。

### 3.5 shop 明确没做的

- 没有把 `endTime` 到期自动 `visible=0`；
- 没有用 `archived` 状态替代 visible（促销有 archived，抽奖用 visible）；
- 管理端默认仍可看到全部历史（靠 status 筛选，不是强制藏）。

## 4. 证据：cf-lottery 现状（半成品 / 断层）

| 层 | 现状 | 证据要点 |
| --- | --- | --- |
| DB schema | **`lottery_draws` 无 `visible` 列** | `src/db/schema.ts` 活动表字段止于 activityConfig / timestamps |
| 后端 PATCH | **仅 draft 可编辑**；无 drawn + visible 特例 | `admin-lottery.ts` `if (draw.status !== "draft") return ...` |
| 公开详情 | slug 存在且 status∈{open,drawn} 即返回；**不读 visible** | `public-lottery.ts` GET `/draws/:slug` |
| 管理列表 | 支持 status/query/kind/时间筛选；**无 visible 筛选**；默认「全部」 | GET `/draws` + AdminLotteryView `statusFilter` 默认 `''` |
| 前端类型/UI | 已有 `visible?`、`visibilityLabel`、`handleToggleVisibility`、drawn 菜单「隐藏/显示」、i18n | 从 shop 迁 UI **未迁列与 API** |
| 时间 vs 状态 | 参与校验看 `startAt/endAt`；**到期不自动改 status** | `participation.ts` 时间窗判断；状态机注释无 auto-close |
| 取消 | draft/open/paused → cancelled；drawn 不可走 cancel 语义（按状态机） | lottery-service 状态机注释 |
| 文档愿景 | 长期状态含 closed/completed/archived；`visibility_policy` 枚举 | docs/019c、021 — **未实现** |

**结论（务必说清）：**  
lottery 管理端「隐藏」按钮与文案 **目前是断路的**：调用 `updateLotteryDraw({ visible })` 会打到「仅草稿可编辑」的 PATCH，且库表无列。  
**不能**对外宣称「后端已可选择隐藏结束活动」——那是 shop 能力，lottery 仅有 UI 壳。

公开端当前主要是 **按 slug 深链**，没有 shop 那种「全站 listPublicDraws + visible=1」的多活动货架时，隐藏的价值仍在：

1. 深链详情在隐藏后应 404/不可用（防旧链接继续传播结果页——策略可选，见 §6）；  
2. 若未来有租户活动广场 / 嵌入列表，必须 `visible=1` 过滤；  
3. 运营心理模型与 shop 对齐，减少双产品心智分裂。

## 5. 「结束」在本产品里到底指什么

避免口语「结束」映射错字段：

| 口语 | 代码现实 | 用户侧表现 | 建议运营动作 |
| --- | --- | --- | --- |
| 报名截止 | `now > endAt`，status 可能仍是 `open` | 无法 join；列表仍可能显示 open | 抽奖类：到点开奖或手动开奖；非抽奖：考虑显式 close（P2）或保持 open+时间拒绝 |
| 已开奖 | `status=drawn` | 可查结果；公开详情允许 | 公示期过后 **visible=0**（推荐） |
| 已取消 | `status=cancelled` | 公开详情当前直接「未开放」 | 管理台用 status 筛选；一般无需 visible |
| 暂停 | `status=paused` | 不可参与 | 恢复或取消；不是隐藏 |
| 草稿 | `status=draft` | 公开不可见（详情拒绝） | 测完删除或发布 |

**open + endAt 已过** 是常见「脏 open」：不是 hidden 问题，是 **生命周期未收口**。最佳实践是：

- 短期：管理台筛选 + 手动开奖/取消；  
- 中期：定时任务仅对 **result_mode=scheduled 且到点** 的活动推进 drawing/drawn（已有 due 扫描方向）；  
- **不要**用 cron 无差别把所有 endAt 过期的 open 直接 visible=0（会误伤「截止后公示、尚未开奖」的 intentional 窗口）。

## 6. 推荐目标架构（lottery 应对齐的最佳实践）

### 6.1 数据：布尔 `visible`，默认 1

```text
lottery_draws.visible INTEGER NOT NULL DEFAULT 1  -- 0 隐藏 / 1 展示
```

- 迁移 ADD COLUMN + 已有行 default 1（与 shop 一致）。  
- **不要**用 status=`archived` 替代第一版 visible（改状态机会牵动删除策略、统计、复制活动等）；archived 可作为 P2 管理台收敛态。  
- **不要**把 `show_winner_list` / `show_participant_count` 与 `visible` 混用：  
  - `visible`：整活动在用户面「有没有这条」；  
  - `show_*`：活动页内「展示哪些统计/名单」。

### 6.2 写 API（对齐 shop，补租户隔离）

1. **drawn（及可选：cancelled 仅允许 visible？——建议第一版仅 drawn）**  
   - `PATCH` 仅接受 `{ visible: 0|1 }`；  
   - 其它字段 409；  
   - 审计 `draw.update_visibility`。  
2. **draft** 创建/编辑可带初始 visible（默认 1）；一般不需要草稿隐藏。  
3. **open/paused/drawing**：第一版 **禁止** 藏（避免「进行中活动从列表消失但仍有人持有链接参与」的运营事故）。若业务强需求「紧急下架」，应用 **pause/cancel**，不是 visible。  
4. 多租户：`WHERE id AND tenant_id` 必须与现有一致。

### 6.3 读 API

| 表面 | 规则 |
| --- | --- |
| 公开详情 GET by slug | `visible=0` → 与不存在或「活动未开放」一致（建议 **404 或 400 统一文案**，不泄露「存在但隐藏」给枚举攻击；slug 已不可枚举则可 400「未开放」与现网一致） |
| 公开列表（若有） | status 白名单 **且** `visible=1` |
| 个人查结果 / OTP my-result | **产品决策点**：见下 |
| 管理列表/详情 | **始终**返回，含 `visible`；可加 `?visible=0|1` 筛选 |
| 管理默认 filter | 建议默认 `lifecycle=active` 虚拟筛：`status IN (draft,open,paused,drawing)`，一键「含已结束」看 drawn/cancelled |

**个人查结果 vs 隐藏（必须拍板）：**

| 策略 | 行为 | 适用 |
| --- | --- | --- |
| **S1 硬隐藏** | visible=0 时详情与 my-result 全拒 | 合规下架、错误公示、测试清场 |
| **S2 列表藏、持码可查** | 列表/裸详情不展示；已参与用户凭邮箱 OTP 仍可查结果 | 公示期结束但仍履约客服 |
| **S3 仅藏名单** | visible 仍 1，只关 `showWinnerList` | 只不想公开展示名单 |

**推荐默认：S1 对齐 shop 的 getPublicDrawDetail；** 履约客服用 **管理端中奖列表 + 重发邮件**，不依赖公开页。若业务要 S2，必须单独 API 与审计，不能 silently 混在 list 过滤里。

### 6.4 管理台 UX

1. 状态列副文案：用户可见 / 已隐藏（有真实字段后才有意义）。  
2. drawn 行：隐藏/显示 + 确认。  
3. 默认列表：**进行中视角**（排除 drawn/cancelled），减少「结束活动刷屏」——这是 **D 轴**，不改库。  
4. 筛选增加：「仅隐藏」「含已结束」。  
5. 批量（接 082）：批量「隐藏已开奖」比批量删更安全，适合清用户视野。

### 6.5 与删除、取消的边界

| 动作 | 数据 | 可恢复 | 适用 |
| --- | --- | --- | --- |
| 隐藏 visible=0 | 保留全部 | 一键再显示 | 公示结束、临时不想曝光 |
| 取消 cancelled | 终态 | 不可恢复为 open | 活动作废 |
| 删除 | 物理或强约束删 | 难 | 测试草稿、无履约 drawn（策略见 082） |
| 归档 archived（P2） | 管理台默认不出现 | 可取消归档 | 长期历史库 |

测试期清场：**优先删 draft / 隐藏 drawn**，慎删有中奖与邮件记录的 drawn。

### 6.6 明确不做

- 不把 `endAt` 过期自动 `visible=0`（无运营确认会误伤）。  
- 不把 visible 塞进 status 枚举。  
- 不给 Dashboard 概览行加隐藏开关当主入口。  
- 不在公开响应里回传 `visible` 字段给匿名用户（无信息增量，少暴露内部开关）。  
- 不引入重型 CMS「定时上下架」直到有明确租户需求。

## 7. 实施优先级（授权后再做）

### P0 — 把断路补成与 shop 同构的最小闭环

1. 迁移：`visible INTEGER NOT NULL DEFAULT 1`  
2. schema + 创建默认 1  
3. PATCH：drawn 仅可改 visible + 审计 + 租户条件  
4. 公开详情（及未来列表）：`visible=0` 拒绝  
5. 前端：`handleToggleVisibility` 真正成功；失败 toast 已有  
6. 单测：隐藏后公开 不可见；管理仍可见；非 drawn 改 visible 拒绝  

### P1 — 管理台列表收敛（低成本高体感）

1. 默认 filter「进行中」（或「进行中 + 草稿」）  
2. `?visible=` 筛选  
3. 批量隐藏 drawn（依赖 082 批量条）  

### P2 — 生命周期收口（可选）

1. 文档化 open+过期的运营手册  
2. 评估 `closed`/`archived` 是否值得进状态机（活动引擎多玩法时再上，避免只为抽奖加状态）  
3. S2 持码可查若产品需要再开

## 9. 结论

1. **最佳实践**是三维分离：**status（业务）/ 时间窗（资格）/ visible（公开展示）**；管理默认筛选只是查询偏好。  
2. **cf-shop 已验证** `visible` + 公开列表/详情过滤 + drawn 限定切换 + 管理端仍可见。  
3. **cf-lottery 当前缺口**：UI/i18n/类型已抄半套，**库与 API 未实现**；公开详情不认 visible；管理默认「全部」易被结束活动淹没。  
4. 落地应 **先 P0 对齐 shop 最小闭环**，再 P1 默认列表收敛与批量隐藏；不要用自动过期改 visible 或过早上 archived 状态机。  

**本文为分析与方案，未改业务代码。** 实施需单独授权。
