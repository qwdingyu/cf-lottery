## 一、先把文档关系说清楚（避免序号混乱）

| 文档 | 本质 | 对业务的价值 | 状态 |
|:-----|:-----|:-------------|:-----|
| **111** | 中转站「日卡拉新 + 退群处罚」的**集成契约** | 获客钩子、可售卖玩法雏形 | 方案级，未全量开发 |
| **112 技术** | 裂变数据可信（registered 归因、自邀、stats 排序） | **销售与运营数字可信的前提** | 已上线 |
| **112 生态** | 拥挤 AI 资源市场里「怎么赢」的**竞争打法** | 截流、差异化、供应链系统化 | 方案级，P0 可零开发试点 |

**一句话**：111 解决「客户怎么被规则抓进来」；112 生态解决「在红海里靠什么赢」；112 技术解决「抓进来的归因与榜单别脏」。三者必须一起看，不能只挑技术或只挑营销文。

## 二、市场判断：我们到底在卖什么

### 2.1 目标市场的真实结构

020a / 111 / 112 共同指向的客群是：

- **一级买家（我们的 SaaS 租户）**：Token 中转站、社群运营者、号池/通道服务商——他们要的是**拉新、留存、可验证信任、可复盘 ROI**。
- **二级受众（租户的客户）**：QQ/TG 群里找额度、通道、号池的人——他们是**一次性对话流量**，信任成本极高。
- **平行竞品**：群里发广告的其他供应商——**不是合作伙伴**，是同一池客户的争夺者（112 修正版已写清）。

供给过剩、价格战、信任稀缺、连接一次性——这四条决定了：

1. **纯「抽奖 SaaS」卖点太薄**：中转站不缺「办一场抽奖」，缺的是「把群流量变成可运营客户资产」。
2. **cf-lottery 的正确定位不是交易撮合平台**，而是 **规则驱动的参与与结果分配引擎**（归因、配额、处罚波及、事件、看板）——与 111 职责边界一致。
3. **市场愿意付费的，是「确定性」**：发了多少卡、谁拉谁、退群罚谁、漏斗哪一环断——比「再做一个漂亮转盘」值钱。

### 2.2 我们相对竞品广告的差异化（销售话术可直接用）

| 竞品群广告 | 用我们系统后 | 销售可强调的一句话 |
|:-----------|:-------------|:-------------------|
| 文字沉底、改价重发 | 货架页常驻、改配置即生效 | 「客户 3 秒看清你有什么」 |
| 口头「保真可测」 | 审计、黑名单、历史可查 | 「可验证，不是再喊一句口号」 |
| 拉新靠吼、退群靠人肉 | 归因 + 配额 + 处罚 Webhook | 「羊毛党成本高于收益」 |
| 客户聊完就走 | 日卡钩子 + 分享裂变沉淀 | 「流量进系统，可二次触达」 |
| 定价凭感觉 | 情报采集（OODA） | 「用竞品广告当免费行情」 |

### 2.3 市场风险（必须写进销售与运营手册）

| 风险 | 影响 | 建议 |
|:-----|:-----|:-----|
| 灰色资源/ToS 争议 | 品牌与支付通道风险 | 产品中性：只做信息结构化与规则；运营侧标注风险品类；销售不承诺「担保真假」 |
| 客户把平台当资金托管 | 法律与对账灾难 | **坚持 111：不存余额、不发兑换码、不托管**；合同与话术统一 |
| 日卡成本失控 | 中转站 ROI 为负 | 配额在 lottery 侧卡死（2 张/人、300 次/天等）；销售先帮客户算「日卡面额 × 有效核销率」 |
| 把 112 做成「资源交易所」 | 动机不成立、开发黑洞 | **禁止**整合竞品供给；只做货架/情报/自己的供应链 |
| 裂变脏数据 | 运营误判 ROI、销售翻车 | 112 技术已做；上线 111 前必须验收 registered + 自邀用例 |

## 三、运营整合：把 111 + 112 落成「周节奏」，而不是功能清单

### 3.1 推荐运营闭环（一张图）

```
竞品广告（观察）──► 玩法 C 情报录入 ──► 调价/备货决策
        │
        ▼
公开货架页 A（差异化） + 日卡活动 D/111（截流）
        │
        ▼  ?ref= 归因（112 技术保证可信）
客户池沉淀 ──► 复购/套餐（020a）──► 老客拉新（裂变 108–112）
        │
自有上游 ──► 采购台 B + 认证 E ──► 货架更新 ──► 再获客
```

**运营原则**：每一周只优化一个漏斗指标，不并行开五个「大系统」。

### 3.2 分角色周动作（可执行）

| 角色 | 本周必做 | 对应文档 | 工具（现有） |
|:-----|:---------|:---------|:-------------|
| 中转站老板 / L2 | 1 个最强品类货架页 + 固定 public_slug 进广告 | 112 A | 公开活动 + 文案配置 |
| 运营 | 每日 5–15 分钟竞品广告录入（品类/价/量/质保） | 112 C | survey/submit |
| 增长 | 日卡/进群钩子活动上线，分享码进群置顶 | 111 + 裂变 | share + ref |
| 客服/风控 | 黑名单与「退群是否连带」规则写清并公示 | 111 阶段二 | blacklist + 审计 |
| 采购 | 有收货需求时开采购响应页，不在群里纯吼 | 112 B | signup_chain / lottery |

### 3.3 与现有产品能力的映射（避免重复建设）

| 运营诉求 | 优先用什么 | 不要做什么 |
|:---------|:-----------|:-----------|
| 拉新归因 | shareRecords / ref / 排行榜（108–112） | 另造邀请体系；不接 shop 推广码 |
| 发卡/扣款 | 中转站账务 + Webhook | lottery 内做余额与兑换码生命周期 |
| 限流防刷 | rateLimitLog + 活动级配额 | 只靠前端隐藏按钮 |
| 信任与封禁 | audit + blacklist + approval | 口头拉黑无记录 |
| 导流变现 | promotion_config / 008b–009 | 平台抽交易佣金（越界） |
| 卖 SaaS 额度 | 020a 兑换码 / 租户配额 | 与中转站日卡混成一套账 |

### 3.4 111 三阶段的运营验收标准（销售交付物）

| 阶段 | 运营可见结果 | 通过线 |
|:-----|:-------------|:-------|
| 一 归因+奖励意图 | 看板：分享→参与→reward.earned 次数 | 与中转站发卡数偏差可解释（Webhook 失败可查） |
| 二 退群处罚 | 处罚名单可审计；误伤可配置关闭「连带被邀请者」 | 幂等：重报不双罚 |
| 三 quota_card | 规则可配置、可复制模板给下一客户 | 不写代码改面额/配额/处罚开关 |

### 3.5 112 技术对运营的「非技术」含义

- **registered 不传 ref**：登录用户点邀请链接「白拉」——群运营会以为裂变坏了，其实是归因断了。  
- **自邀请 / 签到跨日**：榜单与加权被刷，开奖「不公平」投诉会直接打到销售。  
- **stats 码不一致**：用户复制的链接和系统记的不是同一码，客服扯皮。  

**建议**：任何对外承诺「邀请有奖 / 加权开奖」的客户，售前 checklist 必须包含 112 技术验收项。

## 四、销售整合：卖法、包装、定价叙事

### 4.1 不要卖「又一个抽奖工具」

| 弱话术 | 强话术（对齐 111/112） |
|:-------|:----------------------|
| 我们有转盘、九宫格 | 我们是**活动与激励规则引擎**，日卡/拉新/处罚可配置 |
| 帮你整合全网 AI 资源 | 帮你**用系统打赢同质化广告战**（货架+情报+钩子） |
| 保证资源真假 | 保证**过程可审计、关系可归因、指令可对账** |
| 上了就能涨粉 | 上了能把群流量变成**可计量客户池**，ROI 可算 |

### 4.2 三条可售产品线（同一引擎，不同包装）

1. **获客包（111 为主）**  
   - 交付：日卡拉新活动模板 + Webhook 对接说明 + 裂变看板  
   - 买家：有 QQ/TG 群、有日卡成本预算的中转站  
   - 成功标准：有效进群成本、核销率、退群损耗率  

2. **经营包（112 A+C 为主）**  
   - 交付：货架页 SOP + 行情采集表 + 周复盘模板  
   - 买家：已有货、缺「结构化销售页与定价依据」  
   - 成功标准：货架 UV、询单转化、调价次数与毛利  

3. **供应链包（112 B+E，P1）**  
   - 交付：采购响应页 + 认证/黑名单流程  
   - 买家：采购量大、吃过假货/跑路亏的中转站  
   - 成功标准：响应时效、次品率、复购供应商占比  

**SaaS 平台自己的钱**仍走 020a（活动额度/套餐），与中转站「日卡」账本分离——销售报价单上必须两列写清，避免客户以为买了 lottery 就含 Token 额度。

### 4.3 销售流程建议（低摩擦）

1. **发现**：群里是否在打价格战、是否有退群羊毛、是否只有文字广告。  
2. **演示（30 分钟）**：现场建一个货架 slug + 一个带 ref 的分享链接 + 看 joined 计数（证明归因）。  
3. **算账**：日卡面额 × 预计核销 × 预期留存 > 获客成本；并列「不做处罚」时的羊毛敞口。  
4. **边界确认**：兑换码/余额在对方系统；我们出意图与名单；资金不经我们。  
5. **试点 7 天**：单品类货架 + 小预算日卡；复盘后再谈阶段二/三或年框。  

### 4.4 扩展销售（把「自己用」变成「卖给同行」）

112 P2 写的「玩法矩阵 SaaS 化」成立的前提是：

- 自己先用 111+112 跑出**可展示的案例数据**（漏斗、处罚次数、货架转化）；  
- 包装成**行业模板**（中转站日卡、社群拉新、采购接龙），而不是定制项目制；  
- 多租户隔离与白标已是产品基因——卖的是**同样的瑞士军刀配置**，不是为每个中转站重做交易撮合。

## 五、系统整合优先级（专业建议，按 ROI）

### 5.1 现在就该做（P0，偏运营配置 + 最小集成）

| 顺序 | 动作 | 理由 |
|:----:|:-----|:-----|
| 1 | **112 技术能力作为获客活动上线门禁** | 数字不可信则 111 全毁 |
| 2 | **货架页 A 试点 1 个品类**（零开发） | 最快形成「比群广告强」的体感 |
| 3 | **情报 C 手动表**（零开发） | 训练团队 OODA，成本极低 |
| 4 | **111 阶段一**：reward.earned + 配额 + 归因页 | 真正截流；对方系统只收 1 个 Webhook 即可试点 |

### 5.2 值得做（P1，闭环与可售）

| 顺序 | 动作 | 理由 |
|:----:|:-----|:-----|
| 5 | 111 阶段二：`integrations/events` + penalty 波及 | 防羊毛，中转站才敢加大日卡预算 |
| 6 | 采购台 B + 认证 E | 供应链稳定 → 货架敢写「已验证」 |
| 7 | prizeCodes `expiresAt` + 统一 `revoked`（111 §7） | 与中转站解耦，服务「限时奖品/违规撤奖」通用场景 |

### 5.3 可以晚做 / 刻意不做

| 项 | 建议 |
|:---|:-----|
| activity_kind=`quota_card` 玩法化 | 有 ≥1 个付费中转站跑通阶段一/二再做，避免空转抽象 |
| 竞品广告 bot 半自动 | 有稳定录入习惯与字段字典后再做 |
| 资源交易撮合、资金托管、全网供给整合 | **不做**（动机与合规双杀） |
| cf-shop 会员推广码 | **不做**（107） |
| 把 lottery 做成中转站账务 | **不做**（111 边界） |

## 六、对 111 / 112 文档本身的评价（优点与补强）

### 6.1 111 的优点

- 职责切割正确：**意图在 lottery，凭证在中转站**——这是唯一可长期对账的架构。  
- 与产品定位同构：规则、归因、配额、事件，而不是重做 Token 业务。  
- 对面工作量小（2 Webhook + 1 回传）——**B2B 集成能成交的关键**。  
- 有效期分析分层清晰，且与中转站场景解耦。

### 6.2 111 从市场/销售视角仍缺的

1. **单位经济模型模板**：日卡成本、核销率、退群率、连带误伤率——没有这张表，销售无法定价试点。  
2. **身份对齐方案**：QQ / 中转站 account / lottery identity 三键如何绑定（售前必问，文档偏技术事件）。  
3. **失败体验**：Webhook 失败时用户侧文案与补发 SOP（运营 7×24 会卡在这）。  
4. **合同条款要点**：不托管资金、处罚以事件为准、误伤申诉窗口——减少事后纠纷。

### 6.3 112 生态的优点

- 纠正了「整合竞品资源」幻想，改成情报/截流/自有供应链——**战略正确**。  
- OODA + 玩法 A–E 动机自洽，且大量零开发，符合瑞士军刀。  
- 与 111 拼成完整竞争闭环，叙事完整。

### 6.4 112 生态仍缺的

1. **指标字典**：货架 UV、询单率、情报条数、日卡 ROI——没有统一 KPI，周复盘会空转。  
2. **内容与合规运营手册**：哪些品类能上货架公网、哪些仅私链——销售承诺边界。  
3. **与 promotion_config / 导流（008b）的衔接**：货架页如何一键导到下单/客服，而不仅是「看得到」。  
4. **多租户案例包装**：如何把「自营中转站成功」变成「可售模板」而不绑死单一业务。

### 6.5 112 技术

- 评价：**基础设施正确，应视为增长功能的发布门槛，而不是「又一次修 bug」**。  
- 建议：在 L3/售前 checklist 与 042b 类操作指南中增加「裂变可信验收」三节（registered ref、自邀、stats 码一致）。

## 七、专业结论（可直接作决策）

1. **整合主轴**  
   - **市场**：在同质化 AI 资源红海里，卖「可验证的获客与经营系统」，不卖抽奖皮肤，不卖资源交易所。  
   - **运营**：A 货架 + C 情报 + D/111 钩子周节奏；裂变以 112 技术为数据质量门禁。  
   - **销售**：三条包装（获客/经营/供应链）+ 7 天试点 + 账本分离（lottery 额度 vs 中转站日卡）。

2. **扩展主轴**  
   - 先自用跑通指标 → 模板化 → 卖给其他中转站/社群（多租户）。  
   - 技术扩展优先：**事件入口 + 奖励/处罚 Webhook + 凭证 revoked/过期**；不优先重型玩法抽象。

3. **最大战略禁忌**  
   - 整合平行竞品供给、平台托管资金、接入 shop 推广码、为灰色能力做深耦合工具。

4. **建议决策**  
   - **本周**：货架 + 情报（配置向）+ 确认 111 阶段一对接人与身份键。  
   - **两周内**：reward.earned 联调试点；同步准备处罚事件与误伤开关。  
   - **有首单数据后**：再开 quota_card 玩法化与 bot 情报。
