## 一、并发安全与锁机制

### 1.1 参与防重：UNIQUE 约束 + 原子 INSERT

**现状**：`joinDraw` 使用 `INSERT ... SELECT` 合并容量检查与写入，配合 `UNIQUE(tenant_id, draw_id, identity_type, identity_value)` 约束。

```sql
INSERT INTO lottery_entries (...) SELECT ... WHERE (SELECT COUNT(*) FROM lottery_entries WHERE draw_id = ?) < ?
```

**评价**：✅ 正确。SQLite 中 INSERT 是原子操作，SELECT 子查询在同一个语句中执行，避免了「先 count 再 insert」的竞态窗口。UNIQUE 约束兜底防重复。

**风险**：`SELECT COUNT(*)` 在大型候选池（>10000 人）时可能变慢。建议后续添加 `lottery_draws.participant_count` 缓存计数器。

### 1.2 开奖防双发：CAS 状态机

**现状**：`performDraw` 使用 `UPDATE ... WHERE status = 'open'` 原子夺取开奖权。

```typescript
const result = await db.update(lotteryDraws)
  .set({ status: "drawing" })
  .where(and(eq(lotteryDraws.id, drawId), eq(lotteryDraws.status, "open")));
if ((result.rowsAffected ?? 0) === 0) throw new Error("...");
```

**评价**：✅ 正确。SQLite 的 UPDATE 是原子操作，`WHERE status = 'open'` 确保只有一个进程能夺取开奖权。失败后检查 `draw.status === "drawn"` 做幂等返回。

### 1.3 邀请码防超发：条件 UPDATE

**现状**：`joinDraw` 邀请码模式使用条件 UPDATE。

```sql
UPDATE lottery_invite_codes SET used_count = used_count + 1
WHERE id = ? AND used_count < max_uses AND active = 1
```

**评价**：✅ 正确。`rowsAffected` 检查确保原子性。`used_count < max_uses` 条件防止超发。

### 1.4 锁码防重：事务内条件 UPDATE

**现状**：`performDraw` 在 `withDbTransaction` 内使用条件 UPDATE。

```sql
UPDATE prize_codes SET status = 'issued', winner_id = ?
WHERE prize_id = ? AND status = 'available' AND tenant_id = ?
```

**评价**：⚠️ 有关注点。事务内操作是串行化的，但 `rowsAffected` 检查后如果为 0（码不足），当前中奖者没有码但仍被记录为中奖者。这是**设计选择**而非 bug——码不足时中奖者仍记录，但无码可发。需要运营端明确提示。

### 1.5 漏发风险

**现状**：`performDraw` 事务内，如果某个奖项的码不足，中奖者仍被记录但 `prize_code_id` 为空。

**评价**：⚠️ 需要运营端展示。中奖者列表应标注「无码」状态，并提供「补发」操作。当前 admin 路由未实现此功能。

## 二、查询及计算效率

### 2.1 参与人数统计

**现状**：公开活动页使用 `COUNT(*)` 实时统计。

```sql
SELECT COUNT(*) FROM lottery_entries WHERE draw_id = ?
```

**评价**：✅ 可接受。`lottery_entries` 有 `draw_id` 索引（通过 UNIQUE 约束实现），单活动查询走索引。对于 < 10000 人的活动，性能可接受。

### 2.2 开奖候选池读取

**现状**：`performDraw` 读取全部候选池到内存。

```typescript
const entries = await db.select().from(lotteryEntries).where(eq(lotteryEntries.drawId, drawId));
```

**评价**：⚠️ 需要上限保护。如果候选池超过 5000 人，受 Workers 内存限制（128MB）。建议在 `lottery_draws` 添加 `max_participants` 硬限制（当前已有，但默认无限制）。

**建议**：在 `createDraw` 中强制 `max_participants` 必须有值，默认 5000。

### 2.3 中奖名单查询

**现状**：使用 `lottery_winners` 表直接查询，按 `draw_id` 过滤。

**评价**：✅ 正确。`lottery_winners` 有 `UNIQUE(tenant_id, draw_id, entry_id)`，`draw_id` 在索引中，查询走索引。

### 2.4 管理端活动列表

**现状**：`GET /api/admin/draws` 使用 `tenant_id + status + created_at DESC` 索引。

**评价**：✅ 正确。`idx_draws_tenant_status` 索引覆盖此查询。

## 三、扩展性分析

### 3.1 新增抽奖模式

**参与模式扩展**：当前 `participationMode` 字段支持 `open/roster/password/invite_code`。新增模式只需：

1. 在 `joinDraw` 的 `if` 链中添加新分支
2. 如需要新表（如 `lottery_external_checks`），在 schema 中添加
3. 前端公开页添加对应 UI

**开奖模式扩展**：当前 `drawTrigger` 字段支持 `manual/scheduled`。新增 `instant`（即时开奖）或 `batch`（分批开奖）需要：

1. 新增 `performInstantDraw` 函数
2. 在 `processDueDraws` 或 Cron 中添加新触发逻辑

### 3.2 奖项扩展

**多奖项**：`lottery_prize_tiers` 已支持一等奖/二等奖/三等奖。`performDraw` 已实现按奖项逐个分配中奖者。

**加权抽奖**：当前 `randomSelect` 是等概率不放回抽样。加权抽奖需要：
1. 新增 `lottery_entries.weight` 字段
2. 实现加权随机算法（如 Alias Method）
3. 在 `performDraw` 中根据模式选择算法

### 3.3 通知扩展

**当前**：仅支持 Resend 邮件通知。扩展方向：
1. Webhook 通知（中奖后回调客户 URL）
2. 短信通知（集成 Twilio 等）
3. 站内通知（需用户系统）

**建议**：在 `lottery_winners.notification_status` 字段基础上，新增 `notification_channel` 字段。
