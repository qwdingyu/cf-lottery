# 定时自动开奖链路审查

## 背景

管理员反馈"抽奖活动到了截止时间/开奖时间，需要自动开奖，而非管理员手动到后端找到活动然后点击开奖"。

审查目标：确认自动开奖完整链路是否存在、是否完整、是否健壮。

## 各环节详解

### 1. 创建活动时 drawTrigger 的推断

**前端（AdminLotteryView.vue:3747 + ops-utils.ts:191）：**
- `resolveLotteryScheduleFields`：lottery + drawAt 有值 → `drawTrigger='scheduled'` + `resultMode='scheduled'`
- lottery + instant → `drawTrigger='manual'` + `resultMode='instant'`（独立 spin 结果机，不归 Cron 管）
- 非 lottery 即使有 drawAt 也保持 manual（问卷/接龙等不被 Cron 误开奖）

**路由（admin-lottery.ts:662-668）：**
- `activityKind === "lottery" && hasDrawAt && body.drawTrigger === undefined` → `drawTrigger='scheduled'`
- 显式 `body.drawTrigger` 优先（运营刻意手动时尊重）

**服务（draws.ts:221-223）：**
- `activityKind === "lottery" && data.drawAt` → `drawTrigger='scheduled'`
- 最后一层兜底，防止前端/路由绕过

### 2. 创建时 resultMode 的对齐

**路由（admin-lottery.ts:691-701）：**
- `lottery + scheduled + 未传 resultMode 或传了 manual` → 强制设为 `scheduled`
- 避免"公开页文案说系统自动开奖"但实际是 manual 的语义矛盾

### 3. 编辑活动时的一致性

**前端编辑：** 编辑提交也走 `resolveLotteryScheduleFields`，基于当前 `drawTime` 重新推断 `drawTrigger`
- 修改开奖时间 → 重新推断 → 提交正确 drawTrigger
- 清空开奖时间 → drawAt=undefined → drawTrigger=manual → 符合预期

**后端更新（admin-lottery.ts:847）：**
- `body.drawTrigger !== undefined` 时才更新，否则保留原值
### 4. systemd 定时触发

**timer 配置（cf-lottery-maintenance.timer）：**
- 开机 2 分钟后首次执行
- 之后每 5 分钟执行一次
- 精度 30 秒
- Persistent=true（系统关机错过的时间点，开机后补偿执行）

**service 配置（cf-lottery-maintenance.service）：**
- `EnvironmentFile=/root/cf-lottery/.env`（从 .env 读取 CRON_SECRET 和 PORT）
- `curl -fsS -X POST -H "Authorization: Bearer ${CRON_SECRET}" http://127.0.0.1:${PORT:-8787}/api/cron/maintenance`
- Type=oneshot（每次执行一次 curl）
- 安全加固：NoNewPrivileges、PrivateTmp、ProtectHome、ProtectSystem

### 5. 部署脚本安装

**scripts/deploy-to-vps.sh:137-140：**
```bash
install -m 0644 configs/cf-lottery-maintenance.service /etc/systemd/system/
install -m 0644 configs/cf-lottery-maintenance.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now cf-lottery-maintenance.timer
```

**local-deploy-vps.sh：** 只上传部署包，不执行服务器侧步骤。注释中给出了服务器侧手动执行的步骤（含安装 timer）。

### 6. 自动开奖核心

**processDueDraws（lottery-service.ts:150-203）：**
- 查询条件：`status='open'` + `activityKind='lottery'` + `drawTrigger='scheduled'` + `resultMode != 'instant'` + `drawAt <= now`
- 治愈 stale drawing：先查卡在 `drawing` 状态的活动，调用 `healDrawingState` 恢复
- 逐个 performDraw：CAS 更新 `open → drawing`，同一活动仅一个实例能夺取开奖权
- 失败隔离：每个活动独立 try/catch，失败不影响其他活动

**performDraw 内部（draw-execution.ts）：**
- CAS 夺权：`UPDATE lottery_draws SET status='drawing' WHERE status='open' AND id=? AND tenantId=?`
- 检查参与人数，无人参与时跳过（不空开奖）
- 选出 winnerCount 个 PAID 参与者（或全部参与者 if 非直付）
- 原子领取卡密：`UPDATE prize_codes SET status='issued' WHERE status='available' LIMIT 1`
- 更新状态：`drawn` 或恢复 `open`（失败时记录 failureReason）

### 7. Dashboard 到期计数

**admin-lottery.ts:150-158：**
- 管理后台概览页统计「到期待开奖的定时活动」数量
- 查询条件与 processDueDraws 一致：`status='open'` + `drawTrigger='scheduled'` + `drawAt <= now`
- 运营者可见到期活动数量，无需手动排查

## 运行时依赖（自动开奖生效的前提）

| 依赖 | 说明 | 检查方法 |
|------|------|----------|
| **CRON_SECRET** | 服务器 `.env` 必须配置，否则 `/api/cron/maintenance` 返回 503 | `grep CRON_SECRET /root/cf-lottery/.env` |
| **systemd timer 已启用** | `systemctl enable --now cf-lottery-maintenance.timer` | `systemctl is-enabled cf-lottery-maintenance.timer`；`systemctl status cf-lottery-maintenance.timer` |
| **数据库可用** | 服务器 `.env` 的 TURSO_URL/TURSO_TOKEN 有效 | 自动开奖失败时健康检查不通过 |
| **活动时间正确** | 活动 `drawAt` 在 `endAt` 之前（创建时已校验） | `drawAt <= endAt` 校验在 `draws.ts:238` |
| **活动状态为 open** | 活动取消/关闭后不触发自动开奖 | 正常流程 |

## 结论

**定时自动开奖链路完整、正确、健壮。** 无需参考 cf-shop 项目。

- 创建活动时三重保障（前端 + 路由 + 服务）确保 `drawTrigger='scheduled'`
- systemd timer 每 5 分钟自动触发 `/api/cron/maintenance`
- `processDueDraws` 精确扫描到期活动，CAS 防重复开奖
- 测试覆盖了前端推断逻辑和后端端到端自动开奖
- 部署脚本 `scripts/deploy-to-vps.sh` 自动安装 timer

**如果生产环境"到点没自动开奖"，优先排查：**
1. `CRON_SECRET` 是否配置在 `/root/cf-lottery/.env`
2. `systemctl status cf-lottery-maintenance.timer` 是否 active
3. 活动 `drawTrigger` 是否确为 `scheduled`（`SELECT id, drawTrigger, drawAt, status FROM lottery_draws WHERE activityKind='lottery'`）

### 根因：`c.env` 在 Node 下为空

`/api/cron/maintenance` 端点调用 `runScheduledMaintenance(c.env)`，但 **Hono standalone（Node.js）下 `c.env` 为空对象 `{}`，不包含 `process.env`**。`createDbFromEnv(env)` 检查 `env.TURSO_URL` 为空 → `db = undefined` → 抛出 `"数据库未配置"`。

### 修复方案

将 `runScheduledMaintenance` 的参数从 `Bindings`（即 `c.env`）改为 `(db: DbType, env: MaintenanceEnv)`，其中：

- **`db`** 从中间件 `c.get("db")` 获取（中间件已用 `getEnv` 正确处理 `process.env` 回退）
- **`env`** 为 `MaintenanceEnv` 接口，只包含维护任务所需的 6 个配置项，通过 `getEnv(c, ...)` 读取

修改文件：`src/index.ts`（+49/-17 行）
