# 我的卡密命令实现与统一账号体系分析

> 日期：2026-08-10  
> 定位：卡密私聊投递闭环断裂修复 + 账号体系终极方案分析

---

## 1. 背景

卡密奖品通过私聊投递后，若私聊失败（用户关闭临时会话、适配器异常），用户无法找回卡密。  
此前 `/我的奖品` 群内展示已脱敏（只显示 `[群内不展示]`），用户无法在群内查看到卡密明文。  
**这构成 P0 闭环断裂：卡密遗失后无找回路径。**

---

## 2. 解决方案：`/我的卡密` 命令

### 2.1 设计决策

- **不修改 `/我的奖品` 行为**：`/我的奖品` 保持纯查询语义，不产生私聊副作用。  
  `/我的卡密` 是有副作用的操作（私聊发送），两者职责分离。
- **只查询 `prizeCodeId IS NOT NULL` 的中奖记录**：与 `/我的奖品` 的 `hasCode` 标记一致。
- **卡密明文通过 `privateMessages` 侧写私聊发送**：群内回复仅告知数量和私聊提示，不泄露卡密。
- **无卡密奖品时引导用户使用 `/我的奖品`**：避免用户困惑。
- **群内回复明确告知卡密数量**：使用户能确认是否全部收到。

### 2.2 命令识别

```
/我的卡密
我的卡密
/卡密
卡密
```

### 2.3 命令开关

- `BuiltinCommandConfig.myCardCodeEnabled`（默认 `true`）
- 管理端 `AdminQqAssistantView.vue` 新增复选框

### 2.4 数据流

```
用户发送 /我的卡密
  → commands.ts recognizeBuiltinCommand → "card_code"
  → executeCardCodeCommand
    → findPlatformEntryId → 查找用户 entry
    → 查询 lotteryWinners (prizeCodeId IS NOT NULL)
      → LEFT JOIN lotteryPrizeTiers, prizes, prizeCodes
    → 有卡密 → 组装 privateMessages 数组
    → 返回 { reply: "你有 N 条卡密，已私聊发送", privateMessages }
  → platform-qq.ts / platform-telegram.ts
    → 遍历 privateMessages 调用 adapter.send()
    → 私聊失败 → 群内回复追加降级提示
```

### 2.5 测试覆盖

| 场景 | 断言 |
|------|------|
| 未参与活动 | 提示 "还未参与" |
| 已参与但无卡密 | 提示 "还没有获得卡密奖品" |
| 有卡密奖品 | 私聊包含卡密明文，群内不泄露 |
| 多个卡密奖品 | 逐条私聊，N 条私聊消息 |
| 命令关闭 | 提示 "未启用" |

## 3. 终极方案分析：统一账号体系

### 3.1 当前身份模型

```
lottery_entries
  ├── identityType: "email"    → identityValue: "user@example.com"   → ✅ Web 可访问
  ├── identityType: "qq"       → identityValue: "123456789"          → ❌ 无 Web 访问
  └── identityType: "telegram" → identityValue: "987654321"          → ❌ 无 Web 访问

users 表
  ├── email: "user@example.com" (已验证)
  └── authIdentities
        └── provider: "cf-auth", providerUserId: "..." (现有 IdP 绑定)

authIdentities 当前只支持 cf-auth，qq/telegram 不在此表
```

### 3.2 根本问题

QQ/Telegram 用户在 `users` 表中没有对应记录，依赖 `lotteryEntries.identityType/value` 作为唯一身份标识：

1. **无法跨平台关联**：同一人通过 email 参与 + QQ 群参与，被视为两个独立用户
2. **无法登录 Web 端**：Web 页面只接受 email+OTP 或 JWT（cf-auth），QQ/Telegram 用户无法登录
3. **卡密只能通过私聊投递**：没有 Web 端查看入口，私聊失败后 `/我的卡密` 是唯一兜底
4. **无法管理个人资料**：无修改密码、查看历史等功能

### 3.3 终极方案：三端平等身份体系

**核心思想**：将 `users` 表作为统一身份锚点，email、QQ、Telegram 都是登录方式（authentication method），共享同一个 `userId`。

```
users
  ├── id: "uuid-1"
  └── authIdentities (扩展 provider 范围)
        ├── provider: "email",     providerUserId: "user@example.com"  (现有)
        ├── provider: "cf-auth",   providerUserId: "..."              (现有)
        ├── provider: "qq",        providerUserId: "qq_123456789"     (新增)
        └── provider: "telegram",  providerUserId: "tg_987654321"     (新增)

lottery_entries
  └── identityType: "user_id" → identityValue: "uuid-1"  (统一身份)
```

### 3.4 实施路径

#### Phase A（当前 / 已实现）：`/我的卡密` 命令

- 卡密私聊重发兜底，解决 P0 闭环断裂
- 不涉及账号体系改动

#### Phase B（已实现）：QQ/Telegram 身份关联到 `users` 表

**设计决策**：Phase B 不做 `lotteryEntries.identityType` 迁移（保持 `"qq"/"telegram"`），
避免破坏存量参与记录的 `UNIQUE(tenantId, drawId, identityType, identityValue)` 约束。
`users` 表作为旁路关联，为 Phase C（Web 登录）提供身份锚点。

**实现方式：**
- 新增 `provisionPlatformUser` 函数（`src/services/platform/user-provision.ts`）
- 平台入站时（`inbound.ts`），调用 `provisionPlatformUser` 确保 `users` + `authIdentities` 记录存在
- 若已有记录，幂等返回同一 `userId`；若无，自动创建 `users` 行
- 使用 `OAUTH_PASSWORD_PLACEHOLDER` 作为密码（不可密码登录）
- 失败时降级（不阻断命令执行），`userId` 留空

**`PlatformCommandUser` 类型**：新增可选 `userId` 字段，供命令服务做跨平台关联。
命令服务仍以 `identityType + identityValue` 为主键（向后兼容）。

**效果：**
- `users` 表对所有 QQ/Telegram 用户有记录
- `authIdentities` 新增 `provider: "qq"/"telegram"` 条目
- `lotteryEntries` 保持原有 `identityType`，无迁移成本
- Web 登录（Phase C）可通过 `authIdentities` 找到 `users.id`

#### Phase C（中期）：Web 端 QQ/Telegram 登录入口

- QQ 登录：通过 QQ OAuth 2.0 / QR 码扫码，或群内 Bot 发送临时链接
- Telegram 登录：通过 Telegram Login Widget / Bot 内发送验证码
- 登录后使用统一 `JWT.sub = users.id`（与 cf-auth 流程一致）
- Web 端可查看卡密、参与记录、管理个人资料

#### Phase D（远期）：跨平台身份合并

- 同一 `users.id` 可绑定多个 provider（email + qq + telegram）
- 参与记录统一，排行榜、邀请归因等跨平台计算
- 卡密可随时在 Web 端查看，私聊仅作为即时通知

### 3.5 架构影响

| 维度 | 当前 | 终极方案 |
|------|------|----------|
| `authIdentities.provider` | `cf-auth` 限定 | `email`, `qq`, `telegram`, `cf-auth` |
| `lotteryEntries.identityType` | `email`/`qq`/`telegram` | 统一为 `user_id`（逐步迁移） |
| Web 登录 | email+OTP 或 cf-auth | email+OTP + QQ OAuth + Telegram Login |
| 卡密查看 | 私聊 / Web 页面（email 用户） | 私聊 + Web 页面（所有用户） |
| 用户管理 | 无用户中心 | 统一用户中心 |

### 3.6 风险与注意事项

- **安全性**：QQ/Telegram 身份的 `providerUserId` 来自平台消息，需确保不可伪造（入站鉴权 + 平台级 secret）
- **隐私**：`users.email` 对 QQ/Telegram 用户可为空，不影响核心功能
- **迁移**：存量 `lotteryEntries` 的 `identityType = "qq"/"telegram"` 不能一次性迁移到 `user_id`，需渐进式过渡
- **并发**：`provisionIdpUser` 模式已支持并发场景下的幂等处理（`authIdentities` UNIQUE 约束 + 重试），可复用
