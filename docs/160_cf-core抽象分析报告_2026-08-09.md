## 三、核心发现 — 重复代码模式

### 3.1 高优先级（安全/正确性风险）

#### 🔴 #1: JWT 认证中间件 + RBAC 重复

**涉及项目**：cf-lottery (`src/middleware/auth.ts`)
**cf-core 现状**：只有 `createAdminAuth`（静态 Token 认证），没有 JWT + 租户 RBAC 中间件

cf-lottery 的 `middleware/auth.ts` 包含：
- `requireAuth` — JWT 验证 + 用户状态检查
- `requireTenantMember` — 租户成员角色检查（owner/admin/viewer）
- `requirePlatformMember` — 平台运营角色检查
- `signJwt` / `verifyJwt` — JWT 签名/验证

这些逻辑在 cf-auth 和 cf-shop 也有类似需求，但实现不同。cf-core 虽然已有 `auth/jwt` 提供 JWT 签名/验证，但缺少**完整的认证中间件链路**。

**建议**：将 JWT 认证中间件（含租户 RBAC）抽象到 cf-core，提供：
- `createJwtAuth(options)` — 返回 requireAuth 中间件工厂
- `createTenantMemberGuard(allowedRoles)` — 租户角色守卫
- `createPlatformMemberGuard(allowedRoles)` — 平台角色守卫

#### 🔴 #2: DB 级限流（原子 INSERT 模式）重复

**涉及项目**：cf-lottery (`src/lib/rate-limit.ts`)、cf-auth (`src/lib/rate-limit.ts`)
**cf-core 现状**：`DbRateLimiter` 使用 `rateLimitWindows` 表（复合主键 + 窗口计数），与被分析项目的 `rate_limit_log` 表 + 原子 INSERT 模式完全不同

两个项目都使用 `rate_limit_log` 表 + 原子 `INSERT ... SELECT WHERE COUNT < limit` 模式，代码几乎完全一致。

**建议**：将 `checkDbRateLimit` + `cleanExpiredRateLimits` 抽象到 cf-core，作为 `DbAtomicRateLimiter` 或扩展现有 `DbRateLimiter`

#### 🔴 #3: 数据库事务 + SQLITE_BUSY 退避重复

**涉及项目**：cf-lottery (`src/db/client.ts`)、cf-core (`src/db/connection.ts`)
**两者实现不同**：cf-lottery 的 `withDbTransaction` 更健壮（更多 BUSY 模式、可配置重试次数和延迟），cf-core 的版本较简单

**建议**：统一到 cf-core 的 `withDbTransaction`，采用 cf-lottery 的更完善版本

### 3.2 中优先级（减少重复，降低维护成本）

#### 🟡 #4: 有界并发执行工具 (`runBounded`)

**涉及项目**：cf-lottery (`src/lib/concurrency.ts`)
**用途**：邮件发送、Webhook 投递等场景的有界并发
**纯工具**：无业务依赖，可直接提取到 cf-core

**建议**：提取到 `@usethink/cf-core/concurrency` 或 `@usethink/cf-core/utils`

#### 🟡 #5: HTTP 响应封装 (`ok`/`fail`/`getDb`/`safeJsonBody`)

**涉及项目**：cf-lottery (`src/lib/http.ts`)、cf-auth (`src/lib/http.ts`)
**cf-core 现状**：已有 `ok`/`fail` 但签名不同（cf-core 的 fail 返回 `{ ok: false, error }`，项目层返回 `{ ok: false, message, error }`）

**原因**：项目层需要在 `ok`/`fail` 中绑定 `AppEnv` 类型，而 cf-core 的函数是泛型的。这导致每个项目都有一层薄壳。

**建议**：cf-core 的 `ok`/`fail` 已经够用，但需要解决类型绑定问题。考虑提供 Hono 中间件版的 `honoOk`/`honoFail` 或维持现状（薄壳成本低）。

#### 🟡 #6: 平台适配层 (`getEnv`/`getClientIp`/`waitUntil`)

**涉及项目**：cf-lottery (`src/lib/platform.ts`)、cf-auth (`src/lib/platform.ts`)
**cf-core 现状**：已有 `getEnv`/`waitUntil`/`getClientIp`，但实现略有差异

cf-lottery 的 `getClientIp` 有 `TRUST_CF_CONNECTING_IP` 测试开关，cf-auth 的 `getClientIp` 有 `TRUST_PROXY_HEADERS`，两者策略不同。`getEnv` 的回退逻辑也不同。

**建议**：统一到 cf-core 的 `platform`，通过配置选项处理差异，或者维持现状（策略差异是业务需求的反映）。

#### 🟡 #7: 审计日志 (`writePlatformAudit` vs `writeAdminAudit`)

**涉及项目**：cf-lottery (`src/services/admin/platform-audit.ts`)
**cf-core 现状**：`writeAdminAudit` 写入 `admin_audit_logs` 表

cf-lottery 的 `writePlatformAudit` 写入 `audit_logs` 表（不是 `admin_audit_logs`），且字段不同。

**建议**：cf-lottery 应迁移到 `writeAdminAudit`（使用 `admin_audit_logs` 表），或 cf-core 扩展 `writeAdminAudit` 支持更多使用场景。

### 3.3 低优先级（可做可不做）

#### 🟢 #8: CSP 安全头生成

**涉及项目**：cf-shop (`src/lib/csp.ts`)
**用途**：`buildCsp`/`createCspNonce`/`injectCspNonce`
**cf-core 现状**：`buildSecurityHeaders` 在 `security.ts` 中已有，但 CSP 部分较弱

#### 🟢 #9: 公共 Slug 生成

**涉及项目**：多个项目都需要生成公开 slug
**cf-core 现状**：无

#### 🟢 #10: OAuth RP Client

**涉及项目**：cf-lottery (`src/lib/cf-auth-oauth.ts`)
**用途**：cf-auth OAuth 客户端（授权码 + PKCE 流程）
**可抽象性**：低，强绑定 cf-auth 的实现

## 五、执行建议

### 原则
1. **不要同时改多个项目**：一次只提取一个函数，先提取到 cf-core，再逐一更新各消费方
2. **保持向后兼容**：cf-core 新增导出路径，不删除/修改现有路径
3. **项目层保留薄壳**：即使提取到 cf-core，项目层可以保留 `re-export` 薄壳（如 `crypto-compare.ts`），避免全仓改 import
4. **先测试后发布**：cf-core 发布前运行 `npm run prepublishOnly`（type-check + test + verify:boundaries）

### 分阶段执行

#### Phase 1 — 安全优先（高优先级，需逐个评审）
1. 将 cf-lottery 的 `checkDbRateLimit`/`cleanExpiredRateLimits`（原子 INSERT 模式）提取到 cf-core
2. 将 cf-lottery 的 `withDbTransaction`/`isSqliteBusyError` 提取到 cf-core
3. 在 cf-core 中新增 JWT 认证中间件工厂（含租户 RBAC）

#### Phase 2 — 减少重复（中优先级）
4. 提取 `runBounded` 到 cf-core
5. 统一平台适配层（`getEnv`/`getClientIp`/`waitUntil`）
6. 统一审计日志入口

#### Phase 3 — 锦上添花（低优先级）
7. CSP 安全头模块
8. 公共 Slug 生成工具

### 禁止事项
- **不要把业务表 schema 提取到 cf-core**（如 lottery_draws, prizes 等）
- **不要把路由定义提取到 cf-core**（路由是项目特有的）
