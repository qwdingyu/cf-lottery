# 134 营销方案落地差距分析与整改建议

> 日期：2026-08-07
> 关联：docs/132 QQ群营销方案、docs/131 秒杀直付方案、docs/130 历史闪购导流方案
> 问题：「限时抢购(导流)」活动既然是抢购，为什么连价格都没有，商品都没有，抢购什么呢？和支付怎么对接的？
> 状态更新：P0 已落地，详见 docs/136。
> 边界校正：限时抢购已在 `cf-lottery` 中形成身份、名额、支付、回调、发卡闭环；`cf-shop`、淘宝、咸鱼或其他商城只等价为外部导流目标，不是主交易链路。

## 1. 现状分析

### 产品能力已实现但入口不直观

**支付闭环已在代码中完整实现**（docs/133 审查通过）：
- `flashSale.priceCents`：价格配置
- `flashSale.paymentRequired`：直付开关
- `flashSale.currency`：币种
- `flashSale.title`：秒杀商品标题
- 支付配置：`tenant_configs.providers`（L2 后台 `AdminPaymentConfig.vue`）
- 订单系统：`payment_orders` + 回调发卡
- 公开页：`paymentRequired` 时显示「去支付」按钮、二维码、轮询、卡密展示

**当前产品边界**：
- `cf-lottery`：活动内商品名、展示图、价格、库存、场次、名额锁定、EasyPay/ZPay 支付、回调与卡密交付。
- 外部商城：仅在 `paymentRequired=false` 的外部承接型活动中作为 `productLink` / `promotion_config.destination`，地位与淘宝、咸鱼等第三方链接相同。
- `cf-shop`：不是限时抢购主链路依赖，不应把商品表、SKU、购物车、订单域复制或耦合进本项目。

### 运营者的体验断点

| 132 方案期望 | 当前产品形态 | 差距 |
| --- | --- | --- |
| **免费大转盘 + 付费秒杀的组合营销方案** | 运营需手动创建 2 个独立活动，各自配置，手动关联 | **缺「营销方案模板」或引导创建流程** |
| **限时抢购活动自带商品和价格** | P0 后 `flash-sale-rush` 默认启用直付路径，但价格仍需运营填写后才能发布 | **发布前必须校验 priceCents、支付渠道和卡密码池**，避免再次出现“空抢购壳” |
| **配置即发布** | 直付需要额外配置：① 开启 paymentRequired ② 填 priceCents ③ 在 `AdminPaymentConfig.vue` 配支付渠道 ④ 导入卡密 ⑤ 发布预检 | **5 个分散步骤**，零引导 |
| **秒杀倒计时+进度+支付按钮一体化** | 公开页 `FlashSaleGame` 显示进度/倒计时，但「去支付」需要前端按 `paymentRequired` 动态渲染 | 已实现 ✓ |
| **免费→付费的转化钩子** | 无内置机制 | **缺「免费额度告急」提示** |

### 根本原因

**132 方案是「营销专家」设计的完整漏斗**（免费引流→价值教育→秒杀促成交），但 cf-lottery 当前只提供了**原子能力拼装**（转盘/闪购/支付/卡密），没有提供**方案模板**。运营者相当于被给了一盒工具但没有说明书。

## 2. 差距细节

### 2.1 配置入口深

创建「限时抢购（导流）」模板 → 活动编辑页 → 展开「增长配置」→ 展开「秒杀体验壳」→ **勾选 `paymentRequired`** → 才显示价格/币种/商品标题输入框。

### 2.2 默认值已修复，仍需发布门禁兜底

P0 后 `flash-sale-rush` 模板已经默认启用秒杀壳和直付路径：

```ts
defaults: {
  activityKind: "claim",
  experienceType: "flash_sale",
  enableFlashSale: true,
  flashSalePaymentRequired: true,
  flashSalePriceCents: null,
}
```

`flashSalePriceCents=null` 是刻意保留的运营必填状态，避免模板写死假价格。发布预检必须继续阻断未填写 `priceCents`、未启用 EasyPay/ZPay、卡密码池不足等情况。

### 2.3 分散的配置路径

运营完成一次「付费 Token 秒杀」需要依次操作：
1. 创建活动（flash-sale-rush）
2. 编辑活动 → 增长配置 → 秒杀壳 → 开启 `paymentRequired` → 填价格
3. 前往 `/admin/payment-config` 配置支付渠道（当前主力为 EasyPay/ZPay）
4. 导入卡密（`prize_codes`）
5. 发布

这些配置**跨越 3 个页面**（活动编辑 / 支付设置 / 奖品卡密），零引导、零校验提示。

## 3. 整改建议（按 ROI 排序）

### P0：修复模板默认值（立即）

已执行：
- `flash-sale-rush` 改为「限时抢购」，默认启用商品/导流配置与秒杀壳。
- 公开页新增商品化抢购卡，直付价从 `flashSale.priceCents` 来，导流展示价从 `productLink.price` 来。
- 导流秒杀没有安全购买链接时，发布预检从 warning 升级为 error。

**效果**：运营创建闪购活动后，商品、展示价格、场次、名额和支付/导流差异都在主配置路径中可见，不再是“无价格、无商品”的空抢购壳。

### P1：配置步骤串联（1-2 天）

已部分执行：
- 在活动编辑页的 flashSale 直付区域加入「直付发布清单」，前置提示商品名称/订单标题、支付金额、名额、直付开关、唯一卡密奖品。
- 增加「去支付设置」「去准备卡密」直达入口，减少活动编辑 / 支付设置 / 奖品卡密之间来回跳的断点。
- 清单只做前端提示，不伪造真实支付配置或码池库存；最终仍以服务端发布预检为准。

发布预检已在 payment-check 中实现（priceCents 校验、卡密覆盖校验、支付配置校验）。当前前端清单解决的是“发布前看见路径”，但发布失败后的错误项逐条跳转仍可继续细化。

### P2：提供「营销方案」一键创建（2-3 天）

新增「Token 营销组合」模板：
```
一键创建：
  ☑ 免费大转盘（activityKind=lottery, experienceType=wheel, 免费Token卡密）
  ☑ 付费秒杀（activityKind=claim, flashSale, paymentRequired, priceCents）
  ☑ 自动生成转盘→秒杀的导流链接
  ☑ 免费额度梯度预设（每日限量 N 份）
```
模板创建后，运营只需填**档位和价格**即可发布。

### P3：公开页转化钩子（1 天）

- 免费 Token 用完后，转盘结果区/CTA 显示「免费额度已用完？限时秒杀补货」
- 秒杀页倒计时结束前 1 分钟，显示「即将开抢」预热状态
- 这些是前端体验优化，后端已有能力

## 4. 总结

**用户痛点**：「抢购」活动缺价格/商品/支付对接——功能**已实现但入口太深、默认值误导、配置路径分散**。产品形态是「原子能力拼装」，132 方案需要的是「方案模板」。

**整改优先级**：P0(模板默认值,30 分钟)→ P1(配置串联,1 天)→ P2(营销方案一键创建,2 天)→ P3(转化钩子,1 天)。

**结论**：代码能力不是瓶颈，**产品化 layer** 是差距——把分散的 5 个配置步骤收敛为一个「Token 闪购」模板，让运营者 5 分钟上架，而不是 5 个页面来回跳。
