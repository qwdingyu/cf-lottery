# 运营管理后台兑换码系统设计方案

> 文档编号：020
> 创建时间：2026-08-01
> 定位：平台运营者（非 SaaS 租户）向终端用户销售活动额度
> 使用场景：Telegram 社群、Token 中转站、LDXP 宣传、活动策划

---

## 一、核心问题分析

### 1.1 要解决的核心问题

```
运营者（平台方）→ 生成兑换码 → 卖给终端用户 → 终端用户兑换 → 获得活动额度
```

**关键问题：** 按什么维度限制？活动次数？参与人数？还是时间？

### 1.2 三种变现模式的对比

| 模式 | 适合谁 | 用户接受度 | 运营复杂度 | 推荐度 |
|:----:|--------|:----------:|:----------:|:------:|
| **按活动次数** | 偶尔办活动的用户 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | **首选** |
| **按参与人数** | 大型活动运营者 | ⭐⭐⭐⭐ | ⭐⭐⭐ | 次选 |
| **按月收费** | 高频运营者 | ⭐⭐⭐ | ⭐⭐⭐⭐ | 补充 |
| **混合模式** | 所有用户 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | **最优** |

### 1.3 使用场景分析

#### 场景 A：Telegram 社群运营者

**特征：** 每周办 1-2 次抽奖，每次 50-200 人参与，奖品是 USDT 或 Token

**需求：**
- 快速创建活动，不关心品牌
- 低成本，愿意为单次活动付费
- 不需要复杂的统计

**最适合：** 按活动次数收费（5 次/10 次/20 次套餐）

#### 场景 B：Token 中转站

**特征：** 不定期举办大型活动，每次 500-5000 人参与，用于宣传 Token

**需求：**
- 需要大容量参与名额
- 活动频次低但单次规模大
- 需要导出中奖名单做空投

**最适合：** 按参与人数收费（500/1000/5000 人套餐）

#### 场景 C：LDXP 宣传方

**特征：** 配合项目上线做营销活动，每次 200-1000 人

**需求：**
- 需要品牌露出
- 需要导流到外部链接
- 活动周期短，集中爆发

**最适合：** 混合模式（活动次数 + 参与人数）

#### 场景 D：活动策划公司

**特征：** 为多个客户办活动，每月 10-50 场

**需求：**
- 需要团队协作（多成员）
- 需要白标/品牌定制
- 需要导出数据

**最适合：** 按月收费 + 白标附加

## 二、推荐方案：混合额度模型

### 2.1 模型设计

```
每个租户拥有两个独立额度：
┌─────────────────────────────────────────────────────────────────┐
│  活动次数额度（activity_quota）   │  参与人数额度（participant_quota） │
│  每次创建活动消耗 1               │  每个参与者消耗 1                  │
│  可叠加购买                       │  可叠加购买                       │
└─────────────────────────────────────────────────────────────────┘
```

**为什么是两个维度而不是一个？**

| 维度 | 限制 | 用户行为 |
|------|------|---------|
| 仅活动次数 | 用户创建大量活动但没人参与 | 浪费 |
| 仅参与人数 | 用户只办一个活动但拉 10 万人 | 服务器压力 |
| **两者结合** | 既限制活动数量，又限制单活动规模 | 最合理 |

### 2.2 套餐设计

| 套餐 | 活动次数 | 单活动参与上限 | 月费 | 适用场景 |
|:----:|:--------:|:-------------:|:----:|---------|
| 免费 | 3 次 | 100 人 | ¥0 | 体验试用 |
| 基础 | 10 次 | 500 人 | ¥49 | Telegram 社群 |
| 标准 | 30 次 | 2000 人 | ¥149 | Token 中转站 |
| 专业 | 100 次 | 10000 人 | ¥499 | LDXP 宣传 |
| 企业 | 不限 | 50000 人 | ¥1999 | 活动策划公司 |

### 2.3 兑换码设计

```typescript
// 兑换码数据结构
type RedemptionCode = {
  id: string;           // 唯一 ID
  code: string;         // 兑换码（如：LUCKY-2026-A1B2C3）
  plan: string;         // 套餐标识（basic/standard/pro/enterprise）
  activityQuota: number;  // 额外活动次数（如 10）
  participantQuota: number; // 额外参与人数（如 500）
  durationDays: number; // 有效天数（如 30）
  maxUses: number;       // 最大使用次数（通常为 1）
  usedCount: number;     // 已使用次数
  status: 'active' | 'used' | 'expired';
  createdAt: string;
  expiresAt: string;
}
```

### 2.4 兑换流程

```
运营者生成兑换码（管理后台）
  ↓
兑换码发给终端用户（Telegram/微信/邮件）
  ↓
用户在平台输入兑换码
  ↓
系统验证：未过期、未使用、有效
  ↓
扣减额度：活动次数 + 参与人数
  ↓
更新租户套餐和额度
  ↓
兑换成功，用户可创建活动
```

## 三、数据模型与 API 设计

### 3.1 数据库表

```sql
-- 兑换码表
CREATE TABLE redemption_codes (
  id TEXT PRIMARY KEY,
  code TEXT NOT NULL UNIQUE,        -- 兑换码，如 LUCKY-XXXX-XXXX
  plan TEXT NOT NULL,               -- 套餐标识
  activity_quota INTEGER NOT NULL DEFAULT 0,   -- 额外活动次数
  participant_quota INTEGER NOT NULL DEFAULT 0, -- 额外参与人数
  duration_days INTEGER NOT NULL DEFAULT 30,   -- 有效天数
  max_uses INTEGER NOT NULL DEFAULT 1,         -- 最大使用次数
  used_count INTEGER NOT NULL DEFAULT 0,       -- 已使用次数
  status TEXT NOT NULL DEFAULT 'active',        -- active/used/expired
  created_at TEXT NOT NULL,
  expires_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

-- 兑换记录表
CREATE TABLE redemption_records (
  id TEXT PRIMARY KEY,
  code_id TEXT NOT NULL,             -- 关联的兑换码
  tenant_id TEXT NOT NULL,           -- 兑换的租户
  redeemed_at TEXT NOT NULL,         -- 兑换时间
  activity_quota_granted INTEGER NOT NULL DEFAULT 0,  -- 获得的额外活动次数
  participant_quota_granted INTEGER NOT NULL DEFAULT 0 -- 获得的额外参与人数
);
```

### 3.2 管理端 API

| 端点 | 方法 | 说明 |
|------|------|------|
| `/api/admin/redemption-codes` | GET | 兑换码列表 |
| `/api/admin/redemption-codes` | POST | 生成兑换码 |
| `/api/admin/redemption-codes/:id` | PATCH | 更新兑换码状态 |
| `/api/admin/redemption-codes/:id` | DELETE | 删除兑换码 |
| `/api/admin/redemption-codes/redeem` | POST | 兑换（租户侧） |
| `/api/admin/redemption-codes/stats` | GET | 兑换统计 |

### 4.3 兑换码生成流程

```text
运营者选择套餐 → 填写备注 → 系统生成唯一码 → 可批量生成（最多 100 个）
→ 导出 CSV → 发给终端用户
```

### 4.4 兑换码兑换流程

```text
终端用户注册/登录 → 进入"兑换中心" → 输入兑换码 → 系统验证 → 额度生效
```

## 六、与现有套餐系统的集成

### 6.1 当前套餐系统

当前 `tenants` 表已有 `plan` 字段，`PLAN_LIMITS` 定义了每个套餐的额度。兑换码系统需要扩展：

```typescript
// 当前：套餐固定，不可扩展
const PLAN_LIMITS = {
  free: { maxActivities: 10, maxParticipantsPerActivity: 200 },
  pro: { maxActivities: 200, maxParticipantsPerActivity: 5000 },
};

// 扩展后：兑换码可叠加额外额度
// tenants 表新增字段：
// extra_activity_quota: number  // 兑换码额外赠送的活动次数
// extra_participant_quota: number // 兑换码额外赠送的参与人数
```

### 6.2 额度计算逻辑

```typescript
function getRemainingQuota(tenant: Tenant): { activities: number; participants: number } {
  const planLimits = PLAN_LIMITS[tenant.plan] || PLAN_LIMITS.free;
  // 基础额度 + 兑换码额外额度 - 已使用额度
  return {
    activities: (planLimits.maxActivities || 0) + (tenant.extraActivityQuota || 0) - tenant.usedActivityCount,
    participants: (planLimits.maxParticipantsPerActivity || 0) + (tenant.extraParticipantQuota || 0),
  };
}
```

### 6.3 动态套餐额度管理（2026-08-01 补充）

**`PLAN_LIMITS` 不再只能硬编码。** 平台运营者可在 `/admin/config` 的「套餐额度」Tab 中动态修改每个套餐的参数：

| 配置项 | 说明 | 默认值 | 0 的含义 |
|--------|------|:------:|:--------:|
| `plan_free_max_activities` | Free 套餐最大活动数 | 10 | 不限 |
| `plan_free_max_participants_per_activity` | Free 单活动参与上限 | 200 | — |
| `plan_pro_max_activities` | Pro 套餐最大活动数 | 200 | 不限 |
| `plan_pro_max_participants_per_activity` | Pro 单活动参与上限 | 5000 | — |
| `plan_team_max_activities` | Team 套餐最大活动数 | 1000 | 不限 |
| `plan_team_max_participants_per_activity` | Team 单活动参与上限 | 20000 | — |
| `plan_enterprise_max_activities` | Enterprise 套餐最大活动数 | 0(不限) | 不限 |
| `plan_enterprise_max_participants_per_activity` | Enterprise 单活动参与上限 | 100000 | — |

**读取优先级：** `system_config` 表 → 硬编码 `PLAN_LIMITS` 默认值。未在系统配置中设置的套餐项继续使用硬编码默认值。

**0 值语义：** 只有 `*_max_activities` 的 0 表示不限；`*_max_participants_per_activity` 必须大于 0。原因是单活动容量是公开参与热路径的保护阈值，不能用 0 表达不限，否则容易把活动容量误配置成 0。

**影响范围：** 修改后即时生效，影响所有使用该套餐的租户。创建活动时的校验（`enforceTenantActivityQuota`）会使用最新的动态配置。

## 六-B、基础设施约束与设计决策（2026-08-01 补充）

### 6-B.1 约束来源

本项目的运行环境是 Cloudflare Workers Free + Turso/libSQL Free，有以下硬性限制：

| 约束 | 具体值 | 影响 |
|:----:|--------|------|
| Workers CPU 时间 | 10ms/请求 | 热路径不能做大循环、大 JSON、CSV 拼接、高迭代加密 |
| Turso 行读取 | 5亿行/月 | 全表 COUNT/无索引查询会消耗大量配额 |
| Turso 行写入 | 1000万行/月 | 大促级参与写入、索引过多都会放大消耗 |
| Workers 无持久内存 | 多实例 | 内存限流不可靠，需数据库层保证 |

完整约束分析见 `docs/023_Cloudflare免费版与Turso约束下认证和运行安全方案_2026-08-01.md`。

### 6-B.2 对额度模型的直接影响

**"参与人数额度"的实时校验在热路径中不可行。**

原因：`joinDraw()` 是每次用户参与的热路径。如果每次参与都执行 `SELECT COUNT(*) FROM lottery_entries WHERE tenant_id = ?` 校验租户级累计参与人数，随着 `lottery_entries` 表增长，该查询会放大 Turso rows read、数据库计算和请求等待时间。等待数据库 I/O 不计入 Worker CPU，但会消耗 Turso 免费配额并拖慢公开参与链路。

### 6-B.3 当前设计决策

| 校验点 | 实现方式 | 说明 |
|:------:|---------|------|
| 创建活动时校验活动次数 | 预聚合 `lottery_draws` COUNT（按 `tenant_id` 索引，数据量小） | ✅ 可行 |
| 创建活动时校验单活动参与上限 | 读取 `PLAN_LIMITS`（优先从 `system_config` 读取动态配置，兜底用硬编码默认值）+ `extraParticipantQuota` | ✅ 可行，平台运营者可随时在 `/admin/config` 修改 |
| 用户参与时校验活动容量 | `INSERT ... WHERE (SELECT COUNT(*) WHERE draw_id = ?) < maxParticipants`（按 `draw_id` 索引，范围小） | ✅ 可行 |
| 用户参与时校验租户累计参与人数 | **不做实时校验** | ❌ 热路径禁止 |
| 管理后台显示参与人数用量 | 低频后台统计允许实时 `COUNT`，当前显示累计参与人数 / ∞ | ✅ 已恢复；强额度仍等待快照表 |

### 6-B.4 未来方案：快照表

累计参与人数用量将通过**定时任务预聚合**实现，不在热路径中实时查询：

```text
Cron 定时任务（每 5 分钟）：
  → SELECT tenant_id, COUNT(*) FROM lottery_entries GROUP BY tenant_id
  → 写入 tenant_quota_snapshots 表

管理后台查询快照表：
  → SELECT * FROM tenant_quota_snapshots WHERE tenant_id = ?
  → 仪表盘展示参与人数用量
```

这是一个独立的工程任务，不在当前 MVP 范围内。

### 6-B.5 代码层面约束

在 `lottery-service.ts` 的 `joinDraw()` 函数中：

```
容量检查限定在 draw_id 维度（已按 tenant_id, draw_id 索引）。
禁止添加任何形式的租户级全表 COUNT 或 SUM。
```

在 `AdminDashboardView.vue` 的仪表盘中：

```
参与人数用量卡片可以读取 statsData.usage?.participants 展示后台低频统计值。
快照表接入后，再将展示和强额度判断统一到 statsData.limits?.maxTotalParticipants。
```

## 七、风险与应对

| 风险 | 影响 | 应对方案 |
|------|------|---------|
| 兑换码被盗用 | 经济损失 | 单次使用 + 有效期限制 + 使用记录追踪 |
| 用户刷量 | 服务器压力 | 参与人数上限 + 频率限制 |

| 过期未用 | 收入确认 | 设置有效期，过期自动作废 |

## 九、最终建议

**推荐采用"活动次数 + 参与人数"双维度混合模式。**

理由：
1. 活动次数维度防止"刷活动"行为
2. 参与人数维度防止"超大型活动"压垮服务器
3. 两者结合，既灵活又可控
4. 兑换码可叠加，用户可随时扩容
5. 与现有套餐系统无缝集成

**不推荐单一维度**的原因：
- 仅活动次数：用户可创建 100 个活动但每个只有 1 人参与，无意义
- 仅参与人数：用户可办 1 个活动拉 10 万人，服务器扛不住
- 仅按月收费：低频用户觉得不值，高频用户觉得不够

**定价策略建议：**
- 基础套餐（10 次 + 500 人）：¥49/月 — 覆盖 Telegram 小社群
- 标准套餐（30 次 + 2000 人）：¥149/月 — 覆盖 Token 中转站
- 专业套餐（100 次 + 10000 人）：¥499/月 — 覆盖 LDXP 宣传
- 企业套餐（不限 + 50000 人）：¥1999/月 — 覆盖活动公司
