## 三、架构问题清单（按严重程度排序）

### 3.1 🔴 严重问题

#### 问题 1：平台运营者与租户管理员权限未隔离

**现状：** `adminSystemConfigRoute.use("*", requireAuth)` 只做了认证，没有做授权。任何能登录的管理员都可以访问系统配置 API。

**验证：** `admin-system-config.ts` 第 22 行，确认只有 `requireAuth`。

**影响：** 租户 A 的管理员可以修改平台级别的套餐额度、邮件参数等全局配置。

**根因：** `users` 表没有 `role` 字段，JWT 没有角色声明，没有 `requirePlatformOperator` 中间件。

#### 问题 2：注册流程无法创建平台运营者

**现状：** `auth.ts:141-142` 注册时强制创建租户和 tenant_member。

**影响：** 平台运营者必须通过独立的邀请/初始化流程创建，不能通过公开注册。当前没有这个流程。

**验证：** `auth.ts` 第 141-142 行，确认 `insert(tenants)` 和 `insert(tenantMembers)` 是注册流程的必经步骤。

#### 问题 3：平台运营者缺少 tenantId 导致现有路由不可用

**现状：** 现有路由大量依赖 `tenantId = c.get("tenantId")` 做数据隔离。如果平台运营者没有 tenantId：
- 审计日志路由：`eq(auditLogs.tenantId, tenantId)` → tenantId 为空字符串，看不到任何日志
- 兑换码路由：`eq(redemptionCodes.createdBy, tenantId)` → tenantId 为空字符串，看不到任何兑换码
- 仪表盘路由：`getTenantUsage(db, tenantId)` → tenantId 为空字符串，查询失败

**验证：** admin-lottery.ts 第 808、1419、1439 行确认。

**影响：** 平台运营者不能简单地"没有 tenantId"，需要一种特殊的 tenantId 或修改所有相关路由。

### 3.2 🟡 中等问题

#### 问题 4：前端侧边栏混用 L2 和 L3 功能

**验证：** `AdminLayout.vue:104-111` 菜单数组包含系统配置、审计日志、兑换码（L3）与活动管理、奖品管理（L2）。

**影响：** L2 用户可以看到 L3 的入口，点击后可能因后端权限不足而报错，暴露平台功能入口。

#### 问题 5：审计日志 API 按 tenantId 过滤，平台运营者无法查看全量

**验证：** `admin-lottery.ts:808` `eq(auditLogs.tenantId, tenantId)`。

**影响：** 即使平台运营者能登录，也只能看到自己所在租户的日志，无法做全局审计。

#### 问题 6：兑换码 API 按 tenantId 过滤，平台运营者无法管理全量

**验证：** `admin-lottery.ts:1419` `eq(redemptionCodes.createdBy, tenantId)`。

**影响：** 兑换码管理本应是平台运营者功能，但当前只能看到本租户的兑换码。

### 3.3 ⚪ 轻微问题

#### 问题 7：仪表盘只显示本租户统计

**验证：** `admin-lottery.ts:1031-1087` `/api/admin/stats` 按 `tenantId` 过滤。

**影响：** 平台运营者无法看到平台全局统计。

#### 问题 8：没有平台运营者的成员管理界面

**影响：** 无法添加/移除平台运营者，无法管理平台运营者权限。

## 五、改进方案（分阶段实施）

### 5.1 第一阶段：安全修复（立即实施，约 50 行代码）

#### 修复 1：users 表增加 role 字段

```sql
ALTER TABLE users ADD COLUMN role TEXT NOT NULL DEFAULT 'tenant_admin';
-- role 取值范围：'platform_operator' | 'tenant_admin'
```

**文件：** `src/db/schema.ts` — 修改 `users` 表定义

#### 修复 2：JWT 增加 role 声明

```typescript
// src/routes/auth.ts — 登录成功后签发 JWT 时加入 role
const [user] = await db.select().from(users).where(eq(users.username, username)).limit(1);
const token = await signJwt({
  sub: user.id,
  tenantId,
  role: user.role,  // 新增：'platform_operator' | 'tenant_admin'
}, jwtSecret, 7 * 86400);
```

#### 修复 3：新增 requirePlatformOperator 中间件

```typescript
// src/middleware/auth.ts — 新增平台运营者权限中间件
export async function requirePlatformOperator(c: Context<AppEnv>, next: Next) {
  // 先通过 requireAuth 认证
  return requireAuth(c, async () => {
    const role = c.get("role") as string;
    if (role !== "platform_operator") {
      return c.json({ ok: false, message: "无权限，仅平台运营者可操作" }, 403);
    }
    await next();
  });
}
```

**注意：** `requireAuth` 需要同时注入 `role`。当前 `requireAuth` 只注入 `userId` 和 `tenantId`，需要增加 `c.set("role", payload.role || "tenant_admin")`。

#### 修复 4：敏感路由增加 requirePlatformOperator

```typescript
// src/routes/admin-system-config.ts — 系统配置仅平台运营者
adminSystemConfigRoute.use("*", requirePlatformOperator);

// src/routes/admin-lottery.ts — 兑换码路由仅平台运营者
adminLotteryRoute.use("/redemption-codes*", requirePlatformOperator);
```

**审计日志路由的处理：** 审计日志比较特殊——L2 租户管理员应能看到本租户的日志，L3 平台运营者应能看到所有租户的日志。所以不能简单用 `requirePlatformOperator` 一刀切。需要改为：

```typescript
// 审计日志路由：按角色决定是否按 tenantId 过滤
adminLotteryRoute.get("/logs", async (c) => {
  const db = getDb(c);
  const tenantId = c.get("tenantId") as string;
  const role = c.get("role") as string;
  
  const conditions: any[] = [];
  // 平台运营者查看所有日志，租户管理员只看本租户
  if (role !== "platform_operator") {
    conditions.push(eq(auditLogs.tenantId, tenantId));
  }
  // ... 其余查询逻辑
});
```

### 5.2 第二阶段：平台运营者身份体系（短期）

#### 修复 5：平台运营者注册流程

**不能**复用现有注册流程（因为注册会强制创建租户）。需要新增：

```typescript
// 新增路由：POST /api/auth/platform-invite
// 仅现有平台运营者可调用，通过邮箱邀请新平台运营者
// 被邀请者收到验证码，验证后创建用户（role='platform_operator'，不创建租户）

// 新增路由：POST /api/auth/platform-verify
// 验证邀请码，完成注册
```

或者更简单的引导方式：**第一个注册的用户自动成为平台运营者**（通过环境变量 `PLATFORM_INIT_KEY` 或通过数据库 seed 脚本）。

#### 修复 6：平台运营者的 tenantId 处理

**方案对比：**

| 方案 | 优点 | 缺点 | 推荐 |
|:----|------|------|:----:|
| **A：平台运营者使用特殊 tenantId**（如 `__platform__`） | 现有路由不需要修改 tenantId 获取逻辑 | 查询时需要特殊处理 `tenantId = '__platform__'` 的情况 | ❌ 侵入性强 |
| **B：平台运营者没有 tenantId，路由判断** | 语义清晰 | 每个路由都需要检查 tenantId 是否为空 | ⚠️ |
| **C：平台运营者 tenantId 为 null，路由按角色判断** | 语义清晰，与角色绑定 | 需要修改所有 tenantId 使用点 | ✅ **推荐** |

**推荐方案 C 的实现方式：**

```typescript
// 在 requireAuth 中，平台运营者的 tenantId 设为 null
c.set("userId", payload.sub);
c.set("tenantId", payload.role === "platform_operator" ? null : (payload.tenantId || ""));
c.set("role", payload.role || "tenant_admin");

// 路由中按角色判断：
const tenantId = c.get("tenantId") as string | null;
const role = c.get("role") as string;

// 查询条件：平台运营者不限租户，租户管理员限本租户
const conditions = role === "platform_operator" ? [] : [eq(table.tenantId, tenantId)];
```

### 8.2 关键词定义

| 术语 | 定义 |
|:----|------|
| **L1（普通用户）** | 参与公开活动的终端用户，无需登录，不留存 |
| **L2（SaaS 租户管理员）** | 管理本租户活动的管理员，属于某个租户，有 tenant_members 记录 |
| **L3（平台运营者）** | 管理整个 SaaS 平台的运营人员，不隶属于任何租户 |
| **RBAC** | 基于角色的访问控制，通过角色分配权限 |
| **Tenant Isolation** | 租户隔离，不同租户的数据互不可见 |
| **requireAuth** | 当前认证中间件，只验证 JWT 有效性，不区分角色 |
| **requirePlatformOperator** | 待新增的授权中间件，仅在 role='platform_operator' 时放行 |
