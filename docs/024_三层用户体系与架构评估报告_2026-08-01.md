# 三层用户体系与架构评估报告

> 文档编号：024
> 创建时间：2026-08-01
> 最后审查：2026-08-01
> 定位：审查 cf-lottery 作为多租户 SaaS 活动引擎时，平台运营者、租户管理员、普通参与者三层用户体系是否安全、可扩展、可分步实施。
> 审查原则：以当前代码为准；区分已实现事实、目标设计和实施建议；禁止为了平台跨租户能力破坏现有租户隔离。

---

## 一、审查结论

原文判断“当前缺少平台运营者与租户管理员的授权隔离”成立，而且属于上线前必须处理的安全风险。但原文有三处需要修正，否则按文档直接实施会带来灾难：

1. **不能把现有 `/api/admin/*` 改成平台跨租户路由。**
   现有 admin 路由依赖 `tenantId = c.get("tenantId")` 做租户隔离，活动、奖品、成员、Webhook、黑名单等接口都应继续保持租户作用域。平台全局能力应新增 `/api/platform/*`，而不是移除 admin 路由的 `tenantId` 过滤。

2. **不建议近期使用“平台运营者 tenantId = null，然后所有路由按 role 判断”。**
   当前代码大量把 `tenantId` 当作必填字符串传入服务层。直接改成 `null` 会引发空查询、漏过滤、类型漂移和隐藏越权。更安全的做法是：租户路由仍要求 `tenantId`；平台路由单独使用平台授权上下文。

3. **不要只在 `users` 表加一个全局 `role` 就结束。**
   SaaS 最佳实践是把“全局平台权限”和“租户内成员权限”拆开。`tenant_members.role` 只表示租户内角色；平台运营者应使用独立的 `platform_members` 或等价表管理。这样同一个用户未来可以既是某租户 owner，又是平台 support/operator，不会混淆。

最终建议：

```text
不要做重型 RBAC。
采用 RBAC-lite：路由级能力门禁 + 两张成员表 + 代码常量映射。

当前阶段只做止血：
  保护系统配置写入口
  保护额度码生成入口
  修复兑换码并发超发
  现有 /api/admin/* 继续租户隔离

随后再做轻量平台后端：
  /api/platform/tenants            只读分页
  /api/platform/system-config      平台配置
  /api/platform/redemption-codes   平台额度码
  /api/platform/audit-logs         分页审计
```

这个方案的关键是：**把权限判断放在路由入口，不把权限系统做成一个运行时动态查询的产品。**

## 二、当前代码核验

### 2.1 认证与身份

| 事实 | 当前代码 | 结论 |
|------|----------|------|
| JWT 只注入 `userId` 和 `tenantId` | `src/middleware/auth.ts` 中 `requireAuth()` 只 `c.set("userId")`、`c.set("tenantId")` | 已认证，但没有授权 |
| 登录从 `tenant_members` 找租户 | `src/routes/auth.ts` 登录后查询 `tenantMembers.tenantId` 再签 JWT | 一个登录态只绑定一个租户 |
| 注册必然创建租户 | `src/routes/auth.ts` 注册时插入 `tenants` 和 `tenant_members(role="owner")` | 公开注册不能用于创建平台运营者 |
| `users` 表无平台角色 | `src/db/schema.ts` 的 `users` 只有身份和状态字段 | 缺少平台权限模型 |
| `tenant_members.role` 已存在 | `src/db/schema.ts` 中 `tenant_members.role` 默认 `owner` | 只能代表租户内角色 |

### 2.2 路由与权限

| 路由 | 当前保护 | 当前作用域 | 风险判断 |
|------|----------|------------|----------|
| `/api/admin/*` | `requireAuth` | 大多数按 JWT `tenantId` 过滤 | 租户隔离基本成立，但没有 tenant 内角色授权 |
| `/api/admin/system-config` | `requireAuth` | 全局 `system_config` | 高危：任意租户管理员可读写全局配置 |
| `/api/admin/redemption-codes/batch` | `requireAuth` | `createdBy = tenantId` | 高危：任意租户管理员可生成额度码并给自己兑换 |
| `/api/admin/redemption-codes/redeem` | `requireAuth` | 当前租户兑换 | 应保留给租户管理员，不应套平台权限 |
| `/api/admin/logs` | `requireAuth` | 当前租户审计日志 | L2 可看本租户日志是合理的；平台全局日志应走新路由 |
| `/api/system-config/system-config` | 无鉴权 | 只返回公开白名单配置 | 合理，不是平台管理漏洞 |
| `/api/cron/*` | `CRON_SECRET` | 系统维护任务 | 有独立鉴权 |

### 2.3 前端

| 页面 | 当前情况 | 风险 |
|------|----------|------|
| `/admin/config` | 所有登录管理员可见 | 暴露 L3 功能入口，且后端也未拦截 |
| `/admin/redemption-codes` | 所有登录管理员可见 | 可生成额度码，属于实质越权 |
| `/admin/logs` | 所有登录管理员可见 | 当前只看本租户日志，可保留给 L2；平台全局日志应另建 |
| `refreshPublicConfig()` | 请求 `/api/system-config` | 后端实际公开接口是 `/api/system-config/system-config`，保存后同步检查可能误报 |

## 三、三层用户体系定义

### 3.1 L1 普通参与者

职责：

- 访问公开活动页。
- 提交参与信息。
- 查看公开结果或本人结果。

限制：

- 无后台登录态。
- 不应看到租户 ID、内部活动 ID、系统配置、运营数据。
- 所有写入必须通过公开活动规则校验。

### 3.2 L2 SaaS 租户管理员

职责：

- 管理本租户活动、奖品、成员、黑名单、Webhook、API Key。
- 查看本租户仪表盘、活动数据、审计日志。
- 兑换平台发放的额度码。

限制：

- 只能访问自己所属租户。
- 不能修改全局系统配置。
- 不能生成平台额度码。
- 不能查看其他租户数据。

### 3.3 L3 平台运营者

职责：

- 管理平台配置、套餐、兑换码发行、租户状态、用量快照、平台审计、失败投递。
- 查看跨租户运营视图。
- 处理支持工单时可查看指定租户数据，但必须显式选择租户并记录审计日志。

限制：

- 默认不进入租户写路径。
- 不复用普通 `/api/admin/*` 路由绕过租户隔离。
- 跨租户读取优先，写操作必须最小化、显式、可审计。

## 四、推荐权限模型：RBAC-lite，而不是重型 RBAC

### 4.0 为什么不能做重型 RBAC

在 Cloudflare Workers Free + Turso/libSQL Free 前置条件下，以下设计都不适合当前阶段：

| 重型设计 | 风险 |
|----------|------|
| `roles` + `permissions` + `role_permissions` + `user_roles` 全套权限矩阵 | 每个请求需要多表查询或缓存失效设计，复杂度高于当前业务收益 |
| 每个按钮/菜单项都从数据库读取权限 | 增加 Turso rows read，且前端权限不是安全边界 |
| 多租户自定义角色系统 | 会迅速变成 SaaS 权限产品，不符合小而美定位 |
| ABAC/策略表达式引擎 | 规则解释、调试和测试成本高，Workers 免费层不适合在热路径做策略计算 |
| 将权限结果存在 Worker 全局内存 | 多实例不一致，禁用成员后不能保证立即生效 |

当前最优选择是 **RBAC-lite / Capability Gate**：

```text
身份认证：JWT 证明 userId 和当前 tenantId
租户授权：tenant_members 表确认当前用户是否仍属于该租户
平台授权：platform_members 表确认当前用户是否是平台成员
能力判断：代码常量按路由声明，不做数据库权限矩阵
```

资源成本：

| 路径 | 是否增加权限查询 | 原因 |
|------|------------------|------|
| 公开活动页和参与接口 | 否 | L1 无后台权限，不能引入权限查询 |
| 租户后台普通接口 | 可选 1 次 `tenant_members` 索引查询 | 后台低频，换取 JWT 失效/成员移除后的安全性 |
| 平台后台接口 | 1 次 `platform_members` 主键查询 | L3 低频敏感操作，必须数据库确认 |
| 前端菜单 | 读 `/api/auth/me` 一次 | 只改善体验，不作为安全边界 |

因此，这不是完整 RBAC 系统，而是足够轻的路由级授权。

### 4.1 不推荐方案

| 方案 | 不推荐原因 |
|------|------------|
| 只给 `users` 加 `role` | 会把平台角色和租户角色混在一个字段里，未来用户同时属于多个租户或平台团队时会失真 |
| 平台运营者 `tenantId = null` 后让所有路由兼容 | 当前代码到处依赖 `tenantId: string`，改动面大且容易漏过滤 |
| 平台运营者使用特殊租户 `__platform__` | 会污染租户模型，后续统计、配额、审计都要排除特殊租户 |
| 移除 admin 路由的 `tenantId` 过滤 | 直接破坏现有多租户隔离 |
| 只做前端菜单隐藏 | UI 不是安全边界，后端必须拒绝越权请求 |

### 4.2 最小数据模型

只新增一张平台成员表，保留现有租户成员表。不要新增 `permissions`、`role_permissions`、`user_roles` 等矩阵表。

```sql
CREATE TABLE platform_members (
  user_id TEXT PRIMARY KEY,
  role TEXT NOT NULL DEFAULT 'operator',
  status TEXT NOT NULL DEFAULT 'active',
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

建议索引：`user_id` 主键即可。平台成员数量很小，按 `status` 做列表时可以后续再加索引，不需要一开始堆索引增加写入成本。

角色建议：

| 角色 | 权限 |
|------|------|
| `platform_owner` | 管理平台成员、系统配置、套餐、兑换码、租户状态 |
| `platform_operator` | 查看租户、生成兑换码、查看用量和失败投递 |
| `platform_support` | 只读查看指定租户数据，默认不能修改配置和额度 |

租户角色沿用 `tenant_members.role`，只做三类：

| 角色 | 权限 |
|------|------|
| `owner` | 租户内全部管理能力、成员管理、删除/转移敏感操作 |
| `admin` | 活动、奖品、黑名单、Webhook/API Key 管理 |
| `viewer` | 只读查看活动和数据面板，不能创建/修改/删除 |

当前代码里已出现 `operator` 字符串，建议迁移为 `admin` 或在代码常量中把 `operator` 兼容映射到 `admin`，不要长期保留多个同义角色。

### 4.3 路由级能力常量

权限不要存在数据库矩阵里，直接在代码中用常量声明：

```typescript
const TENANT_ROUTE_ROLES = {
  "admin.draw.read": ["owner", "admin", "viewer"],
  "admin.draw.write": ["owner", "admin"],
  "admin.member.write": ["owner"],
  "admin.audit.read": ["owner", "admin"],
} as const;

const PLATFORM_ROUTE_ROLES = {
  "platform.config.write": ["platform_owner"],
  "platform.redemption.write": ["platform_owner", "platform_operator"],
  "platform.tenant.read": ["platform_owner", "platform_operator", "platform_support"],
} as const;
```

这个方案的好处：

1. 不需要多表 join。
2. 权限变更能通过代码审查看到。
3. 测试可以直接覆盖每个敏感路由。
4. 未来真的需要客户自定义角色时，再迁移到权限表，不影响当前 MVP。

### 4.4 中间件建议

中间件建议：

```text
requireAuth
  只验证身份，注入 userId、tenantId

requireTenantMember(requiredRoles?)
  校验 userId 当前仍属于 tenantId
  校验 tenant_members.role
  用于 /api/admin/*

requirePlatformMember(requiredRoles?)
  查询 platform_members
  校验 status = active
  用于 /api/platform/*
```

安全细节：

1. 平台权限不要只信 JWT 中的 role。敏感路由应查询 `platform_members`，这样禁用平台成员后立即生效。
2. JWT 可以携带 `tenantId` 和轻量 `platform` 标记用于 UI，但后端授权以数据库为准。
3. 默认拒绝：没有明确命中的角色和路由能力，一律 403。
4. 平台跨租户操作必须写入审计日志，记录 `actor_user_id`、目标租户、动作、参数摘要。
5. 路由层必须默认拒绝，不能因为缺少 role 就 fallback 到高权限。
6. JWT 中的 platform 标记只能用于前端展示；后端敏感路由必须查 `platform_members`。

### 4.5 登录态建议

保持当前登录模型，不急着做多租户切换：

```text
JWT:
  sub       当前用户
  tenantId  当前租户上下文，用于 /api/admin/*
  iat/exp   签发和过期时间

不建议：
  在 JWT 中塞完整权限列表
  在 JWT 中塞所有 tenant memberships
  在 JWT 中只靠 role 做平台授权
```

需要新增 `/api/auth/me`：

```json
{
  "userId": "u_...",
  "tenant": { "id": "t_...", "role": "owner" },
  "platform": { "role": "platform_operator" },
  "capabilities": [
    "admin.draw.write",
    "platform.redemption.write"
  ]
}
```

`/api/auth/me` 是后台低频接口，可以查询一次 `tenant_members` 和一次 `platform_members`。前端用它渲染菜单，后端路由仍各自校验。

## 五、路由分层设计

### 5.1 保留租户后台路由

`/api/admin/*` 继续代表 L2 租户后台：

| 路由 | 作用域 | 说明 |
|------|--------|------|
| `/api/admin/draws/*` | 当前租户 | 活动管理 |
| `/api/admin/prizes/*` | 当前租户 | 奖品和码池 |
| `/api/admin/members/*` | 当前租户 | 租户成员 |
| `/api/admin/blacklist/*` | 当前租户 | 本租户黑名单 |
| `/api/admin/logs` | 当前租户 | 本租户审计日志 |
| `/api/admin/stats` | 当前租户 | 本租户仪表盘 |
| `/api/admin/redemption-codes/redeem` | 当前租户 | 兑换平台发放的额度码 |

### 5.2 新增平台运营路由

`/api/platform/*` 代表 L3 平台运营后端：

| 路由 | 第一阶段能力 | 资源约束 |
|------|--------------|----------|
| `/api/platform/tenants` | 租户列表、状态、套餐 | 分页，按创建时间/状态索引 |
| `/api/platform/tenants/:id/summary` | 单租户摘要 | 优先读快照，缺失时低频 COUNT 兜底 |
| `/api/platform/system-config` | 全局配置读写 | 替代 `/api/admin/system-config` |
| `/api/platform/redemption-codes` | 额度码生成、列表、统计 | 分页；生成数量上限；审计 |
| `/api/platform/usage-snapshots` | 用量快照读取 | 不扫公开热路径大表 |
| `/api/platform/audit-logs` | 平台级审计查询 | 必须分页和筛选 |
| `/api/platform/webhook-deliveries` | 失败投递查询 | 只读优先，重试需显式确认 |

兼容策略：

- `/api/admin/system-config` 可以临时保留，但必须立刻加 `requirePlatformMember`。
- 新前端逐步切到 `/api/platform/system-config`。
- 平台视角查看租户活动时，不直接复用 `/api/admin/draws` 去掉过滤；应新增平台只读接口或显式“切换到租户上下文”。

## 六、当前必须修复的风险

| ID | 风险 | 严重级别 | 正确修复 |
|----|------|----------|----------|
| R-001 | 任意租户管理员可读写 `/api/admin/system-config` | P0 | 增加平台授权；后续迁移到 `/api/platform/system-config` |
| R-002 | 任意租户管理员可生成兑换码 | P0 | `/redemption-codes/batch` 和平台兑换码列表/统计只允许平台成员 |
| R-003 | 兑换码兑换非原子更新，可能并发超发 | P0 | 使用条件更新：`WHERE id=? AND status='active' AND used_count < max_uses` |
| R-004 | 平台成员身份不存在 | P0 | 新增 `platform_members` 和初始化/邀请流程 |
| R-005 | 平台能力与租户能力混在同一侧边栏 | P1 | 前端按后端返回的 capability 过滤菜单 |
| R-006 | 公共配置刷新路径不匹配 | P1 | 前端改为真实接口或后端增加兼容路由 |
| R-007 | 审计日志缺少平台全局视图 | P2 | 新增 `/api/platform/audit-logs`，不要改租户日志接口 |
| R-008 | 平台统计缺少快照表 | P2 | 建立 `tenant_usage_snapshots`，避免全局实时扫描 |

## 七、分步实施方案

### 7.1 第一阶段：止血，不推翻现有结构

目标：先堵住实质越权，不做大改。

1. 新增 `platform_members` 表和最小初始化流程。
2. 新增 `requirePlatformMember(allowedRoles)`，只用于 L3 敏感路由。
3. 新增 `requireTenantMember(allowedRoles)`，用于 L2 后台路由；先覆盖成员管理、活动写操作、奖品写操作、Webhook/API Key 写操作。
4. `/api/admin/system-config` 增加平台授权，后续迁移到 `/api/platform/system-config`。
5. `/api/admin/redemption-codes/batch`、`/api/admin/redemption-codes`、`/api/admin/redemption-codes/stats` 增加平台授权。
6. `/api/admin/redemption-codes/redeem` 保持租户管理员可用。
7. 兑换码兑换改成条件更新，避免并发超发。
8. 为以上路由补 403 和并发兑换测试。

不做：

- 不新增 `permissions` 表。
- 不新增 `role_permissions` 表。
- 不做每按钮权限配置。
- 不做租户自定义角色。
- 不让平台账号绕过 `/api/admin/*` 的 tenantId 过滤。

### 7.2 第二阶段：平台后端最小闭环

目标：让 SaaS 平台能运营，但不做大而全后台。

1. 新增 `/api/platform/tenants`：分页租户列表、套餐、状态、创建时间。
2. 新增 `/api/platform/redemption-codes`：平台发行和查询兑换码。
3. 新增 `/api/platform/system-config`：替代 admin 系统配置入口。
4. 新增 `/api/platform/audit-logs`：平台审计查询，默认按时间分页，支持 tenantId/action 筛选。
5. 新增 `/api/platform/usage-snapshots`：先定义表和读取接口，后台 Cron 后续补。

资源约束：

- 所有平台列表必须分页，默认 50，最大 200。
- 跨租户统计默认读快照，不在请求内全库 `GROUP BY`。
- 平台导出必须分批，不在 Worker 请求里拼大 CSV。
- 平台接口是后台低频，但仍要记录响应耗时，避免 Turso rows read 失控。

### 7.3 第三阶段：前端体验与权限展示

目标：UI 跟随后端能力，不把 UI 当安全边界。

1. 登录后调用 `/api/auth/me` 返回当前用户的 tenant role、platform role、capabilities。
2. `AdminLayout.vue` 根据 capabilities 渲染菜单。
3. L2 菜单保留活动、奖品、成员、黑名单、租户日志、兑换入口。
4. L3 菜单显示系统配置、平台兑换码、租户列表、平台审计、用量快照。
5. 对无权限页面做 403 空状态，不只依赖路由跳转。

### 7.4 第四阶段：平台跨租户能力

目标：在不破坏租户隔离的前提下提供支持能力。

1. 平台查看某租户详情必须显式带 `tenantId` 参数。
2. 平台写操作默认禁止，必要时用独立接口和审计。
3. 不提供无审计的“静默 impersonation”。
4. 对平台查询增加分页、时间范围和导出限制，避免 Turso rows read 爆炸。

## 九、行业最佳实践对齐

本设计遵循以下原则：

1. **最小权限**：用户只获得完成职责所需的最小能力。
2. **默认拒绝**：未显式授权的请求一律拒绝。
3. **服务端授权**：前端菜单隐藏只用于体验，不能作为安全边界。
4. **职责分离**：平台角色和租户角色分表建模，避免一个字段表达两套权限。
5. **显式跨租户访问**：平台访问租户数据必须通过平台路由、显式 tenantId、审计日志。
6. **渐进迁移**：保留 `/api/admin/*` 租户语义，新建 `/api/platform/*`，避免一次性推翻。

参考：

- OWASP Authorization Cheat Sheet: https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html
- OWASP Access Control: https://owasp.org/www-community/Access_Control

## 十、最终建议

当前文档应作为 P0 安全修复的依据，但实施时必须按下面顺序：

1. 先做 RBAC-lite，不做完整 RBAC。
2. 先加 `platform_members`、`requirePlatformMember()`、`requireTenantMember()`。
3. 先保护系统配置和兑换码生成。
4. 保持现有 `/api/admin/*` 的租户隔离，不做跨租户改造。
5. 再新增 `/api/platform/*` 平台运营后端。
6. 最后做前端菜单和平台仪表盘。

这条路径能保护当前 MVP，不会为了平台化把已有多租户隔离推翻。
